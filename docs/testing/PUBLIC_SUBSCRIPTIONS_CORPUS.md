# Методика испытаний на корпусе публичных подписок (§525)

Корпус — 68 снимков публичных подписочных списков (~20 МБ текста, ~74 000
узлов), закоммиченных в
[`app/test/fixtures/public_subscriptions/`](../../app/test/fixtures/public_subscriptions/README.md).
Он существует, чтобы у подсистемы реестра и разбора была **боевая мера в
числах**: столько-то узлов, столько-то отбраковок таких-то кодов. Синтетические
фикстуры проверяют, что заявленное работает; корпус показывает, что творится в
реальных списках, которых никто не писал под наш парсер.

Запуск — один, из каталога `app/`:

```bash
LX_CORPUS_PUBLIC=1 flutter test test/public_subscriptions                    # прогон + сверка
LX_CORPUS_PUBLIC=1 LX_CORPUS_REPORT=1 flutter test test/public_subscriptions # + report.json/md
LX_CORPUS_PUBLIC=1 LX_CORPUS_UPDATE_EXPECTED=1 flutter test test/public_subscriptions
```

`dart run` не годится: конвейер разбора тянет Flutter (`node_warning.dart` →
l10n → `package:flutter/widgets.dart`), поэтому энтрипоинт один — тест.

## 1. Регрессия реестра при синке контракта

Контракт приезжает из лаунчера (`app/tool/sync_contract.sh`), и правка секции
может тихо перестать читать поле, которое читала.

1. **До синка** — прогон со сверкой: `expected.json` должен совпасть. Не
   совпал — сначала разберитесь с этим, синк тут не при чём.
2. Синк контракта.
3. **После синка** — прогон со сверкой. Диффом тест печатает каждое
   расхождение: `<id>: nodes_total 4456 → 4401`, `<id>: warnings.unknown_key
   12 → 0`.
4. Каждое расхождение получает объяснение, и только потом
   `LX_CORPUS_UPDATE_EXPECTED=1` **отдельным коммитом**, где причина названа в
   сообщении.

**Правило: число узлов не падает без объявленной причины.** Узлов стало
меньше — это дефект, пока не доказано обратное. Законные причины падения
ровно две: реестр научился отбраковывать запись, которую ядро всё равно не
приняло бы (тогда в том же диффе виден рост `dropped.<код>` на ту же
величину), и умерший источник, тело которого выпало из корпуса. Всё прочее —
регрессия.

Рост числа узлов объяснять тоже обязательно: он бывает прогрессом (реестр
научился новой схеме), а бывает тем, что отбраковка перестала срабатывать.

## 2. Паритет с лаунчером

Тот же корпус может гонять Go-раннер лаунчера — общий контракт обязан читать
одни тела одинаково. Читать нужно ровно два файла, и формат у них
устойчивый:

- `app/test/fixtures/public_subscriptions/index.json` —
  `{"schema":1, "subscriptions":[…]}`. Поля записи перечислены в
  [README корпуса](../../app/test/fixtures/public_subscriptions/README.md);
  для прогона нужны `id`, `body_file`, и признак `dead_since` (есть — тела
  может не быть, запись пропускается).
- `bodies/<id>.txt.gz` — тело, gzip. Распаковали → получили сущность ответа
  в том виде, в каком её видит наш `decode()`.

Сравнение — по подпискам, по двум числам: `nodes_total` и карта кодов
(`dropped`, `warnings`). Расхождение в коде при совпавшем числе узлов — тоже
расхождение: значит, стороны по-разному назвали одну и ту же потерю.

Формат нашего результата для сличения — `report.json`, поле `subscriptions[]`:
`{id, nodes_total, by_type, dropped:{код:число}, warnings:{код:число},
coverage:{"протокол|транспорт|security":число}}`.

## 3. Дельты реестра — бэклог

Прогон сам выписывает, чего реестр не знает. Кандидаты берутся из кодов
`uri_param_unknown`, `json_field_unknown`, `unknown_key`,
`scheme_unsupported` в `report.json`.

Разбирать их надо с одной поправкой: **часть «неизвестных» имён — мусор
источника, а не пробел реестра.** В корпусе 24.09.2026 из 9300
`uri_param_unknown` половина (4706) — это `amp;type`, `amp;sni`,
`%3Bpath` и куски телеграм-подписей: провайдер отдал ссылку с
HTML-экранированным `&amp;` или склеил в query своё объявление. Реестру там
вести нечего — это дефект чужого списка. Прежде чем заводить запись, гляньте
в тело: имя вида `amp;<известный параметр>` доказывает поломку источника.

## 4. Обновление снимков

- **Периодичность** — перед синком контракта и по необходимости; календарного
  срока нет: источники живут своей жизнью, и ловить их каждый день незачем.
- **Как** — `dart run tool/public_subs/fetch.dart --refresh` из корня репозитория.
  UA берётся из `app/pubspec.yaml` и повторяет тот, которым представляется
  приложение: панели маршрутизируют тело по UA, и снимок от чужого клиента
  показывал бы не то, что видит LxBox.
- **Снимок один.** Второго каталога с датами нет: история версий живёт в git,
  и `git log -p` по `index.json` отвечает на «когда это изменилось» лучше, чем
  дерево копий.
- **URL умер** — `fetch.dart` ставит записи `dead_since` и **не трогает тело**:
  разбор мёртвого списка остаётся мерой не хуже живого. Ожил — снимок
  перезапишется, `dead_since` надо снять руками. Тела не было вовсе (умер до
  первого снятия) — запись остаётся без `body_file` и прогон её пропускает.
- Обновление снимков почти всегда двигает числа, поэтому идёт **своим
  коммитом**, а `expected.json` — следующим за ним, с «обновление корпуса» в
  причине. Смешивать это с правкой реестра нельзя: в общем диффе не видно,
  что от чего.

## 5. Границы: чего корпус НЕ проверяет и чего с ним нельзя

Корпус — мера **разбора текста**, и только.

Не проверяет:

- **соединение.** Ни один узел не подключается и не пингуется. Живой узел и
  давно мёртвый для корпуса одинаковы;
- **пригодность тела для ядра.** Числа говорят, что разбор дал узел, а не что
  sing-box его примет. Это работа гарда сборки и конформанса;
- **качество серверов.** Узлы чужие, за их работу не отвечает никто.

Нельзя:

- **запускать ядро и собирать конфиг** на корпусных узлах;
- **ходить в сеть** из прогона — ни к подписочным URL, ни к серверам из тел.
  Сеть нужна одному `fetch.dart`;
- **коммитить приватные подписки** — личная ссылка с токеном, оплаченный
  доступ, чужая ссылка из переписки. Публичность обязана быть проверяемой по
  `url` записи;
- **править `report.*` руками** — перезапишется прогоном.

## 6. Метрика покрытия

`report.md`, раздел «Покрытие: протокол × транспорт × security» — таблица
`протокол | транспорт | security | узлов`. Она отвечает на вопрос, который к
числу узлов не сводится: **каких ветвей реестра корпус не трогает вовсе.**

Ветвь с нулём узлов корпусом не проверяется, и регрессию в ней прогон не
поймает — там работают только синтетические фикстуры
(`app/test/fixtures/<протокол>/`). Так, в корпусе 24.09.2026 из девяти родов
узлов реально нагружены пять (`vless` 62 547, `shadowsocks` 5613, `trojan`
2826, `hysteria2` 2454, `vmess` 412), а `socks` и `wireguard` представлены
одним узлом каждый: публичные списки их почти не раздают. Ждать, что корпус
покроет их сам, не надо — это работа фикстур.

## 7. Как добавить подписку

1. Убедитесь, что список **публичный** и это видно по URL (см. оговорку в
   README корпуса).
2. Допишите URL в `app/test/fixtures/public_subscriptions/urls.txt`.
3. `dart run tool/public_subs/fetch.dart` — доберёт только отсутствующие.
4. Прогон с `LX_CORPUS_REPORT=1` и `LX_CORPUS_UPDATE_EXPECTED=1`: у новой
   записи эталона ещё нет, и сверка без обновления упадёт на «нет в эталоне».
5. Коммит: `urls.txt`, `index.json`, тело, `expected.json`, отчёты.

Дубли между агрегаторами **дефектом не считаются**: одни и те же узлы в пяти
зеркалах — норма этого мира, и на меру они влияют только весом. В корпусе
24.09.2026 таких зеркал заметно (`zieng2/wl` лежит на четырёх хостингах,
`etoneya`-семейство — на шести), и это нормально: зеркала проверяют, что
одинаковое тело с разных хостов читается одинаково.
