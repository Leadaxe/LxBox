# L×Box v2.19.1

A hotfix with three independent fixes. The app no longer gets stuck crashing
on Start, XHTTP nodes come back to life, and VLESS nodes with the
post-quantum encryption layer connect at last — until now every single one of
those failed the ping test.

Хотфикс с тремя независимыми исправлениями. Приложение больше не застревает в
вылете по нажатию Start, XHTTP-узлы снова работают, а VLESS-узлы с
постквантовым слоем шифрования наконец подключаются — до сих пор тест пинга
не проходил ни один из них.

Core / Ядро: **sing-box-lx `v1.14.0-lx.18`** (было `v1.14.0-lx.17-rc.5`).

## 🐛 Fixed

### 🔄 The app recovers on its own after a core crash

Reported on 4PDA (evgeny1503): after updating to 2.19 the service stopped
starting at all. The app crashed immediately on Start, then again, and again.
No settings had been changed.

The cause had nothing to do with settings. The core keeps a small cache file
of its own — picked FakeIP addresses, DNS cache, ping results, which node a
selector currently points at. That file got corrupted, and the core reads it
at startup **before anything else**, so it died right there, taking the whole
app process with it.

What made this a dead end: the file does not repair itself, so every
subsequent Start hit the same crash. The one button that deletes it lives in
DNS settings, labelled as a DNS cache reset — nothing about it suggests it has
anything to do with a crash on startup.

Now the app notices at launch that the previous run ended in a crash, and
clears the core's caches before starting it. The second launch goes through
normally. Configs, subscriptions, settings and per-app lists are never
touched — only data the core rebuilds by itself.

The original corruption is not explained by this fix. It repairs the
consequence, whatever the source was.

### 🔌 XHTTP nodes no longer fail the ping test

Reported on 4PDA: a subscription of 75 nodes passed the ping test on 67 in
another client, but only on 36 here — consistently, about half.

Measured on the same subscription on a test device: 30 of 76 passing. Grouping
the failures by transport left no room for chance — every XHTTP node failed,
14 out of 14, while gRPC nodes on the very same servers answered in 78–163 ms.
The core reported `v2ray-xhttp: unexpected status: 404 Not Found`, and the
node was declared dead.

The cause is in the core (fixed in `lx.17`): an XHTTP server normalizes its
own path to end in `/` when the session id travels in the path, and then
routes only requests carrying that prefix. Our `stream-one` mode trimmed the
trailing slash, so a node configured as `/api/v1/feed` was dialed at exactly
that while the server matched `/api/v1/feed/`. No prefix match, `404`, node
counted as dead.

This affects only the `stream-one` branch — which is what `mode: auto`
resolves to on REALITY servers, the shape most subscriptions ship. `packet-up`
was never affected, because its path continues into `/<sessionId>` and
therefore keeps the slash.

Re-measured after the core update on the same 76 nodes: **42 passing instead
of 30**, all 12 recovered ones XHTTP. Two XHTTP nodes still fail, as does one
gRPC node that passed before — that scatter looks like ordinary network noise
rather than a pattern.

Nodes without TLS (18) and Hysteria2 (11) still fail the ping test on this
subscription. Those are separate causes, one of which is addressed below.

### 🔐 VLESS nodes with post-quantum encryption now connect

Some providers put a post-quantum encryption layer inside VLESS itself
(`mlkem768x25519plus` — ML-KEM-768 combined with X25519). It sits beneath the
transport and works *instead of* TLS, so such nodes ship with `security=none`
and are perfectly normal despite having no TLS.

The app dropped that field on import. It never reached the config, so the core
dialed plain VLESS at a server expecting the encryption layer — the connection
silently failed to establish, with nothing in the log. Every node carrying the
field was dead, whatever its transport.

The field is now carried through to the core, unchanged: from `vless://` links
(query parameter) and from Xray-JSON subscriptions (`users[0].encryption`,
which the core expects flattened next to `uuid`). Nodes without it are not
touched — the emitted config stays byte-for-byte identical.

Measured on the subscription from the report: all 12 genuine nodes with the
field went from dead to answering, across every transport — WebSocket, gRPC
and raw TCP alike. Two further entries carrying the field remain unreachable,
and neither is a real server: one is a section header the provider ships as a
node (address `0.0.0.0`), the other a leftover test entry whose key is a
fraction of the required length.

This needs core `v1.14.0-lx.18` or newer. On older cores the field is rejected
outright and the whole config fails to load.

## 🐛 Исправлено

### 🔄 Приложение само чинится после падения ядра

Жалоба на 4PDA (evgeny1503): после обновления на 2.19 сервис перестал
запускаться вовсе. Приложение вылетало сразу по нажатию Start, потом снова, и
снова. Никаких настроек пользователь не менял.

Причина к настройкам отношения не имела. Ядро держит собственный служебный
файл кэша — подобранные FakeIP-адреса, DNS-кэш, результаты пингов, выбранный
в селекторе узел. Этот файл повредился, а ядро читает его при старте **раньше
всего остального**, поэтому и падало прямо там, унося с собой весь процесс
приложения.

Тупиком это делало вот что: файл сам не чинится, поэтому каждый следующий
Start давал тот же краш. Единственная кнопка, которая его удаляет, живёт в
настройках DNS и называется сбросом DNS-кэша — по ней никак не догадаться,
что она имеет отношение к вылету при запуске.

Теперь приложение при запуске видит, что прошлый раз закончился падением, и
сбрасывает кэши ядра до его старта. Второй запуск проходит нормально.
Конфиги, подписки, настройки и списки приложений не трогаются — только то,
что ядро пересоберёт само.

Почему файл повредился, этот фикс не объясняет. Он лечит последствие,
независимо от источника.

### 🔌 XHTTP-узлы снова проходят тест пинга

Жалоба с 4PDA: подписка из 75 узлов в другом клиенте проходит пинг на 67, а
здесь — только на 36, и так постоянно, примерно вдвое меньше.

Замер на той же подписке на тестовом устройстве: 30 из 76. Разбивка провалов
по транспортам не оставила места случайности — падали **все** XHTTP-узлы, 14
из 14, тогда как gRPC-узлы на тех же самых серверах отвечали за 78–163 мс.
Ядро сообщало `v2ray-xhttp: unexpected status: 404 Not Found`, и узел
считался мёртвым.

Причина в ядре (исправлено в `lx.17`): XHTTP-сервер приводит свой путь к
виду, оканчивающемуся на `/`, когда идентификатор сессии передаётся в пути, и
дальше принимает только запросы с этим префиксом. Наш режим `stream-one`
обрезал завершающий слэш — узел с путём `/api/v1/feed` запрашивался ровно так,
тогда как сервер сверялся с `/api/v1/feed/`. Префикс не совпадал, приходил
`404`, узел записывался в мёртвые.

Затронут только режим `stream-one` — именно в него разворачивается `mode:
auto` на REALITY-серверах, а это самая частая форма в подписках. `packet-up`
не страдал никогда: его путь продолжается в `/<sessionId>` и слэш сохраняет.

Перезамер после обновления ядра на тех же 76 узлах: **42 вместо 30**, и все 12
вернувшихся — XHTTP. Два XHTTP-узла по-прежнему не проходят, как и один
gRPC-узел, проходивший раньше, — этот разброс похож на обычный сетевой шум, а
не на закономерность.

Узлы без TLS (18 штук) и Hysteria2 (11) на этой подписке тест пинга
по-прежнему не проходят. Это отдельные причины, одна из которых разобрана
ниже.

### 🔐 VLESS-узлы с постквантовым шифрованием наконец подключаются

Некоторые провайдеры включают слой постквантового шифрования внутри самого
VLESS (`mlkem768x25519plus` — ML-KEM-768 в связке с X25519). Он живёт под
транспортом и работает *вместо* TLS, поэтому такие узлы приезжают с
`security=none` — и это нормально, а не признак поломки.

Приложение теряло это поле при импорте. До конфига оно не доезжало, ядро
подключалось голым VLESS к серверу, который ждёт слой шифрования, — соединение
молча не вставало, в логах ни строчки. Мёртвыми оказывались все узлы с этим
полем, независимо от транспорта.

Теперь поле доносится до ядра без изменений: из ссылок `vless://`
(query-параметр) и из Xray-JSON подписок (`users[0].encryption` — ядро ждёт
его плоским полем рядом с `uuid`). Узлы без этого поля не затронуты вовсе:
конфиг для них остаётся байт в байт прежним.

Замер на подписке из жалобы: все 12 настоящих узлов с этим полем перешли из
мёртвых в отвечающие, причём по всем транспортам сразу — WebSocket, gRPC и
голый TCP. Ещё две записи с этим полем остаются недоступными, но ни одна из
них не является сервером: первая — заголовок раздела, который провайдер кладёт
в подписку как узел (адрес `0.0.0.0`), вторая — забытая тестовая запись с
ключом в разы короче необходимого.

Требуется ядро `v1.14.0-lx.18` или новее. На более старых ядрах поле
отвергается, и конфиг не загружается целиком.

## ⚠️ Note / Оговорка

The check runs on every app launch, before the core starts, and costs a single
file lookup. It triggers on any core crash, not only on cache corruption: the
price of an unnecessary reset is low — a few pings measured again, a selector
back on its default node — while a missed one leaves the app unusable.

Проверка выполняется при каждом запуске приложения, до старта ядра, и стоит
одного обращения к файлу. Срабатывает она на любое падение ядра, не только на
повреждение кэша: цена лишнего сброса невелика — заново измеренные пинги,
селектор на узле по умолчанию, — тогда как пропущенный оставил бы приложение
нерабочим.
