# L×Box — как это работает

Руководство для пользователя: что есть что и за что отвечает. Не про код — про
**логику работы** и порядок настройки.

---

## Что есть что

Термины, в которых чаще всего путаются:

| Слово | Одной строкой | Аналогия |
|---|---|---|
| **Сервер** | Одна точка выхода (одна страна/узел), куда можно подключиться. | Дом, куда ведёт дорога. |
| **Подписка / папка** | **Откуда берутся** серверы: список от провайдера (подписка) или ваша ручная пачка (папка). | Адресная книга с домами. |
| **Авто-узел** | Один пункт списка, **внутри которого пул серверов** и автоматический выбор между ними. | Дом с несколькими дверями — открывается та, что быстрее. |
| **Канал** | **Группа серверов под задачу**: отбирает нужные серверы фильтром и переключает между ними. По каналам вы раскидываете трафик. | Полка, на которую вы ставите нужные дома. |
| **Tunnel apps** | **Кого впускаем** в L×Box вообще (какие приложения телефона). | Турникет на входе. |
| **Detour** («через») | Один сервер ходит **через** другой перед выходом в интернет (цепочка). | Дорога к дому идёт через другой дом. |
| **Правила (Rules / DNS)** | Исключения: какой трафик в какой канал и каким DNS резолвить. | Развилки на дорогах. |

Главное:

- **Сервер ≠ канал.** Сервер — это куда. Канал — это группа «куда» под конкретную
  задачу. Один и тот же сервер может входить в несколько каналов.
- **Подписка/папка — это НЕ канал.** Это просто источник серверов. Серверы из них
  сами по себе трафик никуда не гонят, пока не попадут в канал.
- **Detour — это не отдельный сервер и не канал.** Это надстройка «ходи через
  вот этого» поверх сервера/канала/папки.

## Общая картина: как трафик проходит через L×Box

Трафик приложения проходит **четыре ступени** — каждая отвечает за свой вопрос:

```
   Приложения на телефоне
            │
            ▼
 ┌─────────────────────────┐
 │ 1. Allow-list           │   «КОГО вообще впускаем в L×Box?»
 │    (Tunnel apps)        │   Не впущен → идёт мимо, как будто VPN выключен.
 └─────────────────────────┘
            │  (впущенный трафик)
            ▼
 ┌─────────────────────────┐
 │ 2. Channels             │   «КАКИЕ есть каналы и КУДА по умолчанию?»
 │    (Default traffic)    │   VPN = через туннель · Direct = напрямую.
 └─────────────────────────┘
            │
            ▼
 ┌─────────────────────────┐
 │ 3. Rules                │   «ИСКЛЮЧЕНИЯ из умолчания»
 │                         │   Какой домен/приложение — в какой канал.
 └─────────────────────────┘
            │
            ▼
   VPN-канал (сервер) · Direct · Block
            │
            ▼
 ┌─────────────────────────┐
 │ 4. DNS                  │   «КАК резолвятся имена сайтов»
 └─────────────────────────┘
```

Те же ступени одной строкой:

- **Allow-list** — *этот трафик вообще попадает в L×Box?*
- **Channels** — *каким выходным путём вести по умолчанию (через сервер или напрямую)?*
- **Rules** — *есть ли для него отдельное правило, переопределяющее умолчание?*
- **DNS** — *как для него узнать IP по имени сайта?*

Каждая ступень — отдельный фильтр, и они не заменяют друг друга.

## Режим работы — туннель или локальный прокси

Прежде чем ступени сработают, трафик должен как-то попасть в L×Box. Способ
выбирается в **VPN Settings → Mode**:

- **VPN** (по умолчанию) — системный туннель: L×Box занимает VPN-слот Android
  и ловит трафик приложений целиком. Весь этот гайд написан про этот режим.
- **Local proxy** — туннеля нет вовсе (и значка-ключика тоже): поднимается
  локальный HTTP+SOCKS-прокси, и в L×Box попадает только трафик приложений,
  которым вы вручную прописали этот прокси. VPN-слот Android при этом свободен —
  режим уживается с другим VPN-приложением.
- **VPN + Proxy** — и туннель, и прокси-порт одновременно.

Прокси-порт настраивается там же. Доступ к прокси — либо только с этого
устройства, либо со всей локальной сети: во втором случае авторизация по паролю
обязательна (так через L×Box на телефоне может ходить, например, телевизор или
второй телефон).

Два замечания для прокси-режимов: Tunnel apps (ступень 1) управляет только
туннелем — на прокси «впуск» определяется тем, кого вы на него направили; в
правилах маршрутизации трафик туннеля и трафик прокси можно развести условием
**Inbound**.

## 1. Allow-list (Tunnel apps) — кого впускаем

**За что отвечает:** какие приложения вообще попадают под управление L×Box.

Три режима:

| Режим | Что значит |
|---|---|
| **Off** | Все приложения идут через L×Box (по умолчанию). |
| **Allow-list** | Через L×Box идут **только** выбранные. Остальные — мимо (обычная сеть). |
| **Deny-list** | Через L×Box идут **все, кроме** выбранных. |

Приложение, которое **не** захвачено (не в Allow-list / в Deny-list), L×Box
вообще не видит — его трафик идёт напрямую, как без VPN, и правила (Rules) к нему
**не применяются**.

> **Важно:** сам **L×Box добавлять в Allow-list НЕ нужно** — это ни на что не
> влияет. Приложение само через свой туннель не ходит (его служебные соединения
> и DNS идут мимо tun по физической сети). Если кажется, что «заработало после
> добавления себя» — почти всегда сработало что-то другое (обычно Default
> traffic = VPN, см. ниже).

### Allow VPN bypass — для приложений, которые конфликтуют с VPN

**Зачем это надо.** Некоторые приложения принципиально не хотят работать под
VPN — банковские клиенты (антифрод видит «чужой» IP и блокирует вход),
приложения операторов связи, звонилки с VoLTE/VoWiFi. Обычно они просто перестают
работать, пока туннель поднят. Этот тумблер даёт им лазейку — не отключая VPN для
всего остального.

**Где:** VPN Settings → Mode → Tunnel options → **Allow VPN bypass** (виден в
режимах с туннелем).

- **Выключен (по умолчанию)** — строгий туннель: весь впущенный трафик обязан
  идти через VPN, обойти его приложение не может.
- **Включен** — приложение, которое *само явно попросит систему* дать ему
  физическую сеть (через Android ConnectivityManager), сможет ходить мимо
  туннеля.

Это **разрешение, а не маршрут**: включение само по себе ничего никуда не
переносит — обходить начнут только приложения, которые специально это умеют.
Поэтому не путать с deny-list: deny-list **принудительно** выводит выбранные
приложения из-под VPN (сработает с любым), а Allow VPN bypass лишь **разрешает**
обход тем, кто попросит сам.

Что выбрать: нужно вывести конкретное приложение из VPN железно — deny-list.
Приложение само конфликтует с VPN и умеет запрашивать обход — этот тумблер.
Большинству пользователей он не нужен. После переключения — перезапуск VPN.

## Серверы, подписки и папки — откуда берутся выходы

> Эта часть — не про ступени трафика, а про то, **откуда в приложении вообще
> появляются серверы**. Люди путают три вещи: сервер, подписку и папку. Разница
> простая.

Всё, что даёт серверы, живёт на экране **≡ (меню) → Servers** («Subscriptions &
proxy»). Там три вида «источников», и они выглядят похоже, но ведут себя
по-разному:

| Источник | Что это | Сколько серверов | Обновляется |
|---|---|---|---|
| **Одиночный сервер** | Один сервер, добавленный вручную. | 1 | Никогда (вы его вставили руками). |
| **Подписка** | Список серверов **от провайдера** по ссылке. | много | Сама, по расписанию (или кнопкой «Update»). |
| **Папка** | **Ваша ручная пачка** серверов, сгруппированная под одним именем. | сколько положите | Никогда (вы ей управляете вручную). |

### Одиночный сервер

Один сервер. Вы его добавили, вставив ссылку (`vless://…`, `vmess://…`,
`wg://…`, QR-код и т.п.) или из файла. Обновлять нечего — это статичная запись.
Подходит, когда у вас «просто один конфиг от друга/провайдера».

### Подписка

Ссылка от VPN-провайдера, за которой прячется **целый список серверов**. L×Box:

- сам скачивает список и держит его свежим (по умолчанию раз в сутки; есть кнопка
  ручного обновления);
- при неудачном обновлении **не стирает** старые серверы — продолжает работать на
  прошлом списке;
- показывает от провайдера полезную мету, если он её отдаёт: остаток трафика, дату
  окончания, ссылку на сайт/поддержку.

Есть и **файловая подписка** — когда список серверов вы импортируете из файла, а
не по ссылке. Она ведёт себя как подписка (много серверов под одним именем), но
сама не обновляется — обновляете, подсунув новый файл (**Edit source**).

> **Нет своей подписки?** На том же экране есть **Get WARP** — он бесплатно
> регистрирует Cloudflare WARP и добавляет как сервер. Подробнее — в конце гайда.

### Папка

Папка — это **ваша собственная группа серверов**, которые вы собрали руками. Не
путать с каналом:

- **Папка** отвечает на вопрос «*где лежат* эти серверы» (как папка с файлами:
  общее имя, общий переключатель вкл/выкл, порядок перетаскиванием).
- **Канал** отвечает на вопрос «*какие* серверы использовать для задачи» (см.
  следующий раздел).

Внутри папки — **члены** (members). Каждый член — это ровно один сервер. Члена
можно по отдельности включить/выключить, переставить, а также задать ему
персональный **detour** (см. раздел про detour). Подписку внутрь папки положить
нельзя — папка только для ручных серверов.

**Когда что заводить:**

- один конфиг → **одиночный сервер**;
- ссылка от провайдера → **подписка**;
- набор своих `.conf`/ссылок, которые хочется держать вместе (например «мои
  Mullvad») → **папка**.

### Авто-узлы — один пункт, внутри пул

Авто-узел — это один пункт списка, внутри которого **несколько серверов и
автоматический выбор** между ними. Появляется двумя путями:

- **Из подписки.** Провайдеры кладут в подписку пункт вида «Авто | Лучший
  сервер» — пул из многих серверов. Раньше такой пункт рассыпался на отдельные
  строки; теперь это один узел, и в его строке виден режим и состав:
  `🔀 [15/7]` — пул из 15, в работе 7 (режим балансировки), или `🎯 [3]` —
  «один быстрейший» из трёх.
- **Свой, в папке.** Меню папки → **Add auto node…** — авто-узел из серверов
  этой папки. Членство задаётся тремя способами: все серверы папки, правило
  (include/exclude-regex с живым превью «12 of 37») или явный список галочками.
  Интервал проверки, режим и липкость сессий — в разделе Advanced.

Не путать с авто-двойником канала (`<канал>-auto`, см. раздел про Channels):
двойник собирает узлы **канала** по его фильтру, а авто-узел — самостоятельный
узел, который живёт в общем списке серверов наравне с остальными.

### Как всё это попадает в каналы

Серверы из подписок, папок и одиночек **сами по себе трафик не гонят**. Они
складываются в общий пул серверов, а уже **каналы** выбирают из этого пула нужные
(по фильтру) и подключаются. Поэтому порядок такой: сначала добавили
подписку/папку/сервер → потом канал их подхватил.

> **Про «tag prefix».** У подписки и папки в настройках можно задать префикс —
> короткую метку, которая приписывается к именам всех её серверов. Это удобно для
> фильтров каналов: например, папке дали префикс `mullvad-`, и канал с фильтром
> `^mullvad-` автоматически соберёт ровно её серверы. Если фильтрами каналов не
> пользуетесь — префикс можно не трогать.

### Экран подписки — что внутри

Тап по подписке открывает её экран с вкладками:

- **Nodes** — список узлов. У каждого узла — переключатель: ненужный узел можно
  **выключить**, не трогая саму подписку (выключенные показаны зачёркнутыми и не
  попадают в конфиг; выбор переживает обновления подписки и переименования у
  провайдера). Кнопка «Включить все / Выключить все» сбрасывает накопившееся
  состояние разом. Короткий тап по узлу открывает его **разбор**: вкладка JSON —
  как узел уходит в конфиг, вкладка Source — исходный фрагмент подписки, из
  которого он собрался.
- **Filters** — правила обработки узлов; применяются при импорте и на каждом
  обновлении. Правило = условия + действие. Условие — `путь оператор значение`
  (contains / equals / regex, галки Not и Case-sensitive, несколько условий по
  AND/OR; пустой путь = искать по всему узлу). Действия: **Disable** — спрятать
  подходящие узлы из маршрутизации, **Enable** — вернуть (снимает и ручные
  выключения; правила применяются по порядку, последнее сработавшее побеждает,
  так что связка «выключить всё → включить NL» работает как белый список),
  **Replace** — записать новое значение по указанному пути (целиком или частью,
  с карманами `$1`, `$2`… из regex-групп) — например, починить нестандартный
  TLS-fingerprint у всех узлов сразу. Вкладка **Matches** в редакторе правила
  показывает, к каким узлам оно применится и что изменит, ещё до сохранения.
- **Source** — сырой ответ провайдера. Если тело закодировано base64, галка
  **Decode base64** раскрывает его в тот же вид, с которым работает парсер.
- **Settings** — префикс тегов, detour, интервал обновления, а также:
  - **«При обновлении»** — что делать, когда обновление принесло новый состав
    узлов: *Пересобрать конфиг* (по умолчанию — применяете сами), *Пересобрать
    и перезагрузить ядро* (применяется сразу, соединение рвётся на несколько
    секунд) или *Ничего не делать*.
  - **Fetch identity** — каким «представляться» провайдеру при скачивании:
    Default — глобальные User-Agent / HWID / device-заголовки, Custom — свой
    набор только для этой подписки (удобно, когда несколько панелей и у каждой
    свой HWID-лимит или формат ответа по User-Agent).
- Кнопка **Test servers** — прогнать узлы подписки пингом, не запуская VPN
  (при работающем VPN появится вопрос: остановить и протестировать, или
  отменить — мерить поверх живого туннеля нельзя, результаты врали бы).

> **Приехал один узел «App not supported»?** Это не поломка: панель провайдера
> требует идентификатор устройства (HWID) и до его получения отдаёт
> узел-заглушку. Включите отправку HWID — глобально (App Settings →
> Subscriptions) или в Fetch identity этой подписки — и обновите её.

## 2. Channels — выходные пути

**За что отвечает:** это **выходные пути** — куда трафик может уйти наружу, и
какой путь используется **по умолчанию**.

По умолчанию каналов **три**: один **VPN-канал** (`vpn-1` — ваш основной
туннель) + два служебных — **Direct** и **Block**. Можно **подключить ещё**
VPN-каналы (например разные серверы/группы под разные задачи).

Каждый канал — это «выход»:
- **VPN-канал** (группа серверов из ваших подписок) — наружу через сервер
  (туннель);
- **Direct** — наружу напрямую (мимо туннеля, но всё ещё через L×Box);
- **Block** — никуда (блокировка).

**Default traffic** — какой выходной путь по умолчанию: **VPN** (через сервер)
или **Direct** (напрямую). Применяется к захваченному трафику, для которого ни
одно правило (Rules) не сработало.

> **Это и есть причина частой путаницы.** Если приложение в Allow-list есть, но
> **Default traffic = Direct**, его трафик уходит **напрямую** — и кажется, что
> «VPN не работает». Поставьте **Default traffic = VPN** → пойдёт через туннель.
> Allow-list решает «впускать ли», Channels — «куда вести». Это две разные вещи.

**Авто-выбор узла.** У VPN-канала можно включить авто-двойник (`<канал>-auto`),
который сам выбирает узел из группы. В редакторе канала — два режима:

- **Fastest** — весь трафик идёт на один самый быстрый узел (по замеру задержки).
- **Load balance** — трафик распределяется по пулу из нескольких живых узлов;
  сессии «прилипают» к узлу (sticky), чтобы не рвать соединения при ротации.

**Как канал набирает серверы (фильтр).** Канал не хранит серверы внутри себя — он
**отбирает** их из общего пула (все ваши подписки + папки + одиночки). В редакторе
канала есть **Node filter** — фильтр по имени сервера:

- пусто → в канал попадают **все** серверы;
- текст/regex (например `🇩🇪` или `^mullvad-`) → только серверы, чьё имя совпало;
- тумблер **`!`** слева от поля → наоборот, все **кроме** совпавших.

Синтаксис шаблонов, примеры и разбор отрицания — в разделе
[Регулярные выражения](#регулярные-выражения-regex).

Поэтому **один и тот же сервер может входить в несколько каналов сразу**. Канал — это не «место, где
лежит сервер», а «правило отбора серверов под задачу». Пример: канал «Стриминг» с
фильтром `🇩🇪` соберёт все немецкие серверы из всех источников; они же останутся
доступны и в основном канале `vpn-1`.

> **`vpn-1` — особенный.** Первый канал всегда есть, его нельзя удалить, и на него
> «падают» ссылки, если удалить другой канал. Считайте его каналом по умолчанию.
> Всего каналов может быть до 10.

## 3. Rules — как разруливаем

**За что отвечает:** исключения из умолчания. Какой конкретно трафик в какой
канал.

Правило = **условия + действие**. Условий в редакторе много, по секциям:

| Секция | Что матчит |
|---|---|
| **Match** | домены (точное имя / суффикс / подстрока), IP-подсети (CIDR), «Private IP» (адресат в локальной сети), «Private source IP» (источник — локальный адрес) |
| **Ports** | порты и диапазоны портов |
| **Apps** | конкретные приложения (per-app) |
| **Network & Protocol** | тип трафика **TCP / UDP / ICMP** и протокол приложения, распознанный sniff'ом (tls, quic, bittorrent, dns, …) |
| **Inbound** | каким входом пакет попал в L×Box: через VPN-туннель или через локальный прокси (виден в proxy-режимах) |
| **Wi-Fi** | имя (SSID) или BSSID текущей Wi-Fi-сети — «дома → напрямую» |
| **Rule set** | внешний список доменов/IP в формате `.srs` (скачивает приложение, работает локально; перепроверяется по своему сроку годности — см. редактор правила) |

Внутри одной категории — ИЛИ, между категориями — И (как в sing-box): правило
«приложение Chrome И домен `*.youtube.com` И сеть UDP» сработает только при
совпадении всех трёх.

**Действие** — не только «в какой канал». Рядом с пикером действия есть
шестерёнка **Action & Resolve**:

- **Route to outbound** — обычный маршрут: совпавший трафик в выбранный канал
  (VPN-группа / Direct / Block);
- **Resolve first** — сначала отрезолвить домен, потом маршрутизировать; можно
  навязать семейство адресов и параметры резолва (свой DNS-сервер, стратегия,
  кэш, TTL, client subnet, таймаут);
- **Resolve only** — продвинутый режим: правило только резолвит, маршрут
  выбирают следующие правила (или Default traffic);
- **Force IPv4 (drop AAAA)** — на AAAA-запросы доменов правила отвечать
  локально, чтобы трафик шёл по IPv4; DNS-сервер для этого не нужен. Спасение
  для сетей с полумёртвым IPv6.

Типичные правила:
- реклама/трекеры → **Block**;
- российские домены (`.ru/.рф/…`) → **Direct** (быстрее и без нужды в VPN);
- BitTorrent → нужный канал;
- конкретное приложение → конкретный канал;
- UDP (игры, звонки) → напрямую, TCP — через туннель.

Порядок имеет значение: правила применяются сверху вниз, первое совпавшее
выигрывает; не совпало ни одно → **Default traffic** из Channels.

### Связка правила с DNS

В редакторе правила есть DNS-блок — тумблер **Send DNS to dedicated server**.
Он заводит к правилу **парное DNS-правило**: DNS-запросы доменов этого правила
уходят на выделенный сервер (по умолчанию — авто, по каналу маршрута; можно
выбрать конкретный, включить Force IPv4 и тонкие опции). Так одно правило
решает и «куда трафик», и «как резолвить» — не нужно собирать DNS-правило
вручную. Два ограничения, о которых редактор предупреждает сам: с фильтрами по
портам/протоколам связка недоступна (на момент DNS-запроса они ещё неизвестны),
а rule-set работает, только если в списке есть домены (чисто IP-шные списки
DNS-запросы не матчат).

### Когда формы мало

- **Raw-JSON правило** — правило можно написать сырым JSON (фрагмент
  `route.rules` sing-box): для полей, которых нет в форме. Действие — часть
  самого JSON; синтаксис проверяется прямо при вводе.
- **Вкладка View** — у обычного правила показывает готовый sing-box-фрагмент,
  который уйдёт в конфиг.

> **Presets** — read-only каталог готовых правил. Не применяются сами по себе:
> копируете нужное в Rules (Copy to Rules), дальше это ваше правило.

> **Traffic Processing** — закреплённый пресет первым в списке правил. В нём
> собрана предобработка трафика, на которой держится остальная маршрутизация:
> распознавание протокола (sniff), перехват DNS-запросов (Hijack DNS) и резолв
> адресатов. Его нельзя выключить, удалить или подвинуть — настройки меняются
> внутри самого пресета.

## 4. DNS — как резолвятся имена

**За что отвечает:** как имя сайта превращается в IP. Отдельный слой со своими
правилами.

- **DNS-серверы** — каталог (Cloudflare/Google/Yandex/Quad9/AdGuard/OpenDNS,
  UDP/DoT/DoH). У каждого выбирается, через какой канал он ходит
  (**Outbound/detour**) и IP/профиль. Хотите, чтобы DNS «нужных» приложений шёл
  через туннель (забугорный резолвер видел IP сервера, а не провайдера) —
  выберите серверу Outbound = ваш VPN-канал.
- **DNS-группы** — несколько серверов под одним тегом. Группа сама выбирает,
  кто отвечает, по одной из стратегий: **Stable** — держится за рабочий сервер,
  пока тот не сбоит; **Fastest** — гонка, затем липнет к победителю;
  **Parallel** — каждый запрос гонкой по всем. У участников нет вечного
  «умер»: ошибки помнятся с ограниченным сроком, оживший путь сам возвращается
  в строй. Группу можно ставить всюду, где ставится одиночный сервер:
  дефолтным резолвером, целью DNS-правила.

  **Свою группу собрать просто**: в редакторе DNS-сервера рядом с типами
  UDP / TLS / HTTPS есть четвёртый — **Group**. Вместо адреса — галочки
  участников (любые ваши DNS-серверы), выбор стратегии и сроки памяти об
  ошибках и победах (**Error TTL** / **Win TTL**; второй виден только у
  Fastest). Выключенный или удалённый участник группу не ломает: при сборке
  конфига он просто пропускается с предупреждением, а когда снова включите —
  вернётся на место сам. В списке серверов у группы бейдж
  `GROUP · режим · число участников`, а при поднятом туннеле — текущая цель и
  состояние каждого участника (ошибки, RTT).
- **Shield DNS** — готовая группа `dns_shield`, на свежей установке она стоит
  по умолчанию и как DNS Final, и как Default Domain Resolver. Внутри — Google,
  Cloudflare, OpenDNS, Quad9 и Yandex одновременно, тремя транспортами
  (UDP / DoT / DoH) и двумя путями (напрямую и через VPN). Смысл: ни один отказ
  не выносит резолв целиком — ляжет провайдер, работают остальные; зарежут
  UDP:53 — работают DoT/DoH; упал туннель — работают прямые пути; заблокируют
  прямой доступ — работают туннельные.
- **DNS Final** — резолвер по умолчанию для запросов приложений, если ни одно
  DNS-правило не сматчило. На свежей установке — `dns_shield` (на установках,
  обновившихся со старых версий, мог остаться прежний `cloudflare_udp` —
  группу можно выбрать самим). Хотите жёстко зашифрованный DNS — поставьте
  `google_doh` / `cloudflare_dot` или сервер с Outbound = VPN-канал.
- **Default Domain Resolver** — внутренний резолв самого sing-box (адреса
  серверов, домены в правилах маршрутизации). На свежей установке —
  `dns_shield`. **Не ставьте сюда `local_dns_resolver`** — системный DNS течёт
  к провайдеру мимо VPN.
- **DNS Rules** — какие домены каким DNS-сервером резолвить. Это отдельный
  список на экране DNS Settings; как и правила маршрутизации, DNS-правила
  применяются по порядку (перетаскиваются), у каждого — тумблер. Правила в
  списке берутся из четырёх источников:
  - **свои** — кнопка **Add user rule** (правило пишется JSON-фрагментом
    `dns.rules` sing-box — это инструмент продвинутого уровня);
  - **от пресетов** — включённый пресет маршрутизации приносит свои DNS-правила
    (например, «Russian domains & IPs» резолвит ru-домены собственной группой
    `dns_ru` из трёх независимых путей: UDP через канал пресета, DoT через
    `vpn-1`, DoH напрямую — мёртвая нода в одном из путей не подвешивает
    ru-сайты);
  - **от шаблона** — базовые правила конфигурации;
  - **зеркала правил маршрутизации** — та самая связка «Send DNS to dedicated
    server» из редактора правила (см. раздел Rules): такие записи показаны
    группой и редактируются на стороне правила-родителя.

  Для типового «этим доменам — такой-то DNS» удобнее всего не писать DNS-правило
  руками, а включить DNS-блок прямо в правиле маршрутизации.

## Detour — «ходить через» (цепочки серверов)

**Что это.** Detour — это когда один сервер выходит в интернет **не напрямую, а
через другой сервер**. То самое «через», которым это обычно и объясняют:

```
  вы → [Сервер A] → [Сервер B] → интернет
                    ▲
              это detour A: «сервер A ходит ЧЕРЕЗ сервер B»
```

Зачем это нужно:

- **обойти блокировку по географии выхода** — заходите через сервер A (быстрый,
  близкий), а в интернет выходите с IP сервера B (нужная страна);
- **пробить блокировку самого сервера** — если до сервера B напрямую не достучаться
  из вашей сети, но до A — можно, а A видит B;
- **двойной прыжок ради приватности** — ни один сервер не видит одновременно и вас,
  и конечный сайт.

Detour — это **надстройка**, а не отдельная сущность. Вы берёте уже имеющийся
сервер и говорите ему «а ходи-ка ты через вот этого». Целью detour может быть:

- **другой сервер** (одиночка или член папки);
- **канал** — тогда цель не фиксирована: ядро само выберет лучший сервер из
  канала в момент подключения (это и есть **detour-канал**);
- **None (direct)** — без detour, сервер ходит напрямую (значение по умолчанию).

### Где настраивается

Detour задаётся **у источника серверов**, через единый пикер «выбери, через кого
ходить». Точка входа зависит от того, кому назначаете:

| Кому назначаете detour | Где | Действует на |
|---|---|---|
| **Одному серверу** | Node Settings (тап по серверу) | только этот сервер |
| **Всей подписке** | Subscription → вкладка **Settings** | все серверы подписки |
| **Всей папке** | Folder → вкладка **Settings** | всех членов папки |
| **Одному члену папки** | внутри папки, у члена | только этот член |

В пикере вы увидите разделы: **None (direct)**, **Channels** (если есть
detour-каналы), **This folder** (члены той же папки, когда настраиваете члена) и
**Standalone servers** (одиночки). Выбрали — сохранили.

### Цепочки

Detour можно выстраивать в **цепочку**: A через B, B через C — тогда трафик идёт
`вы → A → B → C → интернет`. Внутри папки можно строить такие цепочки прямо между
её членами (член ходит через другого члена той же папки). Замкнуть цепочку в
кольцо L×Box не даст: при сборке конфига срабатывает детектор циклов — запуск
останавливается, а окно ошибки называет виновников; тап по виновнику ведёт к
владельцу ноды, где кольцо можно разорвать. Член, который служит промежуточным
звеном для другого, помечается значком ⚙.

### Detour-каналы

Обычный канал можно пометить галкой «Use as detour» (редактор канала). Такой
канал становится **переключаемой прослойкой**: любой сервер может ходить
«через этот канал», а какой именно сервер внутри канала будет использоваться —
решает ядро (по скорости). Удобно, когда промежуточный узел хочется иметь не
жёстко прибитым, а «лучшим из группы». Галка — это именно разрешение выбирать
канал как прослойку: целью правил и route final такой канал быть **не
перестаёт** (в списках выбора он помечен значком ⚙).

### Ограничения

- **Нельзя строить цепочку из AmneziaWG в обычный WireGuard** — это подвешивает
  ядро, поэтому такие цели просто не показываются в пикере, а если старый выбор
  стал недопустимым — он сбрасывается на None.
- Detour **не превращается в VPN-поверх-VPN на уровне ОС** — вся цепочка живёт
  внутри одного туннеля L×Box, это выгоднее по ресурсам.

### Как проверить, что detour работает

Включите VPN, откройте **Statistics** (доступно при поднятом туннеле) и загляните
в детали соединения — там есть строка **Detour**, показывающая цепочку выходов
(`A → B → …`), и строка **Chain**. Так видно, реально ли трафик пошёл через
промежуточный сервер.

### Мёртвое звено видно сразу

Если нода с пингом ERR служит промежуточным звеном для других — через неё ходят
другие ноды или DNS-серверы (напрямую или через канал, где она выбрана), — у её
имени появляется значок **⚠**. Тап по значку открывает список пострадавших с
путём зависимости: видно, кого именно утащит за собой это звено. Если от ноды
зависят DNS-серверы, дополнительно показывается баннер — домены такого сервера
тихо не резолвятся, и без подсказки это выглядит как «интернет отвалился без
причины».

## IPv6 — когда включать (обычно — не надо)

По умолчанию IPv6 в туннеле **выключен**, а все стратегии резолва стоят в
`ipv4_only`. Это намеренно: на многих сетях (особенно мобильных) глобальный
IPv6 работает наполовину — адрес выдаётся, но соединения по нему виснут. Тогда
сайты, у которых есть IPv6-адрес, перестают открываться, хотя VPN формально
«работает». Если не уверены, что на вашей сети IPv6 живой, — не включайте.

Настроек, связанных с IPv6, несколько, и разложены они по разным местам:

| Настройка | Где | Что делает |
|---|---|---|
| **Enable IPv6** | VPN Settings → Core → TUN | Даёт туннелю IPv6-адрес. Главный тумблер. |
| **IPv6 address** | там же | IPv6-адрес туннеля. Применяется только при включённом Enable IPv6. |
| **Preferred IP version** | VPN Settings → Core → DNS | Какие адреса предпочитать при DNS-резолве (`ipv4_only` / `prefer_ipv4` / …). |
| **Resolve strategy** | VPN Settings → Core → Network | То же, но для резолва доменов внутри правил маршрутизации. |
| **Force IPv4** | галка внутри некоторых пресетов (Routing → Presets, у тех, что резолвят домены) и у пользовательских правил (шестерёнка **Action & Resolve** рядом с Action) | Резолвить эти домены только в IPv4. Где есть — включена по умолчанию. |

Руками всё это синхронизировать не нужно — главный тумблер делает это сам.
Включили **Enable IPv6** → обе стратегии переключаются в `prefer_ipv4` (IPv6
используется, но IPv4 в приоритете — безопасный режим). Выключили → обратно в
`ipv4_only`. Менять стратегии вручную имеет смысл, только если понимаете зачем
(например `prefer_ipv6` на сети с полноценным IPv6).

Порядок включения, если IPv6 действительно нужен:

1. Убедиться, что сеть отдаёт рабочий глобальный IPv6 (без VPN открываются
   IPv6-only ресурсы).
2. **VPN Settings → Core → TUN → Enable IPv6**.
3. **Перезапустить VPN** (Stop → Start, а не просто пересохранить): системный
   DNS-кэш Android сбрасывается только рестартом туннеля, иначе старые адреса
   ещё какое-то время будут всплывать.
4. Если после этого какие-то сайты стали виснуть — проверить включённые пресеты
   в Routing → Presets: у некоторых внутри есть галка **Force IPv4**, которая
   держит их домены на IPv4. Если IPv6 вам действительно нужен для этих доменов —
   снимите её (иначе можно оставить включённой).

## Частые непонятки

**«Allow-list не работает — добавил приложение, а VPN на него не действует.»**
Проверьте **Channels → Default traffic = VPN**. Allow-list только впускает; куда
вести — решает Channels. С Default = Direct захваченные приложения идут напрямую.

**«Заработало, только когда добавил сам L×Box в Allow-list.»**
Скорее всего сработало не самодобавление, а Default traffic = VPN (если меняли
обе опции). Сам L×Box в туннеле не нуждается — его служебный трафик и DNS идут
мимо tun по дизайну.

**«Хочу: только браузер через VPN, остальное напрямую.»**
Allow-list = только браузер; Channels Default = VPN. Остальные приложения L×Box
не трогает.

**«Хочу: всё через VPN, но рекламу резать и .ru напрямую.»**
Allow-list = Off (или все нужные); Channels Default = VPN; Rules: реклама →
Block, `.ru` → Direct.

**«DNS-запросы видны провайдеру / идут мимо VPN.»**
Из коробки DNS приложений уже не идёт через системный резолвер провайдера
(DNS Final = группа `dns_shield`, в которой есть и шифрованные, и туннельные
пути). Хотите скрыть домены гарантированно — DNS Final ставьте зашифрованный
(`google_doh`/`cloudflare_dot`) или сервер с Outbound = VPN-канал.
Для внутреннего резолва: Default Domain Resolver ≠ `local_dns_resolver`.

**«Чем канал отличается от подписки/папки?»**
Подписка и папка — это **откуда берутся** серверы (источник). Канал — это **группа
серверов под задачу**, он отбирает нужные серверы из всех источников фильтром. Один
сервер может входить в несколько каналов. Добавили подписку/папку → серверы попали
в общий пул → каналы их подхватили.

**«Добавил папку/подписку — а трафик не идёт через неё.»**
Источник серверов сам по себе трафик не гонит. Проверьте, что её серверы попадают
в активный канал (фильтр канала пустой или совпадает с их именами) и что
**Default traffic = VPN**.

**«Что такое detour и зачем он?»**
Detour — это «ходить **через**»: сервер выходит в интернет не напрямую, а через
другой сервер (цепочка `вы → A → B → интернет`). Нужен, чтобы выйти с IP другой
страны, пробить блокировку самого сервера или сделать двойной прыжок. Задаётся у
сервера/подписки/папки в их настройках. Значение по умолчанию — None (без detour).

**«Выбрал сервер целью detour, а он пропал / сбросился на None.»**
Скорее всего цель — обычный WireGuard, а исходный сервер — AmneziaWG: такую цепочку
ядро не тянет, поэтому выбор недоступен. Возьмите целью не-WG сервер или канал.

**«Включил IPv6 — сайты (особенно российские) перестали открываться.»**
Признак сети с нерабочим IPv6: домен резолвится в IPv6-адрес, соединение виснет.
Выключите **Enable IPv6** (VPN Settings → Core → TUN) и перезапустите VPN.
Подробнее — раздел про IPv6 выше.

**«Поменял настройки, а поведение не изменилось.»**
Изменения попадают в работающий туннель после пересборки конфига и перезапуска
VPN — об этом напоминает плашка на главном экране (она сверяется с работающим
ядром: если фактически применять нечего, плашка не появится). Не хотите жать
руками — в App Settings → General есть тумблер автоперезапуска VPN при смене
настроек.

**«В подписке вместо серверов один узел "App not supported".»**
Панель провайдера требует идентификатор устройства (HWID) и до его получения
отдаёт заглушку. Включите отправку HWID (App Settings → Subscriptions, либо
Fetch identity в настройках подписки) и обновите подписку.

**«Переключил канал — пинги пропали / показывают серые числа с `~`.»**
Замеры у каждого канала свои (у каналов разные адреса и таймауты проверки).
Серое число с `~` — последний замер из другого канала, показанный как
ориентир. Запустите массовый пинг в текущем канале — числа станут «своими».

**«Провайдер положил в подписку "Авто | Лучший сервер", а он выглядит одной
строкой.»**
Так и задумано: это авто-узел — один пункт, внутри которого пул серверов и
автоматический выбор (в строке видно режим и состав, например `🔀 [15/7]`).
Раскрывать его на отдельные серверы не нужно — ядро само держится за живые.

**«Приложение упало, и теперь VPN не стартует вовсе.»**
После падения ядра приложение на следующем запуске само сбрасывает служебные
кэши ядра (битый кэш — частая причина «падает сразу по старту»). Конфиги,
подписки и настройки при этом не трогаются. Если не помогло — на экране Debug
(боковое меню) во вкладке Crashes лежит отчёт о падении, его можно отправить
разработчику.

## Если что-то пошло не так — где смотреть

Инструменты, в порядке от простого к глубокому:

- **Пинг и ⚠-метки** на главном экране: ERR у узла — узел не отвечает; значок
  ⚠ — через этот узел ходят другие, и они пострадают вместе с ним (тап
  показывает, кто именно).
- **Statistics** (при поднятом туннеле), три вкладки:
  - **Stats** — трафик по каналам: видно, куда реально уходят байты;
  - **Conns** — живые соединения: какое приложение, к какому хосту, каким
    правилом и через какую цепочку. Однобокие соединения (данные только в одну
    сторону) подсвечены — обычный признак блокировки;
  - **Profiler** — запись всех соединений и DNS-резолвов в реальном времени, с
    фильтрами по приложению/домену/IP. Отвечает на вопросы «какой домен не
    резолвится», «через какой канал ушёл запрос», «куда ходит это приложение».
    У DNS-событий видно и работу DNS-групп: кто из участников ответил, кто
    промолчал.
- **Debug** (боковое меню) — журнал приложения и ядра (вкладка Log; тумблер
  verbose снимает фильтр отладочных сообщений на лету), отчёты о падениях
  ядра (Crashes), снимки его сторожа памяти (OOM) и pprof-профили для
  разработчика (Profiling).
- **Телефон греется или ест память** — VPN Settings → System → Optimization →
  **Memory limit**: в режиме Auto лимит подбирается по объёму RAM устройства;
  там же живут настройки усыпления простаивающих WireGuard-туннелей.

## Порядок настройки с нуля

> **Где что искать.** Разделы открываются из **бокового меню** — свайп от левого
> края или иконка **≡** на главном экране: *Servers* (серверы/подписки/папки),
> *Routing* (каналы, правила, tunnel apps), *DNS Settings*.

1. **Источник серверов** — меню → **Servers** → добавить, выбрав тип под ситуацию:
   - один конфиг → **одиночный сервер** (вставить ссылку/QR/файл);
   - ссылка провайдера → **подписка** (по URL — сама обновляется);
   - своя пачка серверов → **папка**.

   Нет подписки? **Get WARP** выдаст рабочий сервер без неё (см. ниже).
2. **Channels** (меню → Routing → Channels) — проверить, что Default traffic =
   **VPN** (если хотите, чтобы по умолчанию всё шло через туннель).
3. **Allow-list** (Routing → Tunnel apps) — по желанию: Off (всё через L×Box) или
   Allow-list (только выбранные приложения).
4. **Rules** (Routing → Rules) — исключения: реклама → Block, локальные домены →
   Direct, и т.п. (можно скопировать из Presets).
5. **DNS** (меню → DNS Settings) — из коробки стоит группа Shield DNS, которая
   переживает отказ любого отдельного пути; трогать что-то нужно, только если
   хотите жёстко зашифрованный DNS или свои резолверы.
6. **Detour** — по желанию: если нужен выход через цепочку серверов, задайте его в
   настройках сервера/подписки/папки (см. раздел про detour).
7. **Connect** — замочек. Готово.

## Рецепты

### Раздать VPN на другие устройства по Wi-Fi

Телефон с L×Box работает как прокси-шлюз: ноутбук, телевизор или второй телефон
в той же сети ходят в интернет через ваш туннель. Своего клиента им ставить не
нужно — только прописать прокси в настройках Wi-Fi.

**На телефоне с L×Box:**

1. **VPN Settings → Mode** → режим **VPN + Proxy** (туннель работает как
   обычно, плюс появляется прокси-порт) или **Local proxy** (без туннеля, тогда
   VPN-слот Android останется свободным — годится, если на телефоне уже
   работает другой VPN).
2. В блоке **Local proxy**:
   - **Protocol** — **Mixed** (HTTP + SOCKS5 на одном порту): подходит и
     Android-устройствам, и настройкам Wi-Fi-прокси, которые умеют только HTTP;
   - **Listen address** — **0.0.0.0** (все интерфейсы). Дефолтный `127.0.0.1`
     виден только самому телефону — с него другие устройства не подключатся;
   - **Port** — например 2080 (допустимо 1024..65535);
   - **авторизация** — при LAN-адресе включается принудительно и выключить её
     нельзя. Задайте логин и пароль, они понадобятся на клиентах.
3. Подключите VPN и посмотрите **локальный IP телефона** (Android: Настройки →
   Wi-Fi → текущая сеть → IP-адрес). Обычно вида `192.168.x.y`.

**На устройстве-клиенте** — Wi-Fi-сеть → изменить → **Прокси: вручную**:
адрес — IP телефона, порт — ваш (2080), логин/пароль — заданные выше. На
компьютере то же самое делается в системных настройках прокси или в самом
браузере.

Ограничения этого способа:

- **Оба устройства должны быть в одной сети** (один роутер или раздача с этого
  же телефона). Через мобильный интернет извне это не работает — адрес
  `192.168.x.y` за пределами локальной сети не существует.
- **Прокси ловит не весь трафик клиента.** Настройки Wi-Fi-прокси в Android и
  большинстве систем уважают браузеры и часть приложений; игры, мессенджеры и
  всё, что ходит мимо системного прокси, пойдут напрямую. Это не то же самое,
  что VPN на клиенте.
- **Раздача интернета (точка доступа) сама по себе трафик не туннелирует** —
  клиенты хотспота идут мимо VPN, пока не пропишут прокси вручную.
- **Не выставляйте LAN-прокси в чужой/публичной сети** — открытый порт видят
  все соседи по сети. Пароль обязателен именно поэтому.
- Правила маршрутизации к этому трафику применяются: в редакторе правила
  секция **Inbound** позволяет развести «пришло из туннеля» и «пришло с
  прокси» — например, гостей с прокси пускать в отдельный канал.

### Связка с ByeDPI (и другими локальными прокси)

ByeDPI (ByeByeDPI) — отдельное приложение, которое обходит DPI-блокировки
локально, без сервера, и отдаёт результат **локальным SOCKS5-прокси**. L×Box
умеет взять такой прокси **как обычный сервер** — и дальше он живёт по всем
правилам приложения: попадает в каналы, может быть detour'ом, участвовать в
автовыборе.

Зачем: часть сайтов открывается одним обходом DPI, без заграничного сервера —
быстрее и не тратит трафик VPS. И наоборот, ByeDPI можно поставить *перед*
своим VPN как дополнительный слой маскировки.

**Настройка (проверено):**

1. В **ByeDPI** включите режим прокси — он поднимет `127.0.0.1:1080`
   (порт может отличаться, посмотрите в его настройках). Пароль в ByeDPI
   ставить желательно.
2. В L×Box: **Routing → Tunnel apps** → режим **Deny-list** → добавьте туда
   **ByeDPI**. Шаг обязательный: иначе трафик самого ByeDPI зайдёт обратно в
   туннель и получится петля.
3. Добавьте ByeDPI как сервер: **Servers → +** → вставьте ссылку
   `socks5://127.0.0.1:1080#ByeByeDpi` (с паролем —
   `socks5://логин:пароль@127.0.0.1:1080#ByeByeDpi`). Можно и вручную через
   мастер добавления, тип SOCKS.
4. Дальше — как с любым сервером. Три рабочих сценария:
   - **Отдельный канал** — завести канал с фильтром на этот узел и правилом
     отправлять в него нужные домены (YouTube и т.п.), пока остальное идёт
     через заграничный сервер;
   - **Detour** — назначить ByeDPI detour'ом своего VPN-сервера: тогда трафик
     сначала проходит обфускацию, потом уходит в туннель;
   - **В автовыборе** — включить его в пул наравне с обычными узлами.

Оговорки:

- Узел `127.0.0.1` живёт только на этом телефоне — он не имеет смысла в
  бэкапе, перенесённом на другое устройство, и не будет работать, если
  ByeDPI выключен или сменил порт. Пинг такого узла при остановленном
  ByeDPI закономерно даёт ERR.
- Между **ByeDPI** и **ByeByeDPI** (это разные сборки) на форуме сообщали о
  разном поведении: у части пользователей связка взлетела только с
  оригинальным ByeDPI, у части одинаково работали обе. Если трафик не пошёл —
  попробуйте вторую сборку, прежде чем искать причину в L×Box.
- Тем же способом подключается **любой** локальный прокси на телефоне
  (собственный SOCKS5/HTTP-клиент другого сервиса): ссылка `socks://` или
  `socks5://` на его адрес плюс Deny-list, чтобы не закольцевать трафик.

## Get WARP — сервер без подписки

Нет своей подписки? На экране подписок есть **Get WARP** — визард, который
регистрирует бесплатный Cloudflare WARP и добавляет его как сервер. Приватный
ключ генерируется на телефоне и его не покидает. Доступны транспорты WireGuard
и **MASQUE** (Cloudflare QUIC/CONNECT-IP) — MASQUE лучше проходит там, где
обычный WireGuard режут.

Если стандартный адрес WARP на вашей сети заблокирован или еле живой:

- в *Advanced* визарда можно задать **свой endpoint** (`IP:port`), а у MASQUE —
  выбрать порт из списка рабочих;
- кнопка **Make experiment** в том же визарде создаёт папку-эксперимент
  **SCAN WARP**: генерирует пачку WARP-вариантов (WireGuard / AWG / MASQUE) по
  диапазонам адресов Cloudflare и прогоняет их пингом — живые остаются в папке,
  мёртвые выключаются сами. Так можно найти рабочий endpoint именно на вашей
  сети без ручного перебора.

## Список серверов — поиск и метки

**Фильтры.** Над списком серверов на главном экране — фильтры: текстовый
(по имени/regex), чипы по подписке, по протоколу, по транспорту. Слева от
текстового поля есть тумблер **`!`** — он инвертирует фильтр (показать всё,
что **не** совпадает); такой же тумблер есть у чипов. Настройки фильтра
запоминаются отдельно для каждого канала. Синтаксис шаблонов — в разделе
[Регулярные выражения](#регулярные-выражения-regex).

**Эмодзи-метки.** У сервера есть эмодзи-метка в теге. Её можно поменять в
**Node Settings** (кнопка-пикер эмодзи), а при добавлении сервера метка
подставляется автоматически по стране/имени.

**Пинг у каждого канала свой.** Замеры задержки хранятся отдельно для каждого
канала: адрес и таймаут проверки настраиваются per-канал, поэтому «180 мс»,
измеренные разными проверками, — разные величины. Переключение канала не
стирает чужие результаты. Если в текущем канале узел ещё не мерили, показывается
последний замер из другого канала — приглушённый и со значком `~`
(«приблизительно»): число есть, но получено другой проверкой.

## Регулярные выражения (regex)

Regex — это шаблон для поиска по тексту. В L×Box он встречается в четырёх
местах, и **везде работает одинаково**:

| Где | Что фильтрует |
|---|---|
| **Node filter** в редакторе канала | какие серверы попадают в канал |
| **Поиск** над списком серверов | что показывать в списке |
| **Правило членства** авто-узла в папке | какие серверы входят в пул |
| **Условие `matches`** в правилах обработки подписки (Filters) | к каким узлам применить правило |

Простой текст — уже рабочий фильтр: `Germany` найдёт все серверы, у которых в
имени есть это слово. Спецсимволы нужны, только когда простого совпадения мало.

### Отрицание — тумблер `!`, а не символ в шаблоне

Частый вопрос: «как написать *всё, кроме этого*?» Через сам шаблон это делается
громоздко, поэтому отрицание вынесено в отдельную кнопку.

Слева от поля ввода есть тумблер **`!`** — он инвертирует результат: показать
(или взять в канал) всё, что **не** совпало с шаблоном. Такие же тумблеры есть
у чипов фильтров (по подписке, протоколу, транспорту) — каждая категория
инвертируется независимо.

- канал «всё, кроме российских серверов»: шаблон `🇷🇺`, тумблер **`!`** включён;
- канал «только российские»: тот же шаблон, тумблер выключен.

В правилах обработки подписки (Filters) роль тумблера играет галка **Not** у
условия — смысл тот же.

### Что писать в шаблоне

Синтаксис — стандартный regex в стиле JavaScript / Perl (движок Dart RegExp).
Самое нужное:

| Пишем | Значит | Пример |
|---|---|---|
| `\|` | ИЛИ | `🇩🇪\|🇳🇱` — немецкие или голландские |
| `^` | начало имени | `^Premium` — имя начинается с «Premium» |
| `$` | конец имени | `2$` — имя заканчивается на «2» |
| `.` | любой символ | `A.1` — «A», что угодно, «1» |
| `.*` | любой текст (в т.ч. пустой) | `DE.*Fast` — «DE», потом где-то «Fast» |
| `\d` | любая цифра | `\d\d` — две цифры подряд |
| `[abc]` | один из перечисленных символов | `[123]` — «1», «2» или «3» |
| `( )` | группа (нужна для карманов `$1` в правилах подписки) | `^(\w+)-` |
| `\.` | точка как обычный символ | `\.ru` — именно «.ru» |

Полное описание синтаксиса — в
[документации Dart RegExp](https://api.dart.dev/stable/dart-core/RegExp-class.html)
(движок совпадает с
[ECMAScript-регулярками](https://developer.mozilla.org/ru/docs/Web/JavaScript/Reference/Regular_expressions)).
Проверить шаблон удобно на [regex101.com](https://regex101.com/), выбрав
диалект **ECMAScript (JavaScript)**.

### Примеры под задачи

| Задача | Шаблон | Тумблер `!` |
|---|---|---|
| Только немецкие и голландские | `🇩🇪\|🇳🇱` | выкл |
| Всё, кроме пробников и тестовых | `test\|trial\|пробн` | **вкл** |
| Только серверы своей папки с префиксом `mullvad-` | `^mullvad-` | выкл |
| Серверы с номерами 1–3 в конце имени | `[123]$` | выкл |
| Всё, кроме серверов с молнией в имени | `⚡` | **вкл** |
| Отключить сразу несколько стран по названию | `\b(?:Russia\|China\|Hong Kong\|Singapore)\b` | **вкл** |
| Финские узлы, кроме дублей `#2`, `#3`… | `🇫🇮(?!.*#)` | выкл |
| Только премиум-узлы, но не пробные | `^(?=.*Premium)(?!.*trial)` | выкл |

Последний пример — уже продвинутый синтаксис (см. следующий раздел); в
большинстве случаев проще воспользоваться тумблером `!`.

### Отрицание внутри шаблона

Тумблер `!` переворачивает результат целиком: «покажи всё, что **не** совпало».
Но иногда отрицать нужно только **часть** условия, а не весь фильтр. Например:
взять немецкие серверы, **кроме** пробных — тут одно условие положительное
(«есть DE»), другое отрицательное («нет trial»), и тумблером их уже не выразить:
включённый `!` перевернул бы оба сразу.

Для таких случаев есть просмотр вперёд и назад — проверка «что стоит рядом», без
захвата самого текста:

| Конструкция | Значит | Пример |
|---|---|---|
| `(?!…)` | дальше **не** идёт | `^(?!.*trial)` — нигде нет «trial» |
| `(?=…)` | дальше идёт | `^(?=.*Premium)` — где-то есть «Premium» |
| `(?<!…)` | перед этим **не** было | `(?<!trial )DE` — «DE», но не после «trial » |
| `[^…]` | любой символ, **кроме** перечисленных | `[^0-9]$` — имя не заканчивается цифрой |

Тот самый пример «немецкие, кроме пробных» записывается так:
`^(?!.*trial).*DE` — сначала проверка «нигде в имени нет trial», потом обычный
поиск «DE». Тумблер `!` при этом выключен: шаблон уже содержит нужное
отрицание внутри себя.

Отрицания комбинируются: `^(?=.*Premium)(?!.*trial)` — «есть Premium И нет
trial». Конструкции `(?>…)` (атомарные группы) и `X++` (жадные квантификаторы)
не поддерживаются — движок отвергнет такой шаблон.

**Рабочая формула** — «что ищем, чего не должно быть дальше»:

```
(условие)(?!.*(запрет))
```

Пример: нужны финские узлы, но без дублей `🇫🇮 Финляндия #2`, `#3` и т.д.

```
🇫🇮(?!.*#)
```

Читается так: флаг 🇫🇮, и дальше в имени нигде нет решётки. Тумблер `!`
выключен — отрицание уже внутри шаблона.

> **Самая частая ошибка: `.*` внутри скобок пропущено.** Шаблон `🇫🇮(?!2)`
> выглядит логично («флаг, а дальше не двойка»), но берёт **все** финские
> узлы, включая `#2`. Причина: `(?!2)` требует, чтобы двойка стояла
> **вплотную** к флагу (`🇫🇮2`), а в имени между ними ещё « Финляндия #».
> Такого сочетания нет ни у кого — условие выполняется для всех.
>
> | Шаблон | Результат |
> |---|---|
> | `🇫🇮(?!2)` | ❌ берёт всё: ищет `2` вплотную к флагу |
> | `🇫🇮(?!.*#)` | ✅ финские без номера (`#2`, `#3`, любой) |
> | `🇫🇮(?!.*#2)` | ✅ финские, кроме именно `#2` |
>
> То же правило работает и для положительного просмотра: `(?=Premium)` —
> «Premium вплотную», `(?=.*Premium)` — «Premium где-то дальше в имени».

> **Грабля с эмодзи в квадратных скобках.** Шаблон вида
> `^(?![✨⭐🏁🏳️🏴])(?:.*?\()` выглядит правильно, но отсекает **лишнее**:
> заодно исчезают 🇩🇪, 🇫🇷, 🌍 и прочие флаги, которых в списке нет. Причина не
> в отрицании — оно работает. Дело в том, что движок разбирает шаблон
> 16-битными кусками, а эмодзи состоит из пары таких кусков: класс
> `[✨⭐🏁🏳️🏴]` рассыпается на половинки, и общая для всех флагов половинка
> начинает совпадать сама по себе.
>
> Лечится заменой квадратных скобок на перечисление через `|`:
> `^(?!(?:✨\|⭐\|🏁\|🏳️\|🏴))(?:.*?\()`. Правило простое: **эмодзи в
> квадратные скобки не кладите**, перечисляйте через `\|`. Для одного эмодзи
> скобки не нужны вовсе.

### Что нужно знать про поведение

- **Регистр не учитывается.** `warp`, `WARP` и `Warp` совпадут одинаково — во
  всех четырёх местах. Приписка `(?i)` в начале шаблона **не работает** (Dart
  её не поддерживает) и просто сломает шаблон — она не нужна, регистр и так
  игнорируется. Исключение — правила обработки подписки: там у условия есть
  отдельная галка **Case-sensitive**, включающая учёт регистра.
- **Совпадение ищется в любом месте имени**, а не с начала: шаблон `DE` найдёт
  и «DE-1», и «Nord-DE». Чтобы привязать к началу или концу — `^` и `$`.
- **Пустое поле = без фильтра** (в канал попадают все серверы).
- **Битый шаблон** подсвечивается ошибкой «Invalid regex» прямо в поле; при
  сборке конфига нерабочий фильтр канала игнорируется, то есть канал получает
  все серверы (а не ноль).
- **Фильтр, не нашедший ни одного сервера**, показывает предупреждение — канал
  с пустым составом трафик вести не может.
- **Авто-узлы и служебные записи фильтр не прячет.** Узлы автовыбора
  (`🔀`/`🎯`), «Блокировка» и подобные служебные строки остаются в списке при
  любом шаблоне — это точки переключения, и скрывать их фильтром нельзя. Если
  после фильтра «только 🇫🇮» в списке видны `Europe | Auto` и «Блокировка» —
  шаблон ни при чём, он к ним не применяется.
- В редакторе канала под полем есть **живое превью**: `matched: 12 / 37 nodes` —
  сколько серверов поймал шаблон, ещё до сохранения (при включённом `!` строка
  начинается с `excluded →`). Такое же превью есть у правила членства
  авто-узла. Если превью пишет «No node snapshot», список серверов ещё не
  подгружен — подключитесь, чтобы увидеть числа.

## Быстрое подключение

Не обязательно открывать приложение, чтобы включить VPN:

- **Плитка в шторке (Quick Settings).** Добавьте плитку L×Box в панель быстрых
  настроек (шторка → карандаш/редактирование плиток). Тап включает/выключает
  VPN последним использованным профилем.
- **Ярлык на рабочем столе.** Ярлык быстрого подключения так же переключает VPN
  одним нажатием, без открытия основного экрана.

При активном подключении в уведомлении есть кнопки **Stop** и **Reconnect** —
переподключиться можно прямо из шторки.

## Автоматизация — включать VPN по событиям

L×Box умеет управляться из приложений-автоматизаторов (**Tasker, MacroDroid,
Llama, Automate**) — телефон сам включает/выключает VPN и переключает серверы по
событиям, без вашего участия. Типичные сценарии:

- подключаться к домашнему Wi-Fi → **выключать** VPN, к чужому/публичному →
  **включать**;
- запуск конкретного приложения → переключиться на нужный сервер/канал;
- по расписанию или по геозоне — включать/выключать туннель.

Автоматизация **по умолчанию выключена**. Включается в **App Settings →
Automation** (там же можно разрешить L×Box отдавать наружу свои события —
подключился/отключился/обновилась подписка), после чего в автоматизаторе
выбираете L×Box как плагин и нужную команду (Start / Stop / Reconnect / выбрать
сервер и т.п.).

> **Полная инструкция** со списком всех команд, событий и готовыми рецептами
> (в том числе управление из shell/ADB) — в [AUTOMATION.md](AUTOMATION.md).

## Backup — перенос настроек

Открывается из меню → **App Settings → General → Backup & restore**. Экран
делает снапшот вашей конфигурации: подписки, каналы, правила (Rules) и настройки
приложения.
Экспорт сохраняет снапшот в файл, импорт — восстанавливает его (с предпросмотром
перед применением). Это удобный способ перенести настройки на новый телефон или
сохранить их перед переустановкой.
