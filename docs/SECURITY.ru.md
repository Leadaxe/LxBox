## 1. Модель угроз

L×Box — VPN-клиент: он принимает трафик других приложений, заворачивает его в туннель и отправляет на удалённый узел. Отсюда четыре класса угроз:

| Класс | Угроза | Разбор |
|-------|--------|--------|
| **Утечка трафика** | Трафик уходит мимо туннеля или мимо правил маршрутизации: сервер назначения видит IP пользователя, правила не действуют | [§2](#2-утечки-трафика-мимо-туннеля) |
| **Локальная поверхность** | Другое приложение на устройстве пользуется открытым локальным прокси или API клиента | [§3](#3-локальная-поверхность-атаки) |
| **Входящие из туннеля** | Сервер или пир клиентского туннеля (WireGuard, OpenVPN, OpenConnect) открывает соединение внутрь: к устройству, в локальную сеть или в интернет с IP пользователя | [§4](#4-входящие-соединения-из-клиентских-туннелей) |
| **Кража секретов** | Приватные ключи, токены устройства, учётные данные подписок утекают из приложения или из бэкапа | [§5](#5-секреты-на-устройстве) |

## 2. Утечки трафика мимо туннеля

### 2.1 Две оси сопоставления: КУДА и КТО

Правило маршрутизации сопоставляет трафик по одной из двух независимых осей:

- **КУДА** (destination) — по адресу назначения: `ip_cidr`, домен, порт. Отправитель не важен.
- **КТО** (source / owner) — по приложению, которому принадлежит сокет: UID → `package_name`.

Одна ось не заменяет другую: правило по адресу не видит владельца, правило по владельцу не видит адрес. Защита от утечек нужна по обеим.

### 2.2 `0.0.0.0/0 → reject` — фильтр по адресу назначения

`0.0.0.0/0` — CIDR, который совпадает с любым IPv4-адресом назначения. Правило с ним работает по оси КУДА:

```json
{ "ip_cidr": ["0.0.0.0/0"], "action": "reject" }
```

- Совпадает со всем IPv4-трафиком: с приложениями и фоновыми процессами, независимо от владельца.
- `reject` — ядро отвечает RST или ICMP unreachable; `drop` — молча отбрасывает пакет.

Отличие от `final = reject`:

| | Когда срабатывает | Правила ниже |
|---|---|---|
| `final = reject` | трафик не совпал ни с одним правилом | все проверены до него |
| `0.0.0.0/0 → reject` | на своём месте в списке, для любого IPv4 | не срабатывают |

Последним в списке такое правило работает как kill-switch: трафик, не совпавший ни с одним правилом выше, наружу не выходит. Так закрываются утечки по оси КУДА.

### 2.3 Трафик без владельца: почему `curl --interface tun0` обходит атрибуцию

Трафик приложения обычно проходит так:

```
сокет приложения → перехват VpnService → tun0 → ядро видит UID → находит пакет → правила
```

Ядро знает UID сокета и сопоставляет его с `package_name` установленного приложения.

Процесс, который сам привязывает сокет к интерфейсу `tun0` (`curl --interface tun0`, Termux, сетевые утилиты), минует перехват VpnService:

```
curl bind(tun0) → пишет прямо в tun → ядро: UID = INVALID_UID → package = "" (пусто)
```

Такой трафик называют бесхозным (ownerless):

- он не прошёл через перехват VpnService, поэтому владелец сокета не определяется: `INVALID_UID`;
- без UID ядро не сопоставляет трафик ни с одним установленным приложением: `package` — пустая строка;
- в туннеле оказывается трафик, не приписанный ни системе, ни приложению из списка.

Угроза: приложение, исключённое из VPN, привязывает сокет к `tun0`, и его трафик идёт через туннель. Так оно узнаёт адрес VPN-сервера и видит, что VPN включён. Allowlist и detour на этот трафик не действуют: у него нет владельца, с которым они сравнивают. Воспроизводится одной командой `curl --interface tun0 …`.

### 2.4 Правило «Unknown traffic» — фильтр по владельцу сокета

Правило ловит бесхозный трафик из [§2.3](#23-трафик-без-владельца-почему-curl---interface-tun0-обходит-атрибуцию) по оси КТО. Определение пресета `block_unknown` ([`wizard_template.json`](../app/assets/wizard_template.json)):

```json
{ "invert": true, "package_name_regex": "^" }
```

Как это читается:

- `package_name_regex: "^"` — регулярное выражение `^` совпадает с любой строкой, включая пустую: «пакет есть»;
- `invert: true` — переворачивает условие: правило ловит трафик, у которого пакет не определён (пусто, `INVALID_UID`).

У правила стоит `inbound: ["tun-in"]`, поэтому оно действует только на туннель:

- соединения на локальном прокси (`mixed-in`) правило не трогает;
- в чистом режиме Proxy приложение не активный VPN, `getConnectionOwnerUid` ничего не атрибутирует, и правило бездействует, а не отвергает каждое соединение.

Пресет включён по умолчанию. Действие задаёт переменная `outbound`:

| Значение | Поведение |
|-------|----------|
| `direct` (по умолчанию) | Бесхозный трафик выходит напрямую, мимо туннеля. Процесс видит адрес провайдера, а не сервера. Сбой атрибуции не лишает поток сети |
| `reject` | Бесхозный трафик наружу не выходит. Строгий режим: при сбое атрибуции (системные UID, промах `find_process`) у потока нет сети |

Что даёт правило:

1. **Адрес сервера не раскрывается.** Процесс, привязавший сокет к `tun0` в обход VpnService, не выходит через туннель.
2. **Через туннель идёт только атрибутированный трафик.** Всё без владельца уходит напрямую или отбрасывается.
3. **Ось другая, чем в §2.2.** Приложение с валидным UID и адресом назначения `1.2.3.4` ловится правилом `0.0.0.0/0`, но не правилом «Unknown traffic». Бесхозный трафик — наоборот.

**Как проверить на устройстве.** Исключите Termux из VPN (per-app режим) и выполните из Termux:

```bash
curl --interface tun0 https://ifconfig.me/ip
```

Ожидаемый ответ:

| Правило «Unknown traffic» | Ответ |
|---|---|
| включено, `direct` (по умолчанию) | адрес провайдера: соединение вышло мимо туннеля |
| включено, `reject` | таймаут |
| выключено | адрес сервера — утечка |

📖 Та же проверка, механика ядра Android (`SO_BINDTODEVICE` на Linux 5.7+) и то, как другие клиенты обращаются с `INVALID_UID`, — в двух статьях на Хабре: [часть 1, обзор](https://habr.com/ru/articles/1088980/), [часть 2, разбор исправления](https://habr.com/ru/articles/1089082/). Авторы требуют reject для неизвестного владельца в любом per-app режиме. У нас это значение `reject`; по умолчанию стоит `direct`, чтобы сбой атрибуции давал прямое соединение, а не отсутствие сети.

**Итог по утечкам.** Бесхозный трафик входит в tun мимо перехвата VpnService (`curl --interface tun0`, bind из Termux). UID у него не определяется, пакет пустой. Адресные правила вроде `0.0.0.0/0` не отличают его от обычного, отличает только «Unknown traffic». Поэтому защита от утечек держится на обеих осях: КУДА (§2.2) и КТО (§2.4).

### 2.5 Слои: движок маршрутизации и журнал соединений

Бесхозный трафик проходит через два независимых слоя:

- **слой маршрутизации** — движок видит пакет с пустой атрибуцией и применяет к нему действие пресета `block_unknown`;
- **журнал соединений** — поток Live/Profiler, который питается от libbox CommandClient. Clash API `/connections` в приложении нет (§122).

«Правило сработало» и «соединение видно в журнале» относятся к разным слоям. Бесхозное соединение от bind на `tun0` появляется в Live/Profiler коротким событием open+close (профайлер работает с `FilterState(All)`, §176). Действие пресета к нему при этом применено.

Подробнее про диагностические слои — [`DIAGNOSTICS.md`](DIAGNOSTICS.md).

## 3. Локальная поверхность атаки

Угроза: другое приложение на том же устройстве пользуется локальным прокси или API клиента. Этот класс уязвимостей находили в мобильных VLESS-клиентах.

| Мера | Как устроено | Почему |
|---------|---------------|-----|
| **Вход только через TUN** | По умолчанию SOCKS5/HTTP-прокси на localhost нет: трафик входит только через TUN | Через открытый прокси без авторизации любое приложение незаметно ходит через VPN |
| **Авторизация прокси вне localhost** | Если `proxy_listen` — не loopback-адрес, авторизация включена принудительно и не снимается | Прокси, видимый в LAN без пароля, — открытый релей |
| **Нет Clash HTTP API** | Ядро собрано без `with_clash_api`; блок `experimental.clash_api` в конфиге останавливает старт с ошибкой (§122). Управление ядром идёт через libbox CommandClient — внутрипроцессный канал без сетевого сокета | Открытый localhost-API — известная уязвимость мобильных VLESS-клиентов. Нет HTTP-поверхности — нечего сканировать и подбирать |
| **Debug API выключен по умолчанию** | Локальный HTTP Debug API (подписки, правила, настройки, `PUT /config`) не запускается, пока его не включат (`debug_enabled` по умолчанию `false`). С пустым Bearer-токеном сервер тоже не запускается | В установке по умолчанию локального HTTP-сервера нет |
| **Debug API: loopback, Bearer, проверка Host** | Слушает только `127.0.0.1`, порт по умолчанию `9269`. Все эндпоинты, кроме `/ping` и `/help`, требуют `Authorization: Bearer <token>`; пустой токен — отказ. Заголовок Host принимается только `127.0.0.1` или `localhost` (защита от DNS-rebinding): запрос через перепривязанный `evil.com` получит `403` даже с утёкшим токеном | Debug API управляет всем конфигом; доступ из LAN или через CSRF отдал бы его чужому. См. [`debug-api-reference.md`](api/debug-api-reference.md) и спеку §031 |
| **pprof — по требованию, только loopback** | Захват горутин и CPU (§207) поднимает libbox `PProfServer` на `127.0.0.1` (порты 6060–6065) на время захвата, запущенного пользователем, и затем гасит его. Авторизации нет. `network_security_config` разрешает cleartext HTTP только на loopback (`127.0.0.1`, `localhost`, `::1`) | Диагностика не держит постоянно открытый порт без авторизации, а cleartext не выходит за loopback. См. спеку §207 |
| **Ресиверы автоматизации выключены** | Ресивер автоматизации и компоненты Locale-плагина (§047, §157) объявлены `android:exported="true"` и `android:enabled="false"`: они не работают, пока пользователь не включит главный тумблер автоматизации | Без этого тумблера ни одно стороннее приложение не управляет клиентом |
| **VpnService и BootReceiver не экспортированы** | `android:exported="false"` | Сторонние приложения не могут вызвать сервисные компоненты ядра |

Источник — [`020 — Security & DPI Bypass`](spec/tasks/020F-security-and-dpi-bypass/spec.md).

> ⚠️ Включённый тумблер автоматизации (§157) открывает ресивер для любого отправителя на устройстве. Broadcast не несёт идентичности вызывающего, поэтому проверки по приложению нет (`android:permission` не задан намеренно). Команды только управляющие: старт, стоп, смена узла, выбор группы, пересборка, обновление, сброс, urltest; канала для получения секретов нет. Исходящие события несут только метки состояния. См. [`AUTOMATION.md`](AUTOMATION.md), раздел «Безопасность».

## 4. Входящие соединения из клиентских туннелей

Угроза: клиентский endpoint (WireGuard/AWG, OpenVPN, OpenConnect) — двусторонний канал. Сервер или любой пир на той стороне может сам открыть соединение внутрь, а стек gVisor принимает соединение на любой адрес. Без отдельного правила такое соединение идёт по общей маршрутизации. При `final = direct` пир получает доступ к самому устройству (`127.0.0.1`), к локальной сети пользователя и выход в интернет с его IP.

Защита — пресет **Tunnel ingress** (`tunnel-ingress`, §656, контракт 1.1.126–1.1.129):

- **Включён по умолчанию.** Существующим установкам он добавляется один раз при обновлении (поздний дефолт). Если пользователь пресет удалил, обратно он не возвращается.
- **Охват.** Все узлы с типом `wireguard`, `openvpn-client` или `openconnect`: свои серверы, члены папок и узлы подписок. Правила сопоставляются по входящему: `inbound` = тег endpoint.
- **Переключатели узла.** Блок «Incoming connections from this tunnel» на экране узла: доступ к этому устройству (`allow_local`), к локальной сети (`allow_lan`), использование устройства как шлюза (`allow_gateway`). По умолчанию все выключены. У узла подписки переключателей нет, он всегда закрыт.

Правила пресета, сверху вниз:

| Условие | Адреса назначения | Куда |
|---|---|---|
| `allow_local` | `127.0.0.0/8`, `::1/128` | `allowed_out` (по умолчанию `direct-out`) |
| `allow_lan` | частные адреса (`ip_is_private`) | `allowed_out` |
| `allow_gateway` | любые | `gateway_out` (по умолчанию `vpn-1`, как `route.final`) |
| всё остальное от этих endpoint | любые | `closed_out` (по умолчанию `reject`; можно `drop` или outbound) |

DNS-запросы от узлов без `allow_gateway` отвергаются правилом в `dns.rules`, если `closed_out` — `reject` или `drop`. Это правило не зависит от `dns_enable` пресета. Пир, которому открыт только доступ к устройству или LAN, резолвером клиента не пользуется.

## 5. Секреты на устройстве

Все секреты лежат в приватном хранилище приложения открытым текстом. Шифрования хранилища нет и не планируется: защиту даёт песочница Android.

Бэкап бывает двух форматов:
- **нативный** — снимок настроек с категориями на экране Backup;
- **LX Backup** — переносимый формат контракта, общий с лаунчером.

Конфиг ядра собирается из этих данных при каждом старте. Всё, что в нём есть, видно и там, где конфиг показывается целиком.

| Секрет | В конфиге ядра | В бэкапе | Как защищаем |
|--------|----------------|----------|--------------|
| **WARP (WireGuard): приватный ключ, токен Cloudflare, лицензия** | только приватный ключ (endpoint `wireguard`) | да, в обоих форматах: нативный — `warp_account` (категория App settings), LX Backup — `warp[]` (`private_key`, `token`, `license`) | Ключ X25519 генерируется **на устройстве**, в Cloudflare уходит только публичный. Сторонние генераторы-воркеры не используем: они выдают ключ, сгенерированный на сервере. Бэкап переносит регистрацию целиком, иначе «Add WARP» на новой машине заведёт лишнее устройство в Cloudflare. См. [§025 WARP](spec/tasks/025F-warp-integration/spec.md), §393. |
| **MASQUE: ключ ECDSA P-256, токен устройства** | только приватный ключ (endpoint `masque`) | да, в обоих форматах: нативный — `masque_account`, LX Backup — `warp[]` с `type: masque` (`private_key_der`, `token`) | Отдельная пара ключей генерируется на устройстве, в Cloudflare регистрируется (PATCH enroll) только публичная часть. Ключ и токен помечены как никогда не попадающие в логи. См. [§130 MASQUE](spec/tasks/130F-masque-warp-transport/spec.md). |
| **Подписки: URL (часто с токеном доступа)** | нет | да, в обоих форматах (записи `sources[]`) | — |
| **Учётные данные узлов** (uuid, пароли, ключи REALITY/WireGuard своих серверов) | да, в outbound/endpoint узла | своих серверов — да, в обоих форматах (тело узла); узлов подписок — нет, они заново приходят по URL | — |
| **Тело файловой подписки** (§129) | узлы — да | нет: лежит снимком `HttpCache` (ключ `file:<uuid>`) только на устройстве | — |
| **HWID подписки** (`x-hwid`) | нет | глобальный — только в нативном (категория App settings); свой HWID подписки (§289) — в обоих форматах, в `identity` | Не секрет, а постоянный идентификатор установки для панелей с лимитом устройств (Remnawave). С §658 уходит по умолчанию вместе с `x-device-os` / `x-ver-os` / `x-device-model`; выключается тумблером «Send HWID». В бэкапе **намеренно**: на другом устройстве восстановленный бэкап даёт тот же HWID, панель видит одно устройство, перенос не тратит слот. Отдельное устройство для панели — кнопка Regenerate после восстановления. |
| **Bearer-токен Debug API** | нет | только нативный, отдельной категорией «Debug API config», по умолчанию выключенной; в LX Backup нет | Debug API по умолчанию выключен и слушает только loopback (см. §3). |
