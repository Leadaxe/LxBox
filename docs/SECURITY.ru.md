## 1. Модель угроз

L×Box — VPN-клиент: он принимает трафик чужих приложений, заворачивает его в туннель и отправляет на удалённый узел. Отсюда три класса угроз, и от каждого мы защищаемся:

| Класс | Угроза | Разбор |
|-------|--------|------------|
| **Утечка трафика** | Трафик уходит мимо туннеля или мимо политики маршрутизации — деанонимизация, обход просто не работает | [§2](#2-утечки-трафика-мимо-туннеля) |
| **Локальная поверхность** | Открытый локальный прокси или API, которым может воспользоваться другое приложение на устройстве | [§3](#3-локальная-поверхность-атаки) |
| **Кража секретов** | Приватные ключи, токены устройства, учётные данные подписок утекают из приложения | [§4](#4-секреты-на-устройстве) |

## 2. Утечки трафика мимо туннеля

### 2.1 Две оси сопоставления: КУДА и КТО

Любое правило маршрутизации сопоставляет трафик по одной из двух независимых осей:

- **КУДА** (destination) — по адресу назначения пакета: `ip_cidr`, домен, порт. Отправитель не важен.
- **КТО** (source / owner) — по тому, **какому приложению принадлежит сокет**: UID → package_name.

Это разные множества, и путать их нельзя. Защита от утечек строится на обеих осях, но правила разные.

### 2.2 `0.0.0.0/0 → reject` — фильтр по адресу назначения

`0.0.0.0/0` — это IP-CIDR для «**любой IPv4-адрес назначения**». Правило с ним сопоставляет трафик по оси **КУДА**:

```json
{ "ip_cidr": ["0.0.0.0/0"], "action": "reject" }
```

- Матчит **весь** IPv4-трафик без разбора — и приложения, и фоновые процессы, независимо от владельца.
- `reject` = ядро отбрасывает пакет (RST / ICMP-unreachable либо тихий drop).
- Практически равнозначно `final = reject`, **если** правило последнее и выше ничего не сработало. Разница:
  - `final` — фолбэк для трафика, который **не попал ни под одно правило**.
  - `0.0.0.0/0` — **активное** правило: матчит буквально всё и обрывает цепочку, из-за чего правила ниже не выполняются.

**Назначение:** kill-switch. «Если ничего из allowlist не совпало — наружу не выпускать». Закрывает утечки по адресной оси.

### 2.3 Трафик без владельца: почему `curl --interface tun0` обходит атрибуцию

Обычный путь трафика приложения:

```
сокет приложения → перехват VpnService → tun0 → ядро видит UID → резолвит пакет → правила
```

Ядро знает UID сокета и сопоставляет его с `package_name` установленного приложения. Трафик «подписан» владельцем.

Но процесс, который биндится **напрямую на интерфейс tun0** (`curl --interface tun0`, termux, низкоуровневые сетевые утилиты), обходит слой перехвата VpnService:

```
curl bind(tun0) → пишет в tun «сбоку» → ядро: UID = INVALID_UID → package = "" (пусто)
```

Почему такой трафик называют **бесхозным** (ownerless):

- Он не прошёл через штатную точку входа (перехват VpnService) → **владелец сокета не резолвится** → `INVALID_UID`.
- С пустым UID ядро **не может сопоставить** трафик ни с одним установленным приложением → `package` пустая строка.
- В итоге внутри туннеля оказывается трафик, **не приписанный ничему**: ни системе, ни приложению из списка — процесс залез в tun самостоятельно.

**Чем опасно:** такой трафик может уйти мимо политики маршрутизации (например, мимо вашего allowlist или detour) — это потенциальный канал утечки. Воспроизводится тривиально (`curl --interface tun0 ...`), так что дыра реальная, а не теоретическая.

### 2.4 Правило «Unknown traffic» — фильтр по владельцу сокета

Оно ловит бесхозный трафик из [§2.3](#23-трафик-без-владельца-почему-curl---interface-tun0-обходит-атрибуцию) — по оси **КТО**. Определение пресета `block_unknown` ([`wizard_template.json`](../app/assets/wizard_template.json)):

```json
{ "invert": true, "package_name_regex": "^" }
```

Как это читается:

- `package_name_regex: "^"` — регекс `^` матчит **любую** строку (включая пустую): «пакет какой-то есть».
- `invert: true` — переворачивает условие → правило ловит трафик, у которого **пакет НЕ определён** (пусто / `INVALID_UID`).

То есть правило изолирует ровно тот трафик, который входит в туннель без привязки к установленному приложению.

**Что с ним делать** (переменная `outbound` в пресете):

| Значение | Поведение |
|-------|----------|
| `reject` (по умолчанию) | отбросить — бесхозный трафик наружу не выпускается вовсе |
| `direct` | отправить мимо VPN (прямой выход, минуя туннель) |

**Зачем это нужно:**

1. **Закрыть утечку.** Процесс, залезший в tun за спиной VpnService, не сможет вынести трафик мимо политики маршрутизации.
2. **Гигиена туннеля.** Через прокси идёт только трафик легитимных приложений; всё неатрибутированное берётся под контроль (drop или direct).
3. **Ось другая, чем в §2.2.** Легитимное приложение с валидным UID и адресом назначения `1.2.3.4` ловится правилом `0.0.0.0/0`, но **не** ловится «Unknown traffic» — множества почти не пересекаются.

### 2.5 Слои: движок маршрутизации и журнал соединений

Важная диагностическая оговорка. Бесхозного трафика касаются два независимых слоя: **слой маршрутизации** (движок видит пакет и его пустую атрибуцию и применяет `block_unknown`) и **журнал соединений** (поток Live/Profiler, который питается от libbox CommandClient; Clash API `/connections` нет — он удалён при переезде на CommandClient в §122).

Следствия:

- «Правило сработало» и «соединение видно в журнале» описывают **разные слои**. Слой маршрутизации всегда отвергает бесхозный трафик от bind на `tun0` через `block_unknown`, независимо от того, что показывает журнал.
- С §176 (профайлер переехал на `FilterState(All)`) бесхозное соединение от bind на `tun0` **всё же** появляется в журнале Live/Profiler — как короткое событие open+close, — хотя на слое маршрутизации оно по-прежнему отвергается. (До §176 трекер соединений его отфильтровывал, так что прежняя формулировка «его там не будет» больше не верна.)

Подробнее про диагностические слои — [`DIAGNOSTICS.md`](DIAGNOSTICS.md).

## 3. Локальная поверхность атаки

Угроза: другое приложение на том же устройстве злоупотребляет нашим локальным прокси или API (класс уязвимостей, замеченный в мобильных VLESS-клиентах).

| Мера | Как защищаемся | Почему |
|---------|---------------|-----|
| **Вход только через TUN** | По умолчанию нет SOCKS5/HTTP-прокси на localhost — трафик входит только через TUN | Открытый локальный прокси без авторизации = любое приложение молча ходит через VPN |
| **Локальный прокси — авторизация вне localhost** | Если `proxy_listen` ≠ `127.x` (доступен из сети), авторизация включается принудительно | Прокси, видимый в LAN и без пароля, — это открытый релей |
| **Нет Clash HTTP API** | Clash API удалён целиком при переезде на CommandClient (§122) — ядро собрано без `with_clash_api`, а блок `experimental.clash_api` в конфиге теперь даёт **фатальный** отказ старта. Управление ядром идёт через libbox **CommandClient** — внутрипроцессный командный канал **без единого сетевого сокета** | Открытый localhost-API — классическая уязвимость мобильных VLESS-клиентов; без HTTP-поверхности нечего сканировать и нечего брутфорсить |
| **Debug API — opt-in, по умолчанию выключен** | Локальный HTTP Debug API (CRUD подписок, правил, настроек, `PUT /config`) не запускается, пока пользователь его не включит (`debug_enabled` по умолчанию `false`); пустой Bearer-токен тоже оставляет сервер выключенным | В установке по умолчанию локальной HTTP-поверхности атаки не существует |
| **Debug API — loopback + Bearer + проверка Host** | Слушает только `127.0.0.1` (порт по умолчанию `9269`). Все эндпоинты, кроме `/ping` и `/help`, требуют `Authorization: Bearer <token>` (пустой токен = отказ). Проверка заголовка Host отвергает всё, кроме `127.0.0.1` / `localhost` (защита от DNS-rebinding), так что перепривязанный `evil.com` получит `403` даже при утёкшем токене | Доступ к полному управлению конфигом из LAN или через CSRF был бы катастрофой; см. [`debug-api-reference.md`](api/debug-api-reference.md) и спеку §031 |
| **pprof-сервер — по требованию, только loopback, без авторизации** | Захват горутин/CPU (§207) поднимает libbox `PProfServer` на `127.0.0.1` (порты 6060–6065) только на время инициированного пользователем захвата, потом гасит. `network_security_config` разрешает cleartext HTTP **только** на loopback (`127.0.0.1` / `localhost` / `::1`); весь внешний трафик остаётся под запретом cleartext | Диагностика не должна открывать постоянный неавторизованный порт, а послабление для cleartext обязано оставаться в пределах loopback; см. спеку §207 |
| **Ресиверы автоматизации — exported, но выключены** | Ресивер автоматизации и компоненты Locale-плагина (§047/§157) объявлены как `android:exported="true"`, но `android:enabled="false"`, поэтому они мертвы, пока пользователь не включит главный тумблер «принимать команды автоматизации» | Выключено по умолчанию — значит, из коробки ни одно стороннее приложение не может управлять клиентом |
| **VpnService и BootReceiver не exported** | `android:exported="false"` | Сторонние приложения не могут дёргать наши сервисные компоненты ядра |

Источник и планы — [`020 — Security & DPI Bypass`](spec/features/020%20security%20and%20dpi%20bypass/spec.md).

> **Оговорка про автоматизацию (§157).** Когда главный тумблер автоматизации включён, ресивер принимает управляющие команды от **любого** отправителя на устройстве — broadcast не несёт идентичности вызывающего, поэтому пер-аппной аутентификации нет (`android:permission` намеренно не задан). Команды только управляющие (старт/стоп/смена узла/выбор группы/пересборка/обновление/сброс/urltest — канала для вытаскивания секретов нет), а исходящие события автоматизации несут только метки состояния. См. [`AUTOMATION.md`](AUTOMATION.md), раздел «Безопасность».

## 4. Секреты на устройстве

| Секрет | Как защищаем |
|--------|-------------------|
| **Приватный ключ WARP** | Ключ X25519 генерируется **на устройстве** и никогда его не покидает — в Cloudflare уходит только публичный. Сторонние генераторы-воркеры не используем (они выдают приватный ключ, сгенерированный на сервере). См. [§025 WARP](spec/features/025%20warp%20integration/spec.md). |
| **Ключ MASQUE и токен устройства** | Транспорт MASQUE (§130) использует **отдельную** пару ключей ECDSA P-256, сгенерированную на устройстве; в Cloudflare регистрируется (PATCH enroll) только публичная часть, приватный ключ в формате SEC1-DER телефон не покидает. Пер-девайсный Bearer-токен Cloudflare хранится локально и, как и приватный ключ, помечен как никогда не попадающий в логи. См. [§130 MASQUE](spec/features/130%20masque-warp-transport/spec.md). |
| **Bearer-токен Debug API** | Лежит в хранилище настроек; Debug API по умолчанию выключен и слушает только loopback (см. §3). |
| **Учётные данные подписок** | В планах: шифрованное хранилище (Android Keystore), маскирование URL в интерфейсе — см. roadmap в спеке 020. Файловая подписка (§129) дополнительно сохраняет импортированное тело как открытый снапшот `HttpCache` (ключ `file:<uuid>`) в приватном хранилище приложения; тот же пункт roadmap про шифрованное хранилище покрывает и эти снапшоты. |

## 5. Сводная таблица

| Механизм | Ось / слой | Что ловит | Затрагивает приложения? |
|-----------|--------------|-----------------|----------------|
| `0.0.0.0/0 → reject` | КУДА (IP назначения) | весь IPv4-трафик без разбора | да, все |
| `final = reject` | фолбэк | всё, что не попало под правила выше | да, кроме явно описанного |
| **Unknown traffic** (`block_unknown`) | КТО (владелец сокета) | трафик с пустым пакетом (`INVALID_UID`) | **нет** — только бесхозный |
| Нет Clash HTTP API (CommandClient) | локальная поверхность | внутрипроцессное управление, атаковать нечего | — |
| Debug API выключен по умолчанию; loopback + Bearer + проверка Host | локальная поверхность | несанкционированное управление конфигом (только opt-in) | — |
| Вход только через TUN / авторизация в LAN | локальная поверхность | использование локального прокси другими приложениями | — |
| Генерация ключей на устройстве (WARP X25519, MASQUE P-256) | секреты | утечка приватного ключа | — |

**Главный вывод:** бесхозный трафик = вошёл в tun мимо перехвата VpnService (`curl --interface tun0`, bind из termux), UID не резолвится → пакет пустой → ловится **только** правилом «Unknown traffic», а не адресными правилами вроде `0.0.0.0/0`. Поэтому полная защита от утечек требует обеих осей.
