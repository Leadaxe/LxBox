# Как работает FakeIP

FakeIP включают ради двух вещей: мгновенный DNS и отсутствие DNS-утечки до
туннеля. Механика при этом неочевидная. Ниже — разбор по шагам.

Частое заблуждение: «FakeIP — это когда пакет идёт по домену, а не по IP». Нет.
Пакет всегда идёт по IP — без него сеть не доставит ни байта. Просто этот IP
фейковый: заглушка, которую ядро умеет расшифровать обратно в домен.

## 1. Почему нужен DNS

Домен `youtube.com` — не адрес. Сеть (маршрутизаторы, кабели, IP-протокол) не
понимает слов. В заголовке каждого IP-пакета есть поле «куда», и туда влезает
только число — IP-адрес. Места под текстовый домен там нет.

Поэтому любое соединение начинается с перевода имени в число — это DNS:

```
Приложение                         DNS-сервер (провайдер)
    │  1. «какой IP у youtube.com?»       │
    ├──────────────────────────────────────▶│  ← провайдер видит домен
    │  2. «142.250.1.14»                    │
    │◀──────────────────────────────────────┤
    │  3. connect 142.250.1.14:443          │
    ▼                                        ▼
```

Шаг 1–2 неизбежен: без IP приложение не отправит пакет. Без VPN этот
DNS-запрос уже утёк провайдеру — он знает, что вы полезли на YouTube, ещё до
всякого туннеля.

## 2. Почему приложение теряет домен

Приложение знает домен (вы его ввели), но в момент установки TCP-соединения
оперирует уже только IP. Соединение открывается системным вызовом
`connect(IP, порт)` — домен туда не передаётся. Домен приложение использует
отдельно и позже (в TLS-поле SNI, в заголовке HTTP `Host`), но само соединение
— по IP.

Для обычного VPN это проблема. Что видит ядро:

```
Приложение ──[ пакет: dst = 142.250.1.14 ]──▶ ЯДРО VPN
                                            │
                        ядро видит только 142.250.1.14
                        а это какой сайт? Один IP =
                        сотни доменов на CDN. Имя потеряно.
```

Роутить по домену («ютуб — в VPN, ру-сайты — напрямую») уже нельзя: у ядра на
руках голое число, а одному IP на CDN соответствуют сотни сайтов.

## 3. Что делает FakeIP

FakeIP вклинивается в шаг резолва и подменяет ответ. Вместо реального адреса он
мгновенно выдаёт заглушку из служебного диапазона (`198.18.0.0/15` для v4,
`fc00::/18` для v6) — и одновременно запоминает соответствие у себя в таблице.

Фейк-IP работает как номерок из гардероба. Сам по себе он никуда не ведёт (в
интернете нет машины `198.18.0.7`). Но ядро держит таблицу «номерок → пальто»:
`198.18.0.7` = `youtube.com`.

```
Приложение              ЯДРО (телефон)                Интернет / VPN
    │
    │ 1. IP youtube.com?
    ├───────────────────▶ fakeip: держи 198.18.0.7
    │◀─────────────────── (запомнил: .7 = youtube.com)
    │                       ↑ мгновенно, в интернет не ходили
    │ 2. connect 198.18.0.7
    ├───────────────────▶ 3. .7 ? → смотрю в таблицу → youtube.com
    │                        4. роутинг по ДОМЕНУ → в VPN
    │                        5. реальный резолв
    │                           └─(через туннель)─▶ 142.250.1.14
    │◀════════ данные текут: приложение думает, что
              говорит с .7, реально — с 142.250 через туннель ═══▶
```

Три следствия:

- **Скорость.** Шаг 1 мгновенный — номерок выдаётся без похода в интернет.
  Реальный резолв (шаг 5) идёт позже и параллельно, приложение его не ждёт.
- **Нет утечки.** Провайдер не видит `youtube.com`. Единственный настоящий
  DNS-запрос уходит внутри туннеля. Снаружи виден лишь коннект на бессмысленный
  `198.18.0.7`.
- **Точный роутинг.** Шаг 4 работает с именем, а не с IP. По одному CDN-IP не
  различить сайты, по домену — легко.

## 4. В туннель идёт пакет с IP — просто фейковым

Пакет от приложения в туннель всегда несёт IP. Без IP пакета не существует.
Разница между режимами — только в том, какой это IP:

| Без FakeIP | С FakeIP |
|---|---|
| Пакет: `dst = 142.250.1.14` | Пакет: `dst = 198.18.0.7` |
| Настоящий IP ютуба. Приложение узнало его через DNS (и утекло). | Фейковый IP-номерок. Приложение узнало его от fakeip вместо DNS. |

В обоих случаях в туннель заходит нормальный IP-пакет. FakeIP не «убирает IP» —
он подменяет его заглушкой, которую ядро потом расшифрует.

Домен «без IP» появляется не в пакете от приложения, а дальше — на участке
ядро → VPN-сервер. Это другой участок и другой уровень.

## 5. L3 против L7: где домен ехать всё-таки может

Внутри ядро не пересылает фейковый пакет как есть. Оно его терминирует:
распаковывает соединение, вспоминает домен из таблицы и создаёт новое
соединение к VPN-серверу. В этом новом соединении домен может ехать строкой.
Причина — уровень, на котором передаётся адрес.

| Участок 1 · L3 | Участок 2 · L7 |
|---|---|
| **Приложение → Ядро** (внутри TUN). Сырые IP-пакеты. Адрес назначения — только в IP-заголовке, только число. Отсюда фейк `198.18.0.7`. | **Ядро → VPN-сервер.** Прокси-протокол (VLESS/Trojan/…). У него свой «конверт» с полем под адрес, куда влезает домен строкой. |

Соединение ядро→сервер само по себе тоже имеет IP-заголовок — но это IP самого
VPN-сервера (он всегда известен, он в конфиге). А конечный адресат
`youtube.com` едет внутри, на прикладном уровне:

```
L7  прокси-протокол: target = youtube.com:443   ← домен строкой
L4  TCP — порт
L3  IP = 1.2.3.4 (адрес VPN-сервера)            ← IP всё равно есть
```

IP на L3 никуда не делся — это адрес сервера. Домен назначения лежит этажом
выше, в полезной нагрузке. Поэтому резолвит уже сам сервер, на своей стороне:
ядро отдало ему голую строку `youtube.com`, а сервер сам спросил свой DNS и
получил настоящий IP.

Кто резолвит — зависит от протокола:

| Протокол | Кто резолвит |
|---|---|
| VLESS / VMess / Trojan / Shadowsocks / SOCKS (работают на L7) | Домен уходит серверу строкой — резолвит **сервер**. Максимально поздний резолв, правильный CDN у сервера, ноль утечки. |
| WireGuard / WARP (работают на L3) | Только IP-пакеты, конверта под строку нет. Резолвит **ядро** телефона — но DNS-запрос всё равно идёт внутри туннеля, не к провайдеру. |

Отсюда растут domain-fronting и SNI-based routing — они возможны потому, что
адрес назначения у прокси-протоколов живёт на L7, а не в IP-заголовке.

## 6. Два подводных камня

### Порядок правил: sniff перед resolve

Иногда ядру нужно перепроверить домен прямо из трафика — вытащить его из
TLS-поля SNI в ClientHello. Это делает действие `sniff`. `sniff` должен
сработать раньше, чем действие `resolve`: иначе `resolve` побежит резолвить
фейковый `198.18.0.7` как настоящий литерал, а это мусор. Правильный порядок
правил в туннеле:

```
1. sniff       ← достать домен из SNI/Host, пока он ещё виден
2. hijack-dns  ← DNS-запросы завернуть в свой движок (там fakeip)
3. resolve     ← реальный резолв, уже зная домен
```

Если `resolve` стоит первым (частая ошибка скопированных конфигов) — FakeIP
работает вполсилы: домен теряется до того, как его успели снять.

### Персистентность таблицы: store_fakeip

Таблица «фейк → домен» живёт в памяти ядра. При реконнекте (Stop→Start,
моргнула сеть, переключение LTE↔Wi-Fi) она стирается. Но приложения кэшируют
выданный фейк-IP дольше — и продолжают стучаться на `198.18.0.7`, не
перезапрашивая DNS. Ядро уже не знает этот номерок, соединения виснут на
несколько минут.

```
до реконнекта:  таблица: 198.18.0.7 = youtube.com   работает
РЕКОННЕКТ    :  таблица в памяти стёрта
после        :  приложение (кэш живёт) → connect 198.18.0.7
                ядро: «.7 — не знаю такого» → соединение виснет
```

Лечится флагом `store_fakeip`: таблица пишется на диск (в кэш-файл ядра) и при
реконнекте поднимается обратно. Номерки не теряются — залипаний нет. На
мобильном, где сеть моргает постоянно, это не опция, а необходимость.

## Коротко

- Пакет всегда с IP. FakeIP не убирает IP — подсовывает фейковый
  (`198.18.0.7`) вместо настоящего.
- Фейк-IP — это номерок. Ядро держит таблицу «фейк → домен» и расшифровывает
  его на входе в туннель.
- Домен долетает дальше, роутинг идёт по имени, а не по IP — точнее и без
  утечки провайдеру.
- Домен серверу едет на L7 (в теле прокси-протокола). На L3 в пакете всё равно
  есть IP — но это IP самого VPN-сервера.
- Кто резолвит — по протоколу. VLESS/Trojan (L7) → сервер. WireGuard/WARP (L3)
  → ядро, но через туннель.
- Два флага решают многое: `sniff` перед `resolve` + `store_fakeip` для
  переживания реконнектов.

FakeIP не заменяет обход DPI: DPI режет по SNI в ClientHello, а не по DNS. Для
обхода блокировок нужна фрагментация TLS.

---

Доступно в LxBox с версии v2.10.0: Routing → правила → FakeIP.
Диапазоны по умолчанию — `198.18.0.0/15` (v4), `fc00::/18` (v6).
