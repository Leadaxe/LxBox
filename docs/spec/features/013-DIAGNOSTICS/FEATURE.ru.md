# FEATURE 013 — DIAGNOSTICS — диагностика для пользователя и разработчика

| Поле | Значение |
|------|----------|
| Тип | Продуктовая фича |
| Поглотила | `§023F` `§031F` `§038F` `§043F` |
| Состояние | ✅ написана по коду, 2026-09-28 |

## Назначение

Когда «не работает», у разработчика нет устройства пользователя, а у
пользователя нет `adb`. Фича даёт обоим одну и ту же доказательную базу:
журнал приложения и журнал ядра, отчёты о падениях ядра и снимки его памяти,
системную причину смерти процесса, один файл-дамп «всё сразу», снимки
профилировщика живого ядра, запись живых сетевых событий и — для разработчика
на тестовом устройстве — локальный HTTP-интерфейс (Debug API), через который
то же самое читается и меняется без экрана.

Фича защищает три принципа:

- **Улика переживает сбой.** Всё, что нужно для разбора падения, пишется так,
  чтобы пережить смерть процесса: предупреждения журнала, отчёт о панике ядра,
  снимок памяти. Пользователю не нужно ничего включать заранее.
- **Диагностика не мешает работе.** Каждый канал best-effort: сбой чтения
  улики не ломает старт; шумные источники выключены по умолчанию, архивы
  ротируются, запись событий идёт только по явной команде.
- **Корневой доступ — только по явному согласию.** Debug API за токеном видит
  и меняет всё, включая секреты; поэтому он выключен по умолчанию, слушает
  только адрес самого устройства и отвергает чужие имена хоста.

## Обещания

- **P1. Источники журнала не вытесняют друг друга.** У журнала приложения и
  журнала ядра раздельные квоты (300 и 500 записей); поток одного не выдавливает
  другой; переполнение вытесняет старейшую запись своего источника. Свидетель:
  юниты «app spam не вытесняет core entries», «core spam не вытесняет app
  entries», «per-source cap drop oldest». Мутация: общий лимит на оба источника.
- **P2. Общий вид — строго по времени.** Смешанный журнал отдаётся новыми
  сверху поверх обоих источников; очистка одного источника не трогает другой.
  Свидетель: юниты «merged result отсортирован newest-first по обоим source»,
  «clearSource(app) очищает только app, core нетронут». Мутация: склейка списков
  без слияния по времени.
- **P3. Предупреждения переживают перезапуск.** Записи уровней warning и error
  каждого источника сохраняются (до 200 строк и 64 КБ на источник) и после
  перезапуска показываются с пометкой «↑ prev session»; debug и info живут только
  в памяти. Свидетель: ручная проверка — вызвать ошибку (например, `POST
  /action/emulate-error?kind=plain`), убить процесс, открыть Debug. Мутация:
  сохранение без различения уровней.
- **P4. Уровень строки ядра определяется по её тексту.** ERROR/FATAL/PANIC →
  error, WARN → warning, INFO → info, TRACE/DEBUG → debug, нераспознанное →
  info; при нескольких метках побеждает старшая. Свидетель: юниты
  «FATAL → error», «error приоритетнее warn в смешанной строке», «неизвестный
  формат → fallback info», «default-formatter формат WARN[NNNN]». Мутация:
  неизвестная строка получает уровень error.
- **P5. Пересылка журнала ядра — осознанный шаг.** По умолчанию выключена;
  включение вступает в силу только после перезапуска процесса, о чём экран
  говорит сразу и даёт кнопку «Quit & reopen app». Свидетель: ручная проверка —
  включить, не перезапуская, открыть Debug → Core: пусто; после Quit & reopen —
  строки ядра. Мутация: подсказка о перезапуске убрана.
- **P6. Подробный режим ядра включается на лету.** «Verbose (TRACE/DEBUG)»
  пропускает строки трассировки без перезапуска и недоступен при выключенной
  пересылке. Свидетель: ручная проверка `PUT /settings/core_logs_verbose` →
  DEBUG/TRACE в `/logs/core` (§345, device-verified). Мутация: режим читается
  только при старте ядра.
- **P7. Плашка о падении ядра — один раз на конкретный сбой.** После паники ядра
  главный экран один раз показывает «The core crashed last session — tap to share
  the report»; тап или закрытие гасят её для этого сбоя, следующий сбой снова её
  поднимает. Свидетель: юниты «новый краш → показываем; повторный старт →
  молчим», «следующий (более свежий) краш → снова показываем». Мутация: отметка
  «показано» без привязки к конкретному отчёту.
- **P8. Архив сбоев ограничен и цел.** Хранятся 10 свежих отчётов о панике и 5
  свежих снимков памяти; лишние удаляются целиком при старте; текущий отчёт
  ротация не трогает. Свидетель: юниты «оставляет 10 свежих, лишние каталоги
  удаляет целиком», «текущий репорт ротация не трогает», «оставляет keep свежих,
  удаляет остальные». Мутация: удаление только трейса без каталога.
- **P9. «Сбоев не было» — честный ответ.** Пустой текущий отчёт означает «паник
  не было» и в список не попадает; вкладка Crashes есть всегда и сама говорит,
  что канал покрывает только паники ядра. Свидетель: юниты «пустой файл = паник
  не было», «пустой текущий в список не попадает». Мутация: вкладка появляется
  только при непустом отчёте.
- **P10. Дамп говорит, на чём снят.** Корень дампа несёт версию приложения,
  номер сборки и версию ядра. Свидетель: ручная проверка Share dump (§378,
  device-verified). Мутация: версия ядра только внутри снимков.
- **P11. Дамп несёт тела снимков памяти, но не растёт без предела.** Тела
  отдаются только для 5 свежих снимков (текстовые — как есть, бинарные — gzip +
  base64), остальные — сводкой; журнал ядра сверх лимита — хвостом с флагом.
  Свидетель: юниты «body carries all files: text readable, binaries
  gzip+base64», «bodies only for kOomKeep freshest», «go.log over the limit keeps
  the tail and sets the flag». Мутация: тела для всех снимков.
- **P12. Debug API закрыт по умолчанию.** Выключен до явного включения; слушает
  только адрес самого устройства; токен — 32 hex-символа (128 бит), создаётся
  при первом включении. Свидетель: юниты «даёт 32 hex символа», «разные токены
  при последовательных вызовах»; loopback — ручная проверка (запрос по
  LAN-адресу устройства не соединяется). Мутация: пустой токен допускает старт.
- **P13. Без токена — только /ping и /help.** Остальное без точного заголовка
  `Authorization: Bearer <token>` даёт 401. Свидетель: юниты «GET /state без
  токена → 401», «/ping пропускает без auth», «схема должна быть именно
  `Bearer `». Мутация: регистронезависимая схема.
- **P14. Чужое имя хоста отвергается.** Запрос с Host не `127.0.0.1` /
  `localhost` получает 403 даже с верным токеном. Свидетель: юниты «evil.com →
  InvalidHost», «GET /ping с Host: evil.com → 403». Мутация: проверка хоста
  после авторизации только для защищённых путей.
- **P15. Доступ к Debug API нельзя потерять через сам API и импорт бэкапа.**
  Ключи включения, порта и токена не пишутся через `/settings/vars` (409); импорт
  с заменой, где их нет, сохраняет текущие. Свидетель: юниты «replaceRaw
  merge=false keeps device Debug API keys absent in snapshot», «Debug API keys
  from snapshot win»; запрет в `/settings/vars` — `без свидетеля`. Мутация:
  импорт с заменой переписывает `vars` целиком.
- **P16. Файловые маршруты не выходят за свои каталоги.** Имена с обходом пути
  и имена вне белого списка отвергаются (404/400). Свидетель: юниты «traversal в
  &file= отвергается», «не-whitelist имя → 404, даже если файл существует».
  Мутация: имя файла склеивается с каталогом без проверки.
- **P17. Карта API не врёт.** `/help` перечисляет каждый смонтированный префикс;
  коды ошибок стабильны. Свидетель: юниты «каждый смонтированный префикс роутера
  есть в /help?format=json», «коды стабильные (API contract)». Мутация: маршрут
  без записи в `/help`.
- **P18. Зависший обработчик не вешает сервер.** Через 30 с — 504. Свидетель:
  юнит «долгий handler → RequestTimeout». Мутация: ожидание без срока.
- **P19. Секрет не утекает в копируемые снимки API.** Токен в снимке хранения —
  `***`; чувствительные параметры запроса маскируются в журнале запросов.
  Свидетель: юнит «debug_token маскируется, остальные vars pass-through»;
  журнал запросов — `без свидетеля`. Мутация: снимок хранения без скраббера.
- **P20. Живые события пишутся только по явной команде.** Без START события не
  копятся; запись продолжается при уходе с вкладки. Свидетель: юнит «recording
  off → events ignored». Мутация: запись включается открытием вкладки.
- **P21. Плашки живых событий не шумят.** «Не определён владелец» — больше 5
  неатрибутированных событий за 30 с, успешные DNS не в счёт; «DNS failing» —
  не меньше 3 отказов и 20 % за 30 с и только при живой связи. Свидетель: юниты
  «§177-A successful unattributed DNS resolves do NOT light the banner»,
  «2 fail (< минимума 3) → healthy», «5 fail 100%, но НЕТ conn-активности →
  healthy». Мутация: порог по абсолютному числу отказов без гейта активности.
- **P22. Однотипные уведомления сворачиваются.** Уведомления одного кода в одном
  уровне — одна группа с числом и списком записей; счётчики шапки считают записи.
  Свидетель: виджет-тесты «семь записей одного кода → одна плитка», «счётчик шапки
  считает записи, а не группы». Мутация: группировка поверх уровней.
- **P23. Уведомление ядра со ссылкой ведёт по ссылке.** Тап по системному
  уведомлению, пришедшему от ядра, открывает его адрес; адрес дублируется в
  журнал ядра. Свидетель: ручная проверка с узлом Tailscale без авторизации.
  Мутация: уведомление без действия по тапу.
- **P24. Снимок профилировщика — только с живым ядром.** Без поднятого туннеля
  снимок не снимается («VPN must be running…»); сервер снимков существует только
  на время одного запроса. `без свидетеля`.

## Контролируемые параметры

| Настройка | Где | Значения | Дефолт | Когда действует |
|-----------|-----|----------|--------|-----------------|
| Log level | настройки ядра → General | `trace` / `debug` / `info` / `warn` / `error` / `fatal` / `panic` | `warn` | пересборка конфига и перезапуск |
| Forward sing-box logs | App Settings → Diagnostics | вкл/выкл | выкл | после перезапуска процесса |
| Verbose (TRACE/DEBUG) | там же, активен при включённой пересылке | вкл/выкл | выкл | сразу |
| Debug API | App Settings → Diagnostics → Developer | вкл/выкл | выкл | сразу |
| Port | там же | 1024..49151 | 9269 | сразу (сервер перезапускается) |
| Token | там же, Copy / Regenerate | 32 hex | генерируется при первом включении | сразу; старый даёт 401 |
| Lock config (debug) | там же, виден только при включённом Debug API | вкл/выкл | выкл; снимается выключением Debug API | сразу |
| Live retention window | Stats → Profiler | 1m / 10m / 1h | 10m | сразу |

Ключи конфига ядра (контракт): `log.level` = выбранный Log level,
`log.timestamp: true`. Параметры запуска ядра: источник отчёта о падении
`lxbox`, флаг пересылки журнала — из «Forward sing-box logs».

Форматы файлов ядра, которые фича читает: текущий отчёт `CrashReport-lxbox.log`;
архив `crash_reports/<ISO-время>/` = `go.log` + `metadata.json` +
`configuration.json` (ранние сборки — плоский файл); снимки памяти
`oom_reports/<ISO-время>/` = `metadata.json`, `go.log`, `configuration.json`,
`connections.json`, pprof-профили `*.pb`. Дамп — `lxbox-dump-<время>.json`.

## Входы / Выходы

**Входы:** записи приложения; строки журнала ядра; файлы отчётов и снимков
ядра; системная история завершений процесса (Android 11+); хвост системного
журнала своего процесса; поток соединений и DNS-запросов ядра; уведомления,
которые шлёт ядро; HTTP-запросы на `127.0.0.1:<port>`.

**Выходы:** экран Debug (вкладки Log / Crashes / OOM / Profiling, Share dump);
плашка «ядро падало» на главном; вкладка Profiler в Stats; файл-дамп и снимки
через системный share; системные уведомления ядра; JSON-ответы Debug API.

## Data flow

```
приложение → журнал app ─┐                        ┌→ экран Debug / Log
ядро → фильтр уровня → журнал core ─┤→ слияние по времени ┤→ /logs, /diag/applog
     warn/error ─→ файл на источник ─┘ (↑ prev session)   └→ дамп: debug_log
паника ядра → текущий отчёт → (следующий запуск) архив → ротация 10
     └→ плашка (раз на сбой) · вкладка Crashes · /files/crash · дамп
давление памяти → снимок oom_reports → ротация 5 → вкладка OOM · /files/oom · дамп
Share dump / GET /diag/dump → версии + настройки + источники + конфиг + журнал
     + отчёты + снимки + причины завершения + хвост системного журнала
     + стеки горутин (если туннель поднят) → один JSON
START → поток соединений и DNS ядра → буфер (окно хранения) → вкладка Profiler
     → плашки (владелец / DNS) · /profiler/live*
HTTP → проверка хоста → токен → срок 30 с → маршрут → JSON / ошибка
```

## Правила и гарантии

- Чтение улик best-effort: сбой канала — пустое поле, а не сбой экрана или старта.
- Журнал ядра до приложения доходит, только если включена пересылка; строки
  TRACE/DEBUG отбрасываются ещё до приложения, пока выключен Verbose; при
  переполнении очереди (4096 строк) отбрасываются новые строки.
- «Сохранено с прошлого раза» — только warning и error; в файл пишутся только
  записи текущей сессии, поэтому на диске лежит последняя сессия, где были
  предупреждения.
- Ротация архивов идёт при старте приложения, а не при открытии экрана.
- Debug API стартует при открытии главного экрана и при каждом изменении
  переключателя, порта или токена; пустой токен — сервер не стартует.

## Границы

- Живой статус туннеля, скорость, соединения и статистика — 012-LIVE_STATE;
  здесь только запись событий как инструмент разбора.
- Диагностика конкретного узла (проверки, пинги, какие коды получает узел) —
  [009-NODE_HEALTH](../009-NODE_HEALTH/FEATURE.ru.md); здесь — как уведомления с
  кодами показываются.
- Сброс кэшей ядра после падения и автоподнятие туннеля —
  [010-VPN_SERVICE](../010-VPN_SERVICE/FUNCTIONS/recovery.ru.md).
- MCP-обёртка над Debug API (`§035F`) — только спека, не реализована
  (отменена владельцем).
- Встроенный продвинутый просмотрщик журнала (`§023F`) — снят: его место заняли
  Profiler и Debug API.
- Отчёт о падении покрывает только паники ядра; нативные сбои вне ядра и убийство
  процесса системой видны лишь в причинах завершения и хвосте системного журнала.
- Зависит от возможностей ОС: история завершений процесса (Android 11+), доступ к
  системному журналу только своего процесса, показ уведомлений (разрешение на
  уведомления), общий для всех приложений loopback (защита — токен).

## Особенности сопровождения

- Отчёты ядра лежат в рабочем каталоге ядра, а не приложения: чтение по пути
  приложения молча ничего не находило, и канал сбоев месяцами «работал» пустым
  (§316). Старое имя `stderr.log` на текущем ядре не существует.
- Ядро не ограничивает ни архив паник, ни снимки памяти (на тест-устройстве —
  575 снимков, 427 МБ, §318): ротацию держит приложение.
- В Verbose буфер ядра (500 строк) на живом трафике живёт секунды: включать
  точечно и сразу снимать журнал.
- Debug API — корневой доступ by design: аудит проверяет границу (токен, bind,
  default-off, хост), а не маскирование секретов за ней.
