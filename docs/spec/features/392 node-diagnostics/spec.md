# §392 — Node Diagnostics: вкладка «что видно через этот узел»

**Статус:** DEVICE-PENDING
**Ядро:** требует `v1.14.0-lx.25-rc.1`+ (`GetURLViaOutbound`, kernel SPEC 058)
**Связанные:** §236/§296 (probe-сессия — донор модели «узел без VPN»), §090 G2b
(двухвкладочный экран узла), §286 (probe-lifecycle), §322 (узел-группа)

## 1. Проблема

Диагностика узла в приложении — одно число. Пинг отвечает «жив, N мс» и
выбрасывает тело ответа. Вопросы пользователей другого класса:

- «пинг есть, а сайты не открываются»;
- «узел работает, но сервисы считают меня другой страной»;
- «WARP подключён, а `warp=off`».

Это вопросы про **содержимое** ответа. Ответить на них сейчас можно только
переключившись на узел и открыв браузер: диагностика через смену состояния
системы, с обрывом живых соединений.

Ядро закрыло шов вызовом `GetURLViaOutbound` (kernel SPEC 058): HTTP GET через
узел, адресуемый **тегом**, с возвратом тела. Активный selector не трогается.

## 2. Что делаем

Вкладка **Diagnostics** на **всех трёх** экранах деталей узла — общий виджет
[`widgets/node_diagnostics_tab.dart`](../../../../app/lib/widgets/node_diagnostics_tab.dart),
подключённый в каждый:

| Экран | Как попасть | Что знает об узле | Доступные ветки |
|---|---|---|---|
| [`node_inspect_screen`](../../../../app/lib/screens/subscription_detail_screen/node_inspect_screen.dart) (JSON / Source) | тап по узлу в подписке | `NodeSpec` + префикс | probe + боевая |
| [`node_settings_screen`](../../../../app/lib/screens/node_settings_screen.dart) (Settings / JSON) | узел папки / одиночный сервер | `NodeSpec` + префикс | probe + боевая |
| [`outbound_view_screen`](../../../../app/lib/screens/outbound_view_screen.dart) (Overview / JSON) | «Подробности» в меню на главном | только тег конфига | только боевая |

Третий экран работает с уже собранным конфигом и `NodeSpec` не имеет —
временный probe-конфиг собирать не из чего. При выключенном VPN он объясняет,
что проверить узел можно либо включив VPN, либо открыв его из подписки.

```
┌─ Node Settings ────────────────────────┐
│  Settings │ JSON │ Diagnostics         │
├────────────────────────────────────────┤
│  Check                                 │
│  Request sent through this node        │
│                                        │
│  ┌────────────────────────────────┐    │
│  │ Cloudflare trace            ▾  │    │
│  └────────────────────────────────┘    │
│  https://1.1.1.1/cdn-cgi/trace         │
│                                        │
│           [ ▷ Run ]                    │
├────────────────────────────────────────┤
│  Response            200 · 312 ms  [⧉] │
│  ┌────────────────────────────────┐    │
│  │ fl=123f456                     │    │
│  │ ip=104.28.x.x                  │    │
│  │ loc=DE                         │    │
│  │ warp=on                        │    │
│  │ …                              │    │
│  └────────────────────────────────┘    │
└────────────────────────────────────────┘
```

Ключевые решения:

- **Тело показывается как есть.** Никакого парсинга, извлечения полей и
  подсветки: пользователь читает сырой ответ сервиса. Формат чужого сервиса
  меняется — вкладка продолжает работать без единой правки.
- **Запуск только по кнопке.** Ядро (SPEC 058 §5) прямо запрещает фоновые
  обходы: проба — реальный трафик и пробуждение спящих WG-узлов. Открытие
  вкладки ничего не шлёт.
- **Узел адресуется тегом** — активный selector не переключается, живые
  соединения не рвутся.
- **Выпадающий список, не галочки.** Одна проверка за запуск: ответ идёт в одно
  поле, сравнивать несколько одновременно не требуется.

Заголовок над полем ответа несёт HTTP-статус и время обмена, кнопка справа
копирует тело в буфер. Тело обрезано ядром → под полем пометка о том, что
ответ усечён.

## 3. Откуда берётся сессия ядра

Главное ограничение, диктующее модель (унаследовано от §236): два
`CommandServer` на процесс невозможны — `command.sock` один на basePath.
Отсюда две взаимоисключающие ветки, и выбор между ними **автоматический**:

| VPN | Источник | Через что идёт проба |
|---|---|---|
| выключен | probe-сессия (§236), конфиг из одного этого узла | сам узел + его собственная detour-цепочка из raw |
| включён | боевое ядро, `pingClient` | тот же узел в живом конфиге, по тегу |

Пользователю разница показывается строкой под кнопкой, без выбора руками:
лишний переключатель здесь только запутает — обе ветки отвечают на один и тот
же вопрос «что видно через ЭТОТ узел».

**Чего вкладка НЕ делает** (граница из kernel SPEC 058 §5): она не отвечает на
вопрос «через что я хожу прямо сейчас». Живой маршрут со всеми правилами,
sniff'ом и выбором группы проверяется только обычным запросом с устройства.
При включённом VPN проба идёт через *узел*, а не через *текущий маршрут* —
это подписано в UI.

### 3.1 Ветка «VPN выключен»

Переиспользуем `buildProbeConfig` из [`probe_config.dart`](../../../../app/lib/services/probe/probe_config.dart)
с одним узлом — конфиг без inbound'ов, `openTun` не зовётся, local-DNS для
резолва доменных адресов. Тег берём из `tagByIndex[0]`: `allocate()` мог его
уникализировать, брать `node.tag` напрямую нельзя.

Узел-группа (§322) не диагностируется: `buildProbeConfig` кладёт её в
`brokenByIndex` как `'group'`, ядро валит на её пустом urltest весь конфиг
(«missing tags»). Вкладка для группы показывает пояснение вместо кнопки —
члены проверяются поштучно.

Отмена и lifecycle — через `ProbeLifecycle` (§286): инвариант
`stop ∪ dead ∪ background ⇒ halt` распространяется и на диагностику.

### 3.2 Ветка «VPN включён»

Прямой вызов через `BoxService.commandClient` по образцу `ccUrlTestOutbound`.
Тег — отображаемый тег узла в живом конфиге (`TagResolver.displayTag` с
префиксом списка), а не bare-тег: в боевом конфиге узлы подписки живут с
префиксом.

## 4. Слои и файлы

```
widgets/node_diagnostics_tab.dart    вкладка (общая на 3 экрана)
  ├─ node_inspect_screen.dart        подключение (node + tagPrefix)
  ├─ node_settings_screen.dart       подключение (node + tagPrefix)
  └─ outbound_view_screen.dart       подключение (только liveTag)
  └─ services/diagnostics/
       diagnostic_check.dart         реестр предопределённых чекеров
       node_diagnostics_runner.dart  выбор ветки probe/live, один прогон
  └─ vpn/cc_channel.dart             getUrlViaOutbound / probeGetUrl
       └─ VpnPlugin.kt               ccGetUrlViaOutbound / probeGetUrl
            ├─ BoxCommandClient.kt   боевая ветка (pingClient)
            └─ ProbeSession.kt       probe-ветка
```

`NodeDiagnosticsRunner.run` принимает `NodeSpec?`: `null` = вызывающий знает
только тег собранного конфига. При выключенном VPN такой вызов отдаёт
`'no_node'` — probe-конфиг собирать не из чего.

### 4.1 Модель

```dart
/// Предопределённый чекер. Тело не интерпретируется — только адрес и подпись.
class DiagnosticCheck {
  final String id;
  final String title;   // подпись в выпадающем списке (l10n-ключ)
  final String url;
}

/// Итог одного прогона. Обмена не было ⇔ error непустой.
class DiagnosticOutcome {
  final int httpStatus;    // не-2xx — РЕЗУЛЬТАТ, не ошибка
  final String error;
  final int elapsedMs;
  final String remoteAddr;
  final String body;       // показывается как есть
  final bool truncated;
  final String contentType;
}
```

`CcGetUrlResult` в `cc_channel.dart` зеркалит форму ядра
(`status/content/truncated/contentType/remoteAddr/elapsedMs`) — по образцу
`CcDelayResult.fromMap`.

### 4.2 Предопределённые чекеры

| id | Подпись | URL |
|---|---|---|
| `cf_trace` | Cloudflare trace | `https://1.1.1.1/cdn-cgi/trace` |
| `ip2location` | IP & location | `https://api.ip2location.io/` |
| `ipinfo` | IP info | `https://ipinfo.io/json` |
| `cf_trace_https` | Cloudflare trace (hostname) | `https://cloudflare.com/cdn-cgi/trace` |

`cdn-cgi/trace` — дефолт списка: без ключа, читаемые `key=value` построчно,
несёт `warp=`, которого нет больше нигде. Вариант по имени хоста рядом с
вариантом по IP: расхождение между ними само по себе диагностично (DNS против
прямого адреса). `ip2location.io` без API-ключа отдаёт урезанный ответ и жёстко
лимитирован — его 429 показывается как обычный результат со статусом, а не как
поломка узла.

Список — константа в `diagnostic_check.dart`. Ввода произвольного URL нет:
поле ввода превратило бы диагностику в HTTP-клиент через чужие туннели.

### 4.3 Параметры вызова

- `timeout` — 10 000 мс. Диагностика идёт под глазом пользователя; висеть
  дольше бессмысленно, а дефолт ядра (0) не ограничен ничем, кроме вызова.
- `maxBytes` — 64 KiB. Диагностические ответы — сотни байт; дефолт ядра
  256 KiB избыточен. `truncated` показывается пометкой.
- `headers` — `null`. Свой User-Agent не ставим: подмена UA меняет ответ
  сервисов и вводит в заблуждение.

## 5. Приватность

Проба уходит на **сторонний сервис** и несёт ему exit-IP узла. Поэтому:

- ничего не отправляется без явного нажатия — открытие вкладки безопасно;
- URL выбранного чекера показан под списком до запуска — видно, куда уйдёт
  запрос;
- тело ответа не логируется и никуда не отправляется — только на экран
  и в буфер обмена по кнопке.

Для F-Droid-сборки важно: домены не зашиты в сетевой слой, обращение
происходит исключительно по действию пользователя.

## 6. Границы

- Только GET — граница ядра, не наша.
- Тело не интерпретируется приложением.
- Произвольный URL не вводится — только список предопределённых.
- Узел-группа (§322) не диагностируется.
- Не заменяет проверку живого маршрута (см. §3).
- Периодических/фоновых прогонов нет и не будет (kernel SPEC 058 §5).

## 7. Критерии приёмки

- [ ] Вкладка Diagnostics видна на ВСЕХ трёх экранах деталей узла; при её
      открытии сетевых запросов нет.
- [ ] На `outbound_view_screen` при выключенном VPN — пояснение (`no_node`),
      вызова в ядро нет; при включённом — обычный прогон.
- [ ] VPN выключен → проба идёт probe-сессией, в поле появляется тело
      `cdn-cgi/trace` с `ip=`/`warp=`.
- [ ] VPN включён → проба идёт боевым ядром по тегу; активный узел в группе
      НЕ переключается.
- [ ] Не-2xx (например 429 от ip2location) показан как результат со статусом,
      тело в поле, узел не помечен нерабочим.
- [ ] Узел-группа → пояснение вместо кнопки, вызова в ядро нет.
- [ ] Стоп VPN / уход в фон во время прогона → прогон снят (§286).
- [ ] Ядро без `with_lx_command` / старее lx.25 → `Unimplemented` показан
      человекочитаемо, без краша.
- [ ] `flutter analyze` + `flutter test` зелёные; l10n-чекеры зелёные.
