## 1. Зачем

Ядро проверяет конфиг целиком и при первом негодном узле отказывается
стартовать вовсе: `initialize outbound[3] vless[🇩🇪 Frankfurt]: parse
encryption: unknown encryption appearance`. Одна строка в одном узле подписки —
и VPN не поднимается ни на одном узле. Провайдер обновил подписку, человек
нажал Start, получил ошибку на английском и остался без связи.

Дублировать грамматики ядра в приложении — тупик: копия обязана сверяться на
каждом бампе, а отставшая копия отбраковывает годные узлы. Дешёвые проверки
реестра (перечисления, типы, форматы ключей) остаются первым эшелоном; эта
фича — общий второй, на всё, о чём мы не знаем.

## 2. Решения владельца

1. **Новых сущностей нет.** Узел выключается тем же выключателем, что и
   рукой пользователя, и на него вешается предупреждение уровня error.
2. **Триггер — реальный старт ядра.** Перед обычным стартом проверок нет:
   успешный старт не платит ничего.
3. **Остальных негодных вычищает тихий цикл `checkConfig`** — после первого
   отказа старта, без туннеля и без сервиса.
4. **Предел — 10 кругов, дальше вопрос человеку:** продолжить до конца или
   остановить. Подписка на 500 узлов с пачкой негодных — норма, длинный
   старт на ней допустим, но решает человек.
5. **Сообщение — плашка** на главном экране, а не снэкбар.

## 3. Поведение

```
Start
└─ реальный старт ядра (первый, сигнальный)
   ├─ принято → VPN поднят → конец
   └─ отказ
      ├─ ошибка не про узел / без тега / тег не сопоставился → ошибка, как сейчас → конец
      └─ ошибка называет узел → выключить узел + причина
         └─ цикл check (тихо, без туннеля): пересобрать конфиг → checkConfig
            ├─ назван узел → выключить + причина → следующий круг
            │  └─ после 10 кругов → диалог
            │     ├─ Keep checking → следующий круг, дальше без предела
            │     └─ Stop → конец, VPN не поднят, выключенные остаются выключенными
            ├─ ошибка не про узел / тот же тег назван повторно → ошибка → конец
            └─ чисто → реальный старт ядра (второй, финальный)
               ├─ принято → VPN поднят → плашка «выключено N» → конец
               └─ отказ → ошибка, как сейчас → конец
                  (если ошибка называет узел — он тоже выключается с причиной,
                   но третьего старта нет: следующее нажатие Start начнёт заново)
```

Реальных стартов на одно нажатие — два: сигнальный и финальный (решение
владельца 18.09.2026). Финальный либо поднимает VPN, либо показывает ошибку.
Редкая ошибка, которую `check` пропускает, а старт ловит, автоматического
третьего захода не получает — но названный узел выключается, поэтому следующее
нажатие Start уже пройдёт дальше, а не упрётся в тот же узел.


- **Цикл конечен по построению:** каждый круг выключает один узел; круг, на
  котором выключить нечего (тег не сопоставился, ошибка не про узел, тот же
  тег назван повторно), цикл прерывает.
- **Во время цикла** кнопка Start показывает `Checking servers… (%d
  disabled)` (ru: «Проверка серверов… (выключено: %d)»); отмена доступна
  всегда.
- **Диалог после 10 кругов** (тексты согласованы с владельцем 18.09.2026;
  число — из константы предела; слова те же, что в плашке):

  ```
  10 servers disabled — there may be more

  The core has rejected 10 servers so far, and each was
  turned off. Keep checking the rest? On a large
  subscription this can take a while.

  If you stop, the VPN will not start. The servers already
  turned off will stay off.

                                [ Stop ]   [ Keep checking ]
  ```

  ru: заголовок «Отключено серверов: 10 — возможно, есть ещё»; текст «Ядро
  не приняло уже 10 серверов, каждый из них выключен. Проверять остальные? На
  большой подписке это может занять время.» и «Если остановить, VPN не
  запустится. Уже выключенные серверы останутся выключенными.»; кнопки
  «Остановить» / «Проверять дальше». `Keep checking` снимает предел до конца
  этого Start. Слово «scanning» не используется — оно занято сканером
  WARP-endpoint'ов.
- **Стоимость и побочные эффекты `checkConfig`** агент замеряет ДО
  реализации: время одного круга на конфиге 500 и 2000 узлов с rule-set'ами;
  не трогает ли проверка `cache.db` и прочее состояние работающего ядра
  (#1406/#1407 — cache.db открыт всегда), не мешает ли идущему VPN, если цикл
  запущен при Reconnect. Итог — в спеку; если круг дороже ~1 с, вынести
  владельцу до продолжения.
- **Разбор ошибки.** Строка вида `initialize <outbound|endpoint>[<i>]
  <type>[<tag>]: <текст>`; формат нормативен (CANON, по §24.19), источник —
  ядро lx.7+. Строка без тега или не про узел — автоматики нет. Перебором
  виновника не ищем.
- **Тег → узел.** Теги в конфиге уникальны. Для производных записей (хоп
  цепочки, узел папки, WARP, префикс подписки) выключается исходный узел —
  обратное отображение строит сборка, которая эти теги и выдала. Тег,
  которому не нашлось узла (служебная запись приложения), — автоматики нет.
- **Выключение.** Существующая запись «узел выключен» (§283 / §234 / ручной
  сервер) получает необязательное поле `reason` — дословный текст ядра после
  префикса с тегом. Есть `reason` — выключило приложение; нет — человек.
  Ручной сервер (`kind: server`) выключается так же, своим выключателем.
- **Предупреждение.** При разборе на выключенном узле с `reason` ставится
  error с общим кодом реестра (по §24.19, условно `core_rejected`,
  `params: reason`). В списке — красная строка (§471), в шторке — текст ядра.
- **Включение обратно.** Человек щёлкает тумблер — `reason` стирается,
  следующий старт проверяет узел заново; ядро снова отказало — узел снова
  выключен с тем же объяснением. Автоснятие — по смене тела узла и по смене версии ядра, раздел 3b.
- **Выбранный узел.** Если выключен узел, выбранный пользователем, выбор
  уходит по обычным правилам выключенного узла (§283); отдельного сообщения
  об этом нет.
- **Граф.** Выключенный узел — обычная причина «узел недоступен» для сборки:
  цепочка с выключенным хопом, группа, оставшаяся пустой, detour — по
  существующим правилам (§254, §283), fail-closed у detour сохраняется.
  Закрыть тестами, ничего не изобретать.
- **Плашка** (тексты согласованы с владельцем 18.09.2026). На главном
  экране, пока человек не закроет; палитра — `banner_palette`, уровень
  warning; переживает перезапуск приложения, пока не закрыта (состояние
  плашки — не в бэкап). Число выключенных — первым словом заголовка.

  ```
  ⚠  3 servers disabled                                         ✕
     The core rejected them, so they were turned off to let
     the VPN start: Frankfurt-01, Amsterdam-02, NewYork-03 +4 more
                                                       [ Show ]
  ```

  Ключи: заголовок `1 server disabled` / `%d servers disabled`; текст
  `The core rejected it, so it was turned off to let the VPN start: %s` /
  `The core rejected them, so they were turned off to let the VPN start: %s`;
  хвост списка `+%d more` (имён — до трёх); кнопка `Show` — список
  выключенных, по каждому шторка Warnings с текстом ядра; крестик закрывает.
  ru: «Отключено серверов: %d» (конструкция с двоеточием обходит падежи),
  «Ядро их не приняло — они выключены, чтобы VPN смог запуститься: %s»
  (для одного — «Ядро его не приняло — он выключен, чтобы…»), «и ещё %d»,
  «Показать». Кнопки «включить всё обратно» нет: ядро отвергло бы их снова.
  Отдельной строки про выбранный пользователем сервер в плашке нет (решение
  владельца).
- **Бэкап.** `reason` уходит вместе с записью о выключении (allowlist ↔
  export симметрично, §221).
- **Старт без UI** (автозапуск, сторож §428, плитка QS, Intent API §047):
  конфиг собирает Dart. Агент выясняет, жив ли Dart-движок на каждом таком
  пути; где жив — цикл работает; где нет — старт падает как сейчас, починка
  случится при первом Start из приложения. Записать по каждому пути.
- **Безопасность трафика.** Отказ ядра происходит на инициализации, до
  поднятия туннеля; цикл попыток не должен менять поведение kill-switch /
  lockdown — проверить, что между попытками приложение не объявляет
  «подключено» и не роняет уже стоящую защиту.

## 3a. Норма контракта (CANON §9; контракт 1.1.9 → 1.1.10)

- Код `core_rejected` (error, `params: reason`) — тексты из реестра.
- Формат строки ошибки ядра — нормой в CANON §9.
- **Разбор тега.** Тег может содержать `]` и `: `, однозначного разреза нет.
  Слева снимается фиксированный префикс
  (`initialize <outbound|endpoint>[<i>] <type>[`), в остатке берутся все
  вхождения `]: ` СПРАВА НАЛЕВО, каждое даёт кандидата в теги; побеждает
  первый, совпавший с тегами собранного конфига. Таблица примеров CANON §9.2
  — набор для юнитов, взять дословно.
- У лаунчера сигналом считается ещё и его `check` при сборке; у нас триггер —
  только старт, схема раздела 3.

## 3b. Хранение и снятие вердикта (решения владельца 18.09.2026, сказаны в сессии лаунчера: «в модели не надо занимать reason… у нас же есть список уведомлений — просто добавить причину» и «вердикт привязан к телу узла — в LxBox пусть сделают так же»)

**Отдельного поля причины нет.** Вердикт — запись предупреждения
`{ "code": "core_rejected", "params": { "reason": "<текст ядра без префикса
initialize …[tag]:>" } }` — без `path`, без severity (она из реестра).
«Выключило приложение» = узел выключен И у него есть `core_rejected`.
Всё, что выше по тексту названо полем `reason` / `disabled_reason`, читать
как эту запись.

**Где запись живёт у нас.** Предупреждения узла в LxBox не хранятся — они
вычисляются при разборе (`NodeSpec.warnings`), а узлы подписки не хранятся
вовсе (только `sub_cache/` и оверлей выключенных). Поэтому хранится ровно одна
запись, в форме лаунчера, рядом с существующей отметкой о выключении:

| Вид узла | Выключение сегодня | Куда ложится вердикт |
|---|---|---|
| узел подписки | `sources[].disabled: {identity: unix}` (ключ — тег-идентичность, `node_hash.dart`) | `sources[].warnings: {identity: [ {code, params} ]}` — оверлей тем же ключом |
| член папки | `nodes[].enabled: false` | `nodes[].warnings: [ {code, params} ]` |
| ручной сервер | `enabled: false` на источнике | `warnings: [ {code, params} ]` на источнике |

Хранится только `core_rejected`; прочие предупреждения по-прежнему
вычисляются. При разборе сохранённая запись добавляется к `node.warnings`
(дедуп по `(code, path)`). Ключ `warnings` — в allowlist записи и в
slice-таблицу бэкапа симметрично (§221); при импорте — по правилам соседнего
`disabled` (объединение). GC оверлея подписки — вместе с `gcDisabledHashes`.

**Вердикт привязан к телу узла.** Отпечатки не хранятся — сравниваются тела
там, где старое и новое доступны одновременно:

- *Тело то же* (перезапуск, рехидрация из кэша, refetch с тем же телом,
  пересборка) → узел остаётся выключенным, запись держится.
- *Тело изменилось* → вердикт недействителен: запись стирается И узел
  включается обратно; следующий старт проверит его заново. Точки сравнения:
  refetch подписки — `SubscriptionController._fetchEntryByRef` (в одном
  скоупе `current.nodes` и `result.nodes`); правка узла человеком — сохранение
  в редакторе узла / `updateConnectionAt` / `updateMemberAt` (старый и новый
  `rawSource`). Сравнивается каноническая форма тела — `emit()` узла,
  сериализованный с сортировкой ключей; не тег-идентичность (она от тела не
  зависит) и не `nodeIdentityKey` (он не видит TLS и транспорт, а негодным
  бывает именно там).
- *Старого тела нет* (кэш подписки пуст или не читается) → сравнить нечем →
  вердикт снимается: лучше лишняя проверка ядром, чем починенный узел,
  оставшийся выключенным.
- *Обновилось ядро* → все вердикты сбрасываются (запись стёрта, узел
  включён). Нужна одна глобальная настройка «версия ядра, виденная в прошлый
  раз» (`Libbox.version()`; сегодня не хранится) — сравнение на старте
  приложения. В бэкап не идёт.
- *Человек включил узел* → запись стирается, узел проверится снова.
- Узлы, выключенные человеком (без `core_rejected`), не трогаются никогда.
  Узел, выключенный человеком ДО отказа ядра, в конфиг не попадает, и вердикта
  на нём появиться не может.

## 4. Чего не делаем

- Не чиним узел сами — только исключаем.
- Не выключаем ничего по ошибкам времени работы (таймаут, отказ сервера,
  urltest) — только по отказу ядра принять конфиг.
- Не вводим отметку «карантин», отдельное поле причины, отпечатки тела и
  версию ядра на узле (версия ядра — одна глобальная настройка, раздел 3b).
- Не ставим `checkConfig` перед обычным стартом — только после отказа.
  Проверка ядром при Save JSON-источника (§455) остаётся как есть.

## 5. Проверка

Юниты: разбор строки ошибки (outbound, endpoint, теги с эмодзи, скобками и
двоеточиями, строка без тега, ошибка dns/route); тег → исходный узел для
подписки, папки, цепочки, ручного сервера; `reason` в кодеке записи и в
бэкапе; предупреждение на узле. Интеграционный тест цикла на поддельном
клиенте ядра: старт чистый → ни одного `checkConfig`; один негодный → Start,
check чисто, Start; три негодных; одиннадцать → диалог, `Keep checking` доводит до
конца, `Stop` останавливает с выключенными; run-only ошибка на финальном старте → узел выключен, третьего старта нет,
ошибка показана; ошибка не про узел → без автоматики;
тег назван повторно → цикл прерван. Виджет-тесты плашки, диалога и состояния «checking nodes…». Проверка
на устройстве — с владельцем (ссылка из #147).

## 6. Открыто

- Заявка ядру «называть все негодные узлы одной ошибкой» — НЕ подаём: с
  тихим циклом `checkConfig` цена негодного узла — одна проверка, а не
  попытка старта. Вернуться, если замер покажет дорогой круг.
- Дружелюбные тексты по известным префиксам ошибок ядра (`parse encryption:`
  …) — таблица, не разборщик; отдельной задачей после выхода фичи.
