## 1. Зачем

Ядро проверяет конфиг целиком и при первом негодном узле отказывается
стартовать вовсе: `initialize outbound[3] vless[🇩🇪 Frankfurt]: parse
encryption: unknown encryption appearance`. Одна строка в одном узле подписки —
и VPN не поднимается ни на одном узле. Провайдер обновил подписку, человек
нажал Start, получил ошибку на английском и остался без связи.

Дублировать грамматики ядра в приложении — тупик: копия обязана сверяться на
каждом бампе, а отставшая копия отбраковывает годные узлы. Дешёвые проверки
реестра (перечисления, типы, форматы ключей) остаются первым эшелоном; эта
фича — общий второй, на всё, о чём мы не знаем.

## 2. Решения владельца

1. **Новых сущностей нет.** Узел выключается тем же выключателем, что и
   рукой пользователя, и на него вешается предупреждение уровня error.
2. **Триггер — реальный старт ядра.** Перед обычным стартом проверок нет:
   успешный старт не платит ничего.
3. **Остальных негодных вычищает тихий цикл `checkConfig`** — после первого
   отказа старта, без туннеля и без сервиса.
4. **Предел — 10 кругов, дальше вопрос человеку:** продолжить до конца или
   остановить. Подписка на 500 узлов с пачкой негодных — норма, длинный
   старт на ней допустим, но решает человек.
5. **Сообщение — плашка** на главном экране, а не снэкбар.

## 3. Поведение

```
Start
└─ реальный старт ядра (первый, сигнальный)
   ├─ принято → VPN поднят → конец
   └─ отказ
      ├─ ошибка не про узел / без тега / тег не сопоставился → ошибка, как сейчас → конец
      └─ ошибка называет узел → выключить узел + причина
         └─ цикл check (тихо, без туннеля): пересобрать конфиг → checkConfig
            ├─ назван узел → выключить + причина → следующий круг
            │  └─ после 10 кругов → диалог
            │     ├─ Keep checking → следующий круг, дальше без предела
            │     └─ Stop → конец, VPN не поднят, выключенные остаются выключенными
            ├─ ошибка не про узел / тот же тег назван повторно → ошибка → конец
            └─ чисто → реальный старт ядра (второй, финальный)
               ├─ принято → VPN поднят → плашка «выключено N» → конец
               └─ отказ → ошибка, как сейчас → конец
                  (если ошибка называет узел — он тоже выключается с причиной,
                   но третьего старта нет: следующее нажатие Start начнёт заново)
```

Реальных стартов на одно нажатие — два: сигнальный и финальный (решение
владельца 18.09.2026). Финальный либо поднимает VPN, либо показывает ошибку.
Редкая ошибка, которую `check` пропускает, а старт ловит, автоматического
третьего захода не получает — но названный узел выключается, поэтому следующее
нажатие Start уже пройдёт дальше, а не упрётся в тот же узел.


- **Цикл конечен по построению:** каждый круг выключает один узел; круг, на
  котором выключить нечего (тег не сопоставился, ошибка не про узел, тот же
  тег назван повторно), цикл прерывает.
- **Во время цикла** кнопка Start показывает `Checking servers… (%d
  disabled)` (ru: «Проверка серверов… (выключено: %d)»); отмена доступна
  всегда.
- **Диалог после 10 кругов** (тексты согласованы с владельцем 18.09.2026;
  число — из константы предела; слова те же, что в плашке):

  ```
  10 servers disabled — there may be more

  The core has rejected 10 servers so far, and each was
  turned off. Keep checking the rest? On a large
  subscription this can take a while.

  If you stop, the VPN will not start. The servers already
  turned off will stay off.

                                [ Stop ]   [ Keep checking ]
  ```

  ru: заголовок «Отключено серверов: 10 — возможно, есть ещё»; текст «Ядро
  не приняло уже 10 серверов, каждый из них выключен. Проверять остальные? На
  большой подписке это может занять время.» и «Если остановить, VPN не
  запустится. Уже выключенные серверы останутся выключенными.»; кнопки
  «Остановить» / «Проверять дальше». `Keep checking` снимает предел до конца
  этого Start. Слово «scanning» не используется — оно занято сканером
  WARP-endpoint'ов.
- **Стоимость и побочные эффекты `checkConfig`.** Замерена дартовая половина
  круга — пересборка конфига: **26 мс на 500 узлах и 122 мс на 2000**
  (Dart-тест, 5 прогонов после прогрева). Рост линейный, планка «круг дороже
  ~1 с» не достигнута даже на 2000 узлах, поэтому выносить владельцу нечего.
  Сам `Libbox.checkConfig` на устройстве в этой сессии НЕ замерен (прогона на
  эмуляторе не было) — остаётся подтвердить на устройстве вместе с вопросом
  про `cache.db` и про помеху идущему VPN при Reconnect.
- **Разбор ошибки.** Строка вида `initialize <outbound|endpoint>[<i>]
  <type>[<tag>]: <текст>`; формат нормативен (CANON, по §24.19), источник —
  ядро lx.7+. Строка без тега или не про узел — автоматики нет. Перебором
  виновника не ищем.
- **Тег → узел.** Теги в конфиге уникальны. Для производных записей (хоп
  цепочки, узел папки, WARP, префикс подписки) выключается исходный узел —
  обратное отображение строит сборка, которая эти теги и выдала. Тег,
  которому не нашлось узла (служебная запись приложения), — автоматики нет.
- **Выключение.** Существующая запись «узел выключен» (§283 / §234 / ручной
  сервер) получает необязательное поле `reason` — дословный текст ядра после
  префикса с тегом. Есть `reason` — выключило приложение; нет — человек.
  Ручной сервер (`kind: server`) выключается так же, своим выключателем.
- **Предупреждение.** При разборе на выключенном узле с `reason` ставится
  error с общим кодом реестра (по §24.19, условно `core_rejected`,
  `params: reason`). В списке — красная строка (§471), в шторке — текст ядра.
- **Включение обратно.** Человек щёлкает тумблер — `reason` стирается,
  следующий старт проверяет узел заново; ядро снова отказало — узел снова
  выключен с тем же объяснением. Автоснятие — только по смене тела узла, раздел 3b.
- **Выбранный узел.** Если выключен узел, выбранный пользователем, выбор
  уходит по обычным правилам выключенного узла (§283); отдельного сообщения
  об этом нет.
- **Граф.** Выключенный узел — обычная причина «узел недоступен» для сборки:
  цепочка с выключенным хопом, группа, оставшаяся пустой, detour — по
  существующим правилам (§254, §283), fail-closed у detour сохраняется.
  Закрыть тестами, ничего не изобретать.
- **Плашка** (тексты согласованы с владельцем 18.09.2026). На главном
  экране, пока человек не закроет; палитра — `banner_palette`, уровень
  warning; живёт в памяти процесса ([CoreRejectState]) и **не**
  переживает перезапуск приложения (решение 19.09.2026). Значок и причина
  на узле остаются в локальном хранилище. Число выключенных — первым словом
  заголовка.

  ```
  ⚠  3 servers disabled                                         ✕
     The core rejected them, so they were turned off to let
     the VPN start: Frankfurt-01, Amsterdam-02, NewYork-03 +4 more
                                                       [ Show ]
  ```

  Ключи: заголовок `1 server disabled` / `%d servers disabled`; текст
  `The core rejected it, so it was turned off to let the VPN start: %s` /
  `The core rejected them, so they were turned off to let the VPN start: %s`;
  хвост списка `+%d more` (имён — до трёх); кнопка `Show` — список
  выключенных, по каждому шторка Warnings с текстом ядра; крестик закрывает.
  ru: «Отключено серверов: %d» (конструкция с двоеточием обходит падежи),
  «Ядро их не приняло — они выключены, чтобы VPN смог запуститься: %s»
  (для одного — «Ядро его не приняло — он выключен, чтобы…»), «и ещё %d»,
  «Показать». Кнопки «включить всё обратно» нет: ядро отвергло бы их снова.
  Отдельной строки про выбранный пользователем сервер в плашке нет (решение
  владельца).
- **Бэкап** (решение 19.09.2026, §489). Вердикт `core_rejected` и выключение,
  поставленное страховкой, в файл **не** пишутся: узел в бэкапе выглядит
  включённым, после восстановления ядро проверит его заново. Ручное
  выключение (без вердикта) экспортируется как раньше. Импорт старого файла,
  где вердикты ещё были, — вердикты игнорируются, узел восстанавливается
  включённым. Локальное хранилище не меняется: вердикт переживает перезапуск
  на устройстве. Ключ `warnings` остаётся в allowlist хранения (§221).
- **Старт без UI** (автозапуск, сторож §428, плитка QS, Intent API §047):
  конфиг собирает Dart. **Состояние на 19.09.2026: страховка на эти пути НЕ
  заведена.** `runCoreRejectGuard` зовут ровно два места — кнопка Start
  (`home_screen.dart:977`) и Debug API (`handlers/action.dart:290`,
  `start-vpn-headless?guard=true`). На всех прочих путях старт падает так
  же, как до фичи, и починка случается при первом Start из приложения. Так
  и задумано на первом заходе: диалога предела там некому показать, а
  молчаливое выключение узлов без ведома человека — отдельное решение.
- **Безопасность трафика.** Отказ ядра происходит на инициализации, до
  поднятия туннеля; цикл попыток не должен менять поведение kill-switch /
  lockdown — проверить, что между попытками приложение не объявляет
  «подключено» и не роняет уже стоящую защиту.

## 3a. Норма контракта (CANON §9; контракт 1.1.9 → 1.1.10)

- Код `core_rejected` (error, `params: reason`) — тексты из реестра.
- Формат строки ошибки ядра — нормой в CANON §9.
- **Разбор тега.** Тег может содержать `]` и `: `, однозначного разреза нет.
  Слева снимается фиксированный префикс
  (`initialize <outbound|endpoint>[<i>] <type>[`), в остатке берутся все
  вхождения `]: ` СПРАВА НАЛЕВО, каждое даёт кандидата в теги; побеждает
  первый, совпавший с тегами собранного конфига. Таблица примеров CANON §9.2
  — набор для юнитов, взять дословно.
- У лаунчера сигналом считается ещё и его `check` при сборке; у нас триггер —
  только старт, схема раздела 3.

## 3b. Хранение и снятие вердикта (решения владельца 18.09.2026, сказаны в сессии лаунчера: «в модели не надо занимать reason… у нас же есть список уведомлений — просто добавить причину» и «вердикт привязан к телу узла — в LxBox пусть сделают так же»)

**Отдельного поля причины нет.** Вердикт — запись предупреждения
`{ "code": "core_rejected", "params": { "reason": "<текст ядра без префикса
initialize …[tag]:>" } }` — без `path`, без severity (она из реестра).
«Выключило приложение» = узел выключен И у него есть `core_rejected`.
Всё, что выше по тексту названо полем `reason` / `disabled_reason`, читать
как эту запись.

**Где запись живёт у нас.** Предупреждения узла в LxBox не хранятся — они
вычисляются при разборе (`NodeSpec.warnings`), а узлы подписки не хранятся
вовсе (только `sub_cache/` и оверлей выключенных). Поэтому хранится ровно одна
запись, в форме лаунчера, рядом с существующей отметкой о выключении:

| Вид узла | Выключение сегодня | Куда ложится вердикт |
|---|---|---|
| узел подписки | `sources[].disabled: {identity: unix}` (ключ — тег-идентичность, `node_hash.dart`) | `sources[].warnings: {identity: [ {code, params} ]}` — оверлей тем же ключом |
| член папки | `nodes[].enabled: false` | `nodes[].warnings: [ {code, params} ]` |
| ручной сервер | `enabled: false` на источнике | `warnings: [ {code, params} ]` на источнике |

Хранится только `core_rejected`; прочие предупреждения по-прежнему
вычисляются. При разборе сохранённая запись добавляется к `node.warnings`
(дедуп по `(code, path)`). Ключ `warnings` — в allowlist записи и в
slice-таблицу бэкапа (§221); в **файл** вердикт страховки не едет (§489).
GC оверлея подписки — вместе с `gcDisabledHashes`.

**Вердикт привязан к телу узла.** Отпечатки не хранятся — сравниваются тела
там, где старое и новое доступны одновременно:

- *Тело то же* (перезапуск, рехидрация из кэша, refetch с тем же телом,
  пересборка) → узел остаётся выключенным, запись держится.
- *Тело изменилось* → вердикт недействителен: запись стирается И узел
  включается обратно; следующий старт проверит его заново. Точки сравнения:
  refetch подписки — `SubscriptionController._fetchEntryByRef` (в одном
  скоупе `current.nodes` и `result.nodes`); правка узла человеком — сохранение
  в редакторе узла / `updateConnectionAt` / `updateMemberAt` (старый и новый
  `rawSource`). Сравнивается каноническая форма тела — `emit()` узла,
  сериализованный с сортировкой ключей; не тег-идентичность (она от тела не
  зависит) и не `nodeIdentityKey` (он не видит TLS и транспорт, а негодным
  бывает именно там).
- *Старого тела нет* (кэш подписки пуст или не читается) → сравнить нечем →
  вердикт снимается: лучше лишняя проверка ядром, чем починенный узел,
  оставшийся выключенным.
- *Обновилось ядро* → вердикты НЕ сбрасываются (решение владельца, передано
  лаунчером 18.09.2026: «пока ничего не делать… ручного механизма
  достаточно»). Новое ядро, принявшее бы узел, человек проверяет тумблером.
  Настройка «версия ядра в прошлый раз» не заводится.
- *Человек включил узел* → запись стирается, узел проверится снова.
- Узлы, выключенные человеком (без `core_rejected`), не трогаются никогда.
  Узел, выключенный человеком ДО отказа ядра, в конфиг не попадает, и вердикта
  на нём появиться не может.

## 4. Чего не делаем

- Не чиним узел сами — только исключаем.
- Не выключаем ничего по ошибкам времени работы (таймаут, отказ сервера,
  urltest) — только по отказу ядра принять конфиг.
- Не вводим отметку «карантин», отдельное поле причины, отпечатки тела,
  версию ядра в хранении и сброс вердиктов при обновлении ядра.
- Не ставим `checkConfig` перед обычным стартом — только после отказа.
  Проверка ядром при Save JSON-источника (§455) остаётся как есть.

## 5. Проверка

Юниты: разбор строки ошибки (outbound, endpoint, теги с эмодзи, скобками и
двоеточиями, строка без тега, ошибка dns/route); тег → исходный узел для
подписки, папки, цепочки, ручного сервера; `reason` в кодеке записи и в
бэкапе; предупреждение на узле. Интеграционный тест цикла на поддельном
клиенте ядра: старт чистый → ни одного `checkConfig`; один негодный → Start,
check чисто, Start; три негодных; одиннадцать → диалог, `Keep checking` доводит до
конца, `Stop` останавливает с выключенными; run-only ошибка на финальном старте → узел выключен, третьего старта нет,
ошибка показана; ошибка не про узел → без автоматики;
тег назван повторно → цикл прерван; отмена во время цикла → `stoppedByUser`
с уже выключенными. Снятие вердикта ручной правкой — на фактических точках
сохранения редактора (`updateMemberAt`, `updateConnectionAt`):
`app/test/subscription/core_reject_manual_edit_test.dart`. Виджет-тесты
плашки (число, имена, хвост `+N more`, кнопка Show открывает список, крестик)
и диалога предела (тексты владельца, обе кнопки, закрытие мимо кнопок = Stop)
— `app/test/screens/core_reject_ui_test.dart`; там же связка отмены, в которую
упирается кнопка (рендер самой кнопки требует живых контроллеров главного
экрана). Проверка на устройстве — с владельцем (ссылка из #147).

## 6. Открыто

- Заявка ядру «называть все негодные узлы одной ошибкой» — НЕ подаём: с
  тихим циклом `checkConfig` цена негодного узла — одна проверка, а не
  попытка старта. Вернуться, если замер покажет дорогой круг.
- Дружелюбные тексты по известным префиксам ошибок ядра (`parse encryption:`
  …) — таблица, не разборщик; отдельной задачей после выхода фичи.

## Как сделано

### Разбор строки (CANON §9.1–§9.2)

`app/lib/services/core_reject/core_error_parse.dart` — `parseCoreRejection(line,
configTags)`. Слева снимается фиксированный префикс
(`initialize <outbound|endpoint>[<i>] <type>[`), в остатке берутся все вхождения
`]: ` справа налево, каждое даёт кандидата, побеждает первый, чей тег есть
среди `configTags`. Ни один не совпал — `null`, автоматики нет. `null` же на
форме без тега (ядро младше lx.7 пишет `initialize outbound[26]: unknown uTLS
fingerprint`) и на ошибке не про узел (`inbound`, `dns`, `route`). Индекс
разбирается, но на сопоставление не влияет — он диагностический (§9.1).
Функция чистая: теги приходят параметром, ядро и хранение ей не нужны.

**Д-1 (эмулятор, 19.09.2026) — страховка не срабатывала ни разу.** До Dart
строка доходит не голой: Go кладёт свою цепочку (`start or reload service: `),
а Kotlin сверху **локализованный** шаблон `stop_alert_start_failed` — в ru
префикс другой. Разбор требовал `startsWith('initialize ')`, получал `null`, и
автомат стоял в `idle` (round 0). Дословно с устройства:

```
Failed to start service: start or reload service: initialize outbound[33] shadowsocks[⚡ c-ss2022-badkey]: bad key length, required 32, got 5
```

Чинится двумя независимыми путями, ни один не знает текста обёртки:

1. **Сырой текст отдельным полем.** `BoxService` кладёт в бродкаст
   `EXTRA_CORE_ERROR` (`core_error`) — ровно `t.message` от
   `startOrReloadService`, без единой обёртки приложения; `error` рядом
   остаётся локализованной витриной для человека. Дальше `VpnPlugin` →
   `TunnelStatusEvent.coreError` → `HomeController._settleStartOutcome`, где
   он и берётся первым. Видимый текст алерта не менялся.
2. **Разбор ищет грамматику по вхождению.** `initialize ` ищется не с начала
   строки, а по всем вхождениям слева направо; побеждает первое, за которым
   §9 сходится целиком, включая сопоставление тега. Это запасной путь для
   native старше `core_error` — и страховка от любой будущей обёртки.

### Автомат

`app/lib/services/core_reject/core_reject_guard.dart` — `CoreRejectGuard`,
один прогон на одно нажатие Start. Дерево ветвлений раздела 3 перенесено в
докблок файла дословно. Снаружи автомат видит только интерфейс
`CoreRejectHost`: `realStart`, `rebuild`, `check`, `disableNode`,
`askKeepChecking`, `onProgress` — ни туннеля, ни контроллеров, ни хранения он
не знает, поэтому целиком закрывается юнитами на поддельном клиенте ядра
(`app/test/services/core_reject_guard_test.dart`). Фазы — `CoreRejectPhase`
(`idle`, `signalStart`, `checking`, `awaitingPrompt`, `finalStart`, `done`),
исход — `CoreRejectOutcome` (`startedClean`, `startedWithDisabled`, `failed`,
`stoppedByUser`). Предел — `kCoreRejectRoundLimit = 10`; в текст диалога
подставляется именно константа предела, а не счётчик выключенных (он на
единицу больше — узел сигнального старта — и расходился бы с текстами
владельца). Конечность держит множество `_seenTags`: тег, названный повторно,
даёт `null` из `_consume`, и цикл прерывается (CANON §9.5). Отдельная ветка —
`CoreAttempt.unavailable`: моста нет (юнит, старый native, таймаут), отвечать
нечем, автомат деградирует до обычной ошибки.

### Состояние для UI и Debug API

`app/lib/services/core_reject/core_reject_state.dart` — `CoreRejectState.I`,
`ChangeNotifier`. Отдельный синглтон, потому что автомат живёт ровно один
прогон и после `run()` выбрасывается, а плашка «выключено N» и висящий вопрос
про предел прогон переживают. Связь односторонняя: хост пишет через
`onProgress`/`finish`, читают UI и `/core_reject`. Вопрос человеку — через
`Completer`; повторный `askPrompt` при уже висящем вопросе отдаёт ту же
future, иначе первый ожидающий завис бы навсегда.

### Хранение вердикта

`app/lib/models/core_reject_verdict.dart` — `StoredWarning` (`code` + `params`,
без `path` и без severity: она из реестра), `kCoreRejectedCode`,
`upsertVerdict` (дубль по коду замещается свежим, вердикт идёт первым — это
приговор уровня узла, а не деградация поля) и `dropVerdict`.

`app/lib/controllers/subscription_controller/core_reject_ops.dart` — чистые
функции над моделями: `applyVerdict` над тремя видами записи (подписка, член
папки, ручной сервер), `clearSubscriptionVerdict`, `refreshSubscriptionVerdicts`
(снятие по смене тела) и `canonicalNodeBody` — `emit()` узла, сериализованный
с сортировкой ключей. Сравнивается именно он, не тег-идентичность (она от тела
не зависит) и не `nodeIdentityKey` (он не видит TLS и транспорт, а негодным
бывает именно там). Узел, который не эмитится, считается изменившимся: лишняя
проверка ядром дешевле починенного узла, оставшегося выключенным.

**Точки сравнения — три, функция одна.** Refetch подписки идёт картами
(`refreshSubscriptionVerdicts` в `_fetchEntryByRef`): узлов много, приходят
пачкой с сети. Ручная правка в редакторе узла — по одному узлу,
`verdictDroppedByEdit` в `updateMemberAt` (член папки) и `updateConnectionAt`
(ручной сервер): это фактические точки сохранения редактора
(`node_settings_screen.dart` пишет ровно через них). Тело сравнивается тем же
`canonicalNodeBody` — один вопрос, одна функция; изменилось — вердикт
стирается И узел включается обратно тем же составом полей, что у ручного
включения (`enabled: true` + `dropVerdict`). Узел без вердикта правкой не
оживает: выключенное человеком остаётся выключенным. Переименование для
`canonicalNodeBody` — тоже смена тела (`emit()` включает `tag`); сужать не
стали, цена ошибки несимметрична.

Кодек — `app/lib/models/codec/source_record.dart`: ключ `warnings` в трёх
allowlist'ах (`_subscriptionKeys`, `_serverKeys`, `_memberKeys`) и в
slice-таблице бэкапа (`app/lib/services/lx_backup_slice.dart`, три строки
`BackupField(..., 'warnings', _c)`). Санитизация файла —
`app/lib/services/core_reject/core_reject_backup.dart` (§489): на экспорте и
импорте вердикт страховки срезается, локальное хранилище не трогается.

### Связка и контроллер

`app/lib/screens/home/core_reject_host.dart` — `AppCoreRejectHost`,
реализация `CoreRejectHost` поверх контроллеров; всё про туннель, сборку и
хранение живёт здесь. `askPrompt` приходит снаружи: на пути с UI это диалог,
на старте без UI (автозапуск, сторож §428, плитка QS, Intent API §047) его
нет, и ответ всегда `stop` — предел остаётся пределом, починка случится при
первом Start из приложения.

`SubscriptionController`: `disableNodeByCoreTag(tag, reason)` /
`enableNodeByCoreTag(tag)` — выключение и включение тем же путём, что и рукой
человека, плюс запись и снятие вердикта; `coreRejectedNodes` — все стоящие
вердикты для `/core_reject/nodes`; `lastEmittedTagMap` — обратная карта
последней сборки.

`BuildResult.nodeByEmittedTag` (`app/lib/services/builder/build_config.dart`)
— «финальный тег → исходный узел» (CANON §9.3). Карту строит та же сборка,
которая эти теги и выдала, поэтому производные записи (хоп цепочки, узел
папки, WARP, префикс подписки) приводят к исходному узлу без догадок; тег без
узла (служебная запись приложения) автоматики не получает.

`HomeController.startAndAwaitVerdict` — реальный старт с ожиданием вердикта:
текст отказа приходит асинхронно событием статуса, поэтому старт ждётся через
`Completer`. `null` — принято, строка — текст отказа, пустая строка — таймаут
(45 с), на котором автомат деградирует консервативно.

### UI

`app/lib/screens/home/core_reject_ui.dart` — тексты плашки
(`coreRejectBannerTitle`, `coreRejectBannerText`, имён до трёх плюс хвост
`+%d more`), диалог предела (`showCoreRejectPrompt`; закрытие мимо кнопок
читается как Stop — молчание не согласие на долгую проверку) и шторки кнопки
Show. Новых экранов нет: список выключенных ведёт в существующий
`NodeNotificationsView` (§479). Кнопка Start во время цикла — `home_controls.dart`,
плашка — `widgets/app_banner.dart`.

**Отмена.** Во время тихого цикла кнопка остаётся на своём месте и становится
отменой: иконка `Icons.stop_rounded` (та же, что у обычного Stop), подпись
прежняя — `Checking servers… (%d disabled)`, своих строк отмена не заводит.
Нажатие зовёт `CoreRejectState.I.cancelRun()` → `CoreRejectGuard.cancel()`:
круг доигрывает (прерывать ядро на середине `checkConfig` нечем), следующий не
начинается, исход — `stoppedByUser`, ровно как у Stop в диалоге предела. Если
в этот момент висел вопрос про предел, он закрывается ответом `stop` — иначе
автомат ждал бы ответа на диалог, который человек уже перекрыл отменой.
Дотянуться до автомата можно только через [CoreRejectState]: сам он живёт один
прогон, и `bindCancel` в `_runWithCoreRejectGuard` — единственная связь.

### Debug API

`app/lib/services/debug/handlers/core_reject.dart`, описания — в
`DIAGNOSTICS.md`: `GET /core_reject` (фаза прогона), `GET /core_reject/nodes`
(все стоящие вердикты из хранения — в отличие от прогона, переживают
перезапуск процесса), `GET /core_reject/banner`,
`POST /core_reject/banner/dismiss`, `GET /core_reject/prompt` и

**Д-1а — чего не хватало для проверки на устройстве.** Наблюдать фичу было
можно, а завести — нет: старт шёл только с экрана. Добавлено (полные описания
в `docs/api/debug-api-reference.md`):

| Путь | Зачем |
|---|---|
| `POST /action/start-vpn-headless?guard=true` | старт **через страховку** — тот же автомат, что на кнопке Start. Без флага прежний путь байт в байт |
| `POST /action/check-config[?timeout_ms=]` | `Libbox.checkConfig` по текущему собранному конфигу → `{config_ok, error, ms, bytes}`; `error` — сырой текст ядра. Сервер однопоточный ⇒ потолок ожидания, не успели — 409 |
| `GET /subs/{id}?warnings=true` | предупреждения разбора по узлам: `{tag: [{code, severity, path, value, params, title_en, text_en}]}`, пиненный английский |
| `GET /subs/{id}?reveal=true` | теперь отдаёт `raw` и у одиночного `UserServer` (раньше только у члена папки) |
| `GET /nodes/link?tag=` | экспорт узла ссылкой — тот же emit, что у `Copy link`; `{uri, private_key}` либо `{error}` |

Ради первого пункта прогон уехал из экрана в
`app/lib/services/core_reject/core_reject_runner.dart` (`runCoreRejectGuard`):
экран зовёт его же, отдавая своё — тихую пересборку и диалог предела; Debug
API зовёт без них, и предел там остаётся пределом (ответить заранее можно
`POST /core_reject/prompt?answer=keep`). Заодно `core_reject_host.dart`
переехал из `screens/home/` в `services/core_reject/`: виджетов он не знал
вовсе, а сервису нельзя зависеть от экрана.

Форма ответа `warnings` не зависит от того, переведён ли класс предупреждения
на `RegistryWarning`: общий интерфейс — `NodeWarning` (`severity`,
`renderEn()`), у кода реестра дополнительно есть `path`/`value`/`title_en`.

### Замер

Пересборка конфига — 26 мс на 500 узлах, 122 мс на 2000 (Dart-тест, 5
прогонов после прогрева). `Libbox.checkConfig` на устройстве не замерен:
прогона на эмуляторе в этой сессии не было. Устройство остаётся должно —
вместе с вопросами про `cache.db` и про помеху идущему VPN при Reconnect
(раздел 3).
