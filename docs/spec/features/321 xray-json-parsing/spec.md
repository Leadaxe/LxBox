## 1. Зачем

Ветка `JsonFlavor.xrayArray` умеет **один протокол из четырнадцати**.
[json_parsers.dart:27](../../../../app/lib/services/parser/json_parsers.dart):

```dart
final vlessAll = outbounds.whereType<Map<String, dynamic>>()
    .where((o) => o['protocol'] == 'vless').toList();
if (vlessAll.isEmpty) return const [];      // элемент выбывает целиком
```

Элемент без VLESS не даёт ничего и **не сообщает об этом**. Ни warning, ни
запись в лог.

### Обнаружено на реальной подписке

Liberty VPN (30.07.2026, 38 элементов, 138 КБ):

| форма | шт | протокол | доехало |
|---|---|---|---|
| страна | 30 | vless+reality | 30 |
| **GAMING** | **3** | **hysteria2** | **0** |
| Лучший сервер | 1 | vless ×15 | 15 |
| БС | 6 | vless ×3 | 18 |

Три платных узла (Швейцария/Финляндия/Нидерланды GAMING) не доезжают до
пользователя. При этом `Hysteria2Spec` в модели **есть**, из URI и из
sing-box JSON парсится нормально — дыра именно в Xray-ветке.

Потеря маскировалась арифметикой: 61 узел в конфиге = 61 vless-outbound в
файле. Сходилось потому, что не-vless выпадал **до** подсчёта. Правильный
счёт — 64 прокси-outbound, 61 доехал.

### Второй дефект: дубли

Liberty описывает **37 физических серверов 64 записями**. Один
`45.196.208.40` фигурирует в пяти элементах: как «Испания», как кандидат
«Лучшего сервера» и как член трёх «БС». Побайтово идентичен во всех пяти
(проверено: одинаковые `publicKey`/`shortId`/`serverName`/`fingerprint`,
различается только `tag`).

Это не патология провайдера, а следствие схемы Xray: элемент = автономный
конфиг со своим `routing`, и чтобы сервер участвовал в трёх сценариях, его
приходится физически вписывать трижды. Дедуплицировать там негде.

У нас модель другая — узел один, каналы над ним. Поэтому наш список честно
показал размазанное по 38 файлам: **61 строка вместо 37 серверов**.

## 2. Принципы парсинга (нормативная часть)

### P1 — Элемент даёт N узлов, не один

Каждый прокси-outbound элемента становится узлом. Наследие §310, распространяем
на все протоколы.

**Исключения — служебные outbound'ы:**

| protocol | роль | узлом становится |
|---|---|---|
| `freedom` | direct | нет |
| `blackhole` | block | нет |
| `dns` | DNS-перехват | нет |
| остальные | payload | **да** |

Плюс цели `sockopt.dialerProxy` — они приезжают detour-звеном своего
владельца (`⚙ <tag>`), самостоятельным узлом не дублируются. Контракт §018
не меняется.

### P2 — Порядок обработки: от одиночных к многоузловым

Элементы сортируются по числу payload-outbound'ов **по возрастанию**, и
только потом парсятся.

Причина — в связке с P4 (дедуп). Первый увидевший сервер даёт ему имя.
Liberty:

| порядок | результат |
|---|---|
| как в файле | `45.196.208.40` → «🇪🇺 Авто \| Лучший сервер ⚡⚡ proxy-45-196-208-40-direct» |
| **по возрастанию** | `45.196.208.40` → **«🇪🇸⚡Испания»** |

Одиночные элементы = «карточка страны», их `remarks` осмысленны.
Многоузловые = пулы, их `remarks` описывают **группу**, а не сервер.

Сортировка **стабильная**: внутри одной длины порядок файла сохраняется.

### P3 — Имя: `remarks` достаётся ровно одной сущности

**Переписано 31.07.2026** (было: «i == 0 → remarks, остальные → с тегом»).

Элемент подписки описывает одну сущность, и его `remarks` — имя этой
сущности. Кому именно оно принадлежит, зависит от содержимого:

| что в элементе | группа (§322) | узлы |
|---|---|---|
| 1 узел | — | `remarks` |
| N узлов | — | `remarks <тег>` |
| N узлов + `routing.balancers` | `remarks` | `remarks <тег>` |

То есть чистый `remarks` носит **ровно одна** сущность: группа автовыбора,
если она есть; иначе — единственный узел. При нескольких узлах без группы
`remarks` не получает никто.

**Почему изменили.** Прежнее правило отдавало чистый `remarks` первому узлу
(`i == 0`) ради обратной совместимости. Когда §322 добавил узел автовыбора,
берущий то же `remarks`, они стали драться за имя: `allocateTag` разводил их
суффиксом, и в списке появлялись «🇪🇺 Авто | Лучший сервер ⚡⚡» и
«…⚡⚡-1» — на вид близнецы, но первый обычный узел, второй группа.

Проявилось не сразу: у Liberty первый узел «Лучшего сервера» долго
дедуплицировался с другим элементом и имя освобождал. Провайдер сменил его
на `45.196.31.136`, который больше нигде не встречается, — и дыра всплыла.

**`solo` считается по ИСХОДНОМУ числу узлов, не по выжившим** после дедупа
(P4). Если провайдер положил несколько серверов, `remarks` описывает набор, а
не того одного, кто уцелел: иначе имя элемента доставалось бы произвольному
выжившему и уезжало при каждом обновлении подписки. На Liberty таких
элементов шесть — все «БС»-группы, где из трёх узлов остаётся один.

**Фолбэки** (в порядке проверки):

| условие | имя |
|---|---|
| тег пуст | `remarks <i+1>` |
| тег встречается в элементе больше раза | `remarks <i+1>` |
| `remarks` пуст | сам тег, либо `<i+1>` |

Индекс — позиция в **исходном** порядке элемента, не среди выживших: при
пропуске дубля имена не съезжают (P3-инвариант, тест «выживший второй член
не занимает имя первого»).

Повторяющийся тег — исходный случай §310: провайдер зовёт все узлы `proxy`,
и `remarks proxy` их не развёл бы.

**«Main»** (первый в `ordered`) по-прежнему выбирается по приоритету: цель
`dialerProxy` → тег ровно `proxy` → первый в списке. На имя это больше не
влияет — только на порядок в списке.

`_elementLabel` ([:273](../../../../app/lib/services/parser/json_parsers.dart))
принимает `remarks`, outbound, индекс, флаг `solo` и карту частот тегов.

### P4 — Дедуп по идентичности

**Ключ:** `(protocol, server, port, credential)`

`credential` по протоколу:

| протокол | поле |
|---|---|
| vless / vmess | `settings.vnext[0].users[0].id` |
| trojan | `settings.servers[0].password` |
| shadowsocks | `settings.servers[0].password` |
| hysteria2 | `streamSettings.hysteriaSettings.auth` |
| socks / http | `settings.servers[0].users[0].user` (или `""`) |
| остальные | `""` |

Сервер, уже виденный в этом проходе, **пропускается целиком** — второй узел
не создаётся.

**Ключ намеренно не включает транспорт и TLS.** Решение пользователя
(30.07.2026): «протокол сервер порт uuid». Следствие: один сервер с двумя
разными SNI схлопнется в один узел — берётся первый по порядку P2. На
Liberty таких случаев нет (проверено: 0 расхождений в телах при совпадении
ключа), но на других подписках возможны.

**Область действия — один вызов парсера**, то есть одна подписка. Между
подписками дедуп не работает: это разные источники с разными
`tag_prefix`/`detour_policy`, схлопывать их нельзя.

### P6 — Таблица синонимов тегов

При дедупе (P4) известно, что два тега принадлежат одному серверу. Эта связь
**сохраняется**, а не выбрасывается:

```
идентичность                      →  Set<тег>
vless|45.196.208.40|443|<uuid>    →  { proxy,                        (из «Испании»)
                                       proxy-45-196-208-40-direct,   (из «Лучшего»)
                                       proxy-decoy-45-196-208-40-… } (из «БС»)
```

Нужна для §322: провайдер задаёт состав пула тегами (`selector: ["proxy"]`),
а в нашей модели этих тегов после дедупа нет. Таблица переводит тег
провайдера в наш узел независимо от порядка обработки.

Побочно закрывает и обратный вопрос — «под какими ещё именами этот сервер
встречался в подписке»: пригодится в UI узла («Source», §302).

**Время жизни — один разбор подписки.** В storage не уходит: на следующем
обновлении пересобирается из свежего тела.

### P5 — Неподдержанный протокол не теряется молча

Прямая причина этой фичи: три GAMING-узла пропали без следа, и обнаружилось
это только при ручном пересчёте outbound'ов.

Теперь `protocol`, который мы не умеем, вешает `UnsupportedProtocolWarning`
на **соседний узел элемента** — по одному warning на протокол, не на каждый
outbound. Пользователь видит его в списке узлов подписки (`NodeWarningRow`).

**Почему на соседа, а не на свой узел:** узла нет, он и не собрался.
`NodeWarning` живёт на `NodeSpec` — носителя без узла не существует.

**Чего это НЕ покрывает:** элемент, не давший **ни одного** узла (весь пункт
на неподдержанном протоколе), — вешать warning некуда, и такой пункт исчезает
молча. Отдельный канал «warnings уровня подписки» ради этого не заводили:
`parseAll` возвращает `List<NodeSpec>`, менять её сигнатуру и всех
вызывающих несоразмерно. После §321 случай возможен только если провайдер
отдаст пункт целиком на wireguard/ssh/socks — у Liberty таких нет.

## 3. Поддерживаемые протоколы

Xray-схема ≠ sing-box-схема: у Xray `settings.vnext[]`/`streamSettings`, у
sing-box плоские поля. `parseSingboxEntry` **не переиспользуется** — нужен
свой конвертер на протокол.

| Xray `protocol` | NodeSpec | приоритет | примечание |
|---|---|---|---|
| `vless` | `VlessSpec` | есть | `_xrayVlessToSpec`, не трогаем |
| `trojan` | `TrojanSpec` | P1 | `settings.servers[]` |
| `vmess` | `VmessSpec` | P1 | `settings.vnext[]`, `alterId`/`security` |
| `shadowsocks` | `ShadowsocksSpec` | P1 | `method`+`password` |
| `hysteria` (v2) | `Hysteria2Spec` | P1 | **форк-специфично**, см. ниже |
| `socks` | `SocksSpec` | P2 | сейчас только detour-звено |
| `http` | `HttpSpec` | P2 | |
| `wireguard` | `WireguardSpec` | P3 | Xray-форма отличается сильно |
| `freedom`/`blackhole`/`dns` | — | — | служебные, P1 |

### hysteria в Xray — нестандарт

Апстримный Xray hysteria2 **не поддерживает**. Форма из Liberty:

```jsonc
{
  "protocol": "hysteria",
  "settings": { "address": "45.196.193.40", "port": 8449, "version": 2 },
  "streamSettings": {
    "network": "hysteria", "security": "tls",
    "hysteriaSettings": { "auth": "<uuid>", "version": 2 },
    "tlsSettings": { "serverName": "...", "alpn": ["h3"], "fingerprint": "firefox" },
    "finalmask": { "quicParams": { "congestion": "bbr" } }   // ← расширение форка
  }
}
```

Читаем как `Hysteria2Spec`: `address`/`port`/`auth`/TLS. `finalmask` **не
переносим** — у sing-box нет соответствия, и подмешивать чужое расширение в
конфиг нельзя (unknown field валит весь конфиг).

`version` обязан быть `2`; `version: 1` (hysteria v1) — warning и пропуск,
у нас нет `Hysteria1Spec`.

## 4. Алгоритм

```
parseXrayArray(List elements) -> List<NodeSpec>

  1. для каждого элемента посчитать payloadCount
     (outbound'ы, кроме freedom/blackhole/dns)

  2. стабильно отсортировать по payloadCount возрастанию   ← P2

  3. seen = {}                                             ← P4, на весь массив
     result = []

  4. для каждого элемента в новом порядке:
       nodes = parseXrayElement(element, seen)
       result += nodes
       если nodes пуст → warning                           ← P5

  5. вернуть result
```

`parseXrayElement` меняется:

```
parseXrayElement(element, seen) -> List<NodeSpec>

  1. payload = outbounds где protocol не служебный
     если payload пуст → warning + []                      ← P5

  2. dialerTargets = цели sockopt.dialerProxy
     candidates = payload минус dialerTargets

  3. упорядочить: main первым (dialerProxy → тег 'proxy' → первый)

  4. для каждого кандидата i:
       key = identity(ob)                                  ← P4
       если key в seen → continue
       seen += key
       spec = convert(ob, _elementLabel(remarks, ob, i))    ← P3
       если spec == null → warning + continue               ← P5
       приложить sourceCompact/sourceExtended (§302)
       приложить chained если dialerProxy
```

**Важно:** `i` для имени — индекс в `candidates` **до** дедупа. Иначе имена
поедут при пропуске: второй выживший получил бы `i=1` и назвался как
первый.

## 8. Открытые вопросы

1. **WireGuard в Xray-форме** — отложен (P3). Форма отличается настолько,
   что это отдельная таска.
2. **Дедуп между подписками** — намеренно нет. Если одна нода придёт из двух
   подписок, будет два узла с разными префиксами. Это верно: у них разные
   `detour_policy`.
3. **Сортировка P2 меняет порядок узлов в списке** у существующих
   пользователей. Ручной порядок (§071) хранится по id узла и переживёт;
   пользователи без ручного порядка увидят перестановку один раз.
