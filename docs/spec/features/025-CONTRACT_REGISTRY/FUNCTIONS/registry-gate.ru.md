# Гейт реестра на сборке — что запиненное ядро не потянет, в конфиг не попадает

Прежде чем конфиг уйдёт в ядро, каждое тело узла судится ещё раз по схеме реестра для запиненной
версии ядра и тегов его сборки; что ядро отвергло бы — снимается, авторский JSON только
комментируется.

| Поле | Значение |
|------|----------|
| Фича | [025-CONTRACT_REGISTRY](../FEATURE.ru.md) |
| Обещания | P7 P8 P9 P10 P11 |
| Состояние | ✅ написана по коду, 2026-09-29 |

## Что делает

Стадия 5 [конвейера сборки](../../003-CONFIG_BUILD/FUNCTIONS/build-pipeline.ru.md). Разбор судил
узел без ядра (P3 фичи); гейт — место, где ядро наконец значимо. Он получает только записи из
источников узлов — служебные outbound'ы шаблона и группы Направлений не тела узлов и сюда не
попадают. Три проверки, по порядку:

1. **Страховка типа.** Запись без непустого строкового `type` — не тело sing-box: снимается с
   `field_missing` (`field: type`). Идёт до реестра и без него, потому что одна такая запись
   заставляет ядро отвергнуть весь конфиг, не назвав узел.
2. **Узловой гейт ядра.** Протокол, поле или форма-диапазон с `on_core_unsupported: drop_node`,
   чьё требование — `build_tag` по набору тегов приложения, `min_core` по версии ядра — ядро не
   выполняет, снимает запись целиком с кодом реестра (`tailscale_core_unsupported`, коды диапазона
   AWG и 3.x).
3. **Санитайзер по схеме тела** для версии ядра: поле, которого ядро не знает, снимается с
   `unknown_key`, негодные значения — по `on_invalid`, поля `min_core`/платформы снимаются;
   вердикт `drop_node` снимает запись.

## Параметры

| Вход | Значение | Эффект |
|---|---|---|
| Версия ядра | запиненное ядро (`v1.14.2-lx.8`); пусто, если неизвестна | пусто — гейты `min_core` не срабатывают (fail-open) |
| Теги сборки | зеркало тегов AAR в приложении; `null` — неизвестны | `null` — гейты `build_tag` не срабатывают |
| Источник тела | `singbox` у авторского тела, `other` у всего прочего | решает, мягкое правило или жёсткое (ниже) |
| Реестр | грузится из бандла | не загружен — гейт no-op, кроме страховки типа |

## Входы / Выходы

**Входы:** эмитированные `outbounds[]` и `endpoints[]` из источников узлов с признаком
«авторское» у записи; версия ядра и теги.
**Выходы:** тела, очищенные на месте; список снятых записей (они уходят и из пулов Направлений, и
из карты тегов); строки предупреждений для отчёта сборки; предупреждения по финальному тегу
конфига — оттуда их читают карточка узла и Debug API.

## Правила и инварианты

- **Отказ — код реестра, а не ошибка сборки.** Конфиг всё равно пишется; узел снят и назван.
- **Авторское тело только комментируется** ([577](../../../tasks/577-authored-json-registry-reports-only.md)):
  мягкое правило оставляет значение и даёт код с `applied: false`; строка отчёта получает пометку
  `(not applied)`. Жёсткие правила применяются и к авторскому телу: правила `core_rejects`,
  негодный `type`, узловой гейт ядра.
- **Правки — на месте.** Те же map-объекты уже лежат в пулах Направлений; подмена ссылки оставила
  бы половину из них со старым телом.
- **Неизвестное — не «слишком старое».** Неизвестная версия ядра или неизвестный набор тегов узел
  не снимают.
- **Строки отчёта дедупятся** по `tag: текст [path=value]`.
- **Probe-конфиг** (проверки узлов) идёт через тот же гейт; узел, который ядро не потянет, не
  пробуется тоже.
- Повтор кодов разбора: код, который разбор уже поставил на узел, может прийти от гейта ещё раз
  под финальным тегом — карточка группирует записи по коду.
