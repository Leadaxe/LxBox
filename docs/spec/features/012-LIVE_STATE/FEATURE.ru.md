# Живое состояние — статистика VPN-трафика, соединения и работающий конфиг

LxBox показывает живой трафик, открытые соединения и работающий конфиг ядра
sing-box — с приложением-владельцем, правилом и узлом каждого соединения.
Данные видны в полосе трафика на главном экране и на экране Statistics с
вкладками Stats и Conns; вкладка Profiler описана в 028-TRAFFIC_PROFILER.

| Поле | Значение |
|------|----------|
| Фича | 012-LIVE_STATE |
| Тип | Продуктовая фича |
| Поглотила | `§016F` `§122F` `§123F` |
| Состояние | ✅ написана по коду, 2026-09-28 |

## Назначение

Когда туннель поднят, пользователь хочет видеть, что происходит внутри: сколько
передано, сколько соединений открыто, куда ходит конкретное приложение, через
какое правило и какой узел оно ушло, какой конфиг реально крутит ядро. Фича превращает внутреннее состояние ядра в
наблюдаемые экраны и числа — без открытых портов, ручных дампов и внешних
инструментов.

Фича защищает четыре принципа:

- **Два мира статуса не смешиваются.** «Туннель поднят / остановлен» говорит
  служба туннеля; каналы данных ядра дают только статистику. Обрыв или сон
  канала данных не выглядит как падение туннеля.
- **Наблюдение не стоит батареи.** Частота данных режется у источника:
  главному экрану хватает двух тиков в секунду, статистике — десяти, в фоне —
  ноль. В фоне живёт только то, что пользователь явно запустил (запись
  профайлера).
- **Правда о пути пакета — от ядра.** Цепочка «правило → группы → узел →
  detour → цель» и владелец соединения берутся из ядра, а не угадываются
  клиентом.
- **Честное «не знаю».** Вердикт «конфиг устарел» имеет третье значение —
  «ответить нельзя»; несостоявшееся сравнение не выдаётся за совпадение.

## Обещания

- **P1. Статус туннеля не зависит от каналов данных.** Сон или обрыв каналов
  данных ядра не переводит туннель в «отключён»; выключение туннеля в фоне
  замечается и без них. Свидетель: ручная проверка — туннель поднят, свернуть
  приложение на минуту, вернуться: статус «Connected» без мигания, счётчики
  ожили; остановить туннель из шторки при свёрнутом приложении — по возврату
  статус «Disconnected». Мутация: статус туннеля выводится из событий
  подключения канала данных.
- **P2. Частота режется у источника.** Тик статуса: главный 0,5 с, открыт
  Statistics 0,1 с, фон — 0. `без свидетеля` (разовая проверка §164).
- **P3. В фоне живёт только запись профайлера.** Статус и группы/соединения
  засыпают при сворачивании и просыпаются при возврате; начатая запись
  профайлера продолжается. Свидетель: ручная проверка — START в профайлере,
  свернуть на 2 мин, вернуться: в журнале события за время фона. Мутация:
  пауза профайлера вместе с остальными каналами.
- **P4. Счётчики соединений согласованы.** На главном — раздельно «соединения
  приложений» и «соединения к серверам»; первое равно числу на карточке
  Connections в статистике и числу «active» во вкладке Conns. `без свидетеля`.
- **P5. Повторное открытие не теряет данных.** Повторный вход в статистику,
  переподключение туннеля и возврат после смахивания из недавних показывают
  текущие группы и соединения, а не пустой экран. Свидетель: ручная проверка
  — смахнуть приложение при поднятом туннеле, открыть иконкой: группы и
  список соединений на месте (§185 device-verified). Мутация: соединения
  копятся, только пока экран подписан.
- **P6. Правило называется по-человечески.** Имя правила в статистике и
  соединениях берётся из пользовательского справочника; ненайденное — `final`.
  Свидетель: юниты «матч по условиям → title (даже при обрезке списка ядром)»,
  «правило не найдено → fallback final». Мутация: показ сырой строки ядра.
- **P7. Зависшее соединение подсвечено.** TCP старше 3 с с трафиком строго в
  одну сторону помечается «One-way»; UDP, свежие и закрытые — нет. Свидетель:
  юниты «TCP, age≥3s, up>0 down=0 → true», «UDP однобокое → false», «свежее
  (<3s) → false», «закрытое → false». Мутация: порог по возрасту убран.
- **P8. Маршрутная строка одна для соединений и профайлера.** Слева — как
  выбирал роутер (`rule ⇒ группы`), справа от `:` — физический путь пакета
  (вход первым, выход перед целью); пустое правило — `final`; без домена —
  хост из адреса. Свидетель: юниты «§204 routingLineOf 1:1 Conn ↔ Event»,
  «chains и detours несутся РАЗДЕЛЬНО». Мутация: detour вклеен в цепочку групп.

- **P18.** перенесено в [028-TRAFFIC_PROFILER · P16](../028-TRAFFIC_PROFILER/FEATURE.ru.md#обещания).
- **P19. NETWORKS показывает узлы вне списков выбора.** Tailscale-узлы из
  `endpoints[]` без `exit_node` видны отдельным псевдо-направлением при
  поднятом VPN, с состоянием вместо задержки; выбрать такой узел выходом
  нельзя. Свидетель: юниты «состав NETWORKS», «VPN выключен — NETWORKS не
  показывается», «на месте задержки состояние, нажатие не выбирает узел».
  Мутация: NETWORKS пишется в конфиг как группа. Подробно —
  [030-TAILSCALE](../030-TAILSCALE/FEATURE.ru.md).
- **P20. Вердикт свежести трёхзначен.** «Совпадает / устарел / не знаю»;
  «не знаю» не гасит плашку «нужен перезапуск». Свидетель: юниты §324
  «нет канонической формы → unknown (НЕ fresh)», «нет снапшота работающего →
  unknown». Мутация: сбой сравнения трактуется как «совпадает».
- **P21. Снимок работающего конфига принадлежит своей сессии ядра.** Ответ
  ядра, пришедший от прежней сессии после перезагрузки, не принимается;
  после перезагрузки снимок перезахватывается; при опущенном туннеле
  используется сохранённый конфиг. Свидетель: юниты §311 «ответ старого box'а
  не переживает reload», «после reload снапшот перезахватывается ретраями»,
  «туннель down при живом снапшоте → configModel». Мутация: снимок без
  привязки к сессии.
- **P22. Обрыв при смене узла — только переключаемой группы.** При «Interrupt
  connections on switch» закрываются живые соединения с этой группой в
  цепочке; в Conns они становятся закрытыми. `без свидетеля`.

## Контролируемые параметры

| Настройка | Значения | Дефолт | Где |
|-----------|----------|--------|-----|
| Показ закрытых соединений | 30 с / все до выключения | 30 с | переключатель во вкладке Conns; только на время экрана |
| Interrupt connections on switch | вкл/выкл | выкл | принадлежит 010-VPN_SERVICE; здесь — наблюдаемый эффект |

Фиксированные величины (не настраиваются): тик статуса 0,5 с / 0,1 с / 0 в
фоне; перерисовка счётчиков главного экрана не чаще 1 с; пересчёт списков
статистики и соединений не чаще 0,7 с; закрытые соединения ядро держит
5 мин; переподключение канала статуса — от 0,5 с до 8 с. Ручки и квоты
профайлера — 028-TRAFFIC_PROFILER.

**Контракт с ядром.** Ключей конфига фича не отдаёт. Потребляемые вызовы и
подписки ядра: `CommandStatus` (объём, память, горутины, `connectionsIn` /
`connectionsOut`, интервал задаётся подписчиком), `CommandGroup`,
`CommandOutbounds`, `CommandConnections` (дельты; цепочка `chain`, хвост
`detour`, владелец, `createdAt`/`closedAt`), `CommandDNS` (поток DNS-запросов,
потребляется 028-TRAFFIC_PROFILER), `GetGroups`,
`GetOutbounds`, `GetRunningConfig`, `FormatConfig`, `closeConnection`,
`closeConnections`, `SubscribeTailscaleStatus` (`BackendState`, `StateText`).

## Входы / Выходы

**Входы:** статус службы туннеля; подписки и ответы ядра (см. «Контракт с
ядром»); жизненный цикл приложения; жесты — Statistics, START/STOP записи
профайлера, закрытие соединений; сохранённый конфиг; справочник правил.

**Выходы:** полоса трафика главного экрана (↑/↓ объём, соединения приложений
и к серверам, индикатор «Live», время подключения); экран Statistics с
вкладками Stats / Conns; детали соединения; строки узлов NETWORKS; снимок
работающего конфига и вердикт свежести для плашки «нужен перезапуск»; вызовы
`closeConnection` / `closeConnections`.

## Data flow

```
ядро ──CommandStatus──► статус (0,5 / 0,1 / 0 с) ──► полоса трафика, Stats
     ──Group/Outbounds──► группы ─(+ GetGroups-pull)─► список узлов
     ──Connections (дельты)──► накопитель на клиента ──► снапшот
          ├─► Stats: только живые → по правилу
          ├─► Conns: живые + закрытые (30 с / все)
          └─► канал профайлера (при записи) ──► 028-TRAFFIC_PROFILER
     ──CommandDNS──► канал профайлера ────────────► 028-TRAFFIC_PROFILER
     ──GetRunningConfig──► снимок сессии ──► модель узлов; сравнение с
                              каноном сохранённого (FormatConfig) → вердикт
служба туннеля ──статус──► Connected/Disconnected (независимо от каналов)
```

## Правила и гарантии

- Статус туннеля приходит от службы; события «канал данных подключён /
  отключён» используются только для переподключения канала.
- Каналы разделены по жизненному циклу: статус, экраны (группы+соединения),
  профайлер, разовые вызовы; смена частоты статуса не рвёт остальные.
- Соединения приходят дельтами: накопитель применяет каждую дельту, даже
  когда экран не слушает; новому подписчику сразу отдаётся накопленное.
- Пустой снимок групп поверх непустого игнорируется; стартовые группы
  добираются разовым `GetGroups` (до ~5 с шагами 0,4 с).
- Каждый потребитель соединений сам решает, что показывать: Stats — только
  живые, Conns — живые и закрытые, профайлер — всё как события.
- При остановке туннеля кэши каналов сбрасываются.
- Разовые вызовы различают «недоступно» и «пусто»; «недоступно» не трогает экран.

## Границы

- Запуск, остановка, переподключение, распознавание «молчащего ядра» по
  тишине статуса — 010-VPN_SERVICE.
- Профайлер и трасса DNS — 028-TRAFFIC_PROFILER: запись, атрибуция,
  фильтры, здоровье DNS, маршруты `/profiler/*`.
- Журнал приложения и ядра, отчёты о сбоях — 013-DIAGNOSTICS; Debug API —
  027-DEBUG_API.
- Плашка «нужен перезапуск» и когда её поднимать — 003-CONFIG_BUILD; здесь
  только вердикт, умеющий её гасить.
- Замер задержек, пробник — 009-NODE_HEALTH; вкладка Network Tailscale —
  030-TAILSCALE; выбор узла и перечень направлений — 007-NODE_LIST (NETWORKS
  лишь добавляется в него).
- Разбивки трафика по приложениям на экране Stats нет и не планируется
  (решение владельца 2026-09-29, аудит [588](../../tasks/588-spec-kit-revision-audit.md)) — это журнал профайлера.
- Зависит от возможностей ОС: события «передний план / фон», владелец трафика.

## Особенности сопровождения

- Соединения — дельты, а не снапшот. Любая «оптимизация», отбрасывающая
  дельты без подписчика, даёт пустой Stats при живом трафике (§122, §193).
- Один накопитель соединений на два канала роняет ядро — только раздельные (§170).
- После смахивания из недавних каналы данных осиротевают: на первом старте
  нового движка их нужно пересинхронизировать, но только на первом — иначе
  каждое переподключение туннеля теряет соединения (§185, §193).
- Список полей, которые ядро накладывает поверх конфига при старте, живёт в
  двух местах (вердикт свежести и служба); расхождение даёт вечное «устарел»
  или пропущенное изменение — держится тестом-инвариантом (§324).
- После перезагрузки ядро ещё ~1 с отвечает прежним конфигом без ошибки;
  отличать надо по содержимому, а идентичный конфиг после ~5 с принимать
  (§311, §384).
