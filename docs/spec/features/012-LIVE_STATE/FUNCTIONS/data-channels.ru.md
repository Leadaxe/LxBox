# Каналы данных ядра и энергомодель — живые данные без расхода батареи

Все живые экраны этой фичи читают ядро через эти каналы.

| Поле | Значение |
|------|----------|
| Фича | [012-LIVE_STATE](../FEATURE.ru.md) |
| Обещания | P2, P3, P5 |
| Состояние | ✅ написана по коду, 2026-09-28 |

## Что делает

Доставляет живые данные ядра на экраны приложения по встроенному каналу
управления ядра (без открытого сетевого порта) и держит его расход батареи
минимальным: данные текут только туда и только с той частотой, которые
сейчас видны пользователю.

## Параметры

Настроек пользователя нет. Фиксированные режимы:

| Режим | Тик статуса | Когда |
|-------|-------------|-------|
| NORMAL | 0,5 с | передний план, главный экран |
| FAST | 0,1 с | открыт экран Statistics |
| пауза | нет | приложение в фоне |

## Входы / Выходы

**Входы:** жизненный цикл приложения; открытие/закрытие экранов-потребителей;
START/STOP записи профайлера; события ядра.

**Выходы:** четыре независимых канала.

| Канал | Подписки ядра | Живёт | Засыпает в фоне |
|-------|---------------|-------|-----------------|
| статус | `CommandStatus` с интервалом | пока поднят туннель | да |
| экраны | `CommandOutbounds`, `CommandGroup`, `CommandConnections` | пока открыт хоть один потребитель (главный, Statistics) | да, счётчик потребителей сохраняется |
| профайлер | `CommandConnections`, `CommandDNS` | пока идёт запись | нет |
| разовые вызовы | `GetGroups`, `GetOutbounds`, `GetRunningConfig`, `closeConnection`, выбор узла и др. | по требованию | нет |

## Правила и инварианты

- Смена частоты статуса пересоздаёт только канал статуса; группы и
  соединения при этом не рвутся — поэтому каналы и не сливаются.
- Канал статуса после обрыва переподключается сам (0,5 → 8 с), пока туннель
  жив и приложение не в фоне; остальные поднимаются явно.
- Возврат из фона: статус поднимается с текущей частотой; экраны — только
  если потребитель ещё открыт.
- Соединения приходят дельтами. Накопитель применяет каждую, даже без
  подписчика, и отдаёт новому подписчику полный снимок сразу. У каналов
  «экраны» и «профайлер» накопители раздельные.
- Ядро отдаёт и живые, и закрытые (до 5 мин) соединения; что показывать,
  решает каждый потребитель.
- Каждый канал отдаёт подписчикам последний снимок сразу при подписке;
  при остановке туннеля снимки сбрасываются.
- Статус, группы и соединения схлопываются до последнего снимка; DNS-события
  не схлопываются (каждое — отдельный факт), при переполнении очереди
  (4096) отбрасываются новые.
- Группы: пустой снимок поверх непустого — шум, игнорируется; стартовые
  группы добираются `GetGroups` каждые 0,4 с до 12 попыток. `GetGroups` /
  `GetOutbounds` различают «недоступно» и «групп нет».
- Первый старт интерфейса после смахивания при живом туннеле
  пересинхронизирует осиротевшие каналы (сброс счётчика потребителей,
  частота NORMAL, запись профайлера прерывается); на переподключениях
  туннеля — нет.

## Границы

- Переподключение подписки — обязанность клиента: ядро оборванные
  подписки не восстанавливает.
- Канал профайлера сам не переподключается: запись, начатая при опущенном
  туннеле или пережившая его остановку, событий не получает.
- Зависит от возможностей ОС: события «передний план / фон», выживание
  процесса в фоне.
