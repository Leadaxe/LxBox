# Архитектура — слои кода, фасады доменов и структурные аудиты

LxBox держит каждое поведение в одном месте: код разделён на четыре слоя, каждый домен даёт наружу один
фасад, у данных один источник правды. Приложение растёт задачами, а у каждой задачи своё локальное
«быстрее вписать сюда»; правила этой страницы этому противостоят, а аудиты находят структурные долги раньше,
чем те превращаются в класс багов. В отличие от продуктовых фич, здесь нет обещаний пользователю: здесь
правила, которые позволяют менять продукт дёшево, и реестр проверок этих правил.

## Какие принципы защищает

| # | Правило | Что ломается без него | Откуда |
|---|---------|-----------------------|--------|
| A1 | **Четыре слоя с односторонней зависимостью:** UI → Состояние → Сервисы → Платформа. Логики нет в построении экрана; UI ходит к платформе только через слой состояния | UI-код начинает принимать решения, которые нужны и Debug API, и автоматизации — и они расходятся | ARCHITECTURE «The layers» |
| A2 | **Инвариант фасада.** Домен даёт наружу фасад и не знает своих потребителей (в его сигнатурах нет контекста Debug, виджетов, интентов). Адаптеры — Debug HTTP, Automation, UI — знают транспорт и безопасность, но не то, к чему дают доступ. Операция объявлена один раз, адаптеры сводятся к вызову фасада | четыре входа (UI / Debug / бэкап / сборка) переизобретают одну проверку, и одна из копий отстаёт | §291 |
| A3 | **Strangler-fig, а не big-bang.** Новая структура встаёт за старым поведением по одному домену; приложение релизабельно на каждом шаге | рефактор «всё сразу» блокирует релизы и прячет регрессии | §291 |
| A4 | **Cohesion over line count.** Цель — одна ответственность и связность, а не число строк; 600 связных строк легитимны. Крупное делится в пределах той же библиотеки или извлечением поддеревьев | дробление ради метрики разносит один контракт по файлам | §089 |
| A5 | **Нет монстров.** God-object (экран или контроллер, который владеет всем) расщепляется по ответственностям | любая правка задевает всё, тесты не изолируют | §089, §085 |
| A6 | **Структурный рефактор — zero behavior change**; намеренное изменение поведения — отдельный класс работ со своим реестром кандидатов | «попутные» изменения поведения без спеки | §089 / §090 |
| A7 | **Структура вместо обратного разбора.** Метаданные узла (тег, тип, секция, detour, метки транспорта и защиты) разбираются из конфига один раз в модель; принадлежность подписке — префикс-фильтр по тегу; отображаемый тег обратно не разбирается | целый класс багов «UI разбирает свой же display-тег» | §091 (закрыл §077/§079/§080) |
| A8 | **Два канала разной надёжности — не смешивать.** Статус туннеля идёт надёжным нативным каналом и переживает смерть UI; данные экрана (группы, узлы, соединения, трафик) идут эфемерными подписками ядра, привязанными к UI. Три точки синхронизации: уход в фон, возврат, холодный старт UI (сброс нативных подписок) | «Connected, но список пуст после свайпа» | ARCHITECTURE «The invariant», §163, §185 |
| A9 | **Дефолты — в шаблоне**, не в коде; пользовательские значения — поверх, в хранилище | два источника дефолта расходятся | DEVELOPMENT_GUIDE |
| A10 | **Offline-first:** конфиг собирается из кэша без сети; сборка конфига никогда не качает подписки | старт туннеля зависит от сети | DEVELOPMENT_GUIDE |
| A11 | **Английский — единственный исходный язык UI**; остальные — переводы; литерал в отображаемой позиции валит чекер | строки без ключа не переводятся | DEVELOPMENT_GUIDE, §285 |
| A12 | **Каждая ссылка на исходящий существует:** каждый новый путь, эмитящий outbound, группу или ссылку, сверяется со слоем сборки в реестре стражей — ядро на старте падает от висячей ссылки и называет ссылающегося, а не виновника | весь конфиг мёртв из-за одного узла | DEVELOPMENT_GUIDE «Critical risks», `GUARDS.md` |

## Процесс вокруг кода

- **Сначала спека.** До кода — задача в `docs/spec/tasks/`; изменение
  поведения фичи правит её `FEATURE.md` и добавляет себя в ревизии.
- **Коммиты атомарные**, в `develop`, `git add` только своих файлов; force-push,
  `main`, теги и внешние публикации — только по явной команде оператора.
- **Ленивое чтение (решение владельца 2026-09-24).** Не читать файлы целиком,
  когда хватает `grep`/`sed -n`; доки — только по ссылке из задачи; тяжёлое
  (тесты, чекеры, сборки) — не ради того, что проверит CI; вывод резать.
  Долгий прогон тестов — всегда ТЗ дешёвому субагенту, в контекст — только
  резюме (статус, упавшие с файлом и строкой, первый стек). Решения — у
  думающей модели, разбор вывода — у дешёвой.
- **Полный набор тестов — только на CI**; локально — `flutter analyze` по
  всему проекту и тесты своей задачи (см.
  [023-BUILD_CI_RELEASE](../023-BUILD_CI_RELEASE/FEATURE.ru.md)).
- `AGENTS.md` — только роутер по ссылкам; новые правила — в профильный документ.

## Следить за

- **Сервисы импортируют экраны.** Обработчик цепочек в Debug API берёт
  валидацию и кандидатов звеньев из папки экрана редактора цепочки; контроллер
  DNS — резолвер из папки экрана DNS (долг записан в §300). Это нарушение A1.
- **Таблица «документированных крупных исключений» в ARCHITECTURE.md устарела:**
  профайлер трафика стал меньше (≈870 строк), модель пользовательских правил и
  нативный мост выросли (≈1230 и ≈1560). Файлов больше 1000 строк — 24;
  крупнейшие — резервная копия (≈4500), интерпретатор движка разбора (≈4150),
  контроллер подписок (≈3580) — в таблице их нет.
- **Инвариант-тесты §291 не найдены.** Обещанные тесты границ («адаптер не
  импортирует чужой адаптер») в тестах отсутствуют; держится только
  `@visibleForTesting`-страж сырых мутаторов.
- **ARCHITECTURE.md — 2100+ строк с деревом исходников**, которое дрейфует
  при каждом переезде файла; принципы из него перенесены сюда.
- Хвосты 293 / 295 / 297 не переоткрывают зонтик, но и не закрыты.

## Особенности сопровождения

- Аудит устаревает: реестр описывает код на дату прохода. Повторный цикл —
  после крупных переездов слоёв или смены ядра.
- Без адверсариальной проверки реестр заполняется правдоподобными ложными
  находками (219: 66 из 352) — доверие к нему пропадает.
- Эталон вместо правила: когда домен приводится к инварианту, сначала ищется
  уже работающий эталон (probe, подписки, каналы) и копируется его форма.
