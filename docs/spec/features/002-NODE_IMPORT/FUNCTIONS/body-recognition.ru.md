# Опознание тела — списки ссылок, base64, Xray/sing-box JSON и конфиги WireGuard

Тело подписки, файл или вставка относится ровно к одному виду источника, освобождается от
base64-обёртки и режется на записи для нужного разборщика.

| Поле | Значение |
|------|----------|
| Фича | [002-NODE_IMPORT](../FEATURE.ru.md) |
| Обещания | P3 P5 |
| Состояние | ✅ написана по коду, 2026-09-28 |

## Что делает

Смотрит на текст целиком (тело подписки, файл, вставку) и решает, что это:
список ссылок, base64 от чего-то, JSON какого диалекта, `.conf` или профиль
Amnezia. Затем режет его на записи и отдаёт каждую своему разборщику.

## Параметры

Виды источника — таблица реестра; пробуются по приоритету, побеждает меньший.

| Приоритет | Вид | Признак | Записи |
|-----------|-----|---------|--------|
| 10 | `amnezia_link` | начинается с `vpn://`, следующие строки не ссылки | INI на каждый WG/AWG-контейнер |
| 20 | `base64_wrapped` | ≥ 16 символов, алфавит base64 (std или url-safe) | распакованный текст судится заново |
| 30 | `singbox_config_array` | массив конфигов, у outbound'ов `type`, нет `protocol` | `[].outbounds[]` |
| 31 | `xray_config_array` | массив конфигов с `outbounds` | `[].outbounds[]` |
| 32 | `singbox_outbound_array` | массив объектов с `type` | `[]` |
| 33 | `xray_outbound_array` | массив объектов с `protocol` | `[]` |
| 34 | `xray_outbound` | объект с `protocol` | сам объект |
| 35 | `xray_config` | объект, в `outbounds` есть `protocol` | `outbounds[]` |
| 40 | `singbox_outbound` | объект с `type` | сам объект |
| 50 | `singbox_config` | объект с `outbounds`/`endpoints` | `outbounds[]` + `endpoints[]` |
| 60 | `wireguard_conf` | первая некомментарная секция `[Interface]` | сам текст |
| 100 | `uri_lines` | всё остальное | непустые некомментарные строки |

Глубина снятия base64 — 2 слоя. Комментарии списка — `#`, `//`, `;`.

## Входы / Выходы

**Вход:** текст. **Выход:** одна из форм — строки ссылок, INI-тексты, JSON
с объявленным путём к записям, либо «не декодировано» с причиной.

## Правила и инварианты

- Каждый текст опознаётся ровно одним видом; `uri_lines` — ветка по
  умолчанию и никогда не конкурирует с настоящим признаком.
- Base64-ветка выигрывает только если распакованное похоже на документ
  (`://`, `{`, `[`, `[Interface]`); иначе остаётся список строк. Третий слой
  base64 не снимается — узлов нет, исключения нет.
- BOM в начале текста, `\r\n` и url-safe алфавит без паддинга не мешают.
- Неоднозначный массив конфигов (есть и `type`, и `protocol`, либо ни того ни
  другого) остаётся за Xray.
- Одиночный объект с `type` — outbound, даже если у него есть `outbounds`
  (одиночный `selector`).
- JSON с комментариями принимается; в источник узла он сохраняется без них.
- JSON с `proxies` (Clash) опознаётся, но узлов не даёт.
- `.conf` без `[Peer]` — законный текст без узлов, не ошибка.
- Пустое тело, только комментарии, только пробелы → «не декодировано»;
  причина декодера уходит в отбраковку кодом `core_rejected`.
- Без загруженного реестра работает запасной порядок того же содержания;
  совпадение запасных веток с реестром сверяется тестом.

## Границы

- Загрузка тела по URL, лимит размера ответа — [001-SUBSCRIPTIONS](../../001-SUBSCRIPTIONS/FEATURE.ru.md).
- Формат по расширению файла (`584F`) не определяется и не планируется
  (решение владельца 2026-09-29, аудит [588](../../../tasks/588-spec-kit-revision-audit.md)): опознание
  идёт только по тексту.
- Clash YAML не разбирается.
