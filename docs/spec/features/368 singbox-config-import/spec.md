## 1. Зачем

Пользователь sing-box переходит к нам со своим конфигом. Сейчас вставка даёт
«Input is not a subscription URL, proxy link, or outbound JSON»: верхнеуровневый
`Map` с `outbounds`, но без `type`, не проходит ни один гейт.

Разбирать сам outbound мы **давно умеем**: `parseSingboxEntry`
([json_parsers.dart:831](../../../../app/lib/services/parser/json_parsers.dart))
покрывает 13 типов. Дыра не в конвертере, а в распознавании формы и в том, что
над outbound'ами нет обхода — того, что для Xray делают §321/§322/§342.

### Требование паритета

**Всё, что мы умеем с Xray-конфигом, должно работать и с sing-box-конфигом,
включая форму «массив автономных конфигов».** Это не «взять outbounds», а
перенести на sing-box-схему все шесть принципов §321 плюс §322 (группы) и §342
(два прохода).

Таблица соответствия — §3. Расхождения (там, где схемы устроены по-разному)
обоснованы поимённо; молчаливых упрощений нет.

### Что просят в issue

| issue | запрос | ответ |
|---|---|---|
| gh#46 | «добавление сервера вставкой JSON не работает» | все формы распознаются |
| gh#27 | «переношу конфиг с sing-box, не хочу настраивать заново» | узлы + группы + detour; `route`/`dns` — нет |

По gh#27 ожидание сбиваем в UI (§8): импортируется **транспортный слой**, а не
конфиг целиком.

### Побочно закрываемое: три разошедшиеся эвристики

| место | проверка | следствие |
|---|---|---|
| [clipboard_analysis.dart:71](../../../../app/lib/screens/subscriptions_screen/clipboard_analysis.dart) | `startsWith('{'\|'[') && contains('"type"')` | превью обещает «Outbound JSON» |
| [subscription_controller.dart:813](../../../../app/lib/controllers/subscription_controller.dart) | то же + `containsKey('type')` | импорт отказывает |
| [body_decoder.dart:159](../../../../app/lib/services/parser/body_decoder.dart) | `v['type'] is String` | flavor |

Массив `[{"type":"vless",…}]` содержит `"type"` подстрокой → превью говорит
«Outbound JSON»; `_isJsonOutbound` принимает, а `_detectFlavor` для `List`
смотрит только Xray-признак (`first['outbounds'] is List`) → `unknown` → 0 узлов.
Через вставку маскируется: `_addJsonOutbounds` разбирает массив **сам**,
поэлементно. По остальным путям (тело подписки, файл-подписка, re-parse
`rawBody` при загрузке, `addMembersToFolder`) массив даёт **ноль узлов молча**.
Это блокер и для главного сценария: подписка, отдающая sing-box-формат, идёт
через `parseAll`.

Гейт сводится к одному — `decode()` + flavor (§7).

## 2. Четыре формы на входе

| форма | пример | flavor |
|---|---|---|
| одиночный outbound | `{"type":"vless",…}` | `singboxOutbound` (есть) |
| массив outbound'ов | `[{"type":"vless",…},…]` | `singboxArray` (новое) |
| полный конфиг | `{"log":…,"outbounds":[…],"route":…}` | `singboxConfig` (новое) |
| **массив конфигов** | `[{"outbounds":[…],"route":…},…]` | `singboxMulti` (новое) |

Четвёртая — прямой аналог `xrayArray`: подписка, где каждый элемент
самостоятельный конфиг. У Xray это норма схемы (элемент = автономный конфиг со
своим `routing`), у sing-box встречается у провайдеров, генерирующих подписку
пер-узел. Форма отличается от `singboxArray` тем, что элемент — конфиг, а не
outbound: у него нет `type`, но есть `outbounds`.

Первые три сводятся к четвёртой: одиночный outbound = конфиг из одного
outbound'а, массив outbound'ов = конфиг без обёртки, конфиг = массив из одного.
**Ядро парсера одно** — обход массива конфигов; остальное нормализация на входе.

## 3. Паритет с §321: принцип за принципом

| §321 | Xray | sing-box | статус |
|---|---|---|---|
| P1 | элемент → N узлов; `freedom`/`blackhole`/`dns`/`loopback` не узлы | конфиг → N узлов; `direct`/`block`/`dns` не узлы | **паритет** (§3.1) |
| P2 | сортировка элементов по числу payload — приоритет имён | то же | **паритет** (§3.2) |
| P3 | `remarks` достаётся одной сущности: группе или солитёру | роль `remarks` играет тег группы / тег узла | **адаптация** (§3.3) |
| P4 | дедуп по `protocol\|server\|port\|credential` | тот же ключ, от `parseSingboxEntry` | **паритет** (§3.4) |
| P5 | неподдержанный protocol → warning на соседе | неподдержанный `type` → то же | **паритет** (§3.5) |
| P6 | таблица синонимов тегов | то же, плюс она здесь ещё и резолвит `detour` | **паритет** (§3.6) |
| §342 | два прохода: имена / порядок | то же | **паритет** (§3.2) |
| §322 | `routing.balancers` → узел автовыбора | `type: urltest`/`selector` → узел автовыбора | **паритет, проще** (§5) |
| §018 | `sockopt.dialerProxy` → `chained` | `detour` → `chained` | **паритет, шире** (§4) |

### 3.1 P1 — конфиг даёт N узлов

Каждый payload-outbound становится узлом. Служебные — нет:

| sing-box `type` | роль | узлом |
|---|---|---|
| `direct` | прямой выход | нет |
| `block` | блокировка (удалён из ядра ≥1.11, встречается в старых) | нет |
| `dns` | DNS-перехват (там же) | нет |
| `selector`, `urltest` | группа | **не узлом-сервером** — группой (§5) |
| 13 транспортных | payload | **да** |
| неизвестный | — | нет + warning (§3.5) |

Константа `_kSingboxServiceTypes` — **своя**, не переиспользует
`_kXrayServiceProtocols`: наборы совпадают по смыслу, но не по написанию
(`freedom` vs `direct`), и связывать их — ложная экономия, которая сломается при
расхождении схем.

Плюс цели `detour` — приезжают звеном владельца, самостоятельным узлом не
дублируются (§4 P1).

`endpoints[]` (sing-box ≥1.11, там живут WireGuard и MASQUE) обрабатывается
наравне с `outbounds[]`: те же правила, тот же `parseSingboxEntry`. Для
`_payloadCount` (P2) элементы обоих массивов считаются вместе.

### 3.2 P2 + §342 — два прохода

Дословный перенос. Элементы массива сортируются по числу payload-outbound'ов
**по возрастанию** (стабильно, с индексом в компараторе — `List.sort` в Dart
стабилен только до ~32 элементов, §342), парсятся вчерне ради имён и таблицы
синонимов, затем боевой проход идёт **в порядке файла**, выпуская только те
узлы, что закреплены за элементом черновым проходом (`ownedBy`).

Причина та же: элемент-«карточка страны» даёт серверу осмысленное имя, элемент-
пул — техническое. Право назвать достаётся первому увидевшему, поэтому
одиночные идут раньше. А порядок в списке должен остаться авторским.

Для форм 1–3 (§2) массив состоит из одного элемента — сортировка и два прохода
вырождаются, но кода это не касается: ветвления нет.

### 3.3 P3 — имя узла

Здесь схемы расходятся, и это **единственное содержательное расхождение**.

У Xray имя приходит извне outbound'а — из `remarks` элемента; сам outbound несёт
лишь технический `tag`. У sing-box `remarks` нет: имя узла — это его собственный
`tag`, и он, как правило, **уже осмысленный** («🇩🇪 Frankfurt», «hk-01»): провайдер
пишет его для показа в списке.

Поэтому:

| что в элементе | группа | узлы |
|---|---|---|
| N узлов | — | собственный `tag` каждого |
| N узлов + группа | `tag` группы | собственный `tag` каждого |

`remarks`-логика §321 P3 (кому достаётся чистое имя, `solo`, индексные фолбэки)
здесь **не нужна**: драки за имя нет, у каждой сущности имя своё. Это не
упрощение в ущерб — это следствие того, что sing-box-схема уже решает задачу,
которую в Xray решал `remarks`.

Фолбэки остаются на случай, когда провайдер тег не заполнил:

| условие | имя |
|---|---|
| `tag` пуст | `<type>-<server>-<port>` (как `parseSingboxEntry` уже делает) |
| `tag` повторяется в элементе | `<tag> <i+1>` — индекс по исходному порядку (P3-инвариант §321) |

Повтор тега внутри одного конфига невалиден по схеме sing-box, но в массиве
конфигов теги повторяются **между** элементами постоянно (каждый элемент —
автономный конфиг, где `proxy` значит своё). Разводим при коллизии в пределах
элемента; между элементами разведёт дедуп P4 либо `allocateTag` на билде.

### 3.4 P4 — дедуп по идентичности

Ключ тот же: `protocol|server|port|credential`, посимвольно совпадающий с
`nodeIdentityKey` ([node_identity.dart:16](../../../../app/lib/services/node_identity.dart)).

**Считаем от готового `NodeSpec`, а не от сырого JSON.** У Xray пришлось писать
`_xrayIdentity`, дублируя quirk'и конвертеров (vision-udp443 переписывает порт),
и держать инвариант «ключ обязан совпадать посимвольно» комментарием. Здесь
конвертер один и вызывается до дедупа — берём ключ у результата. Инвариант
выполняется по построению, а не по договорённости.

Область действия — **один вызов парсера** = одна подписка. Между подписками
дедуп не работает (разные `tag_prefix`/`detour_policy`).

Транспорт и TLS в ключ не входят — как в §321 P4 (решение владельца 30.07.2026).

Для формы «одиночный конфиг» дедуп по сути no-op: в валидном sing-box-конфиге
теги уникальны, но два разных тега могут указывать на один и тот же сервер, и
тогда дедуп сработает и здесь. Это правильно: у нас узел — это сервер.

### 3.5 P5 — неподдержанный тип не теряется молча

`type`, который мы не умеем, вешает `UnsupportedProtocolWarning` (существующий
класс) на **соседний узел элемента** — по одному на тип, не на каждый outbound.

Та же непокрытая дыра, что в §321 P5: элемент, не давший ни одного узла, исчезнет
молча — носителя warning'а нет. Здесь она компенсируется диалогом импорта (§8),
который показывает счётчики **до** создания узлов, включая строку «N skipped».

Битая форма (мусорный тип поля → `TypeError` внутри конвертера) ловится на
гранулярности **узла**, как в §321: `try/catch` вокруг конвертации одного
outbound'а, протокол уходит в тот же warning как `malformed`. Соседи и остальная
подписка живут.

### 3.6 P6 — таблица синонимов

`tagSynonyms`: тег провайдера → идентичность узла. Копится по всему массиву,
до пропуска дубля (именно у дублей теги и различаются).

У sing-box эта таблица работает **двумя способами**:

1. как в §322 — резолв состава группы, написанного чужими тегами;
2. **дополнительно** — резолв `detour`-ссылок (§4). У Xray `dialerProxy`
   указывает всегда внутрь своего элемента, а `detour` в массиве конфигов может
   указывать на тег, который после дедупа принадлежит узлу из другого элемента.

Время жизни — один разбор подписки, в storage не уходит.

## 4. Detour

В sing-box detour — поле `detour: "<tag>"` на самом outbound'е. У нас —
`NodeSpec.chained` ([node_spec.dart:44](../../../../app/lib/models/node_spec.dart));
при эмите `node_spec_emit.dart:30` разворачивает обратно в `detour: chained.tag`.
Round-trip замкнут, значит импорт detour — это резолв ссылки в вложение.

Шире, чем у Xray: там `dialerProxy` разбирался только для `socks` и `vless`
(`_xrayDetourToSpec`), здесь звеном может стать **любой из 13 типов** —
конвертер общий.

### P1 — цель detour узлом не дублируется

Как §321/§018: outbound, на который ссылаются через `detour`, приезжает звеном
владельца и в список узлов сам не попадает.

**Исключение — цель, на которую ссылаются несколько узлов.** В sing-box один
джамп обслуживает хоть десять outbound'ов; у нас `chained` — вложение, копия
уедет в каждого владельца. Это допустимо (копии идентичны, `allocateTag` разведёт
теги), узлом цель при этом всё равно не становится.

### P2 — цепочки длиннее двух звеньев

`A → B → C` разворачивается рекурсивно: `chained` сам несёт `chained`,
`getEntries` ([node_spec.dart:149](../../../../app/lib/models/node_spec.dart))
обходит цепочку рекурсивно.

**Лимит глубины — 8**, при превышении цепочка обрезается + warning владельцу.
Реальные конфиги — 2–3 звена; неограниченная рекурсия по данным провайдера это
стек.

### P3 — циклы рвём, а не роняем

`A → B → A` невалиден для ядра (`circular outbound dependency`), но в чужом файле
встретиться может.

**Расходимся с §254 намеренно.** §254 судит готовый конфиг пользователя: виновник
— его правка, её надо показать и дать развязать. Здесь кольцо приехало из чужого
файла; пользователь его не создавал и развязать не может — узлов ещё нет. Fatal
означал бы «твой конфиг не возьмём, чини в другом приложении».

Рвём **замыкающее** ребро (ведущее на узел, уже находящийся в текущей цепочке),
владельцу — warning. Дальше узлы обычные, §254 работает как всегда.

### P4 — висячая ссылка

`detour: "nonexistent"` → узел без цепочки + warning. Терять узел из-за битой
ссылки нельзя (§169: отброс негодной части, не целого).

В форме `singboxMulti` «висячая» проверяется **после** таблицы синонимов (§3.6):
тег может принадлежать соседнему элементу.

### P5 — detour на группу

`detour: "auto"`, где `auto` — `urltest`. Типово выразимо (`AutoSelectSpec` —
вариант `NodeSpec`), но семантически у нас не поддержано: `getEntries` развернёт
группу в detour-список, где её членов нет.

Ссылка игнорируется, узел приезжает без цепочки + warning.

## 5. Группы (`urltest` / `selector`)

Наша модель — `AutoSelectSpec` + `AutoSelectParams`
([auto_select.dart](../../../../app/lib/models/auto_select.dart)), эмитится как
`type: urltest`. Здесь **проще, чем в §322**: у Xray группу приходилось
реконструировать из `routing.balancers` + `burstObservatory` + маппинга четырёх
стратегий на два наших режима; sing-box отдаёт готовый `urltest` с теми же
полями.

### 5.1 Параметры

| sing-box `urltest` | наше поле | дефолт при отсутствии |
|---|---|---|
| `url` | `params.url` | `https://cp.cloudflare.com/generate_204` |
| `interval` | `params.interval` | `15m` |
| `tolerance` | `params.tolerance` | 50 |
| `idle_timeout` | `params.idleTimeout` | `30m` |
| `interrupt_exist_connections` | `params.interruptExistConnections` | false |
| `outbounds[]` | `membership` | — (§5.2) |

Дефолты — из наших `AutoSelectParams`, не из апстрима: значения совпадают, а
источник истины должен быть один.

`type: selector` — ручной выбор, своего узла у нас нет. Импортируем как `urltest`
по тому же составу + warning «selector импортирован как автовыбор». Терять
состав, собранный руками, хуже, чем сменить режим отбора. `default`
(предвыбранный член) игнорируем: у `urltest` выбор делают замеры.

### 5.2 Членство — `ExplicitMembers`

`outbounds: ["hk-1","jp-2"]` — список тегов. Берём `ExplicitMembers` (ключи
идентичности), а не `RuleMembers` (regex), как в §322.

Обоснование: §322 имел дело с Xray, где элемент автономен и один сервер физически
вписан в файл многократно — сопоставлять можно было только по тегам, отсюда
regex и scoped-синонимы. Здесь тег внутри конфига ведёт ровно к одному
outbound'у, который мы уже разобрали в узел: идентичность известна **точно**,
гадать regex'ом незачем.

Резолв: тег → outbound → узел → `nodeIdentityKey`. В форме `singboxMulti` — через
таблицу синонимов (§3.6), поэтому пул, написанный на тегах соседнего элемента,
собирается правильно.

`tagSynonyms` у такой группы остаётся заполненной (нужна §302 для ремапа), но
scoped-ветка `resolveAutoSelectMembers`
([server_list_build.dart:187](../../../../app/lib/services/builder/server_list_build.dart))
для `ExplicitMembers` не выполняется — она только в `RuleMembers`.

### 5.3 Вложенные группы

`urltest`, среди членов которого другой `urltest`. `nodeIdentityKey` для группы
возвращает `null` — членом пула она быть не может. Тег выпадает из состава +
warning на внешней группе.

Если состав опустел — группа не импортируется вовсе: пустой `urltest` роняет
старт ядра (`server_list_build.dart:138`).

### 5.4 Имя

`tag` группы → `label` (§243: name=tag). Тег для конфига —
`tagFromLabel(label, 'urltest', 'auto', 0)`, зеркало §322.

## 6. Что не берём из конфига

| ключ | берём | почему |
|---|---|---|
| `outbounds[]`, `endpoints[]` | **да** | это узлы и группы |
| `route` | нет | наша модель генерирует маршрутизацию сама |
| `dns` | нет | у нас §117/§312 со своей моделью |
| `inbounds` | нет | наш inbound — TUN, настраивается приложением |
| `log`, `experimental`, `ntp`, `certificate` | нет | не транспорт |

Игнорирование молчаливое в модели, но **не в UI**: диалог (§8) перечисляет
отброшенное. Пользователь не должен узнать о потере `route`-правил по факту.

## 7. Распознавание формы: один гейт вместо трёх

### 7.1 Flavor

```dart
enum JsonFlavor {
  xrayArray, singboxOutbound, singboxArray, singboxConfig, singboxMulti,
  clashYaml, unknown,
}
```

`_detectFlavor`:

| вход | flavor |
|---|---|
| `List`, `first['outbounds'] is List` **и** элемент не sing-box | `xrayArray` |
| `List`, `first['outbounds'] is List` **и** элемент sing-box | `singboxMulti` |
| `List`, `first['type'] is String` | `singboxArray` |
| `Map` с `type` | `singboxOutbound` |
| `Map` с `outbounds is List` или `endpoints is List` | `singboxConfig` |
| `Map` с `proxies is List` | `clashYaml` |
| прочее | `unknown` |

**Различение Xray и sing-box в массиве конфигов** — обе формы это `List` элементов
с `outbounds`. Признак: элементы Xray несут `protocol`, sing-box — `type`.
Проверяем первый непустой `outbounds[]` первого элемента: `'type' in first` →
sing-box, `'protocol' in first` → Xray. Ни того ни другого → `xrayArray`
(сохраняем текущее поведение: эта ветка существует и работает, менять её
классификацию по неоднозначному входу нельзя).

Порядок проверок для `Map` важен: `type` первым. Одиночный `selector` несёт и
`type`, и `outbounds` — должен остаться `singboxOutbound` (и уехать в §5 как
группа из одного элемента).

### 7.2 Единый гейт

`_isJsonOutbound` и JSON-ветка `analyzeClipboard` удаляются, обе заменяются на
`decode(text)` + flavor. Превью и импорт **не могут** разойтись — читают один
результат.

| flavor | title | subtitle |
|---|---|---|
| `singboxOutbound` | `Outbound JSON` | `<type> — <tag>` |
| `singboxArray` | `Outbound JSON` | `N outbounds (types)` |
| `singboxConfig` | `sing-box config` | `N nodes, M groups` |
| `singboxMulti` | `sing-box subscription` | `N configs, M nodes` |
| `xrayArray` | `Xray config` | `N elements` |

Счётчики — сухим прогоном парсера, не второй эвристикой.

### 7.3 Ветка в `_parseJson`

Три новых case, все в один вход — `parseSingboxConfigs(List<Map>)`:

- `singboxOutbound` → `[{'outbounds': [value]}]`;
- `singboxArray` → `[{'outbounds': value}]`;
- `singboxConfig` → `[value]`;
- `singboxMulti` → `value`.

`singboxOutbound` перестаёт ходить в `parseSingboxEntry` напрямую: единый путь
даёт одиночному outbound'у то же, что остальным (детур, warning'и). Поведение для
него не меняется — массив из одного элемента вырождает P2/P4/P6.

`_addJsonOutbounds` в контроллере **удаляется** — он был обходом отсутствующего
flavor'а. Меняется одно наблюдаемое поведение: массив сейчас создаёт **N записей
подписки** (комментарий «v1 behavior parity»), станет **одной записью с N
узлами**. Так и правильно: вставленный файл — один источник и обновляться должен
целиком. Для одиночного outbound'а разницы нет.

### 7.4 Контейнер: сервер или подписка

Порог — **число узлов**, тот же, что у файлового импорта (§129):

| результат разбора | контейнер |
|---|---|
| 1 узел | `UserServer` (как было) |
| > 1 узла | файловая подписка: `SubscriptionServers(url: 'file:<uuid>')`, `updateIntervalHours: -1` |

Причина не в форме входа, а в устройстве контейнеров. `UserServer` — это «один
сервер»: подпись в списке берётся от протокола первого узла («VLESS server»),
тап открывает экран одного узла, `_fetchEntryByRef` его не обновляет (пункт
«Update» в меню при этом показывается — молчаливый no-op), а операции над
отдельными узлами существуют только у подписки: выключение узла (§283), правила
импорта (§302), список с их состоянием. Конфиг sing-box на десяток узлов с
группой в такой контейнер не помещается — он выглядел бы как один сервер с
враньём в подписи.

Файловая подписка даёт ровно нужное: список узлов, их выключение, правила
импорта, ре-гидрат из `HttpCache` после рестарта (тело — исходный конфиг,
парсится тем же путём). Автообновления у неё нет по построению (`-1`), потому
что источника-URL не существует; при желании пользователь позже впишет URL через
«Edit source…».

Новое поведение здесь не вводится — распространяется существующее: импорт файла
с >1 нодой делает ровно это с 2.15.x.

Папка (`FolderServers`) не создаётся ни на одном из путей импорта: она
появляется только от явного действия пользователя (меню «New folder…», импорт
нескольких файлов, WARP-генератор). §368 этого не меняет.

## 10. Тесты

`test/parser/singbox_config_test.dart` (новый):

**Формы:** одиночный outbound; массив outbound'ов; полный конфиг; массив
конфигов — все четыре дают одинаковые узлы на эквивалентном содержимом.

**P1:** `direct`/`block`/`dns` не становятся узлами; `endpoints` (WireGuard) →
узел; конфиг только из служебных → пусто.

**P2/§342:** массив из элементов разной длины — имя сервера от одиночного
элемента, порядок списка авторский; 40 элементов (за границей стабильности
`List.sort`) — порядок детерминирован.

**P3:** тег пуст → фолбэк `<type>-<server>-<port>`; тег повторяется в элементе →
индексный суффикс.

**P4:** один сервер в двух элементах под разными тегами → один узел; ключ
совпадает с `nodeIdentityKey`.

**P5:** неизвестный `type` → warning на соседе; `outbounds: [42]`,
`streamSettings: "none"`-аналоги → `malformed`-warning, соседи живы.

**P6:** `detour` на тег соседнего элемента резолвится; состав группы на чужих
тегах резолвится.

**Detour:** `A → B` (B не самостоятельный узел, `A.chained == B`); `A → B → C`;
цель с двумя владельцами → копия у каждого, узлом не стала; цикл `A → B → A` →
ребро снято, оба узла живы, warning; висячий → узел без цепочки + warning; на
группу → без цепочки + warning; глубина 9 → обрезано на 8 + warning.

**Группы:** `urltest` из 3 членов → `ExplicitMembers` из 3 ключей; параметры
маппятся; отсутствующие → наши дефолты; `selector` → группа + warning; вложенная
группа → член выпал + warning; все члены выпали → группы нет; одиночный
`selector` как entry → группа, не `unknown`.

**Устойчивость:** `outbounds: "нет"`, `detour: 5`, `outbounds: null`, пустой
объект, глубоко вложенный мусор → не throw, не пусто там, где есть валидные
соседи.

`test/parser/body_decoder_test.dart`: все четыре flavor'а; различение
`xrayArray` vs `singboxMulti`; `selector` как entry → `singboxOutbound`.

**Регресс:** существующие тесты Xray и одиночного outbound'а не меняются — новые
ветки аддитивны.

**E2E:** конфиг → узлы → `buildConfig` → валидный JSON; группа ссылается на
существующие теги; detour-цепочка развёрнута в `detour`-поля.

**Устройство:** импорт реального sing-box-конфига на эмуляторе, старт ядра,
проверка что узлы и группа работают.
