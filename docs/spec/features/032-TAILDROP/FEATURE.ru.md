# Taildrop — файлы, текст и буфер обмена между своими устройствами tailnet

LxBox отправляет и принимает файлы через Taildrop — передачу файлов,
встроенную в Tailscale, — по узлу Tailscale из работающего конфига. Файл
уходит из системного меню «Поделиться» любого приложения или со страницы
устройства на вкладке Network узла; входящие файлы со своих устройств
пользователя попадают во входящие этого узла без шага согласия. Поверх того
же транспорта приложение обменивается буфером и ссылками с десктопным
лаунчером (singbox-launcher): кнопка «📋 Send» в уведомлении VPN
открывает поверх текущего приложения окно «типа чата», которое отправляет на
ПК буфер телефона (или текст, которым поделились или который выделили), а
текст со своего ПК сам ложится в буфер телефона, если узел его принимает.

| Тип | Продуктовая фича |

## Назначение

Пользователь, у которого телефон уже в tailnet через LxBox, хочет перекинуть
фото, документ или ссылку на ноутбук и обратно без мессенджера, облачного
диска и второго VPN-приложения. Официальный клиент Tailscale делает это через
Taildrop; LxBox запускает Tailscale внутри своего туннеля, поэтому должен дать
то же для своего узла. Синхронизация буфера закрывает самый частый случай —
«скопировал здесь, нужно там» — для пары телефон + десктопный лаунчер.

Что происходит сегодня, без этой фичи: ядро из текущего пина уже несёт
Taildrop и, если в админке tailnet Taildrop включён, молча принимает файлы со
своих устройств пользователя в папку `Taildrop` в своём рабочем каталоге. Их
никто не видит: экрана для них нет, готовые файлы лежат там вечно, удаляются
только недокачанные `.partial` старше часа. Фича делает эти входящие
видимыми и управляемыми.

Принципы: **только свои устройства** — Taildrop между машинами одного
владельца, без передачи чужим и расшаренным машинам; **совместимость с
официальными клиентами** — файл или заметка из LxBox на другой стороне
обычный файл Taildrop, а обычный файл Taildrop, присланный в LxBox, здесь
обычный файл; **входящие принадлежат узлу** — у каждого узла Tailscale свои
входящие, и они уходят вместе с узлом; **никакого подглядывания из фона** —
телефон никогда не читает буфер сам, только когда пользователь открыл окно
Send clipboard, и ничего не отправляет без явной отправки.

## Обещания

- **P1. «Поделиться» из любого приложения отправляет на своё устройство в
  сети.** Экран отправки спрашивает узел Tailscale, только если в работающем
  конфиге их несколько, затем пира; в списке пиров только устройства в сети
  того же владельца, что и это устройство. За одну отправку можно передать
  несколько файлов. **Свидетель:** `no witness` (не реализовано);
  запланированная ручная проверка — поделиться двумя фото из галереи,
  ноутбук получает оба. **Мутация:** машина не в сети или расшаренная машина
  в списке пиров.
- **P2. Страница устройства на вкладке Network предлагает «Send file…».**
  Нажатие на устройство открывает его страницу; «Send file…» открывает
  системный выбор файла и отправляет выбранные файлы этому устройству.
  Кнопка видна всегда и активна только у своего устройства в сети, которое
  принимает файлы; иначе неактивна с причиной под ней. **Свидетель:**
  widget-тест вкладки Network (страница устройства, неактивная Send file… с
  причиной), проверка на эмуляторе 2026-11-03 (задача 707, итерация 6).
  **Мутация:** активная кнопка у расшаренной машины или у машины не в сети.
- **P3. Отправка показывает прогресс в уведомлении.** Уведомление называет
  пира и прогресс, пока передача не завершится или не упадёт.
  **Свидетель:** `no witness`; запланированная ручная проверка с большим
  файлом. **Мутация:** экран отправки, который висит до конца передачи без
  уведомления.
- **P4. Файлы со своих устройств принимаются без шага согласия.** Они
  попадают во входящие того узла, через который пришли; пока файл идёт,
  уведомление «receiving from X» предлагает Cancel, по завершении уведомление
  «file from X» предлагает Save и Delete. **Свидетель:** `no witness`;
  запланированная ручная проверка — отправить с ноутбука, на телефоне нет
  запроса. **Мутация:** запрос «принять/отклонить» перед передачей.
- **P5. Входящие — блок на вкладке Network узла.** Он стоит под Devices; у
  каждого файла Save (в Downloads) и Delete. Тап по уведомлению Taildrop
  открывает вкладку Network того узла, на который пришёл файл.
  **Свидетель:** `no witness`; запланированная ручная проверка с двумя узлами
  Tailscale. **Мутация:** тап, открывающий вкладку другого узла.
- **P6. Принятые файлы остаются при узле, пока их не сохранят или не
  удалят.** Несохранённый файл живёт в каталоге Taildrop узла и переживает
  перезапуск приложения и VPN; удаление узла удаляет его входящие.
  **Свидетель:** `no witness`; запланированная ручная проверка.
  **Мутация:** входящие, опустевшие после перезапуска VPN, или файлы,
  оставшиеся после удаления узла.
- **P7. Пока VPN выключен или узел не работает, ничего не движется.**
  Отправка недоступна, приём не идёт. **Свидетель:** `no witness`;
  запланированная ручная проверка — VPN выключен, отправить с ноутбука,
  телефон ничего не получает. **Мутация:** отправка, которая молча встаёт в
  очередь при выключенном VPN.
- **P8. Текст, которым поделились или который выделили, открывает окно Send
  clipboard.** Текст или ссылка из «Поделиться», а также текст, выделенный в
  любом приложении и отправленный пунктом «Send to device» меню выделения,
  открывает окно Send clipboard с этим текстом в поле вместо буфера; уходит
  он служебным файлом (`clipboard`, для одной ссылки — `open_url`), а не
  файлом-заметкой. До задачи 707 (итерация 7) текст из «Поделиться» ехал
  `note-YYYY-MM-DD-HHMM.txt`; заметку теперь делает только Debug API.
  **Свидетель:** `no witness` (запланированная ручная проверка: поделиться
  текстом и выделить текст — окно его показывает). **Мутация:** текст ушёл
  без окна или стал файлом-заметкой.
- **P9. «📋 Send» в уведомлении VPN отправляет буфер на выбранное
  устройство.** Кнопка открывает окно поверх текущего приложения: получатель
  `To: … ▾`, лента переписки с этим устройством, поле с текстом из буфера.
  ➤ отправляет поле командой `clipboard`; «Open on <device>» (только если в
  поле ровно одна ссылка `http(s)`) — командой `open_url`. Отправленное
  встаёт в ленту справа с ✓ или текстом ошибки. Плитки быстрых настроек для
  этого нет (решение владельца 2026-11-03). **Свидетель:** JVM-тесты логики
  окна (служебный файл, «одна ссылка», лента, получатели и порядок отказов —
  задача 707, итерация 7); само окно на устройстве — `no witness`.
  **Мутация:** отправка не тому устройству, что в `To:`.
- **P10. Текст буфера со своего ПК сразу попадает в буфер телефона.**
  Файл буфера поглощается: содержимое кладётся в буфер, файл удаляется и во
  входящих не появляется; из нескольких подряд побеждает последний,
  устаревший отбрасывается. **Свидетель:** `no witness`; запланированная
  ручная проверка с лаунчером. **Мутация:** применённый файл буфера остался
  во входящих.
- **P11. Без явной отправки с телефона ничего не уходит.** Буфер читается в
  поле окна и уходит только по ➤ или «Open on <device>». Клип, который
  Android пометил как чувствительный (пароль), показывается в поле как любой
  другой: перед отправкой видно всё (решение владельца 2026-11-03; до него
  такой клип отклонялся). **Свидетель:** `no witness`; запланированная
  ручная проверка — скопировать из менеджера паролей, открыть окно, до ➤ на
  ПК ничего не приходит. **Мутация:** окно отправляет при открытии.
- **P12. Буфер принимается, только если пользователь включил это у
  узла.** «Accept clipboard and links from my devices» у узла по умолчанию
  выключено и касается только своих устройств (sharee своими не считаются);
  без него команда не выполняется, файл удаляется. Полученный клип никогда не отправляется
  обратно сам. **Свидетель:** `no witness`; запланированная ручная проверка —
  галка снята, отправить с лаунчера, буфер не тронут, во входящих ничего. **Мутация:** буфер телефона перезаписан
  при выключенной настройке.

## Контролируемые параметры

| Ручка | Значения | По умолчанию |
|-------|----------|--------------|
| Узел → «Allow Taildrop» (файлы и служебные команды) | вкл / выкл; выкл — ядро отказывает во входящих и в отправке, узла нет в «Поделиться», нет входящих и «Send file…», команды не обрабатываются; поле узла в конфиге ядра, в бэкапе; нужна опция ядра (запрошена 02.11.2026) | выключено (решение владельца 2026-11-02) |
| Экран отправки → узел | работающий узел Tailscale; спрашивается, только если их несколько | единственный |
| Экран отправки → устройство | своё устройство в сети в tailnet этого узла | — |
| Вкладка Network → страница устройства → «Send file…» | системный выбор файла, один или несколько файлов; неактивна с причиной, если устройство не подходит | — |
| Вкладка Network → входящие → Save / Delete | на файл | — |
| Уведомление → Cancel (приём идёт), Save / Delete (принято) | на передачу | — |
| Уведомление VPN → «📋 Send» | есть, пока VPN поднят и в работающем конфиге есть узел Tailscale с Allow Taildrop; открывает окно Send clipboard | — |
| Окно Send clipboard → `To: … ▾` | свои устройства, принимающие файлы, со всех работающих узлов Tailscale с Allow Taildrop (при нескольких узлах — с именем узла); выбор запоминается | запомненное, иначе первое |
| Окно Send clipboard → ⋮ → Clear | чистит ленту с выбранным устройством | — |
| Меню выделения текста → «Send to device» | открывает окно Send clipboard с выделенным текстом; есть при том же условии, что кнопка уведомления | — |
| Вкладка Network → Taildrop → «Accept clipboard and links from my devices» | один переключатель у узла-получателя; только свои устройства; поле записи узла, в бэкапе | выключено |

Ключи конфига ядра: каталог приёма — `taildrop_directory` endpoint'а; по
умолчанию это `Taildrop` относительно рабочего каталога ядра (не
`state_directory` узла), поэтому он общий для всех узлов Tailscale. Сборка
подставляет каждому узлу `<state_directory>/taildrop` — так у узла свои
входящие, и они удаляются вместе с его каталогом состояния; явный
`taildrop_directory` в теле узла не трогается. Сборка
ядра: ядро из текущего пина уже несёт Taildrop, пересборка не нужна. Служебные
файлы (буфер, ссылки): формат имени, лимит размера, TTL и версия формата —
константы контракта с лаунчером (`docs/contract` и реестр); предложенные
значения — `lx-<время>-<метка>.json`, не больше 64 KiB, TTL 2 минуты, JSON в
UTF-8 без BOM, `"lx": 1`.

## Входы / Выходы

**Входы:** системный intent «Поделиться» (файлы, текст, ссылки) из любого
приложения; меню выделения текста; системный выбор файла; нажатия на вкладке
Network, на странице устройства, в уведомлениях и в окне Send clipboard;
буфер обмена в момент, когда это окно получает фокус; входящие файлы Taildrop со
своих устройств; состояние tailnet от ядра (какие пиры в сети и чьи);
состояние VPN и узла.

**Выходы:** передачи Taildrop пиру; уведомления о прогрессе, приёме и
результате; файлы во входящих узла; файлы, сохранённые в Downloads; буфер
телефона, заполненный из входящего файла буфера; служебные файлы выбранному
устройству; лента окна с ✓ или текстом ошибки.

## Data flow

```
Поделиться (файлы) → экран отправки → узел (если работают несколько) → своё устройство в сети → отправка Taildrop → уведомление о прогрессе
Поделиться (текст) → окно Send clipboard с этим текстом в поле
Меню выделения     → «Send to device» → окно Send clipboard с выделенным текстом
Вкладка Network    → нажатие на устройство → страница устройства «Send file…» → системный выбор → отправка Taildrop → уведомление о прогрессе
Входящие           → ядро принимает со своего устройства → префикс буфера и узел принимает команды?
                     да  → свежий, валидный, последний в серии? → содержимое → буфер телефона · файл удаляется в любом случае
                     нет → входящие узла (каталог Taildrop узла) → «receiving from X» (Cancel) → «file from X» (Save, Delete)
Входящие (блок)    → вкладка Network под Devices → Save → Downloads · Delete → удалён
Уведомление        → «📋 Send» → окно поверх текущего приложения по фокусу читает буфер в поле
                     → нет VPN / нет Allow Taildrop / нет получателей / получатель не в сети / слишком большой? причина над полем
                     : ➤ → команда clipboard · «Open on <device>» → open_url → получатель → ✓ или ошибка в ленте
Выполненный приём  → clipboard / open_url с этого устройства → лента окна слева
Узел удалён        → его каталог Taildrop удаляется вместе с состоянием
```

## Правила и гарантии

- Входящие — у каждого узла свои. Два узла Tailscale в конфиге — два
  устройства в (возможно, разных) tailnet, у каждого свои входящие;
  уведомление и цель тапа по нему называют узел, на который пришёл файл.
- Списки пиров (экран отправки, «Send file…», получатели окна) содержат
  только устройства в сети того же владельца, что и это устройство. Расшаренные
  машины и устройства других пользователей tailnet не появляются никогда:
  Taildrop с ними не работает.
- Приём со своих устройств идёт без шага согласия, как в Tailscale.
  Пришедшее лежит во входящих, пока пользователь его не сохранит или не
  удалит, либо пока не удалят узел.
- Разобранный служебный файл во входящих не показывается никогда: его
  команды выполняются, если узел-получатель принимает их от своих устройств
  («Accept clipboard and links from my devices»), или отбрасываются как
  устаревшие, непринятые или
  перекрытые следующими, а файл удаляется. Неразобранный остаётся обычным
  файлом во входящих. Полученный клип никогда не отправляется обратно.
- Буфер читается только когда окно Send clipboard получает фокус.
  Автоматической отправки при копировании нет; без ➤ или «Open on <device>»
  ничего не уходит, после отправки окно не закрывается, как чат.
- Клип, помеченный как чувствительный, показывается в поле как любой другой
  и уходит только по ➤ (решение владельца 2026-11-03).
- Лента окна живёт только в памяти, пока работает VPN: остановка VPN или
  гибель процесса её стирает; не больше 50 сообщений на устройство, нажатие
  на сообщение копирует его текст.
- «📋 Send», «Send to device» и LxBox в «Поделиться» есть, только
  пока VPN поднят и в работающем конфиге есть узел Tailscale с Allow
  Taildrop; они следуют старту, остановке VPN и перезагрузке конфига, а после
  перезапуска процесса выключены до следующего подъёма VPN.
- Имена файлов, содержимое файлов, текст буфера и имена устройств не попадают
  в лог приложения, дамп для поддержки и Debug API (то же правило, что в
  [030-TAILSCALE](../030-TAILSCALE/FEATURE.ru.md#правила-и-гарантии)).
- Входящие не входят в бэкап, как и состояние узла. Запомненный получатель
  окна тоже не входит: это кэш Kotlin на этом телефоне. Настройки узла
  «Accept clipboard and links from my devices» и «Save received files to
  Downloads» — поля записи узла, едут в бэкапе.

## Границы

- Только свои устройства tailnet. Расшаренные машины и устройства других
  пользователей недоступны самому Taildrop.
- Только пока VPN поднят и узел Tailscale работает. При выключенном VPN
  ничего не принимается — в отличие от официального клиента, который держит
  свой VPN постоянно; файл, отправленный на телефон в это время, падает на
  стороне отправителя.
- Taildrop должен быть включён в админке tailnet: у этого узла должна быть
  возможность file sharing, а отправитель — своё нетегированное устройство
  или устройство с правом file-sharing-send. Без этого фича не работает, и
  интерфейс показывает причину, а не молча ничего не делает.
- Taildrop у самого Tailscale — в статусе alpha.
- С официальными клиентами Tailscale синхронизации буфера нет: файл буфера
  они получают как обычный файл с префиксом в имени. Буфер — только в паре с
  лаунчером.
- Телефон не читает буфер из фона (Android 10 и новее это запрещает); окно
  Send clipboard читает его, когда оно на переднем плане. Плитки быстрых
  настроек для буфера нет. Запись в
  буфер из фона разрешена, поэтому направлению ПК → телефон окно не нужно.
- Это не клон KDE Connect: зеркалирование уведомлений, SMS, пульт,
  управление медиа и подобное — вне фичи.
- Tailscale SSH — см. [030-TAILSCALE](../030-TAILSCALE/FEATURE.ru.md#границы)
  (решено там).

## Особенности сопровождения

- **Taildrop в ядре уже есть.** У sing-box своя реализация Taildrop
  (peerapi-хендлер `/v0/put/`), и тег сборки `ts_omit_taildrop` её не
  вырезает — для неё он no-op (замер 2026-11-02: размер `.so` и `classes.jar`
  побайтно те же с тегом и без). Текущий пин пересборки не требует. Ядро
  десктопного лаунчера тоже с Taildrop; в ядре с обеих сторон делать нечего.
  Сессия ядра проверила это по коду, на устройстве не проверялось.
- **Приём автоматический уже сегодня** (см. «Назначение»): файлы ложатся в
  `taildrop_directory` (по умолчанию `Taildrop` в рабочем каталоге ядра), вне
  всякого интерфейса; `.partial` старше часа удаляются, готовые остаются.
  Ещё ядро само шлёт платформенное уведомление «receiving…»; реализации
  придётся увязать с ним свои уведомления.
- **Отправка** принимает имя файла и размер (отрицательный размер —
  неизвестен), а содержимое приложение стримит порциями, поэтому присланный
  источник `content://` читается напрямую, без временной копии. Отправке нужен
  поднятый сервис с этим узлом — то же, что «только при включённом VPN».
- **Файлы, принятые до фичи** в общую папку ядра по умолчанию, один раз
  переносятся во входящие первого по порядку конфига узла Tailscale; после
  переноса общая папка удаляется. **Открыто:** работает ли приём в
  userspace-стеке на реальном устройстве (по коду — да).
- Сторона буфера у лаунчера — его собственная спека.
- **Протокол буфера принадлежит контракту с лаунчером.** Префикс, лимит
  размера, TTL и кодировка — константы в `docs/contract` и реестре, версию
  контракта заводит лаунчер; числа в этой спеке — текущие значения, при
  расхождении прав контракт. Источник клипа — отправитель Taildrop, в имени
  файла маркера нет.
- **API ядра для приложения** (есть в пине lx.29): `subscribeTaildropInbox`,
  `sendTaildropFiles` (+ `TaildropSendSession.writeChunk` / `finishFile`),
  `downloadTaildropFile`, `deleteTaildropFile`, `cancelTaildropReceiving`,
  `markTaildropInboxRead`; у статуса узла `canShareFiles`, у пира
  `canReceiveFiles` (ядро уже учло право на отправку и своё/чужое). Ядро само
  шлёт уведомления «receiving…» и «received…» с адресом
  `sing-box:taildrop?endpoint=<tag>`.
- Ничего из этого не запускалось на устройстве; страница устройства и
  итерации 1–5 прошли на эмуляторе.
