# FEATURES — фичи L×Box

Каталог фич по образцу Spec Kit ядра
([sing-box-lx/SPECS/FEATURES](https://github.com/Leadaxe/sing-box-lx/tree/lx/SPECS/FEATURES)).

Фича описывает **текущее состояние** предметной области целиком, как
**чёрный ящик**: зачем существует, что обещает пользователю, какие принципы
защищает, чем управляется, что принимает и что отдаёт, где границы. Реализация
(файлы, классы, control flow, платформа) живёт в задачах —
[`../tasks/`](../tasks/README.md); старые спеки фич — задачи с индексом `F`
([`../tasks/F-INDEX.md`](../tasks/F-INDEX.md)).

**Критерий переносимости:** если приложение переписать с нуля на другой
платформе, папка `features/` переносится целиком и не меняется, пока не
изменилось поведение для пользователя.

## Три уровня

```
Фича      features/NNN-NAME/FEATURE.md          зачем, обещания, параметры, границы, список функций
Функция   features/NNN-NAME/FUNCTIONS/<name>.md одна способность фичи: что делает, свои параметры,
                                                инварианты, таблица ревизий
Ревизия   tasks/NNN-title.md | tasks/NNNF-name/  рабочий цикл, изменивший функцию (реализация)
```

Функция — то, что пользователь или соседняя подсистема может назвать отдельно
(«импорт OpenVPN-профиля», «автообновление подписки»), а не слой кода и не экран.
Одна задача может числиться ревизией нескольких функций.

## Шаблон фичи — `NNN-NAME/FEATURE.md`

Шапка-таблица: Тип (продуктовая/процессная), Поглотила (`§NNNF …`), Состояние.
Далее разделы в этом порядке:

1. **Назначение** — что даёт пользователю, зачем существует, какой принцип защищает.
2. **Обещания** — `P1..Pn`, каждое: формулировка наблюдаемого поведения,
   **Свидетель** (тест, названный по поведению, или воспроизводимая ручная проверка),
   **Мутация** (что должно сломать обещание). Обещание без свидетеля помечается
   `без свидетеля` — это кандидат на ревизию, не украшение.
3. **Контролируемые параметры** — все ручки: настройки пользователя (значения,
   дефолт), ключи конфига ядра, которые фича отдаёт (это контракт с ядром).
4. **Входы / Выходы** — что ящик принимает (ссылки, файлы, события ОС, ответы ядра)
   и что отдаёт (конфиг, состояние, уведомления, поведение).
5. **Data flow** — путь данных через стадии, от входа до выхода. Стадии, не файлы.
6. **Правила и гарантии** — инварианты, взаимоисключения, что и когда валидируется.
7. **Границы** — что фича намеренно не делает; что зависит от возможностей ОС.
8. **Функции** — таблица: функция · что делает · какие обещания держит · файл в `FUNCTIONS/`.
9. **Особенности сопровождения** — грабли поведения, которые стоят дорого.

⚠️ **Имён файлов, классов, функций кода, виджетов и платформенных механизмов нет.**
Проверка: реализацию переписали с нуля — `FEATURE.md` не изменился.
Остаются: настройки и их значения, ключи конфига ядра, имена RPC ядра, форматы
ссылок и файлов (это контракты с пользователем и ядром).

## Шаблон функции — `NNN-NAME/FUNCTIONS/<name>.md`

Шапка: Фича, Обещания (какие `P` держит), Состояние. Разделы:

1. **Что делает** — одна способность, в терминах пользователя.
2. **Параметры** — только те ручки, что относятся к этой функции.
3. **Входы / Выходы**.
4. **Правила и инварианты** — включая обработку ошибок: что видит пользователь.
5. **Границы**.
6. **Ревизии** — таблица `# · Ревизия · Статус · Суть`, ссылки на `../../tasks/NNN…`.
   Ревизия — история требований, не реализации: суть в одну строку, без файлов.

## Соглашения

- **Папка фичи — `NNN-NAME`**, UPPER_SNAKE, сквозной номер с `001` — стабильный
  якорь, после присвоения не меняется. Новая фича получает следующий свободный номер.
- **Одна фича — один `FEATURE.md`**, актуальное состояние сверху, без хронологии.
  Хронология — в ревизиях.
- **Фича пишется по коду и тестам**, старые `F`-спеки и задачи — источник ревизий и
  подсказок, а не истина. Расхождение кода с ожиданием — новая задача, не сглаживание.
- **Ссылаться на фичу или функцию, а не на задачу.** Ссылка на задачу — когда нужен
  конкретный разбор.
- **Меняется поведение — правится фича.** `FEATURE.md` и `FUNCTIONS/` — живой дизайн,
  а не архив: задача, меняющая поведение, обновляет их и добавляет себя в ревизии.
