# Раздельное туннелирование — какие Android-приложения идут через VPN

LxBox позволяет выбрать, какие Android-приложения идут через VPN-туннель, а
какие — мимо него, в режимах Off, Allow-list и Deny-list. Android применяет
список при создании туннеля, а конфиг ядра sing-box хранит его как
`include_package` или `exclude_package`.

| Поле | Значение |
|------|----------|
| Фича | 011-SPLIT_TUNNELING |
| Тип | Продуктовая фича |
| Поглотила | `§046F` |
| Состояние | ✅ написана по коду, 2026-09-28 |

## Назначение

Пользователь решает на уровне ОС, какие приложения вообще попадают в туннель:
банк и игры — мимо VPN напрямую через Wi-Fi/мобильную сеть, или наоборот —
«только Telegram через VPN». Это граница **до** ядра: пакеты приложения,
оставленного вне туннеля, в ядро не приходят, правила маршрутизации их не
видят. Настройка живёт на вкладке «Tunnel apps» экрана маршрутизации.

Фича защищает два принципа:

- **Выбор пользователя виден в конфиге.** Список приложений пишется в
  сохранённый конфиг ядра явно и диагностируется по нему; автоматические
  докрутки приложения (своё приложение в allow-режиме) в сохранённый конфиг
  не попадают.
- **Метка должна быть правдой.** «Приложение удалено» говорится только когда
  ОС это подтвердила; сбой проверки не превращается в ложный диагноз.

## Обещания

- **P1. Off не трогает туннель.** В режиме Off в туннельный вход ничего не
  пишется, даже если список не пуст. Свидетель: юниты «mode=off → no changes»,
  «mode=off + non-empty packages → no changes (mode wins)». Мутация: запись
  списка без проверки режима.
- **P2. Режим однозначно задаёт поле ядра.** Allow-list → `include_package` =
  список; Deny-list → `exclude_package` = список; одновременно двух полей нет.
  Свидетель: юниты «mode=allow + 2 pkgs → include_package», «mode=deny + 1 pkg
  → exclude_package». Мутация: поля перепутаны.
- **P3. Пустой список ничего не ломает.** Allow или Deny с пустым списком
  конфиг не меняют — весь трафик идёт в туннель, а не «никто». Свидетель: юнит
  «mode=allow + empty packages → no changes». Мутация: пустой `include_package`.
- **P4. Без туннеля — тихо ничего.** Нет туннельного входа (режим Proxy) —
  список не применяется и ошибки нет; при нескольких туннельных входах
  трогается только первый; в VPN+Proxy список уходит в туннель, а не в порт.
  Свидетель: юниты «no tun-inbound → silent no-op», «inbounds key missing →
  no throw», «multiple tun inbounds — only first», «mode=vpn_proxy → оба
  inbound (tun первый)». Мутация: поиск входа по тегу вместо типа.
- **P5. Список переживает смену режима и перезапуск приложения.** Переключение
  Off/Allow/Deny список не стирает; «Clear all» режим не меняет; настройка
  переживает выход из экрана, перезапуск и резервную копию. Свидетель: юниты
  «staged tun_apps + flushToDisk → round-trip с диска», «round-trip:
  export → reset → import → bytewise equal»; сохранность при смене режима — `без свидетеля`.
  Мутация: смена режима обнуляет список.
- **P6. Правка списка доводится до ядра.** Любое изменение режима или списка
  помечает конфиг «нужна пересборка»; при поднятом туннеле — плашка или
  автоперезапуск по 003. Свидетель: юнит «config-значимые сейверы поднимают
  configDirty». Мутация: сохранение без пометки (§075: рестарт на старом
  конфиге).
- **P7. Своё приложение не выпадает из allow-режима.** В Allow-list приложение
  само дописывает себя в канал туннеля при каждом поднятии, не трогая
  сохранённый конфиг; в Deny и Off — не дописывает (иначе ОС отвергла бы
  туннель со смешанным списком). Свидетель: девайс-смок §124 (Android 15);
  юниты зеркала «свой пакет дописан в конец include_package», «deny → свой
  пакет НЕ дописан». Мутация: самодописывание и в Deny.
- **P8. Выбор в пикере не теряется назад-жестом.** Системный «назад» возвращает
  выбор так же, как стрелка. Свидетель: виджет «системный back возвращает
  текущий выбор (§108)». Мутация: возврат без результата.
- **P9. Прокрутка не снимает галочки.** Выбор меняется только тапом по
  галочке, не по строке. Свидетель: виджеты «тап по названию строки выбор не
  меняет», «тап по чекбоксу переключает». Мутация: переключение по строке.
- **P10. «Удалено» — только подтверждённое.** Метка «uninstalled» появляется
  лишь когда ОС ответила «пакета нет»; таймаут или сбой — повтор, без метки.
  Свидетель: юниты «НЕ помечает not-found и ретраится до успеха», «после
  исчерпания ретраев остаётся unknown». Мутация: сбой кэшируется как «нет».
- **P11. Отсутствующий пакет не мешает старту.** Пакет из списка, которого нет
  на устройстве, пропускается, туннель поднимается. `без свидетеля`.

## Контролируемые параметры

| Настройка | Значения | Дефолт | Когда действует |
|-----------|----------|--------|-----------------|
| Режим (Tunnel apps → Mode) | `off` / `allow` (Allow-list) / `deny` (Deny-list) | `off` | следующее поднятие туннеля |
| Список приложений | идентификаторы пакетов | пусто | следующее поднятие туннеля |

Хранится парой `{mode, packages}`; список нормализуется при записи (без пустых,
без дублей, по алфавиту). Входит в бэкап. Debug API: `GET|PUT
/settings/tun_apps`, тело `{"mode":"off|allow|deny","packages":[…]}`; неверный
режим или имя пакета — 400; ответ несёт `rebuild_needed: true`.

Ключи конфига ядра (контракт):

| Ключ | Когда |
|------|-------|
| `inbounds[type=tun]`.`include_package` | режим `allow`, список не пуст, первый туннельный вход |
| `inbounds[type=tun]`.`exclude_package` | режим `deny`, список не пуст, первый туннельный вход |

Самодописывание своего пакета идёт через параметры запуска ядра
(`includePackage` в override-опциях), а не через конфиг.

## Входы / Выходы

**Входы:** выбор пользователя (режим, пикер, удаление строки, «Clear all»),
Debug API, восстановление бэкапа; список установленных приложений и ответы ОС
«есть / нет пакета».

**Выходы:** поле `include_package` / `exclude_package` в конфиге; признак
«нужна пересборка»; на поднятии туннеля — разрешённые/запрещённые приложения
в системном VPN; в режиме подробного журнала ядра — одна строка
`per-app: mode=… allow_bypass=… applied=N […] not_installed=M […]`.

## Data flow

```
выбор пользователя / Debug API / бэкап
  → нормализация списка → сохранение {mode, packages} → «нужна пересборка»
  → сборка конфига: последний шаг правит первый tun-вход (include | exclude)
  → поднятие туннеля: ядро + свой пакет (только allow) → ОС строит туннель
    с разрешёнными/запрещёнными приложениями; отсутствующие — пропуск
```

## Правила и гарантии

- Режим Off — поведение ОС по умолчанию: все приложения в туннеле.
- Allow и Deny взаимоисключающи в одном туннеле: смешанный список ОС отвергает.
- Список применяется ОС только при создании туннеля; живой туннель его не
  меняет — нужно новое поднятие (старт или перезапуск ядра).
- Состояние «установлено» кэшируется на сессию; сбой проверки — до трёх
  повторов (2, 5, 15 с), затем «неизвестно» и новая попытка при следующем
  заходе на экран.
- Правило по пакету внутри ядра ([004-ROUTING](../004-ROUTING/FEATURE.ru.md))
  видит только трафик, уже попавший в туннель; приложение вне туннеля такому
  правилу не подчиняется. Вкладка говорит это в подсказке и справке.

## Границы

- Режим Proxy: split-tunneling не действует — туннеля нет, а в локальный порт
  приложение идёт по собственной настройке прокси. Вкладка в этом режиме об
  этом не предупреждает.
- «Allow VPN bypass» — другой механизм (приложение само решает выйти мимо
  туннеля), владелец — [010-VPN_SERVICE](../010-VPN_SERVICE/FEATURE.ru.md),
  функция «Режимы работы».
- Маршрутизация по пакету внутри ядра — 004-ROUTING; трафик по приложениям —
  012-LIVE_STATE; плашка и автоперезапуск — 003-CONFIG_BUILD.
- Split по доменам/IP на уровне ОС — не делается (это правила ядра).
- Зависит от возможностей ОС: сам механизм разрешённых/запрещённых приложений
  VPN, видимость списка установленных приложений, реакция на неустановленный
  пакет (на части версий ОС он принимается молча), момент применения — только
  при создании туннеля.

## Связанные фичи

- [003-CONFIG_BUILD](../003-CONFIG_BUILD/FEATURE.ru.md) — пометка «нужна
  пересборка», плашка перезапуска и автоперезапуск, доводящие правку списка до
  живого туннеля.
- [004-ROUTING](../004-ROUTING/FEATURE.ru.md) — правила по пакету внутри ядра
  видят только трафик, уже попавший в туннель; тот же пикер служит условию «по
  приложению».
- [010-VPN_SERVICE](../010-VPN_SERVICE/FEATURE.ru.md) — владеет туннелем, при
  создании которого применяется список, режимами VPN/Proxy (в Proxy списка
  нет) и «Allow VPN bypass».
- [012-LIVE_STATE](../012-LIVE_STATE/FEATURE.ru.md) — трафик по приложениям.
- [027-DEBUG_API](../027-DEBUG_API/FEATURE.ru.md) — Debug API `GET|PUT
  /settings/tun_apps`, читающий и пишущий режим и список.

## Особенности сопровождения

- Шаг, пишущий список, обязан быть **последним** правщиком туннельного входа:
  любой поздний шаг, пересоздающий вход, молча сотрёт выбор пользователя.
- Приложение узнаёт allow-режим по наличию `include_package` у первого
  туннельного входа. Меняешь форму записи (другое поле, другой вход) —
  самодописывание и сравнение «конфиг ядра устарел» разъедутся.
- Сравнение с работающим ядром повторяет самодописывание как append без
  сортировки и дедупликации; нормализация на этой стороне даст вечную плашку.
- Правка списка без пересборки конфига = перезапуск на старом конфиге
  (§075) — выбор «не работает», хотя в настройках он есть.
