## 1. Зачем

Сегодня узел добавляется мастером и правится в настройках с фиксированным набором
полей. Знание «какие поля есть у протокола и что с ними можно» живёт в реестре, а
экраны его не читают. Каждый новый протокол или правило требует правки экранов.

Идея: экран не знает протоколов. Он берёт схему тела из реестра и строит форму по
ней. Поменялся реестр — поменялась форма. Проверка ввода — тот же санитайзер, что
судит разбор и сборку, поэтому редактор не может разойтись с ними.

## 2. Что даёт схема (уже есть, после §553 без обёрток)

- порядок и тип полей → набор и вид виджетов, вложенные секции для объектов;
- `required` → обязательность;
- `values`, `format`, `default` → списки допустимых значений, проверка на лету, подсказка;
- `desc_en` / `desc_ru` → подпись и помощь на обоих языках;
- варианты транспорта по типу → форма меняется от выбора;
- связи (`conflicts`, `requires`, `when`) → скрытие или блокировка полей, которые в текущем сочетании не имеют смысла;
- `secret` → скрытый ввод;
- пометка происхождения из общей суб-схемы → группировка полей («Соединение», «TLS»).

## 3. Контур решения (без деталей)

1. Форма читает тело узла в формате sing-box и пишет обратно такое же тело: один и тот же
   редактор для узла из ссылки, из JSON и созданного вручную.
2. Проверка ввода — прогон тела через санитайзер реестра. Он возвращает коды с путями до
   поля; форма подсвечивает поле и показывает текст кода (реестр их уже отдаёт, экран
   уведомлений узла ими пользуется). Второй валидации в UI нет.
3. Дословный исходник `rawSource` после правки теряется, узел считается отредактированным —
   как сейчас при правке в настройках.
4. Правила версии ядра (`min_when` и т.п.) форма не отражает: их судит санитайзер при
   сохранении.

## 3a. Фаза 1 — JSON-редактор, который знает схему (принято 25.09.2026)

Решение владельца: первой делается не форма, а текстовый JSON-редактор тела узла,
осведомлённый о схеме реестра. Это доведённый до ума второй вариант из §4 (тот, что «в
разы дешевле»). Форма по схеме (§3) откладывается до опыта с фазой 1. Фундамент уже
есть: `re_editor` через `LxCodeEditor` (мастер, экран конфига) и развёрнутая после §553
`FieldSchema`.

**Единственный новый примитив** — разбор JSON с позициями: карта «офсет в тексте →
путь до поля (`tls.server_name`) → `FieldSchema`». `jsonDecode` позиции теряет,
нужен свой небольшой разбор (ожидаемо ~200 строк Dart, только JSON без комментариев).
Все остальные возможности — потребители этой карты, отдельной логики про протоколы
у них нет.

Потребители карты, в порядке пользы:

1. **Подчёркивание ошибок.** Тело прогоняется через санитайзер реестра, коды с путями
   ложатся на строки редактора. Второй валидации нет (как в §3 п. 2).
2. **Нижний лист-попап по ключу или значению под курсором.** Выезжает снизу, с
   прокруткой и схлопыванием (владелец: для редактора это самый удобный инструмент).
   Содержимое: `desc_ru`/`desc_en`, тип, `required`, `default`, допустимые `values`,
   `format`; для поля с кодом санитайзера — текст кода. Лист не занимает клавиатуру и
   не закрывает строку, с которой вызван.
3. **Автодополнение.** Курсор внутри объекта → поля схемы этого объекта минус уже
   введённые; курсор в значении поля с `values` → эти значения; дискриминатор
   транспорта → варианты. Через `CodeAutocomplete` `re_editor` с нашим списком под
   нашу позицию.
4. **Подсветка синтаксиса JSON** — уже есть у `re_editor`, работы не требует.

Что фаза 1 сознательно не делает:

- не прячет и не блокирует поля по `conflicts`/`requires`/`when` — это только форма;
  в редакторе такие сочетания ловит санитайзер и показывает пункт 1;
- не маскирует `secret`: в середине строки маскировка мешает правке; вместо этого
  предупреждение при показе экрана;
- комментарии `//` в самом JSON не поддерживаются: тело уходит в ядро как sing-box
  JSON, а `rawSource` после правки всё равно теряется (§3 п. 3). «Комментарии» к полям
  — это лист из пункта 2, в текст они не пишутся.

Что фаза 1 закрывает из открытых вопросов §4: чужие ключи показываются как есть
(санитайзер судит их, как и остальные); узел любого протокола правится без правки
экрана; узел из подписки правится как есть, с тем же предупреждением о перетирании,
что и сейчас. Открытыми остаются место в навигации и показ молча снятых полей.

## 4. Открытые вопросы (решить до плана)

- ~~Полная форма по схеме или «несколько главных полей + сырой JSON с проверкой
  санитайзером»?~~ Решено 25.09.2026: фаза 1 — JSON-редактор со схемой (§3a), форма
  отложена.
- Как показывать поля, снятые санитайзером молча (`default_when`, нормализация), чтобы
  пользователь не думал, что ввод пропал.
- Место в навигации: замена настроек узла или отдельный «расширенный» режим.
- ~~Что делать с полями, которых нет в схеме (чужие ключи)~~ — в фазе 1 показываются
  как есть (§3a).
- ~~Нужна ли форма для узлов из подписки~~ — в фазе 1 узел правится как есть, с
  предупреждением о перетирании (§3a). Для формы (§3) вопрос остаётся.

## 5. Не входит

Изменения реестра, парсера, сборки. Новых примитивов схемы не требуется: всё, что нужно
форме и редактору, уже есть в поле схемы. Разбор JSON с позициями (§3a) — примитив
редактора, не реестра.
