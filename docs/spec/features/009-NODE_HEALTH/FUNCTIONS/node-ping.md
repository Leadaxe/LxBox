# Пинг узлов

| Поле | Значение |
|------|----------|
| Фича | [009-NODE_HEALTH](../FEATURE.md) |
| Обещания | P1, P2, P3, P4, P6 |
| Состояние | ✅ написана по коду, 2026-09-28 |

## Что делает

Меряет задержку узлов через работающее ядро: одного — пунктом «Ping» в меню
узла, всех видимых — кнопкой пинга на главном экране, автоматически — через
5 с после подключения. Результат виден справа в строке узла числом `NNMS` или
`ERR`, окрашенным по шкале.

## Параметры

| Параметр | Значение |
|----------|----------|
| URL и таймаут | из [настроек пинга](ping-settings.md), по текущему Направлению |
| Автопинг после подключения | вкл (дефолт) / выкл; задержка 5 с |
| Параллельность массового пинга | до 10 замеров одновременно |
| Шкала цвета в списке | < 200 мс зелёный, < 500 мс оранжевый, иначе и `ERR` — красный |

## Входы / Выходы

**Входы:** жест (пункт меню, тап по кнопке, долгий тап — настройки);
переход туннеля в «подключено»; ответ `urlTestOutbound` ядра — задержка или
текст ошибки (провал определяется только непустой ошибкой, задержка 0 мс —
успех).

**Выходы:** замер в карте текущего Направления; `PING…` на время замера;
строка ошибки вида `<узел> → <хост> — <причина>` в журнале и баннере для
одиночного провала; по завершении массового прогона — пересортировка списка
один раз и групповой тест всех URLTest-групп
([urltest-group](urltest-group.md)); пересчёт «корней беды» для detour.

## Правила и инварианты

- **Только при поднятом туннеле.** Кнопка неактивна без туннеля, в занятом
  состоянии, при пустом списке и на псевдо-Направлении NETWORKS.
- **Что не пингуется.** Узел `block` исключается из одиночного и массового
  пинга. Узел с выключенным вручную endpoint'ом показывает `—` нейтральным
  цветом: его провал — не сбой.
- **Порядок — как на экране.** Массовый пинг идёт по отображаемому списку с
  учётом фильтра, сортировки и закреплённых элементов; служебные выходы
  (direct и т.п.) тоже в нём.
- **Снимок на старте.** URL, таймаут и Направление-получатель фиксируются в
  начале прогона (и одиночного замера): переключение Направления посреди
  прогона не уводит результаты в чужую карту.
- **Изоляция по Направлениям.** Массовый пинг очищает замеры только своих
  узлов в своём Направлении, их место на время прогона занимает `PING…`.
  Узел без своего замера показывает последний известный из другого
  Направления с префиксом `~` и приглушённым цветом. Замеры вне Направления
  живут в отдельной карте.
- **Отмена.** Повторный тап во время прогона — стоп: результаты перестают
  применяться сразу, `PING…` снимаются у всех, а уже ушедшие в ядро замеры
  обрываются разрывом отдельного канала пинга (статус и статистика не
  затрагиваются). Групповые тесты, уже запущенные в ядре, доигрывают; новые
  не запускаются.
- **Жизненный цикл.** Остановка/смерть туннеля и отзыв VPN-слота гасят
  массовый пинг и автопинг; сворачивание приложения гасит только автопинг —
  начатый массовый пинг доживает в фоне.
- **Одиночный провал выбранного.** Если провалился узел, который выбран
  какой-то URLTest-группой, для этой группы сразу запускается групповой тест
  с переселектом. Для прочих узлов — ничего.
- **Отрисовка батчами.** Результаты массового прогона применяются пачками
  раз в ~120 мс, чтобы список из сотен узлов не перерисовывался на каждый.
- Замеры живут в памяти и между запусками приложения не сохраняются.

## Границы

- Сортировка по пингу и «Re-sort on manual ping» — 007-NODE_LIST.
- Предупреждение ⚠ на мёртвом узле, от которого зависят другие, —
  006-DETOUR_AND_BALANCE.
- Пинг меряет узел по тегу в боевом ядре; detour и цепочка узла входят в
  замер как часть его пути.
