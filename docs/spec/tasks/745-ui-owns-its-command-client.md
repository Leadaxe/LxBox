## Главное правило

Поведение приложения не меняется. Меняется владение: кто создаёт и закрывает
клиент `command.sock`. Допустимые видимые отличия перечислены в разделе
«Что меняется во времени» — других быть не должно.

## Проблема

После 742 клиент ядра один на процесс: его создаёт сервис (`BoxService`,
`CoreSession.open`), а UI-мост (`VpnPlugin`, 43 обращения) пользуется сервисным
объектом. При разделении на два процесса объект не передать: у UI должен быть
свой клиент, у сервиса — свой.

Класс `BoxCommandClient` (2152 строки) смешивает две роли. По карте вызовов:

- **Нужно сервису без UI:** подписка на статус openconnect и уведомление
  «Sign-in required» (`syncOpenConnectStatus`, `Host`), подпись узла в шторке
  при старте без движка (`selectedNodeLabel`), Taildrop из уведомлений и
  активити (`newCallClient`, `taildropDelete`, `taildropCancelReceiving`,
  `taildropInboxSnapshot`, `tailscaleSnapshot`).
- **Нужно только UI:** статус-стрим (его данные читает только Flutter-sink;
  нативных читателей нет, комментарий «watchdog + скорость» в `BoxService`
  устарел), экран, профайлер, пинг, статус и пинг Tailscale, входящие Taildrop
  потоком, тест соединения, все unary-вызовы из `VpnPlugin`.
- **Пересекает роли:** openconnect — подписку держит сервис, а UI читает
  снимок, отправляет форму и поднимает слушатель SSO на том же состоянии.

## Решение

### A. Два клиента по ролям

- **`ServiceCommandClient`** (новый файл) — сервисная роль. Держатель прежний:
  `CoreSession.client`. Создаёт и закрывает сервис там же, где сейчас.
  Состав: весь блок openconnect (подписка, `openConnectEndpoints`,
  `openConnectNotified`, слушатель SSO, отправка формы и браузера, отмена,
  снимок, эмиссия в `ccOpenConnectSink`), `selectedNodeLabel`, `newCallClient`,
  `taildropDelete`, `taildropCancelReceiving`, `taildropInboxSnapshot`,
  `taildropInboxOnce`, `tailscaleSnapshot`, свой ленивый unary-клиент,
  `shutdownAll`. Интерфейс `Host` (уведомления, журнал) переезжает сюда.
- **`BoxCommandClient`** — роль UI, имя остаётся. Состав: всё остальное.
  Вместо `Host` получает в конструкторе приёмник WARN-строк журнала.
  Держатель — новый объект **`UiCoreSession`** (`client`, `isUp`, `ensure()`,
  `close()`), сторона UI.
- **Общее** для двух клиентов (полоса `lane` — одна на процесс,
  `laneWarningSink`, разрыв клиента, сборка опций, эмиттеры, если нужны обоим)
  — отдельный файл без роли. Логика подключения, поколений, реконнекта,
  JNI-no-throw и порядок закрытия внутри каждого клиента переносятся без
  изменений.

Openconnect в этом шаге целиком остаётся у сервисного клиента: слушатель SSO
должен жить, пока пользователь в браузере, а UI в это время в фоне. Шесть
обработчиков `VpnPlugin` (`ccGetOpenConnectStatus`, отправка формы, отмена,
старт и стоп слушателя, запрос открытия) продолжают ходить в
`CoreSession.client` — это явный, перечисленный остаток общей памяти.

### B. Когда UI создаёт и закрывает клиент

`UiCoreSession.ensure()` создаёт клиент и сразу поднимает статус-стрим
(`startStatus`), если клиента ещё нет и `TunnelState.status == Started`.
Зовётся:

1. в `statusReceiver.onReceive` на `Started` — до передачи события в Dart, на
   главном потоке, поэтому к первому `cc*` из Dart клиент уже есть;
2. в `onAttachedToEngine`, если туннель уже поднят;
3. в каждом обработчике `cc*` роли UI перед обращением к клиенту — страховка
   от гонки «Dart прочитал `Started` через `getVpnStatus` раньше, чем пришёл
   broadcast».

Закрытие (`shutdownAll` + обнуление держателя):

1. **до закрытия командного сервера** — как сейчас. Сервис в
   `closeCommandServerAtomic` зовёт слушателей `CoreSession` «перед
   закрытием»; `UiCoreSession` регистрирует своего в `BoxApplication.initUiSide`.
   Сервис не знает, кто слушает. Порядок прежний: клиент UI, сервисный клиент,
   потом сервер;
2. в `statusReceiver.onReceive` на `Stopped` — если клиент ещё жив (путь,
   который останется при двух процессах);
3. в `onDetachedFromEngine` — движка нет, эмитить некуда.

Там же, в `onDetachedFromEngine`, обнуляются `ccTailscalePingSink` и
`ccConnectionTestSink` (дефект, найденный в 740).

### C. Сторож границ

- В `VpnPlugin.kt` обращение к `CoreSession.client` допустимо только в
  обработчиках openconnect; список заморожен.
- `UiCoreSession` не упоминается в файлах сервисной стороны.
- Исключение «`EventSink` как тип» и доступ к `UiSinks` распространяются на
  `ServiceCommandClient.kt` только ради `ccOpenConnectSink`.

## Что меняется во времени

- Статус-стрим не поднимается, пока нет движка Flutter (старт с плитки,
  автозапуск, AppFunctions). Раньше он тикал в пустоту до первого открытия.
- После закрытия активити (движок отсоединён) клиенты UI закрыты, а не стоят
  на паузе. При возврате клиент создаётся заново; Dart и раньше делал
  `resyncForReopen` на первом подъёме потоков.
- Момент подключения статус-стрима при открытом приложении: был сразу после
  `setStatus(Started)` в потоке сервиса, стал в обработчике broadcast на
  главном потоке. Разница — время доставки broadcast.

## Не делается

- Свой openconnect-клиент у UI и команды сервису через Intent (форма, SSO).
- Отказ от слушателя «перед закрытием»: нужно сначала проверить, что ядро
  закрывает командный сервер при живых клиентах другого процесса.
- `Taildrop.send` и прочие прямые вызовы сервисных функций из `VpnPlugin`.
- `android:process`.

## Проверка

- `compileDebugKotlin`, unit-тесты Kotlin; unit-тест `UiCoreSession`: `ensure`
  без `Started` не создаёт, со `Started` создаёт один раз, `close` идемпотентен
  (создание клиента — через подменяемую фабрику).
- `flutter analyze`, `boundary_check --strict` — 0 нарушений.
- Эмулятор:
  1. холодный старт, старт VPN, данные на экране; время от `Started` до
     подключения статус-клиента и до первых групп — сравнить со сборкой до
     изменения;
  2. старт без UI (`start-vpn-headless` после удаления задачи нельзя — Debug
     API в Dart; старт с плитки), затем открыть приложение: данные пришли;
  3. удаление задачи при живом туннеле, поддельный шлюз AnyConnect: уведомление
     о входе появляется без UI; после возврата — окно входа;
  4. интернет через узел `socks` на хосте до и после закрытия UI;
  5. 50 циклов старт-стоп со случайной паузой 0–3 с; перезапуск ядра и
     `reload-vpn` при открытом экране; после каждого шага — один клиент UI на
     старт, непустые группы при `connected`, нет `TIMEOUT`/`stuck`/`FATAL`;
  6. Stats, профайлер, URL Check, пинг узла, остановка из уведомления.

## Итог

Реализация разделов A, B, C (17.11.2026). Проверено сборкой и unit-тестами;
эмулятор и телефон не проверялись — сценарии раздела «Проверка» открыты.

**Сделано**

- A. `BoxCommandClient.kt` (2152 → 1476 строк) — роль UI, в конструкторе
  приёмник WARN-строк вместо `Host`. `ServiceCommandClient.kt` (455) — сервисная
  роль, держатель `CoreSession.client`, свой unary-клиент. Общее —
  `CommandClientShared.kt` (397): полоса `CommandLane` (`lxbox-cc`, одна на
  процесс) с приёмником предупреждений, no-op обработчик, разрыв клиента,
  ленивый unary-клиент, эмиттеры, разбор типов ядра в map, unary-вызовы обеих
  ролей (`getGroups`, удаление и отмена приёма Taildrop, разовый снимок
  входящих). У каждого клиента поверх — обёртка в одну строку. Код перенесён
  без изменений; `anyClient()` и `stopStatus()` удалены как мёртвые.
- B. `UiCoreSession` (`client`, `isUp`, `ensure()`, `close()`,
  `closeOffMain()`): `ensure()` — в `statusReceiver` на `Started` до передачи
  события в Dart, в `onAttachedToEngine`, в каждом обработчике `cc*` роли UI
  (37 мест). Закрытие — слушатель `CoreSession` «перед закрытием» (регистрирует
  `BoxApplication.initUiSide`, сервис зовёт в `closeCommandServerAtomic` до
  своего `shutdownAll()`), `Stopped`, `onDetachedFromEngine`. Там же
  обнуляются `ccTailscalePingSink` и `ccConnectionTestSink`.
- C. Правила `kt-vpnplugin-coresession`, `kt-uicoresession-ref`,
  `kt-uisinks-member`; `BoxCommandClient.kt` и `UiCoreSession.kt` добавлены в
  UI-файлы правила `kt-ui-boxservice`.

**Отклонения от спеки**

- Обработчиков openconnect, ходящих в `CoreSession.client`, пять, а не шесть:
  «запрос открытия» (`ccTakeOpenConnectOpenRequest`) клиента не касается, он
  читает `UiLaunchRequests`. Пять идут через один аксессор
  `VpnPlugin.openConnectControl()` и узкий интерфейс `OpenConnectControl` —
  так в `VpnPlugin.kt` осталась одна строка с `CoreSession.client`, и правило
  сторожа проверяет признак в самой строке, без списка номеров.
- Исключение «`EventSink` как тип» выдано `CommandClientShared.kt`, а не
  `ServiceCommandClient.kt`: эмиттеры общие, сервисный клиент тип не называет.
  Доступ сервисного клиента к `UiSinks` ограничен полем `ccOpenConnectSink`
  отдельным правилом `kt-uisinks-member`.
- На `Stopped` клиент UI закрывается, только если текущий
  `TunnelState.status` не `Started`: запоздалый `Stopped` прошлого туннеля
  после нового `Started` (быстрый перезапуск, §122) иначе закрыл бы клиента
  нового туннеля вместе со счётчиком экранов.
- На `Stopped` и в `onDetachedFromEngine` (главный поток) ссылка снимается
  сразу, а `shutdownAll()` идёт в отдельной нити (`closeOffMain`), как
  `cancelPing`: главный поток в ядро не ходит (§732). Слушатель «перед
  закрытием» закрывает синхронно, в потоке остановки.
- Приёмник журнала клиенту UI отдаёт `BoxApplication.initUiSide`
  (`UiCoreSession.warningSink`), а не `VpnPlugin`: UI-файлам запрещено
  ссылаться на `BoxService`.
- Unit-тест проверяет обобщённый держатель `ClientHolder`, на котором
  построен `UiCoreSession`, с подменной фабрикой: сам `BoxCommandClient` в
  JVM-тесте не создать (Android `Handler`, libbox).
- Unary-клиент у каждой роли свой. Раньше он был общий, и `ccCancelPing` /
  `ccResyncForReopen` рвали его вместе с сервисными вызовами (подпись узла,
  Taildrop из уведомлений); теперь не рвут.

**Правки при приёмке** (коммит `fix(745)`)

- Обработчики, которые только гасят (`ccDisconnectScreen`,
  `ccDisconnectProfiler`, `ccStop*`, `ccPauseClients`, `ccCancelPing`), берут
  существующий клиент и нового не создают.
- `UiCoreSession.closeForCoreStop()` — слушатель «перед закрытием» запоминает
  старт туннеля (`TunnelState.startedElapsedMs`), и `ensure()` не создаёт
  клиент до следующего старта: между закрытием сервера и `Stopped` статус ещё
  `Started`. Метод `close()` удалён.
