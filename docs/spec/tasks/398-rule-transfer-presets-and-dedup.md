# §398 — обмен правилами: пресеты вне обмена, дедуп по имени, DNS-only экспорт

**Тип:** дефекты + доработка §396 (обмен правилами файлом)
**Зависит от:** §396 (экспорт/импорт), §264 (инвариант `traffic-processing`), §370 (ось `num`)

---

## 0. Что сломалось

Полевая проверка v2.20.11 (владелец, 17.08.2026):

> В версии 2.20.11 можно экспортировать правило «Обработка трафика». Но после
> импорта оно удваивается. Удалить его невозможно.

Плюс два продуктовых требования из того же разбора: не плодить дубли по имени
(«тогда их можно просто удалять») и уметь экспортировать **только** DNS —
серверы и правила — без правил роутинга.

### Root cause дубля

`insertImportedRule` для preset-правила смотрит только шаблон получателя
(есть ли такой `presetId`), но не проверяет, нет ли этого пресета **уже в
списке**. Для inline/srs дубль осмыслен (два разных набора доменов под похожим
именем), для пресета — нет: это ссылка на шаблон, две одинаковые ссылки
эквивалентны одной.

### Root cause «невозможно удалить»

Инвариант §264: `seedRequiredPresets` на каждой загрузке экрана пересоздаёт
несортируемые пресеты (`isSortable: false`, сегодня это `traffic-processing`),
если их нет в списке. Проверка идёт **по `presetId`**, поэтому:

- удалил одну копию из двух → инвариант доволен, вторая осталась;
- удалил обе → seed немедленно создал одну обратно.

Пользователь видит «удаляется, но остаётся». Само по себе это не баг seed'а —
он защищает `sniff`/`hijack-dns`, которые обязаны быть первым правилом
`route.rules`. Баг в том, что импорт вообще позволил создать вторую копию.

## 1. Решения (владелец, 17.08.2026)

1. **Пресеты вне обмена целиком** — ни экспорта, ни импорта. Пресет есть у
   каждого получателя (он из шаблона приложения), переносить нечего. Это
   симметрично уже принятому решению §396 §4.2 п.2 про preset-серверы DNS.
2. **Если в storage уже оказалось два пресета — использовать второй.** Дедуп
   существующего storage делаем при загрузке: из группы с одинаковым
   `presetId` остаётся **последний** (он же нижний по списку) — так
   пользователь, у которого уже задвоилось, чинится сам собой при следующем
   открытии экрана, без ручного удаления.
3. **Дублей по имени не создавать.** Правило с уже занятым видимым именем
   помечается в превью как неимпортируемое: «Уже есть на этом устройстве» —
   ровно как ведут себя DNS-записи. Суффикс « (2)» больше не выдаётся.
4. **DNS-only экспорт.** Кнопка «Продолжить» на первом экране активна и при
   пустом выборе правил — можно уйти на шаг DNS и выгрузить только DNS.

## 2. Изменения

### 2.1 Экспорт: пресеты не показываются

`_exportRules` фильтрует список перед пикером:

```dart
final exportable = [
  for (final r in _customRules)
    if (r.kind != CustomRuleKind.preset) r
];
```

Пункт меню Export остаётся включён, пока есть **хоть что-то** для выгрузки —
непресетное правило, DNS-сервер или DNS-правило (иначе экспортировать нечего
и в шите нечему появиться).

Первый экран пикера при пустом `exportable` показывает поясняющую строку
вместо пустого списка: правила есть, но все они пресетные.

### 2.2 Экспорт: «Продолжить» без правил

Кнопка первого экрана больше не гейтится непустым выбором. Второй экран
(«Добавить DNS») сам решает, что отдать: если и правил, и DNS-выбора нет,
итоговый экспорт не запускается (`_exportRules` выходит молча).

Итоговая кнопка второго экрана уже умеет оба состояния
(«Экспорт (+N DNS)» / «Экспорт без DNS»); при нулевом выборе целиком она
disabled.

### 2.3 Импорт: пресеты отвергаются

`sanitizeImportedRule`: ветка `CustomRuleKind.preset` — всегда
`ImportRuleRejectReason.presetNotTransferable` (новое значение enum'а),
независимо от того, знает ли шаблон получателя такой `presetId`. Значение
`unknownPreset` остаётся для файлов v2.20.11, где пресеты ещё могли попасть в
`rules[]` (текст в превью — тот же смысл: «пресеты не переносятся»).

### 2.4 Импорт: дедуп по имени

Новый параметр санации `existingNames` (видимые имена правил получателя —
`visibleRuleNames`, §279). Совпадение → `ImportRuleRejectReason.nameExists`,
чекбокс disabled, подпись «Уже есть на этом устройстве».

`insertImportedRule` теряет суффиксную ветку: имя больше не мутируется, так
как конфликтные элементы до вставки не доходят. Дедуп по `orderNum` и
перегенерация `id` остаются.

Мультиимпорт: имена уже вставленных элементов добавляются в набор на лету —
файл с двумя правилами одного имени вставит первое, второе отбракует.

### 2.5 Storage-heal: два пресета → остаётся последний

`normalizeRuleOrder` (сегодня seed → разметка → сортировка) получает шаг
дедупа **перед** seed'ом: для каждой группы `kind == preset` с одинаковым
`presetId` остаётся последний элемент в порядке списка.

Почему последний, а не первый: решение владельца («если уж получился в стет 2
пресета, то использовать 2й»); при импорте второй экземпляр — тот, что
приехал из файла, то есть более свежее намерение пользователя.

Функция уже идемпотентна и зовётся из общего пути загрузки, так что старые
задвоенные storage чинятся при первом же открытии экрана Routing без миграции.

## 4. Критерии приёмки

1. Экспорт: «Обработка трафика» и прочие пресеты в списке не показываются.
2. Экспорт: можно ничего не выбрать из правил, нажать «Продолжить», отметить
   только DNS — файл содержит `dns_servers`/`dns_rules` и пустой `rules`.
3. Импорт файла v2.20.11 с пресетом внутри: пресет серый, «пресеты не
   переносятся», остальные правила импортируются.
4. Импорт правила с именем, которое уже есть: серое «Уже есть на этом
   устройстве», дубль не создаётся.
5. Storage с двумя `traffic-processing` (последствие v2.20.11): после
   открытия экрана Routing остаётся один — второй; правило удаляется штатно
   и пересоздаётся seed'ом только если удалить единственное.

## 5. Не-цели

- Отменять инвариант §264 (`traffic-processing` обязателен) — seed остаётся.
- Диалог «Заменить / Копией / Пропустить» на каждое совпадение — владелец
  выбрал «дублей не делать», диалог не нужен.
- Менять формат конверта (`format: 1`): изменения касаются только того, что
  кладётся в `rules[]` и что читается обратно.
