## Проблема

После §546 probe-конфиг (проверка задержки) проходит гард реестра, как боевая
сборка. В §546 записано: 2000 узлов vless (vision + ws + uTLS) — 213 мс с
гардом против 34 мс без, около 90 мкс на узел. Замер не закоммичен, куда
уходит время, не известно. Задача — воспроизводимый бенч и профиль, без
изменения санитайзера и гарда.

## Диагностика

### Бенч

`app/test/perf/registry_guard_perf_test.dart`, по образцу
`test/parser/engine_perf_test.dart`: гейт `LX_PERF=1`, без переменной тест
молчит; число — лучший из N прогонов (по умолчанию 3, `LX_PERF_RUNS`), до
замера один прогрев. Корпус — 2000 узлов из ссылок через `parseUri`, у
каждого узла свой хост и имя. Формы: vless vision (tcp, uTLS), vless ws (uTLS),
vless reality + grpc, trojan, hysteria2 + salamander, shadowsocks, tuic,
wireguard. Набор «§546 vless» — vision и ws через один, набор «смешанный» —
все восемь форм по кругу. Версия ядра — текущий пин `1.14.2-lx.3`.

Что меряется (всё в мкс на узел):

- (a) `buildProbeBatches(nodes, coreVersion: …)` целиком; с версией ядра и с
  пустой; отдельно эмит (`getEntries` + список записей, как в `_buildOne`) и
  гард (`applyRegistryGate` на свежих записях, эмит вне замера — гард пишет
  тело на месте, поэтому вход готовится заново на каждый прогон).
  «Батчи − гард» — оценка сборки без гарда вычитанием.
- (b) `RegistrySanitizer.sanitize` на готовых телах (глубокая копия вне
  замера): с версией ядра, с пустой версией, с `applyCoreGates: false`.
- (c) по одному типу узла на все 2000.
- (d) гард на телах с чужим ключом (`x_junk`) — ровно один код `unknown_key`
  на узел. Чистые после разбора узлы кодов не дают (разбор уже прошёл
  санитайзер), и цену текста кода без этого не увидеть.

Флага «без гарда» у `buildProbeBatches` нет. Сборку без гарда мерили двумя
способами: вычитанием (столбец «батчи − гард») и A/B — вызов
`applyRegistryGate` в `_buildOne` временно закомментирован. Сходятся:
вычитание 5–14 мкс, A/B 4,8–5,0 мкс (вычитание шумнее — два независимых
замера).

Запуск (из `app/`):

```
LX_PERF=1 LX_PERF_RUNS=7 flutter test test/perf/registry_guard_perf_test.dart
```

### Профиль

Сэмплирующий профилировщик Dart VM, из самого теста: `LX_PERF_PROFILE=1`
крутит `buildProbeBatches` с гардом на наборе «§546 vless» 5 с, ставит
`profile_period=100` мкс через `setFlag` и забирает `getCpuSamples` за это
окно. Клиент VM service — JSON-RPC по WebSocket из `dart:io`.

- `dart run` не годится: `package:lxbox` тянет `dart:ui` через
  `flutter/foundation` (`registry.dart` → `package:flutter/foundation.dart`).
- `package:vm_service` в зависимостях приложения нет (только транзитивно),
  отсюда свой клиент на пару десятков строк.
- `flutter test` поднимает VM service только с `--coverage` (или
  `--start-paused`); без него `Service.getInfo()` и `controlWebServer` отдают
  пустой адрес. Таблица под `--coverage` совпала с обычной в пределах шума.

```
LX_PERF=1 LX_PERF_PROFILE=1 flutter test --coverage \
  --coverage-path=/tmp/lcov.info test/perf/registry_guard_perf_test.dart
# один тип узла вместо §546-набора:
LX_PERF=1 LX_PERF_PROFILE=1 LX_PERF_PROFILE_SHAPE=wireguard flutter test --coverage \
  --coverage-path=/tmp/lcov.info test/perf/registry_guard_perf_test.dart
```

Печатается: self по верхнему кадру; self, свёрнутый до кода приложения
(время в `Map.[]`/`String.==` приписано ближайшему кадру lxbox); inclusive по
коду приложения; inclusive по точкам гипотез (`RegExp`, `_parseCore`,
`message`, `Map.from`, `jsonEncode`, `CastMap` …).

Машина: хост macOS, JIT (`flutter test`), под нагрузкой соседних процессов
(load average 9–15). Разброс одного и того же замера между запусками —
до ±5 мкс на узел, поэтому A/B ниже шли с `LX_PERF_RUNS=7` и эффекты меньше
~4 мкс считаются неразличимыми.

Self, свёрнутый до кода приложения: `_Ctx.sanitizeObject` 20,6 %,

По верхнему кадру время — в хеш-таблицах и строках: `_OneByteString.==`
14,5 %, `LinkedHashMap._getValueOrData` 9,8 %, `_OneByteString.hashCode` 5,5 %,
`LinkedHashMap._insert` 5,4 %. Это поиск по картам схемы (`FieldSchema.raw`,
`fields[key]`, `src.containsKey`) и вставка в новые карты при раскрытии схем.
`CastMap.[]` — 12,7 % inclusive: `FieldSchema.raw` — это `cast<String,
dynamic>()`-обёртка, и каждый геттер (`type`, `ref`, `minWhen`, `required` …)
идёт через неё.

Точки гипотез: `RegExp`, `_parseCore`, `coreAtLeast`, `message` — 0,0 %
(в профиль не попали ни разу); `LinkedHashMap.from` — 1,0 %; `jsonEncode` —
4,5 % (весь из `_assemble`, не из гарда).

Почему `sharedSchema` так дорог: `schemaFor` кеширует раскрытую схему
протокола (`_schemaCache`), `transportVariant` — вариант транспорта
(`_transportCache`), а `sharedSchema` раскрывает `tls`/`dialer.common`/
`multiplex` заново на каждый вызов: `_fieldsOf` создаёт карту новых
`FieldSchema`, `_expand` — `order`, `fields`, `relations`. Вызовов на узел
несколько: у vless поля `server`, `server_port` (ref `dialer.common`) и `tls`,
и на каждое — ДВА раскрытия: одно ради `absentWhen` в `_sanitizeValue`
(`body_sanitizer.dart` ~:600), второе в `_sanitizeRef` (~:645). Схема `tls` —
28 полей, у узла из них заполнены 3.

Масштаб обхода схемы: у тела vless ws из 25 полей схемы протокола заполнены
5, из 28 полей `tls` — 3 (`enabled`, `server_name`, `utls`).

WireGuard (профиль `LX_PERF_PROFILE_SHAPE=wireguard`): 39,6 % self — в
`_decodeBase64Lenient` (`parser/uri_utils.dart`), ключи декодируются дважды —
в `normalize` (`_normalizeString`) и в проверке `format` (`_base64Bytes`).
`sharedSchema` у WireGuard не горячий — у тела нет `tls`.

### Вердикт по гипотезам

1. **`_parseCore` компилирует RegExp на каждой проверке — опровергнута.**
   В профиле 0,0 %; мемо не дало разницы; столбцы «версия ядра задана» и
   «версия ""» равны в пределах шума. `min_core` судится только у
   присутствующих полей (`_gated` в `_sanitizeValue`), а их у узла единицы.
   Повторное `RegExp(…)` с той же строкой, судя по замеру (и по второму A/B —
   вынос регулярки в `_decodeBase64Lenient`), дёшево: VM держит свой кеш
   скомпилированных регулярок.
2. **Обход всего `order` схемы с проверками отсутствующих полей —
   подтверждена частично, ~5–8 мкс (≈10 % гарда).** Верхняя граница — правка
   2a, которая поведение меняет (снимает `default_when`, `min_when
   absent_is_zero`, `required`). Внутри этой цены — `_join(prefix, key)`,
   который строится ДО проверки правила (`_minWhenOnAbsent(f, _join(…))`) и
   ещё раз в цикле синхронизации `sanitized` для каждого поля схемы.
3. **`Map.from` на каждую запись — опровергнута.** `LinkedHashMap.from`
   1,0 % inclusive (≈0,7 мкс); A/B в шуме.
4. **`w.message()` на каждое предупреждение — опровергнута.** На чистых
   узлах предупреждений нет вовсе (коды/узел = 0 у всех типов: разбор уже
   прошёл санитайзер), в профиле 0,0 %. На узле с одним кодом — < 1 мкс.
5. **Другое — подтверждена, это основная цена.**
   - `ContractRegistry.sharedSchema` без кеша — 31 % всей сборки, A/B
     −20…−27 мкс/узел (≈40 % гарда).
   - `FieldSchema._relations` пересобирает неизменяемый список на каждый
     вызов `conflicts`/`requires`/`advisory` — 4,8 % (≈3 мкс), после кеша
     `sharedSchema` 6,9 %.
   - `CastMap` вокруг `FieldSchema.raw` — 12,7 % inclusive, но это вместе с
     самим поиском по карте; собственная цена обёртки в A/B не различима.
   - WireGuard: двойное декодирование base64 ключа — ~40 % санитайзера
     WG-узла.
   - `jsonEncode` в `_assemble` — 4,5 %, вне гарда, к задаче не относится.

## Решение

Задача — только замер: санитайзер и гард не менялись. В ветке:

- `app/test/perf/registry_guard_perf_test.dart` — бенч (a)–(d) и профиль;
- этот отчёт.

### Рекомендации (в порядке выигрыша; ни одна не меняет наблюдаемое поведение)

| # | Срез | Ожидаемый выигрыш, мкс/узел (хост, JIT) | Основание |
|---|---|---|---|
| R1 | Кеш `sharedSchema` в `ContractRegistry` по образцу `_schemaCache`/`_transportCache`, сброс там же (`registry.dart` ~:392, ~:482) | −20…−27 (гард 61 → 35–42) | A/B 5, дважды |
| R2 | В `sanitizeObject` для отсутствующего поля: сначала проверить, есть ли у поля правило отсутствия (`min_when.absent_is_zero`, `default_when.absent`, `required`), и только потом строить путь; цикл синхронизации `sanitized` — только по ключам, которые были в теле (остальных в `sanitized` нет) | −3…−6 | A/B 2a (верхняя граница), 2b |
| R3 | Разбирать `conflicts`/`requires`/`advisory` поля один раз (при раскрытии схемы), а не на каждый вызов геттера | ≈−3 (4,8–6,9 % профиля) | профиль; A/B в шуме |
| R4 | WireGuard: декодировать ключ base64 один раз на значение (normalize и format сейчас декодируют отдельно) | ≈−10…−12 на WG-узел, остальным 0 | профиль WG (40 % на декодер, половина — повтор); без A/B |
| R5 | `FieldSchema.raw` — обычная карта вместо `cast`-обёртки | ≤ −2, не различимо | профиль (`CastMap.[]` self 1 %); A/B в шуме |

Итог R1–R3 на хосте — ориентировочно гард 61 → ~30 мкс/узел, сборка probe
батчей на 2000 узлов ~140 → ~75 мс. Поведение: кеш схем безопасен, потому что
реестр неизменен после загрузки (это же обоснование у `_schemaCache`); R2 и R3
меняют только порядок и число вычислений, не результат; R4 — то же значение
из одного декодирования.

Не рекомендуется: мемо `_parseCore` (1), отказ от `Map.from` в гарде (3) и
ленивый текст кода (4) — выигрыша нет или он меньше 1 мкс.

## Риски и edge cases

- Цифры — хост macOS под нагрузкой, JIT. Абсолют между запусками плавает до
  ±5 мкс; выводы опираются на эффекты крупнее ~4 мкс.
- **Телефон — замера нет.** AOT на ARM даст другой абсолют; соотношения
  (доля `sharedSchema`, пренебрежимость 1/3/4) ожидаемо сохранятся, но это не
  проверено.
- Профилю нужен `--coverage`; покрытие меняет только сбор отчёта после теста,
  таблицы с ним и без совпали в пределах шума.
- Корпус чистый (узлы после разбора); на телах с кодами цена текста кода
  измерена отдельно (d).
