Восемь пунктов. Каждый: проблема → решение → критерий приёмки (тест).

## 1. Файловая подписка: правила импорта не применяются, «Re-fetch live» идёт в сеть

Из пункта §591 подтверждены две части из четырёх (Update/Refresh now —
намеренный keep-previous §129F; +10 с — не подтвердилось, файловая всегда
`updateIntervalHours: -1`).

**Проблема.** (а) `_fetchEntryByRef` для `file:` выходит сразу, до разбора и
import-правил (`subscription_controller.dart`, ветка `isFileSubscription`).
Кнопка Apply на вкладке Filters зовёт `updateAt` — правила Disable/Enable/Replace
к файловой подписке не применяются до перезапуска (регидрация их применяет).
(б) `_fetchSourceLive` на вкладке Source зовёт `fetchRaw(UrlSource('file:…'))` —
HTTP-запрос к несуществующему адресу с ретраями и ошибкой на экране.

**Решение.** (а) Обновление файловой подписки = повторный разбор её снапшота в
`HttpCache` тем же конвейером, что и сетевой фетч: import-правила, миграция
отметок, вердикты, отпечаток состава. Файл не перечитывается (§129F, вариант Б),
кэш не перезаписывается, GC отметок не делается (снапшот не сигнал «узел ушёл»,
§283F), `lastUpdated` не трогается (источник не обновлялся). Снапшота нет →
как раньше, keep-previous. (б) Для `file:` вкладка Source показывает снапшот из
`HttpCache`, без сети.

**Критерий.** Тест: файловая подписка + правило DISABLE → `updateAt` → узел
выключен. Тест: снапшот для `file:` читается из кэша, HTTP-клиент не вызывается.

## 2. Дедуп одинакового URL внутри прохода (§027F)

**Проблема.** `AutoUpdater.maybeUpdateAll` перебирает кандидатов по одному;
`_inFlight` снимается в `finally` до следующей записи — вторая запись с тем же
URL фетчится заново (второй запрос к провайдеру за один проход и ещё 10 с паузы).

**Решение.** В пределах прохода URL запрашивается один раз. Ответ первого
успешного фетча (тело + заголовки) отдаётся записям с тем же URL: они
разбираются локально, каждая своими правилами. Паузы перед такой записью нет
(в сеть не идём). Первый фетч URL неудачен → остальные записи этого URL в этом
проходе пропускаются.

**Критерий.** Тест: две подписки с одним URL, проход `force` → один HTTP-запрос,
у обеих узлы обновлены.

## 3. Серверный `profile-update-interval` не валидируется

**Проблема.** `_metaFromHeaders` — `int.tryParse` без проверки диапазона;
отрицательное значение принимается, а в контроллере `current.updateIntervalHours
< 0 ? current : …` его замораживает — автообновление выключено навсегда.

**Решение.** Разбор заголовка принимает только целое ≥ 0 (0 — «по серверу»,
состояние обратимо); отрицательное и мусор → `null` (заголовок игнорируется).
Жёсткий запрет сервера — только пользовательское `-1`; уже записанное сервером
значение `< -1` (пользователь его выставить не может) лечится на следующем
успешном фетче: берётся серверное значение, если оно валидно, иначе дефолт 24.

**Критерий.** Тесты: заголовок `-5` → `updateIntervalHours == null`; `12` → 12;
подписка с записанным `-7` после фетча без заголовка получает 24; с `-1` —
остаётся `-1`.

## 4. «Apply rules» считает выключенные по карте отметок (§283F)

**Проблема.** Снэкбар после Apply берёт `sub.disabledHashes.length`; карта с TTL
хранит отметки узлов, которых уже нет в `sub.nodes` → «N disabled» больше
реального.

**Решение.** Считать узлы текущего списка, чья идентичность есть в карте
(`disabledNodeCount` в `node_hash.dart`).

**Критерий.** Тест: карта с отметкой ушедшего узла → счётчик не учитывает её.

## 5. Кэш тела по `hashCode` URL

**Проблема.** `HttpCache._hash = url.hashCode.toRadixString(16)` — 32 бита,
возможны коллизии; `String.hashCode` не обещан стабильным между версиями Dart.
Кэш — единственный источник тела при регидрации и для файловых подписок:
коллизия подмешает чужое тело, смена хэша — потеряет все тела.

**Решение.** Ключ — `sha256(utf8(url))` в hex. Миграция: при чтении, записи и
удалении, если файла по новому ключу нет, а по старому есть, — старые файлы
(тело и `.headers`) переименовываются в новый ключ один раз.

Почему не «прогреть заново»: у файловой подписки источника для повторной загрузки
нет — снапшот и есть данные; сброс кэша стёр бы все файловые подписки. Онлайн без
сети после обновления стартовали бы с 0 узлов. Риск переноса — только уже
существующая коллизия старого ключа: она переедет как есть (не хуже, чем сейчас),
а вторая запись той же пары после переноса старого файла не найдёт — получит
пустой кэш, а не чужое тело.

**Критерий.** Тест: ключ стабилен (фиксированный sha256); файл по старому ключу
читается по URL и после чтения лежит под новым ключом, старого нет.

## 6. Битый источник своего сервера записывается

**Проблема.** `updateConnectionAt` пишет `rawBody`/`nodes` без проверки, что
разбор дал узлы: сохранение битого источника оставляет запись без узла. У члена
папки (`updateMemberAt`) — откат с ошибкой. Экран ошибку не читает.

**Решение.** `updateConnectionAt` возвращает `UiMsg?`: 0 узлов → запись не
меняется, возвращается `memberParseKeepCurrent` («Could not parse server config —
keeping current»). Экран редактора и `exit_node_store` показывают ошибку, как у
члена папки.

**Критерий.** Тест: `updateConnectionAt` с мусором → ошибка, `rawBody` и `nodes`
прежние.

## 7. Удаление своего сервера спрашивает «Delete subscription?»

**Проблема.** Заголовок диалога удаления без ветвления по типу записи
(`subscription_detail_screen.dart` `_delete`, `entry_context_menu.dart`).

**Решение.** Заголовок по типу: `UserServer` → «Delete server?» (строка уже есть
в l10n), подписка → «Delete subscription?». Общий хелпер для обоих мест.

**Критерий.** Тест хелпера: `UserServer` → ключ «Delete server?»,
`SubscriptionServers` → «Delete subscription?».

## 8. Смена источника на новый URL теряет кэш (решение владельца по вопросу 5: A)

**Проблема.** `updateSourceAt` online: новый источник разобран, узлы подменены,
старый кэш удалён, но тело нового в `HttpCache` не записано → офлайн-старт даёт
0 узлов до следующего успешного обновления. Debug API `PUT /subs/{id}` с `url`
меняет адрес без фетча: узлы в памяти старые, а кэш лежит под старым ключом —
после перезапуска 0 узлов.

**Решение (A).** Прежние узлы и кэш живут до первого успешного обновления по
новому URL. `updateSourceAt` (online, успех) пишет тело и заголовки нового
ответа в кэш под новым URL, затем удаляет старый. `replaceList` при смене `url`
подписки переносит кэш старого адреса под новый (узлы остаются, первый успешный
фетч нового URL перезапишет кэш).

**Критерий.** Тесты: после `updateSourceAt` online кэш нового URL есть; смена
`url` через `replaceList` → кэш доступен по новому URL, регидрация даёт прежние
узлы.
