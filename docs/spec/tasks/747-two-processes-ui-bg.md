## Зачем

Сейчас приложение — один процесс: Flutter-движок, загруженный при первом
открытии окна, остаётся в памяти рядом с туннелем, пока включён VPN, а ядро
(`libbox.so`) остаётся в памяти после остановки VPN, пока открыто окно.
Выгрузить библиотеку из живого процесса нельзя; память возвращает только
завершение процесса. Поэтому окно и туннель расходятся по разным процессам, и
каждый завершается, когда не нужен.

## Решения владельца (17.11.2026)

1. Процессов два, оба именованные: `:ui` — окно с Flutter («морда»), `:bg` —
   всё сервисное (фоновый). Процесса без имени не остаётся.
2. Каждый компонент манифеста несёт `android:process` явно — по манифесту видно,
   что где живёт.
3. Нативные окна Taildrop и плагина автоматизации остаются в `:bg`; форма входа
   OpenConnect остаётся во Flutter (`:ui`).
4. Облегчать Kotlin-код `:bg` не нужно (1,5 МБ из 108); вес `:bg` — это ядро.
5. Работа ведётся в ветке; в `develop` — по отдельному слову (идёт релиз v2.25.23).

## Что показал опыт (эмулятор arm64, Android 14 (API 34), опытная сборка)

- Flutter в `:ui` запускается и работает; клиент ядра из `:ui` получает статус,
  группы, соединения из `:bg`.
- Ядро закрывает командный сервер при живых клиентах другого процесса: 142 мс
  (обычный клиент), 273 мс (процесс клиента заморожен `SIGSTOP`), 1,7–1,9 с под
  нагрузкой хоста; зависаний и принудительных остановок нет. Слушатель «перед
  закрытием» (745) при двух процессах не нужен.
- Старт окна: холодный при живом `:bg` — 1,4–1,5 с, при мёртвых обоих — 2,9 с,
  тёплый — 0,2 с.
- Память (PSS): `:bg` 135 МБ, `:ui` с окном 145–155 МБ (в нём 29 МБ `libbox.so`
  ради клиента), `:ui` после закрытия окна — 100 МБ, пока жив. Один процесс:
  105 МБ без окна, 216 МБ с окном, 240 МБ после закрытия окна.
  **Пока окно открыто, два процесса тяжелее одного на ~70 МБ; выигрыш есть
  только тогда, когда ненужный процесс завершён** — отсюда раздел G.

## Решение

### A. Манифест и процессы

- `MainActivity` — `:ui`. Все остальные наши компоненты — `:bg`.
- Компоненты библиотек переобъявляются с `tools:node="merge"`:
  `ImagePickerFileProvider`, `ShareFileProvider`, `SharePlusPendingIntent`,
  `InitializationProvider`, `ProfileInstallReceiver`, сервисы-метаданные
  image_picker/camera — `:ui`; `AppFunctionCallerVerificationReceiver` — `:bg`.
  Исполнитель сверяет список по собранному манифесту; если `:bg` где-то зовёт
  `ProcessLifecycleOwner`/`androidx.startup`, это решается явно (второй
  провайдер или отказ от вызова), а не замалчивается.
- `activity-alias` атрибута процесса не имеет — живёт в процессе цели.
- `BoxApplication` знает свой процесс (`isUi` / `isBg` по имени). Шаги
  `onCreate` выполняются только на своей стороне: в `:ui` нет
  `Taildrop.sweepInboxesAsync`, `TaildropClip.syncOnProcessStart`,
  `QuickShortcuts.refresh`, `CrashRecovery`; в `:bg` нет `WifiNetworkObserver`
  и регистраций UI. Запуск в процессе без имени — ошибка в лог.
- `Libbox.setup`: в `:ui` — без `crashReportSource`, без oom-killer, без
  `CrashRecovery` (клиенту нужен только рантайм). В `:bg` — **лениво**: при
  первом старте сервиса или другой потребности в ядре, а не в `onCreate`
  (процесс `:bg`, поднятый ради настройки или плитки, не грузит ядро).
  `libboxReady` становится `ensureLibbox()`.

### B. Канал `:ui` → `:bg`: вызов с ответом

Один механизм — `ContentProvider` в `:bg` (`BgControlProvider`, не
экспортируется), метод `call()`. Синхронный, с ответом, сам поднимает `:bg`.
Аргументы и результат — значения `MethodChannel`, закодированные
`StandardMessageCodec` в `ByteArray` внутри `Bundle` (типы Dart-контракта
сохраняются без ручной сериализации).

Обработчики `VpnPlugin`, которым нужна сторона сервиса, **переезжают телом** в
`:bg` (`BgMethods`), а в `VpnPlugin` остаётся пересылка по имени метода. Имена и
формы ответов Dart-контракта не меняются.

- Быстрые вызовы идут одной упорядоченной полосой (порядок `setHasTun` →
  `startVPN` сохраняется). Долгие (`stopVPN`, `pprofProfile`, Taildrop
  send/save, OpenConnect) — на своих потоках. С главного потока UI `call()` не
  зовётся.
- Пересылаются: все чтения и записи настроек (`BootReceiver`, `NativeCache`,
  `AutomationCache` — владелец файлов один, `:bg`), `stopVPN`/`quitApp`
  (ожидание остановки живёт в `:bg`), `getVpnStatus`, `getTunnelUptimeMs`,
  `getCurrentSessionAllowBypass`, `isForeignVpnActive`, подписи уведомления,
  `setCoreLogsVerbose`, `setQuicKnob`, `setMemoryLimit` (+`reloadSetupOptions`),
  `setAppLanguage` (часть для сервисных поверхностей и `Libbox.setLocale`),
  `getMemoryInfo` (память `:bg` — там ядро), `pprofProfile` (результат файлом),
  `PathMtuProbe` (нужен `protect` сервиса), обработчики Taildrop
  (save, send, sendBytes, clip state, service stats, sweep после смены тегов),
  пять вызовов OpenConnect.
- Большие данные через Binder не идут (предел ~1 МБ): конфиг пишет и читает
  сам `:ui` файлом (запись атомарная: временный файл + rename), после записи —
  вызов «конфиг сохранён», по которому `:bg` сбрасывает кэш; байты Taildrop
  больше порога и профили — файлом в `cacheDir`.
- Остаются в `:ui` без пересылки: `cc*` клиента UI, `getCoreVersion`,
  `formatConfig`, `checkConfig`, списки приложений, системные настройки,
  `ProbeSession` (см. D).

### C. Канал `:bg` → `:ui`: события

- `BROADCAST_STATUS` несёт весь снимок: статус, `revoked`, `startedElapsedMs`,
  `sessionAllowBypass`. `:ui` держит копию `TunnelState`, её пишет только
  приёмник статуса и первичный запрос снимка через B при подключении движка
  (broadcast не липкий — окно, открытое при работающем туннеле, иначе видело бы
  `Stopped`).
- Клиент UI (`UiCoreSession`): создаётся по `Started` (как в 745), закрывается
  по `Stopping` и `Stopped`. Слушатель «перед закрытием» и
  `CoreSession.addBeforeCloseListener` удаляются.
- OpenConnect: `:bg` шлёт событие «состояние изменилось» без данных, `:ui`
  забирает снимок вызовом B и отдаёт в свой sink. Пароли и коды идут только
  вызовом B, не broadcast'ом и не в лог.
- Автоматизация и «нативный Stop» (`AutomationBridge`): `:bg` шлёт broadcast с
  действием, приёмник в `:ui` зарегистрирован, пока подключён движок. Без
  движка команда пропускается с записью в лог — как сейчас.
- Лог ядра и строки журнала приложения из `:bg`: поток через pipe. `:ui` при
  подписке на лог получает через B читающий конец
  (`ParcelFileDescriptor`), `:bg` пишет строки; при отписке или гибели `:ui`
  запись прекращается. Гейт «никто не слушает — не форматировать» сохраняется.
  Предупреждения клиента UI пишутся в лог самой UI-стороной.

### D. Проба без туннеля (`ProbeSession`)

Остаётся в `:ui` (до 100 параллельных замеров; пул Binder в `:bg` — 15 потоков).
Сокет ядра один на оба процесса, поэтому:
- перед стартом пробы `:ui` спрашивает `:bg` вызовом «проба начинается»:
  `:bg` отказывает, если туннель не `Stopped`, иначе запоминает «проба идёт»;
- `:bg` перед запуском своего командного сервера, если проба идёт, шлёт
  broadcast «остановить пробу» и ждёт вызова «проба закончена» не дольше 2 с.

### E. Что остаётся как есть

Команды сервису — Intent/broadcast (`ACTION_START`, `ACTION_STOP`, …); сокет
`command.sock`; нативные окна Taildrop и автоматизации в `:bg` рядом с
клиентом сервиса; плитка, автозапуск, сторож, AppFunctions.

### F. Сторож и сборка

- `boundary_check`: каждый компонент исходного манифеста (кроме алиасов) несёт
  `android:process` со значением `:ui` или `:bg`; UI-файлы не трогают
  `CoreSession`, `BootReceiver`, `NativeCache`, `AutomationCache`, `Taildrop*`,
  `ConfigManager` (кроме файлового чтения/записи конфига), `BoxService`,
  `BoxVpnService` (кроме констант и Intent-команд); сервисные файлы не трогают
  `UiSinks`, `UiCoreSession`, `AutomationBridge`-канал.
- Сборка Android проверяет собранный манифест: компонент без
  `android:process` — ошибка сборки (ловит новый плагин с собственным
  компонентом).

### G. Завершение ненужного процесса

- `:ui`: при уничтожении окна с `isFinishing` (смахнули задачу, закрыли) —
  процесс завершается сам после отсоединения движка. Уход в фон (Home) процесс
  не трогает.
- `:bg`: после остановки туннеля (`Stopped`, сервис уничтожен) процесс
  завершается сам с задержкой, если нет причин жить: открытого окна Taildrop /
  автоматизации, идущей передачи Taildrop, ожидающего перезапуска сторожа,
  идущего вызова B. Новый старт туннеля задержку отменяет. Плитку, автозапуск и
  команды автоматизации система поднимает заново.
- `quitApp`: останавливает туннель, просит `:bg` завершиться, завершает `:ui`.
  Настройки, которые читаются один раз на процесс (`core_logs_enabled`,
  `memory_limit`), теперь применяются со следующим стартом туннеля.
- `:ui` при закрытии окна сообщает `:bg` «окно закрыто»; `:bg`, если туннель
  остановлен, завершается.

## Что изменится для пользователя

- Память: VPN включён, окно закрыто — только `:bg`; VPN выключен, окно закрыто —
  ничего. Пока окно открыто — на ~70 МБ больше, чем сейчас.
- Открытие приложения после закрытия окна — холодный старт (порядка 1,5 с на
  эмуляторе) вместо тёплого.
- Экран Stats → Memory показывает память процесса с ядром (`:bg`).
- Остальное поведение не меняется; любое иное отличие — дефект.

## Не делается

- Сборка ядра без части протоколов; перенос `ProbeSession` в `:bg`.
- Нативная форма входа OpenConnect.
- Уведомление «Tailscale просит войти».

## Проверка

- `compileDebugKotlin`, unit-тесты Kotlin, `flutter analyze`, сторож; CI.
- Эмулятор (сборка ветки): холодный старт окна при работающем туннеле — статус,
  аптайм, группы; старт/стоп/reload/reconnect из приложения; стоп из уведомления
  и broadcast'ом — экран узнаёт; 50 циклов старт-стоп; настройки (кнопки
  уведомления, allow bypass, язык, verbose-лог) доходят до `:bg` сразу; лог ядра
  на экране; вход OpenConnect через поддельный шлюз (форма, отмена, ошибка);
  Taildrop из приложения (если есть tailnet — иначе отказ «VPN off» не должен
  подменять настоящий результат); автоматизация broadcast'ом при открытом и
  закрытом окне; проба без туннеля и старт туннеля во время пробы; завершение
  `:ui` и `:bg` по G и подъём плиткой/Intent'ом после него; память и время
  старта — та же таблица, что в опыте; третий процесс не появляется.
- Не проверяется здесь: телефоны.
