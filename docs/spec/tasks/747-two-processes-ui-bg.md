## Зачем

Сейчас приложение — один процесс: Flutter-движок, загруженный при первом
открытии окна, остаётся в памяти рядом с туннелем, пока включён VPN, а ядро
(`libbox.so`) остаётся в памяти после остановки VPN, пока открыто окно.
Выгрузить библиотеку из живого процесса нельзя; память возвращает только
завершение процесса. Поэтому окно и туннель расходятся по разным процессам, и
каждый завершается, когда не нужен.

## Решения владельца (17.11.2026)

1. Процессов два, оба именованные: `:ui` — окно с Flutter («морда»), `:bg` —
   всё сервисное (фоновый). Процесса без имени не остаётся.
2. Каждый компонент манифеста несёт `android:process` явно — по манифесту видно,
   что где живёт.
3. Нативные окна Taildrop и плагина автоматизации остаются в `:bg`; форма входа
   OpenConnect остаётся во Flutter (`:ui`).
4. Облегчать Kotlin-код `:bg` не нужно (1,5 МБ из 108); вес `:bg` — это ядро.
5. Работа ведётся в ветке; в `develop` — по отдельному слову (идёт релиз v2.25.23).

## Что показал опыт (эмулятор arm64, Android 14 (API 34), опытная сборка)

- Flutter в `:ui` запускается и работает; клиент ядра из `:ui` получает статус,
  группы, соединения из `:bg`.
- Ядро закрывает командный сервер при живых клиентах другого процесса: 142 мс
  (обычный клиент), 273 мс (процесс клиента заморожен `SIGSTOP`), 1,7–1,9 с под
  нагрузкой хоста; зависаний и принудительных остановок нет. Слушатель «перед
  закрытием» (745) при двух процессах не нужен.
- Старт окна: холодный при живом `:bg` — 1,4–1,5 с, при мёртвых обоих — 2,9 с,
  тёплый — 0,2 с.
- Память (PSS): `:bg` 135 МБ, `:ui` с окном 145–155 МБ (в нём 29 МБ `libbox.so`
  ради клиента), `:ui` после закрытия окна — 100 МБ, пока жив. Один процесс:
  105 МБ без окна, 216 МБ с окном, 240 МБ после закрытия окна.
  **Пока окно открыто, два процесса тяжелее одного на ~70 МБ; выигрыш есть
  только тогда, когда ненужный процесс завершён** — отсюда раздел G.

## Решение

### A. Манифест и процессы

- `MainActivity` — `:ui`. Все остальные наши компоненты — `:bg`.
- Компоненты библиотек переобъявляются с `tools:node="merge"`:
  `ImagePickerFileProvider`, `ShareFileProvider`, `SharePlusPendingIntent`,
  `InitializationProvider`, `ProfileInstallReceiver`, сервисы-метаданные
  image_picker/camera — `:ui`; `AppFunctionCallerVerificationReceiver` — `:bg`.
  Исполнитель сверяет список по собранному манифесту; если `:bg` где-то зовёт
  `ProcessLifecycleOwner`/`androidx.startup`, это решается явно (второй
  провайдер или отказ от вызова), а не замалчивается.
- `activity-alias` атрибута процесса не имеет — живёт в процессе цели.
- `BoxApplication` знает свой процесс (`isUi` / `isBg` по имени). Шаги
  `onCreate` выполняются только на своей стороне: в `:ui` нет
  `Taildrop.sweepInboxesAsync`, `TaildropClip.syncOnProcessStart`,
  `QuickShortcuts.refresh`, `CrashRecovery`; в `:bg` нет `WifiNetworkObserver`
  и регистраций UI. Запуск в процессе без имени — ошибка в лог.
- `Libbox.setup`: в `:ui` — без `crashReportSource`, без oom-killer, без
  `CrashRecovery` (клиенту нужен только рантайм). В `:bg` — **лениво**: при
  первом старте сервиса или другой потребности в ядре, а не в `onCreate`
  (процесс `:bg`, поднятый ради настройки или плитки, не грузит ядро).
  `libboxReady` становится `ensureLibbox()`.

### B. Канал `:ui` → `:bg`: вызов с ответом

Один механизм — `ContentProvider` в `:bg` (`BgControlProvider`, не
экспортируется), метод `call()`. Синхронный, с ответом, сам поднимает `:bg`.
Аргументы и результат — значения `MethodChannel`, закодированные
`StandardMessageCodec` в `ByteArray` внутри `Bundle` (типы Dart-контракта
сохраняются без ручной сериализации).

Обработчики `VpnPlugin`, которым нужна сторона сервиса, **переезжают телом** в
`:bg` (`BgMethods`), а в `VpnPlugin` остаётся пересылка по имени метода. Имена и
формы ответов Dart-контракта не меняются.

- Быстрые вызовы идут одной упорядоченной полосой (порядок `setHasTun` →
  `startVPN` сохраняется). Долгие (`stopVPN`, `pprofProfile`, Taildrop
  send/save, OpenConnect) — на своих потоках. С главного потока UI `call()` не
  зовётся.
- Пересылаются: все чтения и записи настроек (`BootReceiver`, `NativeCache`,
  `AutomationCache` — владелец файлов один, `:bg`), `stopVPN`/`quitApp`
  (ожидание остановки живёт в `:bg`), `getVpnStatus`, `getTunnelUptimeMs`,
  `getCurrentSessionAllowBypass`, `isForeignVpnActive`, подписи уведомления,
  `setCoreLogsVerbose`, `setQuicKnob`, `setMemoryLimit` (+`reloadSetupOptions`),
  `setAppLanguage` (часть для сервисных поверхностей и `Libbox.setLocale`),
  `getMemoryInfo` (память `:bg` — там ядро), `pprofProfile` (результат файлом),
  `PathMtuProbe` (нужен `protect` сервиса), обработчики Taildrop
  (save, send, sendBytes, clip state, service stats, sweep после смены тегов),
  пять вызовов OpenConnect.
- Большие данные через Binder не идут (предел ~1 МБ): конфиг пишет и читает
  сам `:ui` файлом (запись атомарная: временный файл + rename), после записи —
  вызов «конфиг сохранён», по которому `:bg` сбрасывает кэш; байты Taildrop
  больше порога и профили — файлом в `cacheDir`.
- Остаются в `:ui` без пересылки: `cc*` клиента UI, `getCoreVersion`,
  `formatConfig`, `checkConfig`, списки приложений, системные настройки,
  `ProbeSession` (см. D).

### C. Канал `:bg` → `:ui`: события

- `BROADCAST_STATUS` несёт весь снимок: статус, `revoked`, `startedElapsedMs`,
  `sessionAllowBypass`. `:ui` держит копию `TunnelState`, её пишет только
  приёмник статуса и первичный запрос снимка через B при подключении движка
  (broadcast не липкий — окно, открытое при работающем туннеле, иначе видело бы
  `Stopped`).
- Клиент UI (`UiCoreSession`): создаётся по `Started` (как в 745), закрывается
  по `Stopping` и `Stopped`. Слушатель «перед закрытием» и
  `CoreSession.addBeforeCloseListener` удаляются.
- OpenConnect: `:bg` шлёт событие «состояние изменилось» без данных, `:ui`
  забирает снимок вызовом B и отдаёт в свой sink. Пароли и коды идут только
  вызовом B, не broadcast'ом и не в лог.
- Автоматизация и «нативный Stop» (`AutomationBridge`): `:bg` шлёт broadcast с
  действием, приёмник в `:ui` зарегистрирован, пока подключён движок. Без
  движка команда пропускается с записью в лог — как сейчас.
- Лог ядра и строки журнала приложения из `:bg`: поток через pipe. `:ui` при
  подписке на лог получает через B читающий конец
  (`ParcelFileDescriptor`), `:bg` пишет строки; при отписке или гибели `:ui`
  запись прекращается. Гейт «никто не слушает — не форматировать» сохраняется.
  Предупреждения клиента UI пишутся в лог самой UI-стороной.

### D. Проба без туннеля (`ProbeSession`)

Остаётся в `:ui` (до 100 параллельных замеров; пул Binder в `:bg` — 15 потоков).
Сокет ядра один на оба процесса, поэтому:
- перед стартом пробы `:ui` спрашивает `:bg` вызовом «проба начинается»:
  `:bg` отказывает, если туннель не `Stopped`, иначе запоминает «проба идёт»;
- `:bg` перед запуском своего командного сервера, если проба идёт, шлёт
  broadcast «остановить пробу» и ждёт вызова «проба закончена» не дольше 2 с.

### E. Что остаётся как есть

Команды сервису — Intent/broadcast (`ACTION_START`, `ACTION_STOP`, …); сокет
`command.sock`; нативные окна Taildrop и автоматизации в `:bg` рядом с
клиентом сервиса; плитка, автозапуск, сторож, AppFunctions.

### F. Сторож и сборка

- `boundary_check`: каждый компонент исходного манифеста (кроме алиасов) несёт
  `android:process` со значением `:ui` или `:bg`; UI-файлы не трогают
  `CoreSession`, `BootReceiver`, `NativeCache`, `AutomationCache`, `Taildrop*`,
  `ConfigManager` (кроме файлового чтения/записи конфига), `BoxService`,
  `BoxVpnService` (кроме констант и Intent-команд); сервисные файлы не трогают
  `UiSinks`, `UiCoreSession`, `AutomationBridge`-канал.
- Сборка Android проверяет собранный манифест: компонент без
  `android:process` — ошибка сборки (ловит новый плагин с собственным
  компонентом).

### G. Завершение ненужного процесса

- `:ui`: при уничтожении окна с `isFinishing` (смахнули задачу, закрыли) —
  процесс завершается сам после отсоединения движка. Уход в фон (Home) процесс
  не трогает.
- `:bg`: после остановки туннеля (`Stopped`, сервис уничтожен) процесс
  завершается сам с задержкой, если нет причин жить: открытого окна Taildrop /
  автоматизации, идущей передачи Taildrop, ожидающего перезапуска сторожа,
  идущего вызова B. Новый старт туннеля задержку отменяет. Плитку, автозапуск и
  команды автоматизации система поднимает заново.
- `quitApp`: останавливает туннель, просит `:bg` завершиться, завершает `:ui`.
  Настройки, которые читаются один раз на процесс (`core_logs_enabled`,
  `memory_limit`), теперь применяются со следующим стартом туннеля.
- `:ui` при закрытии окна сообщает `:bg` «окно закрыто»; `:bg`, если туннель
  остановлен, завершается.

### H. Итерация 2 — окно без ядра (слово владельца 17.11.2026)

Первая сборка ветки проверена на эмуляторе: два процесса работают. Но окно
само подключалось к сокету ядра, для чего грузило `libbox.so` и вторую среду
Go (29 МБ кода в `:ui` на опытной сборке плюс куча Go). Владелец: «Ошибка.
Зачем нам два ядра грузить?» — и принял путь: **клиент экрана живёт в `:bg`,
окно получает готовые данные по нашему каналу; `libbox.so` в `:ui` не
загружается вообще.** Упрощение кода — цель, не побочный эффект.

1. `BoxCommandClient` и его держатель переезжают в `:bg`. Держатель создаёт
   клиент, когда туннель `Started` **и** окно подключено (`UiPresence`);
   закрывает перед закрытием командного сервера (внутри процесса, порядок как
   в 745: клиент экрана → сервисный клиент → сервер), при отключении или
   гибели окна. Пауза и возобновление потоков (окно в фоне) — вызовом B.
2. Все `cc*`-обработчики `VpnPlugin` становятся пересылкой в `BgMethods`
   (как уже сделано для остальных). Обработчиков, исполняемых в `:ui` и
   трогающих ядро, не остаётся.
3. Потоки данных `:bg` → `:ui` (статус, outbounds, группы, соединения,
   DNS-запросы, Tailscale, пинг Tailscale, тест соединения, входящие Taildrop,
   OpenConnect, лог ядра) идут одним мультиплексированным каналом — кадр несёт
   имя потока и значение в `StandardMessageCodec`. Механизм — обобщение
   `BgLogPipe`. Окно раздаёт кадры по своим `EventSink`. Событие OpenConnect
   «изменилось + забрать снимок» заменяется кадром со снимком.
   Гейты «никто не слушает — не собирать» сохраняются: подписка и отписка
   `EventChannel` доходят до `:bg`.
4. Прочие обращения окна к ядру уходят в `:bg`: `getCoreVersion`,
   `formatConfig`, `checkConfig` (конфиг — файлом, не через Binder),
   `ProbeSession` целиком (старт, `urlTest`, `getUrl`, отмена, стоп).
   Параллельность пробы (до 100) не должна упираться в пул Binder (15
   потоков): запрос — быстрый вызов с номером, ответ — кадром в канале
   событий. Раздел D (`ProbeGate`, согласование двух процессов на одном
   сокете) удаляется: проба снова в одном процессе с сервисом, гейт прежний.
5. `Libbox.setup` и любые `io.nekohasekai.libbox.*` в `:ui` запрещены:
   `ensureLibbox()` только в `:bg`; сторож получает правило — файлы стороны
   окна не импортируют `io.nekohasekai.libbox`.
6. Копия `TunnelState` в `:ui` остаётся (нужна синхронным читателям в окне),
   но клиент от неё больше не зависит.
7. Проверка: в `/proc/<pid :ui>/maps` нет `libbox.so` ни в одном сценарии
   (открытие, старт/стоп, редактор конфига, пинг без туннеля, вход
   OpenConnect, Stats).

## Что изменится для пользователя

- Память: VPN включён, окно закрыто — только `:bg`; VPN выключен, окно закрыто —
  ничего. Пока окно открыто — больше, чем сейчас, на цену второго процесса
  (оценка 20–30 МБ; после итерации 2 перемерить).
- Открытие приложения после закрытия окна — холодный старт (порядка 1,5 с на
  эмуляторе) вместо тёплого.
- Экран Stats → Memory показывает память процесса с ядром (`:bg`).
- Свёрнутое окно при включённом VPN работает как раньше: автообновление
  подписок и rule-set, команды и события автоматизации — процесс окна
  удерживается живым, пока туннель не остановлен. Память окна освобождается,
  когда окно закрыто (смахнули, Back) или VPN выключен.
- При выключенном VPN свёрнутое окно система может заморозить, как любое
  фоновое приложение: команда автоматизации, требующая Dart, исполнится, когда
  окно вернётся или стартует туннель (`START_VPN` работает всегда).
- Остальное поведение не меняется; любое иное отличие — дефект.

## Не делается

- Сборка ядра без части протоколов; перенос `ProbeSession` в `:bg`.
- Нативная форма входа OpenConnect.
- Уведомление «Tailscale просит войти».

## Проверка

- `compileDebugKotlin`, unit-тесты Kotlin, `flutter analyze`, сторож; CI.
- Эмулятор (сборка ветки): холодный старт окна при работающем туннеле — статус,
  аптайм, группы; старт/стоп/reload/reconnect из приложения; стоп из уведомления
  и broadcast'ом — экран узнаёт; 50 циклов старт-стоп; настройки (кнопки
  уведомления, allow bypass, язык, verbose-лог) доходят до `:bg` сразу; лог ядра
  на экране; вход OpenConnect через поддельный шлюз (форма, отмена, ошибка);

  подменять настоящий результат); автоматизация broadcast'ом при открытом и
  закрытом окне; проба без туннеля и старт туннеля во время пробы; завершение
  `:ui` и `:bg` по G и подъём плиткой/Intent'ом после него; память и время
  старта — та же таблица, что в опыте; третий процесс не появляется.
- Не проверяется здесь: телефоны.

## Итог

Состояние на 17.11.2026: код написан и собран, **на эмуляторе и телефоне не
проверен** — раздел «Проверка» (эмулятор) впереди.

### Что сделано

- **A.** `MainActivity` — `:ui`, остальные 17 наших компонентов — `:bg`; 8
  компонентов библиотек переобъявлены с `tools:node="merge"` (7 — `:ui`,
  `AppFunctionCallerVerificationReceiver` — `:bg`). В собранном манифесте 26
  компонентов, все с процессом; 4 `activity-alias` — без атрибута.
  `BoxApplication` выполняет шаги только своей стороны (`ProcessRole`); в
  процессе без имени — ни одной и ошибка в лог. `Libbox.setup` —
  `BoxApplication.ensureLibbox()`: в `:bg` лениво (перед стартом командного
  сервера и для `pprofProfile`), в `:ui` — в фоне при старте процесса, без
  crash-файла, oom-killer и `CrashRecovery`.
- **B.** `BgControlProvider` (`call()`), кодек `BgCodec` (`StandardMessageCodec`
  в `ByteArray`), сервисная половина обработчиков — `BgMethods`, вызывающая
  сторона — `BgClient` (полоса для быстрых, свой поток для долгих; с главного
  потока вызовов нет). Имена и формы ответов Dart-контракта не менялись,
  Dart-код не менялся. Конфиг пишет и читает `:ui` файлом (`ConfigFile`,
  временный файл + rename), затем `configSaved`; профиль pprof и байты Taildrop
  больше 256 КБ идут файлом в `cacheDir/bg-xfer`.
- **C.** `BROADCAST_STATUS` несёт весь снимок; копия `TunnelState` в `:ui`
  (`acceptMirror`), первичный запрос `tunnelSnapshot` при подключении движка и
  на каждый `getVpnStatus`. Клиент UI закрывается по `Stopping` и `Stopped`;
  слушатель «перед закрытием» и `CoreSession.addBeforeCloseListener` удалены.
  Openconnect — событие без данных + вызов за снимком. Автоматизация и
  «нативный Stop» — `AutomationRelay` (broadcast) → приёмник в `VpnPlugin` →
  `AutomationBridge`. Лог — поток через pipe (`BgLogPipe` → `UiLogPipeReader`).
- **D.** `ProbeSession` в `:ui`, согласование через `ProbeGate`
  (`probeBegin` / `probeEnd`, событие «остановить пробу», ожидание до 2 с).
- **F.** Сторож: правила `kt-ui-service-side`, `kt-automationbridge-ref`,
  `manifest-process`, ужесточён `kt-uisinks-member`; правила
  `kt-vpnplugin-coresession` и `kt-ui-boxservice` сняты (поглощены первым).
  Сборка Android проверяет собранный манифест (`process…Manifest`).
- **G.** `:ui` завершается после закрытия окна (`isFinishing`); `:bg` — по
  `BgLifecycle` / `bgMayExit`; `quitApp` завершает оба.

### Отступления от спеки и решения исполнителя

1. **Pipe лога создаёт окно, а не `:bg`.** В спеке `:ui` получает читающий
   конец через B. Сделано наоборот: `:ui` создаёт pipe и передаёт `:bg` пишущий
   конец. Причина: дескриптор в ответе `call()` остаётся открытым и у
   отправителя — у `:bg` был бы свой читающий конец, и запись не получала бы
   `EPIPE` при гибели `:ui`. Свойства из спеки сохранены (гейт, остановка при
   отписке и гибели окна).
2. **Подключённое окно — причина `:bg` жить.** В списке причин раздела G её
   нет; без неё `:bg` завершался бы через 5 с после остановки туннеля под
   открытым окном, теряя подписку на лог, подписи уведомления и знание «движок
   жив» (нужно `AutomationRelay` для прежней записи в лог). С последним пунктом
   G («окно закрыто → `:bg` завершается») это согласуется.
3. **Привязанная плитка — причина `:bg` жить** (`LxBoxTileService`
   onCreate…onDestroy). Иначе SystemUI поднимал бы процесс заново ради
   привязки, пока открыта шторка.
4. **Команды сервису из окна идут вызовом B, а не Intent'ом напрямую**
   (`startVPN` после согласия, `reloadVPN`, `resetNetwork`, `forceStopVPN`,
   `clearDnsCache`): той же полосой, что `configSaved`, иначе перезагрузка
   могла бы обогнать сброс кэша конфига. Внутри `:bg` команды — прежние
   Intent/broadcast (раздел E).
5. **Ручки quic-go запоминаются** (`lxbox_native_cache`) и применяются при
   загрузке ядра: значение в памяти процесса не переживает новый `:bg`. Побочно
   они теперь действуют и при старте без окна (плитка, автозапуск).
6. **Метка порядка в снимке** (`epoch` + `seq`) — в спеке её нет; без неё ответ
   вызова и broadcast могли бы перезаписать копию не в том порядке. По смене
   `epoch` окно узнаёт, что `:bg` перезапущен, и заново называет себя и
   открывает лог.
7. **Окно знает о себе `:bg`** (`uiAttached` с Binder-меткой, `uiDetached`):
   `:bg` узнаёт о гибели `:ui` через `linkToDeath`.
8. **`setMemoryLimit` при незагруженном ядре** только сохраняет значение (его
   прочтёт `Libbox.setup`); `setAppLanguage` в `:bg` делает всё прежнее, а окно
   дополнительно ставит локаль своему рантайму ядра.
9. **Сторож строже спеки:** из `BoxVpnService` в файлах окна разрешены только
   константы (Intent-команды тоже идут вызовом B, п. 4).
10. **После падения ядра `:bg` грузит ядро сразу, не лениво.** Непустой
    crash-файл при старте `:bg` → `ensureLibbox()` в фоне: `Libbox.setup`
    архивирует репорт (баннер Dart «прошлый запуск упал» читает архив при
    открытии окна), `CrashRecovery` чистит кэши. При лени без исключений баннер
    появлялся бы только после следующего старта туннеля.
11. **Коммиты:** этапы 1–3 одним коммитом (каркас, пересылка и события меняют
    одни и те же обработчики `VpnPlugin`).

### Итерация 2 — окно без ядра (раздел H)

Состояние на 17.11.2026: код написан и собран, **на эмуляторе не проверен**
(первая сборка проверена оркестратором; пункт H.7 — нет `libbox.so` в
`/proc/<pid :ui>/maps` — впереди).

**Сделано.**

- **H.1.** `BoxCommandClient` и держатель (`ScreenCoreSession`, бывший
  `UiCoreSession`) — в `:bg`. Клиент создаётся, когда туннель `Started` и окно
  подключено (`UiPresence`); закрывается первым шагом закрытия командного
  сервера (синхронно, с запретом новых клиентов до следующего старта —
  `closeForCoreStop`, как в 745), при отключении и гибели окна.
- **H.2.** Все `cc*`-обработчики `VpnPlugin` — пересылка в `BgCcMethods`.
  `VpnPlugin.kt` сократился с 1850 до 1010 строк.
- **H.3.** Один канал событий (`BgEventPipe`, обобщение `BgLogPipe`): кадр —
  имя потока + значение. Приёмники потоков в `:bg` — `StreamSinks`; подписка
  и отписка каждого `EventChannel` доходят до `:bg` (`streamListen` /
  `streamCancel`), пауза и возобновление — обычными вызовами `cc*`.
  Очереди (`PipeQueues`): ответы вызовов не теряются, снимки вытесняются
  (последний побеждает), события и лог ограничены; пишет один поток.
- **H.4.** `getCoreVersion`, `formatConfig`, `checkConfig`, `ProbeSession`
  целиком — в `:bg`. `ProbeGate` и раздел D удалены: гейт пробы снова
  внутрипроцессный.
- **H.5.** В файлах окна нет `io.nekohasekai.libbox`, `Libbox.` и
  `ensureLibbox`; правило сторожа `kt-ui-no-core`. `ensureLibbox()` в `:ui`
  бросает исключение.
- **H.6.** Копия `TunnelState` в `:ui` осталась; от неё зависит только ответ
  `getVpnStatus` при сбое вызова.
- Удалено как ненужное: `UiSinks` и строки журнала от стороны окна,
  `UiLogPipeReader`, события-broadcast'ы `BG_OPENCONNECT_CHANGED`,
  `BG_AUTOMATION_ACTION`, `BG_STOP_PROBE`, вызовы `probeBegin` / `probeEnd` /
  `closeLogPipe` / `getAppLanguage` / `taildropFileHashes`, файловые обходы
  для pprof и байтов Taildrop, правила сторожа `kt-uicoresession-ref` и
  `kt-uisinks-member`.

**Решения исполнителя сверх раздела H.**

1. **Окно не перекодирует события.** Кадр потока Dart несёт готовый конверт
   `EventChannel` (`StandardMethodCodec.encodeSuccessEnvelope`), собранный в
   `:bg`; окно отдаёт байты движку как есть (`BinaryMessenger.send`). Конверт,
   а не голое значение: кодек выравнивает `double` от начала сообщения, и
   приписанный позже байт-префикс сдвинул бы выравнивание.
2. **Долгие вызовы асинхронные для всех, не только для пробы.** `invokeAsync`
   запускает метод на потоке `:bg` и возвращается; ответ — кадр `!reply`.
   Так идут остановка туннеля, блокирующие gRPC к ядру, замеры, проба,
   проверка конфига, профиль, Taildrop, openconnect, Path MTU. Массовый пинг
   при включённом VPN (до 100 параллельных `ccUrlTestOutbound`) иначе упёрся
   бы в пул Binder так же, как проба.
3. **Крупные аргументы и синхронные ответы — файлом, одним общим правилом**
   (больше 256 КБ → `cacheDir/bg-xfer`); ответы долгих вызовов идут через pipe
   и не ограничены. Профиль pprof теперь приходит байтами в кадре.
4. **Команды автоматизации — кадром `!automation`**, а не broadcast'ом: один
   механизм на всё, что идёт в окно; `BROADCAST_STATUS` остался broadcast'ом
   (его слушают и без канала событий).
5. **Версия ядра запоминается** на установленную сборку
   (`lxbox_native_cache`): `getCoreVersion` спрашивают и без туннеля, а
   грузить ради строки ядро в свежий `:bg` незачем.
6. **Кодирование — на пишущем потоке канала**, не на главном потоке `:bg` и
   не на потоке ядра; вытесненный снимок не кодируется вовсе.

**По замечаниям 50 циклов старт-стоп первой сборки** (причины в коде найдены
предположительно, циклами не подтверждены):

- **I.** Посылку с аргументами удаляет отправитель (в `finally`); при старте
  `:bg` и окна удаляются посылки старше 10 минут.
- **J.** Вызов в завершающийся процесс получает отказ `BG_EXITING` (точно не

  `ccTaildropSendBytes`. Комментарий исправлен.
- **K.** Опрос раз в 5 с остался только для причин без собственного события
  (идущий вызов, недописанный ответ, передача Taildrop, проба, «старт в

- **L.** Подтвердилось: `setMemoryLimit` во время загрузки ядра не

- **M.** Проверено по зависимостям: в `androidx.appfunctions:1.0.0-rc01` (AAR

### Свёрнутое окно при включённом VPN (находка №1 ревью, решение владельца «держать окно живым»)

Код собран, unit-тест зелёный; на эмуляторе не проверено.

Было: через 1,5–2,5 минуты после Home процесс `:ui` замораживался системой —
вставали таймеры Dart (подписки, rule-set), команды и события автоматизации.
В одном процессе его держал foreground-сервис VPN.

Сделано: пока туннель не `Stopped` **и** окно подключено (`uiHoldWanted`),
`:bg` привязан к пустому сервису окна `UiKeepAliveService` (`:ui`, не
экспортируется) — `UiHold`. Процесс, к сервису которого привязан процесс с
foreground-сервисом, получает его важность: не кэшируется и не замораживается.
Привязка пересчитывается на каждой смене статуса туннеля и при подключении,
отключении и гибели окна.

- **Не поднимает и не воскрешает `:ui`.** Привязка ставится только при
  подключённом окне и снимается внутри вызова `uiDetached` — раньше, чем окно
  завершит процесс (завершение стоит в хвосте той же полосы вызовов).
  `onServiceDisconnected` / `onBindingDied` и метка окна (`UiPresence`)
  снимают привязку сразу. Если система всё же успела пересоздать процесс ради
  привязки, он завершится сам, когда привязку снимут (окна в нём не было).
- **Не мешает жизненному циклу.** После `Stopped` привязки нет: `:ui`
  завершается по закрытию окна, `:bg` под открытым окном перезапускается.
- **Восстанавливается.** Окно открыли при работающем туннеле или после старта
  без окна — `uiAttached` ставит привязку; новый `:bg` — так же.
- **Автоматизация.** При работающем туннеле окно живо, команда исполняется
  сразу. Выбор для оставшегося случая (туннель остановлен, окно свёрнуто и
  может быть заморожено): команда считается отправленной и исполнится, когда
  окно проснётся или стартует туннель; об этом пишется строка в logcat
  (`… sent while the tunnel is stopped — it runs when the window is awake`).


### Интеграция с задачей 750 «ИИ-ассистент» (слияние `develop`, 18.11.2026)

Код собран, тесты зелёные; на эмуляторе не проверено (и сама 750 на Android 16
через `adb shell cmd app_function` не проверялась — сравнивать не с чем).

750 была написана под один процесс. В схеме двух процессов:

- **Операции ассистента для Debug API** (`assistantOverview`,
  `assistantListExits`, `assistantCheckUrl`, `assistantCheckExit`,
  `assistantFindApps`, `assistantAppRoute`, `assistantSelectExit`) — тела в
  `:bg` (`BgMethods`), в окне пересылка долгим вызовом. Формы ответов прежние,
  ошибка операции — `{error: {code, message}}`, коды не менялись. `index` не
  хранится и не логируется; больше 256 КБ идёт файлом по общему правилу.
  Вспомогательный `assistantCall` из `VpnPlugin` переехал в `BgMethods`.
- **Шлюз (`getApiHelp` / `callApi`)** — обратный вызов `:bg` → Dart с ответом
  (`UiCalls`): запрос кадром `!call` с номером, окно подтверждает получение,
  исполняет `invokeMethod("assistantCall")` и возвращает итог вызовом по
  номеру. Политика шлюза по-прежнему только в Dart. Обещанное 750 при
  отсутствии моста сохранено: одна попытка открыть окно, ожидание до 10 с,
  уведомление «Open L×Box…», `app_not_open`. «Мост есть» = окно назвалось
  `:bg` и подтвердило получение запроса за 2 с; окно, замороженное при
  остановленном туннеле, не подтверждает — исход тот же, что у закрытого.
  На время вызова окно удерживается (`UiHold`).
- **Исполнение AppFunction — причина `:bg` жить** на время вызова
  (`BgLifecycle.hold` / `release` вокруг каждой из десяти функций).
- **Отмена.** Операции окна исполняются в общей области корутин и отменяются,
  когда окно отключилось или умерло (раньше — отключением движка): проверка
  адреса не доигрывает впустую, признак «занято» снимается.
- **Сторож:** окну запрещены имена `AssistantCore`, `AssistantBridge`,
  `AppFunctionsGate`, `LxBoxAppFunctions`, `UiCalls`.

Не менялось: состав функций, тумблеры и зеркало `appfunctions_enabled`
(читает `:bg`), Dart-код 750.

### Остановка сносила следующий старт (блокер перед релиз-кандидатом, 18.11.2026)

Код собран, unit-тесты зелёные; на эмуляторе не проверено.

Случай: `reconnect` из Dart (`stopVPN` → сразу `startVPN`) — туннель не
поднялся, `:bg` упал с `ForegroundServiceDidNotStartInTimeException`.

Причина. `BoxService.doStop` в конце делал `setStatus(Stopped)`, затем
`service.stopSelf()`. `setStatus(Stopped)` завершает ожидание `stopAwait` —
ответ `stopVPN` уходит окну, и Dart тут же шлёт `startVPN`
(`startForegroundService`). `stopSelf()` без номера, дошедший до системы после
этого, сносил сервис вместе с уже запрошенным стартом («Bringing down service
while still waiting for start foreground»). В `develop` порядок тот же, но
между двумя строками был субмиллисекундный зазор; после 747 в
`setStatus(Stopped)` добавились `UiHold.sync`, запись `revoked`, строки
журнала — зазор вырос до десятков миллисекунд, а ответ окну идёт через
границу процессов.

Сделано (`StartLedger`):

- сервис останавливает себя только с номером — `stopSelf(startId)` последнего
  **доставленного** старта: система не исполняет такую остановку, если
  запрошен более новый старт, и тот исполняется на том же экземпляре. Номер
  покрывает и старты, принятые, но не исполненные (пришли во время остановки);
- в `doStop` и `stopAndAlert` остановка вызывается **раньше** объявления
  `Stopped`;
- force-stop объявляет `Stopped` раньше конца закрытия ядра (так задумано,
  §129/§140): его фоновая доводка останавливает сервис, только если не начался
  новый старт, а новый старт перед своим командным сервером дожидается доводки
  (не дольше 6,5 с);
- `onRevoke`, отказ `startForeground`, шторм sticky-рестартов, отменённый
  старт — тоже с номером;
- `onDestroy` экземпляра, который уже не `BoxVpnService.live`, общее состояние
  туннеля не трогает.

`startForeground` на пути `ACTION_START` и раньше вызывался до проверки
статуса; исключение в журнале пришло не из-за его отсутствия, а потому что
система снесла сервис между `startForegroundService` и `onStartCommand`.

Где `Stopped` по-прежнему объявляется раньше фактической остановки сервиса:
force-stop (задумано, закрыто поколением и ожиданием); `stopAwait` без живого
приёмника (сервиса уже нет); `onDestroy` при статусе не `Stopped` (без
события, как и раньше).

Это же, вероятно, объясняет невоспроизведённый «потерянный старт»
(`started=true`, туннель не поднялся): тот же порядок, только остановка
успела до `onStartCommand` и без падения процесса — доказательства нет,
журнала того случая не было.
