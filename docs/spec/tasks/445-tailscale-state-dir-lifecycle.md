## Проблема

Сборка 2.24.0 подставляет узлу Tailscale `state_directory` =
`<filesDir>/tailscale/<tailscaleStateDirName(финальный тег)>`
(`build_config.dart`). В каталоге tsnet держит личность устройства в tailnet:
ключи машины и узла, состояние входа (`tailscaled.state`), логи. Норма §9.8
(удалить при удалении узла, сохранить при переименовании, снять сирот, не
класть в бэкап) в коде не реализована. На стенде 14.09 после удаления всех
узлов осталось шесть каталогов; переименование узла дало новое устройство, а
одноразовый `auth_key` был уже потрачен → `invalid key`.

Финальный тег как ключ каталога ломается в трёх местах:

1. переименование узла или смена префикса папки (`tag_policy`) меняет имя
   каталога — узел входит в tailnet новым устройством;
2. санитизация схлопывает кириллицу и эмодзи: `Дом` и `Код` → `___`. У узлов
   подписки с тегами вида `🇷🇺 Москва` такие совпадения обычны;
3. Workspaces: сцена одна на все слоты, каталоги всех слотов лежат в одном
   `tailscale/`, и сборка одного слота не отличает каталог другого слота от
   сироты.

## Решение

Стабильный ключ узла и индекс `tailscale_state.json` «ключ → имя каталога»,
отдельный набор записей на каждый слот Workspaces. Имя каталога выдаётся один
раз, когда узел впервые попадает в сборку, и больше не меняется.
Переименование и перенос узла переписывают ключ записи, файлы не двигаются.
Удаление снимает запись; каталог, на который не ссылается ни один слот,
удаляется, когда ядро остановлено.

### 1. Ключ узла

| Где узел | Ключ | Меняется при |
|---|---|---|
| одиночный сервер (`UserServer`) | `<id сервера>`; второй и следующие узлы Tailscale того же сервера — `<id>#2`, `<id>#3` | переносе в папку |
| член папки | `<id папки>/<сырой тег>`; тёзка с тем же тегом — `<id папки>/<тег>#2` | правке тега, переносе в другую папку, выносе в сервер, перестановке тёзок |
| узел подписки | `<id подписки>/<сырой тег>`, тег уникализирован в источнике (`sourceNodeRawTags`) | смене тега провайдером |

- id источника — uuid (`ServerList.id`, «стабилен на всём жизненном цикле»);
  сырой тег — тот же, что в адресе NodeLink (`node_link_address.dart`).
- Одиночный сервер берёт `id`, а не корневой адрес `{tag}`: переименование и
  смена префикса сервера ключ не меняют, и правка тела мимо реестра (Debug API)
  личность не теряет.
- Выключение узла, члена, папки или источника ключ не меняет: ключи считаются
  по всем хранимым узлам.
- Узел подписки эмитируется: `ServerListBuild.build` кладёт `TailscaleSpec`
  подписки в `endpoints[]`, отбрасываются только его секции
  (`subscription/sources.dart`, info-строка §437). Ключ нужен и ему.
- Ключ — строка индекса, не имя каталога. `tailscaleStateDirName` применяется
  только к выдаваемому имени (§2), поэтому совпадения после санитизации
  личности не смешивают.

### 2. Индекс

`<filesDir>/tailscale_state.json`, запись через tmp + rename:

```jsonc
{
  "version": 1,
  "slots": {
    "Home": { "<ключ узла>": "<имя каталога в tailscale/>" },
    "Work": { }
  }
}
```

- Файл лежит вне `lxbox_settings.json` и вне `kSlotEntries`: в бэкап и в копию
  слота не попадает по построению.
- **Выдача имени.** Узлу без записи выдаётся
  `tailscaleStateDirName(<префикс> <тег>)` — финальная форма без суффикса
  уникализации сборки. Если имя уже есть на диске или записано у любого слота,
  берётся `-1`, `-2`… (тот же порядок суффиксов, что у `allocateTag`). Каталог
  не создаётся: его создаёт ядро на первом старте узла.
- **Сборка** подставляет `state_directory` = `<filesDir>/tailscale/<имя>` по
  записи узла. Узлу с явным `state_directory` в теле запись не заводится, его
  каталог не трогается.
- Нечитаемый индекс считается пустым: слот идёт путём миграции (§5), и
  каталоги, названные по финальной форме, подхватываются снова.
- Операции индекса сериализованы одной очередью (сборка и реестр могут идти
  вперемешку).
- Поле `legacy` — каталоги, найденные при создании индекса (§4, §5).

Почему не «имя каталога = ключ» с переименованием на диске:

- под поднятым VPN каталог открыт ядром. tsnet пишет `tailscaled.state` через
  временный файл в том же каталоге (`ipn/store/stores.go`,
  `atomicfile.WriteFile`), и каталог, переименованный на ходу, теряет записи до
  перезапуска ядра;
- слоты Workspaces делят личности ссылками, без копирования живых файлов (§6);
- миграция сводится к записи в индекс без файловых операций (§5);
- совпадения санитизированных имён не нужно разводить на диске.

### 3. Операции → что с каталогом

«Ядро остановлено» — native-статус туннеля `Stopped` (`getVpnStatus` →
`disconnected` или `revoked`). Ошибка канала считается поднятым туннелем.

| Операция | Ключ | Индекс | Каталог |
|---|---|---|---|
| переименование одиночного сервера (правка тела) | не меняется | — | тот же |
| смена префикса сервера, папки, подписки | не меняется | — | тот же |
| выключение узла, члена, папки, источника | не меняется | — | тот же |
| правка тега члена папки | `F/a` → `F/b` | запись переходит на новый ключ | тот же |
| перенос члена в другую папку | `F1/a` → `F2/a` | то же | тот же |
| перенос сервера в папку | `<id>` → `F/a` | то же | тот же |
| вынос члена в сервер, роспуск папки с сохранением серверов | `F/a` → `<новый id>` | то же | тот же |
| перестановка тёзок в папке | `F/a` ↔ `F/a#2` | записи меняются местами одновременно | за каждым узлом свой |
| цель перехода занята устаревшей записью | — | запись узла побеждает, warning в AppLog | каталог устаревшей записи становится сиротой |
| удаление узла, члена, пачки членов, папки, источника | исчезает | запись снимается сразу | удаляется сразу, если ядро остановлено и на каталог не ссылается другой слот; иначе при ближайшей сборке с остановленным ядром (§4) |
| узел пропал из тела подписки при обновлении | исчезает | снимается при сборке с остановленным ядром | удаляется там же |
| подписка без тела в кэше, сервер с нечитаемым телом, член с битым текстом | не вычисляется | записи контейнера сохраняются | тот же |

Реестр ссылок вызывает переписывание ключей из
`SubscriptionController._relink` — там же, где переписываются ссылки NodeLink,
до `_persist()`. Ключи сопоставляются по самим узлам, как в
`diffNodeAddresses` (объект узла или пара `renamed`). Вызов идёт мимо раннего
выхода реестра: перестановка тёзок меняет ключ, но не адрес.

### 4. Сироты при сборке

`SubscriptionController._generate`, до `buildConfig`:

1. Записи слота `current` дополняются для узлов без записи (§2, §5).
2. Если ядро остановлено:
   - снимаются записи слота, ключей которых нет среди всех хранимых узлов
     Tailscale слота, кроме записей неразобранных контейнеров (§3, последняя
     строка);
   - снимаются наборы записей слотов, которых нет в справочнике Workspaces;
   - каталоги в `tailscale/`, на которые не ссылается ни один слот, удаляются;
     на каждый — info-строка в AppLog
     `Tailscale state of a removed node deleted: tailscale/<имя>`.
3. Если ядро поднято, шаг 2 ждёт следующей сборки при остановленном ядре.

**Под живым ядром.** Выбран вариант «снимать только при остановленном ядре».
Вариант «снимать всё, чего нет в текущем конфиге» не годится: пересборка под
живым туннелем переписывает `singbox_config.json`, а ядро работает с конфигом,
с которым стартовало, и узел, удалённый две пересборки назад, в нём ещё есть.
Хранить набор каталогов «с последнего холодного старта» можно, но статус
туннеля всё равно нужен, а с ним правило «только при остановленном ядре»
проще. Вторая линия: удаляются только каталоги без записи у всех слотов, а у
текущего слота запись есть у каждого хранимого узла. Даже при ложном `Stopped`
под удар попадают только каталоги узлов, уже удалённых из настроек.

**Слот без записей.** Индекс при создании запоминает каталоги, которые уже
лежат в `tailscale/` (поле `legacy`, имена 2.24.0). Пока в справочнике есть
слот без набора записей (сохранён версией без индекса и после обновления не
загружался), эти каталоги не удаляются ни при сборке, ни при операциях реестра
и Workspaces: они названы по финальному тегу и могут принадлежать такому слоту.
Каталоги, выданные индексом, удаляются как обычно. Когда каждый слот собран
или удалён, `legacy` очищается.

### 5. Миграция

Первая сборка слота после обновления — у слота ещё нет набора записей в
индексе:

- для каждого узла ищется каталог по имени, которое давала 2.24.0: финальная
  форма, при занятости — `-1`, `-2`… в порядке узлов. Каталог есть в `legacy`
  (§4) и на него не ссылается другой слот справочника → запись узла указывает
  на него, в AppLog `Tailscale state of node "<тег>" kept: tailscale/<имя>`.
  Файлы не двигаются: конфиг, собранный до обновления, ссылается на тот же
  путь, и живое ядро ничего не замечает;
- каталога нет → узлу выдаётся новое имя (§2);
- подхват идёт один раз: после первой сборки у слота есть набор записей, и
  дальше новые узлы получают только свободные имена. Узел с уже существующей
  записью старый каталог не забирает (новая не затирается); старый каталог без
  ссылок уходит как сирота (§4).

Не подхватываются каталоги, чей тег 2.24.0 уникализировала иначе, чем даёт
порядок хранимых узлов (выключенный тёзка в середине списка сдвигает суффиксы).
Такой узел входит новым устройством; ситуация требует тёзок Tailscale и
выключенных узлов между ними.

### 6. Workspaces

Что делает `workspace_store.dart`:

- стабильного id у слота нет: имя слота = имя папки, `rename` переименовывает
  папку и `current`;
- `saveAs(Y)`: сцена → папка Y, `current = Y`. VPN не трогается. Прежний
  `current` в свою папку не сохраняется: его папка, если есть, остаётся снимком
  с последней загрузки;
- `load(X)`: `WorkspaceController.load` до копирования опускает VPN
  (`stopVpn`), дальше сцена → папка `current`, папка X → сцена, пересборка,
  подъём VPN, если был поднят;
- `delete`: `current` удалить нельзя;
- `recover()` на старте доводит загрузку по журналу;
- без справочника `current` = «Default».

Разбор вариантов:

- **(A) `tailscale/` в `kSlotEntries`.** Load копирует при остановленном VPN —
  годится. Save as идёт при поднятом VPN, копировать нельзя. Без копии папка Y
  остаётся без личностей, и Load Y после цепочки Save as → Save as ставит на
  сцену пустой `tailscale/`. Слоты 2.24.0 копии не имеют, а общий `tailscale/`
  сцены держит каталоги всех слотов: первая загрузка такого слота их затрёт.
  Логи tsnet раздувают размер слота.
- **(B) `tailscale/<id слота>/<ключ>`, без копирования.** Нужен стабильный id в
  справочнике. Load, rename и delete проходят чисто, ломается Save as. Сцена
  после Save as — это Y, и её живые личности должны остаться у Y. Прежний
  `current`, если у него есть папка-снимок, ссылается на те же узлы. Без
  копирования живых файлов личность теряет одна из сторон.
- **(C, выбран) индекс «слот → ключ → каталог».** Каталоги лежат в одном
  `tailscale/`, пространство имён слота — его набор записей в индексе.
  Копирования нет ни в одной операции.

| Операция Workspaces | Индекс | Каталоги |
|---|---|---|
| сборка | записи слота `current` (§4) | сироты — §4 |
| Load X | не меняется; сборка нового `current` читает записи X | не трогаются |
| Save as Y, Y ≠ `current` | записи Y := копия записей `current`, до записи справочника | не копируются; каталоги прежних записей Y, на которые больше никто не ссылается, удаляются сразу |
| Save as в `current` | не меняется | — |
| Rename слота | набор записей переезжает под новое имя, до записи справочника | не трогаются |
| Delete слота | набор записей снимается, после записи справочника | каталоги, на которые не ссылается другой слот, удаляются сразу |
| recover | не меняется | — |

Удаление сразу в Save as и Delete не ждёт остановки ядра: у слота, который не
`current`, узлов в работающем конфиге нет. Load всегда опускает VPN и
пересобирает конфиг нового `current` до старта, а native-перезапуск берёт
сохранённый конфиг `current`. Каталог, общий с `current`, держится его записью.

Проверка целей:

| Цель | Как выполняется |
|---|---|
| личности разных слотов не смешиваются | узлы, созданные в Home и Work независимо, имеют разные id источников → разные ключи → разные каталоги, даже при одном теге и имени папки. Узел, удалённый в Work и добавленный заново с тем же тегом в ту же (скопированную) папку, получает новый каталог: запись снята при удалении |
| переключение не теряет личность | Load каталоги не трогает |
| сборка текущего слота не стирает каталоги других | удаляются только каталоги без записей у всех слотов; слот без записей приостанавливает удаление |
| удаление слота удаляет его личности, переименование сохраняет | Delete снимает набор и удаляет каталоги без других ссылок; Rename переносит набор |
| живые файлы tsnet не копируются | ни одна операция их не копирует |
| первое Save as не теряет личности | записи «Default» копируются в Y, каталоги те же; набор «Default» снимается при сборке, когда «Default» уже нет в справочнике |

**Принятое ограничение.** После Save as узел-копия в обоих слотах — одно
устройство tailnet (общий каталог). Это совпадает со смыслом копии: одноразовый
`auth_key` потрачен один раз, и оба слота входят без него. Слоты не работают
одновременно, общий каталог не делится двумя tsnet. Если в копии сменить
`auth_key` или `control_url` на другой tailnet, узел останется в прежнем:
tsnet с сохранённым входом ключ не читает. Без Workspaces правка узла ведёт себя
так же — вынесено вопросом.

### 7. Бэкап

- `BackupService` и LX Backup (`lx_backup*.dart`) собирают файл из ключей
  `SettingsStorage` и `dart:io` не используют. Индекс и каталоги лежат в
  `filesDir` вне `lxbox_settings.json` — ни во внутренний бэкап, ни в LX Backup
  не попадают. Восстановление на той же машине сохраняет id источников, и узлы
  находят свои записи; на другой машине записей нет — новое устройство и
  повторный вход (норма §9.8 п. 4).
- Вне задачи: у `<application>` в `AndroidManifest.xml` не задан
  `android:allowBackup`, по умолчанию `true`. Системная резервная копия Android
  и перенос между устройствами берут `files/`, включая `tailscale/`. Вынесено
  вопросом.

### 8. Слои (§439 §2.5)

| Слой | Модуль | Что делает |
|---|---|---|
| сервис, чистые функции | `services/tailscale_state/state_keys.dart` | ключи узлов, сопоставление ключей до и после операции, имя каталога (`tailscaleStateDirName` переезжает сюда) |
| сервис, файлы | `services/tailscale_state/state_store.dart` | индекс, выдача имён, миграция, сироты, операции слотов |
| потребители | `SubscriptionController._relink` / `_generate`, `WorkspaceStore.saveAs` / `rename` / `delete` | вызывают сервис, передают корень, имя слота и статус ядра |
| сборка | `BuildSettings.tailscaleStateDirs` | узел → имя каталога; без карты путь по финальному тегу, как в 2.24.0 |

Корень у сборки и реестра — native `filesDir` (`getFilesDir`), у
`WorkspaceStore` — `getApplicationSupportDirectory()`. На Android это один
каталог (`files/`, §417 §2.1). Сбой индекса операцию не останавливает:
Workspaces логирует warning, сборка без карты называет каталог по финальному
тегу (как 2.24.0) с warning.

Швы для тестов контроллера: `SubscriptionController.debugTailscaleStateRoot`
и `debugCoreStopped`.

- удаление члена, пачки, папки, источника; переименование и перенос члена;

- переименование одиночного сервера и смена префикса папки не меняют каталог;
- выключение не трогает каталог;
- сирота снимается при остановленном ядре и остаётся при поднятом;
- миграция: подхват каталога 2.24.0, запись не затирается;
- Workspaces: два слота с одним тегом, Save as, Load, Rename, Delete слота,
  слот без записей приостанавливает удаление;
- сборка: `state_directory` из карты.

### 10. Вопросы владельцу

1. Правка `auth_key` или `control_url` узла Tailscale (и узла-копии в другом
   слоте): выдавать новый каталог? Сейчас tsnet с сохранённым входом новый ключ
   не читает, и переход в другой tailnet правкой узла не работает.
2. Подтверждение удаления узла Tailscale или слота с текстом «удалит вход в
   Tailscale» — видимый текст, в задаче не делался.
3. `android:allowBackup` по умолчанию `true`: ключи Tailscale (и
   `lxbox_settings.json` с аккаунтами WARP) уходят в системную резервную копию.
   Исключить через `dataExtractionRules` / `fullBackupContent` — отдельная
   задача.
4. Лаунчер: NODE_SECTIONS.md §6 называет каталог по финальному тегу. LxBox
   держит своё отображение; в конфиг попадает только путь, в бэкап — ничего.
   Сообщать лаунчеру как вариант реализации?
