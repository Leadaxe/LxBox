# §351 — Теги каналов резервируются в аллокаторе тегов билдера

| | |
|---|---|
| Тип | bugfix (fatal старта ядра) |
| Статус | ✅ Реализовано, тесты зелёные |
| Дата | 2026-08-02 |
| Связанные | [`348`](348-two-month-revision-parser-fixes.md) (находка P3-6 ревизии), [`125 configurable-channels`](../features/125%20configurable-channels/spec.md) |

## Проблема

`_BuildCtx._taken` резервировал только `{direct-out, dns-out, block-out}`.
Селекторы каналов (§125) эмитятся в `_buildChannelGroups` с фиксированным
`c.tag` **мимо** `allocateTag`, а `validateConfig` дубли тегов не проверяет
(`allTags` — Set). Узел подписки с меткой `#vpn-1` (tagFromLabel отдаёт её
как есть) давал два outbound с тегом `vpn-1` → отказ ядра на старте.

## Решение

Резолв `channels` перенесён выше создания `_BuildCtx`; конструктор получает
`reservedTags` — `c.tag` + `c.autoTag` всех активных каналов (фильтр тот же,
что в `_buildChannelGroups`: `enabled || isRequired`). Узел-тёзка получает
суффикс `-N` штатным путём аллокатора.

Решения по месту:

| вопрос | решение |
|---|---|
| `autoTag` резервировать всегда или только при эмите двойника? | Всегда: эмит условный (`auto != null && nodes.isNotEmpty`), а пере-резерв лишь добавит суффикс узлу-тёзке — обратная ошибка стоила бы старта |
| Дубль-детекция в `validateConfig`? | Не в этой таске: резерв закрывает единственный известный путь дубля (всё остальное идёт через `allocateTag`). Расширение sealed `ValidationIssue` — отдельным решением, если появится новый путь |

## Тесты

`test/builder/channel_groups_test.dart` — группа §351: узлы `#vpn-1` и
`#vpn-1-auto` при канале `vpn-1` → дублей нет, селектор остаётся каналом,
узлы переезжают на `vpn-1-1` / `vpn-1-auto-1`.
