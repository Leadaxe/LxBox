# §380 — вернуть naive в сборку F-Droid и включить reproducible builds

| Поле | Значение |
|------|----------|
| Статус | Спека |
| Дата старта | 2026-08-05 |
| Связанные spec'ы | [§379](379-version-code-from-version.md) — схема versionCode; [`FDROID.md`](../../FDROID.md) — публикация; [§013](013-naive-proxy-uri.md) — naive в приложении; [§270](270-naive-tls-fragment-incompatible.md) — его ограничения |

## Проблема

В сборке F-Droid протокол **naive отключён**: build-тег `with_naive_outbound`
вырезается из `cmd/internal/build_libbox/main.go` прямо в метаданных. Причина
была в том, что он тянет `github.com/sagernet/cronet-go`, а тот поставляет
готовый `libcronet.a` (60–64 МБ на архитектуру) — а prebuilt-бинарники в
F-Droid запрещены.

Следствия:

1. **Пользователи F-Droid не получают naive.** Остальные 11 протоколов на
   месте, но узлы `naive://` в каталожной сборке работать не будут.
2. **Reproducible builds невозможны.** Сборка F-Droid намеренно отличается от
   APK с GitHub, значит побайтового совпадения не будет никогда, и APK
   подписывается ключом F-Droid, а не нашим (`7987aec4`, `CN=BoxVPN`).
   Пользователь не может перейти между каналами без удаления приложения.

**Вывод «naive невозможен» был неверным.** Апстрим `io.nekohasekai.sfa` держит
naive в каталоге F-Droid, собирая cronet из исходников. Рецепт из их
метаданных:

```
srclibs:
  - cronet-go@d9ea2601b3a8bd0b2c54ec5c515cb25dfc468dab
prebuild:
  - pushd $$cronet-go$$
  - for arch in arm arm64 386 amd64; do
      go run ./cmd/build-naive --target=android/$arch build;
      go run ./cmd/build-naive --target=android/$arch package --local;
      diff lib/android_$arch/libcronet.a \
           $GOMODCACHE/github.com/sagernet/cronet-go/lib/android_$arch@*/libcronet.a;
    done
  - popd
```

Логика: собрать `libcronet.a` самим, затем `diff` с prebuilt из модуля.
Совпало — значит бинарник соответствует исходникам, и prebuilt перестаёт быть
чёрным ящиком.

## Что предстоит выяснить

Спека описывает направление, но три вещи требуют проверки до реализации.

### 1. Сколько это стоит по времени

`build-naive` собирает **Chromium**: качает `depot_tools`, собирает clang и
sysroot (`get-clang.sh`), затем гоняет `ninja`. Апстрим делает это для четырёх
архитектур в одном билд-блоке.

Наша сборка уже занимает около часа на три ABI (Go из исходников + ядро ×3).
Добавление cronet может увеличить её кратно. F-Droid на это идёт, раз апстрим
там живёт, но нужно измерить: если один блок перестанет укладываться в лимиты
их раннеров, схему придётся менять.

**Проверить:** прогнать один ABI с cronet на ветке метаданных, замерить время.

### 2. Где живёт `build-naive`

Утилиты нет в нашем ядре — она в модуле `cronet-go`
(`cmd/build-naive`). Апстрим запускает её из srclib самого cronet-go, а не из
ядра. Значит нужен ещё один srclib и `$$cronet-go$$` в командах.

**Проверить:** какой коммит `cronet-go` соответствует версии в нашем `go.mod`
(сейчас `v0.0.0-20260731162621-4185d471b2e4`, у апстрима другой).

### 3. Достижима ли побайтовая воспроизводимость

Даже с naive сборки могут не совпасть. Известные расхождения:

| Что | GitHub | F-Droid |
|---|---|---|
| ABI-схема | `--split-per-abi` | три отдельных прогона |
| Проверка JDK в ядре | на месте | вырезана sed'ом |
| legacy-вариант AAR | собирается | вырезан sed'ом |
| Подпись | наш ключ | ключ F-Droid, пока не включён RB |

Первые три придётся свести к одному виду — то есть менять и **наш** CI, не
только метаданные. §379 уже требует убрать `--split-per-abi` на GitHub, что
закрывает первую строку.

Плюс общие для reproducible builds грабли: временные метки в архивах, пути
сборки, версия NDK, порядок файлов в APK. Проверяется только практикой —
`fdroid build` с флагом сравнения.

**Проверить:** после устранения известных расхождений прогнать их
верификацию и посмотреть на реальный diff.

## Что меняется

| Файл | Что |
|------|-----|
| метаданные F-Droid | srclib `cronet-go`, блок сборки cronet, убрать sed, вырезающий `with_naive_outbound` |
| метаданные F-Droid | `Binaries:` + `AllowedAPKSigningKeys:` — только после того, как сборки совпадут |
| `.github/workflows/ci.yml` | привести к тому же виду, что F-Droid (следствие §379) |
| ядро | возможно, вырезание JDK-проверки и legacy-AAR стоит перенести из sed'а в сам `build_libbox` под флагом |
| `docs/FDROID.md` | §3 «Что отличается» — таблица сократится |

### AllowedAPKSigningKeys

Отпечаток нашего ключа — `7987aec41d6521b56bdeec202e383edcff27963918b109b69791bf1f6636c1c4`
(`CN=BoxVPN, OU=Dev, O=Leadaxe`).

⚠️ **Решение необратимо.** Шаблон F-Droid прямо предупреждает: если
reproducible builds не включить сразу, APK подпишут их ключом, и включить
позже уже нельзя. Обратное тоже верно — заявив RB и не добившись совпадения,
получим бесконечно падающую верификацию.

## Что это даёт

- **Naive работает** у пользователей F-Droid — 12 протоколов вместо 11.
- **APK подписан нашим ключом.** Пользователь ставит сборку из F-Droid поверх
  APK с GitHub и наоборот, без удаления приложения. Сейчас это невозможно:
  разные подписи.
- **Доказательство соответствия.** Сторонний сборщик воспроизводит наш
  бинарник байт в байт — сильный аргумент для VPN-клиента, где вопрос доверия
  к бинарнику стоит острее обычного.

## Риски

- **Время сборки.** Может вырасти настолько, что F-Droid откажется собирать
  приложение в разумные сроки. Основной риск.
- **Необратимость RB.** См. выше.
- **Хрупкость.** Любое расхождение между нашим CI и их сборкой ломает
  верификацию. Придётся держать две сборки идентичными при каждом изменении.
- **Зависимость от апстрима.** `build-naive` живёт в `cronet-go`; смена его
  API сломает наш блок.

## Порядок работ

1. Дождаться вливания [!44731](https://gitlab.com/fdroid/fdroiddata/-/merge_requests/44731) — не менять схему под открытым ревью.
2. Реализовать [§379](379-version-code-from-version.md) — он убирает
   `--split-per-abi` и сводит схемы versionCode.
3. Вернуть naive: srclib `cronet-go` + блок сборки, **без** `Binaries`.
   Замерить время сборки. Если укладывается — идти дальше.
4. Свести остальные расхождения между нашим CI и F-Droid.
5. Прогнать верификацию, разобрать diff.
6. Только при совпадении — добавить `Binaries` + `AllowedAPKSigningKeys`.

Шаги 3 и 6 разделены намеренно: naive полезен сам по себе, даже если
reproducible builds не получатся.

## Проверка

1. В сборке F-Droid `libbox.aar` содержит тег `with_naive_outbound`.
2. `diff` собранного `libcronet.a` с prebuilt проходит для всех ABI.
3. Узел `naive://` работает в APK из каталога (device-verify).
4. `fdroid build --verify` подтверждает совпадение с APK из GitHub Release.
5. `apksigner verify --print-certs` на каталожном APK показывает `CN=BoxVPN`.
6. `install -r` APK из F-Droid поверх GitHub-сборки и обратно — проходит.

## Открытые вопросы

- Собирать ли cronet для всех трёх ABI сразу или ограничиться arm64, пока
  время сборки не измерено.
- Стоит ли переносить sed-правки ядра (JDK-гейт, legacy-AAR) в сам
  `build_libbox` под build-тег — это сделало бы обе сборки одинаковыми без
  внешних патчей.
- Universal-APK при reproducible builds: он собирается только на GitHub, а
  значит либо должен появиться в F-Droid, либо остаться вне верификации.
