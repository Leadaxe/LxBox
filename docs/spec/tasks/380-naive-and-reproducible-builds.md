## Проблема

В сборке F-Droid протокол **naive отключён**: build-тег `with_naive_outbound`
вырезается из `cmd/internal/build_libbox/main.go` прямо в метаданных. Причина
была в том, что он тянет `github.com/sagernet/cronet-go`, а тот поставляет
готовый `libcronet.a` (60.7–76.4 МБ на архитектуру: arm64 64.5, arm 76.4,
amd64 60.7, 386 66.8) — а prebuilt-бинарники в F-Droid запрещены.

Следствия:

1. **Пользователи F-Droid не получают naive.** Остальные 11 протоколов на
   месте, но узлы `naive://` в каталожной сборке работать не будут.
2. **Reproducible builds невозможны.** Сборка F-Droid намеренно отличается от
   APK с GitHub, значит побайтового совпадения не будет никогда, и APK
   подписывается ключом F-Droid, а не нашим (`7987aec4`, `CN=BoxVPN`).
   Пользователь не может перейти между каналами без удаления приложения.

**Вывод «naive невозможен» был неверным.** Апстрим `io.nekohasekai.sfa` держит
naive в каталоге F-Droid, собирая cronet из исходников. Рецепт из их
метаданных:

```
srclibs:
  - cronet-go@d9ea2601b3a8bd0b2c54ec5c515cb25dfc468dab
prebuild:
  - pushd $$cronet-go$$
  - for arch in arm arm64 386 amd64; do
      go run ./cmd/build-naive --target=android/$arch build;
      go run ./cmd/build-naive --target=android/$arch package --local;
      diff lib/android_$arch/libcronet.a \
           $GOMODCACHE/github.com/sagernet/cronet-go/lib/android_$arch@*/libcronet.a;
    done
  - popd
```

Логика: собрать `libcronet.a` самим, затем `diff` с prebuilt из модуля.
Совпало — значит бинарник соответствует исходникам, и prebuilt перестаёт быть
чёрным ящиком.

## Что выяснено (05.08.2026)

### `build-naive` есть, коммит наш — другой

Утилита живёт в модуле `cronet-go` (`cmd/build-naive`), не в нашем ядре.
Значит нужен отдельный srclib и `$$cronet-go$$` в командах — как у апстрима.
Таргеты `cmd.go`: android arm64/amd64/arm/386.

Версия в [`sing-box-lx/go.mod:37`](../../../../sing-box-lx/go.mod) —
`v0.0.0-20260731162621-4185d471b2e4`, полный хэш
`4185d471b2e46870521eaa8159776303a29297bf` (31.07.2026). Апстримовый рецепт
пинит `d9ea2601b3a8bd0b2c54ec5c515cb25dfc468dab` — **другой коммит**. Рецепт
переносится не дословно.

**Не учтено исходной спекой:** модули `lib/android_*` пинятся **отдельной**
псевдоверсией — `v0.0.0-20260731161755-38229fb700f6` (коммит `38229fb700f6`,
на 9 минут раньше основного). То есть `diff` сравнивает артефакты **двух
разных коммитов**; блок сборки должен это учитывать, иначе сравнение
развалится на ровном месте.

### Вырезание тега ядро уже умеет само

[`build_libbox/main.go:224-225`](../../../../sing-box-lx/cmd/internal/build_libbox/main.go)
собирает legacy-вариант через `legacyTags := filterTags(sharedTags,
"with_naive_outbound")`. Механизм отбрасывания тега **в ядре есть** — sed в
метаданных дублирует то, что `build_libbox` делает штатно. Это снимает
неопределённость открытого вопроса про перенос sed-правок: инфраструктура на
месте, нужен только флаг.

### Разбор метаданных SFA — три вопроса из четырёх сняты

Читать `metadata/io.nekohasekai.sfa.yml` в fdroiddata **до** любых вопросов
рецензентам: почти всё уже отвечено там.

**gomobile воспроизводим — доказательство от противного.** SFA публикуется с
`Binaries` и `AllowedAPKSigningKeys: 32250a4b5f3a…` — ключ **их**, не F-Droid.
Значит побайтового совпадения они добились, а их сборка гоняет
`make lib_install && make lib_android` на buildserver'е. Вывод: AAR из
gomobile воспроизводим при совпадении Go + NDK + путей. Опасение «два разных
прогона gomobile не сойдутся» снято.

**NDK пинится, и рецепт готовый.** У SFA версия вычитывается `sed`-ом из
`build.gradle.kts` самого проекта, затем `sdkmanager "ndk;$NDK_VERSION"` —
источник истины ОДИН с обеих сторон, пин получается автоматически. У нас тот
же источник (`flutter.ndkVersion`), надо просто читать его в метаданных.
`SOURCE_DATE_EPOCH` у них не фигурирует нигде. Go — srclib `go@go1.25.0`,
собирается из исходников (`./make.bash`).

**Время сборки Chromium приемлемо.** Прецедент в том же каталоге, те же 4 ABI.
CPU сверх 16 гасят явно: `export CPUS_MAX=16` + запись `0` в
`/sys/devices/system/cpu/cpu$c/online`. Спрашивать «выдержат ли раннеры» не
требуется.

**У SFA верифицируется только universal.** `binary:` в каждом блоке SFA
ссылается на `SFA-%v-foss-universal.apk` — один артефакт на версию. Per-ABI
сборки у них существуют, но под верификацию не заведены.

⚠️ Это факт про SFA, а не образец для нас: рецензент просил не ограничиваться
чужим охватом. Итог обсуждения — **три сплита без universal** (см. «Решено
05.08»): универсального блока в каталоге нет, а сплитов у нас три против
одного universal у SFA.

### Раздельная сборка AAR — правила F-Droid (проверено по докам 05.08)

Наш GitHub-CI **не собирает** `libbox.aar` — он скачивает готовый из релиза
форка ядра ([`fetch-libbox.sh`](../../../scripts/fetch-libbox.sh), пин
`libbox.version` + сверка SHA256). SFA компилирует AAR из исходников с обеих
сторон.

**Архитектурное требование юзера — сохранить раздельную сборку — выполнимо, но
не так, как казалось.** Проверка официальных доков дала однозначный ответ:

**1. Готовый AAR из наших GH Releases в рецепт F-Droid брать НЕЛЬЗЯ.**
Inclusion Policy: *«All binary dependencies including JAR files must originate
either from source compilation or Debian repository downloads»*. Список
разрешённых источников закрытый (Maven Central, Google Maven, Sonatype,
JitPack, Debian main…) — **GitHub Releases в нём нет**. Исключения «автор
собрал сам, публично, воспроизводимо» не существует ни в каком виде.
Подтверждено ответом мейнтейнера (Licaon_Kter) в форумном треде ровно про
pre-compiled AAR: отсылка к Inclusion Policy и встречное «why not?» на довод
«это нельзя собрать из исходников».

**2. Reproducible builds этого НЕ легализуют.** `Binaries` описывает **выход**
(с чем сравнить собранный APK), а не входы: *«If specified, F-Droid will
verify the output APK file of a build against the one specified»*. F-Droid всё
равно собирает APK по рецепту, и все входы обязаны быть из исходников.
Сравнение при этом побайтовое, за вычетом подписи: *«the APKs must be
completely identical before and after signing (apart from the signature)»*
(механизм [apksigcopier](https://github.com/obfusk/apksigcopier)).

**3. Прецеденты подтверждают.** SFA собирает `libbox.aar` в рецепте
(`srclibs: go@go1.25.0` + `./make.bash` + `make lib_android`), будучи монорепой
— готовый AAR не подсовывает. CalyxVPN жёстче: закоммиченный `obfsvpn.aar`
F-Droid удаляет через `scandelete` и пересобирает.

**Что это значит практически:**

- **Наш GitHub-CI не меняется.** Раздельная сборка остаётся как есть —
  F-Droid её не касается и не запрещает. `fetch-libbox.sh` продолжает качать
  готовый AAR для наших релизов.
- **Меняется только рецепт fdroiddata:** ядро подключается как
  `srclibs: sing-box-lx@<sha>` с пином на коммит, Go ставится из исходников,
  `libbox.aar` собирается на их buildserver'е и кладётся в `app/libs`.
- **Две стороны работают по-разному** — мы качаем, они собирают — и это
  штатно. Требование одно: чтобы AAR получился одинаковый.

**Запасной путь**, если сборка ядра в рецепте окажется неподъёмной: публиковать
AAR на **JitPack** — он в allowlist и собирает из наших исходников сам, а не
принимает загруженный бинарник.

**Нюанс к проверке:** сканер F-Droid, вероятно, забракует сам механизм
скачивания AAR по URL (у CalyxVPN он удалял даже закоммиченный в дерево файл).
То есть в рецепте `fetch-libbox.sh` придётся не перенаправить, а заменить
сборкой из srclib.

#### NDK: версии разошлись — сведено в ядре 05.08

Сверка показала **разные** версии:

| Где | Было | Формат |
|---|---|---|
| ядро, `lx-build.yml`/`lx-ci.yml`/`lx-release.yml` | `r28` = `28.0.13004108` | `nttld/setup-ndk` |
| приложение, `flutter.ndkVersion` | `28.2.13676358` | SDK-манагер |
| `sdk.go:51` `fixedVersion` | `28.0.13004108` | путь в `$ANDROID_SDK/ndk/` |

`r28c` и `28.2.13676358` — **одно и то же**, записанное в двух нотациях:
`nttld/setup-ndk` принимает только вид `r28c`, `sdkmanager` — только
`28.2.13676358`. Линейка: r28 → 28.0.x, r28b → 28.1.x, r28c → 28.2.x.

Почему это важно: NDK — это прежде всего clang (в r28 — clang 19.0.0,
подтверждено `strings` по `jni/arm64-v8a/libbox.so`). Разные версии clang дают
**разный машинный код** из одного исходника ⇒ разные байты в `libbox.so` ⇒
верификация падает. При этом приложение работает одинаково — расходится только
побайтовое сравнение.

**Сведено юзером 05.08:** в трёх lx-воркфлоу ядра проставлен `r28c`
(апстримовый `build.yml` не тронут). Теперь ядро и `flutter.ndkVersion`
указывают на одну версию, и рецепт F-Droid может вычитывать её из
`build.gradle.kts`, как это делает SFA.

⚠ **Остаточный рассинхрон:** `fixedVersion` в `sdk.go:51` по-прежнему
`28.0.13004108`. В нашем CI это не мешает — `ANDROID_NDK_HOME` от
`setup-ndk` перебивает жёсткий путь (ветка 2 в `findNDK()`). Но на
buildserver'е F-Droid NDK ставится через `sdkmanager` в
`$ANDROID_SDK/ndk/28.2.13676358` ⇒ сработает ветка 1 или 3, и `sdk.go:85`
выдаст «reproducibility warning: using NDK version … instead of …».
Проверить на первом прогоне `fdroid build`.

✅ Пин подтверждён прогоном 05.08: в логе `fdroid build`
`export NDK_VERSION=28.2.13676358` — рецепт вычитал ту же версию, что стоит
в ядре.

### Cronet СОБИРАЕТСЯ — проверено прогоном 05.08

Главный технический риск §380 снят на практике. Прогон рецепта на
buildserver'е F-Droid:

```
[3120/4975] CXX obj/base/base/...
[build] Build complete!
[build] Copied static library for android/arm
[build] Package complete!
```

Chromium из исходников собрался для `android/arm`, `libcronet.a` получен.
**~25 минут на одну ABI**, при четырёх ABI × четыре блока это часы — но
собирается, и `CPUS_MAX=16` работает.

**Две грабли, обе исправлены** (коммит `7554c981a`):

1. **Glob не раскрылся.** Дословный перенос рецепта SFA дал
   `diff: .../lib/android_arm@*/libcronet.a: No such file or directory` —
   fdroidserver прогоняет команды так, что `*` остаётся буквальным.
   Заменено на `find … -name "android_$arch@*" | head -1` + `cmp`, с
   `test -f` на существование эталона.
2. **Модуль с prebuilt ещё не скачан.** `$GOMODCACHE` заполняется в
   `make lib_install`, а блок cronet идёт до него ⇒ сверять было не с чем.
   Добавлен явный `go mod download` четырёх модулей `lib/android_*` перед
   блоком cronet.

**Четвёртая грабля — цикл по всем ABI в каждом блоке.** Дословный перенос
рецепта SFA (`for arch in arm arm64 386 amd64`) означал, что **каждый** из
четырёх build-блоков собирает Chromium под все четыре архитектуры: 16
полных сборок на релиз, ~7 часов машинного времени, причём большая часть
артефактов тут же выбрасывается — блоку нужен только свой ABI.

Сокращено по блокам (коммит `ae79a4ebc`):

| Блок | versionCode | ABI cronet |
|---|---|---|
| armeabi-v7a | 22000501 | `arm` |
| arm64-v8a | 22000502 | `arm64` |
| x86_64 | 22000504 | `amd64` |

**6 сборок вместо 16** — примерно 2,5 часа вместо 7. `go mod download`
сужен так же: качаются только те `lib/android_*`, с которыми блок будет
сверяться. Архитектура `386` не собирается вообще — 32-битный x86 мы не
публикуем.

**Третья грабля — лог.** Одна ABI генерирует столько вывода ninja, что
пробивает лимит GitLab в 4 МБ:

```
Job's log exceeded limit of 4194304 bytes.
Job execution will continue but no more output will be collected.
```

Обрезается ровно на месте падения — читать ошибку нечем. Вывод
`build-naive` заглушен в `/dev/null`.

### Хвосты §382 в рецепте: build-id и NDK 27 против r28c

Замена сканера на `flutter_zxing` ([§382](382-foss-qr-scanner.md)) снимает
блокер ML Kit, но тянет в §380 две вещи.

**1. Линкерный build-id — обязательная строка в рецепте** (коммит
`27dbf8a14`). `flutter_zxing` собирает ZXing-C++ через CMake, линкер
штампует в `.so` уникальный build-id, и два прогона одного исходника
расходятся — верификация падала бы, не начавшись:

```
sed -i -e '1a add_link_options("LINKER:--build-id=none")' \
  $PUB_CACHE/hosted/pub.dev/flutter_zxing-*/src/CMakeLists.txt
```

Путь сверен по [`android/build.gradle:34`](file:///Users/macbook/.pub-cache/hosted/pub.dev/flutter_zxing-2.3.0/android/build.gradle)
пакета — `externalNativeBuild` указывает на `../src/CMakeLists.txt`. Та же
строка стоит в 38 других рецептах каталога.

Это единственный постоянный хвост сопровождения от §382: живёт **в
метаданных**, не в репозитории, и при бампе пакета его надо помнить. Glob
`flutter_zxing-*` написан ровно ради переживания обновлений.

**2. NDK-расхождение — разрешается само, но проверить прогоном.**
[`flutter_zxing-2.3.0/android/build.gradle:30`](file:///Users/macbook/.pub-cache/hosted/pub.dev/flutter_zxing-2.3.0/android/build.gradle)
жёстко объявляет `ndkVersion "27.0.12077973"`, тогда как §380 свёл проект к
`28.2.13676358` (r28c).

Конфликта быть не должно: Flutter берёт **максимум** из версий проекта и
всех плагинов и подставляет его всем
([`FlutterPluginUtils.kt:516-547`](../../../../flutter-sdk/packages/flutter_tools/gradle/src/main/kotlin/FlutterPluginUtils.kt),
`maxPluginNdkVersion`). `28.2.13676358` > `27.0.12077973`, побеждает наш.

⚠ Но рецепт F-Droid ставит `sdkmanager`-ом **только** версию из
`FlutterExtension.kt`. Если Gradle почему-либо попросит 27.0.x, на
buildserver'е его не окажется и сборка упадёт. По логике `maxPluginNdkVersion`
не попросит — проверяется первым прогоном со сканером.

### Блокер: `mobile_scanner` не проходит в F-Droid (§375) — СНЯТ §382

⚠ Уточнение к порядку: этот блокер выявлен на прогоне **до** добавления
cronet. В рецепте с cronet сборка падает раньше — на самом cronet-блоке, —
поэтому до `flutter build apk` и `mobile_scanner` дело пока не доходит.
Блокер никуда не делся, просто всплывёт следующим.

Падает финальный `flutter build apk`:

```
A problem occurred configuring project ':mobile_scanner'.
> Failed to notify project evaluation listener.
   > java.lang.NullPointerException (no error message)
```

**Причина.** Сканер fdroidserver вырезает из
`mobile_scanner-7.4.0/android/build.gradle` проприетарные зависимости:

```
Removing usual suspect 'com.google.android.gms(...)'
Removing usual suspect 'com.google.mlkit'
```

`useUnbundled` по умолчанию `false` ⇒ плагин тянет
`com.google.mlkit:barcode-scanning` — бандленный ML Kit. В F-Droid он
запрещён при любых настройках, это не чинится флагами.

Сам NPE, судя по коду плагина, бьёт на строке 32 его `build.gradle`:

```groovy
def agpMajor = Version.ANDROID_GRADLE_PLUGIN_VERSION.tokenize('.')[0] as int
```

после вырезания `buildscript`-зависимостей `com.android.Version` не
резолвится ⇒ `null.tokenize()`. Подтверждается прогоном с `--stacktrace`.

⚠ **Ложный след, на который я потратил время:** Gradle после падения печатает
блок «Flutter Fix» про AGP 9 и `android.newDsl`. Это эвристическая подсказка,
которая выводится после ЛЮБОГО падения Gradle, а не диагноз — **версии AGP в
логе нет вообще**. Диагностировать по ней нельзя; нужен `--stacktrace` и
строка `What went wrong`.

**Как это решают в каталоге** (прецеденты в fdroiddata):
- `com.nfcarchiver.banana_split`: `sed -i -e '/mobile_scanner/d' pubspec.yaml`
- `info.zverev.ilya.every_door`: то же самое через маркер `#f` в pubspec
- `com.rogeriodocarmo.miroji`: патч, вырезающий ML Kit из expo-camera

То есть все просто **выбрасывают пакет** из сборки F-Droid.

**Наш случай.** У нас `mobile_scanner` импортируется ровно в одном месте —
[`qr_scan_screen.dart`](../../../app/lib/screens/qr_scan_screen.dart) (182
строки), наружу отдаётся `sealed class ScanOutcome`, единственная точка входа
— кнопка в `subscriptions_screen.dart:283`. Границы чистые, подмена
локальная.

Варианты (решение за §375, не за §380):
1. **FOSS-сканер** (ZXing-based) вместо ML Kit — одинаково в обеих сборках,
   расхождений для RB нет. Правит приложение.
2. **Выбросить пакет в рецепте F-Droid** по образцу каталога — но тогда нужна
   заглушка экрана, иначе Dart не соберётся, и появляется расхождение сборок,
   что противоречит цели §380.

Для reproducible builds годится только (1): при (2) APK различаются
функционалом и побайтово никогда не совпадут.

**Кандидат на замену — `flutter_zxing`.** 38 упоминаний в fdroiddata, самый
ходовой FOSS-сканер для Flutter (`business.braid.polycule`,
`com.anywherelan.awl`, `com.reloado.auth`, `eu.heili.wormhole` и др.).

⚠ Грабля, которую они уже решили за нас: `flutter_zxing` собирает нативную
часть через CMake, и линкер вшивает уникальный **build-id** ⇒ байты
расходятся между прогонами. Лечится строкой в prebuild:

```
sed -i -e '1a add_link_options("LINKER:--build-id=none")' \
  $PUB_CACHE/hosted/pub.dev/flutter_zxing-*/*/CMakeLists.txt
```

Это ровно тот класс расхождений, ради которых §380 и затевался: пакет
работает, приложение собирается, но воспроизводимость ломается на уровне
линкера. При переходе на `flutter_zxing` строку надо взять сразу.

### AllowedAPKSigningKeys

Отпечаток нашего ключа — `7987aec41d6521b56bdeec202e383edcff27963918b109b69791bf1f6636c1c4`
(`CN=BoxVPN, OU=Dev, O=Leadaxe`).

⚠️ **Решение необратимо.** Шаблон F-Droid прямо предупреждает: если

позже уже нельзя. Обратное тоже верно — заявив RB и не добившись совпадения,

## Что это даёт

- **Naive работает** у пользователей F-Droid — 12 протоколов вместо 11.
- **APK подписан нашим ключом.** Пользователь ставит сборку из F-Droid поверх
  APK с GitHub и наоборот, без удаления приложения. Сейчас это невозможно:
  разные подписи.
- **Доказательство соответствия.** Сторонний сборщик воспроизводит наш
  бинарник байт в байт — сильный аргумент для VPN-клиента, где вопрос доверия
  к бинарнику стоит острее обычного.

## Риски

- **Детерминизм gomobile — остаётся главным.** Правила F-Droid проверены,
  путь известен; неизвестно одно: сойдутся ли байты AAR, собранного нашим CI
  ядра и их buildserver'ом. Если нет — RB недостижим, никакие правки
  метаданных этого не обойдут. Проверяется экспериментом, не перепиской.
- **Время сборки.** cronet = сборка Chromium. Три сплита — три
  прогона на релиз. Прецедент SFA (`CPUS_MAX=16`) показывает, что это в
  принципе терпимо, но у них 4 ABI без нашего четвёртого блока.
- **Необратимость RB.** `AllowedAPKSigningKeys` должен попасть **до** мержа
  MR — после уже нельзя. Заявив RB и не добившись совпадения, получим
  бесконечно падающую верификацию.
- **Хрупкость.** Любое расхождение между сборкой ядра и их рецептом ломает
  верификацию. Держать синхронными пины Go/NDK при каждом бампе.
- **Зависимость от апстрима.** `build-naive` живёт в `cronet-go`; смена его
  API сломает наш блок. Наш коммит уже разошёлся с апстримовым рецептом.

## Проверка

1. В сборке F-Droid `libbox.aar` содержит тег `with_naive_outbound`.
2. `diff` собранного `libcronet.a` с prebuilt проходит для всех ABI.
3. Узел `naive://` работает в APK из каталога (device-verify).
4. `fdroid build --verify` подтверждает совпадение с APK из GitHub Release —
   для трёх сплитов (universal вне верификации — публикуется только на GitHub).
5. `apksigner verify --print-certs` на каталожном APK показывает `CN=BoxVPN`.
6. `install -r` APK из F-Droid поверх GitHub-сборки и обратно — проходит.

## Решено 05.08.2026

- **Три ABI-сплита, universal НЕ собираем.** Итоговое решение после трёх
  итераций (коммиты `ae79a4ebc` → `aac6415c1`).

  Ход рассуждения: сначала universal планировался четвёртым блоком «чтобы ни
  один артефакт не остался вне верификации», и рецензент это поддерживал
  ([licaon-kter, 05.08](https://gitlab.com/fdroid/fdroiddata/-/merge_requests/44731)):
  «yes, check with an universal APK, but the goal, imho, should be split abi».
  Но с возвратом naive цена изменилась: **каждый блок компилирует Chromium**,
  и fat-блоку нужно три таких прогона — ради артефакта, который каталог всё
  равно не раздаёт (F-Droid отдаёт устройству подходящий сплит).

  Universal остаётся публиковаться на GitHub и **вне верификации**.
  Три прогона Chromium на релиз вместо шести.
- **cronet собирается только под ABI своего блока**, а не под все четыре, как
  в дословном рецепте SFA. Иначе было бы 16 сборок Chromium на релиз (~7
  часов) при трёх реально нужных. `386` не собирается вовсе — 32-битный x86
  не публикуем.
- **sed-правки переносим в `build_libbox` под флаг.** Вопрос снят находкой:
  `filterTags` в ядре уже вырезает `with_naive_outbound` для legacy-варианта —
  механизм есть, нужен только флаг.

### Блокирующий

~~Детерминирован ли `libbox.aar`~~ — **закрыт 05.08 экспериментом**, см.
«Детерминизм AAR». Блокирующих вопросов не осталось.

рецензентам, а прогон `fdroid build` после шага 4.

### Важные

- **Когда переоткрывать тред про `Binaries`** — сейчас или после того, как
  сборки сойдутся. Аргумент за «сейчас»: `AllowedAPKSigningKeys` необратим и
  после мержа MR не добавляется. Аргумент за «после»: заявить RB и не добиться
  совпадения — получить бесконечно падающую верификацию.
- **Не забракует ли сканер F-Droid механизм получения AAR.** У CalyxVPN
  `scandelete` удалял даже закоммиченный в дерево `.aar`. Наш рецепт после
  перехода на `srclibs` prebuilt не тянет, но проверить на первом же прогоне.

### Второстепенные

- Какую версию NDK пинить и не сломает ли пин текущую сборку — сейчас
  наследуется `flutter.ndkVersion` на обеих сторонах.
- Нужно ли синхронизировать `go.version` ядра (`go1.25.12`) с тем, что
  доступно в Debian trixie их buildserver'а через bootstrap-Go.
- Разошедшиеся псевдоверсии `cronet-go` и `cronet-go/lib/*` — держать ли их
  синхронными при будущих бампах или достаточно фиксировать обе в метаданных.
