# §380 — вернуть naive в сборку F-Droid и включить reproducible builds

| Поле | Значение |
|------|----------|
| Статус | Спека |

## Проблема

В сборке F-Droid протокол **naive отключён**: build-тег `with_naive_outbound`
вырезается из `cmd/internal/build_libbox/main.go` прямо в метаданных. Причина
была в том, что он тянет `github.com/sagernet/cronet-go`, а тот поставляет
готовый `libcronet.a` (60.7–76.4 МБ на архитектуру: arm64 64.5, arm 76.4,
amd64 60.7, 386 66.8) — а prebuilt-бинарники в F-Droid запрещены.

Следствия:

1. **Пользователи F-Droid не получают naive.** Остальные 11 протоколов на
   месте, но узлы `naive://` в каталожной сборке работать не будут.
2. **Reproducible builds невозможны.** Сборка F-Droid намеренно отличается от
   APK с GitHub, значит побайтового совпадения не будет никогда, и APK
   подписывается ключом F-Droid, а не нашим (`7987aec4`, `CN=BoxVPN`).
   Пользователь не может перейти между каналами без удаления приложения.

**Вывод «naive невозможен» был неверным.** Апстрим `io.nekohasekai.sfa` держит
naive в каталоге F-Droid, собирая cronet из исходников. Рецепт из их
метаданных:

```
srclibs:
  - cronet-go@d9ea2601b3a8bd0b2c54ec5c515cb25dfc468dab
prebuild:
  - pushd $$cronet-go$$
  - for arch in arm arm64 386 amd64; do
      go run ./cmd/build-naive --target=android/$arch build;
      go run ./cmd/build-naive --target=android/$arch package --local;
      diff lib/android_$arch/libcronet.a \
           $GOMODCACHE/github.com/sagernet/cronet-go/lib/android_$arch@*/libcronet.a;
    done
  - popd
```

Логика: собрать `libcronet.a` самим, затем `diff` с prebuilt из модуля.
Совпало — значит бинарник соответствует исходникам, и prebuilt перестаёт быть
чёрным ящиком.

## Что выяснено (05.08.2026)

### `build-naive` есть, коммит наш — другой

Утилита живёт в модуле `cronet-go` (`cmd/build-naive`), не в нашем ядре.
Значит нужен отдельный srclib и `$$cronet-go$$` в командах — как у апстрима.
Таргеты `cmd.go`: android arm64/amd64/arm/386.

Версия в [`sing-box-lx/go.mod:37`](../../../../sing-box-lx/go.mod) —
`v0.0.0-20260731162621-4185d471b2e4`, полный хэш
`4185d471b2e46870521eaa8159776303a29297bf` (31.07.2026). Апстримовый рецепт
пинит `d9ea2601b3a8bd0b2c54ec5c515cb25dfc468dab` — **другой коммит**. Рецепт
переносится не дословно.

**Не учтено исходной спекой:** модули `lib/android_*` пинятся **отдельной**
псевдоверсией — `v0.0.0-20260731161755-38229fb700f6` (коммит `38229fb700f6`,
на 9 минут раньше основного). То есть `diff` сравнивает артефакты **двух
разных коммитов**; блок сборки должен это учитывать, иначе сравнение
развалится на ровном месте.

### Вырезание тега ядро уже умеет само

[`build_libbox/main.go:224-225`](../../../../sing-box-lx/cmd/internal/build_libbox/main.go)
собирает legacy-вариант через `legacyTags := filterTags(sharedTags,
"with_naive_outbound")`. Механизм отбрасывания тега **в ядре есть** — sed в
метаданных дублирует то, что `build_libbox` делает штатно. Это снимает
неопределённость открытого вопроса про перенос sed-правок: инфраструктура на
месте, нужен только флаг.

### Расхождения GitHub ↔ F-Droid — актуальный список

### Разбор метаданных SFA — три вопроса из четырёх сняты

Читать `metadata/io.nekohasekai.sfa.yml` в fdroiddata **до** любых вопросов
рецензентам: почти всё уже отвечено там.

**gomobile воспроизводим — доказательство от противного.** SFA публикуется с
`Binaries` и `AllowedAPKSigningKeys: 32250a4b5f3a…` — ключ **их**, не F-Droid.
Значит побайтового совпадения они добились, а их сборка гоняет
`make lib_install && make lib_android` на buildserver'е. Вывод: AAR из
gomobile воспроизводим при совпадении Go + NDK + путей. Опасение «два разных
прогона gomobile не сойдутся» снято.

**NDK пинится, и рецепт готовый.** У SFA версия вычитывается `sed`-ом из
`build.gradle.kts` самого проекта, затем `sdkmanager "ndk;$NDK_VERSION"` —
источник истины ОДИН с обеих сторон, пин получается автоматически. У нас тот
же источник (`flutter.ndkVersion`), надо просто читать его в метаданных.
`SOURCE_DATE_EPOCH` у них не фигурирует нигде. Go — srclib `go@go1.25.0`,
собирается из исходников (`./make.bash`).

**Время сборки Chromium приемлемо.** Прецедент в том же каталоге, те же 4 ABI.
CPU сверх 16 гасят явно: `export CPUS_MAX=16` + запись `0` в
`/sys/devices/system/cpu/cpu$c/online`. Спрашивать «выдержат ли раннеры» не
требуется.

**У SFA верифицируется только universal.** `binary:` в каждом блоке SFA
ссылается на `SFA-%v-foss-universal.apk` — один артефакт на версию. Per-ABI
сборки у них существуют, но под верификацию не заведены.

⚠️ Это факт про SFA, а не образец для нас: рецензент прямо сказал не
ограничиваться чужим охватом (см. «Решено 05.08»). Мы верифицируем все четыре
артефакта.

### Раздельная сборка AAR — правила F-Droid (проверено по докам 05.08)

Наш GitHub-CI **не собирает** `libbox.aar` — он скачивает готовый из релиза
форка ядра ([`fetch-libbox.sh`](../../../scripts/fetch-libbox.sh), пин
`libbox.version` + сверка SHA256). SFA компилирует AAR из исходников с обеих
сторон.

**Архитектурное требование юзера — сохранить раздельную сборку — выполнимо, но
не так, как казалось.** Проверка официальных доков дала однозначный ответ:

**1. Готовый AAR из наших GH Releases в рецепт F-Droid брать НЕЛЬЗЯ.**
Inclusion Policy: *«All binary dependencies including JAR files must originate
either from source compilation or Debian repository downloads»*. Список
разрешённых источников закрытый (Maven Central, Google Maven, Sonatype,
JitPack, Debian main…) — **GitHub Releases в нём нет**. Исключения «автор
собрал сам, публично, воспроизводимо» не существует ни в каком виде.
Подтверждено ответом мейнтейнера (Licaon_Kter) в форумном треде ровно про
pre-compiled AAR: отсылка к Inclusion Policy и встречное «why not?» на довод
«это нельзя собрать из исходников».

**2. Reproducible builds этого НЕ легализуют.** `Binaries` описывает **выход**
(с чем сравнить собранный APK), а не входы: *«If specified, F-Droid will
verify the output APK file of a build against the one specified»*. F-Droid всё
равно собирает APK по рецепту, и все входы обязаны быть из исходников.
Сравнение при этом побайтовое, за вычетом подписи: *«the APKs must be
completely identical before and after signing (apart from the signature)»*
(механизм [apksigcopier](https://github.com/obfusk/apksigcopier)).

**3. Прецеденты подтверждают.** SFA собирает `libbox.aar` в рецепте
(`srclibs: go@go1.25.0` + `./make.bash` + `make lib_android`), будучи монорепой
— готовый AAR не подсовывает. CalyxVPN жёстче: закоммиченный `obfsvpn.aar`
F-Droid удаляет через `scandelete` и пересобирает.

**Что это значит практически:**

- **Наш GitHub-CI не меняется.** Раздельная сборка остаётся как есть —
  F-Droid её не касается и не запрещает. `fetch-libbox.sh` продолжает качать
  готовый AAR для наших релизов.
- **Меняется только рецепт fdroiddata:** ядро подключается как
  `srclibs: sing-box-lx@<sha>` с пином на коммит, Go ставится из исходников,
  `libbox.aar` собирается на их buildserver'е и кладётся в `app/libs`.
- **Две стороны работают по-разному** — мы качаем, они собирают — и это
  штатно. Требование одно: чтобы AAR получился одинаковый.

**Запасной путь**, если сборка ядра в рецепте окажется неподъёмной: публиковать
AAR на **JitPack** — он в allowlist и собирает из наших исходников сам, а не
принимает загруженный бинарник.

**Нюанс к проверке:** сканер F-Droid, вероятно, забракует сам механизм
скачивания AAR по URL (у CalyxVPN он удалял даже закоммиченный в дерево файл).
То есть в рецепте `fetch-libbox.sh` придётся не перенаправить, а заменить
сборкой из srclib.

**Эксперимент с детерминизмом всё равно нужен** — но уже не как «разрешат ли»,
а как «сойдутся ли байты»: собрать AAR дважды независимо и сравнить SHA256.
Локально невозможно (нет Android SDK/NDK) ⇒ только через CI ядра.

| Файл | Что |

| метаданные F-Droid | srclib `cronet-go` (наш коммит `4185d471b2e4`, `lib/*` — `38229fb700f6`), блок сборки cronet, убрать sed, вырезающий `with_naive_outbound` |
| метаданные F-Droid | **четвёртый build-блок — universal** (пустой ABI-фильтр, versionCode с ABI=0) |
| метаданные F-Droid | пин NDK по рецепту SFA: `sed` из `build.gradle.kts` + `sdkmanager "ndk;$NDK_VERSION"` |
| метаданные F-Droid | `Binaries:` + `AllowedAPKSigningKeys:` — только после того, как сборки совпадут |
| ядро (CI релиза) | **детерминизм сборки AAR**: пин Go и NDK, `-trimpath`, без абсолютных путей. Наш CI приложения при этом НЕ меняется |
| ядро | вырезание JDK-проверки и legacy-AAR перенести из sed'а в `build_libbox` под флагом — `filterTags` уже есть |

**`.github/workflows/ci.yml` — НЕ меняется.** Раздельная сборка сохраняется:
наш CI продолжает качать готовый AAR через `fetch-libbox.sh`. F-Droid этого не
касается; расхождение в способе получения AAR допустимо, требование только к
результату.

### AllowedAPKSigningKeys

Отпечаток нашего ключа — `7987aec41d6521b56bdeec202e383edcff27963918b109b69791bf1f6636c1c4`
(`CN=BoxVPN, OU=Dev, O=Leadaxe`).

⚠️ **Решение необратимо.** Шаблон F-Droid прямо предупреждает: если
reproducible builds не включить сразу, APK подпишут их ключом, и включить
позже уже нельзя. Обратное тоже верно — заявив RB и не добившись совпадения,
получим бесконечно падающую верификацию.

## Что это даёт

- **Naive работает** у пользователей F-Droid — 12 протоколов вместо 11.
- **APK подписан нашим ключом.** Пользователь ставит сборку из F-Droid поверх
  APK с GitHub и наоборот, без удаления приложения. Сейчас это невозможно:
  разные подписи.
- **Доказательство соответствия.** Сторонний сборщик воспроизводит наш
  бинарник байт в байт — сильный аргумент для VPN-клиента, где вопрос доверия
  к бинарнику стоит острее обычного.

## Риски

- **Детерминизм gomobile — остаётся главным.** Правила F-Droid проверены,
  путь известен; неизвестно одно: сойдутся ли байты AAR, собранного нашим CI
  ядра и их buildserver'ом. Если нет — RB недостижим, никакие правки
  метаданных этого не обойдут. Проверяется экспериментом, не перепиской.
- **Время сборки.** cronet = сборка Chromium. Все ABI плюс universal — четыре
  прогона на релиз. Прецедент SFA (`CPUS_MAX=16`) показывает, что это в
  принципе терпимо, но у них 4 ABI без нашего четвёртого блока.
- **Необратимость RB.** `AllowedAPKSigningKeys` должен попасть **до** мержа
  MR — после уже нельзя. Заявив RB и не добившись совпадения, получим
  бесконечно падающую верификацию.
- **Хрупкость.** Любое расхождение между сборкой ядра и их рецептом ломает
  верификацию. Держать синхронными пины Go/NDK при каждом бампе.
- **Зависимость от апстрима.** `build-naive` живёт в `cronet-go`; смена его
  API сломает наш блок. Наш коммит уже разошёлся с апстримовым рецептом.

## Порядок работ

1. ~~Реализовать §379~~ — **сделано**, коммит `862ac03e`, тег `v2.20.0`.
2. ~~Выяснить правила F-Droid по prebuilt-входам~~ — **сделано 05.08**,
   см. «Раздельная сборка AAR». Ответ: готовый AAR из GH Releases в рецепт
   брать нельзя, ядро подключается как `srclibs`.
3. **Эксперимент с детерминизмом AAR** — два независимых прогона сборки ядра,
   сравнить SHA256. Не зависит ни от чего остального; делать первым, потому
   что отрицательный результат обесценивает шаги 5–7.
4. Перевести рецепт fdroiddata на `srclibs: sing-box-lx@<sha>` вместо
   скачивания AAR. Пин NDK по рецепту SFA. Проверить, что сканер не бракует.
5. Вернуть naive: srclib `cronet-go` + блок сборки, **без** `Binaries`.
   Замерить время сборки на всех ABI. Если укладывается — идти дальше.
6. Свести остаток: sed-правки под флаг, четвёртый блок для universal.
   Прогнать верификацию, разобрать diff.
7. Только при совпадении — добавить `Binaries` + `AllowedAPKSigningKeys`,
   до мержа MR.

Шаги 5 и 7 разделены намеренно: naive полезен сам по себе, даже если
reproducible builds не получатся.

## Проверка

1. В сборке F-Droid `libbox.aar` содержит тег `with_naive_outbound`.
2. `diff` собранного `libcronet.a` с prebuilt проходит для всех ABI.
3. Узел `naive://` работает в APK из каталога (device-verify).
4. `fdroid build --verify` подтверждает совпадение с APK из GitHub Release —
   для **всех четырёх** артефактов, включая universal.
5. `apksigner verify --print-certs` на каталожном APK показывает `CN=BoxVPN`.
6. `install -r` APK из F-Droid поверх GitHub-сборки и обратно — проходит.

## Решено 05.08.2026

- **cronet собираем для всех ABI сразу**, не начиная с одного arm64. Размен
  осознанный: первый прогон длиннее, зато замер сразу даёт настоящую цифру для
  метаданных, а не оценку умножением.
- **Universal-APK идёт в F-Droid** четвёртым build-блоком. Все опубликованные
  артефакты попадают под верификацию, ни один не остаётся вне контура доверия.
  Цена: +1 прогон cronet на релиз и fat APK ~75 МБ в каталоге.

  Подтверждено рецензентом
  ([licaon-kter, 05.08](https://gitlab.com/fdroid/fdroiddata/-/merge_requests/44731)):
  на предложение ограничиться одним universal, как делает sfa, ответ —
  «yes, check with an universal APK, but the goal, imho, should be split abi».
  То есть universal идёт **вдобавок** к трём сплитам, а не вместо них;
  копировать чужой охват не требуется.
- **sed-правки переносим в `build_libbox` под флаг.** Вопрос снят находкой:
  `filterTags` в ядре уже вырезает `with_naive_outbound` для legacy-варианта —
  механизм есть, нужен только флаг.

## Открытые вопросы

### Блокирующий

- **Детерминирован ли `libbox.aar`, собранный gomobile?** Спрашивать
  рецензентов больше не нужно — вопрос решается экспериментом (шаг 3).
  Известно: у SFA рабочий `AllowedAPKSigningKeys` при сборке AAR на
  buildserver'е ⇒ в принципе воспроизводимо. Неизвестно: сойдётся ли **наш**
  прогон с их. **От этого зависит выполнимость RB целиком.**

  Переписка тут не поможет: первая попытка спросить дала «you'll have to
  rephrase, we compare our CI output with your output» — то есть сравниваются
  APK, а про детерминизм AAR ответа нет и не будет. Мерить самим.

### Важные

- **Когда переоткрывать тред про `Binaries`** — сейчас или после того, как
  сборки сойдутся. Аргумент за «сейчас»: `AllowedAPKSigningKeys` необратим и
  после мержа MR не добавляется. Аргумент за «после»: заявить RB и не добиться
  совпадения — получить бесконечно падающую верификацию.
- **Не забракует ли сканер F-Droid механизм получения AAR.** У CalyxVPN
  `scandelete` удалял даже закоммиченный в дерево `.aar`. Наш рецепт после
  перехода на `srclibs` prebuilt не тянет, но проверить на первом же прогоне.

### Второстепенные

- Какую версию NDK пинить и не сломает ли пин текущую сборку — сейчас
  наследуется `flutter.ndkVersion` на обеих сторонах.
