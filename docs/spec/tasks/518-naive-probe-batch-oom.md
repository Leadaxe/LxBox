Часть **D** разбора темы на 4PDA: «приложение падает, когда жму Проверка на
всех серверах» у пользователя с naive-узлами. Сервера для репро нет,
подтверждения на устройстве нет — фикс по механизму.

---

## Проблема

`Test servers` (§236/§296) собирал **ВСЕ** узлы списка в ОДИН probe-конфиг и
поднимал его одним `probeStart`. Конкурентность 6 (`ProbeRunner._concurrency`)
относилась только к `urlTest`-запросам поверх уже поднятого конфига, не к числу
поднятых узлов.

У naive это несоразмерно дорого. Инициализация записи в конфиге создаёт полный
сетевой стек Chromium:

- `sing-box-lx/protocol/naive/outbound.go` — `cronet.NewNaiveClient(...)` на
  **каждый** naive-outbound при разборе конфига;
- там же `Start()` → `h.client.Start()`;
- `cronet-go@v0.0.0-20260912104727-0d28acc44093/naive_client.go:341-347`:

  ```go
  engineCount := 1
  if c.concurrency > 1 && !c.singleEngine {
      engineCount = c.concurrency
  }
  for i := 0; i < engineCount; i++ {
      engine, startError = c.startEngine(tcpDialer, udpDialer, dnsServerAddress)
  ```

  `singleEngine` = `TestForceSingleEngine || runtime.GOOS == "ios"` — на Android
  он всегда `false`, то есть страховки нет.

Итого **один Chromium-движок на каждый naive-узел**, а при
`insecure_concurrency > 1` — ещё и умноженный на concurrency. Папка или
подписка с десятком naive-узлов поднимала десяток Chromium-стеков
одновременно, в **том же процессе, что UI** (`ProbeSession` — не отдельный
процесс: command.sock живёт в глобальном basePath, один `Libbox.setup` на
процесс, `ProbeSession.kt`). При `SetupOptions.oomMemoryLimit` (§173/§271;
«auto» — 200 МБ ниже 3.5 GiB RAM, 384 МБ ниже 7 GiB, иначе 512 МБ; Go
soft-limit = 3/4 от лимита, `setup.go`) это профиль OOM: снаружи «падает
приложение».

Что **не** является причиной (проверено, чтобы не искать снова):

- «в probe-процессе нет libcronet» — процесс один, библиотека та же
  (`sing-box-lx/README.md`, `LX_TAGS` содержит `with_naive_outbound`;
  `docs/KERNEL.md` перечисляет его для нашего `libbox.aar`);
- `applyTlsFragment` (§270, naive отвергает `fragment` fatal) — probe-конфиг
  строится из `node.getEntries(null)` в обход post-step'ов, и это была бы
  ошибка старта, не падение;
- F-Droid-сборка (тег вырезан, §380) даёт warning, а не падение.

## Фикс

### Гейт: не больше `kProbeMaxNaivePerConfig` naive на конфиг

`app/lib/services/probe/probe_config.dart`:

- `kProbeMaxNaivePerConfig = 1` — константа с обоснованием в комментарии.
  Единица, а не 2-4 из первичной оценки: замера RSS одного движка на живом
  naive-узле нет, а цена консервативного значения — только время прогона.
  Поднимать имеет смысл **только** по такому замеру.
- новый `buildProbeBatches(List<NodeSpec?>) → List<ProbeConfig>` — раскладывает
  узлы на конфиги. Не-naive узлы целиком лежат в **первом** батче (как до
  §518 — один конфиг на весь список); каждый naive-узел сверх лимита уезжает
  в свой батч. Вердикты битых/групп/Tailscale лежат в первом батче, чтобы
  вызывающий отдал их один раз.
- `buildProbeConfig` сохранён как `buildProbeBatches(...).firstOrNull ?? …`:
  §392 (`node_diagnostics_runner.dart`) тестирует ОДИН узел и батчирования не
  требует, его вызов не изменился.

Гейт считает **записи** (`outbound.type == 'naive'`), а не Dart-типы узлов:
детур-цепочка узла (`raw.detours`) уходит в тот же конфиг и тоже может быть
naive, а её Dart-тип виден только обходом `chained`. Узел с naive-детуром
неделим — он один и уходит в единственный батч (гейт не может разорвать
цепочку; это принятое исключение, тест его фиксирует).

### Прогон: батчи последовательно, `probeStop` после каждого

`app/lib/services/probe/probe_runner.dart` — `run()` итерирует батчи. На каждый
свой `probeStart` … `probeStop`; `ProbeSession.start` поверх живой сессии — это
рестарт (`ProbeSession.kt`), так что движки предыдущего батча освобождаются до
старта следующего. Гасить сессию только в конце sweep'а нельзя — гейт тогда не
даёт ничего.

Внутри батча узлы идут в исходном порядке (группы сортируются по индексу):
`allocate` уникализирует конфликтующие теги по порядку обхода (`Alpha`,
`Alpha-2`), и без сортировки подсадка не-naive в начало первого батча перевесила
бы, какой из двух одноимённых узлов получит суффикс. Тег каждого узла при этом
остаётся стабильным относительно того, что было до §518, — тест это фиксирует.
Побочно: `usedTags` у батчей независим, поэтому одноимённые naive-узлы,
разъехавшиеся по разным батчам, получают одинаковый базовый тег — это безвредно,
теги адресуются внутри своей сессии.

Инварианты сохранены: порядок индексов, полнота (каждый узел проверяется ровно
один раз), маркер `kProbeVpnRunning`, кооперативная отмена §286 (проверяется
перед каждым батчем), вердикты до ядра. Без naive батч один и прогон дословно
как до §518.

Все вызывающие идут через `ProbeRunner.run` и получают батчирование даром:

- «Проверка на всех серверах» — `folder_detail_screen.dart:311`,
  `subscription_detail_screen.dart:300` (через `ProbeController`);
- Debug API `probe` (§349) — `services/debug/handlers/folders.dart:425`;
- §392 диагностика узла — один узел, `buildProbeConfig`, батч всегда один.

Страховка Start (§478 `core_reject`) probe-конфиг **не** строит — она разбирает
ошибку боевого старта, отдельного пути к правке там нет.

### `insecure_concurrency` снимается в ПРОБЕ

`_buildOne` в `probe_config.dart` удаляет `insecure_concurrency` из каждой
naive-записи probe-конфига: в замере задержки пул изолированных сессий не нужен,
а движки он множит линейно.

Тело боевого конфига **не** затрагивается: `NodeSpec.emit` отдаёт свежую map на
каждый вызов (`emitRaw` строит новую, патч §302 — глубокая копия, §307), так что
probe мутирует только свою копию. Тест это фиксирует прямо: узлу ставится
`patchedJson` с `insecure_concurrency: 8`, probe-конфиг поля не содержит, а
`node.emit(...)` и сам `patchedJson` после сборки пробы целы.

Замечание о происхождении поля: у типизированного узла его быть не может —
`NaiveSpec` такого поля не имеет, `emitNaive` его не пишет, разбор его не читает
(это зафиксировано ожиданием `'naive.insecure_concurrency': 'поля нет в
NaiveSpec и в эмиссии'` в `app/test/contract/body_fields_roundtrip_test.dart`).
Реальный вектор — `patchedJson` (§302 import-rules), где в тело можно положить
произвольные ключи. Снятие — страховка именно от него.

## Лимит памяти probe-сессии: НЕ меняем

`SetupOptions.oomMemoryLimit` задаётся **один раз на процесс** в
`BoxApplication.kt` (`resolveMemoryLimitBytes`) — probe-сессия своего лимита не
имеет и иметь не может: `Libbox.setup` один на процесс, `ProbeSession` живёт
внутри него. Отдельной ручки «лимит для пробы» в libbox нет.

Поэтому вопрос «уложится ли ядро в лимит даже с ОДНИМ naive-движком» остаётся
открытым и лимит не трогается: поднимать общий лимит процесса ради пробы —
менять боевой режим (тот же лимит действует на живом туннеле, и §173 его уже
однажды опускали из-за GC-шторма на WG-пулах). Решать это можно только по
замеру RSS процесса при поднятом одном naive-узле; если один движок не
укладывается, правильный ответ — не лимит, а отказ поднимать naive в пробе
вовсе (вердикт вместо замера, как у Tailscale §435).

Сопутствующий факт (память проекта): `cache.db` открыт ВСЕГДА, probe-сессия
тоже — её куча не «пустая» даже до первого узла.

## Что спросить у пользователя для подтверждения

1. **Сколько naive-узлов** в папке/подписке, на которой падает «Проверка на всех
   серверах» (и сколько там узлов всего).
2. **Лог краша**: Settings → Logs после падения, либо
   `adb logcat -b crash -d` / `CrashReport-lxbox.log` из рабочего каталога.
   Ожидаемая подпись — OOM-убийство процесса (`Cannot allocate memory`,
   `lowmemorykiller`, либо `SIGABRT` из Chromium), а НЕ Dart-исключение.
3. **Модель устройства / общий RAM** — «auto» даёт 200 МБ ниже 3.5 GiB, и на
   таком телефоне порог наступает раньше всего.
4. Падает ли проверка **одного** узла (долгий тап → Test) на том же naive-узле:
   если да, лимита не хватает даже на один движок, и нужен не батч, а отказ
   (см. раздел выше).
5. Настройка **Memory limit** (§271) на устройстве: `off` должен снимать
   падение полностью — это самая быстрая проверка гипотезы владельцем.

## Тесты

`app/test/probe/probe_test.dart`, группа «§518 naive-гейт probe-конфига» плюс
тест раннера:

- 5 naive + 3 vless → батчей `ceil(5/N)`, в каждом naive не больше `N`, все 8
  индексов проверяются ровно по одному разу, не-naive в первом батче;
- без naive — один батч, `configJson` дословно равен `buildProbeConfig`;
- `insecure_concurrency` отсутствует у naive в пробе, боевой emit и
  `patchedJson` целы;
- naive с naive-детуром — две записи в одном батче (гейт считает записи);
- битые/группы — в вердиктах первого батча, один раз;
- внутри батча исходный порядок узлов: уникализация тегов (`Alpha`/`Alpha-2`)
  не сбивается подсадкой не-naive в начало первого батча;
- раннер: 3 naive → 3 `probeStart` и столько же `probeStop`, `probeUrlTest` по
  одному на каждый из 4 узлов.
