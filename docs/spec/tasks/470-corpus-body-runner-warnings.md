# §470 — body-раннер корпуса сверяет `warnings[]`

| | |
|---|---|
| **Статус** | Реализовано, тесты зелёные (5061) |
| **Дата** | 2026-09-18 |
| **Источник** | находка §469; ответ лаунчера 18.09.2026: его body-раннер сверяет весь конверт (`equalEnvelopeJSON` с нормализацией `warnings[]`); форма `value` — CANON §6 (лаунчер `8068f7a0`) |
| **Связанные** | §463 (объектные warnings в URI-раннере), §469, фича 460 |

## Проблема

URI-раннер корпуса (`test/contract/contract_test.dart`) сверяет `warnings[]`
с §463. Body-раннер (`test/contract/body_contract_test.dart`) сверяет состав
узлов и отбраковку, а `warnings[]` — нет. Кейсы тел, чей смысл именно в
предупреждениях (парные `*_pair.body`, `outbound_array_tls_fields`), у нас
зелёные независимо от поведения. §469 наткнулся на это случайно: гейт
`forbidden_for` не ставил `value`, и ни один тест не покраснел.

## Решение

1. Body-раннер сверяет `warnings[]` тем же правилом, что URI-раннер (CANON
   §6/§7, зеркало Go `normalizeWarningsForCompare`): `code` обязателен всегда,
   `path` и `value` — там, где их назвало ожидание; порядок — по правилу
   URI-раннера. Общую функцию сравнения вынести, а не копировать.
2. Загрузка реестра в `setUpAll`, как в URI-раннере после §469.
3. Каждый покрасневший кейс разобрать:
   - наш дефект (код не ставится, нет `path`/`value`, не тот порядок) —
     чинить в коде, с юнитом;
   - расхождение по существу, где наше поведение намеренное, — НЕ подгонять
     и override не заводить (override живёт у лаунчера): перечислить в
     отчёте с диагнозом, в раннере — именованный список ожидающих решения с
     комментарием-причиной по образцу `_overrideIgnored` из §465. Список
     должен быть коротким; больше пяти записей — остановиться и отчитаться.
4. Синк контракта на `8068f7a0` НЕ нужен (менялся только `docs/CANON.md`,
   версия та же); `renderWarningValue` сверить с текстом CANON §6 из этого
   коммита: скаляр как есть, объект `map[k:v k:v]` с сортированными ключами,
   массив `[a b c]`, обрезка по рунам 64 + `…`.

## Критерии приёмки

- body-раннер падает, если у узла лишний или недостающий код (проверить
  подсадкой);
- корпус зелёный; список ожидающих решения — пуст или ≤ 5 с причинами;
- тело узлов и golden не меняются;
- `flutter analyze` всего проекта, `flutter test -j 2` — «All tests passed»;
- спека 460 (раздел про корпус), CHANGELOG (если чинились дефекты,
  видимые пользователю), GUARDS.md при новых правилах.

## Как сделано

**Общий файл вместо копии.** Правила записи и сравнения `warnings[]` переехали
из URI-раннера в `test/contract/corpus_warnings.dart`, оба раннера импортируют
их оттуда. Переехало ровно то, что нормативно: `warningRecordOf` (форма записи
`{code, path?, value?, params?}`), карты пути и значения для рукописных классов,
`warningListOf` (дедуп по `(code, path)` + порядок `body.order` реестра),
`normalizeWarnings`/`normalizeNodeWarnings` (объём сверки задаёт ожидание),
`normalizeDrops`, канонизация и печать конверта. Копии в `contract_test.dart`
удалены — поведение URI-корпуса не изменилось ни на кейс. Реестр грузится в
`setUpAll` и у тел.

**Раннер тел объединяет два пути разбора — и это осознанно.** Первый прогон дал
четыре красных узла, и все четыре — с ПУСТЫМ списком кодов при непустом
ожидании. Причина одна на всех, архитектурная: граница W2a. Санитайзер реестра
при разборе (`parse_warnings.dart`) смотрит на `emit()` уже разобранного узла, а
типизированный парсер JSON (`parseSingboxEntry`) мусор к этому моменту уже снял —
`flow=xtls-rprx-direct` не попал в поле, `tls.insecure` и `tls.alpn` снял
`_tlsFromSingbox` (у него нет аккумулятора warnings по построению),
`totally_unknown_key` не имеет куда попасть в принципе. Коды этих полей у нас
ставит гард сборки (§455, `registry_gate.dart`) — единственный, кто работает на
ДОСЛОВНОМ теле провайдера, которое узел хранит в `rawSource`.

У лаунчера обе половины — один конвейер (парсер тела и санитайзер по реестру
подряд), и его конверт несёт коды обоих. Поэтому раннер объединяет их ЯВНО, у
себя (`_allWarningsOf`): иначе он сверял бы половину поведения приложения, и
кейсы были бы красными при полностью исправном приложении — пользователь эти
коды видит, просто на другом экране (отчёт сборки, а не строка узла).
Прод-поведение ради раннера не менялось. Дедуп по `(code, path)` делает
`warningListOf`, так что код от обоих путей (`field_conflict` у
`trojan-full-tls`) в конверте один раз. Функция схлопнется в `node.warnings`,
когда следующие волны проложат путь от `rawSource` к `NodeSpec.warnings`.

С объединением три из четырёх красных стали зелёными сразу — коды, пути,
значения и порядок сошлись с контрактом побайтно, включая формы
`map[enabled:true fingerprint:chrome]` и `[MTIzNDU2…]`.

**Починенный дефект — один.** `unknown_key` ставился без `value`. Конверт
корпуса его называет (`manual_object_junk` → `totally_unknown_key` =
`whatever`), лаунчер печатает снятое `src[name]`
(`core/config/nodeflow/sanitize.go:370`). У нас человек читал «поле снято:
неизвестный ключ» с путём и не знал, ЧТО потерял, — а по одному пути не понять,
опечатка это или чужой диалект. Правка в `body_sanitizer.dart`: значение
берётся из `src[key]` и печатается тем же `renderWarningValue`. `secret` там
неоткуда взять — ключа в схеме нет, значит нет и флага; лаунчер поступает так же.
Строка гарда сборки стала `[foo=1]` вместо `[foo]`, ожидание
`registry_gate_test.dart` поправлено вместе с комментарием, который прямо
утверждал обратное.

**Список ожидающих решения — ПУСТ.** Расхождений по существу не нашлось:
единственное, что выглядело как расхождение, оказалось нашим дефектом, а
остальное — вопросом того, откуда раннер берёт предупреждения.

**Подсадка (критерий приёмки).** На `tuic_quic_tls_pair` проверены обе стороны:
лишний код в ожидании роняет кейс с полным диффом, снятый `warnings[]` из
ожидания — тоже. Корпус после проверки восстановлен байт в байт (`diff` чист).

**`renderWarningValue` против CANON §6 (лаунчер `8068f7a0`).** Сверено по
тексту канона, расхождений нет: скаляр как есть без кавычек; объект
`map[k:v k:v]` с ключами по возрастанию, вложенный — тем же правилом; массив
`[a b c]` с сохранённым порядком; обрезка по РУНАМ — первые 64 плюс `…`
(U+2026), строка в 64 руны и короче не меняется; `secret` → `***`. Форма была
приведена к канону ещё в §469; §470 закрыл её юнитами
(`body_sanitizer_test.dart`, группа «renderWarningValue — CANON §6»), включая
кейс на не-BMP символы, где руны и кодовые единицы UTF-16 расходятся вдвое.
Синк контракта не запускался — версия та же, менялся только `docs/CANON.md`.
