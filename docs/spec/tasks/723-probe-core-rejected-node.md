## Problem

В подписке пришёл узел Shadowsocks 2022 с негодным ключом
(`2022-blake3-aes-256-gcm`, вторая часть пароля — 27 символов, не base64 и не
32 байта). Разбор ссылки верный: пароль перенесён дословно, ошибка в данных
провайдера.

Туннель страховка 478 подняла: ядро отказало
(`initialize outbound[106] shadowsocks[…]: decode key: illegal base64 data at
input byte 24`), узел выключен, старт повторён.

Пинг на экране подписки после этого не работает вовсе:
`Probe session failed to start: … initialize outbound[105] shadowsocks[…]`.

## Diagnosis

Проба — один временный запуск ядра на конфиге со ВСЕМИ узлами списка
(`buildProbeBatches` → `probeStart`), замеры идут после старта. Ядро
отказывается стартовать на первом узле, который не принимает, и
`ProbeRunner.run` возвращает одну ошибку на весь прогон
(`probe_runner.dart`, ветка `!started.ok`).

Выключенные узлы в пробу идут намеренно (§283: проба отвечает «жив ли
сервер»), поэтому узел, уже выключенный страховкой, попадает в пробный конфиг
и валит его при каждом запуске. Страховки вида «вынуть узел и повторить» у
пробы нет.

## Solution

Две половины, обе в `ProbeRunner.run` — действуют для подписки, папки и
одиночного сервера.

1. **Узел с вердиктом `core_rejected` в пробу не идёт.** Вердикт читается с
   `NodeSpec.warnings` (его туда штампует `stampNodeWarnings`). Такой узел
   сразу получает `ProbeStatus.invalid` с текстом `core rejected: <причина
   ядра>`. Выключенные вручную узлы пингуются как раньше.
2. **Отказ ядра на старте пробы — узел вынимается, старт повторяется.**
   Строка ошибки разбирается тем же `parseCoreRejection` (обе формы, §9.2 и
   §653) против тегов пробного конфига. Тег → индекс узла по
   `ProbeConfig.ownerByTag` (тег детура указывает на свой узел). Узел
   получает `invalid` с той же формой текста, остаток списка собирается
   заново и меряется. Уже измеренные батчи повторно не гоняются.
   - Узел не назван (ошибка не про узел, ядро без тега) — как раньше: одна
     ошибка на прогон.
   - Не больше `kProbeMaxCoreRejects` (16) вынутых узлов за прогон; дальше —
     ошибка ядра на прогон.
   - Проба в подписке ничего не меняет: вердикт не сохраняется, узел не
     выключается (решение: пинг — чтение).

Проверку ключа SS-2022 до ядра (base64 нужной длины) эта задача не делает:
это правило значения в общем контракте, запрос лаунчеру.

## Verification

Юнит-тесты (`probe_core_rejected_test.dart`):

1. Узел со штампом `core_rejected` — в `probeStart` его тега нет, результат
   `invalid` с причиной, остальные измерены.
2. `probeStart` отказывает строкой `initialize outbound[i] type[tag]: …` —
   второй `probeStart` без этого узла, узел `invalid`, остальные измерены,
   прогон возвращает `''`.
3. Отказ без названного узла — прогон возвращает ошибку, как раньше.
4. Ядро отвергает узлы без конца — прогон останавливается на пределе.

На устройстве: подписка с узлом SS-2022 с негодным ключом, VPN выключен, пинг
подписки — все узлы, кроме битого, получают замер; битый — отметку.
