# §318 — Доступ к OOM-отчётам ядра (Debug-вкладка, дамп, ротация)

**Тип:** таска (диагностика)
**Статус:** реализована, DEVICE-PENDING
**Связано:** §316 (краш-репорты ядра — прямой образец, вся обвязка симметрична), §271 (`SetupOptions.oomKillerEnabled`/`oomMemoryLimit`, GC-шторм), §173 (переезд на libbox 1.14), §207 (pprof-профили)

---

## 1. Проблема

На тест-устройстве в `/data/data/com.leadaxe.lxbox/files/oom_reports/`
обнаружено **575 каталогов, 427 МБ** — снимки с 27.06 по 15.07.2026.
Их пишет ядро (`experimental/libbox/oom_report.go:84`), приложение о папке
не знает вовсе: строки `oom_reports` в коде LxBox не было.

Разрыва два, и они зеркалят §316.

**1. Данные недоступны.** Каждый снимок — это pprof-профили кучи в момент,
когда oom-killer ядра увидел превышение порога RSS. Ровно те профили, за
которыми в §207/§271 ходили руками через профайлер на живом процессе. Здесь
они уже сняты — автоматически, в реальный момент проблемы, на устройстве
пользователя — и лежат мёртвым грузом: ни в UI, ни в дампе, ни в Debug API.

Пример метаданных снимка `2026-07-15T07-15-32`:

| поле | значение |
|---|---|
| `memoryUsage` | 440 MB |
| `heapInuse` | 123 MB |
| `numGoroutine` | 424 |
| `numGC` | **1 788 911** |
| `totalAlloc` | 42 GB |

Это подпись GC-шторма из §271 — снятая сама, без участия разработчика.

**2. Папка растёт неограниченно.** Ротации нет ни на одном уровне:

| Уровень | Что ограничивает |
|---|---|
| `oomReporter.WriteReport` (ядро) | ничего: `nextAvailableReportPath` + запись новой папки |
| `oomkiller.Service.writeOOMReport` | дебаунс `now-lastReport < 3600` — не чаще раза в час |
| LxBox | ничего: `CrashReports.prune` чистит только `crash_reports/` |

Дебаунс живёт в поле инстанса сервиса (`lastReportTime`), поэтому на каждом
рестарте туннеля счётчик обнуляется и снимок пишется заново сразу. Отсюда
пары каталогов с разницей в минуту (`00-00-41` / `00-01-57`). Один снимок —
около 750 КБ, из них ~1.2 МБ на два основных профиля.

## 2. Решение

Завести `oom_reports` в приложение по образцу §316, **не трогая ядро**:
модель + список, вкладка в Debug, просмотр, share, ротация на старте,
метаданные в дамп, эндпоинты Debug API.

### 2.1 Состав снимка

Ядро кладёт каталог `oom_reports/<ISO-таймстамп>/`:

| файл | что | в UI |
|---|---|---|
| `metadata.json` | memstats: RSS, heap, GC, goroutines | **головной файл** — показываем |
| `go.log` | сохранённый лог ядра на момент снимка | показываем вторым блоком |
| `heap.pb`, `allocs.pb` | pprof-профили кучи (~580 КБ каждый) | только share |
| `goroutine.pb`, `block.pb`, `mutex.pb`, `threadcreate.pb` | остальные профили | только share |
| `configuration.json` | конфиг на момент снимка | только share |
| `connections.json` | активные и закрытые соединения | только share |
| `cmdline` | `gojni` | только share |

**Головной файл — `metadata.json`, а не `go.log`.** Отличие от §316, где
головной — трейс: у OOM ценность в цифрах памяти, а не в тексте, и именно
их надо видеть в списке без открытия. Каталог без `metadata.json`
пропускаем — это недописанный снимок, а не отчёт.

### 2.2 Модель и список

`lib/services/oom_reports.dart` — по образцу `stderr_reader.dart`:

- `OomReportFile` — `path` (metadata.json), `name` (таймстамп), `mtime`,
  `size` (**весь каталог**, а не головной файл: вес снимка несут профили,
  и в UI надо видеть реальные мегабайты), `dirPath`, `coreVersion`,
  `memoryUsage`, `heapInuse`, `numGoroutine`.
- `OomReports.list()` — новые первыми.
- `OomReports.totalSize()` — суммарный размер папки для заголовка вкладки.
- `OomReports.prune({keep})` — оставить N свежих.
- `OomReports.clear()` — удалить все.

Базовый каталог — тот же `CrashReports.baseDir()` (native `Context.filesDir`;
§316 §2.0: Flutter-овый `getApplicationDocumentsDirectory()` указывает в
`app_flutter` и файлов ядра там нет).

### 2.3 Ротация

`kOomKeep = 5` — меньше, чем `kCrashKeep = 10`: снимок OOM весит 750 КБ
против нескольких КБ у краша, и десяток съел бы 7.5 МБ.

Вызов — в `main.dart`, рядом с `CrashReports.prune()`, одной цепочкой:
чистка на старте, а не при открытии экрана (в Diagnostics пользователь может
не заходить годами — собственно, так 427 МБ и накопились).

### 2.4 UI

Четвёртая вкладка Debug — «OOM» (было три: Log / Crashes / Profiling).
Отдельная вкладка, а не подраздел Crashes: краш и OOM — разные события
(паника против давления памяти), и смешивать их в одном списке значит
терять сигнал.

- Заголовок: пояснение + **суммарный размер архива** + кнопки refresh и
  «удалить все» (с диалогом подтверждения).
- Строка списка: время; подзаголовок — размер каталога, RSS, версия ядра.
- Тап — экран просмотра: таблица memstats из `metadata.json` + `go.log`
  monospace ниже.
- Share — каталог целиком (все профили), по образцу `shareCrashReport`.

Пустой список — нормальное состояние («ядро не упиралось в лимит памяти»),
а не поломка экрана.

### 2.5 Дамп

В `DumpBuilder.build()` — ключ `oom_reports`: **только метаданные**
(`name`, `mtime`, `size`, `core_version` + поля memstats). Тела не кладём:
профили бинарные, в JSON им не место, а `go.log` снимка дублирует общий
лог. Кому нужны профили — share конкретного снимка из UI.

### 2.6 Debug API

`/files/oom/list` и `/files/oom?name=<snapshot>&file=<basename>` — симметрия
с `/files/crash/*`. По умолчанию отдаётся `metadata.json`. Гейт
`_assertSafeName` на обоих параметрах: подкаталог задаёт сервер, клиент
передаёт только basename'ы, traversal невозможен по построению.

## 3. Что НЕ делаем

- **Ядро не трогаем.** Ротация на стороне ядра — правильное место, но это
  отдельный бамп `sing-box-lx` с пересборкой libbox; приложение обязано
  выживать и со «щедрым» ядром. Ротация в LxBox нужна всё равно.
- **Баннер на главном не заводим.** У крашей он есть (`CrashBannerState`),
  потому что краш — событие, требующее внимания. OOM-снимок штатен: ядро
  подобралось к лимиту и записало улику. Дёргать пользователя незачем.

## 5. Проверка на устройстве (DEVICE-PENDING)

1. Debug → вкладка «OOM»: 575 снимков видны, суммарный размер совпадает с
   `du -sh`.
2. После перезапуска приложения остаётся 5 снимков, в логе —
   `Pruned N old OOM report(s)`.
3. Тап по снимку: memstats-таблица заполнена, `numGC` семизначный.
4. Share отдаёт весь каталог, `heap.pb` открывается в `go tool pprof`.
5. `curl /files/oom/list` — тот же список; `?file=heap.pb` отдаёт бинарь.
6. Дамп содержит `oom_reports` с метаданными и без тел.
