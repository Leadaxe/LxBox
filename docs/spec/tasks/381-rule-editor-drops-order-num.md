# §381 — редактор правила терял `num`: ложный «Save changes?» и прыжок правила вверх

**Статус:** ГОТОВО (код + тесты), DEVICE-PENDING
**Тип:** bug-fix. Регрессия §370.
**Зависит от:** §370 (ось `ui.num`), §030 (Custom Rules)
**Затронуто:** `app/lib/screens/custom_rule_edit/edit_controller.dart` (`snapshot()`)

---

## 0. Жалоба

Два симптома, репортились как разные баги (v2.19.7):

1. Заход в любое правило и выход из него без единой правки → диалог «Save changes?».
2. После сохранения правило незаметно меняет позицию в списке. Воспроизведение автора
   жалобы: правило «флибуста», меняется один символ в имени, выход с сохранением —
   порядок на экране выглядит правильным. Переход на Start, возврат в Rules — правило
   уехало вверх.

Корень у обоих один, поэтому и чинятся одной правкой.

## 1. Причина

`CustomRuleEditController.snapshot()` собирает текущее состояние формы в `CustomRule`,
вызывая конструктор подкласса. Во всех четырёх ветках (`inline`/`srs`/`preset`/`json`)
конструктор вызывался **без** `orderNum` — при том, что параметр у всех четырёх есть
(`super.orderNum`), а `toJson`/`fromJson` ключ `num` пишут и читают. Снапшот приезжал
с `num == null`.

Дальше расходится на два наблюдаемых эффекта:

| Путь | Механика |
|---|---|
| Ложный dirty | `isDirty()` = `jsonEncode(snapshot().toJson()) != jsonEncode(initial.toJson())`. У `initial` из storage ключ `num` есть, у снапшота нет → списки отличаются **до первой правки**. Save-иконка в AppBar подсвечена сразу, выход даёт «Save changes?». |
| Прыжок правила | `_openCustomRuleEditor` кладёт `result.saved` в `_customRules[index]` как есть (`routing_screen.dart:784`) — на экране позиция та же, отсюда «порядок выглядит правильным». В storage правило уезжает с `num == null`. При следующем входе на экран `_load()` → `normalizeRuleOrder` → `markRuleOrder` видит `orderNum == null` и размечает правило заново подряд от `kUserRuleNumStart` (1000), то есть в начало пользовательской зоны, после чего `sortRulesByNum` поднимает его вверх. |

Второй эффект объясняет и «иногда замечал странный порядок в более ранних версиях»:
видно его только после ухода с экрана и возврата, а не сразу после сохранения.

Ветка сохранения нового правила (`_addCustomRule`) от бага не страдала — там `orderNum`
проставляется явно через `nextUserRuleNum` после закрытия редактора. Пресет из каталога
(`_copyPreset`) — тоже, там `cr.orderNum = rule.num`.

## 2. Фикс

`snapshot()` переносит `initial.orderNum` во все четыре ветки. Редактор позицию правила
не меняет — за перемещение отвечают drag (`placeRuleAfter`) и добавление нового правила,
поэтому снапшот обязан отдавать номер неизменным.

Неразмеченное правило (`orderNum == null`, storage до §370) остаётся с `null` — его
разметит `markRuleOrder` при загрузке экрана, как и раньше.

Миграция не нужна: правила, уже потерявшие `num` на затронутых версиях, будут размечены
`markRuleOrder` при первой же загрузке. Восстановить их прежние позиции нечем — номер
утрачен; юзер расставляет drag'ом.

## 3. Тесты

`app/test/screens/custom_rule_edit/snapshot_order_num_test.dart` — 6 кейсов:
`snapshot().orderNum` переносится для всех четырёх видов правил, `isDirty()` даёт `false`
на нетронутой форме, неразмеченное правило остаётся с `null`.

До фикса падали 5 из 6 (проходил только кейс с `null`).
