## Проблема

Conn, открывшийся и закрывшийся между тиками CommandClient (первый раз виден
уже закрытым), проходил open-ветку со `startedAt = now` и закрывался diff'ом
в том же проходе → `duration = 0`, хотя ядро несёт `CcConnection.createdAt`
/ `closedAt` (epoch ms). На том же приближении эвристика `tcpReset`
(«<1с и 0 байт») давала ложный reset для conn'а, реально жившего дольше
секунды с 0 байт (idle keep-alive, отменённый запрос).

## Решение

- `startedAt` снапшота — из `createdAt` ядра, когда метка валидна;
- kernel-closed дельта (§176) запоминает `closedAt` в снапшоте
  (`_ConnSnapshot.kernelClosedAt`); diff-закрытие «conn исчез из снапшота»
  остаётся на `now` — у ядра метки нет;
- `tcpClose`: `ts`/`duration`/вход эвристики — от kernel-меток; отрицательная
  длительность (расхождение часов при смешанных источниках) клампится в 0,
  эвристика при отрицательной не судит.

Решения по месту:

| вопрос | решение |
|---|---|
| Валидность метки | `_kernelTime`: epoch ms > 2000-01-01. `0` и малые значения — сентинелы «нет данных» (маркеру isClosed достаточно `closedAt > 0`, тесты §176 шлют `1`) — без порога `closedAt: 1` дал бы событие 1970 года |
| Эвристика tcpReset | Порог не меняется («<1с и 0 байт»), меняется только источник длительности — теперь она детерминированная |

## Тесты

`test/services/traffic_profiler_test.dart` — группа §353: duration от
kernel-меток (4.2с с 0 байт — НЕ reset), честный быстрый close остаётся
reset'ом, сентинел `closedAt=1` не превращается в 1970 год.
