| Тип | Норма контракта |
| Статус | Реализовано (ветка task-640) |
| Дата | 2026-10-14 |
| Связанные | контракт 1.1.116 (TASKS_LXBOX §113, решение владельца 09.10.2026), §633 (Merge при импорте — настоящее слияние), §636 (синк 1.1.117 принёс реестр с этим кодом), BACKUP.md §9 п. 7 |

## Проблема

Синк контракта 1.1.117 (`37e040c6`) принёс и 1.1.116: в
`registry/backup_warnings.json` объявлен код `backup_rules_replaced`
(import, warning, параметр `count`), а норма BACKUP.md §9 п. 7 уточнена.
LxBox нормы не исполняет, код не эмитит — CI красный:
`app/test/contract/registry_sync_test.dart:133` («реестр объявляет коды,
которых LxBox не эмитит»).

Сама норма (инцидент лаунчера 08.10.2026): файл бэкапа с одним узлом,
залитый через `POST /backup/import`, стирал всю маршрутизацию приёмника —
импорт замещал `rules[]` безусловно, разбор не различал «ключа нет» и
`rules: []`.

## Диагностика

- Разбор файла: `decoded['rules'] as List? ?? const []` — и в legacy-ветке
  (`app/lib/services/lx_backup.dart:1186`), и в 1.0 (`:2828`): отсутствие
  ключа и пустой массив дают одно и то же `rules = []`. У `LxBackupFile`
  (`:624`) признака «ключ был» нет.
- План импорта (`app/lib/services/lx_backup_import.dart:296-359`): `rules`
  плана строятся только из `file.rules`; «`rules[]` приёмника в план не
  входят: секция замещается правилами файла» (комментарий `:323`). Запись —
  `SettingsStorage.saveCustomRules(plan.rules)` (`:441`) безусловно.
- Приёмник `LxImportReceiver` (`:38`) своих `rules` не несёт (DNS-правила —
  несёт, `receiver.dns.rules`).
- Режим Merge (§633) — свой путь: правила файла добавляются к правилам
  получателя по `id`/отпечатку, ничего не снимается.
- Экспорт пишет ключ только при непустом списке:
  `if (ruleRecords.isNotEmpty) 'rules': ruleRecords` (`lx_backup.dart:859`).
  Норма п. 3 требует писать всегда.
- Код предупреждения — константы `kWarn*` в `lx_backup.dart:91-219`;
  `registry_sync_test` сверяет реестр с ними и с `_launcherOnlyBackupCodes`.

## Решение

Норма исполняется как записана в TASKS_LXBOX §113 / BACKUP.md §9 п. 7.
Условия — списком:

| Файл | Режим импорта | Правила приёмника | Код |
|---|---|---|---|
| ключа `rules` нет | Replace | остаются как были | — |
| ключа `rules` нет | Merge | остаются как были | — |
| `rules: []` | Replace | снимаются все; `count` = сколько было | `backup_rules_replaced {count}`, только при `count > 0` |
| `rules: [...]` | Replace | снимаются, встают правила файла; `count` = сколько было у приёмника | `backup_rules_replaced {count}`, только при `count > 0` |
| `rules: [...]` или `[]` | Merge | слияние §633, ничего не снимается | — |

«Сколько было у приёмника» — число пользовательских правил приёмника до
импорта (то, что лежит в `SettingsStorage` custom rules), без правил
пресетов/шаблона, если они хранятся отдельно; исполнитель сверяет с тем, что
именно замещает `saveCustomRules`, и считает ровно это.

Что сделать:

1. `LxBackupFile` — признак `rulesDeclared` (bool; `true`, когда ключ `rules`
   есть в корне файла, пусть и `[]`). Выставляется в обоих разборах по
   `containsKey('rules')` на сырой карте до десериализации. `copyWith`
   сохраняет.
2. `LxImportReceiver` — поле `rules` (пользовательские правила приёмника).
   Все места, где приёмник строится (`lx_backup_import.dart` ~`:400`, раннер
   корпуса `app/test/contract/backup_corpus_test.dart:247`, Debug API и
   экран импорта — найти по `LxImportReceiver(`), передают его.
3. План (`planLxBackupImport`): при `!file.rulesDeclared` → `plan.rules` =
   правила приёмника как есть (ось порядка, D-117 и нормализация `vars`
   над ними НЕ прогоняются — файл о правилах молчит, трогать нечего). При
   `rulesDeclared` в режиме Replace — прежнее поведение плюс предупреждение
   `backup_rules_replaced` с `count` = длина правил приёмника, если `> 0`
   (в `file.warnings`/`extraWarnings`, как `backup_var_skipped`). В режиме
   Merge — без изменений.
4. Константа `kWarnRulesReplaced = 'backup_rules_replaced'` рядом с
   остальными `kWarn*`, с комментарием нормы.
5. Экспорт: ключ `rules` пишется **всегда** (`'rules': ruleRecords`, пусть
   `[]`). Проверить тесты экспорта, которые ждали отсутствия ключа при пустом
   списке — ожидания привести к норме (это и есть смысл нормы, а не
   регрессия). Корпус лаунчера не менялся — `backup_corpus_test` должен
   остаться зелёным; если какой-то кейс корпуса ломается на `rules`
   приёмника — сначала проверить, как раннер строит приёмник (п. 2), не
   править ожидания корпуса.
6. Превью импорта (экран, если показывает состав): строка предупреждения
   `backup_rules_replaced` показывается как прочие warning-коды; отдельного UI
   не делать.

Пункт 1 нормы («как прежде») означает: порядок правил, D-117, `vars`-норма-
лизация при `rulesDeclared` не меняются.

## Отклонения при реализации

1. **Строки Merge таблицы.** У импорта LX Backup (`planLxBackupImport`,
   экран Transfer to desktop) режимов нет — он всегда Replace по правилам.
   Merge §633 — слияние документа хранения (`mergeStorageDoc`, полный бэкап
   и Debug API `/backup/import?merge=true`), LX-плана не касается. Строки
   Merge проверены на `mergeStorageDoc` (ключа нет — правила как были; `[]` и
   `[...]` — слияние, ничего не снимается, кодов нет); код не менялся.
2. **Debug API `POST /backup/import`** у LxBox принимает формат полного
   бэкапа хранения (`storage`/`vpn_settings`), а не LX Backup; эндпоинта
   импорта LX нет. Тест хендлера не дополнялся, семантика Replace полного
   бэкапа (документ замещается целиком) не менялась — норма 1.1.116 о файле
   LX Backup.
3. **Запись.** При `!rulesDeclared` `LxBackupImportService.apply` не зовёт
   `saveCustomRules` вовсе (план держит правила приёмника как есть): повторная
   запись прогнала бы их через нормализацию хранения, а файл о правилах молчит.
4. **Detail предупреждения** — `rules: <count>` (превью показывает
   `• ${w.detail}`, как у прочих кодов).
5. **Ожидание `lx_backup_roundtrip_test`** «импорт собственного экспорта в
   совпадающее состояние» дополнено `backup_rules_replaced`: свой экспорт
   несёт ключ, приёмник с правилами — замена названа по норме.
6. **UI не трогался (п. 6), замечено для владельца:** строка превью
   `Importing replaces the current rules.` показывается и для файла без ключа
   `rules`; итоговый снек считает `backup_rules_replaced` в «items not
   applied» (`Imported N rule(s), 1 items not applied` при каждом импорте
   полного файла поверх непустых правил), а в превью код стоит под заголовком
   `Not applied as-is:`. Отдельной фразы UI для кода (TASKS_LXBOX §113 «фраза
   UI для кода») нет.
