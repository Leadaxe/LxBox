## Проблема

Остановка тяжёлого туннеля (AWG/WireGuard-эндпоинт WARP, ~25 живых
соединений) завершается **успешно** за ~5.2с, но пользователь видит красный
снекбар «Stop timed out». Туннель при этом реально остановлен — ошибка
ложная, состояние UI ей противоречит.

Причина — перевёрнутая лестница таймаутов: внутренние бюджеты были короче
реального teardown'а и короче внешних, поэтому объявлял таймаут тот слой,
который вообще не должен был решать.

## Диагностика

Device-проход 03.09 (эмулятор `LxBox_test`, Android 14 arm64). Замеры из
лога:

| Время | Событие |
|---|---|
| 16:13:47.610 | вызов плагина `stopVPN` |
| 16:13:52.810 | фактическое завершение `doStop` (setStatus(Stopped)) |
| 16:13:53.206 | нативный отказ по таймауту (уже после успеха) |

Реальный teardown = **5.2с**. Внутри него `close inbound completed (1.95s)`
плюс завершение WireGuard-устройства.

Цепочка:

1. `VpnPlugin.stopVpn` ждал `withTimeout(5_000)` — истекал за 200мс **до**
   того, как `doStop` доигрывал, и возвращал `false`;
2. `BoxService.doStop` блокирующе ждёт teardown ядра
   (`closeFileDescriptor` → `DefaultNetworkMonitor.stop()` →
   `closeCommandServerAtomic`) до `setStatus(Stopped)` — на тяжёлом туннеле
   это секунды, а не миллисекунды;
3. `false` доезжал до `HomeController.stop()` → `ErrKey.stopTimedOut`;
4. дополнительно на 3-й секунде срабатывала эскалация `_armTransientTimeout`
   → `forceStopVPN` — force-stop поверх ещё живой, штатно идущей остановки.

Внешний Dart-бюджет `_Timeouts.stopVpn` = 10с был с запасом и в проблеме не
участвовал — «узким горлышком» оказались именно внутренние пороги.

### Почему §287 промахнулся

§287 опустил порог эскалации с 10с до 3с: при stop с активным mass-ping'ом
`closeService()` синхронно ждал teardown WG-эндпоинтов пинга и упирался в
10с. Замер тогда дал две точки — чистый stop 0.16с и зависший ~10с — и
модель получилась бинарной: teardown либо мгновенный, либо мёртвый.

Третий случай — **медленный, но живой** teardown (5.2с) — в модель не попал
и оказался ровно между порогами. По ней он классифицировался как зависание.

## Решение

Выстроена лестница бюджетов, строго по возрастанию. Каждый следующий слой
даёт предыдущему договорить и объявляет таймаут, только если тот уже сдался.

| Слой | Было | Стало | Где |
|---|---|---|---|
| Нативный `stopAwait` (обычный стоп) | 5с | **9с** | `BoxVpnService.STOP_AWAIT_TIMEOUT_MS` |
| Нативный `stopAwait` (reconnect) | 6с | **9с** | та же константа |
| Dart `stopVPN` | 10с | 10с (без изменений) | `_Timeouts.stopVpn` |
| Эскалация `forceStopVPN` | 3с | **12с** | `_defaultStoppingTimeout` |

### Обоснование значений

**Нативные 9с.** Должны быть заведомо больше худшего наблюдаемого teardown'а
(5.2с) — с запасом на более слабое железо, — но строго меньше Dart-бюджета
(10с). Зазор в 1с нужен на доставку результата обратно через MethodChannel
(сериализация + hop на Flutter-поток). Если бы бюджеты совпали, Dart успел
бы отвалиться первым: `stopVPN` объявлен с `onTimeoutValue: false`, то есть
Dart-таймаут дал бы точно такой же `false` и ту же самую ложную ошибку — но
уже с другой стороны границы и без строчки в logcat. Нативный слой обязан
отвечать первым, потому что только он знает, чем кончился teardown.

**Reconnect — та же константа.** Путь `BoxVpnService.reconnect` держал свой
литерал 6с, хотя ждёт ровно тот же teardown. Он резал успешную остановку так
же, просто заметили не там. Литерал заменён на общую константу — расходиться
им больше нечем.

**Эскалация 12с.** Force-stop переведён из конкурентов штатной остановки в
backstop: порог больше всей штатной лестницы, поэтому он срабатывает только
когда та уже отработала и провалилась. Забота §287 при этом сохранена — см.
ниже.

Константы не задублированы: Kotlin-стороны обе ссылаются на
`BoxVpnService.STOP_AWAIT_TIMEOUT_MS`, а связь «нативный < Dart < эскалация»
записана комментариями в трёх точках лестницы, чтобы правка одного числа не
прошла мимо остальных.

## Путь честного таймаута

При **реальном** зависании ядра пользователь по-прежнему получает ошибку —
молчаливого бесконечного ожидания нет:

1. ядро не отдаёт `setStatus(Stopped)`; на 9с истекает нативный
   `STOP_AWAIT_TIMEOUT_MS`, в logcat пишется строка таймаута;
2. `stopVpn` возвращает `false` → `HomeController.stop()` показывает
   `ErrKey.stopTimedOut` — теперь это честный сигнал, а не побочный эффект
   короткого бюджета;
3. на 12с добивает эскалация: `forceStopVPN` → `doForceStop` (teardown под
   `withTimeout(2с)` на `forceStopScope`, `stopSelf()` не блокируется) —
   сервис не остаётся жить и роутить вхолостую (сценарий §129).

Итог: раньше ошибку давали и успех, и провал; теперь — только провал. Худший
случай ожидания вырос с 3с до 9с, но эти 9с наступают лишь при настоящем
зависании, тогда как прежние 3с били по каждой тяжёлой, но здоровой
остановке.

## Проверка симметрии

Прогон по `withTimeout` / `Timeout(` / `timeout:` в vpn-слое Kotlin и Dart.
Найденное и вердикт:

| Точка | Значение | Вердикт |
|---|---|---|
| `VpnPlugin.stopVpn` | 5с → 9с | исправлено |
| `BoxVpnService.reconnect` | 6с → 9с | исправлено |
| `_defaultStoppingTimeout` | 3с → 12с | исправлено |
| `_Timeouts.stopVpn` | 10с | без изменений, вершина лестницы |
| `doForceStop` teardown | 3× `withTimeout(2с)` | без изменений — это уже force-путь, его задача не ждать, а добить |
| `_heartbeatTimeout` | 8с | не бюджет остановки: детектор тишины status-стрима у **живого** туннеля; `_tryCleanStop` — fire-and-forget без своего таймаута |
| `_defaultConnectingTimeout` | 15с | другая фаза, teardown'а не касается |
| `_Timeouts.reload` / `dnsCache` | 10с | reload не идёт через `stopAwait` |

Расхождений сверх исправленных не осталось.

## Тесты

`app/test/controllers/stop_timeout_budget_test.dart` — 4 кейса:

- успешный стоп не выставляет `stopTimedOut`;
- медленный, но успешный стоп (native отвечает с задержкой) — тоже без
  ошибки: главный кейс задачи;
- провал штатного стопа (native вернул `false`) — ошибка есть: контракт не
  ослаблен;
- эскалация строго больше Dart-бюджета `stopVPN` — guard лестницы.

Guard проверен на отрицательном контроле: со старым значением 3с падает
(`Expected: a value greater than <10000> / Actual: <3000>`).

Нативный бюджет (`STOP_AWAIT_TIMEOUT_MS`) unit-тестами **не покрыт** — это
Kotlin/coroutines за границей MethodChannel; в Dart-тестах проверяется
контракт над его ответом, само истечение таймаута — только device-проходом.
