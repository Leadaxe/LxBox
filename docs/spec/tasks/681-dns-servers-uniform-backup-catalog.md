## Проблема

Контракт 1.1.134 ввёл норму «шаблонные DNS-серверы в файле — полный список»
с исключением: только для файла того же приложения (`exported_by.app`). Причина
исключения — у лаунчера другая модель: библиотека шаблона эмитится целиком,
записи `kind: template` появляются только у тронутых серверов, «нет записи»
значит «по умолчанию», а у нас после §680 — «удалён». Файл лаунчера, прочитанный
нашим правилом, снёс бы на телефоне весь нетронутый список.

Решение владельца 23.10.2026: **однородность**. Лаунчер переходит на модель
§680 с миграцией, файл несёт каталог источника, правило импорта одно для обеих
сторон, исключение по приложению снимается.

## Решение

### 1. Что меняется в контракте (предложение лаунчеру, следующая версия)

1. **`dns.template_catalog: [tag, …]`** — теги каталога `dns_options.servers`
   шаблона **источника** на момент экспорта. Писатель с этой версии кладёт
   поле всегда; читатель терпит отсутствие (п. 4).
2. **Экспорт `dns.servers`** — полный список состояния источника: у каждого
   сервера каталога, который есть в списке, есть запись (`enabled`, `vars`),
   независимо от того, трогал ли его пользователь. Отсутствие записи при
   наличии тега в `template_catalog` = удалён пользователем.
3. **Правило импорта, одно для обеих сторон.** После слияния §9 п. 5 запись
   `kind: template` приёмника **снимается**, когда выполнены все три условия:
   - тег есть в `template_catalog` файла (источник этот сервер знал);
   - тега нет среди записей `kind: template` файла (источник его удалил);
   - запись приёмника не держит ссылка, переживающая импорт (§117 №7 / §680
     п. 3: сервер активного пресета, `serverTag` правила приёмника, которое
     импорт не заместил, значение `final` / `default_domain_resolver` после
     импорта, член группы из списка после импорта, `domain_resolver` другого
     сервера списка). Удерживаемая запись остаётся с предупреждением
     `backup_dns_entry_kept {entry: "template:<tag>", used_by}`.
   Тег, которого нет в `template_catalog` файла, приёмник не трогает: источник
   о нём не знал, это не удаление. Так закрывается и разница каталогов между
   приложениями (`opendns_doh`, `yandex_dot`), и разница версий одного
   приложения (новый сервер шаблона у приёмника, которого старый источник не
   видел).
4. **Переходный период — файл без `template_catalog`** (записан до этой
   версии): `exported_by.app` равен приёмнику → каталог считается равным
   каталогу шаблона приёмника (поведение 1.1.134); другое приложение →
   слияние без снятия. Это единственное место, где приложение ещё
   упоминается, и оно уходит вместе со старыми файлами.
5. **Ссылки файла на теги, которых у приёмника нет** (другой каталог, другая
   версия, сервер удалён у приёмника и не приехал):
   - запись `kind: template` с неизвестным тегом — пропуск
     `backup_dns_entry_skipped {entry: "template:<tag>"}` (как сейчас, тела в
     файле нет, материализовать нечего);
   - `final` / `default_domain_resolver` на неизвестный или выключенный тег —
     при импорте сбрасываются на умолчание шаблона приёмника с
     `backup_dns_resolver_reset {field, value}` (сейчас LxBox делает это молча
     при загрузке вкладки, `dns_controller.dart:283-299`);
   - группа (`kind: user`, `type: group`) с членами, которых у приёмника нет:
     неизвестные члены снимаются при сборке с предупреждением (как сейчас);
     если **ни одного** известного члена не осталось — группа ввозится
     **выключенной** с `backup_dns_group_empty {tag}` (сейчас пустая включённая
     группа = fatal `EmptyDnsGroup` при сборке);
   - `domain_resolver` сервера на неизвестный тег — ключ снимается при сборке
     с предупреждением (§680 п. 5, уже есть);
   - `serverTag` правила на неизвестный тег — как сейчас (§604 код у
     user-правила, тихий пропуск mirror).

**Принято лаунчером в контракт 1.1.135** (singbox-launcher f3187610, D-139,
TASKS_LXBOX §132; норма — BACKUP.md §9 п. 5, блок «Состав шаблонных
серверов — каталог источника», поле — §2 и схема, коды — `registry/
backup_warnings.json`) с тремя уточнениями:

1. **`required: true` у сервера в шаблоне приёмника — удерживающая ссылка**
   (`used_by: required`): сборка эмитит такой сервер всегда, снятая запись
   вернулась бы сама. В шаблоне LxBox `required` у DNS-серверов нет;
   проверка реализована, чтобы правило было одно.
2. **Файл без `template_catalog`: снятие только в паре LxBox→LxBox**
   (`exported_by.app == lxbox` и приёмник LxBox), иначе слияние: старые файлы
   лаунчера полным списком не были. Для нас это ровно условие 1.1.134.
3. **`used_by` — закрытый словарь**: `final`, `default_domain_resolver`,
   `dns_rule:<server>`, `rule:<name>`, `group:<tag>`, `server:<tag>`,
   `preset:<id>`, `required`; пишется первая удерживающая ссылка по нему.

Плюс в норме: файл без серверов в `dns.servers` состав не трогает, даже с
каталогом. **Лаунчер в этом заходе только терпит поле** (ключ известен,
импорт — слияние без снятия); их модель каталога, миграция и экспорт с
каталогом — SPEC 173 лаунчера.

### 2. Что требуется от лаунчера

- **Модель §680**: посев каталога в состояние один раз (признак — наличие
  списка, как у нас, или свой эквивалент); пользователь удаляет шаблонные
  серверы и возвращает их из каталога; локи по ссылкам (пресет, правило,
  группа, final/default resolver, `domain_resolver`).
- **Миграция существующих состояний** (одноразовая): для каждого сервера
  каталога без записи создаётся запись `{kind: template, tag, enabled: <из
  шаблона>}`. После миграции отсутствие записи означает «удалён». Без неё
  первый же экспорт с новой версии выглядел бы как «пользователь удалил всё
  нетронутое».
- **Экспорт**: все записи списка + `template_catalog`.
- **Импорт**: правило п. 1.3 с локами и переходным п. 1.4.
- UI (удаление, каталог, подписи «used by») — на усмотрение лаунчера, поведение
  задаёт контракт.

### 3. Что меняется у нас (после выхода контракта)

- Экспорт полного LX-бэкапа (`dns_backup.dart`, `dnsToBackup`): поле
  `template_catalog` из `TemplateLoader` (теги `dns_options.servers`).
- Импорт (`applyDnsBackup`): правило п. 1.3 вместо проверки
  `exportedByApp == kLxAppLxBox`; проверка приложения остаётся только в
  переходной ветке п. 1.4 для файлов без `template_catalog`. Проверка локов —
  той же функцией, что считает «used by» на вкладке (§680 п. 3), по состоянию
  **после** слияния.
- Импорт: сброс `final` / `default_domain_resolver` с предупреждением; группа
  без известных членов → `enabled: false` + предупреждение. Коды
  предупреждений — в реестр импорта по образцу `backup_dns_entry_skipped`.
- Контракт: синк новой версии, корпус бэкапа (`test/contract/backup_corpus_test`)
  — кейсы: файл с каталогом, без каталога от своего и чужого приложения,
  удерживаемая локом запись, чужой тег в каталоге приёмника.
- Доки: спека 680 п. 6 (ссылка сюда), STORAGE.md/USER_GUIDE про бэкап — одна
  фраза, CHANGELOG EN+RU.

### 4. Как сделано у нас

- Экспорт: `dnsToBackup(templateCatalog:)` (`app/lib/services/dns/dns_backup.dart`),
  каталог — теги `dns_options.servers` шаблона (`backup_screen.dart`,
  `_templateDnsCatalogOrNull`); шаблон не загрузился — поле не пишется.
- Разбор: `LxDns.templateCatalog` (`lx_backup.dart`, `_dns10`); `null` — ключа
  нет (переходная ветка), `[]` — пустой каталог.
- Импорт: `applyDnsBackup(scene: DnsImportScene)` — порядок: слияние серверов
  и правил DNS → приехавшие пустые группы выключаются → `final`/default
  resolver файла сбрасываются → снятие по каталогу с локами. Сцена
  (шаблон приёмника, итоговые маршрутные правила, пресеты, умолчания
  резолверов) собирается в `planLxBackupImport` после расчёта `rules`,
  то есть по состоянию после импорта. Тег сервера пресета, активного после
  импорта (`activePresetDns`, тег с неймспейсом `<preset_id>:`), при сбросе
  `final`/default resolver считается доступным и без записи в списке — её
  досеет шаг 2 `resolveDnsServersList` на следующей сборке.
- Локи — `app/lib/services/dns/dns_server_holds.dart`: `dnsServerListHolds`
  (ссылки списка: группы, `domain_resolver`, final/default — общий расчёт с
  подписями «used by» вкладки, `dnsServerListRefs` строит метки поверх него)
  и `dnsServerFirstHolds` (весь словарь, первая ссылка). Снятие идёт
  кругами: сервер, которого держал только снимаемый кандидат, снимается на
  следующем круге.
- Ограничения: `rule:<name>` считает любое маршрутное правило с непустым
  `dns.serverTag` (шире лока вкладки, который смотрит только активную
  DNS-опцию: при импорте снятие необратимо); `dns_rule` у ссылок
  `kind: template` не считается — DNS-правил в шаблоне LxBox нет; пресеты
  раскрываются без узлов (`for_each_node` даёт `<узел>-dns`, тегов каталога
  у него не бывает). Кейсы корпуса бэкапа под 1.1.135 лаунчер не добавил —
  покрытие в `dns_backup_merge_test` и `lx_backup_roundtrip_test`.

## Проверка

- LxBox→LxBox (перенос на TV): на источнике удалён `opendns_udp` → у приёмника
  снят; `google_doh` под `dns_shield` → остаётся, предупреждение `kept`.
- Лаунчер→LxBox с `template_catalog` без `opendns_doh`/`yandex_dot`: оба
  остаются у приёмника; серверы, удалённые на десктопе и известные ему, сняты.
- Файл 1.1.134 без `template_catalog` от LxBox → как сейчас; от лаунчера →
  слияние.
- Файл с `final: foreign_tag` → после импорта `final` = умолчание шаблона,
  предупреждение; группа из одних чужих членов → ввезена выключенной.
- Корпус бэкапа и `lx_backup_roundtrip_test` зелёные.
