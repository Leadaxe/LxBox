# §361 — Запоздавший `Started` после смерти сервиса вешает кнопку «Стоп»

| | |
|---|---|
| Тип | bugfix (залипшее состояние, мёртвая кнопка Stop) |
| Статус | ✅ Исправлено — device-verified на эмуляторе |
| Дата | 2026-08-03 |
| Связанные | [`122 commandclient-migration`](../features/122%20commandclient-migration/spec.md) (дедуп `setStatus` — закрывает обратный случай, запоздавший `Stopped` после `Started`), [`140`](140-force-stop-port-race-and-connecting-timeout.md) (`forceStopScope` переживает `onDestroy`; тот же force-stop-путь), [`002`](002-blocking-stopvpn-intent-reset.md) (блокирующий `stopVPN` и его таймаут) |

## Симптом

Приложение в залипшем состоянии: шапка «Подключено», таймер сессии тикает,
трафик 0B/0B, список узлов пуст («В этом канале нет узлов»), канал не выбран.
Кнопка «Остановить» нажимается и ничего не делает — всё остальное в приложении
работает.

В логах:

```
[vpn] stopVPN returned false
[vpn] stopVPN: 5s timeout — native did not report Stopped
[cc] getGroups still unavailable after 12 attempts
[cc] running config unavailable after 12 attempts
```

## Root cause

Ключ — в native-логах (18:58, эмулятор):

```
18:58:11.318  doForceStop ENTER status=Starting
18:58:11.631  setStatus(Stopped)
18:58:20.885  onDestroy status=Stopped receiverRegistered=false   ← сервис мёртв
18:58:21.859  setStatus(Started) — sendBroadcast                  ← +1 секунда!
18:58:25.917  Start failed / Job was cancelled
```

`startSingbox` висит в блокирующем `cs.startOrReloadService(config, …)` — узел
не отвечает, JNI-вызов держит секунды. За это время `doForceStop` сносит сервис
и отменяет `serviceScope`, но **отмена корутины не прерывает блокирующий
JNI-вызов**. Возвращаясь, корутина идёт дальше по прямой и выполняет
`setStatus(VpnStatus.Started)` на уже уничтоженном сервисе, перезаписывая
`Stopped`, выставленный в `onDestroy` секундой раньше.

§122-дедуп здесь не спасает: он гасит повтор **одного** статуса (и ровно
обратный случай — запоздавший `Stopped` после нового `Started`), а тут два
разных статуса в другом порядке. Защита в `onDestroy` (сбросить `currentStatus`
в `Stopped`) отработала — но ДО запоздавшего `Started`.

Дальше цепочка до симптома:

| звено | состояние |
|---|---|
| `BoxVpnService.currentStatus` | `Started` (от запоздавшего вызова) |
| реальный сервис | уничтожен, `receiverRegistered=false` |
| `stopAwait` | `currentStatus != Stopped` ⇒ не уходит по быстрому пути, шлёт `ACTION_STOP` |
| приёмник `ACTION_STOP` | снят вместе с сервисом — **принимать некому** |
| результат | 5с таймаут → `stopVPN` = false → кнопка мертва, UI держит «Подключено» |

Пустой список узлов — то же самое звено: CommandClient стучится в отсутствующее
ядро.

## Решение

Два эшелона.

| # | место | правка |
|---|---|---|
| 1 (корень) | `BoxService.startSingbox` | перед `setStatus(Started)` — `if (!currentCoroutineContext().isActive) return` |
| 2 (страховка) | `BoxVpnService.stopAwait` | нет живого приёмника, а статус не `Stopped` ⇒ привести состояние к правде и ответить сразу, без 5с ожидания в пустоту |
| 3 (следствие 2) | `VpnPlugin.isForeignVpnActive` | сравнивать `NetworkCapabilities.ownerUid` со своим uid — свой осиротевший tun не считать чужим VPN |

Решения по месту:

| вопрос | решение |
|---|---|
| Почему `currentCoroutineContext().isActive`, а не `serviceScope.isActive`? | `serviceScope` пересоздаётся в `resetScope`; живой новый scope соврал бы про нашу отменённую корутину. Проверять надо контекст СВОЕЙ корутины |
| Как `stopAwait` (companion) узнаёт про приёмник? | Новый companion-флаг `stopReceiverAlive`, зеркало `BoxService.receiverRegistered` |
| Почему зеркало в сеттере, а не на сайтах присваивания? | Их шесть (register + пять путей снятия: onDestroy / onRevoke / doStop / doForceStop / exit). Забыть один — молча потерять страховку |
| Зачем второй эшелон, если корень закрыт? | Рассинхрон «статус живой, сервиса нет» может прийти и другим путём (OOM-kill сервиса, аварийный teardown). Второй эшелон превращает залипание в корректный стоп |
| Почему фикс №3 попал в эту же таску? | Он — прямое следствие №2, вскрытое им же (см. ниже). Чинить отдельно значило бы оставить релиз с ложным диалогом на каждый Start |
| API 24-28 без `ownerUid`? | Там остаётся прежнее поведение (любой VPN = чужой). Консервативно осознанно: лишний вопрос юзеру безопаснее молчаливого отзыва чужого туннеля |

### Фикс №3 — ложный «Активен другой VPN»

Всплыл сразу после №2 на том же стенде: на каждый Start приложение показывало
диалог «Сейчас работает VPN другого приложения. Переключиться на L×Box?».

В `dumpsys connectivity` висела осиротевшая VPN-сеть **с нашим собственным uid**:

```
NetworkAgentInfo{network{121} ni{VPN CONNECTED} InterfaceName: tun2
  TransportInfo: <VpnTransportInfo{... sessionId=sing-box ...}>
  OwnerUid: 10193     ← appId com.leadaxe.lxbox
```

`isForeignVpnActive` владельца не проверял: любая сеть с `TRANSPORT_VPN`
считалась чужой, а «своё» отсекал только ранний `return false` по статусу
сервиса. Пока статус залипал в `Started` (сам баг §361), метод выходил первой
строкой и дыры не было видно. Фикс №2 честно переводит статус в `Stopped`, когда
сервиса нет, — и приложение начало опознавать **свой же** брошенный tun как
чужой VPN. То есть мёртвая кнопка сменилась ложным диалогом.

## Device-verify

Эмулятор `emulator-5554` (arm64, Android 14).

Воспроизведение до фикса: включить подписку с недоступными из эмулятора нодами
(«Тайм-аут подключения») → Start → не дожидаясь, инициировать остановку. Старт
уходит в force-stop, следом прилетает запоздавший `Started` — состояние
залипает, кнопка «Стоп» мертва.

После фикса, проверено:

- залипшее состояние снято, штатные старт/стоп исправны: туннель поднимается
  (113 узлов, активная нода, трафик идёт), `ACTION_STOP` → `doStop` →
  `Stopped` за 1.3с;
- смена подписки применяется, состав узлов в конфиге соответствует включённым
  подпискам, `config_dirty` гасится (§360);
- ложного «Активен другой VPN» нет; приложение корректно переподключается к
  собственному живому туннелю после гибели UI-процесса.

**Границы проверки (честно):**

- Саму гонку из п.1 после фикса воспроизвести не удалось — узлы стенда стали
  отвечать (95–155 мс), старт успевает завершиться и в force-stop не попадает.
  Гарантия по разбору логов и кода, не по повторному замеру.
- Фикс №3 проверен только на отсутствие регрессии. Осиротевший tun повторно не
  воспроизводится: все штатные пути (`force-stop`, `kill -9`,
  `/action/force-stop-vpn`) система отрабатывает чисто, интерфейс не остаётся.
  Он и рождался из аварийного пути, который закрыт фиксами №1–2. Основание
  самого фикса — улика из живого сеанса (`dumpsys`: VPN-сеть `ni{VPN CONNECTED}`
  с `OwnerUid: 10193` при мёртвом сервисе), а не гипотеза.
