## Problem

О провале сборки в F-Droid мы узнаём от мейнтейнера каталога, когда он заводит
issue. Сборка 2.25.19 упала 05.11.2026 на получении srclib: пин
`cronet-go@0d28acc4` в рецепте стал недостижим после того, как апстрим 03.11
переписал ветку `go`. Это третий такой случай (06.08, 31.08). Между падением
джобы бота (05:04 UTC) и issue #196 (08:04 UTC) прошло три часа, и всё это
время у нас не было сигнала.

Исправление рецепта ушло в
[fdroiddata!55894](https://gitlab.com/fdroid/fdroiddata/-/merge_requests/55894)
(заменяет MR бота !55831). Пройдёт ли там сборка — тоже нужно узнать не от
человека.

## Diagnosis

- У каждого MR в `fdroid/fdroiddata` (GitLab project `36528`) есть
  `head_pipeline` со статусом. Пайплайн MR бота идёт в проекте
  `fdroid/checkupdates-bot-fdroiddata`, нашего — в форке `leadaxe/fdroiddata`;
  поле `head_pipeline.project_id` называет проект в обоих случаях.
- API GitLab для этих проектов читается без токена (проверено 05.11.2026:
  `merge_requests`, `merge_requests/:iid`, `pipelines/:id/jobs`).
- MR бота называется `bot: Update L×Box to <versionCode>`, наши — `L×Box …`;
  ветка-источник в обоих случаях начинается с `com.leadaxe.lxbox`.
- Ветка по умолчанию в `Leadaxe/LxBox` — `main`. GitHub запускает `schedule`
  только из файла workflow на ветке по умолчанию: сторож начнёт ходить по
  расписанию после того, как файл попадёт в `main`.

## Solution

Отдельный workflow `.github/workflows/fdroid-watch.yml` и скрипт
`scripts/fdroid-mr-watch.sh`.

**Запуск.** `schedule` раз в сутки в 09:30 UTC (бот F-Droid отрабатывает около
05:00 UTC, сборка трёх ABI идёт до трёх часов) и `workflow_dispatch`. Права:
`issues: write`, остальное — чтение.

**Что смотрит.** Открытые MR проекта `36528`, у которых ветка-источник
начинается с `com.leadaxe.lxbox`. Судит по одному — самому новому (наибольший
`iid`): это последняя попытка, более старый упавший MR ею заменён. Открытых MR
нет — сторож молчит.

**Вердикт по `head_pipeline.status` нового MR:**

| Статус | Действие |
|---|---|
| `success` | ничего, строка в логе |
| `failed` | тревога (ниже) |
| остальное (`running`, `pending`, `created`, `canceled`, нет пайплайна) | вердикта нет, строка в логе; следующий прогон через сутки |

**Тревога.** Issue-носитель задан в workflow переменной `FDROID_WATCH_ISSUE`
(сейчас `196`).

1. Если в issue уже есть комментарий с меткой
   `<!-- fdroid-watch pipeline:<id> -->` этого пайплайна — ничего не делать
   (одна тревога на пайплайн, не на каждый прогон).
2. Иначе: issue закрыт — переоткрыть; добавить комментарий на английском:
   ссылка на MR, ссылка на пайплайн, упавшие джобы (имя и ссылка, из
   `pipelines/:id/jobs?scope[]=failed`), метка.

**Код возврата.** Тревога — не провал прогона: сигнал несёт issue, красный
прогон дал бы второе письмо о том же. Ненулевой код — только когда сторож не
смог выполнить проверку (GitLab не ответил, ответ не разобрался, `gh`
отказал).

**Проверка без побочных действий.** `DRY_RUN=1` печатает, что было бы сделано,
и ничего не пишет в GitHub; `FDROID_WATCH_MR=<iid>` подменяет выбор MR.

## Risks and edge cases

- Сторож не предсказывает сбой, а сообщает о случившемся: не позже чем через
  сутки и без участия мейнтейнера F-Droid. Проверка достижимости пинов до
  релиза в задачу не входит (решение владельца: сторож смотрит на сборку MR).
- Новый упавший MR при закрытом или слитом предыдущем: тревога уйдёт в тот же
  issue, он переоткроется.
- MR бота упал, наш заменяющий MR ещё не открыт: тревога по MR бота — это и
  есть нужный сигнал.
- Пайплайн перезапущен вручную и снова упал: у него новый `id`, будет новая
  тревога.
- GitLab меняет лимиты анонимного API: прогон станет красным, это видно в
  Actions.

## Verification

- `DRY_RUN=1 FDROID_WATCH_MR=55831 scripts/fdroid-mr-watch.sh` — MR бота с
  упавшим пайплайном: печатает тревогу с джобой `fdroid build` и то, что issue
  #196 открыт и получил бы комментарий.
- `DRY_RUN=1 FDROID_WATCH_MR=54960 scripts/fdroid-mr-watch.sh` — пайплайн
  `success`: «ничего».
- `DRY_RUN=1 scripts/fdroid-mr-watch.sh` — выбирает !55894.
- После попадания в `main`: ручной запуск `workflow_dispatch`, зелёный прогон.

## Open / follow-up
