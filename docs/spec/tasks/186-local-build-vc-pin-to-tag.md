# §186 — Локальная сборка не должна обгонять релиз по versionCode

**Тип:** tooling / dev-ergonomics fix
**Статус:** ✅ Реализовано
**Приоритет:** Medium (ломает возможность ставить собственные релизы с интернета)
**Связано:** §125 (versionCode авто-согласование), [[apk-build-install-flow]],
[[project_dev_endpoints]]

## Симптом (юзер)

«Надоело что я не могу скачивать собственные релизы!» — после локальной сборки
release с интернета (GitHub Releases) не ставится: Android блокирует как downgrade.

## Корень

**Важно — кто что считает (проверено `aapt dump badging` на собранном APK):**

- `pubspec.yaml` `version: X.Y.Z+<build-number>` — build-number = **просто номер
  коммита** (`git rev-list --count`). И CI, и локальный скрипт пишут сюда голый
  count. НИКТО руками множитель не добавляет.
- **ABI-множитель добавляет САМ Flutter** при `--split-per-abi` (из коробки, в
  `flutter.gradle`): `abiCodes = [armeabi-v7a:1, arm64-v8a:2, x86_64:3]`,
  итоговый `versionCode = build-number + abiCode×1000`. Для arm64 → `+2000`.
  Это одинаково для CI и локалки — множитель НЕ источник расхождения.

Источник расхождения — **разные build-number'ы** (count на разных коммитах):

- **Релиз** собирается CI на коммите **тега** → `count(tag)` зафиксирован.
  Пример: v2.5.0 на теге → build-number=876 → Flutter +2000 → arm64 **vc=2876**.
- **Локальная** сборка идёт на ветке разработки, где коммитов БОЛЬШЕ, чем было
  на момент тега → `count(HEAD) > count(tag)` → build-number выше → vc выше.
  Пример: HEAD count=878 → 878+2000 → локальный **vc=2878** > 2876.

Каждый новый коммит увеличивает разрыв. Как только локалка с vc=2878 стоит на
телефоне — релиз v2.5.0 (vc=2876) **строго меньше** → downgrade-блок → не ставится.

§125 предполагал «локалка попадает в тот же диапазон 2xxx» — но «тот же диапазон»
≠ «не выше релиза». Диапазон (множитель) совпадает, а build-number обгоняет.

## Решение

Локальная сборка пинит build-number к **последнему релизному тегу**, а не к HEAD:
`BUILD_NUMBER = git rev-list --count <last-vN.N.N-tag>`. Flutter добавит тот же
`+2000` (arm64) → локальный vc = `count(tag) + 2000` = **ровно релизный vc**.

При равном versionCode `adb install -r` проходит (downgrade-блок только на СТРОГО
меньший vc) → локалка ⇄ релиз взаимозаменяемы в обе стороны:
- релиз с интернета встаёт поверх локалки (равный vc — ОК);
- локалка встаёт поверх релиза (равный vc — ОК);
- локалка встаёт поверх локалки (равный vc — ОК).

versionName при этом остаётся информативным: `sync-pubspec-version.sh` для
versionName использует `-dev.<since-tag>` суффикс (показывает «на сколько ушли от
тега»), но build-number (= versionCode) пинится к тегу. Так в About видно что это
dev-сборка, а vc не обгоняет релиз.

## Реализация

`scripts/build-local-apk.sh`:
- НЕ зовём `sync-pubspec-version.sh` вслепую (он пишет HEAD-count в build-number).
- Вместо: вычисляем `TAG_COUNT = git rev-list --count <last-tag>`, versionName из
  того же тега (`X.Y.Z-dev.<since>`), пишем `version: <name>+<TAG_COUNT>` в pubspec.
- CI (`ci.yml`) НЕ трогаем — релиз правильно считает count на теге (он и есть тег).

## Границы / риски

- НЕ трогать CI-формулу — релиз корректен (count на коммите тега).
- НЕ трогать `sync-pubspec-version.sh` напрямую (его зовёт pre-commit hook для
  pubspec в репо; build-number там для коммитов нужен растущим). Меняем ТОЛЬКО
  build-local-apk.sh — он формирует версию для локального APK независимо.
- После НОВОГО релиза (новый тег) локальный vc автоматически подтянется к новому
  тегу (count вырастет) — релизы и дальше ставятся поверх. Самоподдерживается.
- Если на ветке нет ни одного тега `vN.N.N` — fallback на старое поведение
  (HEAD-count), чтобы сборка не падала.
