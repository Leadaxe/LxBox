## Проблема

Правило `domain_suffix: rutracker.org → vpn-1` при `route.final: direct-out`
не срабатывает для Chrome: соединение уходит напрямую и рвётся
(`ERR_CONNECTION_ABORTED`). `curl` с того же устройства идёт через VPN.

Без FakeIP ядро узнаёт домен соединения только из сниффера. Chrome
запрашивает у DNS HTTPS-запись (тип 65), получает из неё ECH-конфиг
Cloudflare и шифрует настоящее имя. В ClientHello остаётся внешнее имя
`cloudflare-ech.com`; сниффер берёт его как домен, правило по домену не
совпадает, трафик уходит по `route.final`. Ошибки нет, правило включено —
пользователь причины не видит.

## Диагностика

- Профайлер автора: DNS-запросы Chrome (A и HTTPS) про `rutracker.org` шли
  через наш DNS; TLS/QUIC-соединения Chrome — под `cloudflare-ech.com` в
  `direct-out`. Secure DNS в Chrome выключали — без изменений.
- В приложении блокировка уже есть, но только внутри пресета FakeIP
  (`force`, «Block HTTPS records»): `query_type [HTTPS, SVCB] →
  predefined NOERROR`. Без FakeIP её нет.
- Существующие DNS-аспекты правила (зеркало с сервером, Force IPv4,
  Fixed IP) закрыты гейтом «нет портов, диапазонов, протоколов, `network`»
  (`CustomRule.dnsMirrorEligible`, `forceIpv4Eligible`). У правила автора
  стоит `network: [tcp, udp]` — с этим гейтом оно не получило бы и новую
  опцию. Техническая причина гейта: inline-правило кладёт порты в тот же
  headless-набор, на который ссылается DNS-зеркало, а у DNS-запроса порта
  сайта нет.
- Ядро (`sing-box-lx` v1.14.4-lx.35, `dns/router.go`): DNS-правило с
  `query_type` выключает старый DNS-режим (`defaultRuleDisablesLegacyDNSMode`);
  в новом режиме ссылка на набор, где одни адреса, — ошибка старта
  (`validateLegacyDNSModeDisabledDefaultRule`), смешанный набор (домены +
  адреса) проходит.

## Решение

### 1. Пресет «Block HTTPS/SVCB records» (`block-https`)

- Одно DNS-правило:
  `{"query_type": ["HTTPS", "SVCB"], "action": "predefined", "rcode": "NOERROR"}`.
- `default: false`. В `kLateDefaultPresetIds` не входит — существующим
  пользователям сам не добавляется. Не `locked`.
- Сортируемый. При добавлении встаёт сразу после Traffic Processing:
  `ui.num = 10` (ось `num` по возрастанию: `0` — traffic-processing,
  следующий занятый — `940`). Vars нет: без `dns_enable` DNS-часть пресета
  действует, пока пресет включён.
- Переключатель `force` внутри пресета FakeIP не меняется. Включены оба —
  в конфиге два одинаковых правила, это допустимо.

### 2. Опция правила «Block HTTPS/SVCB records» (`dns.blockHttps`)

- Булево поле в объекте `dns` правила, рядом с `forceIpv4`. Нет поля — `false`.
- Переключатель в секции «DNS & Resolve» редактора, рядом с Force IPv4 и
  Resolve before routing.
- Inline-правило: доступен, когда заполнено хоть одно из `domain`,
  `domain_suffix`, `domain_keyword`, `domain_regex`. Доменов нет —
  переключатель недоступен, правило блокировки не эмитится, даже если в
  хранилище лежит `true`.
- Inline-правило: галка ставится сама, когда поле доменов в редакторе из
  пустого стало непустым (в том числе повторно — стёрли и ввели заново).
  Пользователь может её снять; при дальнейшем вводе в непустое поле она
  обратно не ставится.
- srs-правило: доступен всегда, по умолчанию выключен.
- Уже сохранённые правила не меняются. Debug API и бэкап несут значение
  как записано.
- Не зависит от `dns.enabled` и выбранного сервера. Эмитится и при ответе
  Fixed IP.

### 3. Сборка: единообразно с Force IPv4

- Оба — `predefined`-правило в `dns.rules` со ссылкой на набор правила и
  теми же DNS-безопасными AND-полями, что у существующих зеркал.
- Порядок внутри одного правила: Block HTTPS (`query_type`), затем
  Force IPv4 (`ip_version: 6`), затем зеркало с сервером или Fixed IP.
- Пустой матч (нет ни набора, ни `inbound`) — правило блокировки не
  эмитится, иначе оно глушило бы HTTPS-записи глобально.

### 4. Порты inline-правила — на маршрутном правиле

- `port` и `port_range` inline-правила больше не кладутся в headless-набор,
  а ставятся на маршрутное правило — как уже сделано у srs.
- Смысл правила прежний: (домены/адреса набора) И (порт). Набор становится
  пригодным для ссылки из DNS-правила.
- Правило только с портами (набор пуст) — маршрутное правило без `rule_set`.

### 5. Гейт портов снят со всей секции «DNS & Resolve»

- `dnsMirrorEligible`, `forceIpv4Eligible`, `dnsFixedActive` больше не
  требуют пустых `ports`, `portRanges`, `protocols`, `network`. Остаётся
  `dnsLayerEligible` (§692) и прежние собственные условия (сервер у зеркала).
- Если у правила есть порт, диапазон, протокол или `network`, в секции
  подсказка: «DNS options apply to these domains on any port and protocol».

### 6. Остальное

- Debug API `/rules`: поле `block_https` в объекте `dns` (в стиле соседних
  ключей API), справка `/help`.
- Бэкап: поле едет в JSON правила.
- Вкладка DNS: строка правила показывает аспект Block HTTPS так же, как
  Force IPv4.
- Документация по карте `docs/spec/README.md`: TEMPLATE (пресет), STORAGE
  (поле), GUARDS / ARCHITECTURE при необходимости, USER_GUIDE (ECH и правила
  по домену), `docs/api` (Debug API), CHANGELOG Unreleased.

## Риски и граничные случаи

- **Принято владельцем.** srs-правило с чисто адресным набором (geoip) и
  включённой галкой не даёт ядру стартовать — тот же известный риск, что у
  Force IPv4 (§692).
- **Принято владельцем.** У пользователя есть srs-правило с адресным набором
  и включённой DNS-опцией, и оно работает только потому, что ядро в старом
  DNS-режиме (FakeIP и Force IPv4 выключены). Первая галка Block HTTPS или
  пресет приносят `query_type`, режим становится новым, старт падает.
  Происходит только после действия пользователя; лечится выключением
  DNS-опции у того srs-правила. Предупреждение при сборке не делаем:
  содержимое `.srs` не читаем, оно было бы ложным для наборов с доменами.
- **Смена текста конфига.** У существующих правил с портами меняется
  маршрутное правило и набор; смысл тот же. Эталонные конфиги обновляются.
- **Force IPv4 у правил с портом или `network`.** Если галка была включена,
  а условие гейта не выполнялось, она молча не действовала. После снятия
  гейта начнёт действовать — AAAA для доменов правила глушится на всех
  портах.
- **Собственный DoH приложения.** Chrome с заданным провайдером Secure DNS
  и Firefox с DoH спрашивают мимо нашего DNS — блокировка на них не
  действует. Называется в подсказке переключателя и в USER_GUIDE.
- **Собственные DNS-правила с вкладки DNS.** Тела DNS-правил пресетов и
  зеркала правил идут одной группой в порядке списка правил (§117), пресет
  в ней первый. DNS-правила пользователя с вкладки DNS, стоящие выше якоря
  группы, получают HTTPS-запрос раньше блокировки — для их доменов
  HTTPS-запись уйдёт на сервер. Свойство существующего порядка.
- **Правило только с портами** больше не порождает inline-набор с именем
  правила. DNS-правило с вкладки DNS, ссылавшееся на такой набор по имени,
  станет висячим и выпадет с кодом (§588).
- **Потери при блокировке.** ECH для затронутых доменов и подсказка HTTP/3
  из HTTPS-записи (первый заход по TCP).

## Проверка

- Unit: сборка inline-правила с доменами и портом — порты на маршрутном
  правиле, набор без портов, в `dns.rules` правило блокировки со ссылкой на
  набор; порядок Block HTTPS → Force IPv4 → сервер; `blockHttps: true` без
  доменов не эмитится; srs с галкой; Fixed IP с галкой; правило с `network`
  и Force IPv4 эмитит AAAA-глушилку.
- Unit: пресет `block-https` даёт одно DNS-правило; на существующей
  установке сам не появляется.
- Widget: галка ставится при заполнении доменов, недоступна без доменов,
  не возвращается после ручного снятия; подсказка при порте/протоколе.
- Корпус контракта `rule_dns` (фикстуры 1.1.173) — раннер зелёный.
- CI зелёный. Устройство: сценарий автора (Chrome + сайт Cloudflare с ECH +
  правило по домену) — по возможности на эмуляторе, иначе отмечается как
  непроверенное.

## Нерешённое / follow-up

- Пометка ECH в профайлере соединений («внешнее имя, сайт скрыт») —
  отдельная задача; сначала выяснить, может ли ядро отдавать флаг ECH.
- `remove_client_subnet` в опциях правила — не делается.
- Эквивалентность «порт в наборе» и «порт на правиле» выведена из формулы
  правил sing-box; подтверждается тестами сборки и прогоном на ядре.
