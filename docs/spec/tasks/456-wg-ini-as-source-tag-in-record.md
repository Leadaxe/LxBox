## Проблема

Узел из `.conf` хранил источником не файл, а синтетическую ссылку
`wg://…#имя-файла`, в которую INI переводился ради тега (§243). Источник
переставал быть «тем, что пришло»: комментарии и порядок файла терялись,
вид записи был `uri` вместо `wg_ini`, лаунчер тот же файл хранит как INI.
Ради этого же существовал `memberRawFor` — функция, которая при добавлении в
папку решала, что записать члену, и при пустом источнике пересобирала текст
через `toUri()`. После §454 источник есть у всех узлов, функция лишняя.

## Решение

### 1. Источник WireGuard из INI — сам INI

`parseWireguardIni(config, {nameHint})` даёт узлу `rawSource = config`, байт в
байт. Синтетический `wg://` остаётся внутренним шагом парсера (`_iniToUri` →
`parseWireguardUri`), наружу не выходит. Поле `WireguardSpec.rawIni`
удалено — оно дублировало бы источник.

> **§472 шаг 7 (18.09.2026): синтетического `wg://` больше нет и внутри.**
> INI стал ещё одним МАППЕРОМ конвейера (`mapWireguardIni`, точка входа
> `parseIniViaPipeline`): текст INI переводится в карту sing-box напрямую, без
> сборки query с percent-кодированием и обратного её разбора. Правила §456 не
> изменились ни в чём — `rawSource` это текст файла байт в байт, имя по
> убыванию силы то же, тег остаётся полем записи. Подробности — спека 472,
> раздел 13.6.

`vpn://` (Amnezia, §110): каждый узел контейнера получает источником свой
INI-текст (так уже делает `AmneziaConfig` → `parseWireguardIni`); общая
ссылка `vpn://` остаётся `origin.raw` записи-контейнера.

### 2. Имя узла из INI

INI тега не несёт. Начальное имя при разборе, по убыванию силы:

1. первый комментарий сразу под `[Peer]` без `=` — Proton пишет туда имя
   сервера (`# CH-FREE#11`); строки вида `# Bouncing = 0` в `[Interface]`
   не годятся;
2. `nameHint` — имя файла при импорте (§243), тег записи при чтении
   хранения (§3), поле Tag редактора при Save;
3. `WireGuard`.

### 3. Тег — поле записи

Запись хранения (`server`, член папки) и раньше писала `tag` (контракт 1.0).
Правило чтения «текст побеждает, расхождение — заметка» остаётся для
`uri`/`json`, где тег лежит в тексте. Для `origin.kind: wg_ini` тег записи
**применяется**: узел разбирается с `nameHint = tag`, заметка не пишется.

В памяти тег живёт в узле (как у всех). Чтобы он пережил перечитывание
текста, у `FolderMember` появляется `nameHint` (участвует в `==`/`hashCode`:
тот же INI под другим именем — другая запись), а `updateConnectionAt` /
`updateMemberAt` принимают `nameHint`. Экран узла при Save INI-источника
передаёт поле Tag.

Контракт не меняется: `tag` у записи был, `origin.kind: wg_ini` был; лаунчер
тег в дедупе не сравнивает, INI сравнивает текстом.

### 4. `memberRawFor` удалён

Член папки получает `raw: n.rawSource` и `nameHint` (тег узла, если источник
INI). Фолбэк имени файла (`nameFallback`) остаётся только для ссылок без
своего имени (`rawWithName` во фрагмент); INI и JSON несут имя сами: INI —
через `nameHint`, JSON — в теле.

Точки: `addMembersToFolder`, `addUrlSnapshotToFolder`, перенос одиночного
сервера в папку. Одиночный импорт `.conf`: `rawBody` = INI, тег — в узле и в
записи.

### 4a. Побочные находки (всплыли на тестах)

- **Авто-эмодзи (§090 G2b) у INI-узла.** `_autoEmoji` дописывал эмодзи в
  текст источника (фрагмент ссылки / поле `tag` JSON). У INI тега в тексте
  нет, дописать некуда — эмодзи молча терялось. Теперь на ветке `.conf`
  эмодзи ставится прямо в `tag` и `label` узла; тег — поле записи, поэтому
  переживает рестарт. `label` нужен отдельно: список серверов показывает
  его (`SubscriptionEntry.displayName` предпочитает `label` тегу).
- **`TailscaleSpec` без `rawSource`.** Конструктор зашивал `rawSource: ''`,
  и `parseSingboxEntry` единственным из всех веток не передавал `src`.
  Пока член папки собирался через `memberRawFor` (текст пересобирался
  `toUri()`), дыра была не видна; с `raw: n.rawSource` член Tailscale стал
  пустым и узел терялся. Узел теперь несёт свой объект outbound'а, как все
  остальные типы из JSON.

### 5. Старые записи

Записи с `wg://…#имя` остаются `uri` и читаются как раньше. Миграции нет:
исходного INI у них уже не было.

## Доработка 28.11.2026 — `tag` записи главнее `origin` у любого вида

**Решение владельца 28.11.2026:** `tag` записи, если он есть, всегда
приоритетнее всего, что лежит в `origin`; переименование `origin` не меняет.
Действует и в LxBox, и в лаунчере. Заменяет правило §439 п. 1 «текст
побеждает» и исключение только для `wg_ini` из §3 выше.

### Проблема

Save узла с источником `vpn://` отвечал «Could not parse server config»
(жалоба 27.11.2026, 2.25.22). Редактор переносил имя в текст источника и
дописывал `#WireGuard` к упакованной ссылке, после чего декодер её не читал.
Так же молча не срабатывал эмодзи по умолчанию. Корень — имя узла жило в
тексте источника. У `wg_ini` правило тоже выполнялось не полностью: `tag`
шёл подсказкой, и комментарий под `[Peer]` был сильнее.

### Правила

1. **Чтение.** У записи `server` и у члена папки непустой `tag` заменяет имя
   первого узла, разобранного из `origin.raw`, при любом `origin.kind`. Нет
   `tag` — имя из текста. Группа (`kind: auto`) не затрагивается. Остальные
   узлы многоузлового источника называются по тексту. Заметка «the text wins»
   снята.
2. **Переименование** (поле Tag) пишет только `tag`; `origin.raw` остаётся
   байт в байт. Имена не-первых узлов JSON-документа (аккордеон «Nodes in
   this source») по-прежнему правятся в тексте: своего поля записи у них нет.
3. **Правка Source** — новый ввод. Поле Tag тронуто — берётся оно. Не тронуто
   и в тексте изменили имя (фрагмент ссылки, `tag` JSON) — берётся имя из
   текста. Иначе (в тексте имени нет или оно прежнее) имя записи сохраняется.
4. Имя едет с узлом: перенос в папку и из папки, восстановление из бэкапа.
5. Тело `singbox`, уходящее в конфиг дословно, получает в `tag` имя узла.

### Лаунчер

По коду поведение уже такое: переименование пишет только имя записи, пересборка
узла из `origin` заменяет тело и имя не трогает, правка тела на вкладке JSON
имя тоже не меняет. Правок кода не требуется; в приложении не проверялось.
Норма записана в BACKUP.md, поле `tag` (контракт 1.1.185); в репозитории
лаунчера — коммит `0a210211`, копия контракта в LxBox синхронизирована
(1.1.186). Отдельного кейса корпуса у этого правила нет.

Различие: правило 3 (имя, изменённое в тексте Source, переходит в `tag`) есть
только в LxBox; в контракт оно не вошло.

### Имя у `vpn://`

Решение владельца 28.11.2026: `vpn://<base64>#имя` читается по той же схеме,
что `awg://<base64>#имя`. Всё после первого `#` — имя (percent-encoded), оно
сильнее комментария под `[Peer]` и имени профиля; у профиля с несколькими
контейнерами заменяет имя профиля. Норма — BACKUP.md (контракт 1.1.186), кейс
`corpus/body/uri_list/vpn_link_name`. Эмодзи по умолчанию узлу из `vpn://`
ставится именем записи: фрагмент переименовал бы и прочие контейнеры.

### `#` внутри base64

Меткой ссылки считается только `#…`, стоящий в самой ссылке до декодирования;
`#` внутри base64 — часть пейлоада. Что было сломано (оба случая — узла нет):

| Ссылка | Лаунчер (до 2.4.5 включительно) | LxBox (до 2.26.0 включительно) |
|---|---|---|
| `awg://<base64 .conf>` с комментарием `#` под `[Peer]` | ошибка | читал |
| `vmess://<base64 JSON>` с `#` в `ps` | ошибка | ошибка |

Исправлено: лаунчер `b8fdb8b5` (`core/config/linkmap/parse.go`), LxBox —
`_decodeFormJson` в `services/parser/engine/interpreter.dart` (метка берётся из
исходной ссылки и срезается только как суффикс). Контракт 1.1.187, кейсы
`corpus/uri/wireguard/awg_conf_base64_hash_comment` и
`corpus/uri/vmess/ps_hash_inside_base64`, проходят у обеих сторон. В приложениях
не проверялось.

### Границы

- Эмодзи по умолчанию на входе и имя из файла при добавлении в папку
  по-прежнему пишутся в текст (кроме `vpn://`): это не переименование.
- Хранение `origin` у вставленного `vpn://` (ссылка, а не `.conf`, как велит
  BACKUP.md с 1.1.80) этой доработкой не меняется.
