| | |
|---|---|
| Тип | bugfix (тихий: узлы не поднимаются, ошибки в UI нет) |
| Статус | 🔧 Фикс + тесты, DEVICE-PENDING |
| Дата | 2026-08-03 |
| Связанные | [`028 antidpi sni obfuscation`](../features/028%20antidpi%20sni%20obfuscation/spec.md) (источник бага), [`281`](281-utls-fingerprint-normalize.md), [`343`](343-reality-short-id.md) |
| Источник | Жалоба пользователя (Telegram, 02–03.08.2026) + дамп `lxbox-dump-2026-08-03T20-13-39.json` |

## Проблема

`applyMixedCaseSni` (§028) рандомизирует регистр `server_name` у всех
first-hop outbound'ов, **не исключая REALITY**. Для обычного TLS это
безвредно (RFC 6066 §3 — SNI case-insensitive, на чём и построена §028).
Для REALITY — фатально.

Механика по исходникам ядра:

1. Клиент шифрует `SessionId` через AES-GCM, где AAD — `hello.Raw`, весь
   ClientHello **вместе с байтами SNI**
   (`common/tls/reality_client.go`, `aesGcmCipher.Seal(…, hello.Raw)`).
2. Сервер парсит SNI из ClientHello побайтово, **без нормализации регистра**
   (`utls@v1.8.7/handshake_messages.go:525`), и матчит по map с точным
   строковым ключом: `config.ServerNames[hs.clientHello.serverName]`
   (`utls@v1.8.7/reality.go:385`). Map заполняется одним ключом —
   `options.ServerName` как есть (`common/tls/reality_server.go:95`).

Промах по map → сервер не признаёт клиента, молча уходит в fallback на
маскировочный сайт → `reality verification failed`. Одна изменённая буква
где угодно в имени ломает хендшейк так же, как все.

**Симптом у пользователя.** Расходящаяся пара наблюдений, которая и вывела
на причину:

| действие | результат | почему |
|---|---|---|
| запуск VPN | ни один узел не работает | боевой конфиг идёт через `applyMixedCaseSni` |
| пинг в списке серверов | пинг есть | probe-конфиг (`buildProbeConfig`) собирается своим путём, **мимо** post-steps билдера — SNI остаётся оригинальным |

В дампе: `tls_mixed_case_sni = true`, все 17 узлов двух подписок — REALITY,
`server_name` вида `ya.rU`, `rf-11.RIta-clOuD.coM`, `VPn.XOREALiS.coM`.
Остальные параметры узлов валидны (short_id, public_key, fingerprint, отсутствие
`flow`+`transport`), маршрут здоров (`route.final = vpn-1`, селектор полон) —
mixed-case SNI единственная поломка на пути этих узлов.

## Решение

Гейт в `applyMixedCaseSni`: outbound с `tls.reality.enabled == true`
пропускается целиком. Рядом с существующим `detour`-гейтом и по образцу
`applyTlsFragment`, где так же точечно исключён `naive` (§270).

Признак — именно флаг `reality.enabled`, а не тип outbound'а: REALITY бывает
не только под vless, а обычный vless без REALITY рандомизировать можно.

Решения по месту:

| вопрос | решение |
|---|---|
| Смягчить рандомизацию (только первая метка / не трогать домены-маскировки)? | Нет. Матч по map идёт по строке целиком — любая изменённая буква ломает хендшейк. Гейт бинарный |
| Выключать тумблер целиком при REALITY-узлах? | Нет: тумблер остаётся рабочим для обычного TLS. Гейт per-outbound, не глобальный |
| Предупредить в UI? | Да — help-текст тумблера дополнен строкой про REALITY (иначе пользователь считает, что обфускация покрывает все узлы) |
| Чинить ли то, что probe идёт мимо post-steps? | Не в этой таске. После фикса расхождения нет; сам факт «probe без DPI-обвязки» — отдельное решение (probe меряет доступность узла, не обфускацию) |

## Почему баг тихий

Ядро не логирует причину в UI: узел просто не поднимается. Пользователь
видит «не пингуется и не запускается» на всех узлах сразу, а те же узлы в
других клиентах (где такого тумблера нет) живые — вывод «сломано ваше
приложение», без шанса догадаться про настройку. Затронут любой, кто включил
тумблер на REALITY-подписке; тянется с §028 (2026-04-19).

## Тесты

`test/builder/mixed_case_sni_test.dart` — группа §363:

- REALITY outbound (`tls.reality.enabled = true`) — `server_name` побайтово
  не тронут;
- `reality: {enabled: false}` — рандомизируется как обычный TLS;
- смешанный конфиг: REALITY-узел не тронут, соседний обычный TLS —
  рандомизирован (гейт per-outbound, не глобальный);
- REALITY без `server_name` / с пустым — не падает.
