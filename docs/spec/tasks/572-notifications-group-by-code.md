## Проблема

Список уведомлений узла (`NodeNotificationsView`) группирует записи только по
уровню. Внутри уровня каждое уведомление — своя плитка со своим полным разбором
(«What happened / Why it happens / What you can do»).

Узел из Xray-JSON подписки получает по одному `json_field_unknown` на каждое
непрочитанное поле. У узла VLESS·xhttp·Reality это семь плиток подряд: заголовки
отличаются только именем поля, разбор под каждой дословно тот же. Замер на
устройстве (подписка из 19 узлов, 27.09.2026): у 18 узлов от 2 до 8 записей, из
них `json_field_unknown` — 95 из 100.

Владелец: однотипные сообщения смотрятся плохо; нужен общий код, количество,
список полей и разбор один раз на всю группу.

## Диагностика

- Компонент один на три поверхности (§479): секция Notifications вкладки
  Diagnostics (`widgets/node_diagnostics_tab.dart`), шторка из списка узлов
  (`node_warnings_sheet.dart`), шторка отказа ввода (§500). Правка компонента
  меняет все три сразу — отдельной работы по поверхностям нет.
- Код уведомления даёт `warningCodeOf(warning)`; у рукописного класса без кода
  он `null`.
- Тексты кода берутся из реестра контракта (`registryText` / `registryCause` /
  `registryFix`) с подстановками `path` / `value` / `params`. Заголовок кода
  тоже несёт подстановку: `title_en` у `json_field_unknown` —
  `Configuration: field {query_name} not read`. Заголовка без поля в контракте
  нет.

## Решение

Правится только `app/lib/screens/subscription_detail_screen/widgets/node_notifications_view.dart`
и его тесты. Модель предупреждений, реестр, Debug API и строки списков узлов не
меняются.

### Правило группировки

Внутри уровня записи с одинаковым кодом (`warningCodeOf`) собираются в группу.

| Случай | Что показывается |
|---|---|
| Код встречается в уровне один раз | Плитка как сейчас, без изменений |
| Код `null` (рукописный класс без кода) | Плитка как сейчас, в группу не входит |
| Код встречается 2 раза и больше | Одна плитка-группа |

Порядок групп и одиночных плиток — по первому вхождению кода в уровне. Порядок
записей внутри группы — исходный.

### Плитка-группа

```
ⓘ Configuration: field … not read            7  ⌄
    streamSettings.finalmask.tcp.0.type
    streamSettings.finalmask.tcp.0.settings.delay
    …
    streamSettings.tcpSettings
    What happened
    Why it happens
    What you can do
    Details
```

- **Заголовок** — заголовок кода (`title_<lang>`) с подстановками по правилу
  ниже. Справа число записей группы.
- **Список записей** — по строке на запись, моноширинным шрифтом, как путь в
  нынешней плитке. Текст строки: `path`, если он непустой; иначе
  `Entry: <ownerTag>`, если непустой `ownerTag`; иначе `message()` записи. Если
  у записи есть `value`, оно дописывается к пути через ` = `.
- **Разбор** (`What happened`, `Why it happens`, `What you can do`) и ссылка
  `Details` — один раз на группу, после списка.

### Подстановки в текстах группы

Правило одно для заголовка и всех блоков разбора: подстановка (`path`, `value`,
каждый ключ `params`) делается обычным значением, если оно **одинаково у всех
записей группы**; если значения различаются, вместо него подставляется `…`.

Так группа одинаковых по значению записей сохраняет конкретный текст, а группа
разных полей получает заголовок `Configuration: field … not read` и не
приписывает разбору имя одного случайного поля.

### Что сохраняется

- Счётчики шапки (`✖ 1 · ⚠ 2 · ⓘ 7`) считают **записи**, не группы: число
  совпадает с тем, что видно на значках в списках.
- Маскирование секретных значений (§511): значение в строке записи и в текстах
  группы берётся после `withSecretValueMasked()`.
- Подзаголовок уровня показывается при нескольких уровнях, как сейчас.
- Единственная плитка во всём списке (одиночная запись или единственная группа)
  открыта сразу.
- Новых строк интерфейса нет: число и `…` — `l10n-exempt`.

## Риски и edge cases

- **Текст с `…` читается суше, чем с именем поля.** Принято: имена полей стоят
  списком прямо над разбором.
- **Группа из записей с разным `ownerTag`** (отбраковка записей источника,
  §561/§570): строка записи называет свою запись, подзаголовка `Entry:` у
  группы нет.
- **Код есть, текстов в реестре нет** (реестр не синхронизирован): группа всё
  равно собирается, заголовок — `message()` первой записи, разбор и `Details`
  не показываются — как у нынешней плитки без текстов.
- Сводка по всей подписке (код → список узлов) намеренно не делается: решение
  владельца 27.09.2026, уведомления уровня info действий не требуют.

## Верификация

Тесты — в `app/test/screens/node_notifications_test.dart`:

1. Семь `json_field_unknown` с разными путями → одна плитка-группа, число `7`,
   семь строк путей, блок `What happened` в дереве один.
2. Заголовок такой группы содержит `…` и не содержит ни одного пути.
3. Две записи одного кода с одинаковым `path` и `value` → подстановка обычная,
   `…` в заголовке нет.
4. Код с одним вхождением рядом с группой → обычная плитка, порядок по первому
   вхождению.
5. Счётчик шапки показывает число записей, не групп.
6. Записи разных уровней с одним кодом в одну группу не сливаются.

`app/test/screens/node_notifications_secret_mask_test.dart` остаётся зелёным:
секрет в строке записи группы замаскирован.

Приёмка на устройстве: узел «Германия» подписки из Xray-JSON — в Diagnostics
одна группа из семи полей вместо семи плиток.

## Нерешённое / follow-up

- Заголовок группы без многоточия (`Fields not read`) требует отдельного текста
  в контракте — запрос лаунчеру на ключ заголовка группы у кода. До его
  появления действует правило с `…`.
