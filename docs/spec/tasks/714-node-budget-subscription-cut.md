## Problem

Issue #190 (horvickk, 02.11.2026): подписка-агрегатор на 7 000+ узлов
(`merged.txt`). Старт туннеля проходит, соединение активируется, но
приложение перестаёт отвечать и через ~10 с система убивает процесс (ANR).
После этого остаётся уведомление VPN с «активным» соединением.

Клиент на такой объём не рассчитан и доводиться до него не будет (решение
владельца). Но вылет — дефект. Причины известны:

- сборка конфига и валидация гоняют все N узлов в main-изоляте;
- после старта идёт mass-ping всех членов автовыбора: при concurrency 10 это
  700 раундов, каждый flush (120 мс) пересчитывает производный слой по всем N
  (§446, волны 4–5 не сделаны);
- ядро получает N outbounds и urltest на N членов — память и долгий Start.

## Decisions (владелец, 04.11.2026)

1. **Бюджет узлов, общий на приложение.** Одно число `node_budget`, дефолт
   **1000**, вшит. Настройка в App settings с предупреждением ⚠.
   Минимум 1, верхнего потолка нет.
2. **Что входит в бюджет:** ручные серверы (`UserServer`), включённые члены
   папок (`FolderServers.members` с `enabled`), узлы включённых подписок.
   **Не входят:** Tailscale-узлы, auto-узлы групп/папок/Направлений, цепочки.
3. **Ручное не режется никогда** и вычитается из бюджета первым. Если ручного
   ≥ бюджета, подписки получают 0 узлов и несут предупреждение
   «Budget used by manual servers».
4. **Остаток раздаётся между включёнными подписками поровну с
   перераспределением** (water-filling): каждая берёт `min(размер, доля)`,
   недобор делится между теми, кому не хватило, пока бюджет или подписки не
   кончатся. Считается по размерам (число узлов после разбора и
   import-правил), сами узлы не трогаются. Детерминированно: при равных долях
   и нехватке остаток уходит подпискам в порядке `sources`.
5. **Выключенные подписки не участвуют.** Включение/выключение подписки,
   добавление/удаление ручного сервера или члена папки, смена бюджета —
   пересчёт долей и перерезка подписок **из локального кэша тела, без сети**.
6. **Что режется:** первые N узлов по порядку в подписке (после
   import-правил), без сортировки и пинга. **Защищённые узлы** держатся сверх
   очереди внутри доли подписки: узлы, на которые есть ссылка из Направления
   (закреплённый/выбранный узел), из члена цепочки (`source_chain`), из
   пользовательского правила (outbound-тег). Защищённые берутся первыми, потом
   добор по порядку до N. Если защищённых больше N — берутся все защищённые,
   N превышается (ссылки важнее бюджета), в карточке подписки это видно.
7. **Где режется:** в воркере разбора (§652: `parseCachedBody` /
   `parseFetchedWithRules`, `cache_rehydrate.dart`) — квота и список
   защищённых тегов передаются во входные структуры `CacheParseInput` /
   `FetchParseInput`. После воркера хранилище, конфиг, список, автовыбор,
   mass-ping лишних узлов не видят.
8. **Существующие подписки** больше доли режутся при ближайшем обновлении
   или перерезке по п.5, **не** при обновлении приложения (миграции нет).
9. **Карточка подписки:** вместо «N nodes» — «N of M nodes» когда `N < M`
   (M = размер после разбора и import-правил, до обрезки), плюс значок ⚠ в
   subtitle с подсказкой «Node budget in App settings». Диалога при импорте
   нет. Когда `N == M` — как сейчас.
10. **Настройка:** App settings → General, рядом с `PingConcurrencyTile` (§713,
    тот же образец: поле + Reset, пустое = дефолт, вне диапазона → граница).
    Заголовок «Node budget», подсказка «Above 1000 the app may freeze or be
    killed by the system» с ⚠. Хранение — верхнеуровневый ключ `node_budget`
    в `SettingsStorage` (не в `ping_options`), `set(null)` снимает ключ.
11. **Бэкап:** `node_budget` едет в LX Backup как настройка приложения.
    Ключ лаунчера `max_nodes` у подписки по-прежнему игнорируется (это
    лимит на подписку, у нас бюджет общий); в `docs/contract` отметить, что
    `node_budget` — наш ключ, лаунчеру заявить (контракт не бампать без
    согласования, просто запись в TASKS_LXBOX/запрос).
12. **Debug API:** `GET/PUT /settings/node_budget` по образцу
    `ping_options` (§713).
13. **Уведомление после убийства процесса.** Снятие уже есть (§430:
    `BoxVpnService.clearStaleNotification` из `MainActivity.onCreate`,
    bounce сервиса с `ACTION_CLEAR_STALE_NOTIFICATION`). Задача: воспроизвести
    на эмуляторе — поднять туннель, убить процесс (`adb shell am force-stop`
    НЕ годится, он снимает уведомление сам; использовать `kill -9 <pid>` через
    `adb shell run-as` или `am crash`), проверить, осталось ли уведомление,
    открыть приложение, проверить, что снялось. Чинить **только если** не
    снимается; тогда искать причину в условии `currentStatus != Stopped` и
    в порядке инициализации. Ничего не переносить в `BoxApplication.onCreate`
    (гонка с реальным стартом сервиса).

## Not in scope

- Волны 4–5 §446, ускорение main-изолята под 7k — не делаем.
- Лимит на ручные узлы, Tailscale, цепочки — нет.
- Умный отбор узлов (по пингу, стране) — нет.
- Поддержка `max_nodes` лаунчера как лимита на подписку — нет.

## Verification

Unit (один файл на блок, без полного прогона):
- `test/subscription/node_budget_split_test.dart`: раздача — (a) ручные 100,
  A=50, B=2000 → A 50, B 850; (b) три подписки 10/10/5000 при бюджете 1000 и
  ручных 0 → 10/10/980; (c) ручные 1200 → всем 0; (d) выключенная подписка
  не получает и не отнимает; (e) защищённых больше доли → все защищённые.
- `test/subscription/fetch_parse_worker_test.dart` (дополнить): квота в
  `FetchParseInput` режет, `totalNodeCount` = до обрезки, защищённые теги
  первыми.
- `test/services/settings_storage_node_budget_test.dart`: дефолт 1000,
  clamp снизу 1, `set(null)` снимает.
Эмулятор: подписка из 2 000 узлов (сгенерировать файл) + ручной сервер →
карточка «999 of 2000 nodes» с ⚠, туннель стартует, mass-ping не больше
999; поднять бюджет до 3000 → после refresh 2000. Пункт 13 по сценарию.
