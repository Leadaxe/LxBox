## Проблема

Пользователь (4PDA, evgeny1503) после обновления на v2.19.0 получил невозможность
запустить сервис: приложение вылетает сразу после нажатия «старт». Присланный
`go.log` — паника в bbolt на старте ядра:

```
panic: invalid page type: 2: 10

github.com/sagernet/bbolt.(*Cursor).search
  → bbolt.(*Bucket).Bucket
  → cachefile.(*CacheFile).start        (cache.go:203)
  → box.(*Box).preStart                 (box.go:560)
  → box.(*Box).Start
  → daemon.(*StartedService).StartOrReloadService
  → libbox.(*CommandServer).StartOrReloadService
```

`cache.db` (bbolt) в `filesDir` повреждён. На первом же `Tx.ForEach` при старте
ядро читает страницу с невалидным типом и **паникует**. Паника в горутине с
`locked to thread` → процесс убит целиком.

`2: 10` — страница №2, флаг типа `10` (десятичный) = `0x0A` = `branch|meta`
одновременно. Валидные значения: `branch` 0x01, `leaf` 0x02, `meta` 0x04,
`freelist` 0x10. Такой комбинации не существует — байты заголовка страницы не те,
что там должны быть. Страница 2 — первая после двух meta-страниц, то есть корень.

**User-impact — петля без выхода.** Файл сам не чинится, каждый следующий «старт»
даёт ту же панику. В UI нет ничего, что пользователь мог бы нажать: удаление
`cache.db` живёт только в DNS-настройках как «сброс DNS-кэша» (§263,
[BoxVpnService.kt:198](../../../app/android/app/src/main/kotlin/com/leadaxe/lxbox/vpn/BoxVpnService.kt)),
и связь этой кнопки с крашем старта неочевидна.

Первопричина порчи файла не установлена. Правдоподобная гипотеза — убийство
процесса на середине bbolt-транзакции при обновлении APK (симптом появился ровно
после обновления на 2.19), но воспроизведения нет и подтвердить нечем. Задача
чинит **последствие** независимо от источника — для класса «редкое повреждение
файла» это адекватный подход.

## Диагностика

### Ложный след: per-app allow-list

Пользователь связал падения с per-app: отключил в tunnel apps несколько
приложений — краши прекратились. Отдельно заметил, что стоковый YouTube Music,
удалённый из системы, продолжал висеть в списке LxBox.

К панике это отношения не имеет. В стектрейсе нет ни одного кадра роутинга или
package-матчера: падение происходит в `preStart`, **до** применения конфига.
Совпадение объясняется тем, что правка per-app списка идёт через
`startOrReloadService` — новый `Box`, по пути `cache.db` мог быть пересоздан.

Висящий в списке удалённый пакет — реальный, но отдельный дефект (см.
[Нерешённое](#нерешённое--follow-up)).

### Почему нельзя поймать панику

Паника Go — не Java-исключение. Она валит процесс через `abort()`, `try/catch` в
Kotlin её не увидит. `recover()` на стороне Go тоже не поможет: паника происходит
в другой горутине под `bbolt.(*DB).Batch`. К моменту, когда что-то можно было бы
поймать, процесса уже нет.

Следствие: детект возможен **только постфактум**, на следующем запуске.

### Отвергнуто: валидация bbolt перед стартом

Идея — прочитать первые 4 КиБ (две meta-страницы) и проверить magic
`0xED0CDAED`, версию формата, checksum, границы `pgid`.

Нашего случая это не покрывает: meta-страницы были целы (ядро дошло до открытия
БД и начала транзакции), порча — в теле дерева на странице 2. Полная проверка
означала бы обход всего дерева, то есть ровно то, что делает ядро и на чём
падает. Дешёвого проактивного детектора для этого класса порчи нет.

### Отвергнуто: `ApplicationExitInfo` и sentinel-файл

`getHistoricalProcessExitReasons` (§038,
[VpnPlugin.kt:978](../../../app/android/app/src/main/kotlin/com/leadaxe/lxbox/vpn/VpnPlugin.kt))
даёт `REASON_CRASH_NATIVE` — но только с API 30, а `minSdk = 24`. Промежуток
24–29 потребовал бы второго механизма (sentinel-файл: маркер перед стартом,
снятие после успеха), более грубого — он не отличает краш от убийства по памяти
или смахивания из недавних.

Оба не нужны: ядро уже ведёт собственный файловый учёт крашей, работающий от
minSdk 24 (ниже).

### Найденный источник: `CrashReport-lxbox.log`

libbox через `debug.SetCrashOutput` редиректит Go-stderr в
`workingPath/CrashReport-<source>.log` (`crashReportSource = "lxbox"`,
[BoxApplication.kt:114](../../../app/android/app/src/main/kotlin/com/leadaxe/lxbox/vpn/BoxApplication.kt)).
Обычный файл — **переживает смерть процесса**. Пустой (0 байт) = паник не было;
непустой = прошлая сессия упала.

Порядок в `Libbox.Setup` подтверждён по коду ядра
(`experimental/libbox/log.go:69-77`):

```go
func redirectStderr(path string) error {
    crashReportsDir := filepath.Join(sWorkingPath, "crash_reports")
    archiveCrashReport(path, crashReportsDir)          // ← старый репорт → архив
    archiveCrashReport(path+".old", crashReportsDir)   // ← И .old тоже
    outputFile, err := os.Create(path)                 // ← затирание под новую сессию
    ...
```

`archiveCrashReport` выходит немедленно при `len(content) == 0`
(`log.go:29`) — то есть **критерий «непустой файл = был краш» это ровно тот, по
которому работает само ядро**. В конце — `os.Remove(path)` (`log.go:55`).

Два следствия, на которых стоит решение:

1. `Libbox.setup()` — точка невозврата: до неё улика на месте и `cache.db` никем
   не открыт; после неё репорт уехал в архив, а БД занята ядром.
2. Дедуп «один краш — одна чистка» получается **бесплатно**: `setup` затирает
   репорт, на следующем запуске файл пуст, событие не выстрелит. Хранить stamp,
   счётчик попыток или timestamp не нужно — состояние уже есть в ФС.

## Решение

Событие **`onLaunchAfterCrash`** — отдельная сущность на native-слое, с
независимыми подписчиками, а не ветвление внутри существующего кода баннера.

### Хронология запуска

```
filesDir/ на момент старта процесса:
  CrashReport-lxbox.log       ← НЕПУСТОЙ, если прошлая сессия упала
  cache.db                    ← возможно битый
  crash_reports/              ← архив; сегодняшнего краша там ЕЩЁ НЕТ

initializeLibbox:
  1. size(CrashReport-lxbox.log) > 0 ?
  2.   → onLaunchAfterCrash
  3.        └─ удалить cache.db, очистить cacheDir
  4. Libbox.setup(opts)   ← архивирует репорт, os.Remove, создаёт чистый cache.db
```

Шаги 1–3 — одно обращение к ФС, до того как ядро что-либо открыло. Удаление
`cache.db` в этот момент тривиально безопасно: файл ничей.

### Слои и подписчики

| Слой | Что делает | Когда | От чего |
|------|-----------|-------|---------|
| Детектор (Kotlin) | факт краша + метаданные | до `Libbox.setup()` | непустой `CrashReport-lxbox.log` |
| Подписчик 1 (Kotlin) | чистка `cache.db` + `cacheDir` | синхронно, до `setup` | событие |
| Подписчик 2 (Dart, §316) | баннер «ядро падало» | после старта Flutter | архив `crash_reports/` + собственный stamp |

Две ветки читают **разные файлы в разные моменты** и не конкурируют: чистка —
текущий репорт до `setup`, баннер — архив после. §316 менять не требуется: он
продолжает работать от архива и от `shownCrashStamp`, просто перестаёт быть
единственным местом, где знание о краше существует.

Детектор про подписчиков не знает — добавление третьего потребителя не потребует
трогать ни детект, ни существующие ветки.

### Что чистим

| Объект | Чистим | Обоснование |
|--------|--------|-------------|
| `filesDir/cache.db` | **да** | bbolt: FakeIP-аллокации, DNS RDRC, urltest, выбор в селекторах. Причина падения. Восстановимо целиком |
| `cacheDir` (`tempPath` ядра) | **да** | временные файлы по определению; система сама сносит их под давлением памяти, ядро обязано переживать отсутствие |
| `config.json` | нет | конфиг ядра, не кэш — без него нечего запускать |
| `CrashReport-lxbox.log`, `crash_reports/` | нет | предмет диагностики; репорт нужен ядру для архивации, архив — баннеру §316. Своей же чисткой снесли бы то, по чему детектим |
| настройки, подписки, per-app | нет | пользовательские данные |
| `geoip.db` / `geosite.db` / rule-set | нет | десятки МБ по сети; после краша сеть может не работать — остались бы без маршрутизации. К порче bbolt отношения не имеют |

Чистим на **любом** краше ядра, без разбора трейса (решение юзера). Парсинг на
`bbolt`/`invalid page type`/`cachefile` был бы прицельнее, но пропускал бы редкие
формы порчи; потеря дешёвая, а краш ядра и так не рядовое событие.

### Наблюдаемость

Факт срабатывания — в лог (что сработало, что удалено). Молча мутировать
пользовательское состояние нельзя — инвариант «кнопки НЕ мутируют молча» (§261).

## Риски и edge cases

- **`CrashReport-lxbox.log` непуст не из-за паники.** Ядро пишет туда Go-stderr
  целиком, не только паники. Ложное срабатывание = лишняя чистка восстановимого
  кэша, цена низкая. Осознанный размен на отказ от парсинга трейса.
- **Порядок в ядре зафиксирован по коду 1.14.** При бампе версии перепроверять
  `redirectStderr` — если архивация уедет после `os.Create`, баннер потеряет
  краш. В [KERNEL.md](../../KERNEL.md) — в список ловушек бампа.
- **`.old`-файл — проверять НЕ надо.** `redirectStderr` архивирует и
  `path+".old"` (`log.go:72`), но это единственное упоминание `.old` во всём
  форке: **никто его не создаёт**. Похоже на страховку под старое поведение
  `debug.SetCrashOutput` при ротации. Добавлять его в детект — мёртвый код.
  Перепроверить при бампе ядра или Go, если файл вдруг начнёт появляться.
- **Первопричина порчи не устранена.** Задача лечит последствие. Если файл будет
  биться систематически, пользователь получит регулярный сброс FakeIP и выбора
  узлов в селекторах вместо краша — деградация, но не блокировка.
- **Не покрыто:** порча `cache.db`, не приводящая к панике (тихо неверные данные).
  Детектора нет, в скоуп не входит.

## Верификация

Unit (Kotlin):
- непустой `CrashReport-lxbox.log` → событие, `cache.db` удалён
- пустой (0 байт) → события нет, `cache.db` на месте
- отсутствующий файл → события нет
- `config.json` / `crash_reports/` не тронуты ни в одном сценарии

Device (обязательно, холодным стартом):
1. Намеренно испортить `cache.db` — записать мусор в середину файла через Debug
   API или adb, при остановленном сервисе.
2. Старт → воспроизвести паникуй `invalid page type`, процесс умирает.
3. Второй старт → сервис поднимается; в логе запись о сбросе кэша.
4. Баннер §316 показан ровно один раз, `go.log` в архиве читается и шарится.
5. Повторный старт без нового краша → чистки нет, баннер молчит.

Критерий приёмки: после однократного краша ядра следующий запуск проходит без
вмешательства пользователя.

## Нерешённое / follow-up

- **Удалённые/отключённые пакеты висят в per-app списке.** Ровно то, на что
  пользователь наткнулся (стоковый YouTube Music, удалённый из системы). К панике
  отношения не имеет, чинится отдельно: чистка списка от несуществующих пакетов
  либо пометка «удалено» с быстрым снятием. Отдельная таска.
- **Первопричина порчи `cache.db`.** Гипотеза «убийство процесса на середине
  bbolt-транзакции при обновлении APK» не подтверждена — воспроизведения нет.
  Если появятся ещё случаи с той же сигнатурой — заводить отдельно.
- **Ручной сброс гео-баз / rule-set.** В автоматику после краша намеренно не
  вошло; при необходимости — отдельная кнопка.
