Продолжение разбора темы на 4PDA после §517. Пользователь спросил: при доступе
по белым спискам «никакой сервер не ответит». Замысел владельца:

> «Shield делает то же, но по защищённым каналам, нет утечек DNS; в белых
> списках должны работать соединения Яндекса — DNS Яндекса не угроза, работают
> по защищённому протоколу».

---

## Факты (что было на самом деле)

Группа `dns_shield` в `app/assets/wizard_template.json` перечисляла шесть
членов, включая `yandex_dot`. **Записи сервера `yandex_dot` в базовом
`dns_options.servers` не было** — тег был объявлен только в пресете `ru-direct`
(`selectable_rules[].dns_servers[]`).

Ключевое: сослаться на него из базы нельзя **ни в каком состоянии пресета**.
Теги, объявленные пресетом, при сборке получают неймспейс
`<preset_id>:<tag>` — `namespacePresetTags`
(`app/lib/services/builder/preset_expand.dart:464-546`, §103 C7 / D-012).
Сервер пресета приезжает в конфиг как `ru-direct:yandex_dot`, а группа
ссылается на bare-тег `yandex_dot`. Поэтому член выпадал:

- при **выключенном** `ru-direct` — сервера нет вовсе (§121 уносит его);
- при **включённом** `ru-direct` — сервер есть, но под другим именем.

Отбраковка — в `_filterDnsGroupMembers`
(`app/lib/services/builder/post_steps/dns_servers.dart:391-418`): тега нет ни в
одном ref'е → `dropReason = 'unknown'`, в предупреждения сборки уходит

```
DNS group 'dns_shield': member 'yandex_dot' dropped (unknown)
```

Это подтверждали оба golden-эталона до правки — в том числе `rich_v0`, где
`ru-direct` **включён**: группа всё равно приезжала из пяти членов, и
предупреждение стояло на месте (`rich_v0.config_warnings.json`,
`avd_v0.config_warnings.json`).

Следствия:
1. «Щит» опрашивал **пять** провайдеров, а подсказки в трёх местах обещали
   «races 6 encrypted providers» — число было неверным уже до этой задачи.
2. Под белыми списками резолв не работал вовсе: единственный провайдер,
   который в такой сети отвечает, из гонки выпадал.
3. Предупреждение в каждой сборке — шум, маскирующий настоящие проблемы.

Долг был зафиксирован в §517 («Нерешённое / follow-up»), но там диагноз был
неполным: предполагалось, что член выпадает лишь при выключенном пресете.

## Решение владельца

Минимальный вариант — «идёт»:

1. В базовый `dns_options.servers` добавлена запись `yandex_dot` — прямой DoT,
   **без `detour`**.
2. Состав группы `dns_shield` **не менялся**: `yandex_dot` там уже был
   прописан и теперь резолвится.
3. Пресет `ru-direct` **не тронут**: его `ru-direct:yandex_dot` через `vpn-1`
   остаётся как есть, `yandex_udp` тоже.
4. Движок пресетов **не тронут**.

Рассмотренные и отклонённые варианты: развести имена (`yandex_dot_direct`),
сделать членство условным от пресета (потребовало бы нового примитива в движке
пресетов — сейчас фрагменты пресета умеют только добавлять новые серверы по
тегу, дописать члена в существующую базовую группу нечем, см. `mergeFragments`,
`preset_expand.dart:554-606`).

## Что изменено

`app/assets/wizard_template.json` — новая запись в `dns_options.servers`
(перед группой `dns_shield`, форма как у соседних записей без `vars`):

```json
{ "description": "Yandex DoT (direct)", "enabled": true,
  "server": { "type": "tls", "tag": "yandex_dot", "server_port": 853,
              "server": "77.88.8.8",
              "tls": { "enabled": true,
                       "server_name": "common.dot.dns.yandex.net" } } }
```

**Почему `common.…`, а не `safe.…`.** У Яндекса SNI задаёт профиль
фильтрации, и он жёстко привязан к IP: `77.88.8.8` ↔
`common.dot.dns.yandex.net` (Базовый, без фильтрации), `77.88.8.88` ↔
`safe.dot.dns.yandex.net` (Безопасный), `77.88.8.7` ↔
`family.dot.dns.yandex.net` (Семейный) — по официальной документации Яндекса
(dns.yandex.ru). Записи пресета `ru-direct` используют **Safe**-профиль
(`77.88.8.88` + `safe.…`) — это осознанный выбор автора пресета. Для «щита»
взят нефильтрующий Базовый: щит защищает канал, а не фильтрует содержимое, и
навязывать пользователю блокировки от имени DNS-пресета не его дело.

**Почему без `detour`.** Ровно ради белых списков: если запросы «щита» пойдут
через туннель, а туннель в такой сети не поднялся, резолв снова не работает.
Прямой DoT работает и без туннеля, при этом остаётся шифрованным.

**Почему не UDP.** Открытый текст в группу с именем «shield» не возвращаем —
это и был предмет §517: при `mode: fastest` запрос уходит **всем** членам
сразу, и открытый UDP без TLS-рукопожатия выигрывает гонку, то есть щит
регулярно резолвил бы открыто. `yandex_udp` остаётся только в пресете
`ru-direct`, в базу не добавлен.

**Тексты подсказок не менялись**: «races 6 encrypted providers» теперь
соответствует действительности — в группе шесть шифрованных членов.

### Открытый вопрос владельцу (не чинили)

`ru-direct:yandex_dot` идёт через `detour: vpn-1`, хотя пресет называется
*ru-direct* и под белыми списками туннель может не работать. Явной причины в
коде и спеках нет — только описательные строки шаблона
(`"Yandex Safe DoT (via vpn-1)"`, `"RU DNS group (UDP via direction + DoT via
vpn-1 + direct DoH)"`). При этом тот же пресет уже содержит прямой шифрованный
`yandex_doh` без detour. Решение — за владельцем, в объём §527 по его команде
не входит.

Так же не входит (наследие §517): `quad9_doh` — единственный член группы с
`detour: vpn-1`, то есть члены гонки идут разными путями.

## Риски и edge cases

- **Существующие конфиги не мигрируются** (как в §517). Состав группы
  `dns_shield` при `kind: "template"` берётся из шаблона при следующей сборке
  конфига — там член появится сам. У кого группа сохранена как `inline`,
  останется как была. Автоматической миграции нет и не добавляли.
- Профиль Яндекса в «щите» — нефильтрующий. Кому нужна фильтрация, её даёт
  пресет `ru-direct` (Safe) или базовый `safe_dns_dot`.
- В сетях, где `77.88.8.8:853` недостижим, член просто проиграет гонку —
  `mode: fastest` берёт первый ответ, остальные пять провайдеров на месте.
