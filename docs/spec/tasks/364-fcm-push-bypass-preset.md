# §364 — Пресет «Google push (FCM)»

**Тип:** таска (новый selectable_rule в шаблоне)
**Статус:** реализовано, DEVICE-PENDING
**Источник:** запрос из трекера — push-уведомления опаздывают при заблокированном
экране, когда FCM идёт через VPN.

## Проблема

Постоянное соединение FCM (MTalk) через туннель отваливается при засыпании
устройства: keepalive не доходит вовремя, уведомления приезжают пачкой при
разблокировке.

Грубое решение — увести весь `com.google.android.gms` мимо VPN — не годится:
вместе с push уходит и трафик авторизации Google, из-за чего сбрасывается
регион Google Play.

## Решение

Пресет `fcm-push`: мимо VPN пускается **только** push-трафик — по портам и по
списку хостов FCM. Остальной Google Play не затрагивается.

Пресет **не** `pinned` и `default: false` — добавляется в конец списка, юзер
сам поднимает его выше правил проксирования (иначе не сработает: порядок
правил = порядок матчинга в sing-box). Про это сказано в `ui.description`.

## Состав

Одно правило: внешний `logical and`, внутри — `logical or` из четырёх ветвей.

| ветвь `or` | зачем |
|---|---|
| `port_range: ["5228:5230"]` | **основной матч.** Постоянное соединение MTalk; FCM ходит только по этим портам. Работает и при включённом FakeIP — матч по порту от резолва не зависит |
| `domain` (mtalk, mtalk4, android.apis) | страховка на 443-fallback |
| `domain_suffix` (firebaseinstallations, device-provisioning, iid) | то же; суффикс безопасен — зона `googleapis.com` принадлежит Google |
| `domain_regex: ^alt\d+-mtalk\.google\.com$` | `alt1-8` и будущие `alt9+` одним выражением |

Домены здесь — **страховка**, а не основа: если хост в списке не сматчится,
его почти наверняка поймает `port_range`. Поэтому полнота доменного списка
некритична, и точность `domain` vs `domain_suffix` тоже.

Список сверен с
[Firebase FCM network configuration](https://firebase.google.com/docs/cloud-messaging/network-configuration).
Порт 443 из требований Google отдельной ветвью **не** открывается — это весь
HTTPS; его роль закрывают доменные ветви.

Не взято: `mtalk-staging` / `mtalk-dev` (отладочные хосты Google) и
`accounts.google.com` — последний мимо VPN сбрасывает регион Play, то есть
воспроизводит исходную проблему запроса.

### vars

| var | тип | default | смысл |
|---|---|---|---|
| `outbound` | `outbound` | `direct-out` | куда слать push-трафик |
| `gms_only` | `bool` | `false` | сузить оба правила до `package_name: com.google.android.gms` |

`gms_only` выключена по умолчанию: матчинг по приложению работает только в
режиме VPN (в proxy-inbound у соединения нет владельца-пакета).

### ⚠ `package_name` — ВЕТВЬ внешнего `and`, а не поле правила

Сужение (И) в sing-box выражается **только вложенностью**. Поэтому `gms_only`
добавляет ветвь `{"package_name": [...]}` во внешний `and` — через
array-element `#if` без `else`.

Промежуточная версия клала `package_name` рядом с `mode`/`rules` того же
`logical`-правила (map-spread `#if`). Это **fatal**: `RawLogicalRule` знает
только `mode`/`rules`/`invert` + `RuleAction`
(`option/rule.go:212`), а разбор идёт через
`badjson.UnmarshallExcluded` → `UnmarshalContextDisallowUnknownFields`.
Проверено прогоном на ядре:

```
{"type":"logical","mode":"or",...,"package_name":[...]}
  → DECODE ERROR: package_name: json: unknown field "package_name"
```

Strict-decode валит **весь** конфиг, ядро не стартует — то есть галка положила
бы VPN у каждого, кто её включит. Тест на этот инвариант — в
`preset_expand_test.dart`, с объяснением; не «упрощать» обратно.

При `gms_only=false` ветвь выпадает целиком (`Dropped.instance`,
`if_engine.dart:180`) — пустого `{}` в `rules` не остаётся, и внешний `and`
остаётся с одной ветвью. Вырождения в «матчит всё» нет: `and` по одному
элементу = результат этого элемента (`route/rule/rule_abstract.go:205`).

## Решения по ходу

**Порты и домены — не опции.** В черновике они были двумя галками. Отброшено:
выключение обеих давало правило-пустышку (немой гейт, анти-паттерн §277/§278),
а по отдельности выключать нечего — это ветви одного механизма.

**Без `rule_set`.** Домены лежат прямо в ветвях `or`. Отдельный inline-набор
был в промежуточной версии; он не нужен — висячих ссылок не бывает в принципе,
а `expandPreset` проверяет `rule_set` только на верхнем уровне правила и
внутрь `logical.rules` не смотрит.

**DNS-слоя нет — но в описании предупреждение.** Первый черновик содержал
`dns_rules` со ссылкой на `dns_direct`. Такого тега не существует:
`dns_options.servers` шаблона — это каталог заготовок, теги (`google_udp`
и пр.) появляются только после добавления сервера юзером; `expandPreset`
отбросил бы фрагмент с warning. Зашить свой DNS-сервер в пресет — тоже
неверно: у юзера уже настроен свой.

Матчинг от этого не страдает (`port_range` от резолва не зависит вовсе), но
адреса могут прийти из чужого региона, если DNS идёт через туннель — тогда
push молчит при формально верном маршруте. Поэтому в `ui.description` есть
явная строка: при DNS через туннель добавьте direct-правило для этих хостов
в настройках DNS.

## Проверка

Тесты на реальном шаблоне: дефолты (`and` из одной ветви, четыре ветви `or`,
`package_name` отсутствует), `gms_only=true` (ветвь добавлена, вложенный `or`
не тронут), `outbound=vpn-1` (подстановка).

Форма правила проверена прогоном через декодер ядра (`option.Rule`,
`json.UnmarshalContext`) в обоих состояниях галки — обе декодируются чисто;
верхнеуровневый `package_name` даёт `unknown field`.

**DEVICE-PENDING:** на устройстве не проверялось. Проверить:

1. push доходит при заблокированном экране с включённым VPN;
2. регион Google Play не сбрасывается;
3. формулировка тултипа `gms_only` про «VPN mode only» — оценка по коду
   (`package_name` кладётся в route-правило,
   `post_steps/custom_rules.dart:681`), поведение в proxy-режиме не замерялось.
