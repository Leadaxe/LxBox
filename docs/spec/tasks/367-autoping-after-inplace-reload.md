# §367 — Автопинг не запускается после in-place reload

| | |
|---|---|
| Тип | bugfix (узлы без замеров после смены подписки) |
| Статус | ✅ Исправлено — тесты зелёные |
| Дата | 2026-08-03 |
| Связанные | [`360`](360-config-dirty-lost-during-rebuild.md) (тот же путь «сменил подписку → применилось»), [`338`](338-auto-reload-on-settings-change.md) (галка автоприменения, которая и ведёт в reload), [`311`](311-running-config-from-kernel.md) (ровно та же дыра «висит на переходе в connected» — для снапшота running-конфига) |

## Проблема

Юзер меняет подписку с включённой галкой автоприменения. Туннель
перезапускается, список узлов на главном перерисовывается новым составом — но
**все узлы без задержек**: пинг никто не запустил. При обычном старте туннеля
замеры появляются сами.

## Root cause

`_scheduleAutoPing` вызывается из единственного места —
`_handleStatusEvent`, ветка ПЕРЕХОДА в `connected`.

Галка §338 применяет изменения через `reloadVpn` — in-place reload: ядро
перечитывает конфиг, туннель не рвётся. Статус при этом `connected` →
`connected`. **Перехода нет ⇒ автопинг не планируется.**

Это третий случай одной и той же ошибки. Двумя предыдущими были снапшот
running-конфига (§311) и `_startGroupsPull` (§049 F4) — оба чинились там же, в
`reloadVpn`, прямым триггером. Комментарий в коде говорит об этом дословно:

> `_startGroupsPull` заводится только на переходе в connected, которого при
> reload нет

### Вторая половина: пустой `_state.nodes`

Первая правка (просто позвать `_scheduleAutoPing`) на устройстве **не
сработала** — пингов по-прежнему не было. Логи сеанса 03.08:

```
3:31.230682  §338: auto-reload on settings change
3:31.232977  [vpn] reload → ok=true
3:32.443302  [cc] running config captured (83850 bytes)
   ... groups-push НЕ ПРИШЁЛ, до 3:53 ни одного Mass ping started
```

Пингуем `_state.nodes`, а его наполняет `_applyGroups` из groups-стрима — и
тот при in-place reload может не прийти вовсе (ровно то, о чём предупреждает
§311-комментарий этажом выше в том же методе). Таймер исправно срабатывал через
5с, упирался в `nodes.isEmpty` и тихо выходил.

Экран при этом показывал новый состав узлов — его рисует saved-конфиг, а не
ядро. Отсюда и обманчивость симптома: список свежий, а замеров нет.

Это же объясняет давнее наблюдение юзера «потянул вниз — и всё работает»:
`pullToRefresh` делает ровно недостающее — unary `getGroups` + `_applyGroups`.

## Решение

`reloadVpn` после успешного reload и захвата снапшота **сначала подтягивает
группы, затем** планирует автопинг:

```dart
unawaited(_captureRunningConfig(staleRaw: staleSnapshot));
unawaited(() async {
  await pullToRefresh();      // состав узлов от ядра
  await _scheduleAutoPing();  // §367
}());
```

Порядок обязателен: планировать пинг раньше подтяга — значит снова мерить
пустой/доreload'ный список.

Решения по месту:

| вопрос | решение |
|---|---|
| Не продублируется ли пинг при обычном старте? | Нет: пути раздельны. Переход в `connected` — своя ветка, reload — своя; при reload перехода не бывает по определению |
| Гейты (галка, tunnelUp, пустой список) | Не дублируем — они уже внутри `_scheduleAutoPing`. Выключенная `auto_ping_on_start` уважается и здесь (есть тест) |
| Та же задержка 5с? | Да, `_scheduleAutoPing` берёт свою: после reload ядру нужно время поднять новые outbound'ы — мерить сразу бессмысленно |
| Почему не bump `pingBatchGen` вручную? | Его двигает сам `runMassUrltest`; дублировать sort-инвалидацию не нужно |

## Тесты

`test/controllers/reload_schedules_autoping_test.dart`:

- `reloadVpn` при живом туннеле планирует автопинг (падает на коде до фикса —
  проверено откатом правки);
- там же: `ccGetGroups` вызван и строго ПОСЛЕ `reloadVPN` — иначе снимем
  доreload'ный состав, а таймер сработает на пустом списке (вторая половина
  бага);
- `auto_ping_on_start=false` — не планирует.

Признак «запланирован» читается через `autoPingScheduledForTesting` (геттер
поверх самого таймера, своего состояния не заводит): ждать реальные 5 секунд в
тесте нечестно и хрупко.

Полный прогон: 2838 passed, `flutter analyze` по проекту — чисто.
