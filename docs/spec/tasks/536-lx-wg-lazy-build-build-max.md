## Зачем

§535 привёл ключи сна в корневой блок `lx` и попутно задал владельцу два
вопроса из SPEC 097 — включать ли `lazy_build` и ставить ли `build_max`.
Решение владельца 24.09.2026: **«lazy_build и build_max 5 — делаем»**.

Повод — память на старте. Устройство одного AWG-узла стоит около 17,5 МБ
приёмных батчей, и до сих пор ядро собирало их **все сразу** при старте
туннеля, независимо от того, пойдёт ли через узел хоть один пакет. На
типичном хранении в 11–12 узлов это десятки мегабайт, из которых работает
один. `lazy_build` переносит сборку устройства на первый дайл через узел:
узел стартует разобранным (`never_built`) и собирается, когда через него
правда пошёл трафик. Цена — 0,5–1 с на первом дайле узла, разово.

`build_max` — второй край той же задачи: потолок числа ОДНОВРЕМЕННО собранных
устройств. Без него длинная сессия с переключениями между узлами постепенно
соберёт их все и вернётся к исходному расходу; с потолком самый давний
усыпляется.

## Решение

### 1. Два ключа рядом с порогом сна (`build_config.dart`)

В блок `lx.wg` дописываются `lazy_build: true` и `build_max: 5` — **всегда**,
когда пишется `idle_suspend`:

```json
"lx": { "wg": {
  "idle_suspend": "30s",
  "idle_suspend_reachable": "5m",
  "lazy_build": true,
  "build_max": 5
} }
```

Значения — константы `kLxWgLazyBuild` / `kLxWgBuildMax` в одном месте
(`app/lib/services/builder/build_config.dart`). **Ни ключа storage, ни тумблера
в UI** у них нет: это не настройка, а выбранное поведение сборки.

> **§542:** константы → настройки: `lazy_build` → `wg_lazy_build` (тумблер
> «Lazy tunnel build», дефолт true), `build_max` → `wg_build_max` («Built
> tunnels limit», дефолт 5, `0` = без потолка); VPN Settings → System →
> WireGuard connections.

**Почему в той же ветке, что и `idle_suspend`.** Ядро требует
`lx.wg.lazy_build requires lx.wg.idle_suspend` (`option/lx.go`) — `lazy_build`
без порога сна роняет конфиг на старте. Порог пустой ⇒ блока `lx` нет вовсе
(kill-switch из §215) ⇒ и этих двух ключей нет. Это осознанно: выключенный
idle-suspend выключает всю подсистему разом, одной ручкой.

`build_max` формально самостоятелен (`build_max` без `idle_suspend` ядро
принимает), но держать его в отдельной ветке значило бы иметь два независимых
условия эмиссии на одну подсистему — лишний способ собрать неработающую
комбинацию. Один вход, один выход.

**Почему 5.** Столько узлов человек реально держит в горячем обороте между
переключениями; потолок ниже числа одновременно используемых узлов заставил бы
их разбирать друг друга на каждом переключении (предупреждение самого SPEC
097). На стенде с 11 WG/AWG-узлами потолок упирается сразу — см. «Проверка на
устройстве».

**Чего НЕ пишем.** `build_overflow` — дефолт ядра `wait` нас устраивает
(при упоре в потолок дайл ждёт освобождения слота, а не отваливается).
`lx.masque.idle_timeout` — у узлов WARP MASQUE свой `idle_timeout` в самом
узле, и он приоритетнее глобального (решение из §535 не менялось).

### 2. Probe-сессия — не трогаем

Вопрос 2 из §535 («`build_max` для probe-сессий?») по коду закрывается
отрицательно. Probe-конфиг собирает **не** боевой билдер, а отдельный
`app/lib/services/probe/probe_config.dart`: там свой минимальный JSON
(`log`/`dns`/`outbounds`/`endpoints`/`route.default_domain_resolver`), блока
`lx` в нём нет вовсе.

Дописывать туда эти ключи нельзя и незачем:

- `lazy_build` требует `idle_suspend`, которого у probe-конфига нет, — ядро
  отвергло бы конфиг пробы целиком;
- `build_max` противоречит смыслу пробы: она существует ровно для того, чтобы
  дойти до **каждого** узла, и потолок собранных устройств означал бы, что
  узлы разбирают друг друга прямо во время прогона;
- нагрузка probe-сессии ограничивается своим механизмом — батчами
  (`buildProbeBatches`, `kProbeMaxNaivePerConfig` из §518), а не потолком
  устройств.

### 3. Golden

Диффы `test/fixtures/storage/golden/{avd,rich}_v0.config.json` — ровно две
строки в `lx.wg` на файл, больше ничего (регенерация `UPDATE_GOLDEN=1` по
затронутому файлу).

## Проверка на устройстве

Эмулятор `emulator-5554` (AVD `LxBox_test`), в конфиге **11 WG/AWG-эндпоинтов**
(вход **A** — AmneziaWG 3, восемь AWG-узлов из набора D, два старых WG стенда)
плюс 6 прокси-узлов; активная группа `vpn-1` с Auto (urltest) внутри.
ДО — APK с develop без 536 (`2.25.3-dev.35`), ПОСЛЕ — с 536 (`2.25.3-dev.36`),
хранение одно и то же, между прогонами только `install -r` и `rebuild-config`. APK собран регламентом (`scripts/build-local-apk.sh`,
`--build-number` руками не передаётся). Замер — Debug API
`GET /diag/pprof?profile=heap&query=gc=1&debug=1` (с принудительной сборкой
мусора перед снимком — без `gc=1` цифра гуляет на сотню мегабайт в
зависимости от того, успел ли пройти GC) при живом туннеле на узле A.

Heap сессии ядра, МиБ (HeapAlloc / HeapInuse / Sys), отсчёт от `connected`:

| Момент | ДО (без 536) | ПОСЛЕ (536) |
|---|---|---|
| t≈45 с | 286,4 / 293,4 / 315,9 — `up` 11 | 246,3 / 253,3 / 348,5 — `up` 5, `torn_down` 6 |
| t≈4,5 мин | 112,6 / 118,5 / 315,9 — `asleep` 10, `up` 1 | 52,7 / 60,6 / 420,9 — `asleep` 5, `torn_down` 6 |

Второй прогон ПОСЛЕ на t≈4,5 мин дал 63,6 / 70,5 / 384,5 — тот же порядок.

**Живая куча на установившемся режиме — минус 55–60 МиБ (вдвое), на старте —
минус 40 МиБ.** Выигрыш даёт `build_max`: собранных устройств не больше пяти,
остальные разобраны (`torn_down`) и памяти не держат, тогда как ДО даже
уснувшие (`asleep`) все одиннадцать держали по куску.

**`Sys` вырос на 30–100 МиБ.** Это пик адресного пространства, которое Go
взял у системы и не вернул: устройства собираются и разбираются по кругу
(см. ниже), каждый такой цикл — новые приёмные батчи, и максимум `Sys` выше,
чем при однократной сборке всех одиннадцати.

**`endpoint_states` до первого дайла — `never_built` не наблюдался.** Уже на
t≈6 с после `connected`: `up` 6, `building` 5, `torn_down` 0–1. Причина —
группа Auto (urltest): при старте туннеля она проверяет задержку **всех**
своих членов, то есть дайлит через каждый WG-узел, и ленивая сборка
срабатывает на всех сразу. Дальше в работу вступает потолок: пять собраны,
остальные ждут, в логе ядра `lx idle: build budget: build budget exhausted
(5 built, none idle)` и `teardown <узел> by=budget`, узлы ходят по кругу
`building → up → torn_down`. Без 536 на t≈6 с все 11 `up`, через ~2 мин 10
`asleep`.

Подписи в UI сняты скриншотами экрана Home (список узлов) при установившемся
режиме: `Node asleep` у уснувших и `Node not built yet` у разобранных
(`torn_down` UI показывает той же подписью, что и `never_built`).

Попутно: эмулятор делится с другими сессиями — в окне замера дважды
поставили чужой APK (`2.25.3-dev.37`/`dev.38`, `exit-info: PACKAGE_UPDATED`),
в одном из этих окон туннель погиб по `heartbeat lost`. Прогоны на чужом APK из
таблицы исключены; на своём APK туннель жил все 4,5 мин обоих прогонов.

## Что осталось

**Ленивая сборка на старте не работает при группе Auto.** urltest дайлит всех
членов при старте и далее по своему интервалу, поэтому `never_built` у узлов
в Auto-группе живёт секунды. Экономию сейчас даёт только `build_max`.
Решение не в конфиге LxBox, а в ядре или в модели групп (не проверять
`never_built`/`torn_down`-узлы urltest'ом, или не считать пробу urltest'а
поводом для сборки) — вопрос владельцу/ядру.

**Потолок выселяет выбранный узел.** В логе ПОСЛЕ есть `teardown WireGuard-1
by=budget` — это узел A, выбранный в группе. На стенде A сам по себе не
проходит хендшейк (эмулятор, `sendmsg: input/output error`), поэтому трафика
через него не было и выселение ничего не порвало; на живом узле под
нагрузкой урон не проверен. Если ядро выбирает жертву только по давности
простоя, живой узел выселен не будет — но проверять надо на телефоне.

**Узлы, ждущие слот (`building`), в пробе urltest получают отказ** (`build
budget exhausted`) и в UI показывают `ERR`, хотя сами по себе рабочие. При
пяти горячих узлах это заметно только на хранениях с большим числом WG/AWG.

**Скриншот состояния `never_built`** не снят — по причине выше оно не
наступает; подпись та же, что у `torn_down`, её скриншот есть.
