## Проблема

Нажатие Start даёт «Stopped: Failed to start service: start or reload
service: initialize cache-file: timeout». Пользователям помогает force stop
приложения или «сброс DNS-кэша» — то есть файл не битый, он занят.

## Диагностика (по коду)

1. `cachefile.start` (`experimental/cachefile/cache.go:186`) открывает bbolt
   с `Timeout: 1s`, 10 попыток; на `ErrTimeout` просто повторяет и после
   десятой падает. Самолечение ядра реагирует только на
   `ErrInvalid`/`ErrChecksum`/`ErrVersionMismatch`, блокировку не лечит.
2. cache-file — внутренний сервис, регистрируется первым (`box.go:583`), а
   `Scope.Close` закрывает в обратном порядке (`adapter/lifecycle.go:136`):
   файл отпускается ПОСЛЕДНИМ, после `service`, `inbound`, `endpoint`,
   `outbound`, …, `network`.
3. Когда закрытие виснет на endpoint'ах (класс sing-box-lx#50, WG/AWG),
   ограниченная остановка (§668 — 2 с у VPN, §669 — 3 с у пробы) отпускает
   службу, а старый Box ещё не дошёл до cache-file. Каждый старт VPN создаёт
   новый `CommandServer` (`BoxService.startCommandServer`), проба — свой;
   новый Box в том же процессе ждёт блокировку 10 с и падает.
4. Восстановление из бэкапа — тот же путь: пересборка конфига = stop → start.
5. Порты inbound к этому моменту уже свободны (закрываются до endpoint'ов),
   `command.sock` отпускается первым (§330). Единственный монопольный
   ресурс за зависанием — `cache.db`.

## Почему не из приложения без потерь

- Дескриптор у Go, Kotlin его не закроет.
- Снять flock снаружи (`/proc/self/fd`) — два bbolt на одном файле; зависший
  Box продолжит писать, когда отвиснет (таймер метаданных FakeIP,
  обновление rule-set, RDRC) → порча.
- Копия файла под новым именем отвергнута владельцем: два экземпляра и два
  файла вместо одного.

## Решение

Два слоя, решение владельца 01.11.2026 «скомбинировать»:

1. **Ядро (основной путь, без потерь)** — sing-box-lx#61: `CacheFile.Release()`
   первым шагом `Box.Close`, реестр открытых cachefile по пути и перехват
   файла новым Box перед `bbolt.Open`. Бамп до lx.27, отдельная работа.
2. **Приложение (эта задача, страховка)** — `CacheDbLockRetry`:
   - триггер — сама ошибка старта (`isLockTimeout`: текст содержит
     `initialize cache-file` и `timeout`), НЕ тайм-аут закрытия. Иначе кэш
     терялся бы и тогда, когда ядро всё отпустило бы само;
   - по ошибке: удалить `cache.db` (`BoxVpnService.deleteCacheDbFile`, как
     §263) и повторить `startOrReloadService` ровно один раз. Зависший Box
     остаётся с дескриптором на снятый inode, новый создаёт чистый файл;
   - любая другая ошибка и ошибка повтора идут прежним путём
     (`stopAndAlert` у VPN, `startResult` у пробы);
   - обёрнуты оба старта нового Box на общем файле: VPN
     (`BoxService.startSingbox`) и проба (`ProbeSession.start`). `serviceReload`
     не трогаем: там старый instance закрывается синхронно в том же
     `StartedService` до нового старта, гонки за файл нет.

Цена срабатывания: FakeIP-выдачи, выбор узла в группах (в приложении
отдельно не хранится, идёт через `selectOutbound`), кэш удалённых rule-set
(ядро перекачает `.srs` при старте), история urltest, плюс 10 с первого
неудачного старта. После lx.27 страховка остаётся дежурной и в норме не
срабатывает.

Безопасность удаления: на пути VPN собственный `CommandServer` только что
не стартовал и файл не держит, проба перед стартом VPN остановлена (§236);
на пути пробы VPN не работает (`BoxService.commandClient == null`).

## Проверка

- [ ] Эмулятор: лог `[vpn] start failed on cache.db lock … retry once` и
      успешный старт — только если удастся воспроизвести зависшее закрытие
      (WG-конфиг, stop с превышением 2 с, сразу Start).
- [ ] Отказ другого рода (пустой конфиг, битый узел) — путь не меняется,
      страховка не срабатывает.
- [ ] Владелец на телефоне: сценарий «восстановление из бэкапа» и повторные
      stop/start без force stop.
