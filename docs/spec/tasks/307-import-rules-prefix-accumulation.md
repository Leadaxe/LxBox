# §307 — Import-rules: префикс накапливается в теге при каждом рестарте

**Тип:** bugfix (data-corrupting регресс v2.17.0) · **Статус:** реализовано (2026-07-25, device-pending) · **Размер:** S–M · **Область:** §302 import-rules × билдер × `NodeSpec.patchedJson`

Узел подписки, к которому применилось REPLACE-правило, при каждом старте/рестарте VPN получал **ещё одну копию tag-префикса**. Тег рос неограниченно.

Номер таски: изначально заводилась как §303, переименована — 303 уже занят (`303-ws-early-data-ed-param.md`).

## Репро (4PDA #1263, k-dmitriy)

Подписка + активное import-rule (REPLACE). Префикс `xxx`, старт/рестарт:
```json
{"type": "vless", "tag": "xxx xxx 0004 - Универсальный | 20wl-6-1.legendary"}
```
Меняем префикс на `ууу`, старт/рестарт — старый префикс не уходит, новый клеится сверху:
```json
{"type": "vless", "tag": "ууу ууу xxx xxx 0001 - Универсальный | x5.ru"}
```
Без import-rules баг не воспроизводится.

## Причина (подтверждена по коду)

Разделяемая мутабельная Map между слоем хранения узла и потребителями `emit`:

1. **REPLACE сохраняет патч в узел** — `subscription_controller._applyRulesToNodes`: `node.patchedJson = outcome.patchedJson`.

2. **`emit` отдавал патч ПО ССЫЛКЕ** (`node_spec.dart`): `Outbound(patch)` — тот же Map-инстанс, что хранится в `patchedJson`.

3. **Потребители мутируют map результата `emit` на месте.** Их два:
   - билдер ([`server_list_build.dart:60-63`](../../../app/lib/services/builder/server_list_build.dart)) — пишет `map['tag'] = allocateTag(displayTag(prefix, main.tag))` и `map['detour']`;
   - проба ([`probe_config.dart:65-72`](../../../app/lib/services/probe/probe_config.dart)) — зеркалит билдер, пишет те же `tag`/`detour`.

   `main.tag` — **живой геттер** `map['tag']` (`singbox_entry.dart`), а не `NodeSpec.tag`: у обычного узла `emitRaw` строит свежую map на каждый вызов и мутации одноразовые, а у пропатченного map — это сам сохранённый `patchedJson`. Префиксованный тег впечатывался в патч, следующий build читал его как основу → `displayTag` клеил префикс поверх (`'$prefix $bare'`, не идемпотентен by design).

4. **Движок правил читал основу из `emit`** (`import_rules.dart`): при переприменении правил прошлый патч становился «исходником» — второй канал накопления (substitute-правила съедали собственный прошлый результат).

**Итого:** каждый build конфига в рамках сессии процесса = +1 префикс в сохранённом патче. Смена префикса ничего не убирала — старый уже впечатан, новый добавлялся слева.

Замечание: точки применения правил (сетевой refresh и регидрация из кэша) оперируют свежераспарсенными узлами, поэтому накопление между запусками приложения шло не через них, а через повторные build'ы внутри сессии.

## Решение (реализовано)

Три барьера, независимых друг от друга:

1. **`emit` отдаёт глубокую копию патча** (`node_spec.dart`, helper `deepCopyJson`). Результат `emit` теперь всегда одноразовый — симметрия с `emitRaw`, который строит свежие map на каждый вызов. Потребители (билдер, проба) вольны мутировать его как угодно. Глубокая, а не поверхностная: правила пишут во вложенные map (`tls.utls.…`), полагаться на «билдер трогает только верхний уровень» хрупко.

2. **Движок правил стартует с канонического вида**: `applyRulesToNode` берёт рабочую копию из `emitRaw`, а не из `emit` (`import_rules.dart`). Каждый прогон правил — с нуля, полный, детерминированный; прошлый патч никогда не исходник. Цепочки правил внутри одного прогона работают как раньше (локальная рабочая копия).

3. **Сброс перед переприменением**: `_applyRulesToNodes` обнуляет `patchedJson`/`ruleTrail` у всех узлов до прогона (`subscription_controller.dart`). Сегодня no-op (узлы свежие), но снимает накопление, если сюда когда-нибудь придёт живой список.

**Хеши (§283):** `nodeIdentityHash` строится по `emit − tag − detour`, tag в хеш не входит → фикс хеши не сдвигает, DISABLE-пометки юзеров живы. Закреплено тестами (tag-патч хеш не меняет; патч сути — меняет, by design).

## Сделано в этой же таске (запрос юзера 2026-07-25)

- **Пустая цель REPLACE = substitute по всему узлу** (симметрия с пустым путём условия «ищи везде»): движок обходит все листья JSON, заменяет найденные фрагменты, типы листьев сохраняются (`coerceJsonLike`), следы замен несут реальные пути. Что искать — явный `substitutePattern`, иначе паттерн условия с пустым путём (regex → карманы из совпадения в самом листе). Режим `set` с пустой целью по-прежнему непригоден (весь узел строкой не затирается) — `isUsable` + Save-блокер в редакторе. В сводках пустая цель показывается как `*`.
- **Значок «modified» и показ замен ожили**: были завязаны на `NodeSpec.originLine`, который никогда не проставлялся (мёртв с рождения §302) — значок и diff не показывались вовсе (4PDA #1262 «превью пустое»). Переведены на `ruleTrail` (заполняется контроллером при КАЖДОМ применении правил — refresh и регидрация из кэша, значок переживает рестарты). Поле `originLine` удалено.
- **Замены — вкладкой внутри разбора ноды** (решение юзера): «Replacements» третьей вкладкой в `NodeInspectScreen`, видна только у пропатченных нод (`ruleTrail` непуст). Показывает следы «путь: до → после»; рядом вкладка JSON с итоговым видом. Прежний пункт меню долгого тапа «View replacements» + его диалог удалены — замены живут там же, где остальной разбор узла.
- **Строка списка нод остаётся оригинальной** (решение юзера): `label`/`tag`/`server`/`port` — поля парсера, то есть ДО замен; факт правки показывает только карандаш. Патч виден в разборе ноды.

## Смежное из того же репорта — НЕ в этой таске

Решения юзера 2026-07-25:
- Кнопка `Apply rules` активна при отсутствии правил — **норма** (Apply = перезагрузка тела, нужна и для отката удалённых правил).
- Ярлык `matches` — **нормальный**, не трогаем.
- WARP-генератор: сохранение отредактированного шаблона — **не требуется**.
