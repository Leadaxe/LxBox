## Что и почему

У лаунчера пришёл баг: правило с тремя `.srs` после переоткрытия помнило один,
потому что тело правила держало один URL. Лаунчер перешёл на список. На границе
бэкапа контракт нёс один `ref`, и при переносе на телефон та же потеря
повторилась бы. Контракт добавил необязательное `rules[].refs` (все URL по
порядку, `ref` = первый, пишется при двух и более). Кейс корпуса
`backup/srs_multi_refs` у нас был красным: импортёр давал
`backup_unknown_field` на незнакомое поле.

Владелец решил: не провозить, а сделать то же самое — одно правило маршрута с
несколькими наборами.

## Что сделано

| Слой | Было | Стало |
|---|---|---|
| Модель `CustomRuleSrs` | `String srsUrl` | `List<String> srsUrls`, `srsUrl` = первый (геттер). JSON: `srsUrl` всегда, `srsUrls` при двух и более; чтение — `srsUrls` главнее. `cacheIdAt(id, i)`: индекс 0 = `id` (старые файлы кэша валидны), дальше `<id>~<i>` |
| Сборка `_applySrsSingle` | один `rule_set`, `rule_set: "<tag>"` | `rule_set` на каждый набор (`<name>`, `<name>-2`, …), одно правило с `rule_set: [теги]`; при одном наборе строка — конфиг байт-в-байт прежний. Нет файла хотя бы одного набора → правило пропущено с warning (частичной регистрации нет). `resolve`-правило и DNS-mirror получают то же множество тегов |
| `build_config` | путь по `cr.id` | путь по каждому `cacheId` |
| Экран Routing | скачан/не скачан по одному файлу | «скачано» = есть все файлы; загрузка всех по порядку, первый провал = провал правила; удаление правила и смена URL чистят все файлы; смена состава списка = смена URL (правило выключается до повторной загрузки) |
| Редактор правила | одно поле URL | то же поле многострочное, по одному URL на строку (подсказка под полем); ☁ активна, когда валидны все; Clear cache чистит и сохранённые, и набранные |
| Автообновление §366 | кандидат на правило | кандидат на каждый набор со своими метаданными, TTL общий |
| Debug API | `srs_url` | плюс `srs_urls` в сериализации; PATCH/POST принимают `srs_urls` (главнее) и `srs_url`; `download-srs` качает все, возвращает `paths` |
| Бэкап | `ref` | экспорт `ref` = первый + `refs` при двух и более; импорт `refs` главнее `ref`; `refs` в allowlist ключей правила; раннер корпуса сверяет `refs`, когда ключ есть в ожиданиях |

## Сценарии, которые проверены тестами

- модель: нормализация (trim, пустые, повторы), roundtrip JSON, copyWith одиночным и списком, `summary` «SRS: host (+N)»;
- сборка: три набора → три `rule_set` и одно правило; один набор → строка; нет одного файла → пропуск; resolve + список тегов;
- бэкап: импорт `refs`/`ref`, экспорт `ref`+`refs`, круг `import(export(x)) = x`;
- корпус контракта `backup/srs_multi_refs` — зелёный.

Не проверялось на устройстве: сценарий редактора с двумя URL и загрузкой (логика та же, что у пресетов с несколькими remote rule_set, которые на устройстве работают).
