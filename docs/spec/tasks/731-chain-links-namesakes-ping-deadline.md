## Problem

Четыре жалобы одного пользователя:

1. **#2001** — пинг подвисает на части WARP-узлов в цепочках: таймаут 5 с не
   срабатывает, в логе тишина.
2. **#2002** — после дублирования узла в папке копия с другим именем заменяет
   в цепочке исходный узел, а «нода не найдена» показывается про копию;
   удалённый узел остаётся в списке цепочки до перезахода на экран.
3. **#2003** — цепочки уходят в конец списка при сортировке по умолчанию.
4. **#2005** — detour-узел из папки не виден на главном экране, detour из
   другой папки не выбрать; просит опцию «show detour nodes on main screen».

## Diagnosis

Проверено по коду 15.11.2026.

### 1. Пинг без ответа ядра — дефект приложения (и, возможно, ядра)

Замер идёт унарным RPC libbox: `runNodeUrltest` / `runMassUrltest`
(`home_controller/ping_orchestration.dart`) → `CcChannel.urlTestOutbound`
(`vpn/cc_channel.dart`) → `BoxCommandClient.urlTestOutbound` (Kotlin).
Таймаут (`ping_options.timeout_ms`, шаблон 5000 мс) передаётся ядру и
держится только им. Ни Dart, ни Kotlin вызов не ограничивают: если RPC не
вернулся, одиночный пинг не снимает индикатор «PING…», воркер массового
пинга навсегда занимает слот (при зависании всех слотов проход не
заканчивается), в лог ничего не пишется. Особой ветки для `type: chain` и
WireGuard в пути пинга нет.

Почему ядро не отвечает на замер цепочки с WARP-звеном в срок — по коду
приложения не установить; на живом WARP не воспроизводилось. Это отдельный
вопрос к ядру.

### 2. Копия узла в папке — два дефекта

**2а. Реестр ссылок уводит ссылку на копию.** Члены папки с одинаковым тегом
делят один адрес `{folder_id, tag}` (`containerRawTags`, «у тёзок побеждает
первый»; сборка резолвит ссылку в первого). `diffNodeAddresses`
(`settings_storage/node_link_registry.dart`) этого не учитывал: копию узла `A`
добавили в папку (тег тот же), затем переименовали в `B` — в `moves` попадало
`{f, A} → {f, B}`, и `rewriteNodeLinks` переписывал на копию позицию цепочки,
detour члена, detour источника и состав autogroup оригинала. Нарушение
NODE_LINK §6 п. 3: ссылка не переуказывается на другой узел.

**2б. Снимок редактора цепочки устаревает.** Редактор берёт цели (кандидаты
пикера, признак «позиция потеряна») из последнего собранного конфига
(`chain_hop_targets.dart`). Правки состава папки конфиг не пересобирают —
он собирается при правке цепочки, добавлении источника и уходе с Servers.
Поэтому на том же заходе: позиция, уведённая на копию (2а), показана
потерянной — копии в конфиге ещё нет; удалённый узел остаётся в пикере
позиций. После перезахода на экран конфиг пересобран и всё сходится.

### 3. Цепочки в конце списка — по дизайну

Список главного экрана — члены группы Направления в порядке конфига. Сборка
ставит цепочки после всех узлов источников (`build_config.dart`, пул
Направления: `selectorEntries`, `replaceBuild.candidates`,
`chainResolution.tags`; комментарий §393 C3, корпус
`chain_is_a_node_in_directions` нормирует `[…узлы, hop-chain]`). Порядок
цепочки на Servers (§524) влияет только на то, кто на кого может сослаться;
§524 «Что НЕ сделано»: главный экран оставлен как есть. В режиме Ping узел
без замера уходит в хвост (`_compareLatency`).

### 4. Detour-узлы на главном — настройка есть, чужая папка закрыта решением

Звено detour скрыто из выбора узлов (features/006: «звенья скрыты из выбора
узлов»); показ включают «Register detour servers» / «Register detour in auto
group» в настройках подписки и папки (`DetourPolicy.registerDetourServers`,
`registerDetourInAuto`). Пикер detour (`detour_target_picker.dart`) предлагает
одиночные серверы, членов своей папки и detour-Направления; чужие папки
закрыты решением [239](239-folder-detour-symmetry.md): «Чужие папки — НЕЛЬЗЯ».
Формат ссылки (`NODE_LINK`) узел чужого контейнера допускает.

## Solution

Исправляются дефекты 1, 2а, 2б. Пункты 3 и 4 — на решение владельца (ниже).

- **1.** `CcChannel.urlTestOutbound` ждёт ответ не дольше «таймаут замера +
  запас 3 с» (при `timeoutMs = 0` — 10 с + запас). Истёк — результат с
  ошибкой `no reply from core in N ms` и строка уровня warning в логе. Узел
  получает ERR, слот массового пинга освобождается. Вызов в ядре не
  отменяется: `cancelPing` рвёт общий клиент вместе с чужими замерами.
  Одно место — покрыты одиночный и массовый пинг и послойная проба цепочки.
- **2а.** В `diffNodeAddresses` адрес держит первый узел с ним; тёзка ниже по
  списку ни `moves`, ни `gone` не порождает. Оставшийся на месте тёзка
  по-прежнему удерживает адрес от гашения.
- **2б.** `editChainAndPersist` перед открытием редактора зовёт
  `refreshChainEditorSnapshot`: при `SettingsStorage.configDirty` конфиг
  пересобирается общим путём `regenerateSourcesConfig` (применение к туннелю
  решает гейт §338/§667). Чистый флаг — сборки нет.

## На решение владельца

Решения по умолчанию (15.11.2026, по слову владельца «идти до логического
конца»; **подтвердить у владельца**): п. 3 — оставить по дизайну, код не
менять; п. 4 — вариант (а), код не менять, отвечать ссылкой на «Register
detour servers». Варианты ниже — если владелец решит иначе.

- **П. 3.** Эмитить цепочки в пул Направления в позиции из общего списка
  источников (§524) — смена поведения и нормы корпуса контракта
  (`chain_is_a_node_in_directions`), затрагивает лаунчер. Дешевле: в режиме
  Default держать цепочки над узлами только на главном экране.
- **П. 4.** (а) ничего не менять, отвечать ссылкой на «Register detour
  servers»; (б) тумблер показа у отдельного члена папки; (в) открыть в пикере
  detour узлы чужих папок и подписок — отмена решения 239, реестр ссылок
  такие ссылки уже ведёт (перенос, переименование, удаление).

## Дополнение 25.11.2026 — дедлайн замера probe-сессии

**Повод.** Telegram, сообщения 12043, 12079, 12094 (24.11.2026): тест серверов
подписки при выключенном VPN каждый раз встаёт на одном и том же узле (131),
с выключенным TLS Fragment проходит весь список.

**Диагностика.** Пункт 1 закрыл только боевой замер (`urlTestOutbound`).
Замер пробы `CcChannel.probeUrlTest` → `ProbeSession.urlTest` (Kotlin) ждал
ответ без предела, а `ProbeRunner._runPool` держит слот, пока замер не
вернётся. Ядро при `tls.fragment` после каждого куска ClientHello ждёт ACK
(`common/tlsfragment/wait_linux.go`, `writeAndWaitAck`) и выходит только по
ACK или по отмене контекста конфига клиента TLS (`tf.NewConn(conn, c.ctx, …)`),
а не по таймауту замера. Узел, который принял TCP и молчит на данные, держит
слот до `probeStop`. Десять таких узлов (concurrency по умолчанию) занимают
весь пул, и прогон стоит. Без фрагментации тот же узел падает по таймауту
ядра. Дефект ядра передан отдельно; здесь — страховка приложения.

**Решение.** `probeUrlTest` получает тот же дедлайн, что `urlTestOutbound`:
общий `_urlTestWithReplyDeadline` в `vpn/cc_channel.dart`, «таймаут замера +
3 с», по истечении — ошибка `no reply from core in N ms` и строка warning в
логе. Зависший вызов в ядре гасится `probeStop` в конце батча (сессия
закрывается, контекст конфига отменяется).

**Проверка.** `app/test/vpn/cc_url_test_reply_deadline_test.dart` — две
probe-группы: нет ответа → ошибка по дедлайну; ответ в срок проходит как
есть. Не проверено: эмулятор и телефон, узел с молчащим сервером под
фрагментацией.
