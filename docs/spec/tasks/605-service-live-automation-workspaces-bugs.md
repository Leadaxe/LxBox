## 1. (010) Уведомление об ошибке старта снимается сразу

**Проблема.** `BoxService.stopAndAlert` показывает текст ошибки через
`notification.show()` — это постоянное foreground-уведомление (id=1), — и
следующей строкой зовёт `notification.stop()` →
`stopForeground(STOP_FOREGROUND_REMOVE)`, которое то же уведомление снимает.
Пользователь, у которого старт упал в фоне (автостарт, плитка, Tasker),
ошибки не видит.

**Решение.** Ошибку показывать через `notification.showAlert()` —
отдельное уведомление (id=2) на том же канале, переживающее `stopSelf()`
(как у шторма sticky-рестартов §428). Постоянное снимается, как и раньше.
Структурные сигналы `alert:<type>:<details>` (их разбирает Flutter и
показывает диалог) в шторку не выводятся: сырой код пользователю не нужен.

**Приёмка.** После неудачного старта в шторке остаётся уведомление
«VPN error» с текстом ошибки; постоянного уведомления нет. Проверка — на
устройстве/эмуляторе (JVM-тестов рядом нет): пустой конфиг → Start из плитки.

## 2. (012) Запись профайлера не переподключается после перезапуска туннеля

**Проблема.** `TrafficProfiler.startGlobalRecording` поднимает
`profilerClient` один раз (`CcChannel.acquireProfiler`, счётчик 0→1).
Native `shutdownAll` на каждой остановке туннеля рвёт `profilerClient`, а на
следующем `connected` его никто не поднимает: счётчик в Dart остался 1,
чип «Live» горит, событий нет. То же при старте записи с опущенным туннелем
(первый `connect()` падает, повтора нет).

**Решение.** `CcChannel.restartProfiler()` — переподнять native-клиент, если
его держит хоть один потребитель (`_profilerRefs > 0`), по образцу
`restartTailscaleStatus`. Зовётся из `HomeController._startCcStreams` на
каждом `connected` рядом с `connectScreen`.

**Приёмка.** Юнит-тест: при `_profilerRefs > 0` `restartProfiler` шлёт
`ccConnectProfiler`, при 0 — ничего. На эмуляторе: запись → Restart →
`/profiler/live` снова наполняется.

## 3. (014) Приём команд расходится с системой после бэкапа и смены набора

**Проблема.** `automation_receive_enabled` — обычная переменная allowlist.
`setComponentEnabledSetting` (включение receiver'ов) зовётся только из
обработчика тумблера. Восстановление бэкапа и загрузка набора меняют
переменную, но не компонент: набор с «выкл» оставляет приём включённым, и
наоборот. После восстановления бэкапа не перечитываются и emit-гейты.

**Решение.** `syncAutomationFromStorage()` (`services/automation/`):
перечитать emit-гейты и выставить компонент по сохранённой переменной.
Вызов — на старте приложения (заодно лечит уже разошедшиеся установки),
после загрузки набора (шаг `_reloadStateFromDisk`) и после восстановления
бэкапа.

**Приёмка.** Юнит-тест: переменная `true`/`false` в хранилище → функция
передаёт то же значение в native-вызов и перечитывает гейты.

## 4. (014) Отказ ядра после принятого `SWITCH_NODE` молчит

**Проблема.** `actionSwitchNode` проверяет предусловия и запускает
`home.switchNode(tag)` без ожидания. Отказ `selectOutbound` ловится внутри
`switchNode` (только `lastError` + строка журнала); `VPN_ERROR` не
отправляется — ждущий Tasker уходит в таймаут.

**Решение.** `switchNode` возвращает `bool` (успех / уже активна / нечего
делать — `true`, пойманная ошибка — `false`). Automation-хендлер по `false`
шлёт `VPN_ERROR(code: switch_failed, message: node switch failed: "<tag>")`.
Произвольный текст исключения в открытый broadcast не идёт (как в
`automationErrorSignal`). UI-путь не меняется. Код `switch_failed`
добавляется в AUTOMATION.md.

**Приёмка.** Юнит-тест: `ccSelectOutbound` → `false`, `actionSwitchNode` →
эмитится `VPN_ERROR` с `code=switch_failed`.

## 5. (014) Тумблер Health ничего не включает

**Проблема.** 042F — won't-fix, источника Health-событий нет
(`emitHeartbeatFailed`/`emitLatencyDegraded` без вызовов). Но в App Settings →
Automation тумблер Health выглядит рабочим, а AUTOMATION.md обещает, что
события «появятся вместе с §042 health watchdog».

**Решение.** Убрать тумблер Health из UI (и его строку из каталогов ru/zh).
Имена событий остаются зарезервированными в AUTOMATION.md и спеке 014, без
обещания источника; переменная хранилища и гейт эмиттера остаются как
зарезервированные (бэкапы с ключом не ломаются).

**Приёмка.** В App Settings → Automation три категории: Lifecycle, State,
Subscription. AUTOMATION.md (EN/RU) и спека 014 не обещают Health-событий и
не упоминают категорию в UI.

## 6. (018) Авто-подключение после смены набора минует страховку отказа ядра

**Проблема.** Загрузка набора при поднятом VPN выставляет флаг
авто-подключения; после пересборки `HomeScreen` зовёт
`_controller.start()` напрямую. Кнопка Start идёт через
`runCoreRejectGuard` (фича 478: отказ ядра, назвавший узел, выключает узел и
повторяет). Набор с отвергаемым узлом после переключения просто не
поднимается.

**Решение.** В ветке авто-подключения звать `_runWithCoreRejectGuard()`
вместо `_controller.start()`.

**Приёмка.** Код ветки авто-подключения совпадает с путём кнопки Start.
Юнит-теста нет: ветка живёт в `HomeScreen._bootstrap` и требует всего
экрана; проверка — на эмуляторе (набор с узлом, который ядро отвергает →
Load при поднятом VPN → узел выключен, туннель поднят).

## 7. (020) Проверка dev-сборки в вопросе об обновлениях; порядок Skip/Enable

**Проблема.** Вопрос «Check for updates?» пропускается для dev-сборки по
`version.contains('-dev.')`, а `UpdateChecker` считает dev-сборкой
`contains('-dev') || startsWith('0.0.0')`. Сборка `0.0.0-dev` вопрос
получает, хотя чекер для неё молчит. Второе замечание — «порядок Skip/Enable
не зависит от канала» — расхождение комментария с кодом: спеки 395 и 020
(first-run) требуют от канала только умолчание при закрытии «назад», порядок
кнопок фиксированный.

**Решение.** Одна функция `UpdateChecker.isDevBuild` для обоих мест.
Комментарий в `home_dialogs.dart` привести к спеке (канал = только дефолт
при закрытии); порядок кнопок не менять.

**Приёмка.** Юнит-тест `isDevBuild`: `0.0.0-dev`, `2.25.9-dev.3`, `0.0.0` —
dev; `2.25.9` — нет.

## 8. (020) Отклики «выбор узла» и «применение пресета» объявлены, но не вызываются

**Проблема.** `HapticService.onNodeSelect`/`onPresetApply` объявлены,
вызовов нет.

**Решение.** Спека 020 (haptic-feedback, «Boundaries») прямо говорит: выбор
узла и применение пресета отклика не дают. Мёртвые методы удалить; поведение
не меняется.

**Приёмка.** Методов в `haptic_service.dart` нет, `flutter analyze` чист.

## 9. (028) Плашка «DNS / router events off» без предмета

**Проблема.** На вкладке Live профайлера при выключенном «Forward sing-box
logs» висит плашка «DNS / router events off — turn on 'Forward sing-box
logs'». После §180/§044 профайлер из журнала ядра не берёт ничего (DNS —
структурный поток `CcChannel.dnsQueries`, владелец — из CommandClient),
плашка обещает потерю, которой нет.

**Решение.** Удалить виджет `core_logs_hint_banner.dart`, его показ в
`live_events_tab.dart` и два мёртвых ключа ru/zh. Упоминания в 013
(core-log, live-events) и 028 (FEATURE, attribution) убрать, EN+RU.

**Приёмка.** Плашки нет; ключей «DNS / router events off» и «— turn on
'Forward sing-box logs'» в каталогах нет; `hardcoded_check` и `flutter
analyze` чисты. Тестов на плашку не было.

## 10. (028 P2) Ложный tcpClose после STOP→START

**Проблема.** `startGlobalRecording` чистит буфер, но не `_connSnapshots`.
Соединение, открытое до STOP, на первом снапшоте после START отсутствует →
diff-блок `_ingestCcConnections` считает его закрывшимся и кладёт tcpClose
прошлой сессии в новый буфер.

**Решение.** START сбрасывает и `_connSnapshots`. `_closedHandled` не
трогаем: ядро держит закрытые соединения до 5 мин, без дедупа их закрытия
всплыли бы в новой сессии. Идёт в паре с пунктом 2 (переподключение
записи после рестарта туннеля).

**Приёмка.** Юнит `traffic_profiler_test.dart` «после STOP→START в буфере
только новая сессия»: conn `a` до STOP, `b` после START → буфер `[b]`, без
tcpClose. P2 в спеке 028 получает свидетеля.
