### 2.1. Реестр и единый конвейер разбора (фичи 460 → 472 → 480)

Слой автомата чистый: `services/core_reject/` не знает виджетов. Хост —
фасад над контроллерами. Это соответствует §291.

### D1. Страховка не является единственным входом старта — и на Dart тоже

**Серьёзность:** высокая как находка; **не чинить**  
**Тип:** новое (спека 478 признавала только Kotlin-обход)  
**Вердикт:** 20.09.2026, владелец. Норма записана в спеку 478.

Спека 478 говорит: страховку зовут кнопка Start и
`start-vpn-headless?guard=true`; остальное (QS, сторож, Intent, автозапуск)
идёт мимо и падает как прежде. Это подтверждено:

| Вход | Путь | Страховка |
|---|---|---|
| Кнопка Start на главном | `home_screen.dart:960` → `runCoreRejectGuard` | да |
| Debug `start-vpn-headless?guard=true` | `action.dart:298` | да |
| Debug / Automation `start-vpn` | `guard=false` → `home.start()` | нет (осознанно, §494) |
| QS-тайл | `LxBoxTileService.kt:99` → `BoxVpnService.start` | нет |
| Boot / auto-start | `BootReceiver.kt:275` | нет |
| Сторож | `VpnWatchdog.kt:125` | нет |
| Intent API §047 | `LxBoxIntentReceiver.kt:90`, `LocaleSettingReceiver.kt:48` | нет |

**Dart-входы без страховки, которых спека на сверке не называла:**

1. **Кнопка Reload, VPN выключен** («Rebuild config + connect») —
   `home_controls.dart:318` → `_rebuildAndStart` → `_controller.start()`
   (`home_screen.dart:892`).
2. **Reload при живом туннеле** — `_rebuildAndReconnect` → `reconnect()` →
   `_startInternal()` (`home_controller.dart:950`).
3. **Автоподключение после смены workspace** — `home_screen.dart:475` →
   `_controller.start()`.
4. **In-place reload / автоприменение §338** при живом туннеле —
   `reloadVpn()` → `startOrReloadService`.

Автомат висит не на `start()`. `HomeController.start()` / `_startInternal()` —
примитив «скажи native поднять сервис». Прогон (`runCoreRejectGuard`) —
обёртка жеста кнопки Start: она сама вызывает `startAndAwaitVerdict()` →
`start()`. Reload, workspace и меню Reconnect бьют в примитив напрямую —
поэтому автомата не видят. Класть проверку внутрь `start()` нельзя: автомат
его вызывает, будет рекурсия.

**Почему не оборачивать всё.** Автомат имеет право выключать узлы, потому
что человек нажал Start. Размазать его на любой подъём VPN — тихое
выключение без этого жеста (как раз то, чего спека 478 не хотела на
путях без UI).

**Kotlin (плитка QS / boot / сторож / Intent) — не чинить.** Это не сборка
нового состава. Все четыре зовут `BoxVpnService.start` → `ConfigManager.load()`
→ последний JSON, который Dart уже записал. Типичный путь: Start со
страховкой выключил негодное, пересобрал, записал, поднял; перезагрузка /
плитка / сторож поднимают этот файл. Сторож ещё чище: возвращает то, что
уже крутилось. На диске лежит последний *сохранённый* конфиг, не обязательно
последний удачно стартовавший (Dart мог записать «Rebuild only» без старта) —
это не повод чинить Kotlin: сборку по-прежнему делает Dart.

Что это за входы:

- **QS** — плитка L×Box в шторке быстрых настроек. Тап включает/выключает
  VPN, приложение не открывается (экран нужен только пока нет согласия VPN).
- **Boot** — галка автозапуска: после загрузки телефона `BOOT_COMPLETED` →
  тот же старт с диска.
- **Сторож (§428)** — не кнопка. Пока туннель «желателен», живой сервис
  переставляет будильник; процесс умер без явного Stop — будильник поднимает
  сервис снова. Ручной Stop не перебивает.
- **Intent (§047)** — Tasker / MacroDroid / `am broadcast`. По умолчанию
  выкл. Команда start-vpn идёт в native напрямую, не в кнопку Start.

**Прочий Dart — тоже не чинить.** Если с диска стартует тот же конфиг, что
уже держал туннель, — взлетит. Если конфиг новый (Reload dirty, reconnect
после пересборки, смена слота, автоприменение) — это «примени другое», а не
«верни как было». Автомат здесь не должен сам выключать узлы: отказ, туннель
лежит, человек жмёт Start — проверка с согласием. Снятие живого туннеля при
Reload/Reconnect — цена смены состава, не баг 478.

Полный фасад «безопасный start/reconnect везде» не делаем. `reloadVpn()` в
эту команду и не входил бы: это перечитывание файла в живом box, не
stop+start.

Нотсы: не обещать «на любом способе поднять туннель». Правда — «кнопка Start
выключает негодный узел и поднимает остальных».

### D2. Три источника уведомлений, не один

**Серьёзность:** высокая  
**Тип:** частично закрыто §505, шов остался

Заявленный единый API — `warningsForConfigTag` (разбор + вердикт + сборка).
Фактически:

| Поверхность | Откуда берёт |
|---|---|
| Главный экран (presenter) | `warningsForConfigTag` + `lastBuildWarningsByTag` |
| Diagnostics одиночного / члена папки | то же |
| Подпись одиночного на Servers | то же |
| Список узлов **подписки** | только `node.warnings` (`subscription_node_list.dart:76`, `node_inspect_screen.dart:89`) |
| Счётчик на строке подписки/папки | `entryWarningSummary` — разбор + вердикт, **без** сборки (`entry_warnings.dart:143–154`) |
| Inspect из листа страховки | вердикт дописывается мутацией `stampNodeWarnings` перед пушем (`core_reject_ui.dart:102`) |

`lastBuildWarningsByTag` живёт **только в памяти сессии**
(`subscription_controller.dart:145–148`), заполняется в `generateConfig`.
Холодный старт без dirty/пустого конфига **не** пересобирает
(`home_screen.dart:458`) — гард реестра на сборке на главном снова пуст,
пока кто-то не нажмёт Reload. §505 починил разбор+вердикт; предупреждения
**сборки** после рестарта по-прежнему дырявые.

Отсюда же дефект, который владелец поймал на эмуляторе (AWG MTU на Servers
есть, на главном нет): два агента написали **две спеки с номером 505**
(`505-home-badge-cold-start.md` и `505-home-node-badge-user-server.md`) с
разным «единым источником». Задачей §513 первая слита во вторую и удалена. Код ближе ко второй, но подписка и счётчик
строки её не используют.

Корень дырявой сборки после рестарта — D17: карта в памяти вместо полей
записи `body` / `warnings`.

### D3. Доменная склейка уведомлений лежит в `screens/`

**Серьёзность:** средняя  
**Тип:** новое

`warningsForConfigTag` / `mergedNodeWarnings` / `entryWarningSummary` живут
в `screens/subscriptions_screen/entry_warnings.dart`. Их импортируют главный
экран, настройки узла, папка, подписка. Это не презентация — это правило

(`services/` или контроллер), не экран источника.

`mergedNodeWarnings` уже в `controllers/…/core_reject_ops.dart`; UI-склейка
с сборкой — рядом, в screens. Два модуля, одна ответственность.

### D4. Вердикт дописывается мутацией `NodeSpec.warnings`

**Серьёзность:** средняя  
**Тип:** новое (следствие 478 + 283)

`stampStoredVerdicts` / `stampNodeWarnings` **вставляют** `core_rejected` в
список предупреждений разобранного узла (`core_reject_ops.dart:559–579`).
Комментарий сам говорит: предупреждения при пересчёте замещаются целиком,
вердикт иначе пропадает. Отсюда:

- часть экранов читает `node.warnings` и «случайно» видит вердикт, если
  штамп уже прошёл;
- часть читает `mergedNodeWarnings` без мутации;
- `unstampCoreRejected` обязан пройтись по инстансу при ручном включении.

Это тот же класс ловушки, что §283 (кэш identity / подмена инстансов).
Штамп на объекте — скрытый второй канал рядом с `nodeWarnings` в хранилище.

### D5. Реестр объявляет примитивы, движок их не исполняет — молча

**Серьёзность:** средняя  
**Тип:** долг спеки 480, проверено

- `emit.refuse_when` (WG, больше одного пира) и `round_trip_only: "emit"`
  (dialer→detour) — в реестре 1.1.42, движок не читает. Линтер не краснеет.
  Сейчас недостижимы из-за сводки `.conf` к одному пиру **до** эмита; когда
  многопировый узел доедет до эмита целиком, отказ не сработает, и это
  узнает пользователь, не CI.
- `on_unrecognized` (вместо ветки `clash_yaml`) не исполняется. Запасной
  путь в `body_decoder.dart:96–100, 206–211` рукописный: JSON без своей
  ветки не должен превратиться в «список ссылок из одной строки». Две дороги
  опознания документа.

### D6. Оверлеи и красный корпус — две правды emit

**Серьёзность:** средняя  
**Тип:** долг, проверено

`contract_draft/` держит расхождения, без которых Copy link на телефоне и на
десктопе даст разную ссылку: ss padding (`=` срезается у нас), xhttp
`emit_as`, ws `eh`, vmess `json_map`. Это не баг сборки — осознанный раскол
сторон. Для пользователя «скопировал на телефоне → вставил на десктопе»
round-trip **не** гарантирован на этих схемах, хотя нотсы говорят обратное
общим тезисом.

Красные кейсы корпуса (спека 480 §12/§15): `naive/empty_host_rejected`
(`parse_error` vs `emit_error`+`field_missing`); пачка `xray/*` (бухгалтерия
`dropped[]`, род группы `urltest` vs `group`). На CI корпус с гейтом
`existsSync` часть путей скипает — зелёный CI не доказывает паритет этих
кейсов.

гоняет его по **дословному** телу. Но модель — фильтр: ключ, который

дословный JSON и ставит код; список подписки без пересборки — нет. Это
ровно D2: предупреждение сборки не переживает холодный старт.

Карточка узла с мусором «сразу при разборе» (CHANGELOG) верна для пути, где
санитайзер видит raw; не верна как общее правило для всех кодов гарда.

Уточнение по коду (`parse_warnings.dart`):

- узел конвейера (`isPipelineParsed`) второй проход по `emit()`
  **пропускает** — иначе `value` стал бы каноном (`chrome` вместо
  написанного `HelloChrome_120`);
- не-конвейерный узел судится по `node.emit()` — ключ вне схемы туда не
  попадает;
- `annotateFromRawBody` закрывает sing-box JSON; **Xray `rawSource` —
  объект Xray**, санитайзер его отказывает (`parse_warnings.dart:117–123`).
  У Xray-узла `unknown_key` на разборе по-прежнему только у гарда сборки,
  пока маппер не построит sing-box-карту.

### D13. Экраны узла не слушают `entry` — кэш identity §283

**Серьёзность:** средняя  
**Тип:** новое

`NodeSettingsScreen` снимает `_node` и `_notifications` в `_load()`
(`node_settings_screen.dart:98–166`) и не подписывается на `widget.entry` /

Список самой подписки по-прежнему слушает entry — тот фикс §283 не
откатили. Сломан только экран деталей.

### D14. Тело ↔ модель всё ещё рукописная вторая таблица

**Серьёзность:** средняя  
**Тип:** долг 480, проверено

URI / Xray / INI маппятся движком. `parseSingboxEntry` (`json_parsers.dart`,

молча не доезжает. Round-trip `parse(emit(body))` может потерять то, что
лаунчер держит.

Это не оверлей, а второй источник истины внутри приложения.

### D17. Кеш записи не используем: `body` и `warnings`

**Серьёзность:** средняя (нагрузка / батарея; не старт VPN)  
**Тип:** новое (владелец, 20.09.2026, разбор D2)  
**До тега v2.25.0:** не чинить — отдельная задача, если брать

В модели записи уже есть оба механизма кеша:

- `body` — распакованная заготовка узла в форме sing-box (кеш от
  `origin.raw`);
- `warnings` — поле записи (у подписки карта по узлу, у одиночного / члена
  папки — список).

Ими почти не пользуемся.

`origin.raw` — истина, это верно (§455: `body` для серверов **не пишется**,
при загрузке и при `body` в чужом бэкапе текст источника разбирают заново).
Предупреждения разбора живут только на объекте `NodeSpec` в памяти и после
рестарта **считаются снова** из `origin`. Поле `warnings` на диске занято
вердиктом страховки (`core_rejected` + `enabled`), не списком разбора и не
гардом сборки. Гард сборки — третья, уже вовсе не запись: карта
`lastBuildWarningsByTag` в контроллере, до следующей `generateConfig` или
смерти процесса.

Следствие: каждый холодный старт гоняет парсер по всем узлам, хотя объект
sing-box уже однажды получали; значки сборки на главном требуют ещё и полной
пересборки конфига (D2, D9). Это лишняя работа на CPU и не
энергоэффективно — механизмы кеша в контракте записи для этого и были.

Чинить — начать писать и читать `body` как кеш (с инвалидацией при смене
`origin` / бампе парсера) и складывать в `warnings` записи не только вердикт,
но и коды разбора/сборки, которые должны переживать рестарт. Норма «origin =
истина, body не истина» при этом не отменяется: кеш, не кнопка Regen.
