## Решение владельца (24.09.2026)

> «Как мы храним по маркеру kind, так мы должны и структуру держать. У нас есть
> узлы, прямые узлы, автоматические узлы, узлы-цепочки и папки/подписки с узлами
> внутри. Разных списков быть не должно. Цепочки — такие же серверы, как
> авто-серверы; в экспорте бэкапа категория Routing для цепочек — ошибка, они
> идут в серверы.»

## Что было: расщепление жило НАД диском

На диске список уже был единый — один массив `sources[]`, дискриминатор `kind`
(`subscription`/`server`/`folder`/`chain`), порядок записей нормативен, отдельного
ключа `chains`/`detours` нет с §439. Двойственность была в пяти слоях выше:

| Слой | Что было | Цена |
|---|---|---|
| **Модели** | `sealed ServerList` («контейнер узлов») и `SourceChain` — самостоятельный класс без супертипа и интерфейса | нет типа «запись списка»; порядок нельзя выразить как данные |
| **Хранение** | ДВА писателя над одним массивом: `sources_rules.dart` (часть без цепочек) и `chains.dart` (часть цепочек). Каждый вписывал свой род в чужой контекст, НЕ имея на руках чужих записей | `_spliceSourceKind` — восстановление потерянной при расщеплении информации сопоставлением слотов по ключу. Дал подряд два бага: §511 M1 (удаление сдвигало соседей того же рода) и §511 M2 (одна нечитаемая запись отвергала любой drag) |
| **Контроллер** | держал только `_entries` (контейнеры); цепочки читал с диска ad-hoc; `applyEntryOrder` принимал только entry-id — теги цепочек выразить было нечем | контроллер не знал о смешанном порядке |
| **Экран Servers** | три источника истины в одном `State` (`entries`, `_chains`, `List<String> _sourceKeys`), сшивка в `_rows()` на каждый кадр | один drag = ДВЕ независимо падающие записи на диск; порядок жил как `List<String>` в state одного экрана, а не как данные |
| **Debug API / бэкап** | `GET /subs` цепочек не видел вовсе (`/chains` — отдельный роут); экспорт бэкапа относил цепочки к категории Routing | смешанный порядок диска нельзя было ни прочитать, ни выразить через API |

Ключевой вывод: **слоты — цена расщепления моделей, а не свойство хранения.**
При «просто одном массиве с `kind`» сопоставление слотов не нужно: писатель
получает весь список и пишет его целиком.

## Что стало: единая модель в памяти/UI, формат на диске БЕЗ изменений

### 1. Модель — `app/lib/models/source_entry.dart`

`sealed class SourceEntry` с общим `sourceKey`, `kind`, `enabled`,
`displayLabel`. Члены:

| Член | Что несёт | `sourceKey` |
|---|---|---|
| `ContainerEntry` | `ServerList` — подписка / одиночный сервер / папка | `id:<uuid>` |
| `ChainEntry` | `SourceChain` — цепочка | `chain:<tag>` |
| `OpaqueEntry` | сырую запись, которую кодек не прочитал (§141 P1.8c): чужой или будущий `kind`, битый JSON | `raw:<индекс>` |

Идентичность НЕ двигали: у контейнера остался uuid, у цепочки — тег; ключ
производный и не хранится. Форма ключа (`id:` / `chain:`) — та же, что была у
`SettingsStorage.sourceKeyForId`/`sourceKeyForChain` (§509).

Грабля, на которую наступили при реализации: `SourceEntry.kind` обязан быть
`kind` **записи на диске**, а не `ServerList.type` — у одиночного сервера `type`
отдаёт историческое `user` (имя формы 2.23.2), тогда как на диске стоит `server`.

`OpaqueEntry.sourceKey` нестабилен между перестановками (это индекс). Допустимо
ровно потому, что записи нет ни в UI, ни в сборке конфига: её адресуют только
«останься где стоишь».

### 2. Хранение — один читатель, один писатель

- `_sourceEntriesOf(doc)` — единственное чтение массива; `getServerLists` и
  `getChains` стали его СРЕЗАМИ (`whereType`), а не независимыми проходами.
- `_writeEntries(entries)` — единственный писатель. Получает весь список,
  пишет его целиком; `OpaqueEntry` едет своим сырым объектом байт в байт.
- `SettingsStorage.getSourceEntries()` / `saveSourceEntries()` /
  `sourceEntriesOf()` — публичный API смешанного списка.
- **Удалено:** `_spliceSourceKind`, фильтры «не-цепочек» (`if (_isChainRecord(r))
  continue;` в чтении источников и его зеркало в чтении цепочек),
  `_sourceRecordKey` (ключ теперь на модели).
- `_reorderSources` переписан на `SourceEntry` — та же семантика (§511 M2:
  частичная перестановка законна, нечитаемые держат слоты; §511 m4: `bool` +
  `AppLog`), но без работы с сырыми `Map`.
- `saveServerLists` / `setChains` **остались фасадами** (~100 сайтов вызова в
  `lib/` и тестах): читают список целиком и заменяют свой род через
  `_replaceKind<T>`. Это единственное место, где сопоставление слотов по ключу
  ещё нужно — у фасада на руках нет ответа, КАКОЕ из мест своего рода
  освободилось. Единый писатель в этом не нуждается.

**Долг §511:54-59 закрыт.** Нечитаемая запись теперь полноправный элемент
списка, а не «то, чего писатель не трогает»: она переживает ЗАПИСЬ, а не только
чтение, и уезжает на диск со всеми ключами, которых модель не держит.

### 3. Контроллер

- `sourceEntries()` — весь список всех родов: контейнеры из живых `_entries` (с
  fetch-состоянием), цепочки и нечитаемые записи с диска.
- `applySourceOrder(keys)` — порядок ОДНОЙ записью на диск, ключи любого рода.
  Взаимный порядок контейнеров зеркалится в `_entries` **в памяти**, без второго
  `_persist`: иначе следующая мутация (toggle, rename, авто-refresh) вернула бы
  прежний порядок.
- Барьер поколения §515 (`stale`) на месте: первая строка `applySourceOrder`.
- `applyEntryOrder` остался для перестановки ТОЛЬКО контейнеров (Debug API
  legacy, тесты); общий drag идёт через `applySourceOrder`.

### 4. Экран Servers

`_chains`, `_sourceKeys` и сшивка трёх источников в `_rows()` сняты. Строки
берутся из одного `List<SourceEntry> _sources`, `_chains` остался геттером-срезом
для диалогов (редактор цепочки хочет соседей). `_SourceRow` сохранён: он живёт
внутри одного экрана и держит индекс записи в контроллере (счёт его мутаций, не
общего списка). Drag → одна `applySourceOrder`.

«Удаление из середины» и «перестановка при нечитаемой записи» проходят по
построению: писатель получает весь список.

### 5. Сборка конфига — без изменений поведения

Ацикличность цепочек держится индексом в `sources[]` (`build_config.dart`,
`chain_nodes.dart`). Сборка получает цепочки через `getChains()`, который теперь
СРЕЗ единого чтения в том же порядке массива — инвариант «позиция ссылается
только на цепочку ВЫШЕ» сохранён по построению. Тесты `chain_emit`,
`detour_direction_gates`, `detour_append_replace`, `runtime_chain`,
`chain_positions_block` зелёные без правок.

### 6. Бэкап — цепочки в серверы

Экспорт: `sources[]` больше НЕ режется по роду записи — весь ключ едет галкой
**Server lists**. `availableCategories()` и `countFor()` это отражают (цепочки в
счёте серверов); `_hasAnyRouting` цепочек больше не считает; merge-импорт
цепочек идёт той же галкой. Функция `_isChainRecord` в `backup_service.dart`
удалена — делить стало нечего.

**Обратная совместимость ЧТЕНИЯ.** Старый архив, где цепочки экспортировали
галкой Routing, читается по-прежнему: цепочки лежат в том же ключе `sources[]`,
и восстановление берёт их оттуда независимо от того, какой галкой их когда-то
экспортировали. Что изменилось для старого файла: применяются они теперь
галкой Server lists, а не Routing. Тест на это есть
(`backup_service_legacy_test`: «старый архив с цепочками читается галкой Server
lists»).

Формат файла НЕ менялся: тот же ключ, те же записи, тот же порядок, тот же
`storage_version`, тот же `lx_backup: 2`. **Ни один golden не перегенерирован**
— `golden_config`, `golden_backup`, `golden_storage_roundtrip`, `lx_backup_v10`,
`lx_backup` зелёные на прежних фикстурах.

Внешний LX Backup 1.0 не трогали: у него своя корневая секция `chains[]` и своя
спека (§393 C9).

### 7. Debug API

`GET /subs` отдаёт ВЕСЬ список источников в порядке `sources[]`; каждая запись
несёт `source_key`. Цепочка — `kind: "SourceChain"` с `nodes_count` =
`hops_count` = число позиций (§520). Нечитаемая — `kind: "Unreadable"` с
`record_kind`. Маршрут цепочки здесь не разворачивается: его читает и правит
`/chains/{tag}` — `/subs` отвечает за состав и порядок.

`POST /subs/reorder` принимает `source_key` любого рода; голый uuid тоже
(форма до §524, клиенты её знают). Одна запись на диск вместо цикла
`moveEntry` по одному.

`GET /state/subs` цепочек НЕ включает: это снимок состояния контроллера
подписок (fetch-состояние, счётчики), а не список источников. Документировано.

### 8. Workspaces

Слот пространства (§417) — папка с КОПИЕЙ файлов состояния; `_copySceneToSlot`
копирует файлы целиком и записей никогда не разбирал. Правок не потребовалось;
`workspace_stale_controller_persist_test`, `workspace_legacy_slot_load_test`
зелёные.

## Инварианты

1. **Один упорядоченный список — единственный источник истины о порядке.**
   Порядок = порядок `sources[]` на диске, «порядок как данные».
2. **Один писатель массива** (`_writeEntries`). Перестановка, удаление и toggle
   любого рода — ОДНА запись на операцию.
3. **Идентичность не двигается:** uuid у контейнера, тег у цепочки. `sourceKey`
   их только накрывает и не хранится.
4. **Нечитаемая запись держит своё место** и уезжает на диск байт в байт.
5. **Формат на диске, версия storage, контракт 1.x, бэкап — без изменений.**
6. **Ацикличность цепочек** — от порядка списка (ссылка только ВВЕРХ), тем же
   индексом, что раньше.
7. **Барьер §515** остаётся на уровне контроллера, а не в писателе хранения:
   под писателем есть легитимные клиенты вне `HomeScreen` (импорт бэкапа,
   Debug API, шаги регидрации).

## Что НЕ сделано (открытые вопросы)

**Главный экран (`node_list_presenter.dart`) цепочек как источников не
показывает.** Презентер фильтрует ЭМИТИРОВАННЫЕ узлы по префиксу подписки; у
цепочки нет своих узлов — она сама эмитируется одним outbound'ом и уже стоит в
пуле как узел. Пришивать её к презентеру «источником» значило бы выдумать
сущность, которой в пуле нет. Оставлено как есть; если владелец имел в виду
отдельную строку-раздел на главном, это другая задача (какой у неё смысл в
списке узлов — вопрос владельцу).

**`_entries` контроллера остался списком ТОЛЬКО контейнеров.** Полное слияние
цепочек в `_entries` потребовало бы переписать ~50 индексных мутаций
(`toggleAt(index)`, `_entries[index]`, `removeAt`) и все их вызовы из семи
экранов — риск, несоразмерный выигрышу: порядок как данные и один писатель
достигнуты `sourceEntries()`/`applySourceOrder()`. Записи родов, у которых нет
общих мутаций (у цепочки нет fetch, у подписки нет hops), всё равно
адресовались бы через `switch`.

**Авто-узел (§322) корневым родом списка НЕ стал** и не должен: по дизайну он
член `folder.nodes[]`, а не запись `sources[]` (см. `509:32`). Претензия «узлы
автоматические» как род общего списка сегодня не выполняется по дизайну §322 —
единый корневой список этого не меняет.
