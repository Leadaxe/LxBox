## Problem

«Тест серверов» (⏱ на экране подписки и папки) идёт probe-сессией при
выключенном VPN и собирает свой конфиг без detour-политики источника: узел
проверяется напрямую. Родная цепочка узла (`⚙`-звенья из тела) в пробу
попадает, а `DetourPolicy.overrideDetour` источника — нет.

Следствия:

- в сети, где интернет есть только через прокси (WAP-шлюз оператора,
  корпоративный прокси), тест показывает «нет пинга» по всем узлам при
  рабочей боевой цепочке;
- пользователь нигде не видит, что тест и туннель ходят разными путями.

## Diagnosis

Проверено по коду 15.11.2026:

- `app/lib/services/probe/probe_config.dart`, `_buildOne`: тело узла берётся
  `node.getEntries(null)`; шапка файла прямо говорит «Detour-политика НЕ
  применяется». `_assemble` ставит `main.detour` только на первое звено
  родной цепочки.
- `app/lib/services/probe/probe_runner.dart`: проба возможна только без VPN
  (второй CommandServer в процессе невозможен); через боевое ядро не
  тестируем сознательно (236: замер шёл бы поверх активного Направления, а
  выключенные узлы выпали бы из конфига).
- Боевая сборка, `app/lib/services/builder/server_list_build.dart`: ссылка
  `policy.overrideDetour` откладывается (`ctx.deferDetour`) и разрешается
  вторым проходом `resolveDeferredDetours`, когда собраны все источники.
  Режимы: `useDetourServers=false` — цепочка снята; override + append —
  ссылка хвостом родной цепочки; override + `replaceDetourChain` — родная
  цепочка отброшена.
- Цель ссылки (`NodeLink`) бывает двух родов. Конкретный узел: узел
  одиночного сервера (корневая ссылка) или узел папки / подписки
  (`folderId` + сырой тег). Имя, за которым стоит выбор в рантайме:
  Направление и его `-auto`, служебный outbound шаблона, цепочка, узел-группа.
- Экраны `subscription_detail_screen.dart` и `folder_detail_screen.dart`
  зовут `ProbeRunner.run(nodes, tlsByIndex: …)`; о detour пользователю не
  сообщается ничего.

### Наблюдение с 4PDA: «тест не работает с detour при prefer_ipv6»

Pauk и k-dmitriy (27.10.2026, версии 2.25.17–2.25.18): тест серверов
перестаёт работать, когда у подписки задан detour, причём только при
`dns_strategy = prefer_ipv6`; без detour или с ipv4-стратегией работает.
Владелец тогда не воспроизвёл. Проверено по коду 15.11.2026:

- Probe-путь (тест без VPN) в 2.25.17 и 2.25.18 тот же, что до §730:
  `_buildOne` берёт `node.getEntries(null)`, detour-политику источника не
  читает; DNS пробы — один сервер `{"type": "local"}` без `strategy`,
  `route.default_domain_resolver` на него же. Переменные шаблона проба
  берёт только для `lx.sniff_guard`, `tls_fragment*`, `tls_mixed_case_sni`
  (`loadProbeVars`), `dns_strategy` / `resolve_strategy` — нет.
  `yieldToBuildDetour` срабатывает только на родной цепочке узла. Значит
  через probe-сессию сочетание «detour + prefer_ipv6» на результат влиять
  не может: **объяснения в probe-коде нет**.
- Оба параметра есть в БОЕВОМ конфиге: `dns.strategy = @dns_strategy`
  (`wizard_template.json`) и detour узлов источника. Пинг узлов на главном
  при включённом VPN (`home_controller/ping_orchestration.dart`) идёт через
  боевое ядро — вероятно, пользователи мерили так. Гипотеза (не проверена,
  в коде ядра не подтверждена): при `prefer_ipv6` адрес сервера узла
  резолвится сначала в IPv6, и через detour (HTTP/SOCKS-прокси оператора без
  IPv6) соединение с IPv6-адресом не устанавливается или висит до таймаута
  замера, тогда как прямой дайл без detour сразу получает «сеть недоступна»
  и переходит на IPv4. Это поведение ядра в туннеле, не дефект пробы, и в
  объём §730 не входит — кандидат в отдельную задачу (воспроизвести на
  эмуляторе без IPv6 с detour на HTTP-прокси).

## Solution

Согласовано владельцем 15.11.2026 («статические можно учесть,
динамические — Направления и подобное — не учитывать; если не учтено — явно
писать»), решения — в разделе «Принятые решения».

### 1. Классификация detour источника

Новый файл `app/lib/services/probe/probe_detour.dart`, чистая функция от
источника и списка всех источников. Три исхода:

| Исход | Когда | Что делает тест |
|---|---|---|
| нет | override не задан, или `useDetourServers=false` в режиме append (так же, как боевая сборка: REPLACE применяет ссылку и при выключенном `useDetourServers`) | как сейчас |
| учтён | ссылка указывает на один конкретный узел (не группа, не Tailscale), цель включена и у неё нет своего override | узел идёт через цель |
| не учтён | Направление, `-auto`, служебный outbound, цепочка, группа; ссылка не разрешилась или неоднозначна; цель выключена (сам узел, его источник, отметка узла подписки, выключенный член папки); у цели свой override; ссылка на сам узел | как сейчас + пометка |

Корневая ссылка сопоставляется с узлами одиночных серверов по
display-тегу (`TagResolver.displayTag`); ровно одно совпадение — «учтён»,
иначе «не учтён». Ссылка с `folderId` — по `id` контейнера и сырому тегу
(`containerRawTags`).

«Свой override цели» — эффективная политика узла-цели в его источнике: у
подписки и сервера — `detourPolicy`, у члена папки —
`FolderDetourPlan.policyFor` (личный detour, exempt, папочный replace).

**Папки.** Эффективная политика каждого члена — та же, что у боевой сборки:
`FolderDetourPlan.policyFor(i, folder.detourPolicy)`
(`server_list_build.dart`). Приоритет отсюда: папочный REPLACE сильнее
личного detour; иначе личный detour члена сильнее папочного append;
член-цель папочного override (и всё, что достижимо из него по интра-рёбрам)
— exempt, папочный override на нём не применяется. Проба тестирует и
выключенных членов, поэтому план считается над папкой «как если бы все члены
были включены»; индекс плана = индекс члена.

Цель у источника: `targetSkipChain` — у источника цели
`useDetourServers=false`, её родная цепочка в туннеле снята, в пробе тоже;
TLS-уровни цели — её источника (§636).

### 2. Сборка probe-конфига

`buildProbeBatches` / `_buildOne` получают необязательный план detour по
индексу узла. Для «учтён»:

- записи цели (`target.getEntries(null)`, с её родной цепочкой) кладутся в
  конфиг рядом с узлом; у каждого тестируемого узла своя копия — теги
  уникализирует существующий `allocate`;
- режим повторяет боевой: append — цель хвостом родной цепочки узла,
  replace — родная цепочка не эмитится (`skipDetour: true`);
- уступки detour (`yieldToBuildDetour`) и гард реестра применяются как для
  родной цепочки; лимиты naive / WireGuard считают и записи цели.

Ссылки внутри родной цепочки цели после уникализации тегов переводятся на
новые теги (копия цели на каждый узел даёт `-2`, и сырой `detour` звена
указал бы на чужую копию).

### 3. Пометка на экране

Под панелью теста на экранах подписки и папки, тем же стилем, что сводка
(`lib/widgets/probe_detour_note.dart`):

| Исходы узлов с detour | Текст |
|---|---|
| все «не учтён» | `Detour of this source is not applied in the test — nodes are checked directly.` |
| все «учтён», одна цель | `Tested through %s.` (префикс источника цели + сырой тег) |
| все «учтён», целей несколько (личные detour членов папки) | `Tested through each node's own detour.` |
| смешанно (папка) | `Detour is applied in the test for %d of %d; the others are checked directly.` — учтённые из всех узлов с detour |

Пометка видна всегда, когда у источника (или хотя бы у одного члена папки)
задан detour, а не только после прогона.

### 4. Диагностика узла и Debug API

- Диагностика узла без VPN (`node_diagnostics_runner.dart`,
  `node_diagnostics_tab.dart`): тот же план для одного узла (индекс 0),
  пометка — под заголовком Response у результата probe-ветки. Маршрут дают
  экран настроек узла (член папки / одиночный сервер, по сохранённому
  состоянию источника) и разбор узла подписки. Экран просмотра outbound'а
  собранного конфига и разбор узла из листа отказа ядра источника не знают —
  там узел проверяется напрямую, без пометки.
- Debug API `POST /folders/{id}/probe` (`handlers/folders.dart`): план тот
  же, что у кнопки; у члена с detour в результате поле `detour`:
  `applied` (+ `detour_via` — тег цели) или `unapplied`.

### 5. Экран Settings → Detour server (найдено на эмуляторе 15.11.2026)

У подписки без родных цепочек (ветка §111) строка «Detour server» рисовала
путь «Phone → цель → Nodes» по одному `overrideDetour`. При хвосте режима
None (`use_detour_servers=false` + override, APPEND) сборка ссылку снимает —
узлы шли напрямую, а экран обещал цель; проба вслед за сборкой давала «нет
detour», пометки не было (Liberty VPN владельца, цель WARP MASQUE). Теперь
строка показывает «None — nodes connect directly», если ссылка не применится
(`overrideDetour` пуст или ни `useDetourServers`, ни `replaceDetourChain`);
выбор цели в пикере ставит `useDetourServers=true`, пометка под тестом
появляется сразу (62ea1c1e). Заодно сводка теста больше не наезжает на общий
переключатель — зазор 16, как у строки узла (afa44faf).

### Что не входит

- Обновление подписки через её detour и предупреждение о прямом DNS —
  отдельные задачи.
- `useDetourServers=false` без override: туннель снимает родную цепочку
  узла, проба — по-прежнему нет (поведение до §730, вне объёма).

## Принятые решения (владелец, 15.11.2026)

1. Цель со своим override (прокси за прокси) — «не учтён», один уровень,
   без рекурсии.
2. Папки учитываются так же, как подписки, в этой задаче, включая личные
   detour членов (`FolderMember.detour`) с боевым приоритетом
   (`FolderDetourPlan.policyFor`).
3. Диагностика узла без VPN — в этой задаче.
4. Тексты пометок приняты (по умолчанию, **подтвердить у владельца** —
   две формулировки для папки ниже): «Detour of this source is not applied in the test
   — nodes are checked directly.» и «Tested through %s.». Две
   дополнительные формулировки для папки (несколько целей, смешанные
   исходы) — моё решение по поручению, см. таблицу §3.
5. Риск «цель WireGuard / naive множит дорогие записи и дробит батчи»
   владелец понимает и принимает: копия цели на каждый узел, лимиты
   naive / WG считают и её записи.

## Risks and edge cases

- Цель — WireGuard / naive: копия цели на каждый узел умножает дорогие
  записи, прогон разобьётся на батчи по одному-двум узлам и станет долгим
  (принято владельцем).
- Цель выключена в своём источнике: боевая сборка уронит узлы (fail-closed);
  в пробе — «не учтён».
- Ядро отвергает саму цель: страховка §723 вынимает по одному узлу, чей
  конфиг несёт копию цели (`ownerByTag`), до предела
  `kProbeMaxCoreRejects`, затем прогон завершается ошибкой старта.
- Одноимённые одиночные серверы: неоднозначность → «не учтён».
- Результат теста теперь зависит от живости цели: мёртвый прокси = все узлы
  красные. Пометка «Tested through …» это объясняет.
