# §287 — Долгая остановка VPN при активном mass-ping'е (WG-teardown блокирует stop)

**Тип:** bug + UX · **Статус:** in progress (develop)

## Проблема

Пользователь: «нажимаю СТОП — он очень долго не прерывается, что-то на большом
количестве пингуемых нод». Наблюдение уточнено: «если конфиг меньше WG — всё
работает норм». То есть остановка виснет на конфигах с **большим числом
WireGuard-эндпоинтов** (у пользователя ~30 WARP AWG/MASQUE-нод, все на WG) —
но только когда перед стопом шёл mass-ping.

## Диагностика (device-verified, Debug API + logcat)

Замеры времени `stop → фактический disconnected` (порог поллинга 50 мс):

| Сценарий | Время |
|---|---|
| stop без пинга (сразу после connect) | **0.16 с** |
| stop в разгар mass-ping (`?all=true`) | **10.22 с** |
| stop с `cancelPing` непосредственно перед ним | **10.16 с** (не помог) |

logcat медленного цикла: между `doStop ENTER` и `doStop cleanup done` проходит
10–17 с. Вся задержка — в нативном `BoxService.closeCommandServerAtomic()` →
libbox **`cs.closeService()`**, который синхронно ждёт teardown всех
WG-эндпоинтов.

### Корень

`urlTestOutbound` в mass-ping открывает **реальные исходящие соединения** через
каждую WG-ноду к ping-URL. `closeService()` при остановке закрывает sing-box
instance и ждёт закрытия этих соединений/эндпоинтов по внутренним таймаутам
WireGuard. Чем больше WG-нод — тем дольше (ровно «меньше WG → норм»).

Два усугубляющих фактора:

- **`_cc.cancelPing()` не спасает** — disconnect pingClient рвёт RPC на стороне
  клиента, но уже открытые в ядре соединения продолжают висеть и держат
  `closeService`.
- **`doStop` не оборачивает Go-teardown таймаутом** (в отличие от `doForceStop`,
  где каждый вызов под `withTimeout(2_000)`) — ждёт ядро неограниченно.

### Почему при этом всё же останавливается (а не виснет навсегда)

Safety-timer `_armTransientTimeout` (§140): при статусе `Stopping` Dart взводит
таймер `_stoppingTimeout`; по истечении — `forceStopVPN()` → `doForceStop()`
(гасит UI сразу, teardown под `withTimeout(2с)` на `forceStopScope`). **Порог
был 10 с** — эти 10 с пользователь и видел как «долго крутится СТОП».

## Решение

Снизить `_stoppingTimeout` **10 с → 3 с**. Раньше отдаём управление уже
существующему и уже принятому в проекте force-stop-пути. Пользователь не ждёт
зависший WG-teardown; при зависании `doForceStop` вытаскивает за ~3 с.

Минимальная правка — одна константа (+ согласование двух комментариев). Не
трогаем `doStop`, `doForceStop`, ядро.

### Почему это безопасно (нет зомби-горутин)

`withTimeout` в `doForceStop` оборачивает **ожидание** Kotlin-стороны, а не сам
`box.Close()`. Go-горутина `box.Close()` уже запущена через JNI и **не
отменяется** Kotlin'ом — Kotlin лишь перестаёт ждать её возврата. Поэтому:

- `box.Close()` → endpoint manager → последовательный `endpoint.Close()` по
  каждому из ~30 → каждый `ClientBind.Close()` → воркеры завершаются штатно.
- Доигрывает в фоне ~10–15 с, **не блокируя UI** (`stopSelf()` уже прошёл).
- Воркеры гаснут по порядку — **не зомбируют**; gVisor netstack освобождается
  корректно.

Остаточный путь — `stopSelf()` убивает процесс до конца `box.Close()`. Но
`BoxVpnService` живёт в основном процессе (нет `android:process`), и `stopSelf`
процесс **не** убивает, пока жив UI (Activity на переднем плане при нажатии
Stop) — так что `box.Close()` спокойно доигрывает. Если же процесс всё-таки
умрёт — OS принудительно освобождает fd/сокеты/память, use-after-free
невозможен (процесса нет). Bind-коллизии на рестарте нет: WG биндит эфемерные
UDP-сокеты (в отличие от фиксированного Clash-порта 63130, §140).

## Вне скоупа — корень в ядре

Настоящий корень: `closeService()` не должен ждать in-flight dial'ы, порождённые
пингом, при закрытии WG-эндпоинтов. Это физика teardown в `sing-box-lx`
(WG-endpoint при close ждёт зависший dial). App-side порог 3 с — паллиатив,
снимающий боль пользователя; корневой фикс — отдельной задачей в ядре.

## Приёмка

- Stop с активным mass-ping'ом на конфиге с многими WG → UI освобождается за
  ~3 с (было ~10 с).
- Stop без пинга не регрессирует (~0.16 с, до порога 3 с далеко — легитимный
  teardown под форс не попадает).
- `flutter analyze` зелёный; тестов на старое значение `_stoppingTimeout` нет.
