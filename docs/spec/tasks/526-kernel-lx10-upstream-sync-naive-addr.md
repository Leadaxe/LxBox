# 526 — Ядро v1.14.1-lx.10 (SPEC 095: синк upstream + SPEC 099: Диагностика naive не роняет процесс)

| Поле | Значение |
|------|----------|
| Статус | **Released в v2.25.3** (24.09.2026). Реализовано (бамп пина). Проверено: версия ядра в APK и на устройстве, javap-дельта, `option/`, туннель на доменном AWG3.1-пире без паник. **Не снято:** Диагностика узла ×3 через UI и замер секунд рукопожатия — стенд (см. «Что проверить осталось») |

| Связанные | §522 (предыдущий бамп, lx.9), §468/§462/§461/§457 (та же процедура), `docs/KERNEL.md` («Gotchas when bumping the version»), память `kernel-bump-emulator-verify` |

## Зачем

Два независимых повода, оба закрываются одним пином.

**Диагностика убивала приложение.** При живом туннеле Диагностика узла `naive`
завершала процесс мгновенно, независимо от лимита памяти: пробник диагностики
читал адрес соединения внутри туннеля, а у соединения Cronet адреса нет.
Разыменование этого nil роняло ядро целиком. Трафик через такой узел и `urltest`
при этом работали — то есть узел был исправен, а диагностика его же и убивала.

**Доменные WG/AWG-пиры стоили пяти секунд.** Первое рукопожатие с пиром,
заданным доменным именем, теряло первую попытку: в логе
`handshake did not complete after 5 seconds, retrying`, переключение на такой
узел — 5,4–5,7 с. Фикс апстримный, но требует пересадки форка wireguard-go на
v0.0.7, поэтому приходит только вместе с синком.

## Решение

- `app/android/libbox.version`: `v1.14.1-lx.9` → `v1.14.1-lx.10`;
  AAR приносит `scripts/fetch-libbox.sh` с проверкой SHA256 против релизного
  `SHA256SUMS` (маркер `.libbox.version` в `libs/`, сам AAR в git не идёт).
- Контракт (§460, готча 2 в `KERNEL.md`) **не трогаем**:
  `git -C sing-box-lx diff v1.14.1-lx.9 v1.14.1-lx.10 -- option/` — **пусто**
  (0 файлов при 70 изменённых файлах в диффе целиком), новых полей конфига нет,
  реестр протоколов и `min_core` в силе. Готча 6 (`vless.encryption`) ни при чём:
  `lx_encryption.go` в диффе релиза не участвует.
- Кода приложения задача не трогает: ни новых строк UI, ни l10n. Новый метод
  `Libbox.hasTunInbound(String)` приложение не вызывает — он аддитивный и пришёл
  из апстрима.

$ unzip -p app-arm64-v8a-release.apk lib/arm64-v8a/libbox.so | strings -a \

подтверждает `GET /device` → `core_version: 1.14.1-lx.10` (готча 4 про

### Что проверить осталось (стенд, не код)

**Диагностика узла ×3 через UI** (шаг, ради которого задача трогает SPEC 099) в
этом прогоне **не снята**, и **замер секунд рукопожатия — тоже**. Причины обе
стендовые, к коду отношения не имеют.

- **UI недоступен.** Гость держал на экране системный диалог
  `Process system isn't responding`, затем `System UI isn't responding`, и
  пересоздавал его после каждого закрытия. Тап-путь Диагностики (Home → долгий
  тап → View details → таб Diagnostics → `Run`) снять нельзя: диалог системы
  лежит поверх, а `am start` подтверждает, что LxBox — и есть top-most instance.
  Обойти через Debug API нельзя принципиально: живая ветка диагностики
  (`ccGetUrlViaOutbound` → libbox `getURLViaOutbound`, то самое место из SPEC
  099) вызывается только с экрана узла, а `POST /folders/{id}/probe` при живом
  VPN отвечает `conflict: VPN is running — stop it before probing`, то есть
  идёт probe-сессией, а не той ветки, которая падала.
- **Секунды рукопожатия недостоверны.** У AWG-пиров на этом эмуляторе в логе
  стоит `ERROR ... failed to send handshake initiation: disabled UDP GSO`, и
  именно из-за него первый init теряется (runbook описывает это как известный
  артефакт эмулятора: «фейл одного handshake-init, ретраи идут, на исход не
  влияет»). Пока артефакт на месте, отделить выигрыш SPEC 095 от него нельзя —
  цифра была бы вымышленной. Ретраи, которые видны в логе, привязаны к **чужим**
  простаивающим пирам (`WireGuard`, `SWITZ-just-awg2`, WARP) и к keepalive
  («stopped hearing back after 15/22 seconds»), а не к начальному рукопожатию
  того узла, на который переключились.
- **Почему стенд в таком состоянии.** Хост во время задачи был перегружен (load
  average до 87 при сборке APK, своп — меньше 1 ГБ свободного из 30 ГБ; после
  сборки на машине параллельно работал чужой Go-линковщик на 92 % CPU). Гость
  трижды терял системный процесс, и в `logcat -b crash` каждый раз падали
  **только системные процессы** Android: `system_server`
  (`java.lang.IllegalStateException: Could not create IpClient` ←
  `DeadObjectException`, то есть умер модуль сетевого стека), затем каскадом
  `com.android.phone`, `com.android.networkstack.process`, `nexuslauncher`,
  `gms`, `googlequicksearchbox` с `DeadSystemException`. Пакет
  `com.leadaxe.lxbox` в этих трейсах **не встречается ни разу**. После каждого
  падения `eth0`/`wlan0` поднимались DOWN и без IPv4 (`ping 10.0.2.2` →
  `Network is unreachable`); руками не лечится, потому что сетью в Android
  владеет `ConnectivityService`, а он не инициализировался. Полный рестарт
  эмулятора сеть восстанавливал (`0% packet loss` до `1.1.1.1`), и именно на
  восстановленном стенде сняты шаги 1–4 выше.

Память проекта описывает это как «сплошной отказ = проверь стенд»: то, что
осталось, надо снимать на разгруженной машине, иначе падение системных
процессов выдаст себя за падение приложения. Что **уже** доказано и от стенда не
зависит: ядро в APK и на устройстве — `1.14.1-lx.10`, javap-дельта аддитивная,
`option/` не менялся, ядро под живым туннелем на доменном AWG3.1-пире не падает
(0 паник, 0 строк в crash-буфере).

Скриншоты прогона — в scratchpad задачи (`bump526/`), в репозиторий не идут.

## Регресс

- `flutter analyze` — `No issues found!`.
- Версия пина в `test/` встречается только в двух местах, и оба — **логика
  сравнения версий, а не утверждение о строке пина**:
  `app/test/contract/body_sanitizer_test.dart:1307` требует, чтобы
  `coreAtLeast('1.14.1-lx.10','1.14.1-lx.9')` был `true` (то есть сравнение
  числовое, а не лексикографическое, где `lx.10 < lx.9`), и
  `app/test/builder/core_chain_capability_test.dart` проверяет тот же
  компаратор на синтетических версиях. Ни один тест не сверяет содержимое
  `app/android/libbox.version`, поэтому бамп их поведение не меняет и правки в
  `test/` не нужны. Ещё два упоминания (`body_sanitizer_test.dart:1001`,
  `task_512_registry_schemes_test.dart:231`) — комментарии про lx.8.
- Полный `flutter test` в этой задаче не гоняется (регламент: прогон — в CI).
  Dart-кода задача не трогает.
