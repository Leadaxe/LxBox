# §355 — Граф detour-зависимостей: ⚠ на мёртвой ноде, от которой зависят другие

**Тип:** таска
**Статус:** реализовано 03.08.2026 (юниты графа 10/10, виджет-тест метки, полный сьют 2743 зелёный; DEVICE-PENDING)
**Связано:** kernel SPEC 046 (мёртвый DNS-detour морозил пакетный цикл — починено в ядре `v1.14.0-lx.20-rc.2`), §354 (ru-DNS через группу — смягчил DNS-кейс тремя путями), §312 (DNS-группы), §254 (detour-циклы: билдер уже обходит граф), §084 (DanglingDetourRef), §096 (`detourRefCount` в списке нод), §125 (каналы), §283 (detail-экран ноды), §308 (rescue urltest-групп)

## 1. Проблема

Инцидент 02.08.2026: DNS-сервер `yandex_udp` с `detour: vpn-2`, в vpn-2 руками
выбрана нода с пингом −1 (silent-drop). До ядрового фикса SPEC 046 это вешало
весь форвардинг; после фикса — «всего лишь» тихо не резолвятся все ru-домены.
Юзер при этом не видит **ничего**: нода с −1 в списке выглядит как любая другая
мёртвая нода, и догадаться, что через неё ходит DNS (или другие ноды по
detour-цепочке), невозможно — связь знает только билдер.

Обобщение: неработающая нода делает неработающим канал, в котором она выбрана;
канал — все ноды и DNS-серверы, для которых он detour; и так по цепочке.
Сейчас эта цепочка нигде не материализована для UI.

## 2. Не-цели

- **Никакой новой активной диагностики.** Не пингуем невыбранные группы и не
  добавляем фоновых проб: работаем только от уже имеющихся событий (замер
  пинга, смена выбора группы). Нода, которую ни разу не мерили, — `unknown`,
  не тревожим.
- **Не мутируем выбор selector'ов.** Ручной выбор канала — священен
  («кнопки не мутируют молча», §261/§262). Только показ проблемы.
- **Не помечаем пострадавших.** ⚠ — только на корне беды; зависимые
  перечисляются в detail корня, но сами в списке не подсвечиваются
  (иначе визуальный шум расползается по списку).
- **Без ядровой стороны.** Ядро могло бы слать структурированные
  connection-failure события через CC, но это новая фича форка (против
  CONSTITUTION тонкого downstream) и не нужна для v1: всё сырьё уже стекается
  в приложение. Возможная отдельная спека в будущем.

## 3. Модель: граф зависимостей

### 3.1 Узлы и рёбра (статика — из билдера)

Типы узлов: **нода** (outbound), **канал** (selector/urltest-группа),
**DNS-сервер**. Рёбра «кто через кого»:

```
нода        --detour-->  нода | канал
dns-server  --detour-->  нода | канал
канал       --member-->  ноды (состав)
```

Билдер уже обходит этот граф при валидации (§254 циклы, §084 висячие ссылки —
[validator.dart](../../../app/lib/services/builder/validator.dart)), но
результат выбрасывает. Новое: на каждой генерации конфига билдер публикует
**индекс обратных зависимостей** (`нода/канал ← [кто ссылается]`) рядом с
parsed config. Инвалидация естественная — пересборка конфига.

### 3.2 Динамика (из уже существующих потоков)

- **выбор канала** — groups-стрим CommandClient (`selected` каждой группы);
- **health нод** — delay-карта `delayByChannel` (HomeState) после любого
  замера: single ping / mass ping / group urltest.

### 3.3 Health ноды — три состояния

| Состояние | Правило |
|---|---|
| `alive` | хоть в одном канале последний замер > 0 |
| `dead` | замеры есть и **все** имеющиеся = −1 |
| `unknown` | замеров нет — не тревожим |

У замеров нет таймстампов (`delayByChannel` хранит голые числа), поэтому
«свежесть» неопределима — правило консервативное намеренно: противоречивые
замеры (−1 в одном канале, 150ms в другом) читаются как «жива», меньше ложных
тревог.

### 3.4 Распространение болезни

BFS вверх по обратным рёбрам от `dead`-ноды:

```
dead(нода) → sick(канал)        если канал.selected == нода И канал — selector
sick(канал) → sick(нода/dns)    у кого detour == канал
sick(нода)  → …                 рекурсивно (каналы, где она выбрана; кто на неё detour'ится)
```

- **Urltest-каналы исключены из «болезни по выбору»** — они самолечатся
  (§308 rescue делает переселект сам); варнинг мигал бы на секунды. Urltest-
  канал болен только если `dead` **все** его члены.
- Циклы в графе исключены билдером (§254), но guard от повторного посещения
  в BFS обязателен (защита от рассинхрона).
- Пересчёт — на двух событиях: обновление delay-карты, смена выбора группы.
  Граф — сотни узлов, BFS мгновенный; дебаунс не по времени, а по состоянию:
  UI обновляется только когда множество «корней беды» изменилось.

## 4. UI

1. **⚠-метка в списке нод** — на ноде, которая `dead` **и** от которой
   транзитивно зависят другие (DNS-серверы или ноды). Просто мёртвая нода без
   зависимых метку не получает — это фильтр от шума.
2. **Sheet «Broken dependencies» по тапу на ⚠-метку** — список DNS-серверов
   и нод, зависящих от корня, с путём зависимости (`yandex_udp — via vpn-2`,
   `node X — direct detour`); DNS-жертвы сверху. *(Отступление от исходного
   наброска «секция в detail-экране ноды»: выделенного detail-экрана у нод
   Home нет — есть контекстное меню и sheet-паттерн §254 detour_cycle_sheet;
   sheet по тапу на метку точнее по контексту и дешевле. `directDependents`
   в модели оставлен для будущей секции «кто через меня» на живой ноде.)*
3. **Баннер на Home — только для DNS-ветки** (решение юзера 03.08.2026):
   когда болен DNS-сервер, юзер не смотрит в список нод — у него «просто не
   работает интернет». Текст в духе:
   `DNS server "yandex_udp" routes through dead node "L: Россия" (selected in vpn-2)`.
   Механизм — существующий lastError-баннер. Для «болен только другой узел»
   баннера нет — достаточно метки.

Все строки — английские (en = ключ перевода), без §-номеров в видимых текстах.

## 6. Критерии приёмки

1. Репро инцидента (конфиг: DNS-сервер detour → selector-канал, в нём выбрана
   нода; нода получает −1 по пингу) → на ноде ⚠, в её detail — DNS-сервер с
   путём, на Home — баннер DNS-ветки.
2. Та же нода при живом замере в любом канале → метки и баннера нет.
3. Нода без замеров (`unknown`) → метки нет.
4. Мёртвая нода, выбранная только в urltest-канале → метки нет (канал
   самолечится §308).
5. Цепочка в две ступени (нода → канал A → нода-detour → канал B → DNS) —
   болезнь доходит до DNS, баннер называет корневую ноду.
6. Смена выбора канала на живую ноду мгновенно снимает метку и баннер.
