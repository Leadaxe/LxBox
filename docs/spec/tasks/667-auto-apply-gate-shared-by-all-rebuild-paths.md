## Проблема

Владелец, 18.10.2026: галка App Settings → General → «Auto-restart VPN on
settings change» срабатывает нестабильно — «меняю route или сервера,
включаю/выключаю, а применяется не всегда».

Инспекция кода (без устройства) нашла четыре расхождения между обещанием
§338 («любое изменение конфига применяется само, плашек не остаётся») и
тем, как изменение доезжает до reload.

## Диагностика

Применение живёт в одной воронке `_rebuildAndClearDirty`
(`lib/screens/home_screen.dart`): пересборка → `saveParsedConfig` → хук
`_maybeAutoReload`. Воронку заводят только четыре события: возврат на home
(`homeReturnObserver`), догон после `busy`, реакция автообновления подписки,
гейт на Start и bootstrap. Хук делает reload при одновременном выполнении
условий:

1. галка включена;
2. туннель в состоянии `connected`;
3. `configChangedNeedRestart` после сохранения (§324: saved разошёлся с
   running);
4. `canReload` — туннель `connected` и прошло ≥ 3 с с прошлого reload.

Пути Routing/DNS/per-app (LazyPersistMixin, dirty синхронно), тумблер узла
внутри подписки, выключение подписки, автообновление и bootstrap через
воронку проходят. Дефекты — ниже.

### Д1. Включение подписки: dirty поднимается после разбора кэша

`SubscriptionController.toggleAt` (`subscription_controller.dart:2512`) при
включении делает `await ensureHydrated(entry)` (§652: чтение тела из
HttpCache + разбор в изоляте, на больших подписках — заметные доли секунды)
и только потом `_persist()`, который ставит `configDirty = true`. Гидрация
`busy` не поднимает. Нажатие Back до конца гидрации → `_onReturnToHome`
видит `configDirty == false` и `busy == false` → пересборки нет; флаг
поднимается уже на home → синяя плашка «Settings changed», reload не
происходит. Выключение такого окна не имеет (`_persist` первым оператором),
отсюда «иногда».

Тот же рисунок в `settings_screen.dart:212-276`: четыре тумблера ставят dirty
после `await SettingsStorage.save…`. Окно короче (запись файла), но
структурно то же.

### Д2. Правка Направления с home идёт мимо хука

Долгий тап по узлу → «Apply to …» → редактор Направления
(`node_list.dart:787-820`). Редактор — pushed route; `await openDirectionEditor`
возвращает управление ПОСЛЕ pop, то есть `_onReturnToHome` уже отработал с
чистым флагом. Затем путь сам делает `generateConfig` + `saveParsedConfig`,
`_maybeAutoReload` не зовётся. Комментарий на строках 812-813 («пересборка на
возврате на home применит правку сама») ложен. Итог при включённой галке:
розовая плашка «Config changed — restart VPN», снек «Restart VPN to apply»
подавлен, reload не идёт.

### Д3. Правка цепочек и добавление источников делают reload всегда

`regenerateSourcesConfig` (`chain_edit/chain_edit_flow.dart:76-88`) после
сохранения зовёт `reloadVpn()`, если `canReload`, — без галки и без вердикта
§324. Вызывается из `subscriptions_screen._regenerateAndSave` (после ЛЮБОГО
добавления сервера/подписки/цепочки на Servers) и из
`owner_navigation._editChainFromOwnerLink`. Директива 24.08 (§558) требовала,
чтобы правка цепочки «доезжала до сборки»; reload сверх того галку
игнорирует. Решение владельца 19.10.2026: это дефект — применение к живому
туннелю решает галка, а не путь, которым пришло изменение. Побочно этот
безусловный reload занимает 3-секундный cooldown и роняет следующее
применение (Д4).

### Д4. Пропуск по cooldown без повтора

`_maybeAutoReload` (`home_screen.dart:1150`) при `!canReload` пишет warning
и выходит; повтора никто не планирует. Вторая правка в пределах 3 с после
прошлого reload (или после reload Д3) остаётся розовой плашкой. Снек
`_rebuildConfig` (`home_screen.dart:1304`) при этом обещает «reloading VPN»:
`willAutoReload` не смотрит на `canReload`.

### Д5. Идентичная повторная запись гасит флаг «устарел»

`saveParsedConfig` (`home_controller/config_io.dart:95`) считает
`needRestart` от текстового диффа с ПРЕДЫДУЩЕЙ записью; §323 при
`changed == false` флаг гасит. Если первая запись взвела флаг, а reload по
ней сорвался (cooldown, Д4), вторая запись того же конфига снимает флаг,
хотя ядро на старом конфиге. Повтор после cooldown (Р1) тогда ничего не
найдёт. Так бьёт Servers → «Update all»: реакция автообновления внутри
прохода ожидается и пересобирает сама; экран после неё собирает ещё раз
(`_updateAll`, `subscriptions_screen.dart:864-866`) — идентичная запись.

### Д6. Присоединение к летящей пересборке теряет правку

`_rebuildAndClearDirty` при `_rebuildInFlight != null` присоединяется к
чужой пересборке. `generateConfig` снимает `configDirty`, если не
изменился состав источников (§360, `_compositionSignature`); правка vars
или Routing, сделанная за время полёта, в сверку не входит — флаг гаснет,
конфиг её не содержит. Окно — длительность пересборки при быстрой
навигации.

### Вне объёма

- Servers → «Update all» при неизменившемся составе: реакции нет, повторная
  сборка экрана даёт тот же конфиг — дефекта нет (после Р4 сборки там не
  остаётся вовсе).

## Решение

Принцип: **решение «применять ли к живому туннелю» принимает один гейт**, а
пути пересборки лишь сообщают ему, что конфиг сохранён.

### Р1. Гейт переезжает в `HomeController`

Новый метод `Future<bool> applyIfAutoReload()` в `HomeController`
(рядом с `reloadVpn`, `canReload`). Возвращает `true`, если reload запущен.
Условия, все одновременно, иначе `false`:

1. `SettingsStorage.getAutoReloadOnChange()` — галка включена;
2. `state.tunnelUp`;
3. `state.configChangedNeedRestart`;
4. `canReload`.

При срыве только по п. 4 из-за cooldown (туннель `connected`, прошло < 3 с)
гейт планирует **один** отложенный повтор на момент истечения cooldown;
повтор заново проверяет пп. 1–4 (конфиг могли применить руками, туннель —
опустить) и не ставит второго таймера, если один уже ждёт. Срыв по
не-`connected` повтора не планирует: конфиг подхватит Start.

На окно применения контроллер держит `state.autoApplying == true` (новое
поле `HomeState`): от решения «запускаем» до завершения `reloadVpn`.
`activeBanners` читает его из state; локальное `_autoApplying` в
`home_screen.dart` и параметр `autoApplying` у `HomeControls`/`app_banner`
снимаются. Так подавление розовой плашки на время reload работает на любом
пути, не только на воронке home.

`_maybeAutoReload` в `home_screen.dart` сводится к вызову гейта; чтение
галки для текста снека остаётся там, где было, но `willAutoReload`
дополняется `_controller.canReload` (Д4, текст).

### Р2. Пути, минующие воронку, зовут гейт

- `regenerateSourcesConfig` (Д3): вместо `if (canReload) reloadVpn()` —
  `applied = await homeController.applyIfAutoReload()`. Возвращаемое
  значение по-прежнему управляет текстом снека в `_regenerateAndSave`
  («regenerated & applied» только когда reload запущен). При выключенной
  галке и живом туннеле остаётся розовая плашка — как у всех прочих правок.
- Путь Направления с home (Д2): после `saveParsedConfig` —
  `await controller.applyIfAutoReload()`; снек «Restart VPN to apply
  changes» показывать, когда гейт вернул `false` и туннель поднят. Ложный
  комментарий удалить.

### Р3. Dirty до первого await (Д1)

- `toggleAt`: `configDirty = true` первым оператором при включении
  подписки, до `ensureHydrated`. Ранний `return` после гидрации
  (контроллер `stale` или запись удалена) флаг не откатывает: лишняя
  пересборка дешевле потерянного изменения.
- `settings_screen.dart`: в четырёх тумблерах переставить
  `configDirty = true` перед `await SettingsStorage.save…`.

### Р4. Вердикт §324 решает в обе стороны (Д5)

В `saveParsedConfig`: при `tunnelUp` и непустом `runningConfigRaw` —
`needRestart = (вердикт == stale)`, независимо от текстового диффа с
прошлой записью. Текстовый дифф со sticky-правилом §323 остаётся только для
случаев без снимка (туннель down, `unknown`). Цена — один `formatConfig` на
запись при живом туннеле (сейчас он платится только при `changed == true`).
Из `_updateAll` собственную пересборку убрать: реакция прохода уже собрала
и применила; экрану остаётся снек со счётчиком узлов по `entries`.

### Р5. Поколение dirty вместо сверки состава (Д6)

`SettingsStorage`: сеттер `configDirty = true` инкрементирует счётчик
поколений. `generateConfig` запоминает поколение на входе и снимает флаг
только при равенстве на выходе; `_compositionSignature` в этой роли
снимается (§360 покрывается по построению). В `_rebuildAndClearDirty`:
если вызов присоединился к чужой пересборке, после её завершения при
`configDirty == true` запустить свою — один раз, без цикла.

### Что НЕ меняется

- Single-flight §107 как механизм, cooldown 3 с и его величина, тексты
  снеков.
- Поведение при выключенной галке везде, кроме Д3: там исчезает
  безусловный reload после правки цепочки/добавления источника (появляется
  обычная розовая плашка при живом туннеле).
- UI: ни одного нового элемента; тексты снеков прежние, меняются только
  условия их показа.

## Проверка

Тесты — по одному файлу на затронутую область, без прогона каталогов:

- `test/subscription/toggle_during_rebuild_test.dart` (или новый
  `toggle_at_marks_dirty_before_hydration_test.dart`): после вызова
  `toggleAt` на выключенной подписке с непустым кэшем `configDirty == true`
  синхронно, до завершения future.
- `test/subscription/auto_reload_on_change_test.dart`: решение гейта —
  четыре условия порознь; cooldown активен → reload не сразу, а после
  истечения cooldown ровно один раз; второй вызов во время ожидания второго
  таймера не ставит.
- Новый тест `regenerateSourcesConfig`: галка выключена, туннель
  `connected`, конфиг изменился → `reloadVpn` не вызван; галка включена →
  вызван.
- `test/vpn/config_staleness_test.dart` (или соседний по `saveParsedConfig`):
  два сохранения одного конфига при живом туннеле и снимке running, отличном
  от него → флаг взведён после обоих.
- `test/subscription/toggle_during_rebuild_test.dart`: `configDirty = true`
  во время `generateConfig` (любой источник, не только состав) → флаг после
  генерации остаётся `true`.

На устройстве (владелец): галка включена, туннель поднят —

1. Servers → включить выключенную подписку с большим кэшем → сразу Back:
   туннель перезапускается, плашек нет.
2. Home → долгий тап по узлу → Apply to … → Save: reload идёт, плашки нет.
3. Правка цепочки при выключенной галке: reload нет, розовая плашка есть;
   при включённой — reload, плашки нет.
4. Две правки подряд с интервалом < 3 с: вторая применяется после cooldown,
   плашка не остаётся.
