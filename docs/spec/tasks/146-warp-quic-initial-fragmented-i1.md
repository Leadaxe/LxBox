## 0. TL;DR для агента ядра

Текущая реализация 009 для `ip=quic` генерирует `i1` как **один линейный CRYPTO-фрейм** (`CRYPTO off=0` со всем ClientHello + хвост) либо как 1-RTT short header. **Этот вариант режется реальным DPI.**

Нужно: для `ip=quic` генерировать `i1` как **полноценный QUIC Initial (RFC 9001), в котором ClientHello разбит на несколько CRYPTO-фреймов, выложенных в payload в ПЕРЕМЕШАННОМ (out-of-order) порядке, с вставками PING- и PADDING-фреймов между ними**. Первый CRYPTO-фрейм в wire-порядке должен иметь **offset ≠ 0** (не начало ClientHello).

Это **device-proven**: пакет такой структуры (свой ClientHello, свой SNI, свежая крипта) пробивает DPI стабильно. Линейный — нет. Единственная отличающаяся переменная между PASS и FAIL — порядок/фрагментация CRYPTO-фреймов.

---

## 1. Почему это работает (механизм)

DPI и настоящий QUIC-сервер парсят Initial-пакет **по-разному**:

- **Настоящий QUIC-сервер** (RFC 9000/9001): AEAD-расшифровывает (Initial-ключи выводятся публично из DCID — секрет не нужен), **перебирает ВСЕ фреймы**, каждый CRYPTO-фрейм кладёт в reassembly-буфер по его `offset` независимо от порядка прихода, и только когда байты `[0..N)` собраны непрерывно — отдаёт TLS-парсеру.

- **Line-rate DPI**: ради пропускной способности **не держит reassembly-буфер**. Типичная дешёвая реализация: расшифровать → взять **первый** CRYPTO-фрейм → считать, что он с `offset 0` и содержит начало ClientHello → распарсить TLS / сосканировать SNI.

Когда первый wire-фрейм имеет `offset = 236` (середина ClientHello), DPI:
1. не видит начала ClientHello там, где ожидает,
2. не умеет переупорядочить фреймы по offset,
3. парсит мусор → длины TLS-записи не сходятся → парс прерывается,
4. **fail-open** (пропускает) — потому что настоящий Chrome тоже легитимно фрагментирует большие ClientHello, и fail-closed ломал бы обычный QUIC-трафик.

Настоящий WARP-сервер фреймы переупорядочит и handshake состоится; DPI — нет.

> **NB.** `i1` — это **decoy** (standalone-приманка, src=nil, шлётся ПЕРЕД WG-handshake; см. 009 `send.go:135`). Его задача — чтобы **первый пакет потока** выглядел как легитимный старт QUIC-сессии к популярному домену, и DPI классифицировал поток как «QUIC к CDN», не применяя WG-фингерпринт к последующим пакетам. `i1` не обязан завершать никакой реальный TLS-handshake.

## 2. Device-доказательство (почему именно out-of-order)

Тест: A/B на реальном LTE с активным DPI. Все варианты — идентичный outer QUIC-заголовок (1250б, length-поле `0x44d0`=1232), **тот же WG-peer/ключи/endpoint**, тот же SNI; отличается **только** структура CRYPTO-фреймов внутри расшифрованного payload. Метрика — Clash delay-тест узла (PASS = есть delay, FAIL = Timeout), ≥3 раунда, рядом — контрольный заведомо-рабочий узел.

| Вариант i1 | Структура payload | Результат |
|---|---|---|
| Линейный | 1× `CRYPTO off=0` (весь ClientHello) + zero-PADDING | ❌ Timeout (×N) |
| Приблизит. фрагментация маленького CH | случайная нарезка ~60б CH | ❌ Timeout |
| Out-of-order (реалистичный 294б CH + frame-план из §3) | как §3 | ✅ PASS, 257–861 мс |
| Контроль (заведомо рабочий) | out-of-order | ✅ PASS |

Out-of-order вариант проверен с **тремя разными SNI** (`apteka.ru`, `gosuslugi.ru`, `www.google.com`) — все проходят стабильно. Значит алгоритм **не привязан к конкретному домену/снимку** и пригоден для генерации с нуля.

**Вывод:** причина блокировки — строго линейность (один фрейм с offset 0). Фрагментация с перемешиванием лечит. SNI в рабочем пакете лежит **целиком** (НЕ расщеплён через границу фрейма) — значит дело именно в **порядке фреймов**, а не в разрыве строки SNI.

## 3. Целевой алгоритм генерации i1 (детально, воспроизводимо)

Эталонная структура — реверс рабочего пакета + device-проверенная реконструкция «с нуля». Реализатор ядра воспроизводит ЭТО для `ip=quic`.

### 3.1. ClientHello (≈294 байта, реалистичный, НЕ голый SNI)

Текущий 009 строит «голый SNI-only» ClientHello (~67б, empty cipher_suites). **Этого недостаточно** — нужен правдоподобный браузерный ClientHello. Структура (TLS 1.3):

```
handshake_type = 0x01 (ClientHello)
length         = u24
legacy_version = 0x0303
random         = 32 random bytes        (КАЖДЫЙ вызов свежие — uniqueness)
session_id     = empty (len 0)          (или 32 random — но в эталоне 0)
cipher_suites  = НЕ ПУСТО (≥1, напр. 0x1301 TLS_AES_128_GCM_SHA256); эталон len=6
compression    = null (0x00, len 1)
extensions (эталонный набор и длины, total ≈243б):
   0x000a supported_groups        (len 8;  x25519 0x001d)
   0x000d signature_algorithms    (len 20)
   0x0000 server_name (SNI)       (len 14 для 14-симв. домена; host_name)
   0x0033 key_share               (len 38; x25519, 32-байт pubkey)
   0x0039 quic_transport_params   (len 105)   ← делает CH «как QUIC-клиент»
   0x4469 GREASE                  (len 5)
   0x002d psk_key_exchange_modes  (len 2)
   0x0010 ALPN                    (len 5;  "h3")
   0x001b compress_certificate    (len 3)
   0x002b supported_versions      (len 3;  0x0304 TLS1.3)
```

- Точный набор/порядок extensions не критичен побайтово, **критично**: (а) cipher_suites непустой, (б) присутствуют key_share + supported_versions + ALPN + quic_transport_params (чтобы CH был «как настоящий QUIC-клиент»), (в) **итоговая длина ClientHello ≈290–294б** — этого достаточно, чтобы при нарезке по offsets из §3.2 получились те же 6 фрагментов. Добивать до целевой длины можно `padding`-extension (`0x0015`, нули).
- SNI (`id`) подставляется в server_name. **Domain — массовый легитимный** (РФ-инфраструктура `apteka.ru/gosuslugi.ru/...` или `www.google.com`); НИКОГДА `cloudflare-*`/vpn-маркеры (DPI читает SNI после публичной расшифровки Initial — см. §1; маркер = блок).

### 3.2. Frame-план (wire-order) — ТОЧНАЯ раскладка эталона

ClientHello (294б) режется на **6 CRYPTO-фрагментов** по offset-границам `[0, 236, 266, 275, 283, 290]` (длины фрагментов: 236, 30, 9, 8, 7, 4). Фрагменты выкладываются в payload Initial-пакета в следующем **wire-порядке** (именно в этом порядке байты идут в пакете — это то, что DPI читает первым):

```
 # | frame    | offset | len  | назначение
---+----------+--------+------+----------------------------------
 1 | CRYPTO   |   236  |  30  | ← ПЕРВЫЙ фрейм: offset ≠ 0 (out-of-order!)
 2 | PADDING  |    —   | 176  | 0x00 run
 3 | PING     |    —   |   1  | 0x01
 4 | PADDING  |    —   | 647  | 0x00 run
 5 | CRYPTO   |   266  |   9  |
 6 | PING     |    —   |   1  | 0x01
 7 | CRYPTO   |   283  |   7  |
 8 | CRYPTO   |   290  |   4  | хвост ClientHello (290..294)
 9 | PADDING  |    —   |  72  | 0x00 run
10 | CRYPTO   |     0  | 236  | ← начало ClientHello — ПОЧТИ В КОНЦЕ пакета
11 | CRYPTO   |   275  |   8  |
```

**Инварианты, которые ОБЯЗАНЫ выполняться** (это и есть DPI-bypass):
- **I1.** Первый CRYPTO-фрейм в wire-порядке имеет `offset ≠ 0` (в эталоне 236).
- **I2.** Фрейм с `offset = 0` (начало ClientHello) выложен НЕ первым (в эталоне — 10-й из 11).
- **I3.** Между CRYPTO-фреймами есть PADDING-runs и ≥1 PING-фрейм.
- **I4.** Объединение всех CRYPTO-фреймов по offset даёт непрерывный валидный ClientHello `[0..294)` без дыр и без перекрытий.

Допустима **рандомизация раскладки** (другие точки разреза, другой перемешанный порядок, другие размеры PADDING), ПОКА выполняются I1–I4 и суммарный payload укладывается в length-поле. Это снижает общую сигнатуру между юзерами. Минимально — можно зашить эталонную раскладку выше; лучше — генерировать раскладку с инвариантами I1–I4.

### 3.3. Сборка QUIC Initial (RFC 9001) — крипта

Outer-пакет — стандартный QUIC v1 Initial. Параметры эталона:

```
first byte    = 0xC0 | (pn_len - 1)          (long header, Initial, pn_len=1 → 0xC0)
version       = 0x00000001                    (QUIC v1)
DCID          = 8 random bytes                (КАЖДЫЙ вызов свежие)
SCID          = empty (len 0)
token         = empty (len 0)
length        = varint(pn_len + len(payload) + 16)   ; эталон length-поле = 1232 (0x44d0)
packet_number = 0  (1 байт)
payload       = [frame-план §3.2], добитый PADDING (0x00) до (length - pn_len - 16) = 1215 байт
                → итоговый пакет 1250 байт
```

Крипта (RFC 9001 §5, Initial secrets — **стандарт, как в текущем 009**):

```
INITIAL_SALT  = 38762cf7f55934b34d179ae6a4c80cadccbb7f0a      (QUIC v1)
initial_secret = HKDF-Extract(INITIAL_SALT, DCID)
client_secret  = HKDF-Expand-Label(initial_secret, "client in", "", 32)
key = HKDF-Expand-Label(client_secret, "quic key", "", 16)     ; AES-128
iv  = HKDF-Expand-Label(client_secret, "quic iv",  "", 12)
hp  = HKDF-Expand-Label(client_secret, "quic hp",  "", 16)
HKDF-Expand-Label info = u16(len) ‖ u8len("tls13 "+label) ‖ ("tls13 "+label) ‖ u8len(context=0) ‖ 0x00
nonce = iv XOR (packet_number right-aligned в 12 байт)
ciphertext = AES-128-GCM(key, nonce, plaintext=payload, aad=header)   ; 16-байт tag
header protection:
   sample = ciphertext[4-pn_len : 4-pn_len+16]   (для pn_len=1 → ct[3:19])
   mask   = AES-ECB(hp, sample)
   first_byte ^= mask[0] & 0x0f
   pn_bytes[i] ^= mask[1+i]
packet = header ‖ ciphertext
```

### 3.4. CRYPTO / PING / PADDING — кодирование фреймов

```
CRYPTO  = 0x06 ‖ varint(offset) ‖ varint(length) ‖ data
PING    = 0x01
PADDING = 0x00  (run из N нулей)
varint (RFC 9000): <64 → 1 байт; <16384 → 2 байта (0x4000|n); иначе 4 байта (0x80000000|n)
```

### 3.5. Выход

`i1` эмитится как существующий CPS-формат `<b 0x...>` (сплошной `<b>`, весь зашифрованный пакет одним blob — как сейчас 009 кладёт линейный i1). Никаких `<r>`-сегментов не требуется (уникальность даёт свежий DCID+random на вызов). Транспорт CPS не меняется.

## 4. Что меняется относительно текущего 009

| | Текущий 009 (`ip=quic`) | Цель (§146) |
|---|---|---|
| ClientHello | голый SNI-only (~67б, empty cipher_suites) | реалистичный ~294б (cipher_suites + key_share + ALPN + quic_transport_params + supported_versions) |
| CRYPTO-фреймы | 1 (или ≤2 in-order) | 6 фрагментов |
| Порядок | in-order (первый = offset 0) | **out-of-order** (первый = offset≠0, offset 0 почти в конце) |
| PING/PADDING | нет | PING + PADDING interleave между CRYPTO |
| Результат на DPI | блокируется | проходит (device-proven) |

`dns`/`stun`/`sip` ветки 009 — **вне скоупа** этой таски (отдельный вопрос; на тестовом DPI они тоже не проходили, но причина может отличаться). Скоуп §146 — **только `ip=quic`**.

Поля `id/ip/ib` (§143) и их валидация — **без изменений**. Меняется только то, во что ядро разворачивает `ip=quic` → теперь фрагментированный Initial вместо линейного.

## 5. Контрольные векторы (для верификации реализации)

Реализатор должен уметь подтвердить структуру **обратным разбором** собственного вывода:

1. **Расшифровка.** Сгенерированный `<b 0x...>` blob (взять DCID из заголовка, вывести Initial-ключи по §3.3) AEAD-расшифровывается без ошибки тега. Если тег не сходится — крипта битая.
2. **Frame-walk.** В расшифрованном payload: ≥6 CRYPTO-фреймов, ≥1 PING (0x01), PADDING-runs. Первый CRYPTO в wire-порядке имеет `offset ≠ 0` (инвариант I1).
3. **Reassembly.** Объединение CRYPTO-фреймов по offset → непрерывный ClientHello `[0..N)`, `[0]==0x01`, парсится как валидный TLS ClientHello, SNI == заданный `id` (инвариант I4).
4. **Размер.** Итоговый пакет ≈1250б (length-поле 1232), как реальный padded QUIC Initial (≥1200, RFC 9000 §14.1).
5. **Уникальность.** Два вызова с одним SNI → разные DCID, разный TLS random → полностью разный ciphertext (нет общей сигнатуры между юзерами).
6. **Эталон-парсер не тавтологичен.** Тест проверяет СТРУКТУРУ/инварианты (I1–I4), а не «два вывода различны».

> Контрольные данные эталона (для сверки): рабочий пакет — 1250б, ClientHello 294б, offsets `[0,236,266,275,283,290]`, wire-order из §3.2, SNI лежит contiguous в фрейме `CRYPTO off=0 len=236`.

## 5A. Тестовые данные (device-proven рабочие узлы)

Три `i1`, **реально прошедшие DPI на устройстве** (тест-телефон, LTE с активным DPI, Clash delay-PASS, 17.06). Формат: **3 входных параметра → сгенерированный результат**. Использовать как фикстуры для тестов реализации.

> **Почему не «input → точный i1-hex»:** QUIC Initial **недетерминирован** — DCID и TLS `random` свежие на каждый вызов, поэтому байты `i1` каждый раз разные (это требование §5.5, иначе общая сигнатура). Поэтому вектор = **вход → детерминированные инварианты** (что ОБЯЗАНО выполняться для любого корректного вывода) + один **полный сквозной hex-пример** для разовой сверки крипты.

### Вход (общий для всех трёх)

```
ip  = quic                          # interface PROTOCOL (НЕ IP-адрес!) — маскировка под quic
id  = <SNI, см. ниже>               # interface DOMAIN — домен в SNI ClientHello
ib  = chrome                        # interface BROWSER — на QUIC влияет косметически (chrome|firefox|curl)
preset (AmneziaWG-поля вокруг i1, см. ниже):
  jc=4 jmin=40 jmax=70  s1=0 s2=0 s3=0 s4=0  h1=1 h2=2 h3=3 h4=4
```

> **Про нейминг `id/ip/ib`:** это **проприетарный формат WireSock** (`i`nterface **d**omain / **p**rotocol / **b**rowser), НЕ индустриальный стандарт. По документации WireSock «Protocol Masking» (Id/Ip/Ib) — их собственная фича, отдельная от стандартных AmneziaWG Magic Headers (S/H). Стандартный AmneziaWG использует `i1..i5` (CPS-теги); WireSock их НЕ поддерживает, заменив на `id/ip/ib`. Совместимости с amneziawg-go / AmneziaVPN / обычными WG-клиентами у `id/ip/ib` нет — только WireSock и наше ядро 009 (которое эту фичу скопировало, §143). Названия лаконичны до неочевидности (`ip` ≠ IP-адрес, а «protocol»). Менять нельзя — ядро 009 ждёт именно эти ключи на входе.
>
> **Следствие для §146 (важно):** `i1` — это **стандарт AmneziaWG** (понимают все AWG-клиенты), а `id/ip/ib` — нишевый WireSock-формат. §146 переводит `ip=quic` на генерацию явного фрагментированного `i1` — т.е. с нишевого формата на стандартный CPS-тег. На входе остаётся `ip=quic` (контракт 009 не ломаем), но РЕЗУЛЬТАТ — стандартный `i1`.

**Что такое `preset`** — это **стандартные AmneziaWG-поля обфускации**, которые LxBox кладёт в КАЖДЫЙ WARP-узел рядом с `i1` (`amneziaPreset()` в `warp_client.dart`). `i1` — не единственная обфускация; preset — «всё остальное». Тест должен генерировать `i1` в ЭТОЙ обвязке (иначе узел не поднимется по другой причине, и вывод про `i1` будет ложным):

| Поле | Знач. | Смысл (AmneziaWG) |
|---|---|---|
| `jc` | 4 | **junk packet count** — N мусорных пакетов перед handshake (вместе с `i1` сбивают DPI-сигнатуру) |
| `jmin`/`jmax` | 40/70 | мин/макс размер junk-пакета (байт) |
| `s1`/`s2` | 0/0 | junk-префикс перед init/response-пакетом. **0 обязателен** — иначе init/response перестают быть бит-в-бит как plain WG и **Cloudflare-сервер отвергает handshake** |
| `s3`/`s4` | 0/0 | (AWG2 доп. поля, 0) |
| `h1`/`h2`/`h3`/`h4` | 1/2/3/4 | magic headers для init/response/cookie/transport. **Стандартные WG message-types** — менять нельзя, иначе Cloudflare не распознает пакет |

> Т.е. `s/h`-поля держат WG-handshake бит-в-бит совместимым с Cloudflare, а `jc`+`i1` маскируют поток до handshake. Меняем в §146 **только содержимое `i1`** (`ip=quic` → фрагментированный Initial); preset-поля не трогаем.

| PING-фреймов | 2 | 2 | 2 | |
| PADDING-runs | `[176, 647, 72]` | `[176, 647, 72]` | `[176, 647, 72]` | |
| CH реассемблится, `[0]==0x01` | да | да | да | |
| SNI в реассембл. CH | (см. NB) | да, CH-offset 72 | да | |

**Что тест должен проверить для каждого V-i:** сгенерировать i1 для данного `id`, расшифровать (§5.1), frame-walk (§5.2): первый wire-CRYPTO `offset≠0`, ≥6 CRYPTO, ≥1 PING, PADDING-runs; реассемблировать CH по offset, убедиться `[0]==0x01` и (для длинных доменов) SNI на месте.

> **NB про `apteka.ru` (короткий 9-симв. домен) — важно для реализации.** В нашем Python-прототипе фрагментация резалась по **фиксированным** offset'ам `[0,236,...]`. Для `apteka.ru` extension-раскладка короче → SNI попал на стык фрагментов и в реассемблированном CH строка не собралась целиком — **CH технически слегка повреждён**, но узел **всё равно прошёл DPI** (это доказывает: load-bearing фактор = инвариант I1 out-of-order, а целостность SNI вторична). **Для корректной реализации ядро ДОЛЖНО резать CH по его РЕАЛЬНЫМ границам/длине (динамически), а не по зашитым offset'ам** — тогда SNI собирается при любой длине домена (I4 выполняется честно). Зашитые `[0,236,...]` в таблице — это offsets ЭТАЛОННОГО 294б CH; в реализации точки разреза вычисляются от фактической длины CH с сохранением инвариантов I1–I4.

## 6. Acceptance (ядро)

- [ ] `ip=quic` генерирует QUIC Initial с реалистичным ≥290б ClientHello (cipher_suites непуст, key_share/ALPN/supported_versions/quic_transport_params присутствуют), SNI = `id`.
- [ ] ClientHello фрагментирован на ≥6 CRYPTO-фреймов, выложенных out-of-order: первый wire-фрейм `offset≠0`, фрейм `offset=0` НЕ первый (инварианты I1–I2).
- [ ] PING + PADDING interleave между CRYPTO-фреймами (I3).
- [ ] CRYPTO-фреймы реассемблируются в валидный непрерывный ClientHello, SNI на месте (I4).
- [ ] RFC 9001 крипта корректна: собственный вывод AEAD-расшифровывается, тег сходится, header protection валиден (контрольный вектор §5.1–5.3).
- [ ] Свежие DCID + TLS random на каждый вызов; два вызова → разный ciphertext (§5.5).
- [ ] Пакет ≈1250б (padded ≥1200).
- [ ] Структурные тесты (обратный разбор, I1–I4), НЕ тавтологии.
- [ ] `id/ip/ib`-валидация и `dns/stun/sip`-ветки 009 — без регресса.
- [ ] Конфликт `id/ip/ib` с явным `i1` по-прежнему отвергается.
- [ ] **Device-smoke в заблокированном регионе:** узел `ip=quic` с фрагментированным i1 — туннель up + реальный трафик через DPI (а не только на чистой сети). Эталон рядом для контроля.

---

## 7. Вне скоупа

- `dns`/`stun`/`sip` фрагментация (отдельная таска при необходимости).
- Серверная сторона / probe-response (client-only, как 009).
- Byte-identical replay конкретного снимка — НЕ цель (наоборот, рандомизация раскладки I1–I4 снижает сигнатуру).
- JA3/uTLS fingerprint — не требуется (DPI бьётся на фрагментации, не на TLS-fingerprint).
