## Проблема

Тест `commitManualReorder … переживает рестарт приложения` в сборке
`bundle1_test.dart` упал «failed after test completion»:

```
PathNotFoundException: Cannot rename file to '/tmp/node_sort_no_dirty_XRKFHP/lxbox_settings.json',
  path = '…/lxbox_settings.json.10.tmp'
_atomicSave ← _save ← SettingsStorage.setNodeSort ← HomeController._persistSort
  ← HomeController.commitManualReorder ← node_sort_no_dirty_test.dart:119
```

Коммит, на котором упало, сортировку не трогал. В том же логе соседи
`mass_ping_delay_scope_test` и `home_direction_remembered_test` печатали
`home direction save failed: PathNotFoundException …` — та же гонка, но там
ошибку ловит `catchError` контроллера, и тест не падает.

## Диагностика

- `HomeController._persistSort` зовёт `SettingsStorage.setNodeSort` через
  `unawaited` — запись настроек fire-and-forget (для приложения это верно:
  UI не ждёт диска).
- `setNodeSort` = `await _load()` → `_save()` → `_atomicSave`: копия в `.bak`,
  запись `.tmp` с `flush`, `rename` в main. Несколько шагов ввода-вывода.
- Третий тест не ждал записи вообще (`getNodeSort` отвечает из кэша в
  памяти, не с диска). `tearDown` делал `dispose`, паузу 50 мс и удалял
  `tempDir`. На загруженном раннере запись не укладывалась в 50 мс —
  `rename` попадал в удалённый каталог. В сборке изолят живёт дальше
  (следующие тест-файлы), поэтому ошибка доезжает и валит тест задним числом;
  при одиночном прогоне файла изолят успевает завершиться, и падения не видно.
- Прошлая починка (`bcb6aae45`) добавила в первые два теста опрос каталога
  («файл есть, `.tmp` нет три раза подряд») — эвристика, которая к тому же не
  покрывала третий тест и окно, пока сеттер ещё в `_load()` (ни файла, ни
  `.tmp` ещё нет, но запись уже обещана).
- `SettingsStorage._pendingSave` — один слот: при перекрывающихся `_save()`
  хранит только последнюю запись и обнуляется первой завершившейся, так что
  ждать его снаружи нельзя.

**Причина:** тест удалял временный каталог, не дождавшись фоновой записи
настроек, начатой `_persistSort`; способа дождаться всех начатых записей у
хранилища не было.

## Решение

Дефект теста, но ждать ему было нечем — в хранилище добавлен тестовый
механизм ожидания, поведение приложения не меняется.

- `SettingsStorage._savesInFlight` — набор незавершённых `_save()`; запись
  учитывается с первого `await` (путь к файлам) и снимается в `finally`
  после `touchConfig` (§113 — тоже ввод-вывод в каталоге).
- `SettingsStorage.settleSavesForTesting()` (`@visibleForTesting`): ждёт
  незавершённое чтение `_loadInFlight` (сеттер в этот момент ещё до
  `_save()`), даёт шаг цикла событий, ждёт все записи; повторяет, пока не
  станет тихо. Ошибки записей не глотает — их получает тот, кто запись
  начал. Только для `test()` на живом времени.
- `node_sort_no_dirty_test`: `tearDown` = `dispose` → `settleSavesForTesting`
  → удаление `tempDir`; эвристика `settleSaves` и пауза 50 мс сняты.
- `mass_ping_delay_scope_test`, `home_direction_remembered_test`: тот же вызов
  перед удалением `tempDir` (запоминание Направления §724 пишет
  fire-and-forget).

## Риски и крайние случаи

- В fake-async зоне `testWidgets` чтение может зависнуть навсегда —
  `settleSavesForTesting` тогда тоже; в доке метода это сказано, вызывающие
  — обычные `test()`.
- Остальные тесты `test/controllers/` с паузой 50 мс в `tearDown` настроек
  не пишут (в логе их записей нет); переводить их не стали.

## Проверка

- Воспроизведение: временная задержка 300 мс перед `rename` в `_atomicSave`
  (не закоммичена) + за тестами файла ещё один тест на 1 с (изолят живёт, как
  в CI-сборке). Версия теста из `HEAD` упала дословно как в CI
  (`Cannot rename file to …/lxbox_settings.json`, «Some tests failed»).
  Первая версия починки (учёт только `_save()`) под той же задержкой упала
  с `Cannot open file …0.tmp` — так найдено окно `_load()`. Итоговая
  версия под задержкой — зелёная; соседние два файла — зелёные.
- Без задержки: 50 копий файла в одном изоляте (`group` × 50, 150 тестов) —
  все зелёные, `PathNotFoundException` нет; 30 отдельных прогонов файла
  подряд — 30/30 зелёные (машина под нагрузкой параллельных сборок).
- `flutter analyze` по изменённым файлам — чисто; `tool/arch/boundary_check.dart` — 0 нарушений.

## Не делается

- `_pendingSave` (один слот) не переделан: читатель `_loadFromDisk` ждёт его
  только при пустом кэше; отдельная задача, если понадобится.
- `CHANGELOG.md` не трогается — видимого пользователю эффекта нет.
