# §596 — Таймаут старта растёт с числом узлов

| Поле | Значение |
|------|----------|
| Тип | B (баг) |
| Статус | D (сделано) |
| Фича | — |
| Дата | 2026-09-30 |
| Связанные | §519 (надбавка за endpoint'ы), §140 (debug-override), §595, фича 478 (страховка) |

## Проблема

Жалоба 30.09.2026 (подписка OVI-vpn, ~230 узлов): VPN перестал запускаться.

На эмуляторе страховка отработала штатно: ядро отвергло узел с битым
mlkem-ключом, страховка его сняла и сделала финальный старт. Финальный старт
упал с `Start timed out after 15 s (post-start did not finish, 0 endpoints)`.
По logcat ядро дошло до `Started` на 15,0 с, а таймаут фазы `connecting`
сработал на 15,5 с и через `forceStop` убил уже поднявшийся туннель.
Повторный старт с валидным конфигом повторил то же.

## Диагностика

`HomeController._effectiveConnectingTimeout` (§519): база 15 с + надбавка
только за WG/AWG-endpoint'ы, потолок 4 мин. Число обычных узлов
(`outbounds`) порог не двигает, хотя ядро инициализирует каждый из них на
старте, и на большой подписке и слабом устройстве 15 с не хватает.

## Решение (владелец, 30.09.2026)

«15 секунд на старт давай плавающими сделаем: на каждый узел 0,1 с, и если
узлов 240, то это 24 с».

Порог `connecting`:

```
max(15 с, 0,1 с × N) + надбавка §519 × E, не выше потолка 4 мин
```

- `N` — число узлов в сохранённом конфиге (`configModel.nodes`: outbounds и
  endpoints узлов).
- `E` — число endpoint'ов, как сейчас (§519).
- 240 узлов без endpoint'ов → 24 с; 100 узлов → 15 с (база).
- Debug-override (§140, `set-transient-timeout`) по-прежнему берётся дословно.

Текст причины (`StopStartTimeout`) не меняется. Debug API, который отдаёт
`debugEffectiveConnectingTimeout`, дополнительно показывает `nodes`.

## Критерии приёмки

1. 240 узлов, 0 endpoint'ов → 24 000 мс; 100 узлов → 15 000 мс; 240 узлов и
   2 endpoint'а → 24 с + 2 × надбавка §519; очень большое N упирается в
   потолок.
2. Debug-override не масштабируется.
3. Юнит-тест на формулу в тестовом файле §519.
4. Эмулятор: подписка OVI (220 узлов + битый mlkem), Start кнопкой →
   страховка снимает узел, финальный старт укладывается в новый порог,
   туннель `connected`.

## Проверка

Коммит `fix(596)` (этот же коммит, хеш — в истории ветки).

- Формула — `HomeController._effectiveConnectingTimeout`
  (`app/lib/controllers/home_controller.dart`), константа
  `_connectingTimeoutPerNode = 100 мс`; `debugEffectiveConnectingTimeout`
  отдаёт `nodes`. Отдельного поля Debug API с действующим порогом нет —
  `nodes` видно в строке лога `connecting timeout armed: …ms (nodes=N endpoints=E)`.
- Страховка (фича 478) своего порога 15 с не имеет: её старты идут через
  `start()` и тот же safety-timer. Ожидание вердикта
  (`startAndAwaitVerdict[Headless]`) было жёстко 45 с — теперь
  `max(45 с, порог connecting + 5 с)`, чтобы на большой подписке не бросать
  ожидание раньше safety-timer'а.
- `test/controllers/connecting_timeout_endpoints_test.dart` — 10/10 зелёные
  (5 новых кейсов §596); `home_core_reject_test.dart` — зелёный;
  `flutter analyze` — чисто.
- Эмулятор (п. 4), 30.09.2026, сборка 2.25.9-dev.10 (develop 354856ac):
  подписка OVI, 221 узел, в конфиге 232 выхода, среди них узел с битым
  mlkem-ключом. Start кнопкой: `connecting timeout armed: 23200ms
  (nodes=232 endpoints=0)` → ядро отказало на узле → страховка сняла его →
  финальный старт `armed: 23100ms (nodes=231)` → `Started` через 0,3 с,
  исход `started_with_disabled`, туннель `connected`. Прежний отказ по 15 с
  на этом стенде объяснялся перегрузкой хоста (ANR): на свободном хосте
  старт занимает доли секунды, новый порог — запас для слабых устройств.
