## Проблема

Механизм §047 найден (сессия sing-box-lx, 31.07.2026). В system-стеке sing-tun
весь новый TCP из TUN идёт через локальный TCP-listener. Приёмная петля
(`stack_system.go:370-384`) на любой ошибке `Accept()` выходит **навсегда и
молча**, а стек продолжает жить: `tunLoop` переписывает каждый новый SYN на
кешированный порт мёртвого листенера, ОС отвечает RST, RST де-НАТится обратно
приложению. Итог — весь новый TCP получает мгновенный `ECONNREFUSED` (~16 мс)
до рестарта VPN; UDP/QUIC/DNS живут (listener-free путь). Это в точности
симптоматика §047, включая «`/delay` API работает, а приложения нет».

Фактура с устройства (OnePlus CPH2411, Android 15, ядро v1.14.0-lx.17-rc.3):
goroutine-дамп сломанного состояния показывает живые `tunLoop`/`TCPNat`/`UDPNat`
при **отсутствующем** `acceptLoop`; listener-сокета на адресе TUN нет;
`ListenOverflows=0, ListenDrops=0` — SYN до сокета не доходят вовсе.

**Чего не хватает:** кто именно убивает листенер. LxBox и libbox живут в одном
Android-процессе — пространство fd общее, и чужой `close()` по
переиспользованному номеру бьёт в Go-сокет. Два воркфлоу-аудита по 14 агентов
(Go-сторона sing-box-lx и Kotlin-сторона LxBox, 31.07.2026) виновника статикой
**не доказали**: внутри sing-tun/sing-box/LX-дельт закрывателя нет, рестарт-путь
daemon последователен и чист, а все 16 статических сценариев на Kotlin-стороне
опровергнуты чтением кода.

Уточнение механики из ядровой спеки, сужающее поиск: голый чужой `close(fd)`
**не будит** горутину, запаркованную в netpoll `Accept` — она осталась бы видна
в дампе. Раз петля исчезла, `Accept` вернул реальную ошибку: либо `ErrNetClosing`
(закрытие через Go-объект с тем же `poll.FD`), либо `EBADF`/`ENOTSOCK` (close
или переиспользование номера в момент активного `accept4`). Поэтому errno из
warn-лога ядра **называет путь убийства** — это первая развилка диагностики.

> ⚠️ **Развилка пройдена (2026-08-01), и ни одна из перечисленных ветвей не
> подтвердилась**: errno оказался `EINVAL` — жертву не закрывают, а лишают
> listening-состояния. См. раздел «Находка с устройства» ниже; поиск
> переориентирован с `close` на `shutdown`.

Статика исчерпана. Ловим динамикой.

## fdsan: закрыт как инструмент (не применять)

Исходный план шагом №1 предполагал включить fdsan в fatal-режиме. Проверено —
делать не нужно, и он бы всё равно промолчал. Три независимых причины, любой из
которых достаточно:

1. **Включать нечего.** bionic ставит FATAL сам в `__libc_init_fdsan()` начиная
   с API 30; CPH2411 — API 35, `debug.fdsan` пусто (`getprop`, 31.07.2026).
   Java/Kotlin-API для смены уровня не существует: libcore биндит только
   теговые функции, `set_error_level` живёт в process-wide глобале libc.
2. **Жертва нетегирована.** fdsan реагирует только на close fd с владельческим
   тегом; Go-сокеты тега не имеют (Go зовёт `socket(2)` напрямую, мимо bionic и
   libcore). При нетегированной жертве CAS `0→0` проходит молча.
3. **Close вообще не происходит** — это следует из `EINVAL` (см. ниже) и
   перекрывает пункт 2. Раз закрытия нет, реагировать fdsan не на что **даже
   если бы жертву протегировали**.

Пункт 3 закрывает и напрашивавшийся follow-up «попросить ядро тегировать Go-fd
через `android_fdsan_exchange_owner_tag`»: тегирование ничего бы не дало.
fdsan из плана удалён целиком, tombstone'ы можно не искать.

## Находка с устройства (2026-08-01): жертву не закрывают, а разлушивают

Ядро rc.4 (`v1.14.0-lx.17-rc.4`, SPEC 040) поймало **два живых срабатывания**
самолечения listener'а и залогировало errno. Полный текст первой строки:

```
00:02:20 WARN inbound/tun[tun-in]: system stack: tcp4 listener (port 42813)
         accept failed: accept tcp4 172.16.0.1:42813: accept4: invalid argument
         — recreating listener
00:02:20 WARN inbound/tun[tun-in]: system stack: tcp4 listener recreated
         (port 42813 → 37443, recoveries: 1)
```

**errno = `EINVAL`, а не `EBADF`/`ENOTSOCK`/`ErrNetClosing`.** Это меняет
модель бага: `accept4` отдаёт `EINVAL`, когда дескриптор **жив и остаётся
сокетом, но перестал быть слушающим**. Закрытия жертвы не было вовсе —
следовательно вся ветка рассуждений про close (свой ли, чужой ли, по
переиспользованному номеру) описывает не тот механизм.

### Разбор `EINVAL` по коду ядра Linux

Проверено по исходникам (v6.6), потому что от точной семантики зависит, где
искать. `accept4` проверяет условия в жёстком порядке — и состояние сокета
**последним**:

| Проверка | Где | errno |
|---|---|---|
| fd открыт? | `net/socket.c` `__sys_accept4` → `fdget` | `EBADF` |
| fd — сокет? | `net/socket.c` `do_accept` → `sock_from_file` | `ENOTSOCK` |
| flags валидны? | `net/socket.c` `__sys_accept4_file` | `EINVAL` |
| `sk_state == TCP_LISTEN`? | `net/ipv4/inet_connection_sock.c` `inet_csk_accept` | `EINVAL` |

```c
/* inet_connection_sock.c, inet_csk_accept() */
error = -EINVAL;
if (sk->sk_state != TCP_LISTEN)
    goto out_err;
```

Раз получен `EINVAL`, а не `EBADF`/`ENOTSOCK` — **fd открыт и остаётся сокетом**,
до проверки состояния ядро дошло. Дескриптор тот же.

**Что выводит живой сокет из `TCP_LISTEN`** (исчерпывающе):

- **`shutdown(fd, SHUT_RD)` или `SHUT_RDWR`** — `net/ipv4/af_inet.c`
  `inet_shutdown()`: для `TCP_LISTEN` при взведённом `RCV_SHUTDOWN` идёт
  `sk->sk_prot->disconnect()` → `tcp_set_state(sk, TCP_CLOSE)` +
  `inet_csk_listen_stop()`. Комментарий в самом ядре называет это «temporary
  solution for missing close() in multithreaded environment. It is _not_ a good
  idea». **`SHUT_WR` для листенера — no-op**, эту ветку можно не искать.
- **`connect()` на листенере** — тот же `tcp_disconnect`.
- **`tcp_abort()` / netlink `SOCK_DESTROY`** — механизм, которым **Android netd
  рвёт сокеты при смене сети**. Но он дополнительно ставит `sk_err`, поэтому
  `accept` вернул бы скорее `ECONNABORTED`; чистый `EINVAL` делает эту ветку
  менее вероятной, хотя полностью не снимает.

**Два побочных следствия, объясняющих прежние аномалии.** `shutdown` не отдаёт
номер fd в пул (дескриптор остаётся открытым) — отсюда молчание fdsan. И он
**будит** запаркованную в netpoll горутину через `sk->sk_state_change()` — отсюда
исчезновение `acceptLoop` из дампа, которое статический аудит не смог объяснить
голым `close`. Обе загадки закрываются одной гипотезой.

**Совместим ли `EINVAL` с переиспользованием номера fd?** Формально да, но в
одном узком случае: номер достался новому **TCP**-сокету не в listen-состоянии.
Соседние варианты дают другие errno — под файл/pipe `ENOTSOCK`, под UDP-сокет
`EOPNOTSUPP` (у `inet_dgram_ops` accept = `sock_no_accept`). Прежняя гипотеза
про переиспользование этим не воскрешается, но и не опровергнута на 100%.

**Сценарий «TUN снесён при reload» — проверен и не подходит.** Разбор
`net/ipv4/devinet.c` `inetdev_event()`: на `NETDEV_DOWN`/`NETDEV_UNREGISTER`
ядро не обходит TCP-сокеты и не трогает `sk_state`. Листенер на исчезнувшем
адресе **остаётся в `TCP_LISTEN`**, просто перестаёт получать SYN — что сходится
с `ListenOverflows=0, ListenDrops=0` из §047, но `acceptLoop` при этом бы не
вышел. Сам по себе teardown интерфейса `EINVAL` не даёт.

**Версионная деталь для датировки.** В Go ≤1.23 `internal/poll/sock_cloexec.go`
на `EINVAL` делал fallback на обычный `accept`, перезаписывая errcall на
`"accept"` — то есть пара «`accept4` + `invalid argument`» была недостижима. В
Go 1.24 fallback вырезан. Ядро собирается Go 1.25.x ⇒ строка подлинная, но этот
симптом **не мог наблюдаться на сборках до Go 1.24**.

Что из этого следует для плана:

1. **Искать `shutdown(SHUT_RD|SHUT_RDWR)`, а не `close()`.** `SHUT_WR`
   исключён — для листенера это no-op. Прочие кандидаты (менее вероятные):
   `connect` на том же fd, netd `SOCK_DESTROY` при смене сети.
   Неинвазивная проверка состояния живого fd, если понадобится:
   `getsockopt(fd, SOL_SOCKET, SO_ACCEPTCONN)` вернёт `0` на убитом листенере.
2. **Триггер — `reload`, подтверждён экспериментом.** Оба срабатывания
   произошли через ~1 с после `[vpn] reload → ok=true`. Но убивает не каждый
   reload: серия из 10 подряд дала одно срабатывание (`recoveries: 1`) —
   нужна дополнительная совпадающая по времени операция. Отсюда «плавающесть»
   §047 и провал попыток репро спокойной серией `reconnect` (120/120 и 30/30
   чисто, ни одной красной пробы).
3. **fdsan окончательно бесполезен** для этой жертвы — и не по причине из
   раздела выше (нетегированность), а по более простой: **close не
   происходит**, а fdsan реагирует только на close. Оба обоснования
   независимо ведут к одному выводу.
4. **fd-логи остаются главным инструментом**, но их надо расширить: логировать
   не только `closeFileDescriptor`, но и весь reload-путь
   (`startOrReloadService` и соседние операции над сокетами), сопоставляя по
   таймстампу с warn'ом ядра. Уровень `Log.w` сохранить: в ядре errno чуть не
   потерялся, утонув в потоке INFO — та же грабля применима и здесь.

Practical: воспроизведение теперь дешёвое — серия `POST /action/reload-vpn`
(интервал ~3 с) при включённом форвардинге core-логов
(`PUT /settings/core_logs_enabled {"enabled":true}` + force-stop приложения,
`Libbox.setup` одноразовый). Признак поимки — warn `accept failed` с errno
и следом `listener recreated`.

## План

### Шаг 1 — логирование номеров fd с таймстампами

Цель — получить таблицу «номер fd ↔ момент ↔ путь», по которой на битой
итерации видно, был ли номер листенера переиспользован и кем.

| Место | Что логировать |
|---|---|
| `BoxVpnService.openTun` ([BoxVpnService.kt:410-413](../../../app/android/app/src/main/kotlin/com/leadaxe/lxbox/vpn/BoxVpnService.kt)) | `pfd.fd` сразу после `builder.establish()`, до `service.fileDescriptor.set(pfd)` |
| `BoxService.closeFileDescriptor` ([BoxService.kt:301-304](../../../app/android/app/src/main/kotlin/com/leadaxe/lxbox/vpn/BoxService.kt)) | номер закрываемого fd + **тег пути** (кто позвал: `doStop` / `doForceStop` / `onRevoke` / `onDestroy`) |

Тег пути обязателен: `closeFileDescriptor()` сейчас вызывается из нескольких
мест без различения, а именно порядок и источник закрытия — предмет поиска.
Значит сигнатура становится `closeFileDescriptor(reason: String)` по образцу уже
существующего `closeCommandServerAtomic(reason)` — единообразно с соседним кодом.

Таймстамп — монотонный (`SystemClock.elapsedRealtime()`), чтобы сопоставлять с
логами ядра, не завися от настенных часов.

Логи идут в logcat под существующим `TAG` на уровне `Log.w` и **остаются в
релизе** (решение владельца, 01.08.2026). `w` виден под дефолтным порогом
logcat — при разборе случая не надо помнить про фильтр, строки просто есть:

```bash
adb logcat -d -v time | grep -a '\[fd §329\]'
```

Это и мотив релизной жизни: инструментировка доживёт до следующего случая §047
в реальной работе, и снимать придётся только logcat, без пересборки.

Буфер это не забивает: по две строки на цикл старт/стоп туннеля (`openTun` +
`close`), в горячем пути (пакеты, соединения) не пишется ничего. Единицы строк
в день при обычном пользовании; ~200 за сотню итераций репро-серии.

Промежуточно уровень понижался до `Log.i` (расчёт «под дефолтным порогом не
видно»), но возвращён на `w`: видимость по умолчанию важнее тишины в проде при
таком объёме.

### Шаг 2 — репро-серия

Серия `POST /action/reconnect` через Debug API с интервалом 4-5 с. Статистика
из ядровой сессии: **108 рестартов → 3 поломки** (итерации 8, 8, 22), затем 78
подряд чистых. Вероятность кластеризуется на «грязном» процессе (fd-churn/GC),
отсюда плавающий характер и наблюдение §047 «каждый цикл деградации короче».

Практический вывод для методики: гонять **после активного использования**
(браузер, мессенджеры — набить fd-churn), а не на свежезапущенном процессе;
свежий процесс даёт ложноотрицательный результат. Серия — не менее 100 итераций.

Скрипт кладём в `scripts/` рядом с `lxbox-diag.sh`: цикл reconnect + проба после
каждой итерации + сбор logcat при первом же красном результате.

### Шаг 3 — детектор поломки

Два независимых сигнала, оба дешёвые:

1. **TCP-проба с устройства** — `nc` на заведомо живой адрес. Красный =
   мгновенный `Connection refused` (~16 мс, не таймаут) при **рабочих** UDP/DNS.
   Разделение важно: именно эта асимметрия отличает §047 от обычного обрыва.
2. **fdsan-tombstone** — пассивно, см. выше. Ожидается, что не прилетит;
   прилетит — значит поймали направление (i), что само по себе результат.

Плюс ядровая половина, уже готовая в sing-box-lx (задача 040): patched sing-tun
warn-логирует errno смерти листенера и самолечится. На битой итерации в логах
ядра должен быть warn «accept loop died … recreated» — и **errno в нём называет
путь убийства** (`ErrNetClosing` ⇒ закрытие через Go-объект;
`EBADF`/`ENOTSOCK` ⇒ голый close/переиспользование номера). Это первое, что
надо прочитать на красной итерации.

### Шаг 4 — сверка маркеров на битых итерациях

На каждой красной итерации проверить logcat на три маркера:

| Маркер | Где | Что значит присутствие |
|---|---|---|
| `doForceStop ENTER` | [BoxService.kt:511](../../../app/android/app/src/main/kotlin/com/leadaxe/lxbox/vpn/BoxService.kt) | сработал force-путь — teardown шёл не по штатной ветке |
| `Timeout in stopping` | [home_controller.dart:515](../../../app/lib/controllers/home_controller.dart) | transient-таймаут Dart-стороны, т.е. ядро не ответило вовремя |
| `[vpn] onDestroy` | [BoxService.kt:250](../../../app/android/app/src/main/kotlin/com/leadaxe/lxbox/vpn/BoxService.kt) | Android убил сервис — пересечение с рестартом |

**Отдельный сигнал — `onDestroy` без парного close.** `onDestroy` не закрывает
fd сам: он делает `serviceScope.cancel()`, что может снять in-flight
`doStop`-корутину **до** её `closeFileDescriptor`. Тогда fd остаётся незакрытым
и его номер продолжает жить, пока Android не приберёт процесс. В логе это видно
как `[vpn] onDestroy` **без** парного `[fd §329] close(doStop)` — прямой
кандидат на источник переиспользуемого номера. Проверять на каждой красной
итерации наравне с тремя маркерами выше.

Две поправки к grep'у, иначе маркеры не найдутся: строка Dart собирается
шаблоном (`'Timeout in ${expected.name}, forcing disconnect'`) — искать по
`Timeout in`, а не по целой фразе; `[vpn] onDestroy` логируется на уровне
`Log.d`, поэтому logcat нужно снимать без фильтра по приоритету (`*:D`).

**Их отсутствие подтверждает выводы аудита** (рестарт шёл штатно и последовательно)
и снимает с подозрения force/timeout/destroy-ветки, оставляя гипотезу
переиспользования номера fd единственной живой. Присутствие любого — наоборот,
немедленно сужает поиск к конкретной ветке и делает дальнейшую динамику
необязательной.

## Риски и edge cases

- **Гейзенбаг.** Логирование меняет тайминги; гонка с окном в сотни миллисекунд
  может перестать воспроизводиться. Поэтому логи минимальны (единицы строк на
  рестарт, без форматирования в горячем пути) и пишутся из тех же потоков, что и
  существующие вызовы, без новых синхронизаций.
- **Серия может не дать ни одной поломки.** При 3/108 отрицательная серия из 100
  итераций — не опровержение. Нужна либо более длинная серия, либо более грязный
  процесс. Это ограничение методики, а не признак починки.
- **Номер fd переиспользуется быстро.** Само по себе совпадение номеров в логе
  не доказывает виновность — нужен порядок событий по монотонному таймстампу
  (закрытие ПОСЛЕ того, как номер выдан листенеру).
- **Тегирование Go-fd (запрос к ядру) — вне этой задачи.** Оно бы усилило
  поимку, но требует правки ядра и отдельного релиза AAR.
- **Не покрыто:** фикс самого триггера. Задача — только поимка. Фикс — отдельной
  задачей по её результатам.

## Нерешённое / follow-up

1. **Фикс триггера** — отдельная задача после поимки.
2. **Запрос команде ядра: тегировать Go-fd** через
   `android_fdsan_exchange_owner_tag`, в первую очередь dup'нутый tun-fd
   (`experimental/libbox/service.go:76`). Превращает направление (ii) в (i) и
   даёт abort со стеком нарушителя. Не блокирует эту задачу.
3. **Счётчик восстановлений ядра наружу** — ядровая задача 040 закладывает
   атомарный счётчик, health-RPC отложен. Когда появится — тикающий счётчик в
   проде станет постоянным индикатором «триггер всё ещё жив».
