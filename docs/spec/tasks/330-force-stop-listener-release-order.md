## Жалоба

4PDA: eXense #1355, dewch #1360, k-dmitriy #1364/#1365. Зависание в «Stopping»,
после него **порт остаётся занят — другая программа его открыть не может**;
помогает повторный старт-стоп. Лог пользователя (#1364/#1365):

```
Timeout in stopping, forcing disconnect
[vpn] forceStopVPN sent (timeout in stopping)
reconnect: stop timed out, aborting start
```

## Почему это не §287

§287 лечила **длительность** ожидания («стоп долго крутится»): снизила
`_stoppingTimeout` 10с → 3с, чтобы раньше отдать управление force-пути. Это
сработало и остаётся правильным. Но жалоба — про **последствие** срабатывания
force-пути, чего §287 не чинила.

Более того, §287 сделала этот путь **систематическим**. По её же замерам
легитимный teardown на конфигах с ~30 WG-нодами занимает 10–17с — под порог 3с
он не укладывается практически никогда. Утверждение §287 «легитимный teardown
под форс не попадает» верно только для замера «stop без пинга — 0.16с».

## Корень

Цепочка из лога ложится на код буквально:

1. [`home_controller.dart:515`](../../../app/lib/controllers/home_controller.dart) — сработал порог 3с.
2. [`:525`](../../../app/lib/controllers/home_controller.dart) → broadcast `ACTION_FORCE_STOP` → `doForceStop()`.
3. [`BoxService.kt:557`](../../../app/android/app/src/main/kotlin/com/leadaxe/lxbox/vpn/BoxService.kt) — `withTimeout(2_000) { closeCommandServerAtomic(...) }`.

`withTimeout` **кооперативен**: блокирующий JNI-вызов он не прерывает, только
отпускает корутину Kotlin. А в `closeCommandServerAtomic` порядок был:

```kotlin
runCatching { cs.closeService() }   // ← залипает на 10-17с (WG-teardown, §287)
runCatching { cs.close() }          // ← до этой строки выполнение не доходит
```

Залипший `closeService()` не отдавал управление следующей строке, поэтому
`cs.close()` — тот самый вызов, что освобождает слушающий сокет — **не
вызывался вовсе**. Выполнение уходило на `stopSelf()`
([:560](../../../app/android/app/src/main/kotlin/com/leadaxe/lxbox/vpn/BoxService.kt))
раньше, чем порт освобождался.

Итог: Clash-порт 63130 + `command.sock` заняты ещё 8–15с после того, как UI уже
показал «отключено». `stopSelf()` процесс не убивает (UI на переднем плане —
§287 это сама отмечает), поэтому OS порт тоже не приберёт. «Помогает
старт-стоп» — к повторной попытке WG-teardown доигрывает, `cs.close()`
отрабатывает.

**Что упустила §287.** В разделе «Почему это безопасно» сказано: «Bind-коллизии
на рестарте нет: WG биндит эфемерные UDP-сокеты». Для WG верно. Но
CommandServer держит **фиксированный** порт 63130, и на него этот аргумент не
распространяется — ровно тот случай, который §140 чинила порядком вызовов.
Порядок остался правильным, но таймаут разорвал его фактически.

## Решение

Развязать освобождение слушающего сокета и teardown ядра — поменять их местами:

```kotlin
runCatching { cs.close() }          // ← сокет свободен сразу
runCatching { cs.closeService() }   // ← пусть залипает, порт уже отдан
```

`close()` не блокируется: teardown WG живёт целиком в `closeService()`.

### Почему развязка безопасна (проверено по ядру v1.14.0-lx.17-rc.4)

| Вызов | Что делает | Берёт `serviceAccess`? |
|---|---|---|
| `CommandServer.Close()` ([`command_server.go:180`]) | `grpcServer.Stop()` + `common.Close(listener)` + `StartedService.Close()` (только subscriber'ы) | **нет** |
| `CommandServer.CloseService()` ([`command_server.go:207`]) → `StartedService.CloseService()` ([`daemon/started_service.go:245`]) | держит мьютекс на всё время `instance.Close()` | **да** |

Общего состояния между ними нет, порядок ядру безразличен. `instance` живёт под
`serviceAccess` и `Close()` его не трогает.

Обратный порядок не ломает и штатный `doStop`: `closeService()` не ходит в
gRPC-транспорт, а CommandClient-канал разрывается выше по функции
(`commandClient?.shutdownAll()`).

Побочная деталь: `cs.setError()` в error-ветке `closeService()` теперь зовётся
после `Close()` — subscriber'ы уже закрыты, сообщение никуда не доедет.
Не регресс: вызов и раньше был best-effort в `runCatching`, а на force-пути UI
к тому моменту уже погашен.

Добавлена строка `[fd §330] listener closed(<reason>) at=<ms>` (`Log.w`,
монотонная метка — единообразно с инструментировкой §329): по ней на устройстве
видно фактический момент освобождения порта, а не намерение.

## Что НЕ делаем

- **Порог 3с не трогаем** — возврат к 10с вернёт исходную жалобу §287.
- **Ядро не трогаем** — корневой фикс (`closeService()` не должен ждать
  in-flight dial'ы от пинга) остаётся отдельной задачей, вынесенной за скоуп
  ещё в §287. Эта правка снимает пользовательскую боль на app-стороне.

## Нерешённое / follow-up

1. **Корневой фикс в ядре** — `closeService()` не должен ждать in-flight dial'ы
   от mass-ping'а при закрытии WG-эндпоинтов (наследуется из §287).
2. **Фоновой teardown переживает `stopSelf()`** — по §287 это признано
   безопасным (воркеры гаснут по порядку). Здесь ничего не меняется, но при
   корневом фиксе п.1 вопрос отпадёт сам.
