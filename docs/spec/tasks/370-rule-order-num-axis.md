# §370 — порядок правил: разреженная ось `ui.num` + `ui.isSortable`

**Статус:** СПЕКА (реализация в этой же таске)
**Тип:** замена концепта упорядочивания правил. Модель + шаблон + storage + нормализация + UI.
Ядро и `route.rules`-сборка НЕ трогаются (порядок эмита как был — по списку `customRules`).
**Заменяет:** §264 в части `ui.pinned` (поле выпиливается), §369 целиком (его фиксы
поглощены новой моделью).
**Зависит от:** §264 (locked-пресет, объект `ui`), §030 (Custom Rules)

---

## 0. Проблема

`ui.pinned` (§264) — фиксированная позиция, умеет только «прибить к началу». Из этого:

- нет способа задать правилу стартовое место в середине или в конце списка;
- пресет из каталога вставляется по эвристике `_computeInsertIndex` (reject → верх,
  direct → после reject-блока, остальное → хвост), которая ничего не знает о шаблоне и
  уже дала баг §369 (`fcm-push` прыгал на index 0, выше `traffic-processing`);
- у большинства правил порядка нет вообще — он определяется тем, в каком порядке юзер
  их добавлял.

Решение владельца: дать **каждому** правилу число на разреженной оси. Число — стартовая
позиция, а не забитая навсегда сортировка: юзер двигает drag'ом, ось перестраивается.
Зазоры между значениями оставлены осознанно — чтобы позже можно было вписать новый
пресет между существующими, не переделывая раскладку.

## 1. Модель

`SelectableRule` (`parser_config.dart`) — поле `pinned` удаляется, добавляются два:

| Поле `ui` | Тип | Смысл | Дефолт |
|---|---|---|---|
| `num` | int | позиция на оси | `1000` (середина пользовательской зоны) |
| `isSortable` | bool | можно ли двигать drag'ом | `true` |

`isPinned` (`pinned != null`) заменяется на `!isSortable`. Поле `locked` **остаётся** — оно
ортогонально: `locked` про «нельзя выключить/удалить» (тумблер, delete-гейт), `isSortable`
про «нельзя двигать». У `traffic-processing` истинны оба, но это разные инварианты.

`CustomRule` (sealed, `custom_rule.dart`) — новое поле `num` в базовом классе, сериализуется
во всех четырёх подклассах (`inline`/`srs`/`preset`/`json`).

## 2. Раскладка оси (решение владельца)

| Правило | `num` | `isSortable` |
|---|---|---|
| traffic-processing | 0 | **false** |
| private-ip | 950 | true |
| block-ads | 960 | true |
| fcm-push | 970 | true |
| bittorrent | 980 | true |
| *(VoWiFi — зарезервировано)* | *990* | *true* |
| **пользовательские** | **1000–1100** | true |
| ru-inside | 1110 | true |
| ru-direct | 1120 | true |
| fakeip | 1130 | true |
| unknown-traffic | 1150 | true |

Зона 1000–1100 — сто слотов под правила юзера; шаблонные пресеты стоят по краям с шагом 10
(девять свободных номеров между соседями под будущие вставки). 1140 свободен намеренно.

`traffic-processing` — единственный `isSortable: false`: он несёт `sniff`, который обязан
быть первым правилом `route.rules` (извлекает домен до матчинга роутинга, см. §264 §1).

## 3. Сортировка

Список правил всегда отсортирован по `num` (возрастание). При равных `num` — порядок в
массиве (стабильная сортировка; равенство возможно после исчерпания зазора, см. §4).

`num` — **не** одноразовая подсказка при вставке: он живёт в storage и является
авторитетным источником порядка. Массив `customRules` хранится уже отсортированным.

## 4. Drag: «встать за целевым» + ленивый сдвиг

Правило владельца — сдвигать соседей только когда номер реально занят:

```
drag правила R на позицию за элементом T:
  want = T.num + 1
  если want свободен  →  R.num = want                    // сдвига нет
  иначе               →  всем правилам с num >= want: num += 1
                         R.num = want
```

**Почему именно так (обоснование, не переизобретать):** каскадный сдвиг +1 на каждом drag'е
съедал бы зазоры и двигал шаблонные якоря — тогда `num` из шаблона перестал бы что-либо
гарантировать, и вписать новый пресет между `ru-inside` (1110) и `ru-direct` (1120) стало бы
невозможно. При ленивом сдвиге уплотнение локально (только в точке перетаскивания), а вся
ось ниже стоит на месте. Перенумерация/нормализация зон **не делается** — она бы ровно эти
якоря и ломала.

Вырождение (забить 1000…1100 подряд) теоретически возможно, но съедает одну позицию за
перетаскивание и только там, куда таскают. Упрёмся — добавим точечно, не сейчас.

Сдвиг пропускает `isSortable: false` (их `num` неизменен). Сейчас такой один и он на 0,
то есть выше любого `want` — каскад в него не упирается.

## 5. Разметка существующего storage

**Миграции как отдельного версионированного шага НЕТ** (решение владельца — «не нравятся
эти все миграции»). Разовая разметка при загрузке: у правила нет `num` → проставляем.

- правило-пресет, чей `presetId` есть в шаблоне → `num` из шаблона;
- всё остальное (пользовательские inline/srs/json + пресеты, которых в шаблоне уже нет) →
  подряд от 1000: 1000, 1001, 1002… в текущем порядке массива.

Принятое следствие: правила из старого storage получают номера в начале пользовательской
зоны и оказываются приоритетнее добавленных после обновления. Владелец: «ну, так бывает».

Второе следствие, видимое юзеру: при первом запуске список **перетасуется** — например
пользовательское правило, стоявшее ниже `ru-direct`, уедет выше (1000+ против 1120).
Это прямое следствие раскладки, не баг.

## 6. Вставка нового правила

Эвристика `_computeInsertIndex` (reject/direct/хвост) **удаляется** — её роль переходит к `num`.

- **пресет из каталога** → `num` из шаблона; если занят, ленивый сдвиг как в §4;
- **новое пользовательское правило** → `max(num среди 1000..1100) + 1`, при пустой зоне 1000.
  Если зона исчерпана (максимум = 1100) → тот же `num`, что у последнего (равенство
  допустимо, порядок доопределяется массивом).

## 8. Тесты

- разметка: пресет по `presetId` из шаблона; не-шаблонное подряд от 1000; идемпотентность;
- сортировка по `num`, стабильность при равенстве;
- drag: свободный `want` → без сдвига; занятый → сдвиг только тех, кто `>= want`;
- `isSortable: false` не двигается и не сдвигается;
- вставка пресета из каталога встаёт по шаблонному `num` (регресс §369: `fcm-push`
  ПОД `traffic-processing`);
- вставка пользовательского → конец зоны; исчерпание зоны → равный `num`.
