## Проблема

Кэш DNS ядра работает с настройками по умолчанию: малый размер, устаревший
ответ не отдаётся, после перезапуска кэш пуст. Первое обращение к каждому
сайту после запуска VPN ждёт ответа DNS через туннель.

## Решение владельца (27.09.2026)

1. В шаблон конфига добавляются три поля ядра.
2. Все три выносятся в настройки, на вкладку DNS.
3. Кнопка очистки кэша DNS уже есть, новая не нужна.

## Поля ядра

Проверено по исходникам `sing-box-lx` 1.14.2-lx (`option/dns.go`,
`option/experimental.go`, `dns/client.go`, `dns/router.go`).

| Поле | Смысл | Уточнение |
|---|---|---|
| `dns.cache_capacity` | размер кэша | число записей, не байты; ядро поднимает значение ниже 1024 до 1024 |
| `dns.optimistic` | устаревший ответ отдаётся сразу, запись обновляется в фоне | принимает `true` или объект `{enabled, timeout}`; срок годности устаревшего ответа по умолчанию 3 суток после истечения TTL |
| `experimental.cache_file.store_dns` | кэш DNS пишется в `cache.db` и переживает перезапуск | `cache_file` в шаблоне уже включён, с `store_fakeip` |

## Решение

### 1. Шаблон

```json
"dns": {
  "cache_capacity": "@dns_cache_capacity",
  "optimistic": "@dns_optimistic"
},
"experimental": {
  "cache_file": {
    "enabled": true,
    "path": "cache.db",
    "store_fakeip": true,
    "store_dns": "@dns_store_cache"
  }
}
```

Остальные поля разделов `dns` и `experimental` не меняются.

### 2. Переменные шаблона

| Переменная | Тип | По умолчанию | Допустимые значения |
|---|---|---|---|
| `dns_cache_capacity` | число | `4000` | от 1024 до 65535 |
| `dns_optimistic` | bool | `true` | |
| `dns_store_cache` | bool | `true` | |

Значение по умолчанию одно для всех платформ. Размер кэша по умолчанию 4000
записей (решение владельца 27.09.2026, контракт 1.1.95); верхняя граница 65535
совпадает с отсечкой подстановки целых в шаблоне, исключений нет (контракт 1.1.94).

Срок годности устаревшего ответа в настройки не выносится, действует срок
ядра.

### 3. Вкладка DNS

| Настройка | Вид | Подпись |
|---|---|---|
| DNS cache size | число | Number of cached answers. |
| Serve stale answers | переключатель | Answer from cache at once and refresh in the background. |
| Keep DNS cache after restart | переключатель | |

Место: экран DNS (`app/lib/screens/dns_settings_screen.dart`), рядом с
существующей кнопкой Clear DNS cache.

Ввод вне допустимых значений не сохраняется, поле показывает границы.

Изменение любой из трёх настроек помечает конфиг как требующий пересборки,
как остальные настройки DNS.

### 4. Кнопка очистки кэша

Исполнитель проверяет, что существующая очистка убирает и записи, сохранённые
в `cache.db` при `store_dns`. Если не убирает, очистка дополняется; способ
вносится в спеку.

### 5. Существующие пользователи

Переменные новые, сохранённых значений у пользователей нет: действуют
значения по умолчанию. Отдельного переноса нет.

Пользователь с собственным шаблоном или с правкой разделов `dns` и
`experimental` через JSON: его значения не перезаписываются.

### 6. Порядок работы исполнителя

1. Опись: как объявлены и хранятся существующие переменные DNS, где строится
   вкладка DNS, как работает очистка кэша. Опись вносится в спеку.
2. Шаблон и переменные.
3. Вкладка DNS.
4. Проверка раздела 4.

## Риски и edge cases

- **Устаревший адрес.** Сайт сменил адрес: первое обращение уходит на старый,
  следующее на новый. Средство: выключить Serve stale answers или очистить кэш.
- **Смена узла.** Ответы, полученные через прежний узел, остаются в кэше.
  Адрес ближайшего сервера сайта может не соответствовать новому узлу.
- **`cache.db`.** Файл открыт всегда, и при пробе узла. Рост файла от записей
  DNS исполнитель оценивает по числу записей и вносит оценку в спеку.
- **Рабочие пространства.** `cache.db` в слот не входит; кэш DNS общий.

## Верификация

Тесты (гонять только затронутые файлы):

- сборка: конфиг по умолчанию содержит три поля со значениями по умолчанию;
- сборка: изменённые значения попадают в конфиг;
- сборка: `dns_cache_capacity` вне границ не попадает в конфиг;
- вкладка DNS: три настройки видны, изменение помечает конфиг;
- эталоны конфига обновляются только на три новых поля.

Критерии приёмки:

1. Ядро принимает конфиг с тремя полями (`checkConfig`).
2. Разница эталонов конфига: только три новых поля.
