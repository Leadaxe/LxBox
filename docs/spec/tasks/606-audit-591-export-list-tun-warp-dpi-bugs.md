## 1. 002 — «Copy link» молчит на узле без ссылки

**Проблема.** Реестр контракта отказывает строить ссылку WireGuard-телу с
несколькими `peers`; эмиттер отдаёт `uri: ''`
(`app/lib/services/parser/engine/emitter.dart`, `_refuse()`).
`copyNodeUri` (`app/lib/screens/home/node_actions.dart`) при пустой ссылке
делает `return` без сообщения — пользователь жмёт «Copy link», и ничего не
происходит. Хуже: для WG-узла сначала спрашивается подтверждение про
приватный ключ, и только потом — тишина. Реестр (общий с лаунчером) не
меняется: отказ формата — его решение; чинится только сообщение.

**Решение.** Ссылка строится до диалога про ключ. Пустая ссылка → снэкбар
`This node cannot be shared as a link.`, буфер обмена не трогается, диалог
про ключ не показывается.

**Приёмка.** Виджет-тест `copy_node_uri_private_key_test.dart`: WG-узел с
двумя peers → снэкбар есть, диалога про ключ нет, буфер пуст.

## 2. 007 — узлы без префикса и чип источника

**Проблема (аудит).** Фильтр относит узлы без префикса к категории `custom`,
чипа `custom` нет (§095) → чип источника их прячет.

**Вердикт: не подтверждается как дефект.** Обещание фичи
(`007-NODE_LIST/FUNCTIONS/node-filters.md`, «Source — by tag prefix»):
«A node without a prefix … belongs to no chip: selecting a chip hides it, `!`
keeps it». Код ведёт себя ровно так. Выбор фильтра живёт только в памяти
(`NodeFilterViewModel._byDirection`), сохранённого до §095 `custom` в
выборе быть не может. Остаток — мёртвая категория `'custom'` в
`node_filter.dart` (без видимого эффекта). Не чинится.

## 3. 007 — перетаскивание при активном фильтре

**Проблема.** `onReorderItem` (`app/lib/screens/home/widgets/node_list.dart`)
собирает новый порядок из видимого `displayList` и отдаёт его
`commitManualReorder`, который заменяет `manualOrder` целиком. Скрытые
фильтром узлы (и скрытые detour-узлы) выпадают из ручного порядка, а
`HomeState._computeSortedNodes` ставит отсутствующие в порядке узлы в хвост.
Одно перетаскивание под фильтром «Германия» отправляет все остальные узлы в
конец списка.

**Решение.** Новый порядок = полный текущий порядок (`viewSortedNodes`, без
закреплённых), в котором двигается только перетащенный узел: он встаёт сразу
после ближайшего видимого соседа сверху по новой позиции (если соседа сверху
нет — перед ближайшим видимым соседом снизу; если видимых соседей нет — на
прежнее место). Остальные узлы, видимые и скрытые, сохраняют взаимный
порядок. Чистая функция `mergeManualReorder` в
`app/lib/screens/home/manual_reorder.dart`.

**Приёмка.** Юнит-тест `manual_reorder_test.dart`: при скрытых узлах
перетаскивание видимого не меняет позиции скрытых относительно друг друга и
не уводит их в хвост; без фильтра результат совпадает с прежним
(перестановка видимого списка).

## 4. 011 — Debug API `PUT /settings/tun_apps`: `count` до дедупа

**Проблема.** Ответ `count: pkgs.length` считает список до дедупа, хранилище
(`backup_tun.dart`, `_setTunApps`) пишет уникальные имена. `["a.b","a.b"]` →
`count: 2`, в хранении одно имя. Заглавная буква в шаблоне имени пакета
(аудит, вторая половина) — допустима правилами имён пакетов Android, не
дефект, не меняется.

**Решение.** Хэндлер дедупит (порядок первого вхождения) до ответа; `count` —
число уникальных имён.

**Приёмка.** Юнит-тест `tun_apps_put_count_test.dart`: дубли в запросе →
`count` = числу уникальных, совпадает с `getTunApps().packages.length`.

## 5. 015 — свой endpoint WARP без проверки `host:port`

**Проблема.** 025F обещала ошибку валидации до запроса при невалидном
endpoint; мастер (`app/lib/screens/warp_wizard_screen.dart`, `_register`)
отдаёт `_endpoint.text.trim()` в `addWarp` без проверки. Опечатка
(`1.2.3.4`, `host:99999`) уходит в узел, узел не поднимается.

**Решение.** `WarpAccount.isValidEndpoint(String)`: `host:port`, где host —
имя/IPv4 (`[A-Za-z0-9.-]+`) или IPv6 в скобках (`[…]`, как пишет пул,
`warp_endpoint_picker.dart`), port — 1…65535. Непустое невалидное поле →
снэкбар `Endpoint must be host:port`, регистрации нет. Пустое → дефолт, как
сейчас.

**Приёмка.** Юнит-тест `warp_endpoint_validation_test.dart`: дефолт, IPv4,
`[IPv6]:port`, имя — валидны; без порта, порт 0/65536/не число, голый IPv6
без скобок, пробел — невалидны.

## 6. 015 — карточка статуса регистрации не видна

**Проблема.** `_register` ставит `_result` (карточка `_StatusCard`), затем
`onAdded()` и `pop()` — карточка не успевает появиться. У MASQUE карточки
нет вовсе. Обещание фичи (`015-WARP/FUNCTIONS/wireguard-node.md`,
«Success»): снэкбар, пересборка, «the wizard closes» — закрытие и есть
обещанное поведение, карточка — мёртвый код.

Варианты были: A — удалить карточку и `_result` (обещание фичи не меняется);
B — не закрывать мастер, показать карточку (WG и MASQUE) и кнопку `Done`.

**Решение владельца (2026-09-30): A.** `_StatusCard`, поле `_result` и
неиспользуемые строки l10n (`Registered: WARP`, `Registered: WARP+`) удалены;
мастер закрывается сразу, как и раньше. Поведение не меняется, отдельного
теста нет (удалён код, до которого UI не доходил).

## 7. 016 — пинг/проба без фрагментации и mixed-case SNI

**Проблема.** Probe-конфиг (`app/lib/services/probe/probe_config.dart`,
`_assemble`) собирается мимо post-steps билдера: `applyTlsFragment` и
`applyMixedCaseSni` зовутся только в `build_config.dart`. Пинг показывает
«узел жив», хотя в туннеле узел идёт с фрагментацией/смешанным регистром
SNI и может не подниматься. Движок контракта не затронут — это post-steps
приложения. §363 (таблица решений) сознательно оставил вопрос отдельным
решением: «probe меряет доступность узла, не обфускацию».

Варианты были: A — применять оба post-steps в probe; B — только mixed-case
SNI; C — оставить как есть.

**Решение владельца (2026-09-30): A** — пинг проверяет тот же путь, что
трафик. `buildProbeConfig`/`buildProbeBatches` принимают `vars` (переменные
шаблона, `loadProbeVars()` → `SettingsStorage.getAllVars()`, сбой чтения →
без anti-DPI), `_assemble` в конце зовёт `applyTlsFragment` и
`applyMixedCaseSni` — те же функции, что `build_config.dart`. Семантика §574
сохранена: detour у main назначается и уступки (`yieldToBuildDetour`)
снимаются до шагов, а оба шага пропускают outbound с `detour`. Гейт §363
(REALITY) — внутри `applyMixedCaseSni`, общий. Движок контракта и ядро не
затронуты. Вызывающие: `probe_runner.dart`, `node_diagnostics_runner.dart`.

**Приёмка.** `test/probe/probe_anti_dpi_vars_test.dart`: поля `tls` probe-
конфига совпадают с туннельными post-steps над тем же телом (SNI — без учёта
регистра), регистр SNI действительно меняется, без переменных — как раньше,
у узла с detour `fragment` нет, у первого хопа есть.

## 8. 016 — `fragment_fallback_delay` не проверяется как duration

**Проблема.** `applyTlsFragment`
(`app/lib/services/builder/post_steps/tls_transforms.dart`) пишет
`vars['tls_fragment_fallback_delay'] ?? '500ms'` как есть: `500`, `fast`,
`1 s` уходят в конфиг, ядро отвергает конфиг целиком. Половина «пишется при
любой галке» не подтверждена: пишется только у узла, получившего
`fragment`/`record_fragment` — это и есть обещание фичи.

**Решение.** Значение, которое ядро не разберёт как duration
(`parseCoreDurationNanos` → `null`), заменяется умолчанием `500ms`.

**Приёмка.** Юнит-тест в `test/builder/` (тест tls-фрагментации): невалидная
задержка → в `tls.fragment_fallback_delay` пишется `500ms`; валидная
(`1s`, `250ms`) — как есть.
