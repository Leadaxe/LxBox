## Почему импорта в пустоту недостаточно

Импорт — слияние по идентичности, а не замена. Проверить слияние импортом в
пустое состояние нельзя: там слияние и замена дают ОДИН И ТОТ ЖЕ итог, а
стороны, разошедшиеся в ключе слияния, остаются неразличимы. Кейс, у которого
нет предсостояния, не отличит «совпавшая запись осталась локальной» от
«запись перезаписана файлом» и «локальная, которой в файле нет, сохранена» от
«раздел заменён целиком».

## Конвенция предсостояния

Кейс корпуса бэкапа может положить рядом `<case>.pre.backup.json`. Порядок
раннера строгий:

1. пустое состояние;
2. импорт `<case>.pre.backup.json`;
3. слияние `<case>.backup.json` в получившееся состояние;
4. сверка с `<case>.expected.json`.

Файла `pre` нет → импорт идёт в пустое состояние, как во всех прежних кейсах.

Две вещи, которые легко нарушить и обе стоили бы красного корпуса:

- **`<case>.pre.backup.json` сам кейсом НЕ является.** Раннер отсеивает его из
  списка кейсов, иначе погонит предсостояние отдельным прогоном и будет искать
  несуществующий `<case>.pre.expected.json`.
- **Предупреждения предсостояния в сверку не идут.** Оно декорация сцены, а не
  предмет кейса; сверяются только предупреждения основного импорта.

## Состояние в раннере — те же чистые функции, что у приложения

«Состояние» раннера — то же, что у приложения: список источников
`List<ServerList>`. Собирается он теми же чистыми функциями, которыми его
собирает импорт (`_applySources` в `app/lib/screens/backup_screen.dart`):

```
mergeBackupSubscriptions(state, file.subscriptions).lists
  → mergeBackupServers(…, file.servers).lists
```

Раннер отличается от приложения ровно тем, что состояние держит в списке, а не
в storage. Норма слияния при этом живёт в одном месте на оба вызова: раннер,
повторяющий её своей копией, гарантировал бы только сам себя.

**Выносить в чистые функции ничего не пришлось.** §401 и §405 уже вынесли обе
секции, которых касается кейс, — `mergeBackupSubscriptions` и
`mergeBackupServers` (`app/lib/services/lx_backup.dart`), — и в
`backup_screen.dart` осталось только чтение и запись storage. Остальные секции
импорта в кейсе не участвуют: `rules[]` замещаются целиком (§9 п.7), DNS
сливается своей чистой функцией `applyDnsBackup` (`dns_backup.dart`), `warp[]`
— слоты по типу.

## Поля ожидания слияния

Оба необязательны: отсутствие ключа значит «не проверяем».

`subscriptions` — **исчерпывающая** карта `url → {label, prefix, postfix,
enabled?, nodes?, pending_disabled?}`. Исчерпывающая не для красоты: подписка,
которой в ожиданиях нет, — это либо не оставленная локальная, либо задвоенная,
и обе ошибки видны только сверкой всего набора, а не поиском отдельных ключей.

- `nodes` — сырые теги узлов, которые обязаны пережить слияние: состав
  локальной подписки в файл не едет и потеряться не вправе;
- `pending_disabled` — отметки выключения, сверяются отсортированными: это
  объединение двух множеств, порядок в нём смысла не несёт;
- `postfix` у LxBox поля не имеет вовсе (тег источника здесь только префикс),
  поэтому сверяется с пустой строкой — ожидание корпуса пишет `""` ровно в том
  же смысле «постфикса нет».

`root_servers` — теги корневых одиночных узлов **в порядке состояния**:
совпавшие держат локальную позицию, новые встают в конец. Дедуп по телу
проверяется именно ОТСУТСТВИЕМ второй записи в этом списке, а не наличием
первой.

Ожидание `folders` теперь читается из СОСТОЯНИЯ после слияния, а не из разбора
файла. До 0.12.5 папку описывал один файл целиком; с предсостоянием её
половина приезжает первым импортом, и разбор второго о ней уже ничего не
знает.

## Кейс `merge_sources_by_url`

Единственный на сегодня кейс с предсостоянием; фиксирует все четыре ключа
слияния разом.

| Сцена (`pre`) | Файл кейса | Итог |
|---|---|---|
| подписки A и B (у B префикс `b:`, отметка `local-mark`) | B с другими настройками (`B new`, `bb:`, отметка `x`), подписка C | A, B, C: A нетронута, B держит позицию и `id`, настройки взяла из файла, отметки ОБЪЕДИНИЛИСЬ (`local-mark` + `x`), C в конец |
| корневой сервер S1 (`uri`) | тот же S1 под тегом `S1-renamed-elsewhere`; он же с другим `#фрагментом`; новый S2 | S1, S3, S2 — дубли узнаны по телу и пропущены без warning |
| корневой сервер S3 (`config_json`) | `S3-reordered` — то же тело с переставленными ключами и своими `tag`/`detour` внутри JSON | второй записи нет: порядок ключей не значим, `tag`/`detour` из сравнения сняты |
| папка Proton с членом P1 | Proton с `P1-elsewhere` (тело P1) и P2 | Proton = `[P1, P2]` |

Предупреждений нет вовсе: ни одна из этих операций потерей не является.

Кейс прошёл **без правок `lib/`**: канон тела и регистрозависимость тегов
завёл §406, слияние подписок и серверов — §401/§405. Раннер лишь стал это
проверять.

Каждая из трёх ветвей дедупа проверена отключением — без неё кейс краснеет:

| Что сломать | Что покажет кейс |
|---|---|
| дедуп по сырой строке вместо канона | `root_servers` = `[S1, S3, S2, S1-other-fragment, S3-reordered]` |
| отметки `disabled` замещать вместо объединения | `pending_disabled` = `[x]` вместо `[local-mark, x]` |
| дедуп члена папки снять | Proton = `[P1, P1, P2]` |
| локальные подписки не сохранять | набор подписок теряет A |

## Норма §9 п.2: тело берётся из ИСХОДНИКА

Проверено по коду и подтверждено: канон считается от `rawBody` одиночного
сервера (`lx_backup.dart`, множество тел локальных узлов) и от `raw` члена
папки — то есть от исходника записи, а не от материализованного outbound'а.
Материализованный узел в сравнение не попадает ни в одной из трёх точек:
`nodes` / `NodeSpec` merge не читает вовсе.

Частный случай, который норма называет отдельно, у нас тоже сходится: у
сервера, заведённого руками через мастер (SOCKS/HTTP), исходника-URI нет, и
`rawBody` ему пишется эмитированным JSON-outbound'ом. Это ровно тот
«материализованное тело — ключ у записи, у которой исходника нет вовсе», о
котором говорит §9, и сравнение остаётся симметричным: `canonicalNodeBody`
снимает верхнеуровневые `tag`/`detour` с обеих сторон.

## Норма §9 п.6: `warp[]` при занятом слоте

Проверено по коду `backup_screen.dart` / `warp/warp_backup.dart`: приехавший
аккаунт при занятом слоте пропускается `continue` — **молча**, без warning'а;
при пустом слоте разбирается и записывается. У LxBox аккаунты — слоты по типу
(`wg` и `masque`), и это частный случай ключа аккаунта из нормы: занятый слот
и есть «аккаунт с таким ключом уже стоит». Правок не потребовалось.
