# §379 — versionCode из версии, а не из числа коммитов

| Поле | Значение |
|------|----------|
| Статус | Спека |
| Дата старта | 2026-08-05 |
| Связанные spec'ы | [§065](065-version-from-tag.md) — версия вычисляется из тега; [§186](186-local-build-vc-pin-to-tag.md) — пин локального vc к тегу; [`RELEASE_PROCESS.md` §2.2](../../RELEASE_PROCESS.md) — текущая схема; [`FDROID.md`](../../FDROID.md) — потребитель схемы |

## Проблема

`versionCode` вычисляется как `git rev-list --count` — число коммитов в
истории. Значение зависит от того, сколько раз кто-то закоммитил, а не от
того, какая это версия. Из-за этого:

**1. Версию нельзя прочитать из исходников.** `pubspec.yaml` в git держит
placeholder (`2.19.2-dev.57+1491` на момент написания), реальная версия
пишется туда прямо перед `flutter build` и никуда не коммитится. Прочитать
её из тега нельзя: `rev-list` — не функция от `v2.19.7`.

Это блокирует автообновление в F-Droid. Их `checkupdates` читает версию из
репозитория на теге и падает с *Couldn't find any version information*
(проверено), поэтому в метаданных стоит `UpdateCheckMode: None` и каждая
версия требует ручного MR. Рецензент
([fdroiddata!44731](https://gitlab.com/fdroid/fdroiddata/-/merge_requests/44731))
просил это починить.

**2. Замкнутый круг при попытке закоммитить.** Записать `2.19.7+1606` в
pubspec и поставить тег на этот же коммит нельзя: коммит увеличивает
`rev-list` до 1607, и записанное значение сразу становится неверным.

**3. Две несовместимые схемы.** На GitHub `--split-per-abi` заставляет
Flutter-плагин переписать код как `ABI * 1000 + versionCode`
(`FlutterPlugin.kt:623`), в F-Droid этого флага нет и код берётся как есть.
Для 2.19.7 одна и та же сборка получает 3606 на GitHub и 16062 в F-Droid.

## Решение

Считать `versionCode` из самой версии — детерминированно, без обращения к
истории.

```
versionCode = ((major × 10000 + minor × 100 + patch) × 100 + PRE) × 10 + ABI
```

Разбор кода `21908512`:

```
 2  19  08  51  2
 │   │   │   │  └── ABI    архитектура
 │   │   │   └───── PRE    стадия
 │   │   └───────── patch
 │   └───────────── minor
 └───────────────── major
```

### Поля

| Поле | Диапазон | Источник | Когда меняется |
|------|----------|----------|----------------|
| major | 1–213 | тег | ломающие изменения |
| minor | 00–99 | тег | новые фичи |
| patch | 00–99 | тег | обычный релиз (правило проекта — по умолчанию бампать только patch) |
| PRE | 01–49 | суффикс `-rc.N` | release candidate перед релизом |
| | **50** | суффикс отсутствует | **финальный релиз** |
| | 51–98 | суффикс `-hotfixN` | заплатка к вышедшему релизу |
| | 99 | — | свободно |
| ABI | 0 / 1 / 2 / 4 | таргет сборки | universal / arm32 / arm64 / x86_64 |

### Когда `-hotfixN`, а когда бамп patch

`-hotfixN` — только если **релиз что-то сломал**: регрессия или критичная
поломка в уже выпущенной версии (краш на старте, отвалившийся протокол,
неработающее обновление). Смысл суффикса — «заплатка к конкретному релизу»,
а не «следующая версия».

Обычные исправления, даже срочные, идут бампом patch, как и раньше:
`v2.15.3` → `v2.15.4`.

### Порядок выпусков

| Событие | Тег | PRE | Код arm64 |
|---|---|---|---|
| кандидат | `v2.19.8-rc.1` | 01 | 21908**01**2 |
| кандидат | `v2.19.8-rc.2` | 02 | 21908**02**2 |
| **релиз** | `v2.19.8` | **50** | 21908**50**2 |
| регрессия | `v2.19.8-hotfix1` | 51 | 21908**51**2 |
| следующий | `v2.19.9-rc.1` | 01 | 21909**01**2 |

Строго возрастает — проверено сквозняком от 2.19.7 до 3.0.0.

### Почему ABI последней цифрой

Каталог F-Droid сортирует версии по `versionCode`. При схеме Flutter
(`ABI × 1000 + code`) архитектура попадает в старшие разряды, и x86_64-сборка
старого релиза оказывается «новее» armv7-сборки нового — список едет
вперемешку. Прямое требование рецензента.

Побочный эффект: **`--split-per-abi` придётся убрать**, иначе Flutter снова
домножит ABI поверх нашего числа. Вместо одного прогона — три отдельных с
`--target-platform` и `LXBOX_ABI_FILTER`, как уже сделано в метаданных
F-Droid.

### Почему universal — 0

Universal ставится на любую архитектуру, поэтому в рамках одной версии он
наименее специфичен: 0 ставит его ниже всех сплитов. Обновления это не
затрагивает — разница между версиями (10 000) на два порядка больше разницы
между ABI (максимум 4), поэтому любой переход вперёд по версии монотонен при
любом раскладе ABI: universal 2.19.9 несёт 21909**50**0, arm64 2.19.8 —
21908**50**2.

Запрещён единственный переход: со сплита на universal **той же** версии.
Это не обновление, а ручная замена того же кода приложения другой упаковкой —
делается через удаление.

## Что меняется

| Файл | Что |
|------|-----|
| `.github/workflows/ci.yml` | `BUILD_NUMBER` считается из версии, а не `rev-list`; вместо `--split-per-abi` — отдельный прогон на таргет (три сплита + universal) |
| `scripts/build-local-apk.sh` | та же формула; пин к тегу (§186) сохраняется |
| `app/pubspec.yaml` | реальная версия коммитится при релизе вместо placeholder |
| `docs/RELEASE_PROCESS.md` | описание схемы в §2.2 |
| `docs/FDROID.md` | §1.1 и §4 — расчёт кода |
| метаданные F-Droid | `UpdateCheckMode: Tags` + `UpdateCheckData` + `VercodeOperation` |

### Локальные сборки

`build-local-apk.sh` переводится на ту же формулу и продолжает пинить код к
**последнему релизному тегу** — как сейчас. То есть dev-сборка получает тот
же `versionCode`, что релиз этой версии, а отличается только `versionName`
(`2.19.7-dev.15`).

Это сохраняет поведение §186: равный код Android не блокирует, поэтому
`install -r` проходит в обе стороны и релиз с GitHub ставится поверх dev-сборки
без удаления. Если оставить скрипт на `rev-list`, а CI перевести на новую
формулу, коды разойдутся (1606 против 21907502) и это сломается.

### Метаданные F-Droid

После перехода:

```yaml
UpdateCheckMode: Tags
UpdateCheckData: app/pubspec.yaml|version:\s.+\+(\d+)|.|version:\s(.+)\+
VercodeOperation:
  - '%c * 10 + 1'
  - '%c * 10 + 2'
  - '%c * 10 + 4'
AutoUpdateMode: Version v%v
```

Прецедент в их каталоге — `app.atrium`: Flutter, `%c * 10 + ABI`, читает
`app/pubspec.yaml`. Один в один наш случай.

## Совместимость

**Монотонность соблюдается.** Текущий arm64 несёт 3606, новая схема даёт
21907502 — больше, обновления у пользователей не сломаются. Проверено по
всем тегам от v2.19.4.

Переход **необратим**: понизить `versionCode` Android не позволит никогда.

## Границы

| Что | Предел | Сейчас |
|---|---|---|
| major | 213 (дальше int32) | 2 |
| minor, patch | 99 | 19, 7 |
| rc на версию | 49 | не использовались |
| hotfix на релиз | 48 | не использовались |

Минимальное значение — 1, отрицательных не бывает: все слагаемые
неотрицательны. Это важно, поскольку Android отвергает отрицательный
`versionCode`.

## Проверка

1. `git tag v2.19.8-rc.1` → APK несёт 21908012 (arm64).
2. Тег без суффикса → 21908502.
3. `apkanalyzer manifest print` на всех APK релиза: коды различаются последней
   цифрой (0/1/2/4), совпадают в остальном.
4. Локальная сборка на коммите после тега: `versionName` содержит `-dev.N`,
   `versionCode` равен коду тега.
5. `install -r` релизного APK поверх локальной сборки и обратно — проходит
   без удаления приложения.
6. В метаданных F-Droid `fdroid checkupdates com.leadaxe.lxbox` находит
   версию вместо *Couldn't find any version information*.

## Открытые вопросы

- **Порядок выката.** Схема меняет коды GitHub-релизов скачком
  (3606 → 21907502). Стоит ли выпускать это отдельным релизом или совместить
  с очередным — решать при реализации.
