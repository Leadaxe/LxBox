## Проблема

Элемент подписки, не ставший узлом (битый транспорт `malformed_stream`,
протокол вне реестра `unsupported_protocol`, недостижимый релей и т. п.),
сегодня оставляет причину предупреждением на **чужом** узле: первом выжившем
того же элемента, иначе первом узле подписки (§404 P3, §321 P5). Человек
открывает рабочий узел и видит ошибку, которая к нему не относится. Корпус
контракта и лаунчер ждут другого: запись только в `dropped[]` конверта
подписки, у соседа предупреждений нет.

**Решение владельца 26.09.2026 — вариант 2:** отбраковка записывается только
в `dropped[]` на уровне подписки, сосед чист; отбраковки показываются в сводке
подписки (экран источника), а не на узле.

## Диагностика

- Норма P3/P5 в коде: `app/lib/services/parser/json_parsers.dart` (~:188–200,
  ~:335–350 — `unsupported`, `rejected`, `unread` вешаются на первого
  выжившего), `app/lib/services/parser/parse_all.dart` (~:390–404 — остаток
  `dropped` на первый узел подписки; D-088 уже кладёт всё в `out`).
- UI сегодня: `dropped[]` виден только в баннере ошибки ввода
  (`subscriptions_screen/widgets/parse_input_error_banner.dart`,
  `subscriptions_screen.dart:574` → `showNodeWarningsSheet`) — то есть когда
  разбор дал ошибку/пустой результат. Для непустой подписки записи `dropped`
  пользователю не показываются: `subscription_detail_screen.dart` слова
  `dropped` не содержит. Хранится ли `dropped` у источника между разборами —
  проверить (`UiMsg.dropped`, модель источника/подписки, кодек хранения).

## Решение

1. **Разбор:** снять перенос причин отбраковки на соседа (P3 и P5 — один
   механизм): `unsupported`/`rejected`/`unread` в `json_parsers.dart` и
   остаток `dropped` в `parse_all.dart` больше не попадают в `warnings` узла.
   `dropped[]` конверта остаётся единственным местом (D-088 уже так). Коды и
   параметры записей не менять. Тесты, закреплявшие P3/P5 на соседе, снять или
   переписать на «сосед чист, запись в dropped».
2. **Хранение:** `dropped[]` последнего разбора хранится у источника
   (подписки), чтобы сводка показывала его и после перезапуска; при новом
   разборе заменяется. Форму хранения согласовать с существующим кодеком
   источника; в бэкап не едет (производное, восстанавливается разбором) —
   сверить с BACKUP.md.
3. **UI, сводка источника:** на экране подписки
   (`subscription_detail_screen.dart`) строка «N entries dropped» с переходом в
   ту же шторку `showNodeWarningsSheet` (тексты по кодам, как сейчас). На
   карточке источника в списке — счётчик, если > 0. Строки только английские,
   без §NNN. Баннер ошибки ввода остаётся для пустого результата.
4. Документация: параграф в спеке, где описан §404 P3 (найти по grep в
   docs/spec), `CHANGELOG.md` Unreleased — видимое изменение поведения.

Правило кампании: имён схем/протоколов в Dart не добавлять.

## Риски и edge cases

- Подписка, где не выжил никто: как сейчас — баннер ошибки + шторка.
- Один и тот же элемент отбракован по нескольким причинам — одна запись на
  причину, дедуп по (код, параметры), как в конверте.
- Отбраковка детур-владельца (P3 «недостижимый релей») тоже уходит в
  `dropped`, зависимые узлы своё предупреждение о недостижимом релее сохраняют,
  если оно про них самих.

По одному файлу: тесты `json_parsers_test`, `parse_all`-тесты (найти по имени),

виджет-тест экрана подписки на строку «dropped» и открытие шторки. Полный
прогон — CI.

### Итог

1. **Разбор.** `json_parsers.dart`: списки `unsupported`/`rejected`/`unread`
   сняты, каждая отбраковка записи сразу идёт в `dropped` (D-088). Вердикт
   секции без причины и битая форма (`catch`) — `form_unrecognized` с тегом
   записи; `protocol_unsupported` дописывает `scheme` из поля `protocol`
   (движок ставит код без параметра, а текст реестра его ждёт).
   `parse_all.dart`: перенос остатка на первый узел подписки снят.
   `singbox_config.dart`: тот же механизм §368 §3.5 — `parseSingboxConfigs`
   получил `dropped:`, тип вне ядра → `protocol_unsupported` (`scheme` = `type`),
   битая форма → `form_unrecognized`. Имён схем в Dart не добавлено.
2. **Хранение.** `SubscriptionServers.dropped` — рядом с `nodes` и так же
   производно: в кодек записи, бэкап и равенство не входит. Ставится на
   refresh, смене источника, файловых подписках (вставка, файл) и при
   регидрации из кэша тела после перезапуска (тот же разбор). Вид —
   `summaryDropped()` (`node_warning.dart`): по старшему уровню, секреты
   скрыты. Пустой результат refresh прежний `dropped` не трогает — он
   согласован с показанными узлами прошлого разбора.
3. **UI.** `SubscriptionMeta` — строка «N entries dropped» (иконка ошибки,
   шеврон) → `showNodeWarningsSheet`. Карточка в списке — «N dropped».
   Ключи — `ru`/`zh` каталоги. Баннер ошибки ввода для пустого результата
   не менялся.
4. **Документы.** Пометка «Пересмотрено §561» в §404 п. 5, §321 P5,
   §368 §3.5 и таблице носителей; строка CHANGELOG (Changed).

## Нерешённое / follow-up

- **Закрыто задачей 570 (`13f0c8b2`):** шторка пишет «Entry: <тег>» по
  `NodeWarning.ownerTag`. Было: шторка не называет запись, к которой относится причина (`ownerTag`):
  текст по коду, как у узла. Если понадобится «какая именно запись» —
  отдельная правка `NodeNotificationsView`.
- **Закрыто задачей 570 (`b054db6a`):** сводка сводит одинаковые записи по
  (код, параметры, владелец); конверт `dropped[]` разбора не трогается.
  Запись без своего владельца получает имя записи источника (контейнер
  `.conf`, строка `vpn://` с номером контейнера). Было: дедупа между
  элементами нет (как и в конверте): одинаковая запись в двух элементах даёт
  две строки `dropped`.
- **Закрыто задачей 570 (`b054db6a`):** пустой refresh кладёт свои причины
  в сводку (узлы остаются от прошлого разбора; после перезапуска сводку
  восстанавливает разбор кэша прежнего тела). Было: отбраковка пустого
  refresh (0 узлов) в сводку не попадает — сводка
  держит разбор, чьи узлы показаны. Причины пустого ответа видны в логе.
- **Закрыто задачей 570 (`13f0c8b2`):** диалог вставки показывает
  «N entries will be skipped» и шторку причин. Было: счёт отбраковок подписки считается по боевому проходу; в диалоге
  импорта вставки (`clipboard_analysis`) они по-прежнему не показываются.
