## Problem

Код и доки описывают механизм прохода `ip=quic` как «поточный DPI не собирает CRYPTO-фреймы,
берёт первый, парсит мусор и fail-open». Это **гипотеза**, записанная как факт. Против неё
есть логичное возражение: fail-open на неразобранное пропускал бы и `jc`-шум, а шум без `i1`
на том же DPI даёт Timeout (исходная точка §143/§146).

Device-фактов у нас ровно три (§146 §2, 17.06, один телефон, один оператор):
один линейный CRYPTO offset 0 → Timeout; случайная нарезка короткого ~60б CH → Timeout;
out-of-order 6 фрагментов, реалистичный 294б CH → PASS. **Реалистичный CH, нарезанный по
порядку** (аналог `record_fragment` для TCP), не проверялся.

## Diagnosis

Что отличает out-of-order Initial от шума для классификатора: внешний слой криптографически
проверяем (Initial-ключи выводятся из DCID, AEAD-тег сходится), падает только разбор TLS внутри.
Что отличает его от линейного — неизвестно; кандидаты (009 §8): запуск машины состояний QUIC
с ожиданием ответного Initial; политика «читаемый QUIC к WARP-порту»; ответ настоящего
QUIC-responder Cloudflare.

Прогон с in-order нарезкой разделяет: **«не читается SNI»** (I1, offset первого фрейма ≠ 0)
от **«много фрагментов + PING/PADDING»** (форма пакета). В in-order вариантах форма та же,
что у рабочего, отличается только порядок.

## Solution

Три узла, один WARP-аккаунт (зарегистрирован 08.10.2026 через `api.devices.cloudflare.com`),
один endpoint `162.159.192.1:2408`, одинаковый пресет `jc=4 jmin=40 jmax=70 s1=s2=0 h1..h4=1..4`,
без `Reserved` (как рабочие конфиги §142). Отличается **только `I1`**, профиль chrome, 6 CRYPTO + 2 PING + PADDING, 1250 байт, та же крипта RFC 9001:

| Плечо | I1 | Что проверяет |
|---|---|---|
| **A** `inorder_randomcuts` | CRYPTO по порядку, offset 0 первым, случайные точки разреза; SNI может лечь на стык | «штатный fragment»: читаемо DPI с дешёвой конкатенацией, не читаемо DPI «только первый фрейм» |
| **B** `inorder_sni_in_first` | по порядку, первый фрейм 97 байт содержит SNI целиком | читаемо любым DPI, даже без сборки |
| **C** `control_outoforder` | боевой генератор ядра (`masqueI1`), первый фрейм offset 24 | контроль, ожидается PASS как в §146 |

Два набора SNI, по три плеча в каждом: `apteka.ru` (9 символов) и `wartune.mail.ru`
(15 символов, проверка длинного имени). Generic ClientHello в обоих случаях 294 байта:
расширение padding компенсирует длину SNI, так что форма пакета у наборов одинаковая.
Фактическая раскладка фреймов — `617-exp-vectors/i1_arms_walk.txt` и `i1_arms_walk_wartune.txt`,
CPS-блобы — `617-exp-vectors/i1_*.cps` (приманки, секретов не содержат).
Конфиги с приватным ключом (`exp617_*.conf`) переданы владельцу вне репозитория.

Генерация: временный Go-тест в пакете `transport/wireguard` ядра (тег `with_awg`), повторяющий
`buildInitialPacket` с планом, у которого перестановка заменена тождественной (A) или с
нарезкой, где первый разрез строго после SNI (B). В ядро ничего не добавлялось.

## Risks and edge cases

- DPI запоминает состояние по IP/5-tuple: после неудачного плеча следующее может быть
  «наказано». Между плечами менять порт в endpoint нельзя (переменная), поэтому пауза
  и повтор C после каждого FAIL.
- Один телефон, один оператор, один день: вывод только про этот DPI.
- Cloudflare на `:2408` может отвечать на QUIC Initial (H1 из 009 §8); этот прогон H1 не
  отделяет. Для неё нужен отдельный T3: тот же i1 на IP без QUIC-responder.

## Verification

Процедура на тест-телефоне, LTE, VPN хоста выключен:

1. Импортировать шесть `.conf` как узлы (ввод INI), не менять endpoint и пресет.
2. Порядок прогонов в каждом наборе SNI: C → A → C → B → C, каждое плечо ≥3 замера delay-тестом, пауза 30 с между плечами.
3. PASS = есть delay; FAIL = Timeout. Записать миллисекунды.

Чтение результата:

| A | B | C | Вывод |
|---|---|---|---|
| PASS | PASS | PASS | Порядок ни при чём, работает форма (фрагменты + PING/PADDING). Объяснение в коде и доках ложное, ядро можно упростить до in-order, SNI читаем. |
| FAIL | FAIL | PASS | Блокирует именно читаемость начала ClientHello (I1). Объяснение остаётся гипотезой, но инвариант I1 подтверждён как load-bearing. |
| PASS | FAIL | PASS | DPI читает только первый фрейм; SNI на стыке спасает, целый SNI в первом фрейме режется → это SNI-политика к WARP-адресу, а не порядок. |
| любое | любое | FAIL | Стенд или DPI изменились с 17.06, результат плеч не интерпретировать; повторить позже. |

**Эмулятор** (`emulator-5554`, приложение 2.25.10-dev.31, ядро lx.12, папка `EXP-617`,
headless `/folders/{id}/probe` на `https://1.1.1.1`, 12 с, три раунда):

| Плечо | Раунды 1/2/3 |
|---|---|
| P чистый WG | failed ×3 (`context deadline exceeded`) |
| J только junk | failed ×3 (`Head "https://1.1.1.1": context deadline exceeded`) |
| A, B, C (оба SNI) | ok ×3 каждое, 5,0–5,7 с |

Чтение:

- **Проводной DPI не отвечает на вопрос §146.** Он режет голый WireGuard-handshake к WARP
  (P: 0 из 9 на двух стендах), но пропускает любое плечо с AWG-префиксом, включая in-order A и B
  с читаемым SNI. Порядок CRYPTO-фреймов на этом стенде не несёт нагрузки.
- **Junk без i1 нативно проходит (8/9), на эмуляторе нет (0/3).** Расхождение не разобрано.
  Кандидаты: другой код ядра (lx.8 vs lx.12), путь через NAT эмулятора, артефакт первого
  init на эмуляторе (см. ниже). Нужен разбор core-лога пробы J на эмуляторе.
- **Задержка 5,0–5,7 с у всех успешных плеч на эмуляторе** совпадает с REKEY_TIMEOUT WireGuard:
  первый init теряется, проходит повтор. Нативно те же плечи дают 65–130 мс. Вероятнее всего это
  известный артефакт эмулятора (`disabled UDP GSO … checksum offload` на первом init), не DPI;
  не проверено.
- Вопрос «читаемый in-order против out-of-order» остаётся открытым до прогона на LTE-стенде §146.
  Конфиги для него готовы (шесть плеч + P + J).

(`617-exp-vectors/native_mac_results_v2_own_accounts.txt`): P 0/2, J 2/2, A 5/5, B 5/5, C 11/11,

бинаря (lx.8 и lx.12 одинаково), ни от аккаунта. Debug-лог P: `sending handshake initiation`
четыре раза, ответа нет ни разу.

**Эмулятор, `tcpdump -i any udp port 2408` (root на AVD):**

| Плечо | На проводе |
|---|---|
| P | 3× инициация 148 байт наружу, входящих нет. Handshake глушится. |
| J | 4 junk + 148; первая попытка без ответа, повтор через 5 с получает 92 (response); дальше SYN/SYN-ACK через туннель проходят, ClientHello 1296 уходит, **входящих 1312 нет** — HEAD висит до таймаута. |
| A | i1 1250 + 4 junk + 148, ответ 92 через ~1 с, затем полный TLS: входящие 1312 ×3, HEAD ok. |

Провал J на эмуляторе — не на рукопожатии: сессия поднимается, рвётся возврат больших пакетов.
Нативно с того же адреса J проходит целиком (тело `cdn-cgi/trace` получено). Нативный захват
невозможен без sudo (нет BPF), сравнить дословно нельзя. Три ранних «ok» P на эмуляторе
(375/640/422 мс, без захвата) объяснения не имеют; при захвате P падал 3 из 3.

**Групповая проба на одном аккаунте непригодна:** сервер WireGuard держит один адрес на ключ,
одновременные рукопожатия воруют друг у друга сессию. Дальше только один узел на аккаунт и
последовательно.

**Телефон (LTE Tele2, CPH2411):** стенд готов, Debug API отвечает, но телефон заблокирован,
токен с экрана снять нельзя. Прогон не делался. Конфиги v2 на восьми аккаунтах лежат в scratchpad.

| Плечо | apteka.ru | wartune.mail.ru |
|---|---|---|
| P чистый WG | fail 0/2 (`context deadline exceeded`) | — |
| J только junk | fail 0/2 (`Head … deadline exceeded`) | — |
| C контроль out-of-order | ok 6/6, 211–424 мс | ok 4/4, 207–248 мс |
| A in-order, случайная нарезка | ok 3/3, 230–370 мс | ok 3/3, 185–231 мс |
| B in-order, SNI целиком в первом фрейме | ok 3/3, 220–287 мс | ok 3/3, 226–236 мс |

Стенд различает: голый WG и junk режутся, как в §146. Но in-order A и B проходят наравне с C.
Это строка «PASS / PASS / PASS» таблицы чтения выше: **нагрузку несёт сам QUIC Initial впереди
потока (валидный заголовок, выводимые ключи, сходящийся AEAD), а не порядок фрагментов.**
Инвариант I1 (первый CRYPTO с offset ≠ 0) не load-bearing. Читаемый SNI не мешает.

Что это меняет:

1. Шапка `transport/wireguard/quic_initial_awg.go` («WHY OUT-OF-ORDER WORKS», fail-open) и
   009 §3.1 «Почему так» — ложны как механизм; переписать: device-факт только таблица A/B,
   механизм неизвестен, кандидаты из 009 §8.
2. `amneziawg-explained.ru.md` §3.3: убрать «разрезан и отправлен не по порядку… DPI парсит
   мусор» как объяснение; оставить «QUIC Initial с ClientHello и SNI=`id`», отметить, что
   перемешивание сохранено как запас против DPI с буфером сборки, но на известных стендах
   не требуется.
3. Ядро можно оставить out-of-order (вреда нет, запас есть) либо дать ручку in-order; это
   решение владельца, не этой задачи.
4. §146 вывод «причина — строго линейность» опровергнут частично: линейный **один** фрейм там
   падал, но многофрагментный in-order с теми же PING/PADDING проходит. Различие между
   «один фрейм» и «шесть по порядку» не проверялось здесь; если важно, отдельное плечо L.

## T4 — плечо L (один линейный CRYPTO), 08.10.2026 вечер — НЕ ИНТЕРПРЕТИРУЕТСЯ

По решению владельца (через агента ядра) до правок ядра гонялось плечо **L**: i1 = QUIC Initial 1250 байт,
один CRYPTO offset 0 со всем ClientHello (294 байта), без PING, только PADDING; и **L+ping**: тот же
один фрейм + 2 PING + PADDING-runs как в боевом плане. Блобы `617-exp-vectors/i1_L*_*.cps`,
раскладка `i1_arms_walk_L.txt`. Тот же стенд и правила, свой аккаунт на узел, 20 проб
(`617-exp-vectors/phone_lte_tele2_L_run_results.txt`): **все 20 ok, включая P (чистый WG, 213 мс)**.

Сразу после сеанса, тем же способом: P fail, J fail, P fail, J fail. То есть во время L-сеанса стенд
был в окне, когда пропускал и голый WireGuard, а через несколько минут снова режет. Результаты L и
L+ping за этот сеанс **не засчитываются**: контроль P прошёл.

Что это значит для методики: контроль P (а лучше и J) обязан идти **в каждом раунде рядом с
проверяемым плечом**, а не один раз на сеанс. Сеанс, где P прошёл хоть раз, бракуется целиком.
Утренний LTE-прогон (26 проб) этому критерию удовлетворяет: P 0/2 и J 0/2 стояли между плечами A/B/C.

Повтор T4: порядок на каждый раунд `P, L, C, P, Lp, C`, оба SNI, не меньше трёх раундов; при
первом же `P ok` раунд в брак и пауза ≥10 мин.
