# Localization — a guide for translators and developers (§279 / §285)

How localization works in L×Box and what to touch for the usual tasks: a new
language, a new string, editing an existing one, translating the template, a
hotfix. The architecture and the decisions behind it are in
[the §279 spec](spec/features/279%20localization/spec.md) plus
[the getLocalText review](spec/features/279%20localization/getlocaltext.md); the
subsystem inside the codebase is described in
[ARCHITECTURE.md → Localization](ARCHITECTURE.md#localization-l10n-279--285); the
checkers live in [`app/tool/l10n/README.md`](../app/tool/l10n/README.md).

Languages in the first version: **en** (the base, the source of truth) and **ru**.

## The model: natural keys (§285)

Since §285 there are no artificial ARB keys (`commonCancel` and the like) any
more. **The English text at the call site IS the key**; the translation comes
from `assets/l10n/<tag>/ui.json`, and a miss (no dictionary, no key, no form)
degrades into the English key itself with the arguments substituted:

```dart
getLocalText.s("Cancel")                       // → "Отмена" (ru) / "Cancel" (en, fallback)
getLocalText.s("Connected to %s", host)         // printf substitution
getLocalText.plural("%d servers", n)            // plural
getLocalText.s(1, "OK")                         // special form no. 1 (special["1"])
getLocalText.plural(1, "%d items", n)           // special form plus plural
```

`getLocalText` is a global getter (`services/l10n/locale_controller.dart`), and
the active locale is tracked by `LocaleController` (which reloads the dictionary
as part of the language-switch pipeline). No BuildContext is needed, so it is
available from services, controllers and parsers. `GetLocalText.en` is the
English renderer pinned for machine-facing surfaces.

The engine is `services/l10n/get_local_text.dart` (printf `%s/%d/%1$s/%%`, the
form index, fallback to the key); the plural strategies live in
`plural_resolver.dart` (`RuPluralResolver` = CLDR one/few/many/other,
`EnPluralResolver` = one/other).

### The dictionary format, `assets/l10n/<tag>/ui.json`

A flat map of `englishKey → entry`. There are three kinds of entry:

```jsonc
// a plain string
"Save": { "value": "Сохранить" },

// a plural: value is an object holding every form of the language's resolver
// (ru: one/few/many/other)
"%d servers": {
  "value": {
    "one":   "%d сервер",
    "few":   "%d сервера",
    "many":  "%d серверов",
    "other": "%d сервера"
  }
},

// a collision: one English text maps to different Russian translations
// depending on context. The root value is form 0; special["N"] is special form
// N, invoked as getLocalText.s(N, "...") / .plural(N, "...", n).
"OK": {
  "value": "ОК",
  "special": { "1": { "value": "OK" } }
}
```

There is deliberately no separate `en` dictionary: English is the base language
and lives in the code (the key *is* the English call-site text). For `en` — and
for any missing file — the dictionary is null, so rendering goes straight through
the English key.

## What makes up one language

| Artifact | en | ru (the model for a new language) |
|---|---|---|
| Natural-key dictionary of UI strings | — (the base: English text in the code, which is also the key) | `app/assets/l10n/ru/ui.json` |
| Overlay for the template's display text | — (the base: English text in `wizard_template.json`) | `app/assets/l10n/ru/template.json` (hand-written, the key is the English text) |
| Native Android strings | `app/android/app/src/main/res/values/strings.xml` | `.../res/values-ru/strings.xml` |
| Locale declaration for Android 13+ | — | `.../res/xml/locales_config.xml` |
| List of supported locales | — | `LocaleController.supportedTags` / `.supportedLocales` (`app/lib/services/l10n/locale_controller.dart`) |
| Entry in the language picker | — | `app/lib/screens/app_settings_screen/widgets/general_tab.dart` |

## Adding a new language (end to end)

Using `de` as the example:

1. **UI dictionary**: create `app/assets/l10n/de/ui.json` — one
   `{ "value": ... }` entry (a plain string, or a plural object holding every
   CLDR form for `de`) per English key that occurs in the code. `ui_check` prints
   the full list of keys (every “missing” is a key absent from the dictionary).
   The language directory `assets/l10n/<tag>/` is a directory asset in
   `pubspec.yaml`; `ru` is already declared there, but a new language `de` needs
   its own `assets/l10n/de/` entry in `pubspec.yaml` (otherwise `ui.json` and
   `template.json` never make it into the bundle).
   - **Plurals**: `value` is an object. The set of forms is dictated by the
     language's resolver. For a new language, add a `<Lang>PluralResolver` to
     `plural_resolver.dart` and wire it into
     `LocaleController._buildGetLocalText` (today: `ru → RuPluralResolver`,
     everything else → `EnPluralResolver`). `ui_check` verifies that the forms
     are complete against `resolver.forms`.
   - **Collisions**: if one English text has to be translated differently in
     different places, the code calls `getLocalText.s(N, "...")` at the differing
     site and the translation goes into `special["N"].value`. See below.
2. **Template overlay**: create `app/assets/l10n/de/template.json` — the same
   shape as the UI dictionary, keyed by the English text of the display field:
   ```json
   "Log level": { "value": "Protokollstufe" }
   ```
   The full key list is the set of display strings extracted from
   `wizard_template.json` (the node's English text is the key; English is the
   base language, so there is no separate en file); `template_check` reports the
   missing ones. The file reaches the bundle through the same
   `assets/l10n/de/` directory entry in `app/pubspec.yaml` from step 1 — a
   forgotten entry turns the Flutter test that loads the overlay from rootBundle
   red. Prohibited (enforced by CI): a `value` must not start with `@` (that
   would read as a var reference, since the overlay is applied before
   substitution) and must not contain `{`.
3. **Android**: `res/values-de/strings.xml` — a translation of every translatable
   key from `values/strings.xml` (`kotlin_check` verifies parity: the sets of
   keys and of `%n$s` placeholders must match). Wire values (channel IDs,
   actions, extras) are not kept in resources — they are not in strings.xml at
   all.
4. **Locale declaration**: `<locale android:name="de"/>` in
   `res/xml/locales_config.xml` (per-app language on Android 13+), plus `'de'` in
   `LocaleController.supportedTags` / `supportedLocales`.
5. **Picker**: an entry with the endonym (`Deutsch`) in `general_tab.dart` — the
   label deliberately does NOT come from the dictionary, because every language
   is labelled in itself (`// l10n-exempt: endonym`).
6. Run the gates: `flutter analyze && flutter test` plus all four checkers with
   `--strict` (see the README in tool/l10n).

No structural changes are required: `MaterialApp` reads
`LocaleController.supportedLocales`, the `TemplateLoader` cache is keyed by tag,
and the native resolver `L10n.kt` uses the tag from prefs as-is.

## A new UI string (Dart)

1. In the code: `getLocalText.s("English text")` (widgets, services, controllers
   — no BuildContext needed). Plurals use `getLocalText.plural("%d English", n)`
   with a printf `%d`. Arguments are either `%s`/`%d` in order or `%1$s`/`%2$d`
   with an explicit position. For stored errors and statuses use the typed
   `UiMsg` and call `render()` at display time (the machine-facing twin is
   `renderEn()`).
2. Translation: add an entry to `assets/l10n/ru/ui.json` under the same English
   text as the key, carrying the same set of placeholders (`ui_check` verifies
   the arity). A missing entry falls back to the English key; under `--strict`
   that is a **missing** and fails.
3. A hardcoded literal in a display position (including ternary and switch
   branches) will not pass CI — `hardcoded_check` runs with an empty baseline.
   `Text(getLocalText.s("..."))` is legal (the literal is an argument to
   getLocalText, not a direct argument to `Text`). Anything untranslatable (wire
   tags, units, endonyms) is marked with `// l10n-exempt: <reason>` on the
   literal's line or the line above.

An untranslated key (missing) and an orphan key (in the dictionary but not in the
code) both fail `ui_check --strict` (an AST scan of `getLocalText` call sites).

## Collisions (same en → different ru)

One English text sometimes has to be translated differently depending on where it
appears (for example `"OK"` as «ОК» in a dialog versus the Latin «OK» as a
technical term). The answer is **special forms**:

- the root `value` is form 0 (`getLocalText.s("OK")`);
- at the differing site the code calls `getLocalText.s(1, "OK")` and the
  translation goes into `special["1"].value`.

`ui_check` keeps this in sync: an index N used in the code must have a
`special["N"].value` (otherwise a **shape** failure), and a `special["N"]` that is
defined but never used is an **orphan-special** (a warning; a failure under
strict).

## Editing the English text

- **A UI string**: the English text is the key. Change the literal in the code and
  the key changes with it; the old entry in `ru.json` becomes an orphan (a
  `ui_check --strict` failure) and the new key is missing. Fix `ru.json`: rename
  the key, and revisit the translation if the meaning shifted.
- **The template** (display fields in `wizard_template.json`): the key is the
  English text itself (just like a UI string; English is the base, so there is no
  separate en file). Edit the text in the template and the key changes; there is
  no regeneration step — `template_check` extracts the keys from the template on
  every run. Changed text means a new key: the old entry in the locale file
  becomes an unknown key (a `template_check` failure) and the new key is missing
  (a warning; a failure under strict). Fix the locale file: rename the key, and
  revisit the translation if the meaning shifted — the same workflow as for a UI
  string.

## The baseline hotfix path (same-file replacement)

`hardcoded_baseline.json` is empty, but the rule stays in place for temporarily
grandfathered sites: the baseline gate forbids **growth** in a file's site count,
not changes to hashes. Rewording an existing literal (a typo, or renaming a
variable inside an interpolation — the hash is canonicalized, `${...}` → `{}`) is
legal: `dart run tool/l10n/hardcoded_check.dart --write-baseline` replaces the
hash and the file's counter does not grow. Only two things are forbidden: a site
appearing in a file that had none in the baseline, and the counter growing.

## `// l10n-exempt`

A targeted exclusion from the ratchet: a comment on the literal's line or the
line above, carrying a reason. Legitimate cases: wire tags shown verbatim
(`direct-out`), unit widgets (`'ms'`), endonyms in the language picker, protocol
terms. Not legitimate: “we'll translate it later”.

## What is never translated

Logs, Debug API responses, automation/Tasker payloads, `emitWarnings`, wire
values and tags, filenames, user data (channel labels and so on), and OS or core
payloads (diagnostic passthrough). Machine-facing surfaces render English through
`UiMsg.renderEn()` → `GetLocalText.en` (the allowlist lives in
`tool/l10n/render_allowlist.json`). Units (`B/KB/MB/GB`, `Mbps`, `ms`) and the
duration suffixes `d/h/m/s` stay Latin in every locale.
