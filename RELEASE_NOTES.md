# L×Box v2.8.1

Новая настройка **«Suspend idle tunnels»** — **радикально снижает нагрузку на
телефон, если в подписке много WireGuard/AmneziaWG-соединений**. Ядро усыпляет
недостижимые WG/AWG-туннели после простоя, освобождая память и снимая нагрузку с
CPU/батареи. Ядро обновлено до rc.18.

**Где включить:** **VPN Settings → вкладка System → секция Optimization →
Suspend idle tunnels**.

## ✨ Новое

### Suspend idle tunnels (§128 / §215)

**Где:** **VPN Settings → System → Optimization → Suspend idle tunnels**

| Порог | Что делает |
|---|---|
| Off (по умолчанию) | Фича выключена |
| 30 seconds / 2 minutes / 5 minutes | Усыпить туннель после стольки простоя |

Ядро гасит любой WG/AWG-эндпоинт, который **одновременно** недостижим из
активного маршрута **и** простаивает дольше порога. Пробуждение — мгновенное, на
следующем использовании. Активный туннель (тот, через который идёт трафик) не
трогается.

**Зачем — и почему эффект тем сильнее, чем больше WG.** Каждый живой
WireGuard-туннель держит приёмные буферы (~8 МБ на воркер), и сборщик мусора
постоянно их сканирует. Если в подписке **много WG-нод**, а трафик идёт лишь
через одну, остальные впустую держат десятки-сотни мегабайт памяти и **греют
процессор круглосуточно** — телефон садит батарею и нагревается на ровном месте.
Idle-suspend это убирает: чем больше у вас WG-соединений, тем радикальнее
выигрыш. На реальной подписке из 11 WG-нод — **освобождается ~130–155 МБ памяти,
а доля сборщика мусора в CPU падает с ~56 % почти до нуля** (см. Verified ниже).

## 🔬 Verified

- `flutter analyze` — **No issues found**; builder-тесты idle-suspend — **passed**.
- Ядро — **`v1.14.0-lx.1-rc.18`** (SPEC 020 idle-suspend). CommandClient API не менялся.
- **Device CPH2411 / Android 15, реальная подписка (11 WG-нод):**
  - недостижимые+простаивающие ноды усыпляются ровно по порогу (edge-triggered),
    активная (`route.final`) — никогда; пробуждение на дайле; kill-switch (`Off`)
    работает — тик не запускается.
  - **память:** приёмные буферы `223.9 → 89.9 МБ` (−134 МБ), при 9-нодном тесте — до −155 МБ.
  - **CPU:** доля сборщика мусора `~56 % → почти 0`; загрузка процесса ядра `~260 % → ~3 %`.
  - живой трафик активного туннеля не затронут.
